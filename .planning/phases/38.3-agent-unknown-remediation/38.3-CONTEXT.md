# Phase 38.3: AGENT-UNKNOWN Remediation - Context

**Gathered:** 2026-05-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Close audit gaps by guaranteeing non-null app identity fields across all audit events. Missing application identity is populated with an explicit `AGENT-UNKNOWN` sentinel (not `None` or omitted). A metric counter tracks AGENT-UNKNOWN frequency per interception path. The remediation path is documented externally.

This phase delivers AUDIT-05 (v0.7.1 Operational Hardening).

</domain>

<decisions>
## Implementation Decisions

### AGENT-UNKNOWN Sentinel Format
- **D-01:** When `source_application` or `destination_application` cannot be resolved, emit an explicit sentinel `AppIdentity` with `image_path: "AGENT-UNKNOWN"`, `publisher: "AGENT-UNKNOWN"`, `trust_tier: "unknown"`, `signature_state: "unknown"`. Do NOT use empty strings or `None`.
- **D-02:** Remove `#[serde(skip_serializing_if = "Option::is_none")]` from `source_application` and `destination_application` fields on `AuditEvent`. These fields must ALWAYS be present in the JSON output so auditors can guarantee non-null app identity fields.

### File Interception Applicability
- **D-03:** File interception (`run_event_loop`) currently only captures `application_path` (raw PID-to-path via `GetModuleFileNameExW`). For **BLOCK events only**, also resolve full `AppIdentity` (publisher + trust tier via `WinVerifyTrust`) and populate `source_application`. For **ACCESS events** (ALLOW, AllowWithLog), continue using `application_path` only — do not incur WinVerifyTrust overhead on the hot path.
- **D-04:** USB and disk block events are device-level enforcement, not app-to-app flows. Populate `source_application` with the AGENT-UNKNOWN sentinel (per D-01) since these paths do not attempt app identity resolution. The field is always present per D-02.

### Metric Counter Design
- **D-05:** Use in-memory `AtomicUsize` counters per interception path: `file_unknown_count`, `clipboard_unknown_count`, `usb_unknown_count`, `disk_unknown_count`, `chrome_unknown_count`.
- **D-06:** Flush counters to the audit log every 50 AGENT-UNKNOWN occurrences AND on graceful shutdown. The flush event uses `EventType::ConfigChange` with a structured summary in the `justification` field (e.g., `"AGENT-UNKNOWN:file=12,clipboard=3,usb=0,disk=0,chrome=0"`).
- **D-07:** Counters reset on agent restart. This is acceptable for v0.7.1 operational hardening.

### Remediation Path in Schema
- **D-08:** No schema change for remediation hints. The `AuditEvent` type does NOT gain a `remediation_hint` field.
- **D-09:** Remediation path documented in external admin docs and SIEM runbooks only. The AGENT-UNKNOWN sentinel is self-describing enough for auditors to identify the gap; they consult external docs for the fix.

### Claude's Discretion
- The exact flush interval (50 occurrences) and event type (`ConfigChange`) for metric flushing may be adjusted by the planner if a better pattern exists in the codebase.
- Whether to add a new `EventType::Metric` variant vs reusing `ConfigChange` is at planner discretion. `ConfigChange` is preferred to avoid enum expansion.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `dlp_common::AppIdentity` -- derives `Default`, `Serialize`, `Deserialize`. `#[serde(default)]` at struct level means missing JSON keys yield empty strings + Unknown tiers. Will be used to construct the AGENT-UNKNOWN sentinel.
- `AuditEvent::with_source_application()` / `with_destination_application()` -- builder methods for populating app identity fields.
- `audit_emitter::get_application_metadata(pid)` -- resolves raw image path from PID via `OpenProcess` + `GetModuleFileNameExW`. Used as the foundation for full `AppIdentity` resolution on file BLOCK events.
- `audit_emitter::TEST_CAPTURE_ENABLED` / `TEST_EVENT_SINK` -- test infrastructure for asserting on emitted audit events. New tests should use `enable_test_capture()` + `drain_test_events()`.

### Established Patterns
- `#[serde(skip_serializing_if = "Option::is_none")]` is used throughout `AuditEvent` for optional fields. Per D-02, this MUST be removed from `source_application` and `destination_application` only.
- File interception pipeline (`run_event_loop`) uses builder pattern: `AuditEvent::new(...).with_access_context(...).with_policy(...)` then `emit_audit(&ctx, &mut audit_event)`. New code should follow this pattern.
- USB/disk block events use `policy_name = Some("reason string")` and `policy_id = None` (per WR-03) to avoid misleading SIEM rules. Same pattern applies to AGENT-UNKNOWN sentinel events.
- Metric/telemetry patterns: `tracing::info!` with structured fields for operational metrics. No existing metrics module in the agent.

### Integration Points
- `AuditEvent` schema change affects all crates that serialize/deserialize it: `dlp-common` (source of truth), `dlp-agent` (emission), `dlp-server` (ingestion), `dlp-admin-cli` (display). Backward compatibility must be preserved for legacy audit logs.
- File BLOCK events in `run_event_loop` currently emit `AuditEvent::new(EventType::Block, ...)` then call `emit_audit()`. The AGENT-UNKNOWN sentinel must be injected here when `source_application` resolution fails.
- Clipboard alerts in `pipe3.rs` already populate `source_application`/`destination_application` from UI messages. When UI sends `None`, the agent must substitute the AGENT-UNKNOWN sentinel before emission.
- Chrome connector handler (`chrome/handler.rs`) currently uses `"AGENT-UNKNOWN"` as an `agent_id` fallback. This is unrelated to the app identity sentinel but confirms the string is already in use in the codebase.

</code_context>

<specifics>
## Specific Ideas

- The sentinel string `"AGENT-UNKNOWN"` is already used in `chrome/handler.rs` as an `agent_id` fallback. Reuse the same string constant for consistency.
- `AppIdentity::default()` produces empty strings + `Unknown` tiers. The AGENT-UNKNOWN sentinel is a deliberate override of the default, not a change to the default itself.
- Flush threshold of 50 occurrences is a heuristic. The planner may adjust based on expected event volume.
</specifics>
