# Phase 55.1: Code Review Report

**Reviewed:** 2026-06-20
**Depth:** standard
**Files Reviewed:** 2
**Status:** issues_found

## Summary

Phase 55.1 introduces a new `enforcement_mode` field on `CorrelatorConfig` and three `is_audit()` guards in the bypass correlator to suppress bypass alerts when the global enforcement mode is `Audit`. The implementation also propagates the mode from `AgentConfig.enforcement.global_mode` into the correlator at startup time in `service.rs`, and wires the DACL tripwire to respect the same mode.

The code is generally correct but contains one **critical** security-adjacent correctness issue, two **warnings** around maintainability and test coverage, and one **info** item about documentation drift.

## Critical Issues

### CR-01: `emit_audit_event` is NOT guarded by `is_audit()`, causing SIEM spam in Audit mode

**File:** `dlp-agent/src/bypass_correlator.rs:855`
**Issue:** `emit_alert` correctly suppresses the bypass alert and the `PendingAlert` batching when `is_audit()` is true, but it still unconditionally calls `self.emit_audit_event(reason, &event).await` at line 848. In Audit mode, the hook DLL returns ALLOW for all operations, so the absence of a journal entry is expected behavior -- not a bypass. Emitting `BypassAlertDetected` audit events to the SIEM in this case creates false-positive noise and violates the phase's intent of "suppressing bypass alerts in Audit mode."

The `emit_audit_event` call should be moved inside the `is_audit()` guard block, or `emit_audit_event` itself should check the mode before writing to the JSONL log.

**Fix:**
```rust
// In emit_alert, after the is_audit() guard:
if self.config.enforcement_mode.is_audit() {
    trace!(...);
    return;
}
// ... construct alert ...
let pending = PendingAlert::new(alert);
let mut batch = self.alert_batch.lock().await;
batch.push(pending);
// Only emit audit event when we are actually emitting a bypass alert:
self.emit_audit_event(reason, &event).await;
```

## Warnings

### WR-01: `emit_alert` is `async` but the `is_audit()` guard does not use `.await` -- yet the function is called from non-async contexts

**File:** `dlp-agent/src/bypass_correlator.rs:781`
**Issue:** `emit_alert` is declared `async fn`, but the `is_audit()` early-return path at line 785 does not `.await` anything. More importantly, the function is called from `handle_etw_event` (also async) which is fine, but there is a risk that future refactors might call `emit_alert` from a synchronous context. The current design is safe, but the `async` keyword on `emit_alert` is unnecessary since it only does `await` on `self.alert_batch.lock().await` and `self.emit_audit_event(...).await` -- both of which could be restructured. This is a minor maintainability concern, not a bug.

**Fix:** Keep as-is for now, but consider making `emit_alert` a synchronous method that pushes to a channel if the design evolves.

### WR-02: No test verifies that `emit_audit_event` is suppressed in Audit mode

**File:** `dlp-agent/src/bypass_correlator.rs:1836-1860`
**Issue:** The test `test_audit_mode_suppresses_emit_alert` only checks that the `alert_batch` is empty after calling `emit_alert` in Audit mode. It does NOT verify that `emit_audit_event` was also suppressed. Since `emit_audit_event` writes to a JSONL log via `crate::audit_emitter::emit`, and the test does not mock or capture the audit emitter, a regression where `emit_audit_event` continues firing in Audit mode would not be caught.

**Fix:** Extend the test to enable the test capture sink (as done in `test_emit_ntdll_patching_enabled_event` in service.rs) and assert that no `BypassAlertDetected` events were emitted:

```rust
#[tokio::test]
async fn test_audit_mode_suppresses_emit_alert() {
    crate::audit_emitter::enable_test_capture();
    // ... existing test body ...
    let events = crate::audit_emitter::drain_test_events();
    assert!(events.is_empty(), "emit_audit_event must be suppressed in Audit mode");
}
```

## Info

### IN-01: Doc comment on `CorrelatorConfig::enforcement_mode` is slightly misleading about "only Audit suppresses"

**File:** `dlp-agent/src/bypass_correlator.rs:94-96`
**Issue:** The doc comment says "Only Audit suppresses; PerPolicy, Block, and AuditAndBlock continue emitting alerts." This is true for the correlator's current behavior, but it is an implementation detail rather than a design invariant. If a future mode (e.g., `SilentBlock`) is added, the comment becomes a lie. The comment should describe the current behavior without making it sound like a permanent contract.

**Fix:**
```rust
    /// Phase 55.1: Global enforcement mode used to suppress bypass alerts in Audit mode.
    /// When the mode is `Audit`, the hook DLL returns ALLOW for all operations, so the
    /// absence of a journal entry is expected behavior and bypass alerts are suppressed.
    pub enforcement_mode: EnforcementMode,
```
