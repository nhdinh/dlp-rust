## 1. OpenCode Review

### 1.1 Plan 55.1-01: Structural Wiring

#### Summary
Clean, minimal structural plan. Adds `enforcement_mode: EnforcementMode` to `CorrelatorConfig`, wires `agent_config.enforcement.global_mode` through `service.rs`. Two tasks, one test, clear success criteria. No scope creep.

#### Strengths
- **Grounded in existing types** -- `EnforcementMode` already exists in `dlp_common::abac` with `is_audit()` method (line 433). No new enum or trait needed.
- **Correct dependency on `EnforcementConfig`** -- `EnforcementConfig` at `dlp-agent/src/config.rs:93` already has `global_mode: EnforcementMode` (default: `PerPolicy`). The plan's wiring matches the existing struct exactly.
- **Backward-compatible default** -- `CorrelatorConfig::default()` sets `Block`, which means `is_audit()` returns false, so no suppression in new tests or standalone construction. Safe.
- **Fits existing pattern** -- the `..Default::default()` override at the construction site (`service.rs:1617`) is the same pattern already used for `reduced_mode`.

#### Concerns
- **MEDIUM: Default mismatch between config types** -- `EnforcementConfig::default()` is `PerPolicy` (config.rs:107), but the plan proposes `CorrelatorConfig::default()` as `Block`. These differ semantically: `PerPolicy` means "defer to policy", while `Block` means "enforce". The service.rs wiring overrides it so production is correct, but the mismatch could confuse future maintainers who construct `CorrelatorConfig` directly. Consider using `EnforcementMode::default()` (which resolves to `Block` via `#[default]` at abac.rs:417) rather than hardcoding `EnforcementMode::Block`.
- **LOW: No `PerPolicy` guard test** -- The test `test_correlator_config_default_mode_is_block` confirms the default, but no test validates that `PerPolicy` is treated as non-suppressing (which is the default production config at `EnforcementConfig` level). If the guard logic is later refactored to use `!is_blocking()` instead of `is_audit()`, `PerPolicy` (which is not blocking) would start suppressing incorrectly. A `test_perpolicy_mode_allows_emit_alert` would lock in the invariant.
- **LOW: Import not explicitly from `dlp_common::abac`** -- the plan says "Import `dlp_common::abac::EnforcementMode`" -- confirm the re-export path. `EnforcementMode` lives at `dlp-common/src/abac.rs:412`, so the import would be `dlp_common::abac::EnforcementMode`. If the crate re-exports it at `dlp_common::EnforcementMode`, prefer that.

#### Suggestions
1. Add a unit test that proves `PerPolicy` does not suppress (alongside the 5 tests in plan 02).
2. Use `enforcement_mode: EnforcementMode::default()` in `CorrelatorConfig::default()` instead of `EnforcementMode::Block` to tie the default to the enum's `#[default]` and avoid drift.

#### Risk Assessment
**LOW** -- Self-contained, non-invasive, backward-compatible. The only risk is the default divergence (medium severity but low likelihood of causing harm since production always overrides).

### 1.2 Plan 55.1-02: Audit-Mode Suppression Guards

#### Summary
Adds three guard clauses at strategic layers of the correlator, plus 5 unit tests. Well-structured with clear rationale for each guard's placement. The `trace!` logging level is appropriate.

#### Strengths
- **Three-guard approach is correct, not overkill** -- Each guard covers a distinct entry path:
  - **Guard 1** (`handle_etw_event`): Efficiency -- avoids expensive journal discovery, QPC conversion, and path normalization that would be immediately discarded. Under heavy ETW event load, this is significant.
  - **Guard 2** (`submit_bypass_alert`): Covers the hook IPC path (separate code path, different call site). The hook DLL can still detect overwrites/patches and self-report even in Audit mode (it returns ALLOW but monitors integrity).
  - **Guard 3** (`emit_alert`): Final safety net -- catches any code path (current or future) that reaches the common alert construction/emission point.
  
  Having only guard 3 would waste correlation CPU in Audit mode. Having only guard 1 would miss the hook IPC path. The three layers provide both efficiency and correctness.

- **Guard placement is optimal** -- Guard 3 is at the very top of `emit_alert`, which is good -- it prevents any `BypassAlert` construction, batch push, AND `emit_audit_event` in one check. This keeps the code modification minimal.
- **`trace!` logging level** is correct -- suppression is expected behavior in Audit mode, not an error, warning, or notable event. `info!` would be too noisy for every suppressed event.
- **Test coverage is good** -- 5 tests cover Audit suppression (3 entry paths), Block allowance, and AuditAndBlock allowance. All three relevant `EnforcementMode` variants under the guard (`is_audit()` returns true for only `Audit`) are covered.

#### Concerns
- **MEDIUM: Missing `PerPolicy` test** -- Since `EnforcementConfig::default()` is `PerPolicy`, this is the most common production configuration. A test confirming `PerPolicy` does not suppress (i.e., alerts flow) is important for regression safety, especially since `PerPolicy` is explicitly not `Audit` but also not `Block`/`AuditAndBlock`. If someone later edits the guard condition to `!is_blocking()` instead of `is_audit()`, `PerPolicy` (returns false for `is_blocking()`) would start suppressing silently.
- **LOW: Guard 1 in `handle_etw_event`** -- The plan says to place the guard "after the allowlist check and before the on-demand journal discovery block." Currently `handle_etw_event` also has a WR-11 check (`nt_path_converted`) at the top. Consider placing the audit guard before WR-11 and allowlist checks for maximum efficiency. Practically this is noise (allowlist is a DashMap get -- ~100ns), but it keeps the guard pattern consistent: "if audit mode -> return immediately."
- **LOW: `submit_bypass_alert` guard should be before `alert.agent_id = self.agent_id.clone()` enrichment** -- The plan says "at the very top of the method before any enrichment or batch mutation." This correctly avoids wasted heap allocations (agent_id.clone(), format! for correlation_reason, etc.). Good.
- **LOW: No stress/perf test** -- The guard exists partly for efficiency under load, but no benchmark verifies that the early return meaningfully reduces CPU in Audit mode. Not a blocker for a gap-closure phase, but worth noting.

#### Suggestions
1. Add a 6th test: `test_perpolicy_mode_allows_emit_alert` -- same pattern as `test_block_mode_allows_emit_alert` with `EnforcementMode::PerPolicy`. This locks in the invariant for the default production config.
2. Consider placing the Audit guard in `handle_etw_event` immediately after `fn` entry (before WR-11 check) to make the short-circuit behavior maximally obvious to future readers.
3. Add a doc comment on `enforcement_mode` in `CorrelatorConfig` clarifying that only `Audit` suppresses (not `PerPolicy`, `Block`, `AuditAndBlock`), referencing D-04 and MODE-01.

#### Risk Assessment
**LOW** -- All three guards are pure synchronous checks (`match self.config.enforcement_mode { EnforcementMode::Audit => return, _ => {} }`). No new dependencies, no config parsing, no control flow restructuring. Tests provide solid coverage. The pattern is trivially revertable if wrong.

### 1.3 Cross-Plan Assessment

#### Dependency Ordering
Correct. Plan 01 must land first (the config field must exist before guards can read it). The plans are correctly marked `wave: 1` and `wave: 2` with `depends_on: ["01"]`.

#### Do the plans achieve the phase goal?
Yes. The MODE-01 gap requires suppressing all bypass alerts (both ETW-derived and hook-derived) when the global mode is Audit. The three guards cover:
- ETW-derived alerts: Guard 1 (`handle_etw_event` early return) + Guard 3 (`emit_alert` final safety net)
- Hook-derived alerts: Guard 2 (`submit_bypass_alert` early return)
- The `NoHookJournal` false-positive scenario described in the phase context: Guard 1 skips the journal discovery in Audit mode (no `emit_alert` call at all), Guard 3 catches any `emit_alert` call from any remaining path.

#### Re: correlator recreation pattern
The plan opts for static config at construction time (recreate on config change). This is the right choice:
- Dynamic mode updates require synchronization across the `DashMap` state, the `Arc<Mutex<Vec<PendingAlert>>>` batch, and the four spawned tasks. That's messy, error-prone, and not justified for a gap-closure.
- The existing pattern in `service.rs` already recreates the correlator on config changes.
- The current architecture doesn't have a live config update path for the correlator; introducing one would be scope creep.

#### Overall Risk
**LOW** -- Minimally invasive (2 files modified, ~25 lines of logic + tests), backward-compatible, no new dependencies, no behavioral change for `Block`/`AuditAndBlock`/`PerPolicy` modes. The plans correctly scope to the minimal fix for MODE-01 without over-engineering.

## 2. Claude CLI Review

### 2.1 Cross-Plan Assessment

#### Summary
Both plans present a sound, defense-in-depth approach to closing the MODE-01 gap. Plan 55.1-01 correctly identifies that `CorrelatorConfig` and `BypassCorrelator` must carry the global enforcement mode before any suppression logic can be added, and it preserves backward compatibility with a `Block` default. Plan 55.1-02 adds layered Audit-mode guards at the three natural emission boundaries (`handle_etw_event`, `submit_bypass_alert`, and `emit_alert`), which is more robust than guarding a single chokepoint because the bypass correlator currently appears to mutate state at multiple layers. The test matrix covers the three required suppression cases and the two allowance cases. Overall, the plans are well-scoped, security-aware, and aligned with the milestone audit finding.

#### Strengths
- **Defense-in-depth guard placement**: Guarding `handle_etw_event`, `submit_bypass_alert`, and `emit_alert` ensures that even if a future refactor bypasses one path, Audit-mode suppression still holds.
- **Backward-compatible default**: Defaulting `CorrelatorConfig.enforcement_mode` to `Block` prevents regression in existing deployments.
- **Correlator recreation pattern**: Snapshotting the mode at construction avoids subtle race conditions that would come with dynamic mode updates.
- **Clear threat model**: Each plan explicitly documents accepted and mitigated risks, including the accepted risk that Audit mode is operator-chosen monitoring behavior.
- **Explicit trace-level suppression logging**: Using `trace!` keeps expected monitoring-mode noise out of operator logs while still leaving an observability hook.
- **Scoped test coverage**: The five new unit tests map directly to the three suppression paths and the two non-Audit modes.

#### Concerns
- **MEDIUM -- `trace!` may be too quiet for security-relevant suppression**: Bypass suppression is expected in Audit mode, but it is still a security-relevant policy decision. If operators enable Audit mode for forensics and later wonder why no bypass alerts appeared, `trace!` may not be visible in normal log levels. Consider `debug!` with a stable, searchable message or a counter metric.
- **MEDIUM -- No test verifying service.rs wiring**: Plan 55.1-01 adds the field and claims the service test passes, but it does not add an explicit test that `agent_config.enforcement.global_mode` actually reaches `CorrelatorConfig`. If the struct literal is reordered or the `..Default::default()` fallback is used incorrectly, the default `Block` could silently mask a wiring regression.
- **LOW -- `emit_alert` guard may mask future logic bugs**: Guarding `emit_alert` is correct as a safety net, but if all future bypass paths are expected to flow through it, the earlier guards could make the `emit_alert` guard unreachable in unit tests. This is acceptable but should be documented so future maintainers do not assume the final guard is dead code.
- **LOW -- No integration/E2E coverage for config reload**: The recreation pattern is correct, but there is no test verifying that a policy/config reload actually reconstructs the correlator with the new mode. This is a gap in the "config changes recreate correlator" invariant.
- **LOW -- Threat model accepts admin tampering twice**: T-55.1-01 and T-55.1-06 are essentially the same accepted risk. Consolidating them would make the threat model cleaner.

#### Suggestions
- Add an explicit unit or integration test in Plan 55.1-01 that asserts the correlator constructed from a parsed `AgentConfig` with `global_mode = Audit` receives `EnforcementMode::Audit`.
- Consider adding a `debug!` or `info!` log line the first time an Audit-mode suppression guard fires per event path, or expose a counter (e.g., `bypass_alerts_suppressed_total{mode="audit"}`) so operators can observe suppression without drowning in `trace!` lines.
- Add a test in Plan 55.1-02 that confirms the `handle_etw_event` guard fires *before* journal discovery to justify the "efficiency" claim.
- Document why three guards are necessary in a short code comment near `emit_alert`, so future maintainers do not remove the safety net during refactoring.
- If `EnforcementMode` does not already implement `is_audit()` / `is_block()` helpers, add them as part of Plan 55.1-01 so the guards read cleanly.

#### Risk Assessment
**Overall Risk: LOW**

The plans correctly identify the root cause, sequence the work in the right dependency order (structural wiring before suppression logic), and apply multiple independent guards. The main residual risks are observability and wiring-test gaps, both of which are addressable within the existing scope. There is no evidence of scope creep or over-engineering; the three-guard strategy is justified by the correlator's multi-layered alert emission paths. With the suggested additional wiring and guard-order tests, this phase should close MODE-01 cleanly.
