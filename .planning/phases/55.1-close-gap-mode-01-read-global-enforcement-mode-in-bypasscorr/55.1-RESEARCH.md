# Phase 55.1: Close Gap MODE-01 - Read global_enforcement_mode in BypassCorrelator - Research

**Researched:** 2026-06-19
**Domain:** Rust enterprise DLP — bypass alert suppression in Audit global mode
**Confidence:** HIGH

## Summary

Phase 55.1 closes the MODE-01 gap identified in the v0.10.0 milestone audit: the `BypassCorrelator` in `dlp-agent/src/bypass_correlator.rs` does not read `global_enforcement_mode`, so Audit-mode bypass events still trigger false-positive alerts. In Audit mode, the hook DLL returns ALLOW for all operations (after journaling), so the hook journal will show the operation, and ETW correlation will find a match — producing no bypass alert. However, if the hook is not loaded (e.g., new process, injection race, or the hook DLL has been unloaded), the journal will not exist, and the correlator will emit a `NoHookJournal` alert. This is a false positive in Audit mode because the operator explicitly chose not to block, and the absence of a journal is expected behavior when the system is in monitoring mode.

The fix is to add `global_enforcement_mode` awareness to the `BypassCorrelator` and suppress all bypass alerts (both ETW-derived and hook-derived) when the global mode is `Audit`. The correlator is initialized in `dlp-agent/src/service.rs` at line 1615, where `CorrelatorConfig` is constructed. The `AgentConfig` already has `enforcement.global_mode: EnforcementMode` (from Phase 55). The correlator must receive this mode at construction time and check it before emitting any alert.

Two implementation approaches were considered:
- **Approach A** (defense in depth): Check `global_enforcement_mode` inside `emit_alert()` and `submit_bypass_alert()` — suppresses at the last moment, safest against future code paths.
- **Approach B** (efficiency): Check `global_enforcement_mode` in `handle_etw_event()` before correlation work — skips expensive journal discovery and correlation entirely in Audit mode.

The recommended approach is **Approach B with a guard in `submit_bypass_alert` as defense in depth**: skip correlation in `handle_etw_event` when mode is `Audit` (early return after allowlist check), and also guard `submit_bypass_alert` and `emit_alert` to suppress any alerts that might arrive via other paths (e.g., hook IPC). This is the most efficient and maintainable solution.

**Primary recommendation:** Add `enforcement_mode: EnforcementMode` to `CorrelatorConfig` and `BypassCorrelator`, pass `agent_config.enforcement.global_mode` at construction time in `service.rs`, and check `mode.is_audit()` in `handle_etw_event`, `emit_alert`, and `submit_bypass_alert` to suppress all bypass alerts in Audit mode.

### Pattern 3: Audit-Mode Guard in emit_alert (Defense in Depth)
**What:** Early return from `emit_alert` when `global_enforcement_mode == Audit`, suppressing any alert that reaches this method via an unexpected path.
**When to use:** Final safety net — ensures no bypass alert is ever emitted in Audit mode.
**Example:**

```rust
        trace!(

    // ... rest of existing alert construction ...
}
```

### Anti-Patterns to Avoid
- **Do NOT suppress only in `severity_for_alert`:** Returning `"info"` or `"none"` still creates an alert batch entry and audit event. The requirement is to suppress the alert entirely, not just downgrade severity. The Phase 55 D-04 decision says bypass severity is independent of policy mode, but the MODE-01 gap requires full suppression in Audit global mode.
- **Do NOT make the correlator dynamically update its mode:** The correlator is recreated on config changes (the `service.rs` pattern for `RunLoopContext`). Passing an `Arc<Atomic<EnforcementMode>>` adds unnecessary complexity. Just pass the mode at construction time.
- **Do NOT change the hook DLL:** The hook DLL already behaves correctly in Audit mode (returns ALLOW after journaling). The gap is purely in the correlator's alert emission logic.

## Common Pitfalls

### Pitfall 1: Suppressing Only ETW-Derived Alerts, Not Hook-Derived Alerts
**What goes wrong:** The fix only guards `handle_etw_event` but `submit_bypass_alert` (hook IPC path) still emits alerts in Audit mode, causing false positives from hook self-reported bypasses.
**Why it happens:** The hook DLL can send `BypassAlert` payloads over IPC (Phase 53/54). If the correlator's `run()` loop receives these and calls `submit_bypass_alert`, they will still be batched and flushed.
**How to avoid:** Guard BOTH `handle_etw_event` AND `submit_bypass_alert` (and `emit_alert` as final safety net).
**Warning signs:** Integration test shows bypass alerts in the batch even when `global_mode == Audit`.

### Pitfall 2: Forgetting to Suppress Audit Events in Audit Mode
**What goes wrong:** `emit_alert` constructs a `BypassAlert` and also calls `emit_audit_event`. Even if the alert is suppressed, the audit event might still be written to the local JSONL log, causing SIEM noise.
**Why it happens:** The guard is placed after `emit_audit_event` is called, or the audit event is emitted independently.
**How to avoid:** Place the guard at the very top of `emit_alert` (before any construction or audit emission). The `emit_audit_event` call is inside `emit_alert`, so guarding `emit_alert` covers both.
**Warning signs:** SIEM receives `BypassAlertDetected` events while in Audit mode.

### Pitfall 3: Not Passing the Mode at Correlator Construction
**What goes wrong:** The correlator defaults to `Block` mode and never receives the actual `global_mode`, so alerts are never suppressed.
**Why it happens:** `service.rs` constructs `CorrelatorConfig` with `..Default::default()` and the new `enforcement_mode` field defaults to `Block` (for backward compatibility).
**How to avoid:** Explicitly pass `agent_config.enforcement.global_mode` in the `CorrelatorConfig` constructor in `service.rs` at line 1615.
**Warning signs:** Unit tests pass (they construct the correlator directly with `Audit` mode) but production still emits alerts.

### Pitfall 4: Breaking Backward Compatibility
**What goes wrong:** Existing `CorrelatorConfig::default()` returns `Block` for the new `enforcement_mode` field, which is correct for production, but tests that construct `CorrelatorConfig::default()` and expect Audit-mode behavior will fail.
**Why it happens:** The default for `enforcement_mode` must be `Block` (not `Audit`) to preserve existing behavior for users who don't set the mode. Tests that need Audit mode must explicitly set it.
**How to avoid:** Use `#[serde(default)]` or `Default` impl that sets `enforcement_mode: EnforcementMode::Block`. Update any tests that expect Audit-mode suppression to explicitly construct the config with `Audit`.
**Warning signs:** Tests that previously passed now fail because the default changed.

### Pitfall 5: Confusing "Policy Mode" with "Global Enforcement Mode"
**What goes wrong:** The Phase 55 D-04 decision says "bypass alert severity is independent of policy mode." A developer might read this and think the MODE-01 gap is not a real gap.
**Why it happens:** D-04 refers to *per-policy* enforcement mode (the mode on an individual policy). The MODE-01 gap is about the *global* enforcement mode (`global_enforcement_mode = Audit`), which overrides all policies. In Audit global mode, the entire system is in monitoring mode, and bypass alerts are false positives.
**How to avoid:** The fix checks `global_enforcement_mode` (from `AgentConfig.enforcement.global_mode`), NOT the per-policy `enforcement_mode`. The severity mapping remains independent of per-policy mode, but alert *emission* is gated by global mode.
**Warning signs:** Code comments or PR description conflates "policy mode" and "global mode."

## Open Questions

1. **Should the correlator log at `trace!` or `debug!` level when suppressing an alert?**
   - What we know: The suppression is expected behavior in Audit mode, not an error.
   - What's unclear: Whether operators want visibility in logs that bypass alerts were suppressed.
   - Recommendation: Use `trace!` for per-event suppression (high volume) and `debug!` once at correlator startup when mode is Audit. This matches the existing pattern in `handle_etw_event` which uses `warn!` for skipped events.

2. **Should `AuditAndBlock` mode also suppress bypass alerts?**
   - What we know: `AuditAndBlock` mode blocks AND audits. Bypass alerts indicate real evasion attempts.
   - What's unclear: Whether the operator expects bypass alerts in `AuditAndBlock` mode.
   - Recommendation: NO — only `Audit` mode suppresses bypass alerts. `AuditAndBlock` and `Block` mode should continue emitting bypass alerts. This is consistent with the Phase 55 D-04 decision that bypass alerts are independent of policy mode; the suppression is only for pure Audit (monitor-only) mode.

3. **Should the `emit_audit_event` call also be suppressed?**
   - What we know: `emit_alert` calls `emit_audit_event` which writes to the local JSONL log.
   - What's unclear: Whether SIEM should still see bypass audit events in Audit mode (for forensics) even if alerts are suppressed.
   - Recommendation: YES — suppress both the alert and the audit event. In Audit mode, the operator is explicitly monitoring, and bypass "detections" are false positives (the hook is not loaded, which is expected in monitor mode). If the operator wants forensics, they should use `AuditAndBlock` mode. The milestone audit says "Audit mode still produces alerts" — this includes audit events.
