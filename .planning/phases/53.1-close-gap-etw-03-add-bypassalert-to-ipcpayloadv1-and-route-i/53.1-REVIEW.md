# Phase 53.1: Code Review Report

**Reviewed:** 2026-06-18
**Depth:** standard
**Files Reviewed:** 4
**Status:** issues_found

## Summary

This phase adds `BypassAlert` to the IPC protocol envelope (`IpcPayloadV1`), implements agent-side routing of bypass alerts to a correlator channel, and updates the hook DLL's `emit_bypass_alert` to use envelope-wrapped serialization with a new fire-and-send (`send_raw_oneway`) pipe helper. Volume class query/response variants were also added to the protocol.

The implementation is structurally sound but contains several correctness and security issues: a hardcoded protocol version that contradicts documentation, silent error swallowing on security-critical paths, debug print leakage, unsafe pointer casts without layout guarantees, and missing response handling for certain envelope variants that could cause client deadlocks.

## Critical Issues

### CR-01: `emit_bypass_alert` silently zeroes timestamp on clock skew

**File:** `dlp-hook-dll/src/ntdll_patcher.rs:684-687`
**Issue:** `SystemTime::now().duration_since(UNIX_EPOCH).unwrap_or_default().as_secs()` returns `0` if the system clock is before the Unix epoch. For a security alert, a zero timestamp destroys forensic correlation and SIEM timeline accuracy. This is a data integrity issue on security telemetry.
**Fix:**
```rust
let now = std::time::SystemTime::now()
    .duration_since(std::time::UNIX_EPOCH)
    .expect("system clock before Unix epoch");
```
Or propagate the error and log via `debug_log` if clock skew is a concern.

### CR-02: `eprintln!` debug print in `connect_pipe` violates project logging standards

**File:** `dlp-hook-dll/src/pipe_client.rs:197`
**Issue:** The project CLAUDE.md (sections 9.13, 9.14) mandates: "NEVER commit debug `println!` statements" and "When reporting errors to the console, use `tracing::error!` instead of `println!`". The `eprintln!` in `connect_pipe` leaks debug output to stderr in production and could expose pipe names or Win32 error codes. This is a security hygiene violation.
**Fix:** Remove the `eprintln!` line entirely, or replace with `crate::debug_log` if diagnostic output is needed.

### CR-03: `build_bypass_alert_envelope` hardcodes `version: 1` contradicting Phase 53 spec

**File:** `dlp-hook-dll/src/ntdll_patcher.rs:664`
**Issue:** The `BypassAlert` doc comment in `dlp-common/src/hook_ipc.rs:207` explicitly states: "Protocol version — set to 2 for Phase 53 alerts; set to 1 for Phase 51 alerts." This is a Phase 53 implementation, yet `build_bypass_alert_envelope` hardcodes `version: 1`. This creates a protocol version mismatch that downstream consumers (bypass correlator, SIEM) may use to distinguish alert capabilities.
**Fix:**
```rust
version: 2, // Phase 53 alert with ETW correlation fields
```

### CR-04: `send_raw_oneway` silently discards `SetNamedPipeHandleState` errors

**File:** `dlp-hook-dll/src/pipe_client.rs:158-162`
**Issue:** `let _ = SetNamedPipeHandleState(pipe, Some(&mode), None, None);` silently ignores errors. If the pipe mode cannot be set to `PIPE_READMODE_MESSAGE`, the subsequent `write_frame` may write in byte mode, causing frame boundary confusion on the server side. This could lead to malformed frames or desynchronization.
**Fix:**
```rust
unsafe {
    let mode = PIPE_READMODE_MESSAGE;
    if let Err(e) = SetNamedPipeHandleState(pipe, Some(&mode), None, None) {
        let _ = CloseHandle(pipe);
        return Err(PipeError::Win32((e.code().0 as u32) & 0xFFFF));
    }
}
```

### CR-05: Agent `handle_connection` never sends responses for non-Request envelope variants

**File:** `dlp-agent/src/hook_ipc.rs:337-359`
**Issue:** For `BypassAlert`, `VolumeClassQuery`, `VolumeClassResponse`, and `Response` payload variants, the server reads the frame but never writes a response back to the pipe. While `send_raw_oneway` (used by the current hook DLL) does not wait for a response, the protocol design does not guarantee that all clients will use oneway sends. A client using `send_request` or `send_raw_request` for a `VolumeClassQuery` will deadlock waiting for a response that never arrives. Additionally, the `VolumeClassQuery` path has a TODO but no placeholder response, violating the principle that every request should receive a response or an explicit disconnect.
**Fix:** For `VolumeClassQuery`, send a `VolumeClassResponse { class: None }` fail-closed response. For `BypassAlert`, the protocol should either (a) define a minimal acknowledgment response, or (b) document that this payload must only be sent via oneway. For `VolumeClassResponse` and `Response` (unexpected from client), send an error response or disconnect explicitly.

### CR-06: `CacheAccessor` impl uses unsafe pointer cast without `#[repr(C)]` guarantee

**File:** `dlp-agent/src/hook_ipc.rs:65-76`
**Issue:** The implementation casts `&ClassificationCache` to `*const CacheHeader` via `unsafe { &*(self as *const _ as *const crate::classification_cache::CacheHeader) }`. Unless `ClassificationCache` is `#[repr(C)]` and `CacheHeader` is its first field with guaranteed layout, this is undefined behavior. The "SAFETY" comment does not justify the layout invariant. A future compiler or struct reordering could break this.
**Fix:** Either (a) ensure `ClassificationCache` is `#[repr(C)]` with `CacheHeader` as the first field and document the invariant, or (b) use a safe accessor method on `ClassificationCache` that returns the version.

## Warnings

### WR-01: `emit_bypass_alert` silently drops bincode serialization failures

**File:** `dlp-hook-dll/src/ntdll_patcher.rs:690`
**Issue:** `if let Ok(payload) = bincode::serialize(&envelope)` silently drops the alert if serialization fails. For a security alert, this is a data loss risk. The error should be logged.
**Fix:**
```rust
match bincode::serialize(&envelope) {
    Ok(payload) => { let _ = crate::pipe_client::send_raw_oneway(...); }
    Err(e) => {
        let msg = format!("[dlp-hook] BypassAlert serialization failed: {:?}", e);
        crate::debug_log(&msg);
    }
}
```

### WR-02: `test_handle_connection_routes_bypass_alert` is a no-op test

**File:** `dlp-agent/src/hook_ipc.rs:1002-1039`
**Issue:** The test creates a bypass channel, builds an envelope, and then discards everything with `let _ = (...)`. It never actually calls `handle_connection` with a real pipe, so it provides zero runtime coverage of the alert routing logic. The comment even admits this: "We can't easily mock a pipe here, so we verify the function signature compiles."
**Fix:** Either implement a real pipe-based test (using `start_mock_server` and a client that sends the envelope), or remove the test and replace with an integration test. A compile-time signature check is not a unit test.

### WR-03: `send_raw_oneway` hardcodes 50ms connection timeout without justification

**File:** `dlp-hook-dll/src/pipe_client.rs:155`
**Issue:** `const CONNECT_TIMEOUT_MS: u32 = 50;` is arbitrary and may be too short for systems under heavy load. The hook DLL is in the hot path of file operations; a timeout here could cause alert loss.
**Fix:** Document the rationale (e.g., "50ms is a best-effort budget to avoid blocking the hooked thread") or make it a configurable parameter with a default.

### WR-04: `build_bypass_alert_envelope` populates ETW correlation fields with empty placeholders

**File:** `dlp-hook-dll/src/ntdll_patcher.rs:658-677`
**Issue:** Fields `agent_id`, `image_path`, `file_path`, `operation`, `severity`, `correlation_reason` are all hardcoded to empty strings or zeros. The doc comment says this is a "pure helper" but these fields are critical for SIEM correlation. The function should either accept these as parameters or document that callers must populate them.
**Fix:** Add parameters for the populated fields, or add a `// TODO(Phase-53-followup): populate ETW correlation fields` comment.

### WR-05: `is_target_in_our_trampoline_range` false positive when trampolines are null

**File:** `dlp-hook-dll/src/ntdll_patcher.rs:617-621`
**Issue:** If all four trampoline function pointers are null (e.g., in a test or corrupted binary), `min = 0`, `max = 0`, and with the 16KB margin, any target from `0` to `16384` would be considered "in range". This is a false positive that could mark a stub as `Clean` when it is actually corrupted.
**Fix:**
```rust
if min == 0 && max == 0 {
    return false; // All trampolines null — cannot verify
}
```

### WR-06: `BypassAlert` serde default for `version` is `0` but spec says `1` or `2`

**File:** `dlp-common/src/hook_ipc.rs:208-209`
**Issue:** `#[serde(default)]` on `version: u32` means a missing field deserializes to `0`. The documentation says version should be `1` (Phase 51) or `2` (Phase 53). `0` is not a valid protocol version per the spec. This could confuse downstream consumers.
**Fix:** Use `#[serde(default = "default_alert_version")]` with a function returning `1` (or `2`), or change the field type to an enum.

### WR-07: `accept_loop` has identical code in both Tokio and non-Tokio branches

**File:** `dlp-agent/src/hook_ipc.rs:276-295`
**Issue:** The `Some(ref _h)` and `None` branches are identical. The comment says "Synchronous handling (same as no-runtime path)" which means the Tokio runtime detection is dead code duplication. This is a maintenance hazard.
**Fix:** Remove the `match rt` and handle both cases uniformly, or actually offload to `spawn_blocking` when a runtime is present.

### WR-08: `find_hook_descriptor` returns raw mutable pointer without `unsafe` marker

**File:** `dlp-hook-dll/src/ntdll_patcher.rs:563`
**Issue:** The function returns `Option<*mut crate::HookDescriptor>` and internally performs `hook as *const _ as *mut _`, yet the function is not marked `unsafe`. While callers must use `unsafe` to dereference, the function itself performs an unsafe cast that could violate aliasing rules. By Rust convention, functions that perform unsafe operations should be marked `unsafe` if their safe use depends on invariants.
**Fix:** Mark the function `unsafe` and document the invariant that the returned pointer is valid only for the lifetime of the `HOOKS` array.

### WR-09: `get_detour_trampoline` holds mutex guard across `trampoline()` call

**File:** `dlp-hook-dll/src/ntdll_patcher.rs:523-525`
**Issue:** `let guard = DETOURS.lock(); guard[idx].as_ref().map(|d| d.trampoline() as *const ())` holds the `parking_lot::Mutex` guard while calling `trampoline()`. While `parking_lot` is efficient, this is unnecessary lock contention. The trampoline pointer can be copied out first.
**Fix:**
```rust
fn get_detour_trampoline(fn_name: &str) -> Option<*const ()> {
    let idx = stub_name_from_str(fn_name)?.index();
    let guard = DETOURS.lock();
    let ptr = guard[idx].as_ref().map(|d| d.trampoline() as *const ());
    ptr
}
```
(Actually the current code is already minimal; this is a minor style note.)

### WR-10: `BypassAlert` `image_sha256` field uses `Option<String>` without length validation

**File:** `dlp-common/src/hook_ipc.rs:218`
**Issue:** The `image_sha256` field is `Option<String>` with no validation. A malformed or excessively long string could be injected. While bincode has a 64MiB frame limit, there's no per-field validation.
**Fix:** Consider using a fixed-size array `[u8; 32]` for the raw hash and hex-encoding at display time, or add validation in the deserialization path.
