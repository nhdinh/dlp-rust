# Phase 53.1: Code Review Report

**Reviewed:** 2026-06-18
**Depth:** standard
**Files Reviewed:** 4
**Status:** issues_found

## Summary

This review covers the Phase 53.1 implementation that adds `BypassAlert` to `IpcPayloadV1` and routes it through the named-pipe IPC path. The changes span the agent-side pipe server (`dlp-agent/src/hook_ipc.rs`), shared protocol types (`dlp-common/src/hook_ipc.rs`), the hook DLL patcher (`dlp-hook-dll/src/ntdll_patcher.rs`), and the hook DLL pipe client (`dlp-hook-dll/src/pipe_client.rs`).

One critical issue was found: a test assertion in `ntdll_patcher.rs` checks for `version: 1` when the production code explicitly sets `version: 2` for Phase 53 alerts. Two warnings concern an unused `tokio::runtime::Handle` parameter and a potential race condition in `send_raw_oneway`. Two info-level items note a TODO comment and a test-only assertion.

## Critical Issues

### CR-01: Test Assertion Mismatches Production Code — `version` Field

**File:** `dlp-hook-dll/src/ntdll_patcher.rs:765`
**Issue:** The `test_build_bypass_alert_envelope` test asserts `alert.version == 1` at line 765, but `build_bypass_alert_envelope` at line 674 unconditionally sets `version: 2`. This means the test will **fail at runtime** or, if it currently passes, the production code has been changed without updating the test. Either way, the test does not validate the actual production behavior, making it a broken safety net.

**Fix:** Update the test assertion to match the production value:
```rust
assert_eq!(alert.version, 2);
```

## Warnings

### WR-01: Unused `_rt` Parameter in `accept_loop`

**File:** `dlp-agent/src/hook_ipc.rs:252`
**Issue:** The `accept_loop` function accepts `_rt: Option<tokio::runtime::Handle>` but never uses it. The doc comment on `run` (lines 197–206) explicitly states that "each accepted connection is off-loaded to `tokio::task::spawn_blocking`" when a Tokio runtime is present, but the actual implementation does not spawn any tasks — it handles connections synchronously on the accept thread. This is a documentation/implementation mismatch that could mislead callers into believing the server is non-blocking under Tokio.

**Fix:** Either:
1. Remove the `_rt` parameter and update the doc comment to reflect the actual blocking behavior, OR
2. Actually use the runtime handle to spawn connection handlers in `tokio::task::spawn_blocking` as documented.

### WR-02: `send_raw_oneway` Does Not Verify Write Completeness

**File:** `dlp-hook-dll/src/pipe_client.rs:170–176`
**Issue:** `send_raw_oneway` calls `write_frame` (which internally calls `write_all`) and then immediately closes the handle. However, `WriteFile` on a named pipe with `PIPE_TYPE_MESSAGE` mode may buffer data internally. Closing the handle immediately after `write_frame` returns could truncate the message if the pipe server's read side has not yet consumed the bytes, especially under high load or when the pipe buffer is full. The fire-and-send pattern is documented as intentional, but there is no `FlushFileBuffers` call to ensure the bytes have left the client-side buffer.

**Fix:** Add a `FlushFileBuffers` call before `CloseHandle` in `send_raw_oneway`, or document the truncation risk explicitly if it is acceptable:
```rust
// After write_frame succeeds:
unsafe { windows::Win32::Storage::FileSystem::FlushFileBuffers(pipe).ok(); }
let _ = unsafe { CloseHandle(pipe) };
```

## Info

### IN-01: TODO Comment in Production Helper

**File:** `dlp-hook-dll/src/ntdll_patcher.rs:667–668`
**Issue:** `build_bypass_alert_envelope` contains a `TODO(Phase-53-followup)` comment indicating that ETW correlation fields are not yet populated. While TODOs are not inherently bugs, this one leaves a production function producing alerts with empty `agent_id`, `image_path`, `file_path`, `operation`, `severity`, and `correlation_reason` fields. The alert will reach the bypass correlator but with minimal forensic value.

**Fix:** Either populate the fields now (if the data is available in the caller context) or file a follow-up issue and reference it in the comment.

### IN-02: Test Uses `unwrap_or_default()` for Timestamp Instead of `expect`

**File:** `dlp-hook-dll/src/ntdll_patcher.rs:750`
**Issue:** In `test_build_bypass_alert_envelope`, the timestamp is computed with:
```rust
.duration_since(std::time::UNIX_EPOCH)
.unwrap_or_default()
```
This silently swallows a system-clock-before-Unix-epoch error and produces `0`, which could mask test environment issues. The production code in `emit_bypass_alert` (line 697) correctly uses `.expect("system clock before Unix epoch")`.

**Fix:** Align the test with production behavior:
```rust
.expect("system clock before Unix epoch")
```
