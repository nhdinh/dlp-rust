# Phase 53.1: Close gap ETW-03 — add BypassAlert to IpcPayloadV1 and route in agent hook_ipc

**Researched:** 2026-06-17
**Domain:** Rust IPC protocol evolution, named-pipe framing, agent-side message routing
**Confidence:** HIGH

## Summary

This phase closes integration blocker INT-BLOCK-01 from the v0.10.0 milestone audit. The hook DLL (Phase 51) already emits `BypassAlert` frames over the named pipe to the agent, but the agent's `handle_connection` in `dlp-agent/src/hook_ipc.rs` unconditionally deserializes every frame as `HookRequest` via `bincode::deserialize`. The `IpcPayloadV1` enum in `dlp-common/src/hook_ipc.rs` has no `BypassAlert` variant, so any bypass alert from the hook DLL fails deserialization and is silently dropped.

The fix is a three-crate coordinated change: (1) extend `IpcPayloadV1` with a `BypassAlert(BypassAlert)` variant in `dlp-common`, (2) update `dlp-agent/src/hook_ipc.rs` to deserialize into `IpcEnvelope`/`IpcPayloadV1` and route `BypassAlert` payloads to the bypass correlator instead of the ABAC handler, and (3) ensure the hook DLL's `emit_bypass_alert` in `ntdll_patcher.rs` wraps the alert in the proper `IpcEnvelope::V1` envelope before serialization.

The `BypassAlert` struct already exists in `dlp-common/src/hook_ipc.rs` (added in Phase 53 Plan 04) with all v2 fields and `#[serde(default)]` backward compatibility. The bypass correlator in `dlp-agent/src/bypass_correlator.rs` already has an `emit_alert` method that constructs `BypassAlert` from ETW events; the new requirement is to add an entry point that accepts hook-derived `BypassAlert` directly (self-reported bypass) without requiring ETW correlation.

**Primary recommendation:** Add `BypassAlert(BypassAlert)` to `IpcPayloadV1`, update agent `handle_connection` to match on the payload variant, route bypass alerts to a new `bypass_correlator::submit_bypass_alert()` entry point, and update the hook DLL's `emit_bypass_alert` to wrap in `IpcEnvelope::V1`. Add round-trip unit tests in `dlp-common` and routing tests in `dlp-agent`.

### Pattern 1: Versioned IPC Envelope with Variant Discrimination
**What:** All IPC messages are wrapped in `IpcEnvelope::V1(IpcMessageV1 { payload: IpcPayloadV1::... })`. The agent deserializes the envelope, then matches on the payload variant to route to the correct handler.
**When to use:** Any time the hook DLL needs to send a new message type to the agent. This preserves protocol versioning and backward compatibility.
**Example:**
```rust
// Source: dlp-common/src/hook_ipc.rs (existing pattern)
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub enum IpcPayloadV1 {
    Request(HookRequest),
    Response(HookResponse),
    VolumeClassQuery(VolumeClassQuery),
    VolumeClassResponse(VolumeClassResponse),
    // NEW: BypassAlert(BypassAlert),  // <-- Phase 53.1 addition
}
```

### Pattern 2: Synchronous Pipe Handler -> Async Correlator Channel
**What:** The pipe handler `handle_connection` runs synchronously (blocking read). When a `BypassAlert` arrives, it must be handed off to the async `BypassCorrelator` task without blocking the pipe loop.
**When to use:** Any time a synchronous IPC handler needs to feed an async consumer.
**Example:**
```rust
// Source: dlp-agent/src/hook_ipc.rs (proposed pattern)
use crossbeam_channel::Sender;

fn handle_connection(
    pipe: HANDLE,
    handler: &HookHandler,
    bypass_tx: &Sender<BypassAlert>,  // NEW: channel to correlator
) -> Result<()> {
    loop {
        let frame = read_frame(pipe)?;
        let envelope: IpcEnvelope = bincode::deserialize(&frame)?;
        match envelope {
            IpcEnvelope::V1(msg) => match msg.payload {
                IpcPayloadV1::Request(req) => {
                    let resp = handler(req);
                    let payload = bincode::serialize(&resp)?;
                    write_frame(pipe, &payload)?;
                }
                IpcPayloadV1::BypassAlert(alert) => {
                    bypass_tx.send(alert).ok();  // best-effort, non-blocking
                }
                // ... other variants
            }
        }
    }
}
```

### Anti-Patterns to Avoid
- **Deserializing every frame as HookRequest:** This is the current bug. The agent must deserialize into `IpcEnvelope` first, then discriminate.
- **Sending raw BypassAlert without envelope:** The hook DLL must wrap in `IpcEnvelope::V1` so the agent can version-match and route correctly.
- **Blocking the pipe loop on correlator flush:** Bypass alerts must be sent via a channel, not by directly calling async `flush_batch`.

## Common Pitfalls

### Pitfall 1: Hook DLL Sends Raw BypassAlert (Not Wrapped in Envelope)
**What goes wrong:** If the hook DLL serializes `BypassAlert` directly (not inside `IpcEnvelope::V1`), the agent's `bincode::deserialize::<IpcEnvelope>` will fail with a deserialization error, and the alert is silently dropped.
**Why it happens:** The existing `emit_bypass_alert` in `ntdll_patcher.rs` does `bincode::serialize(&alert)` directly (line 651). It must be updated to wrap in the envelope.
**How to avoid:** Update `emit_bypass_alert` to construct `IpcEnvelope::V1(IpcMessageV1 { payload: IpcPayloadV1::BypassAlert(alert) })` before serialization.
**Warning signs:** Unit test `bypass_alert_roundtrip_through_envelope` will fail if the hook side is wrong.

### Pitfall 2: Agent Deserializes as HookRequest (Not Envelope)
**What goes wrong:** If `handle_connection` continues to do `bincode::deserialize::<HookRequest>(&frame)`, bypass alerts will fail deserialization and be logged as "malformed request".
**Why it happens:** Current code at line 265 of `dlp-agent/src/hook_ipc.rs` does exactly this.
**How to avoid:** Change deserialization target to `IpcEnvelope`, then match on `IpcPayloadV1::Request` vs `IpcPayloadV1::BypassAlert`.
**Warning signs:** Unit test `handle_connection_routes_bypass_alert` will fail.

### Pitfall 3: Bypass Alert Channel Backpressure Blocks Pipe Loop
**What goes wrong:** If `handle_connection` calls an async method directly (e.g., `correlator.emit_alert().await`), the synchronous pipe loop will block, breaking hook DLL latency guarantees.
**Why it happens:** `handle_connection` is a synchronous function running in a blocking thread. It cannot `.await`.
**How to avoid:** Use a `crossbeam_channel::Sender<BypassAlert>` to hand off the alert to the correlator's async task. The send is non-blocking (bounded channel with `try_send` or unbounded channel).
**Warning signs:** Hook DLL pipe round-trip latency will spike in benchmark tests.

### Pitfall 4: BypassCorrelator Has No Entry Point for Hook-Derived Alerts
**What goes wrong:** The existing `BypassCorrelator` only consumes ETW events via `handle_etw_event`. It has no method to accept a pre-constructed `BypassAlert` from the hook DLL.
**Why it happens:** The correlator was designed for ETW->journal correlation, not for hook self-reporting.
**How to avoid:** Add a `submit_bypass_alert(&self, alert: BypassAlert)` method that wraps the alert in `PendingAlert` and pushes it to the batch, bypassing the ETW correlation logic.
**Warning signs:** Integration test "hook-emitted alert reaches server" will fail.

### Agent Routing Logic
```rust
// Source: dlp-agent/src/hook_ipc.rs (proposed change)
fn handle_connection(
    pipe: HANDLE,
    handler: &HookHandler,
    bypass_tx: &crossbeam_channel::Sender<BypassAlert>,
) -> Result<()> {
    loop {
        let frame = match read_frame(pipe) {
            Ok(f) => f,
            Err(e) => { debug!(error = %e, "read error"); break; }
        };

        let envelope: IpcEnvelope = match bincode::deserialize(&frame) {
            Ok(e) => e,
            Err(e) => {
                warn!(error = %e, "malformed envelope");
                continue;
            }
        };

        match envelope {
            IpcEnvelope::V1(msg) => match msg.payload {
                IpcPayloadV1::Request(req) => {
                    let response = handler(req);
                    let payload = bincode::serialize(&response)?;
                    write_frame(pipe, &payload)?;
                }
                IpcPayloadV1::BypassAlert(alert) => {
                    if let Err(e) = bypass_tx.send(alert) {
                        warn!(error = %e, "bypass alert channel closed");
                    }
                }
                IpcPayloadV1::VolumeClassQuery(query) => {
                    // existing logic
                }
                IpcPayloadV1::VolumeClassResponse(resp) => {
                    // hook DLL should never send this; log and drop
                    warn!("unexpected VolumeClassResponse from hook DLL");
                }
            }
        }
    }
    Ok(())
}
```

### BypassCorrelator Entry Point for Hook-Derived Alerts
```rust
// Source: dlp-agent/src/bypass_correlator.rs (proposed addition)
impl BypassCorrelator {
    /// Accepts a hook-derived bypass alert directly (self-reported).
    ///
    /// Unlike `handle_etw_event`, this does NOT perform journal correlation.
    /// The hook DLL is self-reporting a bypass (e.g., EDR overwrite, patch race).
    /// The alert is batched and flushed to the server like ETW-derived alerts.
    pub async fn submit_bypass_alert(&self, alert: BypassAlert) {
        let pending = PendingAlert::new(alert);
        let mut batch = self.alert_batch.lock().await;
        batch.push(pending);
        // Batch flush task will pick it up on next interval.
    }
}
```

## Open Questions (RESOLVED)

1. **RESOLVED: Should the hook DLL set `version=2` or `version=1` for self-reported alerts?**
   - Decision: Keep `version=1` for hook self-reported alerts (they are structurally simpler — no ETW correlation fields). The agent correlator will treat them as `BypassReason::HookOverwritten` or `PatchRaced` and compute severity accordingly.
   - Implemented in: Plan 53.1-03 Task 1.

2. **RESOLVED: How does the bypass correlator distinguish ETW-derived vs hook-derived alerts?**
   - Decision: `submit_bypass_alert` bypasses the ETW correlation logic entirely and just batches the alert. The existing `severity_for_alert` method already handles all `BypassReason` variants correctly.
   - Implemented in: Plan 53.1-02 Task 1.

3. **RESOLVED: Should the agent send a response back to the hook DLL for BypassAlert frames?**
   - Decision: No. The hook DLL uses a fire-and-send pattern for bypass alerts (open pipe, write envelope, close pipe without reading). The existing `send_raw_request` already opens and closes the pipe per call, so no response is expected.
   - Implemented in: Plan 53.1-03 Task 1.
