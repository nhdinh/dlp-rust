# Phase 53.1: Close gap ETW-03 — add BypassAlert to IpcPayloadV1 and route in agent hook_ipc

**Gathered:** 2026-06-17
**Status:** Ready for planning
**Source:** Milestone audit / ROADMAP gap closure

<domain>
## Phase Boundary

This phase closes integration blocker INT-BLOCK-01 from the v0.10.0 milestone audit. The hook DLL already emits `BypassAlert` frames over its named pipe to the agent (introduced in Phase 51), but the agent's IPC deserializer treats every frame as a `HookRequest` and `dlp-common/src/hook_ipc.rs::IpcPayloadV1` has no `BypassAlert` variant. The result is that hook-DLL-generated bypass alerts are silently dropped before they can reach the `BypassCorrelator` and be persisted/routed to SIEM.

Scope:
1. Extend `IpcPayloadV1` in `dlp-common/src/hook_ipc.rs` with a `BypassAlert(BypassAlert)` variant.
2. Add the `BypassAlert` IPC type definition in `dlp-common` (reuse fields already defined for the server-side `BypassAlert` where possible).
3. Update `dlp-agent/src/hook_ipc.rs` to discriminate incoming pipe envelopes and route `BypassAlert` payloads to `bypass_correlator.rs` instead of the ABAC/policy path.
4. Ensure the hook DLL's existing `BypassAlert` emission over the pipe serializes with the new envelope.
5. Add unit + integration tests proving a hook-emitted bypass alert reaches the correlator.

Out of scope:
- Changing the ETW consumer (Phase 53 Plan 01).
- Changing the journal ring buffer (Phase 53 Plan 02).
- Changing server-side `POST /audit/bypass` or admin TUI (Phase 53 Plan 05 / Phase 54).
- Changing SIEM/alert-router wiring (Phase 53 Plan 06).
- Addressing MODE-01 / monitor-mode interaction with bypass alerts.
</domain>

<decisions>
## Implementation Decisions

### IPC Protocol
- Add `BypassAlert(BypassAlert)` to `IpcPayloadV1` in `dlp-common/src/hook_ipc.rs`.
- The `BypassAlert` struct must contain at minimum: `agent_id`, `pid`, `image`, `path`, `op`, `ts`, `file_object`, `correlation_reason` (mirrors ETW-03 requirement and existing server-side type).
- Derive `Serialize`, `Deserialize`, `Debug`, `Clone`, `PartialEq` for the new variant and payload type.
- Use `#[serde(default)]` on all new fields for backward compatibility with any persisted test fixtures.

### Agent Routing
- `dlp-agent/src/hook_ipc.rs::handle_connection` (or equivalent) must inspect `IpcEnvelope::V1(IpcMessageV1 { payload })` and dispatch `IpcPayloadV1::BypassAlert` to `bypass_correlator::submit_bypass_alert(...)` (or existing correlator entry point).
- `IpcPayloadV1::Request` continues down the existing ABAC/policy decision path unchanged.
- Keep the change local to IPC deserialization + routing; do not refactor the correlator internals.

### Hook DLL Emission
- `dlp-hook-dll/src/ntdll_patcher.rs` (or existing emitter) already constructs a bypass alert and sends it over the pipe; ensure it wraps the alert in `IpcEnvelope::V1(IpcMessageV1 { payload: IpcPayloadV1::BypassAlert(...) })` before `bincode::serialize`.
- If the hook currently sends a raw `BypassAlert` or `HookRequest`-shaped frame, update to the new envelope.

### Testing
- Unit test in `dlp-common`: round-trip serialize/deserialize `IpcPayloadV1::BypassAlert` through bincode.
- Unit test in `dlp-agent`: `handle_connection` routes a `BypassAlert` payload to a mock correlator and does not treat it as a `HookRequest`.
- Integration test (if feasible in existing e2e harness): a hook DLL trampoline scenario emits a bypass alert and the agent's correlator receives it.
</decisions>

<specifics>
## Specific Ideas

- The server-side `BypassAlert` type likely lives in `dlp-server/src/db/repositories/bypass_alerts.rs` or a shared model. Consider whether to move/re-export a canonical type to `dlp-common` so both hook DLL and server use the same struct. If that is too large a change for a gap closure, define a minimal `BypassAlert` in `dlp-common/src/hook_ipc.rs` and provide a `From`/`Into` conversion to the server type in the agent.
- The agent correlator currently consumes ETW-derived events; ensure the new entry point accepts hook-derived alerts without requiring a real ETW event or journal lookup (the hook is self-reporting the bypass).
- Correlation reason for hook-emitted alerts should be a new variant such as `HookSelfReported` or similar, distinct from `NoHookJournal`.
</specifics>
