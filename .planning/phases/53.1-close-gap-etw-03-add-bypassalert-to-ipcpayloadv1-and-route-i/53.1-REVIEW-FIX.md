## Skipped Issues

### WR-10: `BypassAlert` `image_sha256` field uses `Option<String>` without length validation

**File:** `dlp-common/src/hook_ipc.rs:218`
**Reason:** Advisory design suggestion, not a fixable bug. Changing `Option<String>` to `[u8; 32]` would break bincode serialization compatibility with existing alerts and require changes across all consumers (agent, hook DLL, correlator, SIEM). The reviewer frames this as "Consider using..." which is a design trade-off, not a required fix. Per the spec, `image_sha256` is a hex digest (64 chars) stored as `Option<String>`; bincode's 64MiB frame limit already provides an upper bound on frame size. A per-field length validation would be better addressed in a dedicated deserialization validation layer (e.g., a `TryFrom` or `serde` visitor) in a future phase.
**Original issue:** The `image_sha256` field is `Option<String>` with no validation. A malformed or excessively long string could be injected. While bincode has a 64MiB frame limit, there's no per-field validation.
