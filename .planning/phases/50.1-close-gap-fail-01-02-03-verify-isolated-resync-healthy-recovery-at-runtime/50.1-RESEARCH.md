# Phase 50.1: Close gap FAIL-01/02/03 — verify ISOLATED->RESYNC->HEALTHY recovery at runtime

**Researched:** 2026-06-18
**Domain:** Windows shared-memory cache, hook DLL fail-mode state machine, runtime recovery verification
**Confidence:** HIGH

## Gap Summary

Phase 50 implemented the shared-memory classification cache, fail-mode state machine, and background thread. Phase 50.1 is an inserted gap-closure phase to **verify at runtime** that a hooked process transitions `ISOLATED -> RESYNC -> HEALTHY` when the agent recovers and publishes a fresh cache version.

The existing Phase 50 tests are mostly:
- Unit tests for `FailModeState` transitions (`dlp-hook-dll/src/fail_mode.rs`)
- Synthetic/simulated benchmarks (`dlp-e2e/tests/cache_benchmark.rs`)
- Contract/constant tests (`dlp-e2e/tests/phase50_requirements.rs`)

What is **missing** is an integration test that exercises the real agent-side `ClassificationCache` writer and hook-DLL-side `CacheLookup` reader together, drives the state machine into `ISOLATED`, publishes a new version, and asserts the background thread detects it and the process recovers to `HEALTHY`.

## Requirements

- **FAIL-01**: Hook DLL fail-mode state machine: HEALTHY -> DEGRADED (3 consecutive pipe failures) -> ISOLATED (10 consecutive failures OR cache stale) -> RESYNC (pipe recovered + new cache version) -> HEALTHY
- **FAIL-02**: Asymmetric tier-gated fail semantics: T3/T4 fail-closed when ISOLATED; T1/T2 fail-open
- **FAIL-03**: Per-tier staleness budgets: T4=30s, T3=60s, T2=5min, T1=30min

## Existing Implementation State

### Implemented and working

- `dlp-agent/src/classification_cache.rs`: Creates `Global\DlpClassificationCache`, double-buffered atomic version flip, rebuild API, prepopulate T3/T4 roots.
- `dlp-agent/src/cache_pusher.rs`: Debounced rebuild background thread.
- `dlp-agent/src/service.rs`: Initializes cache and pusher at startup.
- `dlp-hook-dll/src/fail_mode.rs`: `FailModeState` with Healthy/Degraded/Isolated/Resync, hysteresis (3 successes to exit Degraded, 5 to exit Isolated/Resync), asymmetric decisions.
- `dlp-hook-dll/src/background_thread.rs`: Polls version word every 100ms in ISOLATED/RESYNC, calls `record_pipe_success(version)` on fresh version.
- `dlp-hook-dll/src/classification_cache.rs`: Read-only `CacheLookup`, thread-local LRU, version invalidation.

### Runtime recovery path

1. Hook DLL enters ISOLATED after 10 pipe failures (or stale cache).
2. Agent recovers and calls `ClassificationCache::rebuild(entries)` -> publishes new even `version_word`.
3. Hook DLL background thread reads `version_word`, detects `version > cache_version_seen_at`, calls `record_pipe_success(version)`.
4. `record_pipe_success` transitions `ISOLATED -> RESYNC` because `cache_version > last_seen`.
5. Subsequent successful pipe round-trips (or simulated successes) increment `consecutive_successes`; after 5, state transitions `RESYNC -> HEALTHY`.
6. During RESYNC, LRU is flushed and new decisions use the new cache.

### Testability gaps

- No test wires a real `ClassificationCache` (writer) with `CacheLookup` (reader) and `FailModeState`.
- No test verifies the background thread detects a fresh version and triggers RESYNC.
- No test verifies the full `ISOLATED -> RESYNC -> HEALTHY` cycle end-to-end.
- No test verifies in-flight decisions during RESYNC complete using the old cache.

## Recommended Plan Scope

Phase 50.1 should produce **one executable plan** with two waves:

**Wave 1**: Runtime integration test harness
- Add `dlp-hook-dll/tests/isolated_resync_recovery.rs` integration test.
- In test setup, create a real `ClassificationCache` (via `dlp-agent` dev-dependency) and populate it with a T3/T4 path.
- Map the cache read-only using the hook DLL's `CacheLookup` path.
- Drive `FailModeState` to ISOLATED with 10 simulated pipe failures.
- Start the hook DLL background thread with the mapped header.
- Publish a new cache version via `ClassificationCache::rebuild`.
- Assert background thread detects fresh version and state becomes RESYNC within 200ms.
- Assert 5 consecutive `record_pipe_success` calls transition to HEALTHY.

**Wave 2**: In-flight decision guarantee and adversarial recovery
- Add test: a decision started before RESYNC completes using the old cache snapshot.
- Add test: odd `version_word` during rebuild is ignored by background thread (writer in progress).
- Add test: stale cache (T4 budget exceeded) triggers ISOLATED transition even with working pipe.
- Add test: RESYNC -> ISOLATED on pipe failure during recovery.

## Success Criteria

1. A Windows integration test creates a real shared-memory cache, drives ISOLATED, publishes a new version, and verifies RESYNC detection within 200ms.
2. The same test verifies RESYNC -> HEALTHY after 5 consecutive successes.
3. In-flight decision test proves old cache is used until LRU flush.
4. All tests pass `cargo test -p dlp-hook-dll --test isolated_resync_recovery` on Windows.
5. Non-Windows tests gracefully skip Windows-only assertions.
6. No production behavior changes — only tests and minor testability helpers.

## Cross-Cutting Constraints

- Cache non-authoritative invariant: ABAC authority never bypassed.
- Background thread must not be created from DllMain in production (tests can use direct call).
- Use `Ordering::Acquire/Release` correctly around version word reads/writes.
- Tests must clean up shared-memory mapping handles to avoid leaks.
