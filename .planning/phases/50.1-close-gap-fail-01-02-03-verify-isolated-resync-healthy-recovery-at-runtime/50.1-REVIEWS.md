# Cross-AI Plan Review — Phase 50.1

## OpenCode Review

### Summary

The plan is well-structured and addresses the correct gap (no integration test for the ISOLATED->RESYNC->HEALTHY recovery path). It correctly identifies the testability helpers needed and the 9 tests that cover the recovery cycle, edge cases, and adversarial conditions. However, it has three significant blind spots: **(1)** a structurally different `CacheHeader::compute_checksum` between agent and hook-dll that the integration test will trigger, **(2)** a background-thread lifecycle problem that makes sequential test execution unsafe, and **(3)** a missing test-specific shared-memory namespace that risks interfering with a live agent.

### Strengths

- **Correct gap identification**: The plan accurately diagnoses that Phase 50 has no cross-crate integration test for the runtime recovery cycle, only unit tests for `FailModeState` transitions.
- **Sound recovery-path logic**: The ISOLATED->RESYNC detection via background thread reading `version_word` and calling `record_pipe_success` matches the production code exactly.
- **Real shared-memory wiring**: Using `dlp-agent` as a dev-dependency (already present in `dlp-hook-dll/Cargo.toml:37`) makes it possible to create a real `ClassificationCache` and map it via `CacheLookup` — this is the key design enabler.
- **Appropriate test scoping**: 9 tests that cover the main cycle, in-flight guarantees, odd-version skip, staleness trigger, RESYNC failure back to ISOLATED, LRU flush, and asymmetric decisions. No scope creep.
- **Threat model**: Acknowledges the global mapping collision and raw-pointer-safety risks, with mitigations.
- **Serialized execution**: `--test-threads=1` correctly prevents collisions on the global mapping singleton.
- **Existing tests preserved**: No production logic changes; helpers are `#[cfg(test)]` gated.

### Concerns

#### HIGH: `_reserved` ABI mismatch between agent and hook-dll `CacheHeader`

The plan claims agent and hook-dll structs match "byte-for-byte," but they do not:

- Agent at `dlp-agent/src/classification_cache.rs:115`: `_reserved: [u8; 40]` (offsets 88–127)
- Hook-dll at `dlp-hook-dll/src/classification_cache.rs:76-81`: `allowlist_offset: u64`, `allowlist_count: u64`, `_reserved: [u8; 24]` (offsets 88–127)

The hook-dll `compute_checksum` XORs `allowlist_offset` + `allowlist_count` + 3 reserved u64s; the agent XORs 5 reserved u64s. Both currently XOR against zeros, so checksums match accidentally. But if the plan adds a `#[cfg(test)]` helper that calls `rebuild()` (which calls `compute_checksum` on the agent side) and then the hook-dll side validates with its own `compute_checksum`, the test will pass only because all 40 bytes remain zeroed. **This is a latent production bug** — if the agent ever writes non-zero data to `_reserved`, the hook-dll will misread the allowlist fields and fail checksum validation. The integration test would mask this bug because all values are zero.

**Fix**: Either add `allowlist_offset` and `allowlist_count` to the agent's `CacheHeader` (removing the struct divergence), or align `_reserved` sizes to 40 bytes in both.

#### HIGH: Background thread lifecycle unsynchronized across sequential tests

The plan's Task 1 adds `reset_thread_started_for_test()` to enable restarting the background thread. However, `shutdown_background_thread()` (line 121-134) signals the event but **does not join the thread** — it just drops the handle and returns. The thread remains running in the process, polling the shared memory. When test 1 ends and test 2 starts:

1. `reset_thread_started_for_test()` sets `THREAD_STARTED` to false.
2. Test 2 creates a **new** `ClassificationCache` mapping (different memory address).
3. Test 2 calls `start_background_thread()` with the new `cache_header`.
4. The **old thread from test 1** is still polling the **old** (unmapped or reused) `cache_header`, and will read garbage or crash.

The `background_thread_loop` has a null-pointer guard at line 155-167, but a dangling non-null pointer is UB.

**Fix**: Either (a) make `shutdown_background_thread()` truly join the thread (with timeout), or (b) add a cancellation flag that the background thread checks every cycle, or (c) restructure tests so each test does its own thread lifecycle within a single binary run. Option (a) is simplest — use a `Condvar` or an additional `AtomicBool` that the loop checks after `WaitForSingleObject` returns `WAIT_TIMEOUT`.

#### MEDIUM: Production global mapping namespace used by tests

The plan's integration tests use `CACHE_NAME` = `"Global\DlpClassificationCache"`, which is the same namespace as the production DLP agent. If a developer runs the test while the real agent is running:

- `CreateFileMappingW` will open a handle to the EXISTING agent mapping (it doesn't create a new one).
- Writing to the agent's mapping in the test will corrupt the production cache.
- If the test runs as a non-Admin user, `OpenFileMappingW` on the agent's mapping (which restricts to SYSTEM + Administrators) will fail, breaking the test.

The threat model (T-50.1-01) acknowledges this as "test-only, no sensitive data," but doesn't adequately mitigate the interference risk.

**Fix**: Use a test-specific name like `"Global\DlpClassificationCache_TestPhase50_1"` for integration tests, ideally configurable via a `#[cfg(test)]` override of `CACHE_NAME`.

#### MEDIUM: Staleness test doesn't exercise state machine transition

Test `stale_cache_triggers_isolated` (Task 3) calls `is_cache_stale` directly rather than driving the state machine. The actual DEGRADED->ISOLATED transition via staleness requires the pipe-client code to check staleness before calling `record_pipe_failure`. The plan's test only validates the helper function, not the integration path. This means **the integration path for staleness-triggered isolation remains untested** after this phase.

**Fix**: Either wire a test that actually drives the cycle (set clock by manipulating `created_at_epoch_secs` in the mapping header, then call the pipe-client's staleness check), or document this as a remaining gap for a follow-up phase.

#### LOW: `in_flight_decision_uses_old_cache` test is underspecified

The plan says "Populate LRU with version 1 entry. Enter RESYNC. Assert old cache still used until LRU flush." But the LRU is thread-local (line 621-624 of hook-dll's `classification_cache.rs`). The test must run `lru::insert` on the same thread that checks `lru::get`. Additionally, the "old cache" is actually the `CacheLookup::lookup()` method which reads from shared memory — during RESYNC, it reads whatever version the header has. The guarantee isn't about the shared memory (which changes atomically) but about in-flight snapshots taken at the start of `lookup()`. The plan should clarify that the test validates `LruCache` behavior with version pinning, not shared-memory read isolation (which can't be done since the whole mapping flips atomically).

#### LOW: Timing sensitivity

The plan asserts "RESYNC within 500ms" but the background thread polls every 100ms. Under CI load, 500ms may be tight. Consider using 2000ms with a tighter assertion (e.g., 200ms average) for a looser absolute timeout.

### Suggestions

1. **Fix the CacheHeader ABI divergence** before implementing the integration test — either add `allowlist_offset` + `allowlist_count` to the agent-side struct or grow `_reserved` to 40 bytes in the hook-dll. Otherwise the test will pass for the wrong reason (all zeros) and mask a production bug.

2. **Fix background thread join** in `shutdown_background_thread()` — use an `AtomicBool` cancellation flag that the loop checks after each `WaitForSingleObject` timeout. This makes sequential tests safe.

3. **Use a test-specific mapping name** — make `CACHE_NAME` overridable via `#[cfg(test)]` or add a `new_with_name(name)` constructor to `ClassificationCache`.

4. **For the staleness test**, consider adding a `record_cache_stale()` method to `FailModeState` that the pipe client calls, making it testable through the state machine instead of via the helper function directly.

5. **Increase timing tolerance** from 500ms to 2000ms for the `isolated_to_resync_via_background_thread` test, with a comment explaining the polling interval.

6. **Add a test for `CacheLookup` retry on odd `version_word`** — the `lookup()` method (line 260-267) yields once if version is odd. This should be tested to ensure the yield doesn't cause issues under contention.

7. **Document the `from_raw_pointer` SAFETY contract** more thoroughly — the plan mentions `# Safety` doc but should explicitly state that the caller must ensure the mapping outlives the `CacheLookup`.

### Risk Assessment: MEDIUM

The plan would likely produce working tests as specified, and the 9 tests would validate the recovery path end-to-end. However, the **CacheHeader ABI divergence** and **background thread lifecycle** issues mean the tests either mask a production bug or cause flaky/crashing behavior in sequential test runs. These must be resolved before implementation. The staleness gap is a known limitation the plan chooses to accept. With the fixes above (particularly items 1-3), risk drops to LOW.

## Claude Review (This Session)

### Summary

The plan correctly identifies the v0.10.0 milestone audit gap: FAIL-01/02/03 state machine and recovery logic is implemented but the runtime ISOLATED->RESYNC->HEALTHY auto-recovery path is unverified. The plan proposes 9 integration tests across 3 tasks with appropriate testability helpers. However, source-grounding verification reveals two confirmed production defects that the plan's tests would either mask or be blocked by.

### Strengths

- **Precise gap targeting**: The plan directly addresses the `INT-BLOCK-03` blocker from the v0.10.0 milestone audit: "Background thread exists but automatic ISOLATED->RESYNC runtime behavior is unverified."
- **Real cross-crate integration**: Using `dlp-agent` as a dev-dependency to create real shared memory and mapping it via `CacheLookup` is the correct approach — synthetic mocks would not catch ABI or ordering bugs.
- **Comprehensive coverage matrix**: The 9 tests map cleanly to requirements: FAIL-01 (state transitions, odd-version guard, in-flight guarantee, LRU flush, RESYNC->ISOLATED), FAIL-02 (asymmetric decisions), FAIL-03 (staleness budget).
- **Non-Windows skip strategy**: Correctly uses `#[cfg(not(windows))]` early-return rather than conditional compilation on the entire test module, which keeps the test code compiled and type-checked on all platforms.
- **No production behavior changes**: All proposed modifications are `#[cfg(test)]` gated or in test files only, satisfying the "no production changes" constraint.

### Concerns

#### HIGH: CacheHeader ABI divergence — `compute_checksum` mismatch between agent and hook-dll (verified)

**Source-grounded verification**: 
- `dlp-agent/src/classification_cache.rs:734-756`: `compute_checksum` XORs `magic` through `created_at_epoch_secs`, then XORs `_reserved` in 5x u64 chunks (40 bytes total). No `allowlist_offset` or `allowlist_count` fields exist in the agent struct.
- `dlp-hook-dll/src/classification_cache.rs:378-402`: `compute_checksum` XORs `magic` through `created_at_epoch_secs`, then XORs `allowlist_offset` and `allowlist_count`, then XORs `_reserved` in 3x u64 chunks (24 bytes total).

**Impact**: Both structs claim to be 128 bytes, but the field layouts differ at offsets 88-127. The agent has `_reserved: [u8; 40]` while the hook-dll has `allowlist_offset: u64`, `allowlist_count: u64`, `_reserved: [u8; 24]`. Since both sides zero `_reserved` on init and never write non-zero data to it, checksums currently match. But the integration test would pass for the wrong reason and mask this latent production bug. If the agent ever populates `_reserved` or the hook-dll populates allowlist fields, checksum validation will fail.

**Mitigation needed**: The plan must include a task to align the `CacheHeader` structs and `compute_checksum` implementations before the integration test can be considered valid. This is a prerequisite, not a post-test fix.

#### HIGH: Background thread `shutdown_background_thread()` does not join — sequential test unsafety (verified)

**Source-grounded verification**:
- `dlp-hook-dll/src/background_thread.rs:121-134`: `shutdown_background_thread()` calls `SetEvent(bt.shutdown_event)` but does NOT call `JoinHandle::join()`. The comment explicitly states: "we can't easily do a timed join in std, so we just drop the handle and let the thread exit on its own."
- `BACKGROUND_THREAD` is a `std::sync::OnceLock<BackgroundThread>` — once set, it cannot be reset. The plan's `reset_thread_started_for_test()` only resets `THREAD_STARTED`, not `BACKGROUND_THREAD`.

**Impact**: In a sequential test run:
1. Test 1 starts background thread with header A. Thread A polls header A.
2. Test 1 calls `shutdown_background_thread()` — event is signaled but thread A continues running until its next `WaitForSingleObject` timeout (up to 100ms).
3. Test 1's `ClassificationCache` is dropped, unmapping header A.
4. Test 2 calls `reset_thread_started_for_test()` and `start_background_thread()` with header B. But `BACKGROUND_THREAD` is already set (OnceLock), so `start_background_thread()` returns early at line 83 (THREAD_STARTED is true after reset, but BACKGROUND_THREAD.set() would fail on second call — actually the code doesn't check BACKGROUND_THREAD, only THREAD_STARTED, so it would proceed to create a new thread... but the old thread is still running with a dangling pointer).

Wait — re-reading: `start_background_thread` checks `THREAD_STARTED.swap(true, Ordering::SeqCst)` at line 83. If `reset_thread_started_for_test()` sets it to false, the swap returns false and the function proceeds. But `BACKGROUND_THREAD.set()` at line 111 will PANIC on the second call because `OnceLock::set` returns `Err` if already initialized, and the code uses `let _ = BACKGROUND_THREAD.set(...)` which ignores the error. So the second start would fail silently to store the new `BackgroundThread` struct, but would still spawn a new thread. The old thread continues running with a dangling pointer.

**Mitigation needed**: The plan must add a task to fix `shutdown_background_thread()` to actually join the thread, and to make `BACKGROUND_THREAD` resettable for tests (e.g., replace `OnceLock` with a `Mutex<Option<BackgroundThread>>` or add a test-only `reset_background_thread_for_test()` helper).

#### MEDIUM: Staleness test validates helper, not integration path

The `stale_cache_triggers_isolated` test calls `is_cache_stale()` directly. The actual production path for staleness-triggered ISOLATED is: the pipe client checks staleness before each operation, and if stale, calls `record_pipe_failure()` which drives the state machine. The plan does not test this integration path. This is acceptable for a gap-closure phase if documented as a remaining gap, but the plan should be explicit about it.

#### MEDIUM: `CACHE_NAME` is hardcoded — test/live agent collision risk

The `CACHE_NAME` constant in `dlp-agent/src/classification_cache.rs:70` is `"Global\DlpClassificationCache"`. The plan's tests use `ClassificationCache::new()` which uses this hardcoded name. If a developer runs tests while the DLP agent service is running, the test will open the agent's mapping (same name) and either corrupt it or fail with access denied. The threat model acknowledges this but the mitigation (`--test-threads=1`) only prevents test-test collisions, not test-agent collisions.

**Mitigation needed**: Add `#[cfg(test)]` override of `CACHE_NAME` or a `new_with_name()` constructor.

#### LOW: Timing assertions may be flaky under CI load

The plan asserts "RESYNC within 500ms" and "within 200ms" in different places. The background thread polls every 100ms. Under CI load or VM contention, 500ms may be tight. Recommend 2000ms timeout with a comment about the 100ms polling interval.

### Suggestions

1. **Add a prerequisite task** to align `CacheHeader` ABI between agent and hook-dll before any integration test work. This is a production bug that must be fixed regardless of the test plan.

2. **Add a prerequisite task** to fix `shutdown_background_thread()` to properly join the thread. Replace `OnceLock` with a resettable mechanism for tests, or add a `#[cfg(test)]` `reset_background_thread_for_test()` that uses `unsafe` to reset the `OnceLock` (possible via `std::ptr::write` to the inner cell, though this requires care).

3. **Add `#[cfg(test)]` `CACHE_NAME` override** to prevent test/live agent collision. The simplest approach: `#[cfg(test)] const CACHE_NAME: &str = "Global\DlpClassificationCache_Test";`.

4. **Clarify the staleness test scope** in the plan: explicitly state that `stale_cache_triggers_isolated` validates the `is_cache_stale` helper, and that the full pipe-client staleness-driven state machine transition is out of scope for this phase (or add it as a stretch goal).

5. **Increase timing tolerance** to 2000ms for all background-thread detection tests.

6. **Add a test for `CacheLookup::lookup()` retry on odd `version_word`** — the `lookup()` method yields once when version is odd. This behavior should be tested under contention.

### Risk Assessment: HIGH

The plan would produce tests that either **mask a production bug** (CacheHeader ABI divergence) or **crash/flake** (background thread dangling pointer). These are not test bugs — they are production bugs that the tests would expose if they weren't masked by zeroed memory. The plan must be amended to include prerequisite tasks to fix these issues before the integration tests can be considered valid. Without these fixes, the phase cannot achieve its stated goal of "verifying at runtime" the recovery path, because the verification would be built on an inconsistent ABI and unsafe thread lifecycle.

## Consensus Summary

Both reviewers independently identified the same two HIGH-severity issues:

1. **CacheHeader ABI divergence** between agent and hook-dll — the `compute_checksum` implementations differ in which fields they XOR, and the struct layouts differ in the `_reserved` vs `allowlist_offset`/`allowlist_count` region. This is a latent production bug that the integration test would mask because all values are zeroed.

2. **Background thread lifecycle** — `shutdown_background_thread()` does not join the thread, and `BACKGROUND_THREAD` is a `OnceLock` that cannot be reset. Sequential tests would leave a dangling thread polling unmapped memory, causing UB or crashes.

Both reviewers also identified the same MEDIUM concern about the hardcoded `CACHE_NAME` causing test/live agent collisions, and the same LOW concern about timing sensitivity.

### Agreed Strengths

- Correct gap identification (no cross-crate integration test for runtime recovery)
- Sound approach using real shared-memory wiring via dev-dependency
- Appropriate test scoping (9 tests covering core cycle + edge cases)
- `#[cfg(test)]` gating prevents production exposure
- Non-Windows skip strategy is correct

### Agreed Concerns (Priority Order)

1. **HIGH**: CacheHeader ABI divergence — `compute_checksum` and struct layout mismatch between agent and hook-dll. Must fix before integration tests.
2. **HIGH**: Background thread `shutdown_background_thread()` does not join; `BACKGROUND_THREAD` OnceLock is not resettable. Must fix before sequential tests.
3. **MEDIUM**: Hardcoded `CACHE_NAME` risks test/live agent collision. Should use test-specific name.
4. **MEDIUM**: Staleness test validates helper only, not full pipe-client integration path. Document as gap or extend.
5. **LOW**: Timing assertions (500ms) may be flaky under CI load. Recommend 2000ms.

### Divergent Views

- **OpenCode** rates overall risk as MEDIUM, believing the plan would "likely produce working tests as specified" with fixes. **Claude** rates overall risk as HIGH, because the two HIGH issues are production bugs that must be fixed as prerequisites, not alongside the test work. The plan as written does not include these prerequisite tasks.
- **OpenCode** suggests adding `allowlist_offset`/`allowlist_count` to the agent struct. **Claude** agrees and additionally notes that the `compute_checksum` implementations must be made identical (same field list, same XOR order).
- **OpenCode** suggests an `AtomicBool` cancellation flag for the background thread. **Claude** agrees and additionally notes that `OnceLock` must be made resettable for tests (or replaced with `Mutex<Option<BackgroundThread>>`).
