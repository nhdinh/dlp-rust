# Phase 50.1: Code Review Report

**Reviewed:** 2026-06-19T00:45:00Z
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

This phase aligned the CacheHeader ABI between the agent and hook-dll, fixed the background thread lifecycle for test safety, and added 10 integration tests for the ISOLATED->RESYNC->HEALTHY recovery cycle. The code is generally well-structured and the tests cover the key state transitions. However, several correctness and robustness issues were identified during adversarial review.

## Critical Issues

### CR-01: CacheHeader ABI alignment depends on manual field ordering — no compile-time struct layout verification

**File:** `dlp-agent/src/classification_cache.rs:87-120` and `dlp-hook-dll/src/classification_cache.rs:47-81`
**Issue:** Both crates define an identical `CacheHeader` struct with `#[repr(C, align(8))]`, but there is no compile-time guarantee that the two definitions remain in sync. The structs are copy-pasted between crates. If a future phase adds a field to one crate but not the other (or changes field order), the ABI will silently break. The integration test `cross_crate_checksum_validation` only catches mismatches at runtime, not at compile time. This is a latent correctness risk for a security-critical shared-memory protocol.
**Fix:** Extract `CacheHeader` (and `PrefixEntry`, `HashEntry`) into `dlp-common` as a shared struct with `#[repr(C, align(8))]`, and have both crates import it. This guarantees single-source-of-truth for the ABI. If cross-crate sharing is not viable, add a `build.rs` script or a `const` assertion that verifies both struct definitions have identical `size_of` and `align_of` values by comparing against known constants.

### CR-02: `THREAD_STARTED` flag can desynchronize from `BACKGROUND_THREAD` state, causing leaked threads or double-starts

**File:** `dlp-hook-dll/src/background_thread.rs:46-49, 84-86, 152-159`
**Issue:** `THREAD_STARTED` (AtomicBool) and `BACKGROUND_THREAD` (Mutex<Option<...>>) are separate variables with no atomic transaction linking them. The `start_background_thread` function does:
1. `THREAD_STARTED.swap(true, Ordering::SeqCst)` — if already true, returns early.
2. Creates event and spawns thread.
3. Locks `BACKGROUND_THREAD` mutex and stores the handle.

If `shutdown_background_thread` runs between steps 1 and 3, it will see `THREAD_STARTED=true` and try to signal/join the old thread (which may not exist yet), while the new thread spawns anyway. Conversely, `reset_background_thread_for_test` resets `THREAD_STARTED` to false but does not verify the mutex is empty — if a test calls `reset_background_thread_for_test` without first calling `shutdown_background_thread`, the old thread handle is dropped without joining, leaking the thread. In a DLL context, leaked threads can prevent clean process detach.
**Fix:** Use a single `Mutex` to guard both the "started" flag and the thread handle together. The state should be an enum: `NotStarted | Starting | Running(BackgroundThread)`. This ensures all transitions are atomic and prevents the split-brain between the flag and the mutex.

## Warnings

### WR-01: `shutdown_background_thread` busy-waits for 5 seconds with 10ms sleep — inefficient and imprecise

**File:** `dlp-hook-dll/src/background_thread.rs:136-144`
**Issue:** The join-timeout loop uses a busy-wait (`while start.elapsed().as_secs() < 5 { if handle.is_finished() { break; } sleep(10ms) }`). This consumes CPU and scheduler time for up to 500 iterations. More importantly, if the thread is stuck (e.g., the shutdown event was lost), the loop exits after 5 seconds and calls `handle.join()` anyway, which will block indefinitely since `is_finished()` was already checked.
**Fix:** Use `std::thread::JoinHandle::join()` directly with a timeout mechanism, or use a `std::sync::mpsc` channel for the thread to signal completion. On Windows, consider using `WaitForSingleObject` on the thread handle with a timeout. If the timeout expires, log a warning and detach the thread rather than blocking forever.

### WR-02: `reset_background_thread_for_test` is not gated by `#[cfg(test)]` despite claiming to be test-only

**File:** `dlp-hook-dll/src/background_thread.rs:148-159`
**Issue:** The doc comment says "This is test-only and gated by `#[cfg(test)]`", but the function has no `#[cfg(test)]` attribute. It is a `pub` function exported from the crate root via `lib.rs`. A production caller could accidentally call it, shutting down the background thread and resetting the fail-mode state machine mid-operation. This is a safety hazard.
**Fix:** Add `#[cfg(test)]` to `reset_background_thread_for_test`. If integration tests need it (and they run the crate as a dev-dependency, which compiles without `cfg(test)`), gate it behind the `test-helpers` feature instead and only enable that feature in `[dev-dependencies]`.

### WR-03: `is_cache_stale` ignores tier-specific budgets and always uses T4 (30s) — contradicts documented tier budgets

**File:** `dlp-hook-dll/src/fail_mode.rs:440-460`
**Issue:** The function documentation says "Check if the cache is stale based on the most conservative budget (T4)" and the code hardcodes `STALENESS_BUDGETS[3]` (30s). However, the `STALENESS_BUDGETS` array defines tier-specific budgets (T1=30min, T2=5min, T3=60s, T4=30s), and the `staleness_budget_for` function exists to look them up. The `is_cache_stale` function takes no `Classification` parameter, so it cannot apply the correct budget for the data being accessed. This means a T1 (Public) cache entry will be considered stale after 30 seconds even though its budget is 30 minutes. In production, this could cause unnecessary fail-closed denials or premature ISOLATED transitions.
**Fix:** Add a `classification: Classification` parameter to `is_cache_stale` and use `staleness_budget_for(classification)` instead of hardcoding `STALENESS_BUDGETS[3]`. Update all call sites (including tests) to pass the classification.

## Info

### IN-01: `test-helpers` feature in `Cargo.toml` is defined but unused

**File:** `dlp-hook-dll/Cargo.toml:39-41`
**Issue:** The `test-helpers` feature flag is declared but nothing in the codebase is gated behind it. All test-only helpers (`reset_background_thread_for_test`, `set_cache_version_seen_at`, `from_raw_pointer`, `header_for_test`, `mapping_handle_for_test`) are unconditionally compiled. The feature is dead code.
**Fix:** Either remove the unused feature from `Cargo.toml`, or actually use it to gate test-only exports. The latter is preferred for production hygiene.

### IN-02: `decide_resync` is documented as "same logic as Healthy" but delegates to `decide_isolated` — documentation/implementation mismatch

**File:** `dlp-hook-dll/src/fail_mode.rs:398-418`
**Issue:** The doc comment says "Same logic as Healthy: use cache if available, otherwise pipe." but the implementation calls `decide_isolated(classification, op)`. The `decide_isolated` function applies asymmetric fail-closed logic (T3/T4 write -> deny), which is NOT the same as Healthy logic (which would fall through to the pipe for ABAC evaluation). During RESYNC, the system is supposed to be recovering and using fresh cache data, not applying the same restrictive rules as ISOLATED. This may be intentional (fail-closed during recovery), but the documentation contradicts the implementation.
**Fix:** Clarify the doc comment to state that RESYNC intentionally applies ISOLATED-style fail-closed decisions until full recovery is confirmed, or change the implementation to match the documented Healthy behavior. Either way, the docs and code must agree.
