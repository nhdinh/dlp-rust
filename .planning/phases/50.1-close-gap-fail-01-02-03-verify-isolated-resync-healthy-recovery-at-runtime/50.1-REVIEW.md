# Phase 50.1: Code Review Report

**Reviewed:** 2026-06-20
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

This review covers the Phase 50.1 implementation of FAIL-01/02/03 gap closure: ISOLATED -> RESYNC -> HEALTHY recovery at runtime, including the background thread for cache version polling, fail-mode state machine, shared-memory classification cache (agent writer and hook-DLL reader), and integration tests.

The code demonstrates solid architectural thinking around the fail-mode state machine, sequence-lock protocol for cache publication, and defensive programming. However, several critical issues were found:

1. **Race condition in background thread startup** (CR-01): The `Starting` state is set under the mutex, then the mutex is dropped while the event is created. If `shutdown_background_thread` is called during this window, it sees `NotStarted` (because the state was already swapped to `Starting` but the thread hasn't been spawned yet), and returns without doing anything. But the thread creation continues and the state becomes `Running`. This is actually a bug in the opposite direction: the `Starting` state prevents shutdown from seeing `NotStarted`, but the real issue is that after `drop(guard)` on line 129, another thread could call `start_background_thread` again, see `Starting`, and return. That's fine. The real bug is: if `CreateEventW` fails, the code reverts to `NotStarted` on line 140. But between lines 129 and 140, another `start_background_thread` call could see `Starting` and return. That's fine. The real issue is more subtle: after `drop(guard)` on line 129, the thread is spawned on line 151. Between spawn and line 164 (where we set `Running`), another thread could call `shutdown_background_thread`, see `Starting`, and return without doing anything. Then the thread starts running but nobody can shut it down until the state transitions to `Running`. Actually, the comment on line 30 says `Starting` prevents the race where shutdown runs between `THREAD_STARTED` swap and mutex lock. But looking at the code: `shutdown_background_thread` matches `Running(bt)` to get the handle. If state is `Starting`, it returns early (line 191-193). So during the window between `drop(guard)` (line 129) and `*guard = BackgroundThreadState::Running(bt)` (line 165), any call to `shutdown_background_thread` will see `Starting` and return without doing anything. The thread will then be spawned and set to `Running`, but the shutdown signal was missed. This is a **race condition**: shutdown can be silently ignored if called during startup.

2. **TOCTOU in cache header access** (CR-02): In `background_thread_loop`, the code checks `cache_header.is_null()` on line 253, then inside the `Isolated` branch on line 297, it checks `cache_header.is_null()` again. But between the first check and the dereference on line 301, the pointer could become invalid if the shared memory is unmapped by another thread. The `cache_header` is a raw pointer passed into the thread. If the main thread drops the `CacheLookup` or `ClassificationCache` that owns the mapping, the pointer becomes dangling. The background thread has no way to know the mapping is still valid. This is a use-after-free risk.

3. **Unsafe `std::mem::replace` with placeholder JoinHandle** (CR-03): In `shutdown_background_thread` (line 185-188), the code uses `std::mem::replace` to swap the `JoinHandle` with a placeholder `std::thread::spawn(|| {})`. The placeholder thread is spawned but never joined. This leaks a thread handle on every shutdown. More importantly, the `BackgroundThread` struct is left in an inconsistent state where `thread_handle` points to a different thread than `shutdown_event`. If any code accesses `bt.thread_handle` after this replace (which shouldn't happen since we took the handle, but the struct is still stored in `Running`), it's referencing the wrong thread. The real issue: the `BackgroundThread` struct is still in the mutex as `Running(bt)`, but `bt.thread_handle` now points to a dummy thread. If `shutdown_background_thread` is called again (which shouldn't happen but could due to a bug), it would try to signal and wait on the dummy thread. This is a logic error that could lead to incorrect behavior.

4. **Missing `#[allow(dead_code)]` on `decide_resync` doc comment** (WR-01): In `fail_mode.rs` line 399, `#[allow(dead_code)]` is placed before the doc comment on `decide_resync`, not on the function itself. The attribute applies to the following item, which is the doc comment... actually in Rust, attributes before doc comments apply to the item the docs are for. But the placement is unusual and could be confusing. More importantly, `decide_resync` is marked `#[allow(dead_code)]` but is never called in production code. This is dead code that should either be used or removed.

5. **Stale cache transition logic not wired** (WR-02): The `is_cache_stale` function is defined and tested, but the actual state machine transition `DEGRADED -> ISOLATED` on stale cache is not wired into `record_pipe_failure`. The comment on line 552 of `fail_mode.rs` says "failures >= 10 OR cache stale" but the code only checks `failures >= DEGRADED_TO_ISOLATED_THRESHOLD`. The staleness check is never performed in the state machine.

6. **Test-only `set_state` marked as `pub` without test gate** (WR-03): In `fail_mode.rs` line 323, `set_state` is marked `pub` and has a safety doc comment, but it's not gated with `#[cfg(any(test, feature = "test-helpers"))]`. It's used by tests but exposed as a public API. This violates the principle of least exposure for unsafe operations.

7. **LRU cache doesn't handle hash collisions or eviction properly** (WR-04): In `classification_cache.rs` (hook-dll), the `LruCache::get` method scans linearly from index 0 to `limit`. When a version mismatch is found, it clears the entry (line 564) but doesn't decrement `count`. This means `count` can overcount valid entries, causing the scan to include cleared slots. The `count` field is supposed to be the number of valid entries, but it's never decremented on invalidation or eviction. This could cause the cache to appear full when it has many cleared slots, and the linear scan might hit cleared entries before valid ones because the circular buffer wraps around but the scan limit is wrong.

8. **Missing `#[cfg(test)]` on `CACHE_NAME` test override** (WR-05): In `dlp-hook-dll/src/classification_cache.rs` lines 65-66, the `CACHE_NAME` constant is overridden for tests using `#[cfg(test)]`. However, `#[cfg(test)]` only applies when running `cargo test` for the current crate. When the integration test in `dlp-hook-dll/tests/isolated_resync_recovery.rs` imports `dlp-hook-dll` as a dependency, it's compiled as a non-test library. The integration test uses `Local\DlpClassificationCache_TestPhase50_1` directly in `create_test_cache`, but the `CacheLookup::get()` method (used in production trampolines) would try to open `Global\DlpClassificationCache` because the integration test binary compiles `dlp-hook-dll` without `cfg(test)`. This is a test/production mismatch that could cause integration tests to pass while production code uses the wrong name. Actually, looking more carefully: the integration test creates `ClassificationCache` from `dlp-agent` with the test name, and then creates `CacheLookup::from_raw_pointer` with the raw pointer. It doesn't use `CacheLookup::get()`. So this is not a bug in the test. But the `CACHE_NAME` override is only for unit tests within the crate, not integration tests. This is a design issue, not a bug.

9. **Magic number 260 for path length** (IN-01): In `dlp-hook-dll/src/classification_cache.rs` line 417, the prefix length check uses `260` as a hardcoded maximum. This is the `MAX_PATH` constant on Windows but is not named as such. It should be a named constant.

10. **TODO comment in production code** (IN-02): In `dlp-hook-dll/src/lib.rs` line 543, there's a `TODO(Phase 53)` comment in production code. While not a bug, it's a code smell that indicates incomplete implementation.

## Critical Issues

### CR-01: Race Condition — Shutdown Silently Ignored During Thread Startup

**File:** `dlp-hook-dll/src/background_thread.rs:114-166`
**Issue:** The `start_background_thread` function drops the mutex guard while creating the Windows event and spawning the thread. During this window, `shutdown_background_thread` sees `Starting` and returns early without doing anything. The thread is then spawned and transitions to `Running`, but the shutdown signal was missed. This means the background thread can leak if shutdown is requested during startup.

**Fix:** Keep the mutex locked across the entire startup sequence, or use a separate atomic flag that `shutdown_background_thread` can set to request shutdown even before the thread is fully running. Alternatively, re-check the shutdown request after transitioning to `Running`.

```rust
// Option 1: Keep mutex locked across startup
let mut guard = BACKGROUND_THREAD_STATE.lock().unwrap();
match &*guard {
    BackgroundThreadState::NotStarted => {
        // Create event and spawn thread while holding lock
        let shutdown_event = unsafe { CreateEventW(...) }?;
        let thread_handle = std::thread::spawn(...);
        *guard = BackgroundThreadState::Running(BackgroundThread {
            shutdown_event,
            thread_handle,
        });
    }
    _ => return, // Already started
}
// Lock released here after thread is fully registered
```

### CR-02: Use-After-Free Risk in Background Thread Cache Header Access

**File:** `dlp-hook-dll/src/background_thread.rs:246-334`
**Issue:** The `background_thread_loop` receives a raw `*const CacheHeader` pointer. It checks `is_null()` defensively, but the pointer could become dangling if the `ClassificationCache` (agent-side) or `CacheLookup` (hook-side) that owns the mapping is dropped while the background thread is still running. The thread dereferences this pointer on every 100ms tick without any validity check. If the mapping is unmapped, this is a use-after-free that could crash the process or cause data corruption.

**Fix:** Use a shared atomic flag or `Arc<AtomicBool>` to signal when the mapping is valid. The background thread should check this flag before dereferencing the header. Alternatively, pass an `Arc<CacheHeaderProxy>` that implements `Drop` to set an invalidation flag.

```rust
// In the thread loop:
if cache_header.is_null() || !mapping_valid.load(Ordering::Acquire) {
    // Wait for shutdown
    loop { ... }
}
```

### CR-03: Thread Handle Leak and Struct Inconsistency in Shutdown

**File:** `dlp-hook-dll/src/background_thread.rs:174-222`
**Issue:** The `shutdown_background_thread` function uses `std::mem::replace` to swap the `JoinHandle` with a placeholder thread (line 187). This placeholder thread is never joined, leaking a thread handle. More critically, the `BackgroundThread` struct stored in `Running(bt)` now has a `thread_handle` pointing to a dummy thread instead of the actual running thread. If any future code accesses `bt.thread_handle` (e.g., for a second shutdown attempt), it will operate on the wrong thread.

**Fix:** Take ownership of the entire `BackgroundThread` struct from the mutex, not just the `JoinHandle`. Use `std::mem::take` or restructure the enum to allow taking the full struct.

```rust
// Restructure the enum:
enum BackgroundThreadState {
    NotStarted,
    Starting,
    Running { shutdown_event: HANDLE, thread_handle: JoinHandle<()> },
}

// In shutdown:
let (event, handle) = match &mut *guard {
    BackgroundThreadState::Running { shutdown_event, thread_handle } => {
        let event = *shutdown_event;
        let handle = std::mem::replace(thread_handle, std::thread::spawn(|| {}));
        *guard = BackgroundThreadState::NotStarted; // Transition immediately
        (event, handle)
    }
    _ => return,
};
drop(guard); // Release lock before waiting
// Signal and wait...
```

## Warnings

### WR-01: Dead Code — `decide_resync` Never Called in Production

**File:** `dlp-hook-dll/src/fail_mode.rs:399-418`
**Issue:** `decide_resync` is marked `#[allow(dead_code)]` and is never invoked by production code. The RESYNC state transitions back to HEALTHY after 5 successes, but during RESYNC, the actual hook trampolines don't appear to call `decide_resync`. This means the RESYNC state's decision logic is not actually wired into the enforcement path.

**Fix:** Either wire `decide_resync` into the hook trampoline decision path, or remove it if RESYNC is intended to use the same logic as ISOLATED/HEALTHY.

### WR-02: Stale Cache Transition Not Wired into State Machine

**File:** `dlp-hook-dll/src/fail_mode.rs:249-261`
**Issue:** The state machine documentation (line 552) states that `DEGRADED -> ISOLATED` can occur on "failures >= 10 OR cache stale". However, `record_pipe_failure` only checks `failures >= DEGRADED_TO_ISOLATED_THRESHOLD` and never calls `is_cache_stale`. The staleness check is tested in isolation but not integrated into the actual state transitions.

**Fix:** Add staleness checking to `record_pipe_failure` when in `Degraded` state:

```rust
FailState::Degraded => {
    if failures >= DEGRADED_TO_ISOLATED_THRESHOLD || is_cache_stale(...) {
        FailState::Isolated
    } else {
        FailState::Degraded
    }
}
```

### WR-03: Unsafe `set_state` Exposed as Public API Without Test Gating

**File:** `dlp-hook-dll/src/fail_mode.rs:323-325`
**Issue:** `set_state` allows direct manipulation of the fail-mode state without going through the proper transition guards. It's marked `pub` and not gated with `#[cfg(any(test, feature = "test-helpers"))]`, making it available to any consumer of the crate. This bypasses all hysteresis and safety checks.

**Fix:** Gate the function:

```rust
#[cfg(any(test, feature = "test-helpers"))]
pub fn set_state(&self, new_state: FailState) {
    self.state.store(new_state as u8, Ordering::Relaxed);
}
```

### WR-04: LRU Cache Count Not Decremented on Invalidation

**File:** `dlp-hook-dll/src/classification_cache.rs:555-566`
**Issue:** When `LruCache::get` finds a version mismatch, it clears the entry string (`self.entries[i].0.clear()`) but does not decrement `self.count`. This means `count` monotonically increases to 128 and then stays there, even when many entries are invalidated. The `get` method uses `self.count.min(128)` as the scan limit, so once `count` reaches 128, it always scans all 128 slots. This is inefficient and could cause the cache to skip valid entries that were inserted after invalidated ones because the circular buffer wraps around but the scan limit is wrong.

Actually, looking more carefully: `count` is only incremented in `insert` and never decremented. The `get` method scans `0..limit` where `limit = self.count.min(128)`. If `count` reaches 128, it scans all entries. But since invalidated entries have empty strings, they won't match any path. The real issue is that `count` represents the number of insertions, not valid entries. When an entry is invalidated, the slot is effectively empty but still counted. This doesn't cause incorrect results, just wasted iterations. However, if `count` is used elsewhere to make decisions about cache fullness, it would be wrong.

**Fix:** Decrement `count` when invalidating, or track valid entries separately:

```rust
// In get():
if *version == current_version {
    return Some(*classification);
}
// Version mismatch — remove the entry and compact.
self.entries[i].0.clear();
self.entries[i].1 = Classification::T1;
self.entries[i].2 = 0;
if self.count > 0 {
    self.count -= 1;
}
// Shift remaining entries to fill the gap (or use swap_remove pattern)
```

### WR-05: Missing `Drop` Implementation for `BackgroundThread`

**File:** `dlp-hook-dll/src/background_thread.rs:82-89`
**Issue:** `BackgroundThread` contains a Windows `HANDLE` and a `JoinHandle`. The struct has `#[allow(dead_code)]` on both fields, but there's no `Drop` implementation to ensure the event handle is closed. While `shutdown_background_thread` does call `SetEvent` and attempts to join, if the struct is dropped without going through shutdown (e.g., due to a panic or early return), the event handle leaks.

**Fix:** Implement `Drop` for `BackgroundThread`:

```rust
impl Drop for BackgroundThread {
    fn drop(&mut self) {
        unsafe {
            let _ = windows::Win32::Foundation::CloseHandle(self.shutdown_event);
        }
    }
}
```
