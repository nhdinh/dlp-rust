# Phase 58.10 Plan 01: Apply Enforcement Mode in Hook IPC Deny Path (Agent Side) Summary

**One-liner:** Extracted a pure 3-tuple enforcement-mode gate (`apply_effective_mode_to_hook_decision`) and a testable closure body (`evaluate_hook_request`) so the agent hook-IPC path flips any Audit-mode DENY to ALLOW and emits a full-parity audit, closing the agent-side half of gap MODE-01.

## What Was Built

The agent hook-IPC decision closure (`service.rs`) previously returned `offline.offline_decision(&evaluate_req)` verbatim, ignoring enforcement mode — so Audit-mode hook-mediated file operations were physically blocked instead of ALLOWed-with-audit, contradicting Phase 55 Success Criterion #2 on the hook path. This plan mirrors the verified interception-path pattern (`interception/mod.rs:413-465`) onto the hook path.

**Task 1 — pure helper (`0abb05c0`):**
- Added `apply_effective_mode_to_hook_decision(global_mode, &eval_resp) -> (Decision, bool, EnforcementMode)` — a pure function (no config access, no I/O) that computes the effective mode via `compute_effective_mode` and flips an audit-mode DENY to ALLOW. The 3-tuple returns `effective_mode` up front so the caller builds the audit's `policy_mode` string without recomputing.
- Added `#[cfg(test)] mod hook_ipc_mode_gate` with the six-test matrix: global {Audit, Block, PerPolicy, AuditAndBlock} x cache {hit, miss} x tier, asserting all three tuple elements. Cache-miss `None -> Block` default (D-02) means only a global Audit override relaxes the miss path (T-17 preserved).

**Task 2 — extracted closure body + shim (`63770634`):**
- Added `pub fn evaluate_hook_request(req, caller_sid, offline, approval, hash_cache, global_mode) -> (HookResponse, Option<AuditEvent>)`. It holds the full decision body (approval-override early return, COPY/MOVE volume-class warn, `offline_decision`, mode gate, Audit flip, exactly-one-audit construction). `global_mode` is an EXPLICIT parameter (no CONFIG `OnceLock`) and the audit is RETURNED (not emitted), so Plan 03's e2e test can drive Audit and Block cases in one process. Marked `pub` per the cross-plan visibility handoff.
- The production closure is now a thin shim: resolves identity (unchanged early return), reads `global_mode` LIVE via `with_config(|cfg| cfg.enforcement.global_mode)` every request (never captured at init), delegates to `evaluate_hook_request`, and emits the returned audit via `EMITTER.emit`.
- Exactly one audit per op: a full-parity `Access` audit on flip (`would_have_denied=true`, `policy_mode="Audit"`, the classification carried by the `EvaluateRequest`, app-identity enrichment via `enrich_audit_with_app_identity` + `set_destination_application`), the existing `Block` audit otherwise. No `BlockNotify` in Audit mode.
- Added two direct-call tests proving the extracted function end-to-end without the `OnceLock` or a live pipe: global Audit + cached DENY -> ALLOW + parity audit; global Block + cached DENY -> DENY + block audit.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Fixed `needless_borrow` clippy lint in extracted function**
- **Found during:** Task 2 (clippy run).
- **Issue:** `hook_request_to_evaluate_request(&req, ...)` where `req` is already `&HookRequest` produced a `&&HookRequest` double-reference (the original closure had `req` by value).
- **Fix:** Pass `req` directly (`hook_request_to_evaluate_request(req, ...)`).
- **Files modified:** `dlp-agent/src/service.rs`
- **Commit:** `63770634`

### Documented Limitation (classification tier on the parity audit)

**2. [Rule 4-adjacent / scope note] Parity audit threads `evaluate_req.resource.classification`, which is currently always `T1`**
- **Found during:** Task 2 test authoring.
- **Issue:** The plan's must-have truth #1 calls for the parity audit to carry "the REAL tier that drove the deny." However, `hook_request_to_evaluate_request` builds the `EvaluateRequest` with `resource: Resource { path, ..Default::default() }`, and `HookRequest` carries no classification field — so `evaluate_req.resource.classification` is always `Classification::T1` (the `Default`). Consequently, on a true cache MISS the fail-closed path (`fail_closed_response`) sees T1 and returns ALLOW, never DENY; the T3/T4 fail-closed DENY is only reachable via a cache HIT (a cached `EvaluateResponse`).
- **Resolution:** Implemented exactly as the plan's fixed `evaluate_hook_request` signature dictates — the parity audit threads `evaluate_req.resource.classification` (the only tier the function can know). The direct-call tests drive the flip via a cache HIT with a cached DENY (the D-06 path where the per-policy mode IS known), which is fully reachable and exercises the gate + parity-audit construction end-to-end. The pure-helper matrix (Task 1) covers the cache-miss T3/T4 semantics directly via hand-constructed `EvaluateResponse` values.
- **Impact / follow-up:** Threading the real path-based tier into the parity audit requires the DLL to send classification on `HookRequest` (a `HookRequest` schema change) or an agent-side path classifier — both are architectural changes outside this plan's fixed signature and are deferred. The agent-side mode gate, flip, and parity-audit machinery are all in place and correct; only the tier value is bounded by the current `HookRequest` shape. This does NOT weaken T-17 (the miss path stays fail-closed for non-Audit global modes) and does NOT affect the DLL-side fast-path (Plan 02/03), which knows the tier from the shared cache.
- **Files modified:** none beyond the planned change (documented here for the verifier).
