# Cross-AI Plan Review -- Phase 66.1

## Codex Review (GPT-5.5)

> Reviewer: Codex CLI (OpenAI GPT-5.5)
> Reviewed: 2026-06-11T17:30:00Z
> Model: gpt-5.5
> Status: Post-revision review (plans were already revised after Round 1/2)

### Summary

The plans cover much of the plumbing, but as written they do **not fully achieve Phase 66.1** because the hook DLL IPC enforcement path is explicitly deferred. That conflicts with success criterion 6 and the phase goal. The other major risks are around override placement: approval must override only an **ABAC DENY**, never an NTFS deny, service fail-closed deny, malformed/offline deny, or unrelated effective-mode block. Plan 03 also proposes reaching into `ApprovalCache` internals after `check()`, which is brittle and likely race-prone; the cache API should return the verified claims directly.

### Strengths

- **Plan 01:** Adds `matched_label_id` with `#[serde(default)]`, preserving compatibility. Correctly separates `ApprovalOverride` from `ApprovalUse`. SIEM routing with `triggers_alert = false` is correct.
- **Plan 02:** Correctly reuses server-side path-to-label resolution instead of duplicating logic in the agent. Keeps `resolve_tier()` as a compatibility wrapper. Covers exact, inherited, fallback, lookup-failed cases in tests.
- **Plan 03:** Correctly avoids using a nonexistent `get()` API. Recognizes that `ApprovalCache::check()` must perform JWT re-verification. Keeps cache wiring explicit.
- **Plan 04:** Correctly identifies that hook IPC lacks identity data and that guessing identity from path would be unsafe. Adds PID-to-SID resolution in a security-conscious fail-closed manner. Defers hook behavior rather than implementing an insecure approximation.

### Concerns

#### Plan 01
- **[MEDIUM]** Adding `ApprovalOverride` to `EventType` may require updates beyond `routed_to_siem()` and `triggers_alert()`, such as display formatting, database enum serialization, TUI filters, SIEM mapping, or exhaustive matches.
- **[MEDIUM]** The plan mentions audit event enrichment fields, but only modifies `audit.rs` for `EventType`. If the audit event schema does not already support `approver_sid`, `approval_expiry`, `justification`, and `would_have_denied`, this plan is incomplete.
- **[LOW]** Placing `matched_label_id` after `would_have_denied` is fine for serde JSON, but any non-serde positional/binary use of `EvaluateResponse` should be checked.

#### Plan 02
- **[HIGH]** Fallback behavior needs sharper definition. If fallback produces a tier but no concrete label ID, approval cache cannot safely match an approval token. Returning a synthetic or ambiguous label ID would be dangerous.
- **[MEDIUM]** `ResolvedTierWithId` duplicates existing `ResolvedTier` shape. If the existing enum encodes source/fallback behavior, a parallel struct can drift unless carefully mapped.
- **[MEDIUM]** "Set `matched_label_id` on ALL construction sites" is necessary but easy to miss. `EvaluateResponse::default_deny()` / `default_allow()` and ad hoc literals must all be covered.

#### Plan 03
- **[HIGH]** `check_approval_override()` reads `cache.cache.get(&key.encode())` after `cache.check()`. That reaches into internals, may not compile if private from the helper location, and introduces a race between validation and audit enrichment.
- **[HIGH]** The helper returning a modified `EvaluateResponse` is risky. Approval override is an enforcement decision and audit event, not necessarily a mutation of the server's ABAC evaluation result.
- **[MEDIUM]** `ApprovalCacheKey::from_evaluation(... dst: Option<&str>)` needs a canonical destination encoding. Passing `None` must map exactly to how approval tokens encode no destination.
- **[MEDIUM]** The plan does not mention action normalization. `abac_action.to_string()` must exactly match approval workflow action strings.
- **[LOW]** Adding a ninth positional parameter to `spawn_event_loop` increases call-site fragility.

#### Plan 04
- **[HIGH]** The plan does not satisfy the phase goal or success criterion 6 because hook DLL IPC override is deferred. This should be a blocker for Phase 66.1 as scoped.
- **[HIGH]** "After effective mode computation, only when blocking and DENY" is too broad. Approval must override only an **ABAC DENY**. It must not override NTFS deny, fail-closed offline deny, tier-gated deny, malformed request deny, or system protection deny.
- **[HIGH]** Hook IPC structural wiring without actual override may create a false sense that WORKFLOW-04 is complete.
- **[MEDIUM]** `get_sid_for_pid` uses Windows APIs that require careful handle cleanup. The plan should explicitly require RAII/handle closing.
- **[MEDIUM]** `OpenProcess(PROCESS_QUERY_INFORMATION)` may fail where `PROCESS_QUERY_LIMITED_INFORMATION` would succeed.
- **[MEDIUM]** Audit event enrichment must preserve the original deny reason/policy and add approval metadata, not overwrite too much context.

### Suggestions

1. **Change `ApprovalCache::check()` to return `Option<ApprovalClaims>`** containing verified claims. This avoids internal map access and keeps verification/audit data atomic.
2. **Return a distinct result** like `ApprovalOverrideDecision { claims, key }` instead of mutating `EvaluateResponse`.
3. **Split the phase honestly:** either keep Phase 66.1 scoped to file monitor only and change success criteria, or include hook IPC ABAC evaluation plus identity propagation/resolution now.
4. **Add an explicit guard:** approval override is allowed only when `ntfs_allowed == true`, ABAC decision is deny, and the deny source is policy evaluation with `matched_label_id = Some`.
5. **Add tests proving approval does not override NTFS deny** and does not override offline fail-closed deny.
6. **Use `PROCESS_QUERY_LIMITED_INFORMATION`** in `get_sid_for_pid` for broader compatibility with protected processes.
7. **Add tests for action string mismatch** and destination-scope mismatch.

### Risk Assessment

**HIGH.** The shared/server plans are mostly reasonable, but the implementation set does not yet meet the stated phase requirements. The hook path is deferred, and the file path needs stronger source-of-deny gating to ensure approval tokens override only ABAC denies. Before execution, revise the plans around three points: make `ApprovalCache::check()` return verified claims, define canonical key/action/destination mapping, and either implement hook IPC approval end-to-end or explicitly rescope the phase.

### Claude Review (Round 1)

#### Summary

The four-plan structure follows a sound dependency chain: shared types (Wave 1), server-side population (Wave 1), service-layer plumbing (Wave 2), and enforcement-path integration (Wave 3). Plans 01-03 are well-scoped with clear contracts and backward-compatibility measures. Plan 04, however, carries the bulk of the risk: the hook DLL path's user identity resolution is semantically incorrect (using file-path-based SID resolution instead of process-based), the `check_approval_override` helper assumes cache API methods that may not exist, and several audit-event fields are left as hardcoded placeholders. The plans will achieve the phase goal for the file monitor path, but the hook DLL path may enforce approvals against the wrong user identity if implemented exactly as specified.

#### Strengths

- **Clean dependency ordering.** Waves 1->2->3 are correctly sequenced; Plan 04 correctly declares dependencies on all three upstream plans.
- **Backward compatibility is addressed.** `#[serde(default, skip_serializing_if = "Option::is_none")]` on `matched_label_id` prevents deserialization failures with cached offline responses; `resolve_tier` kept as a thin wrapper avoids breaking existing consumers.
- **Shared helper extraction.** `check_approval_override` and `ApprovalCacheKey::from_evaluation` in Plan 03 eliminate duplication between the two enforcement paths and centralize the override logic.
- **Audit trail design is thorough.** `EventType::ApprovalOverride` with `would_have_denied=true`, `approver_sid`, `approval_expiry`, and `justification` provides a complete compliance record; `triggers_alert=false` prevents false-positive storms.
- **Fail-closed behavior is preserved.** When `matched_label_id` is `None` (offline mode), the approval cache check is skipped and the original DENY stands.
- **Threat model coverage.** Each plan includes a STRIDE register with specific threat IDs and mitigations.

#### Concerns

##### Plan 01
- **LOW:** `EventType::ApprovalOverride` insertion order in the enum should be carefully placed to avoid disrupting existing variant ordinal values if any code relies on `discriminants()` or `as u32` casts. Verify no downstream code does ordinal-dependent matching.

##### Plan 02
- **LOW:** `depends_on: []` is technically incomplete. While `dlp-server` compiles against the current `dlp-common`, once `PolicyStore::evaluate` sets `matched_label_id`, the `dlp-common` change from Plan 01 must be available. Wave grouping handles this, but the explicit dependency should be `["66.1-01-PLAN.md"]`.

##### Plan 03
- **HIGH:** The `check_approval_override` implementation calls `cache.get(&key)` (line 179) and `cache.check(&key, dst)` (line 181), but the `ApprovalCache` API documented in the research only exposes `check()`, `insert()`, `remove()`, `sweep_expired()`, `len()`, and `is_empty()`. There is no `get()` method. The plan includes a fallback note ("implement `get_unchecked`"), but this is a real API gap that must be resolved before implementation. If `cache.check()` already performs full JWT re-verification, calling both `get()` and `check()` would double-verify.
- **MEDIUM:** The `check_approval_override` function signature returns `Option<(EvaluateResponse, ApprovalClaims)>` but the research code example only returns `Option<EvaluateResponse>`. The tuple return is the right choice for audit enrichment, but verify that `ApprovalClaims` is `Clone` (it likely is) since the helper clones it.

##### Plan 04
- **HIGH:** **Hook DLL path uses wrong identity resolution.** Task 3 uses `session_map.resolve_for_path(&req.path)` to obtain the user SID. In `run_event_loop`, this is correct because the file monitor is session-scoped and the path belongs to that user's session. In the hook DLL path, `req.path` is the *target file being accessed*, not the *requesting user's session*. Two different users can access the same file path. Using path-based resolution means the hook path could check approvals for the wrong SID, causing either false denials (cache miss for correct user) or **false allows** (cache hit for wrong user). This is a security-critical bug. The correct approach is to use `get_sid_for_pid` (added in Task 1) on the process PID, but `HookRequest` does not carry a PID. Either add `pid` to `HookRequest` (with bincode compatibility risk) or find another IPC context to resolve the caller identity.
- **MEDIUM:** **Destination scope is always `None`.** Both enforcement paths pass `None` for `dst`. This means destination-specific approvals (e.g., "approve copy to USB drive X only") will not work. The research acknowledges this as an open question, but the plans should either (a) derive `dst` from the operation context or (b) explicitly document that destination-scoped approvals are not yet supported in this phase.
- **MEDIUM:** **Hook IPC audit event has hardcoded `None` and `0`.** Task 3 sets `agent_id: None` and `session_id: 0` with comments "may need to thread through." These are not optional cosmetic fields; they are required for audit correlation. The plan should specify how `agent_id` and `session_id` are obtained and threaded through `HookIpcServer` before claiming the task is done.
- **MEDIUM:** **Failed approval annotation is misleading.** Task 2 appends "approval invalid or expired" whenever `matched_label_id.is_some()` and the cache misses. This message is wrong when the user simply never had an approval for that label/action. It should distinguish between "no approval found" and "approval expired/invalid."
- **MEDIUM:** **`get_sid_for_pid` may fail with `ERROR_ACCESS_DENIED`.** `OpenProcess` with `PROCESS_QUERY_INFORMATION` on arbitrary PIDs can fail for protected processes, cross-session processes, or processes with higher integrity levels. The function returns `Option<String>`, which handles failure gracefully, but the hook path must not assume SID resolution always succeeds.
- **LOW:** **No metrics or observability.** The plans do not include any `tracing` spans or counters for approval cache hit/miss rates in enforcement. Given the ~50us JWT verification cost, operators will want visibility into how often this path is exercised.

#### Suggestions

- **Fix hook DLL identity resolution before implementing Plan 04.** Options in order of preference:
  1. Add `pid: u32` to `HookRequest` with `#[serde(default)]` and update the hook DLL to populate it (bincode + default is safe if the DLL rebuild is coordinated).
  2. Use the pipe connection's client token to resolve SID (if the named pipe identity is available).
  3. If neither is feasible, document that hook-path approval overrides are deferred and the hook path should skip the approval check (fail-closed) rather than use the wrong identity.
- **Verify `ApprovalCache` internal API before coding Plan 03.** Read `dlp-agent/src/approval_cache.rs` to confirm whether `get()` exists. If not, implement `get_unchecked` that returns `Option<&CachedApproval>` without JWT verification, since `check()` already re-verifies.
- **Improve block reason annotation.** Use three cases: (a) no `matched_label_id` -> no annotation, (b) `matched_label_id` present but no cache entry -> "blocked -- no active approval", (c) cache entry present but invalid/expired/scope mismatch -> "blocked -- approval invalid or expired."
- **Thread `agent_id` and `session_id` through `HookIpcServer`.** The `service.rs` call site that constructs `HookIpcServer` has access to these values; pass them into the server struct so audit events are complete.
- **Add tracing for enforcement decisions.** Add `tracing::debug!` logs for approval cache hit/miss in both paths to aid production debugging.
- **Add a cross-crate integration test.** Verify that a full flow (server evaluates -> agent checks cache -> override applied) works end-to-end, not just unit tests in individual crates.

#### Risk Assessment

**Overall Risk Level: MEDIUM**

**Justification:** Plans 01-03 are low-risk, well-bounded type and plumbing changes with clear test coverage. Plan 04 carries the bulk of the risk due to the hook DLL identity resolution gap, which is a **security-relevant correctness issue** rather than a simple bug. If implemented as written, the hook path could check approvals against the wrong user SID, potentially allowing unauthorized access. The file monitor path is sound and will work correctly. The `ApprovalCache` internal API uncertainty in Plan 03 is a compilation risk but easily resolved during implementation. The destination-scope gap is a functional limitation but not a security issue. Recommend resolving the hook DLL identity question before executing Plan 04.

### OpenCode Review (Round 1)

#### Summary

This is a well-scoped, tightly focused phase that correctly identifies the core gap (ApprovalCache exists but is never consulted) and proposes a clean three-wave strategy: shared types -> server-side population -> service-layer wiring -> enforcement integration. The file-monitor path is thoroughly specified. The hook IPC path has significant unresolved gaps that risk leaving it half-wired. Overall the plan is sound but needs tighter specification around the hook path, action string normalization, and error handling.

#### Strengths

- **Correct architectural layering**: Adding `matched_label_id` to `EvaluateResponse` (Plan 01) before wiring the cache (Plan 03) is the right dependency order. Without the label ID, the `ApprovalCacheKey` cannot be constructed.
- **Wave ordering is clean**: Shared types -> server-side -> service wiring -> enforcement. No circular dependencies between waves.
- **Shared `check_approval_override` helper** (Plan 03): Extracting the approval cache check into one function used by both enforcement paths prevents divergence and duplicated logic.
- **Backward compat via serde attributes**: Adding `#[serde(default)]` and `#[serde(skip_serializing_if)]` on the new field is the correct approach -- `EvaluateResponse` only crosses the wire as JSON (confirmed: no bincode path), so this is safe.
- **Proper audit semantics**: `routed_to_siem()=true`, `triggers_alert()=false` for `ApprovalOverride` is the correct choice -- overrides should be logged for compliance but not trigger security alerts.
- **`spawn_event_loop` has only 1 call site** (at `service.rs:1627`), minimizing signature-change blast radius.

#### Concerns

##### Plan 03 -- Service-layer wiring

1. **HIGH: Tests call `run_event_loop` directly, not `spawn_event_loop`** -- The plan only mentions updating `spawn_event_loop` and `run_event_loop` signatures. But all existing tests pass `run_event_loop` parameters directly (confirmed: 0 test call sites for `spawn_event_loop`, multiple direct `run_event_loop` calls in tests). These test call sites must also be updated, or a builder/options struct should be used to avoid breaking them. Every test that constructs a `run_event_loop` call will need an `Arc<ApprovalCache>` argument -- this is ~5-8 test sites across `interception/mod.rs`, `comprehensive.rs`, etc.

2. **MEDIUM: 8th positional parameter is a code smell** -- `run_event_loop` already takes 8 positional arguments. Adding a 9th (`approval_cache`) makes it harder to read and maintain. Consider introducing an `InterceptionOptions` / `RunLoopConfig` struct that bundles the optional enforcers + approval cache. This is a refactoring opportunity the plan should consider -- or at minimum, `approval_cache` should be grouped adjacent to the other `Arc` parameters, not tacked on at the end.

3. **LOW: `run_event_loop` signature change requires updating all callers in a single commit** -- If Plan 03 and Plan 04 are in different waves, the code won't compile between them unless the signature change happens in the same wave as the first consumer. Ensure Plan 03 + Plan 04 are not split across merges.

##### Plan 04 -- Enforcement wiring

4. **HIGH: Hook IPC path has no SID/PID source** -- `HookRequest` does NOT carry `user_sid` or `pid` fields (confirmed). Plan 04's hook path says "check approval cache after inner_handler returns DENY" but provides no mechanism to construct the `ApprovalCacheKey` (which requires a SID). The plan adds `get_sid_for_pid()` to `identity.rs`, but **`HookRequest` is never extended to carry a PID**. Without either (a) adding `pid` to `HookRequest`, (b) adding `user_sid` directly to `HookRequest` (cheaper -- the hook DLL can get it from the thread token via `GetUserNameExW`), or (c) skipping the hook path entirely for this phase, the hook enforcement path **cannot work**.

5. **HIGH: Hook IPC `inner_handler` does not perform real ABAC evaluation** -- Current `inner_handler` in the hook path is a placeholder (heuristic-based or test stub). `HookResponse` is a different type from `EvaluateResponse`. The plan says "After inner_handler returns DENY" -- but there is no ABAC policy evaluation in the hook path today. Wiring approval cache override without first wiring real ABAC evaluation means the cache check is never reached. This is either a missing prerequisite or the plan implicitly assumes another phase delivers it.

6. **MEDIUM: `with_cache` name collision** -- `HookIpcServer::with_cache()` already exists (line 108 of `hook_ipc.rs`) and wraps a `CacheAccessor` for classification cache hints, NOT the `ApprovalCache`. The plan says "Extend HookIpcServer to accept approval_cache" but the existing `with_cache` takes `Arc<dyn CacheAccessor>`. This will require either a new constructor (e.g., `with_approval_cache`) or modifying `with_cache` to accept a second cache -- which changes its signature for existing callers.

7. **MEDIUM: Action string normalization between paths** -- The file monitor path maps actions via `PolicyMapper::action_for(&action)`. The hook DLL path receives raw action strings (`"CREATE"`, `"WRITE"`, etc.) from the DLL. `ApprovalCacheKey` uses these action strings for matching. If approval tokens store action strings in one format and the enforcement path uses a different format, the cache lookup will miss. The plan should specify action string normalization (or at minimum document that both paths must use the same action vocabulary).

8. **MEDIUM: `get_sid_for_pid` error handling** -- The plan adds `get_sid_for_pid(pid: u32) -> Option<String>`. `OpenProcess` can fail for protected processes (`STATUS_ACCESS_DENIED`), and `OpenProcessToken` fails for exited processes. When `None` is returned, the caller must gracefully fall through (skip approval cache check and keep the DENY). The plan should explicitly document this "fail-closed on SID resolution failure" behavior.

9. **LOW: Approval stale window** -- The poll task runs every 60 seconds. Between polls, if an approval is revoked on the server, the cache still returns it as valid (assuming the JWT hasn't expired). This is a design property of the polling approach, not a bug, but the plan should acknowledge the staleness window and document it as a known limitation.

##### Plan 01 -- Shared types

10. **MEDIUM: `EventType::ApprovalOverride` vs existing `EventType::ApprovalUse`** -- The audit module already has `EventType::ApprovalUse` (line 195 of `audit.rs`, defined in Phase 61) with identical routing properties (`routed_to_siem()=true`, `triggers_alert()=false`). `ApprovalUse` was intended for tracking approval consumption at enforcement time but was never emitted. Adding `ApprovalOverride` creates two semantically overlapping variants. What distinguishes them? Options: (a) reuse `ApprovalUse` (removes dead code), (b) clearly document that `ApprovalOverride` is the *enforcement-time* event while `ApprovalUse` is reserved for a different purpose. Without clarification, this adds confusion to the audit schema.

11. **LOW: `cache.rs` constructors for `EvaluateResponse` need updating** -- `cache.rs:178` and `cache.rs:186` construct `EvaluateResponse` directly (for `fail_closed_response`). These will not include `matched_label_id` since they're offline fallback paths. This is correct behavior (offline = no label resolution), but the plan should verify these constructors still compile and work as expected -- they should default `matched_label_id` to `None`.

##### Plan 02 -- Server-side

12. **MEDIUM: Server-side callers of `resolve_tier`** -- The plan keeps `resolve_tier` as a thin wrapper. The research didn't enumerate all callers of `resolve_tier` within the server. If `resolve_tier` is called from `PolicyStore::evaluate` and the plan switches to `resolve_tier_and_label_id`, all internal callers must be audited. If any callers exist outside `PolicyStore::evaluate` (e.g., admin API endpoints), they should continue using `resolve_tier` -- which the plan correctly handles by keeping the old function.

13. **LOW: Offline mode limitation is correct but worth documenting in PLAN.md** -- The plan acknowledges `matched_label_id` is `None` in offline mode (fail-closed). This means approval cache keys cannot be constructed offline, so approval overrides won't work in offline mode. This is the correct design (approval tokens require server verification), but should be explicitly documented so it's not mistaken for a bug later.

#### Suggestions

1. **Add `pid` to `HookRequest` or shortcut through thread token** -- The hook path gap must be resolved. The cleanest approach: have the hook DLL query its own PID (`GetCurrentProcessId()`) and send it in `HookRequest.pid`. The agent service then calls `get_sid_for_pid(pid)` to resolve the SID. This avoids serializing SID strings over the pipe (saves ~40 bytes per request). Alternatively, have the DLL query the thread token SID and send it directly in `HookRequest` -- simpler but slightly more coupling.

2. **Introduce `InterceptionOptions` struct or use `Option<Arc<ApprovalCache>>`** -- To avoid the 9th parameter, either bundle the optional enforcement components into a config struct, or accept `Option<Arc<ApprovalCache>>` in `run_event_loop` (defaulting to `None` = no approval override capability). This also makes signature changes backward-compatible for tests that don't need the approval cache.

3. **Remove dead `EventType::ApprovalUse` or merge with `ApprovalOverride`** -- If `ApprovalOverride` supersedes `ApprovalUse`, remove the now-dead variant from the `EventType` enum in this same phase. If both are needed, add doc comments to each clarifying the semantic distinction.

4. **Add action string normalization documentation or validation** -- Add a comment or small mapping function that ensures action strings from both enforcement paths use the same vocabulary before constructing `ApprovalCacheKey`. The simplest fix: `ApprovalCacheKey::from_evaluation` should accept an `action: &str` and call `.to_uppercase()` or similar normalization.

5. **Document the fail-closed behaviors explicitly** -- Add PLAN.md entries for:
   - "What happens if `get_sid_for_pid` returns `None`?" -> Skip cache, keep DENY
   - "What happens if `matched_label_id` is `None`?" -> Skip cache, keep DENY
   - "What happens if the approval JWT re-verification fails?" -> Log, skip cache, keep DENY
   All of these should produce distinct audit log messages so operators can diagnose silent failures.

6. **Add `would_have_denied` propagation** -- The `ApprovalCache::check()` currently returns a hardcoded `EvaluateResponse` with `would_have_denied: false`. When called as an override (Plan 04), it should preserve the original ABAC response's `would_have_denied` value. Either: (a) extend `check_approval_override` to accept the original response and propagate its `would_have_denied`, or (b) have the audit event read it from the original response before overriding.

7. **Consider approval cache pre-check before ABAC evaluation** -- For the hook hot path (~50us JWT reverification on every DENY), consider: is there a fast-path where we check the cache BEFORE ABAC evaluation? If the cache has a valid approval, we could skip ABAC entirely. This saves ~2-5ms of evaluation time per hit at the cost of doing Ed25519 verification even for ALLOWs. Worth profiling but likely not needed for v1.

#### Risk Assessment

**Overall: MEDIUM** (elevated from LOW due to hook path gaps)

**Justification:**
- The file-monitor enforcement path (the more common path) is LOW risk -- well-specified, correct dependency order, minimal blast radius (1 call site).
- The hook IPC path has **two HIGH-severity gaps** (no SID/PID, no real ABAC evaluation) that must be resolved before the phase can deliver end-to-end hook path coverage. These gaps do not affect the file-monitor path, so the phase can succeed without them -- but the PLAN.md should explicitly scope the hook path as partially deferred if SID resolution is postponed.
- The `EvaluateResponse` field addition is safe (JSON-only wire format). The server-side change is contained. The service-layer wiring has manageable blast radius.
- If the hook path is explicitly deferred to a follow-up phase and the scope is narrowed to "file-monitor path only," risk drops to **LOW**. Recommend the plan authors decide whether to fully resolve the hook path gaps in this phase or cut scope.

### Claude Review (Round 2)

#### Summary

The four plans form a coherent, well-staged implementation that correctly closes the WORKFLOW-04 gap. The wave-based dependency structure (shared types -> server-side population -> service-layer plumbing -> enforcement integration) is logical and minimizes blast radius. The decision to **defer hook DLL path overrides** is well-justified given the research findings on incomplete PID-to-SID identity resolution and missing real ABAC evaluation in that path. Security posture is strong throughout, with consistent fail-closed defaults, proper JWT re-verification on cache reads, and dedicated audit events that route to SIEM without triggering alert storms. The test coverage is comprehensive across all four waves.

#### Strengths

- **Excellent backward compatibility**: `#[serde(default, skip_serializing_if = "Option::is_none")]` on `matched_label_id`, `Option<Arc<ApprovalCache>>` parameters, and thin wrapper preservation of `resolve_tier` all minimize breakage risk.
- **Clear three-stage pipeline preserved**: NTFS check -> ABAC policy check -> approval cache override. The override is explicitly positioned as the **final** stage, which matches the security invariant.
- **Fail-closed by default**: Every error path (`get_sid_for_pid` failure, cache miss, race condition, offline mode) falls through to DENY or skip.
- **Well-justified deferral**: Hook DLL override is deferred with structural prep only -- avoids building on unstable foundations (wrong identity resolution, no ABAC evaluation).
- **Comprehensive test coverage**: Each plan specifies exact test scenarios including edge cases (inherited match, disabled label-aware, offline no label_id, audit mode skip).
- **Audit event design is operationally sound**: `ApprovalOverride` routes to SIEM (`triggers_alert=false`) ensuring visibility without noise; `would_have_denied=true` preserves the original decision for compliance trails.
- **Threat model integration**: Each plan references specific threats (tampering, repudiation, information disclosure) and maps mitigations to concrete code changes.

#### Concerns

- **[MEDIUM] Race condition in `check_approval_override`**: The helper calls `cache.check()` then immediately reads `cache.cache.get(&key.encode())`. Between these two operations, a concurrent `sweep_expired()` or background poll could remove the entry. The helper returns `None` -> falls through to DENY (fail-closed, so safe), but the ~50us Ed25519 re-verification is wasted and the audit trail won't reflect that a valid token *was* present momentarily. More importantly, this couples the helper to the `pub` DashMap internal structure -- a refactor of `ApprovalCache` storage could silently break this.
- **[MEDIUM] `get_sid_for_pid` privilege model untested**: `OpenProcess(PROCESS_QUERY_INFORMATION)` fails for protected processes (browsers with sandboxing, anti-cheat software, some security agents). The service account running `dlp-agent` may not have `SeDebugPrivilege`. Fail-closed is correct, but when the hook path is eventually wired, legitimate operations from protected processes will be incorrectly blocked. This limitation should be documented beyond a simple code comment.
- **[MEDIUM] Offline mode creates an approval gap**: When the server is offline, `EvaluateResponse` carries no `matched_label_id`, so the approval cache is never consulted.
