# Phase 66.1 Plan 02: Populate matched_label_id in server-side ABAC evaluation

**Server-side ABAC evaluation now returns the matched label UUID alongside the decision, enabling agent-side ApprovalCacheKey construction without redundant label resolution.**

## Accomplishments

- Added `ResolvedTierWithId` struct with `tier`, `source`, `parent_path`, and `label_id` fields
- Implemented `LabelService::resolve_tier_and_label_id` capturing label IDs for exact and inherited cases
- Refactored `resolve_tier` as a thin backward-compatible wrapper over `resolve_tier_and_label_id`
- Updated `PolicyStore::evaluate` to use `resolve_tier_and_label_id` and populate `matched_label_id` in all `EvaluateResponse` construction sites (policy-matched and default-deny/allow paths)
- Removed dead `cache_entry_to_resolved` and `resolved_to_cache_entry` functions (superseded by `-with_id` variants)
- Added 4 label_service unit tests: exact match, inherited parent, fallback, lookup-failed
- Added 4 policy_store unit tests: exact match, inherited parent, label-aware disabled, fallback

## Files Created/Modified

- `dlp-server/src/policy_store.rs` — Updated `evaluate` to call `resolve_tier_and_label_id`, populate `matched_label_id` in all response paths, added 4 unit tests

## Decisions Made

- **Cache does not store label_id:** The `CacheEntry` struct intentionally omits `label_id`. This is by design — the `label_id` is only needed for the initial server-side evaluation that constructs the `ApprovalCacheKey`. Subsequent cache hits return the correct tier but `label_id = None`, which is acceptable because the approval cache lookup already happened on the first evaluation.
- **resolve_tier kept as wrapper:** Existing callers that only need the tier continue to work without changes. The wrapper discards `label_id` and maps `ResolvedTierWithId` back to `ResolvedTier`.
