# Phase 66.1: workflow-04-approvalcache-enforcement - Context

**Gathered:** 2026-06-11
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 61 built the Approval Workflow Engine with a complete agent-side `ApprovalCache` (JWT verification, TTL expiry, background polling from server). However, the cache is **never consulted during enforcement** — the `interception::run_event_loop` evaluates ABAC via `offline.evaluate()` and determines the final decision without checking approvals, and the hook DLL IPC handler (`hook_ipc.rs`) also skips the cache. This phase wires `ApprovalCache::check()` into both enforcement paths so that approved operations (carrying a valid JWT token) override an ABAC DENY.

**Requirements:** WORKFLOW-04

**Success Criteria (what must be TRUE):**
1. When a user has a valid approval token for (sid, data_object_id, action, destination_scope), an ABAC DENY on that exact tuple is overridden to ALLOW by the agent.
2. The override is validated with Ed25519 JWT signature re-verification (~50us) against the cached server public key.
3. Expired or revoked tokens are rejected (lazy expiry on access + 60s background sweep).
4. Destination scope mismatches (e.g. USB drive A approval used for USB drive B) are rejected.
5. Every approval override emits an auditable event with approver SID, approval ID, expiry, and justification.
6. The override check works in both the file monitor event loop and the hook DLL IPC handler.

</domain>

<decisions>
## Implementation Decisions

### data_object_id resolution (D-01)
- **D-01.1:** Add `matched_label_id: Option<String>` to `EvaluateResponse` in `dlp-common/src/abac.rs`. The server already resolves path -> label during ABAC evaluation; returning the matched label ID lets the agent reuse the server's resolution to build `ApprovalCacheKey`.
- **D-01.2:** The new field uses `#[serde(default)]` for backward compatibility with existing EvaluateResponse consumers.
- **D-01.3:** When the server is offline, `EvaluateResponse` carries no `matched_label_id`, so the approval cache cannot be consulted. This is acceptable: offline mode already falls back to tier-gated fail-closed/fail-open semantics (FAIL-01..03 from Phase 50).

### Integration points — file monitor vs hook DLL (D-02)
- **D-02.1:** Wire approval cache check into **both** enforcement paths:
  - File monitor path: `dlp-agent/src/interception/mod.rs` in `run_event_loop`, after `offline.evaluate()` returns and after effective mode is computed. If `response.decision == DENY` and `effective_mode` is not Audit-only, call `ApprovalCache::check()` with the resolved `ApprovalCacheKey`.
  - Hook DLL path: `dlp-agent/src/hook_ipc.rs` in `handle_hook_request`, after the `inner_handler` returns its `HookResponse`. If `response.decision == DENY`, check `ApprovalCache`.
- **D-02.2:** In both paths, the approval cache check is the **final override** after all other evaluation is complete. The three-stage pipeline from Phase 61 is preserved: NTFS check -> ABAC policy check -> approval cache override.

### Audit event on approval override (D-03)
- **D-03.1:** Emit a **dedicated `EventType::ApprovalOverride`** (new enum variant in `dlp-common/src/audit.rs`) when an approval token overrides a DENY.
- **D-03.2:** The override event carries:
  - `matched_policy_id = Some("approval:{jti}")`
  - `approver_sid` (from the cached approval claims)
  - `approval_expiry` (from `claims.exp`)
  - `justification` (from the cached approval claims, or "pre-approved" if absent)
  - `would_have_denied = true`
- **D-03.3:** The event routes through SIEM relay with `triggers_alert = false` (this is a legitimate override, not a security incident).
- **D-03.4:** If the approval check fails (expired, bad signature, scope mismatch), emit a standard `EventType::Block` with `reason` annotated ("blocked — approval invalid or expired").

### Claude's Discretion
- Approval cache check ordering: cache check happens AFTER effective mode computation. If `effective_mode.is_audit()`, the physical operation is already ALLOWed (audit-only mode from Phase 55) — no need to check the approval cache because the operation proceeds regardless. This avoids unnecessary JWT verification overhead.
- `ApprovalCacheKey` construction: use `matched_label_id` from `EvaluateResponse` as `obj_id`; if `None`, skip approval cache check (can't form a valid key).
- The hook DLL path reuses the same `ApprovalCacheKey` construction logic as the file monitor path — extract a shared helper in `dlp-agent/src/approval_cache.rs` (e.g. `ApprovalCacheKey::from_evaluation(response, sid, action, dst)`).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `ApprovalCache` (`dlp-agent/src/approval_cache.rs`): Fully functional lock-free cache with Ed25519 JWT re-verification, TTL expiry, lazy eviction, destination scope matching (`scope_matches` with exact + prefix-wildcard). Already wired into `RunLoopContext` and populated by background poll task.
- `EvaluateResponse` (`dlp-common/src/abac.rs`): Currently has `decision`, `matched_policy_id`, `reason`, `enforcement_mode`, `would_have_denied`. Adding `matched_label_id` is a trivial additive change.
- `EventType` (`dlp-common/src/audit.rs`): Extensible enum with `#[serde(default)]` support for new variants. Add `ApprovalOverride` here.
- `AuditEvent::with_policy()` and `AuditEvent::with_would_have_denied()` — existing builder methods for audit enrichment.

### Established Patterns
- **Three-stage pipeline** (Phase 61 CONTEXT.md): NTFS check -> ABAC policy check -> approval cache override. The third stage is missing; this phase adds it.
- **Effective mode computation** (Phase 55): `compute_effective_mode(global_mode, policy_mode)` in `dlp-common/src/abac.rs`. Audit mode short-circuits to ALLOW before the approval cache check.
- **Audit emission in run_event_loop**: Build `AuditEvent` with `AuditEvent::new(...)` -> enrich with `with_policy()`, `with_would_have_denied()`, `with_access_context()` -> `emit_audit()`. Same pattern applies for `ApprovalOverride` events.
- **Hook IPC cache-aware handler** (`hook_ipc.rs`): `handle_hook_request()` wraps `inner_handler` and post-processes the response. Same pattern: post-process `HookResponse` to check approval cache when `decision == DENY`.

### Integration Points
- `dlp-agent/src/interception/mod.rs:408` — `let response = offline.evaluate(&request).await;` — insert approval cache check after this line, before effective mode is applied (actually AFTER effective mode, but only when effective_mode is not Audit).
- `dlp-agent/src/interception/mod.rs:412-418` — effective mode computation. If `effective_mode.is_audit()`, skip approval cache check.
- `dlp-agent/src/hook_ipc.rs:298` — `let mut response = inner_handler(req.clone());` — insert approval cache check after this line.
- `dlp-agent/src/service.rs:1016` — `approval_cache: Arc<crate::approval_cache::ApprovalCache>` is already in `RunLoopContext` and passed through.
- `dlp-server/src/policy_store.rs` — Add `matched_label_id` population during ABAC evaluation (likely in the policy match logic where label resolution already happens).

### Code Gaps
- `dlp-agent/src/interception/mod.rs` `run_event_loop` has NO reference to `ApprovalCache` — it is not passed as a parameter. The `spawn_event_loop` call site in `service.rs` must be updated to pass `Arc<ApprovalCache>` through.
- `dlp-agent/src/hook_ipc.rs` `handle_hook_request` has no access to `ApprovalCache`. The `HookIpcServer::with_cache` constructor and handler wiring need to be extended.
- `dlp-common/src/abac.rs` `EvaluateResponse` has no `matched_label_id` field.
- `dlp-common/src/audit.rs` `EventType` has no `ApprovalOverride` variant.

<specifics>
## Specific Ideas

- Approval cache check helper: Extract a shared function `check_approval_override(cache, response, sid, action, dst) -> Option<EvaluateResponse>` in `approval_cache.rs` to avoid duplicating the logic between file monitor and hook DLL paths.
- The `ApprovalCacheKey` uses `obj_id` (label ID) not path. If server offline returns no `matched_label_id`, the agent cannot check approvals — this is correct fail-closed behavior.
- For the hook DLL path, the hook request (`HookRequest`) does not carry the user SID. The agent must resolve the user SID from the process PID (same pattern as `run_event_loop` does via `session_map.resolve_for_path`). This may require extending the hook request or using the process PID from the request.
- The approval poll task in `service.rs` already fetches active approvals from `GET /agent/approvals/active` and populates the cache. No server-side changes needed for the poll mechanism.
</specifics>
