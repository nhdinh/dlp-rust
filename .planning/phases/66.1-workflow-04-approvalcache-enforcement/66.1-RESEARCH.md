# Phase 66.1: Close gap: WORKFLOW-04 — wire ApprovalCache into enforcement

**Researched:** 2026-06-11
**Domain:** Rust / Windows DLP Agent — ABAC enforcement pipeline integration
**Confidence:** HIGH

## Summary

Phase 61 built a fully functional `ApprovalCache` in `dlp-agent/src/approval_cache.rs` with Ed25519 JWT re-verification, TTL expiry, lazy eviction, destination scope matching, and a background poll task that syncs active approvals from the server every 60 seconds. The cache is already wired into `RunLoopContext` at `service.rs:1016` and populated at startup (`service.rs:1224-1242`). However, **the cache is never consulted during enforcement** — neither the file monitor event loop (`interception/mod.rs:run_event_loop`) nor the hook DLL IPC path (`hook_ipc.rs:handle_hook_request`) reference `ApprovalCache`.

This phase closes that gap by:
1. Adding `matched_label_id` to `EvaluateResponse` (server-side resolution already happens; we just need to return it).
2. Adding `EventType::ApprovalOverride` to `dlp-common/src/audit.rs` for auditable override events.
3. Wiring `ApprovalCache::check()` into both enforcement paths as the **third stage** of the pipeline: NTFS check -> ABAC policy check -> approval cache override.
4. Updating `spawn_event_loop` signature and call site to pass `Arc<ApprovalCache>`.
5. Extending `HookIpcServer::with_cache` (or creating a new constructor) to accept and use `ApprovalCache`.

**Primary recommendation:** Implement the approval override as a shared helper `check_approval_override()` in `approval_cache.rs`, called from both `run_event_loop` (after effective mode computation, only when `effective_mode.is_blocking()`) and `handle_hook_request` (after `inner_handler` returns a DENY). Emit `EventType::ApprovalOverride` on successful override; emit standard `EventType::Block` with annotated reason on failed/expired approval check.

## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01.1:** Add `matched_label_id: Option<String>` to `EvaluateResponse` in `dlp-common/src/abac.rs`. The server already resolves path -> label during ABAC evaluation; returning the matched label ID lets the agent reuse the server's resolution to build `ApprovalCacheKey`.
- **D-01.2:** The new field uses `#[serde(default)]` for backward compatibility with existing `EvaluateResponse` consumers.
- **D-01.3:** When the server is offline, `EvaluateResponse` carries no `matched_label_id`, so the approval cache cannot be consulted. This is acceptable: offline mode already falls back to tier-gated fail-closed/fail-open semantics (FAIL-01..03 from Phase 50).
- **D-02.1:** Wire approval cache check into **both** enforcement paths:
  - File monitor path: `dlp-agent/src/interception/mod.rs` in `run_event_loop`, after `offline.evaluate()` returns and after effective mode is computed. If `response.decision == DENY` and `effective_mode` is not Audit-only, call `ApprovalCache::check()` with the resolved `ApprovalCacheKey`.
  - Hook DLL path: `dlp-agent/src/hook_ipc.rs` in `handle_hook_request`, after the `inner_handler` returns its `HookResponse`. If `response.decision == DENY`, check `ApprovalCache`.
- **D-02.2:** In both paths, the approval cache check is the **final override** after all other evaluation is complete. The three-stage pipeline from Phase 61 is preserved: NTFS check -> ABAC policy check -> approval cache override.
- **D-03.1:** Emit a dedicated `EventType::ApprovalOverride` (new enum variant in `dlp-common/src/audit.rs`) when an approval token overrides a DENY.
- **D-03.2:** The override event carries:
  - `matched_policy_id = Some("approval:{jti}")`
  - `approver_sid` (from the cached approval claims)
  - `approval_expiry` (from `claims.exp`)
  - `justification` (from the cached approval claims, or "pre-approved" if absent)
  - `would_have_denied = true`
- **D-03.3:** The event routes through SIEM relay with `triggers_alert = false` (this is a legitimate override, not a security incident).
- **D-03.4:** If the approval check fails (expired, bad signature, scope mismatch), emit a standard `EventType::Block` with `reason` annotated ("blocked — approval invalid or expired").

### Claude's Discretion
- Approval cache check ordering: cache check happens AFTER effective mode computation. If `effective_mode.is_audit()`, the physical operation is already ALLOWed (audit-only mode from Phase 55) — no need to check the approval cache because the operation proceeds regardless. This avoids unnecessary JWT verification overhead.
- `ApprovalCacheKey` construction: use `matched_label_id` from `EvaluateResponse` as `obj_id`; if `None`, skip approval cache check (can't form a valid key).
- The hook DLL path reuses the same `ApprovalCacheKey` construction logic as the file monitor path — extract a shared helper in `dlp-agent/src/approval_cache.rs` (e.g. `ApprovalCacheKey::from_evaluation(response, sid, action, dst)`).

## Architecture Patterns

### System Architecture Diagram

```
File Monitor Event Flow:
  FileAction -> run_event_loop()
    -> resolve identity (session_map)
    -> USB/Disk/Cloud pre-checks (short-circuit)
    -> offline.evaluate(&request) -> EvaluateResponse
      -> server-side: PolicyStore::evaluate() -> matched_label_id populated
    -> compute_effective_mode(global_mode, policy_mode)
    -> IF effective_mode.is_blocking() AND decision == DENY:
         -> ApprovalCache::check(key, dst) -> Option<EvaluateResponse>
            -> cache hit + valid JWT + scope match -> ALLOW override
            -> cache miss/expired/invalid -> keep DENY
    -> emit_audit() -> EventType::ApprovalOverride OR EventType::Block
    -> IF denied -> pipe1::send_to_ui(BlockNotify)

Hook DLL IPC Event Flow:
  HookRequest -> handle_hook_request()
    -> inner_handler(req) -> HookResponse (ABAC evaluation)
    -> IF response.decision == DENY:
         -> ApprovalCache::check(key, dst) -> Option<EvaluateResponse>
            -> cache hit + valid -> override to ALLOW in HookResponse
            -> cache miss -> keep DENY
    -> build_cache_hint() -> attach to response
    -> return HookResponse to DLL
```

### Pattern 2: Post-Process Override (Hook IPC)
**What:** After `inner_handler` returns `HookResponse`, post-process to check approval cache if decision is DENY.
**When to use:** Hook DLL IPC path where the handler returns a `HookResponse` (not `EvaluateResponse`).
**Example:**
```rust

// MISSING: check approval cache and override decision if valid

```

### Anti-Patterns to Avoid
- **Checking approval cache before effective mode:** If `effective_mode.is_audit()`, the operation is already allowed — checking the cache wastes ~50us of Ed25519 verification per DENY.
- **Using path instead of label ID for cache key:** `ApprovalCacheKey` uses `obj_id` (label ID), not path. The server must return `matched_label_id` for the key to be constructible.
- **Skipping audit on override:** Every override must emit an auditable event for compliance. Silent overrides break audit trails.
- **Modifying HookRequest bincode layout:** The hook DLL and agent communicate via bincode. Adding fields to `HookRequest` requires rebuilding the DLL. Use `#[serde(default)]` and only add fields if absolutely necessary.

## Common Pitfalls

### Pitfall 1: Hook DLL Does Not Carry User SID
**What goes wrong:** `HookRequest` has `path`, `action`, `cache_version`, `protocol_version`, `op` — but **no `user_sid`**. The approval cache key requires the user's SID. Without it, the cache cannot be checked.
**Why it happens:** The hook DLL runs inside the target process and does not resolve the Windows user identity. The agent's `run_event_loop` resolves SID via `session_map.resolve_for_path()`.
**How to avoid:** The hook IPC path must resolve the user SID from the process PID (same pattern as `run_event_loop`). This may require:
  - Extending `HookRequest` to include `pid` (already present in `HandleHookRequest` but not in `HookRequest` used for classification), OR
  - Using the process token from the pipe connection to resolve SID.
**Warning signs:** Approval cache always misses in hook path; hook DLL blocks operations that should be approved.

### Pitfall 2: `matched_label_id` is `None` in Offline Mode
**What goes wrong:** When the server is offline, `OfflineManager::offline_decision()` returns a cached `EvaluateResponse` or a fail-closed/fail-open default. Neither carries `matched_label_id`. The approval cache cannot be consulted.
**Why it happens:** Label resolution happens server-side in `PolicyStore::evaluate()`. Offline mode has no label service access.
**How to avoid:** This is **by design** per D-01.3. Document that offline mode cannot use approval overrides. The agent falls back to tier-gated fail-closed/fail-open semantics.
**Warning signs:** Operations approved while online are blocked when the agent goes offline.

### Pitfall 3: `spawn_event_loop` Signature Change Ripples
**What goes wrong:** Adding `approval_cache: Arc<ApprovalCache>` to `spawn_event_loop` changes its signature. The call site in `run_loop_init` (line 1627) must be updated. Any test code that calls `spawn_event_loop` directly will break.
**Why it happens:** `spawn_event_loop` is a private `fn` in `service.rs`, but tests may construct `RunLoopContext` or call `run_event_loop` directly.
**How to avoid:** Update the signature and all call sites. Check `cargo test` for compilation errors in test modules.
**Warning signs:** Compilation errors in `service.rs` or test files after signature change.

### Pitfall 4: `EvaluateResponse` Backward Compatibility
**What goes wrong:** Adding `matched_label_id` to `EvaluateResponse` without `#[serde(default)]` breaks deserialization of old JSON responses cached in the agent's offline cache or stored in test fixtures.
**Why it happens:** Old `EvaluateResponse` JSON does not have the `matched_label_id` field.
**How to avoid:** Add `#[serde(default)]` to the new field. Verify with a backward-compat test (pattern exists in `dlp-common/src/abac.rs` line 915-922).
**Warning signs:** `serde_json::Error` on deserialization of cached responses.

### Pitfall 5: Hook DLL Bincode Compatibility
**What goes wrong:** If `HookRequest` or `HookResponse` fields are added without `#[serde(default)]`, bincode deserialization in the hook DLL (which may be an older build) will fail.
**Why it happens:** Bincode does not support unknown fields. Unlike JSON, there is no `#[serde(default)]` fallback for missing fields in bincode.
**How to avoid:** Do NOT add new required fields to `HookRequest` or `HookResponse`. If new fields are needed, use `#[serde(default)]` and ensure the hook DLL can handle defaults. Better: avoid changing the IPC struct at all and pass approval data out-of-band.
**Warning signs:** Hook DLL crashes with bincode deserialization errors; pipe connections drop.

### Shared approval override helper

```rust
// dlp-agent/src/approval_cache.rs
use dlp_common::{EvaluateResponse, Decision};
use dlp_common::approval::ApprovalCacheKey;

/// Checks whether an approval token overrides a DENY decision.
///
/// Returns a new `EvaluateResponse` with `Decision::ALLOW` if a valid
/// approval exists in the cache. Returns `None` if no approval matches
/// or if the approval is invalid/expired.
pub fn check_approval_override(
    cache: &ApprovalCache,
    response: &EvaluateResponse,
    sid: &str,
    action: &str,
    dst: Option<&str>,
) -> Option<EvaluateResponse> {
    let label_id = response.matched_label_id.as_deref()?;
    let key = ApprovalCacheKey::new(sid, label_id, action, dst);
    cache.check(&key, dst)
}
```

## Open Questions

1. **Hook DLL user SID resolution**
   - What we know: `HookRequest` does not carry `user_sid`. The agent resolves SID in `run_event_loop` via `session_map.resolve_for_path()`.
   - What's unclear: Can the hook IPC handler resolve SID from the process PID (same as `run_event_loop`), or does the pipe connection context provide it?
   - Recommendation: Investigate using `OpenProcessToken` + `GetTokenInformation(TokenUser)` on the PID from `HookRequest`. If not feasible, document that hook path approvals require extending `HookRequest` (bincode compat risk).

2. **Destination scope for `ApprovalCacheKey`**
   - What we know: `ApprovalCacheKey` has an optional `dst` field for destination scope matching.
   - What's unclear: For the file monitor path, what is the "destination" for a file write? For a copy to USB, the destination is the USB drive letter.
   - Recommendation: For simple read/write operations, `dst = None`. For copy/move operations to external destinations, derive `dst` from the path's volume class or drive letter. Start with `None` for all operations and refine in a follow-up.

3. **`matched_label_id` population in `PolicyStore::evaluate()`**
   - What we know: `ResolvedTier::Exact(tier)` currently only returns the tier, not the label ID.
   - What's unclear: Does `LabelService` have a method that returns both tier and label ID for a path?
   - Recommendation: Check `dlp-server/src/label_service.rs` for `resolve_tier` implementation. May need to add a `resolve_label_id` method or extend `ResolvedTier` to carry the ID.

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Token replay (different destination) | Elevation of Privilege | `scope_matches()` with exact + prefix-wildcard matching |
