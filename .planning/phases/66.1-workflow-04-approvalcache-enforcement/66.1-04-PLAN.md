<objective>
Wire ApprovalCache::check() into the file monitor enforcement path as the third stage of the pipeline. Prepare structural wiring for the hook DLL path (constructor + PID-to-SID utility) but DEFER the actual hook-path override check to a follow-up phase because the hook path lacks real ABAC evaluation today.

Purpose: This is the core deliverable of Phase 66.1 — making the ApprovalCache actually consulted during file monitor enforcement so approved operations override ABAC DENY decisions. The hook DLL path is structurally prepared but not activated until real ABAC evaluation is wired.
Output: File monitor path checks approvals after ABAC evaluation, emits ApprovalOverride audit events, and respects destination scope matching. Hook IPC path has structural preparation (constructor + get_sid_for_pid) but skips the override check.
</objective>

fn handle_hook_request(
    req: HookRequest,
    inner_handler: &HookHandler,
    cache: &Arc<dyn CacheAccessor>,
) -> HookResponse {
    let current_version = cache.current_version();
    if req.cache_version > 0 && req.cache_version < current_version {
        info!(... "stale DLL detected");
    }
    let mut response = inner_handler(req.clone());

## Review feedback addressed in this plan

### HIGH concerns

1. **Hook DLL path uses wrong identity resolution (both reviewers):** The original plan used `session_map.resolve_for_path(&req.path)` which resolves the file owner, not the requesting user. This is a security-critical bug. Resolution: The hook DLL path's approval override is DEFERRED to a follow-up phase. Plan 04 does NOT implement hook-path override checking. Instead, it adds `get_sid_for_pid()` (for future use) and structurally prepares `HookIpcServer` to accept an approval cache, but the override check is NOT wired into `handle_hook_request`. A TODO comment documents the deferred work.

2. **ApprovalCache lacks `get()` method (Claude review):** Already fixed in Plan 03 revision — `check_approval_override` uses `cache.check()` only.

3. **Hook IPC path has no real ABAC evaluation today (OpenCode review):** The `inner_handler` in the hook path is a placeholder/heuristic, not real ABAC. `HookResponse` is a different type from `EvaluateResponse`. Wiring approval override on top of a placeholder is premature. Resolution: Hook-path approval overrides are DEFERRED. Plan 04 only structurally prepares the hook path (constructor + storage) without activating the override logic.

4. **Tests call `run_event_loop` directly (OpenCode review):** Already fixed in Plan 03 revision — `approval_cache` is `Option<Arc<ApprovalCache>>` with no direct test callers.

### MEDIUM concerns

5. **Destination scope always `None` (both reviewers):** Both paths pass `dst=None`. Documented as a known limitation in the plan — destination-scoped approvals are not yet supported. A TODO comment marks where `dst` derivation should happen.

6. **EventType::ApprovalUse vs ApprovalOverride overlap (both reviewers):** Addressed in Plan 01 — `ApprovalUse` documented as reserved/unused; `ApprovalOverride` is the active enforcement-time event.

7. **Action string normalization (OpenCode review):** The file monitor path uses `PolicyMapper::action_for(&action)` which returns an `Action` enum. The hook DLL path receives raw strings. For the file monitor path, `abac_action.to_string()` is used. Documented: both paths must use the same action vocabulary. The `ApprovalCacheKey::from_evaluation` accepts `action: &str` — callers must ensure consistent casing.

8. **Hook IPC audit fields incomplete (Claude review):** Since hook-path override is deferred, this concern is moot for Plan 04. When the hook path is wired in a future phase, `agent_id` and `session_id` must be threaded through `HookIpcServer`.

9. **Block reason annotation (Claude review):** Fixed — three distinct cases: (a) no `matched_label_id` -> no annotation, (b) `matched_label_id` present but no cache entry -> "blocked — no active approval", (c) cache entry present but invalid/expired/scope mismatch -> "blocked — approval invalid or expired".

10. **`get_sid_for_pid` error handling (OpenCode review):** Documented fail-closed behavior — when `OpenProcess` fails (protected process, cross-session, higher integrity), `get_sid_for_pid` returns `None` and the caller skips the cache check, keeping DENY.

11. **`with_cache` name collision (OpenCode review):** `HookIpcServer::with_cache()` already exists for `CacheAccessor`. The new constructor is named `with_approval_cache` to avoid collision.
