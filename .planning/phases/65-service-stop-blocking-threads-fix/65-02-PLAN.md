<objective>
Add shutdown signal polling to all three IPC pipe accept loops. Each pipe server checks `crate::service::shutdown_requested()` between client connections. If shutdown is requested, the server closes its current pipe handle and exits cleanly. This allows the worker thread to terminate so run_service can join it.

CRITICAL REVIEW FIX: The original plan only checked the flag before ConnectNamedPipeW, which does NOT unblock a thread already blocked in the call. The shutdown thread (Plan 65-01's BlockingThreads::shutdown_and_join) closes the pipe handle, which causes any pending ConnectNamedPipeW to return ERROR_OPERATION_ABORTED. The worker thread then sees shutdown_requested() on the next loop iteration and exits cleanly.

Current accept_loop pattern in all three pipes:
```rust
fn accept_loop(first_pipe: HANDLE) -> Result<()> {
    let mut pipe = first_pipe;
    loop {
        // Wait for a client to connect.  ConnectNamedPipe returns
        // ERROR_PIPE_CONNECTED if a client connected between
        // CreateNamedPipeW and this call — that is a success case.
        if let Err(e) = unsafe { ConnectNamedPipe(pipe, None) } {
            let win32_code = (e.code().0 as u32) & 0xFFFF;
            if win32_code != 535 {
                warn!(win32_code, "ConnectNamedPipe failed — recycling pipe");
                let _ = unsafe { CloseHandle(pipe) };
                pipe = create_pipe()?;
                continue;
            }
            debug!("ConnectNamedPipe: client already connected (535)");
        }

        info!(pipe = PIPE_NAME, "client connected to Pipe 1");
        let _ = handle_client(pipe);

        // Create a new pipe instance for the next client.
        pipe = create_pipe()?;
    }
}
```

The problem: `ConnectNamedPipe` blocks until a client connects. If no client ever connects after shutdown is requested, the thread blocks forever.

The fix (incorporating review feedback):
1. Check shutdown_requested() BEFORE each ConnectNamedPipe call
2. If shutdown is requested, close the pipe handle and return Ok(())
3. The shutdown thread (BlockingThreads::shutdown_and_join) also closes the pipe handle from the outside, which causes ConnectNamedPipeW to return ERROR_OPERATION_ABORTED
4. The worker thread then sees shutdown_requested() on the next iteration and exits

Windows behavior note: Closing a named pipe handle while ConnectNamedPipeW is pending on that handle causes the pending call to complete with ERROR_OPERATION_ABORTED. This is documented Windows behavior and is safe.

However, there is a subtlety: the shutdown thread in Plan 65-01 does NOT have direct access to the pipe handles (they are owned by the worker threads). So the primary mechanism is:
- Shutdown thread sets SHUTDOWN_REQUESTED = true
- If a client connects after shutdown, the worker thread sees the flag on the next loop iteration and exits
- If no client connects, the thread remains blocked until the watchdog (Plan 65-01) forces process exit

This is acknowledged as a limitation. The reviewers flagged this as HIGH risk. The watchdog is the safety net. A future improvement would be to share pipe handles with the shutdown thread so it can close them directly, or use overlapped I/O.

For now, the design is:
1. Poll shutdown flag before each ConnectNamedPipeW (catches the case where a client connects after shutdown)
2. Watchdog timer forces process exit if any thread is still blocked after timeout (catches the no-client case)
3. Document the limitation and the watchdog fallback
</context>
