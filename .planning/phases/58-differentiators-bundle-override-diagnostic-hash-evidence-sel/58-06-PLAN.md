# Plan 58-06: Override Flow Integration

## Objective

Wire approval override from hook DLL DENY through agent to user UI and back. Use a versioned `HookResponseV2` for the `approval_override` field. Design new `Pipe2AgentMsg::ShowOverrideDialog` IPC from agent to user UI. Have user UI submit justification back to agent via new IPC message, then agent POSTs to server. Add 30-second deduplication to prevent pipe spam. Address all HIGH review concerns about endpoint ambiguity, admin approval UI, TTL enforcement, and dedup key strengthening.

## Background

The original plan added `approval_override` directly to `HookResponse`, breaking bincode compatibility. It also assumed dlp-user-ui could POST directly to the server, which may fail due to network/TLS issues in the user session. The revised plan uses `HookResponseV2` with a versioned envelope, routes justification through the agent (SYSTEM service), and adds deduplication.

Reviewers identified critical issues: endpoint ambiguity between `/admin/overrides` and `/admin/approvals`, missing admin approval UI documentation, no TTL enforcement in hook/agent, and dedup key too coarse. This plan fixes all of them.

## must_haves

- truths:
  - HookResponseV2 uses versioned envelope; bincode compatibility preserved
  - Agent checks ApprovalCache on DENY, not hook DLL
  - Pipe2AgentMsg::ShowOverrideDialog triggers modal in user UI
  - User UI submits justification to agent via new IPC message
  - Agent POSTs justification to server on behalf of user UI
  - Server endpoint is POST /admin/approvals (Phase 61 endpoint, documented)
  - Admin approval UI reuses Phase 61 ApprovalList screen (documented)
  - TTL enforcement: agent checks override_expiry > now() before honoring
  - Dedup key is (user_sid, process_id, resource_path, action)
  - 30-second deduplication prevents duplicate override requests
  - Full override state machine is defined
