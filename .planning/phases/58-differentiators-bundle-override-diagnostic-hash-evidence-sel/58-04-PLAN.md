  <action>
    Modify dlp-server/src/admin_api.rs:
    1. Add DiagnosticQuery struct (derive Deserialize):
       - since: Option<String> (ISO 8601 timestamp)
       - user_sid: Option<String>
       - policy_id: Option<String>
       - limit: Option<usize> (default 50)
       - offset: Option<usize> (default 0)
    2. Add DiagnosticListResponse struct (derive Serialize):
       - total: usize
       - snapshots: Vec<DiagnosticSnapshot>
    3. Implement async fn list_diagnostics_handler(
       State(state): State<Arc<AppState>>,
       Query(q): Query<DiagnosticQuery>,
    ) -> Result<Json<DiagnosticListResponse>, AppError>:
       - Parse `since` string to DateTime<Utc> if provided
       - Build DiagnosticFilter from query params
       - Access the agent's diagnostic aggregator through AppState
       - Call get_snapshots_paginated(filter, limit, offset)
       - Return Json(DiagnosticListResponse { total, snapshots })
    4. Register route:
       .route("/admin/diagnostics", get(list_diagnostics_handler))
       - Must be AFTER the .route_layer(middleware::from_fn(admin_auth::require_auth)) line so it's JWT-protected
    5. Add integration tests in dlp-server/tests/ (or inline in admin_api.rs #[cfg(test)]):
       - test_diagnostics_api_empty: No snapshots -> returns empty list
       - test_diagnostics_api_with_data: Ingest snapshots, verify filtered retrieval
       - test_diagnostics_api_pagination: Verify limit/offset work
       - test_diagnostics_api_auth: Verify 401 without JWT

    Note: The admin API needs access to the agent's diagnostic aggregator. Since dlp-server and dlp-agent are separate crates, the diagnostic data must be exposed through AppState. If AppState doesn't currently hold agent references, add an Arc<DiagnosticAggregator> field (or a channel/bridge). The simplest approach: the agent exposes a lightweight HTTP endpoint that the server proxies, OR the server reads from a shared in-memory store. Given the architecture, the most practical approach is:
    - The agent has its own HTTP server (or the admin API talks to the agent via an internal API)
    - OR: Add a field to AppState that holds an optional Arc<DiagnosticAggregator> populated when the agent and server run together (test mode)
    
    For simplicity and following existing patterns, implement the endpoint to return data from AppState.diagnostic_aggregator (an Option field that is None when server runs standalone, Some when bundled with agent). The tests can populate this field directly.

    KNOWN LIMITATION: The AppState Option<Arc<DiagnosticAggregator>> workaround is a temporary simplification. In production, the server should query the agent via an internal HTTP endpoint or a shared message bus. This avoids coupling the server crate to agent internals and supports standalone server deployments. Future phase should design an agent HTTP endpoint for diagnostic queries.

|----------|-------------|
| Admin -> Server API | Authenticated via JWT; rate limited |
| Server -> Agent | Internal network; agent JWT authenticated |
| Agent -> Hook DLL | Named pipe; read-only polling |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-58-11 | Information Disclosure | Diagnostic API | mitigate | JWT auth required; filtered by user_sid/policy_id; no cross-user data exposure |
| T-58-12 | Tampering | Audit event hash | mitigate | Hash computed in hook DLL from buffer directly; stored as-is; no server-side recomputation |
| T-58-13 | Denial of Service | Diagnostics API | mitigate | Pagination (default 50, max 1000); rate limiting via existing admin API middleware |
</threat_model>
