         - Create two new bounded crossbeam channels: `(correlator_tx, correlator_rx)` and `(lazy_tx, lazy_rx)` with capacity `etw_kernel_file::CHANNEL_CAPACITY`.
         - Spawn a dedicated OS thread named `etw-kernel-file-fanout` that reads from `etw_consumer.receiver()` and, for each event:
           - Sends a clone to `correlator_tx` using `send` (blocking, preserves bypass detection).
           - Sends the original or another clone to `lazy_tx` using `try_send`; on `TrySendError::Full`, log `warn!` and increment an atomic overflow counter (lazy injection is lower priority than bypass correlation).
         - **Backpressure policy and coverage analysis**: Document the fanout behavior in a code comment at the fanout thread spawn site:
           - The bypass correlator uses a blocking send because missing a bypass event is a security-relevant correctness failure.
           - The lazy injector uses a bounded channel with `try_send` because lazy injection is a best-effort coverage backstop, not a correctness gate.
           - If the lazy channel is full, the event is dropped for lazy processing but is still processed by the bypass correlator.
           - Coverage impact: under normal load the lazy channel (1024 events) drains as fast as the lazy injector can resolve tiers and inject. The only coverage loss from a dropped event is when a low-confidence process touches a T3/T4 path while the channel is full; the first such event per process is already intentionally counted as missed, and subsequent events would be covered after injection. Sustained drops could therefore degrade the >=99% event-coverage guarantee only if the channel remains full across multiple events from the same newly-discovered low-confidence process. To bound this risk, log every drop and export the overflow counter in the periodic telemetry event (Plan 07); operators can increase channel capacity or investigate lazy-injector stalls if the counter grows.

Store the handle.
