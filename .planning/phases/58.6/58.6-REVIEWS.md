## Codex Review

**Review Summary**

I verified the referenced code directly. GitNexus MCP resources/tools were not available in this session, so the review is based on source inspection. Overall, the plan set is directionally strong and decomposes the feature into sensible waves, but the phase is **HIGH risk** because the key guarantee, `>=99% coverage of actual T3/T4 file-operation events`, is not proven by the proposed lazy-injection design: the first ETW file event that triggers lazy injection is already missed. There are also concrete compile/testability gaps around Windows gating, private constants, classification-cache substitution, and service startup wiring.

### Plan 01 — Config And Registry Foundations

**Summary:** Good foundational plan. It matches real extension points in `AgentConfig` and `ProcessRegistry`, but it underestimates how many existing tests and pattern matches need exact updates.

**Strengths**
- Existing config loading already uses `serde_ignored`, so backward-compatible unknown-key behavior is real: `dlp-agent/src/config.rs:370`.
- The plan correctly identifies the two manual `AgentConfig` literals that will need the new field: `dlp-agent/src/config.rs:710` and `dlp-agent/src/config.rs:760`.
- Registry state is centralized and small enough to extend cleanly: `ProcessState` is at `dlp-agent/src/process_registry.rs:65`.

**Concerns**
- **MEDIUM:** `try_claim` currently rejects every existing entry, including retryable failures: `dlp-agent/src/process_registry.rs:225`. Adding `PendingRetry` changes core race semantics and must update exact tests such as `test_try_claim_second_call_returns_already_claimed` at `dlp-agent/src/process_registry.rs:510`.
- **LOW:** `ProcessCounts` is currently process-state-only: `dlp-agent/src/process_registry.rs:433`. Adding event counters here mixes state-derived and atomic event-derived metrics; later plans should make that distinction explicit.

**Suggestions**
- Add `record_injected_with_path` internally and keep `record_injected` as an immediate-path compatibility wrapper.
- Add a test that old TOML saves back with `[targeted_injection]` defaults, since `save()` serializes the entire struct at `dlp-agent/src/config.rs:446`.

**Risk Assessment:** MEDIUM. Mostly mechanical, but registry semantics affect the injection hot path.

### Plan 02 — PE Import Scanner

**Summary:** Useful primary signal, but the plan needs sharper failure semantics. Partial PE reads and parse errors will often collapse to score `0`, which can increase false negatives unless paired with fallback.

**Strengths**
- Dependency placement is plausible; `dashmap`, `sha2`, `ferrisetw`, `crossbeam-channel`, and `glob` already exist in `dlp-agent/Cargo.toml:128-143`.
- `allowlist::canonicalize_path` exists and is cheap to reuse for cache keys: `dlp-agent/src/allowlist.rs:275`.

**Concerns**
- **MEDIUM:** "Read up to `pe_max_scan_bytes` and parse" can return false negatives for large or unusual PE layouts if import data lies outside the cap. The plan says return `0` on parse failure, but targeted mode treats low score as low confidence, not necessarily universal fallback.
- **LOW:** Current new-module pattern in `lib.rs` is mostly Windows-gated: `dlp-agent/src/lib.rs:151-181`. Non-Windows stubs must avoid importing Windows-only modules such as `allowlist`, which is only exported on Windows at `dlp-agent/src/lib.rs:160`.

**Suggestions**
- Distinguish `ScoreUnavailable` from `score = 0`; use unavailable data to trigger `fallback_universal_sweep` or immediate injection in fail-safe mode.
- Add a test fixture PE rather than relying mainly on `C:\Windows\System32\notepad.exe`.

**Risk Assessment:** MEDIUM. Good module boundary, but false-negative handling is underspecified.

### Plan 03 — Command-Line Reader

**Summary:** Valuable secondary signal, but the Windows PEB reader is under-specified for cross-architecture and access-denied cases.

**Strengths**
- The plan correctly avoids treating basename alone as sufficient, which reduces spoofing risk.
- It aligns with existing path normalization and glob dependency: `glob` is already present in `dlp-agent/Cargo.toml:143`.

**Concerns**
- **HIGH:** The plan does not specify 32-bit target process handling from a 64-bit agent. The injector explicitly supports x86/x64 DLL selection: `dlp-agent/src/hook_injector.rs:148-155`, so the command-line reader must handle WoW64 PEB layouts or mark command line as unavailable.
- **MEDIUM:** Tokenizing Windows command lines with "simple quotes" is likely weaker than Windows argument parsing rules. False negatives here directly reduce immediate injection.
- **MEDIUM:** Protected processes are expected to deny reads, but the classifier later may interpret unknown command line as low confidence rather than fail-safe.

**Suggestions**
- Use `CommandLineToArgvW` semantics for tokenization tests.
- Add explicit `CommandLineStatus::{Known, AccessDenied, UnsupportedArch, ParseError}` instead of collapsing all failures to booleans.

**Risk Assessment:** HIGH. Cross-process PEB parsing is fragile and easy to get wrong.

### Plan 04 — Hybrid ProcessClassifier

**Summary:** The right architectural center, but cache invalidation and platform gating need more detail.

**Strengths**
- Centralizing allowlist/PPL before injection matches the current duplicated flow in `UniversalInjector::handle_event`: allowlist at `dlp-agent/src/universal_injector.rs:171`, PPL at `dlp-agent/src/universal_injector.rs:182`.
- Existing `AllowlistMatcher::check` is a clean API for classifier reuse: `dlp-agent/src/allowlist.rs:101`.

**Concerns**
- **MEDIUM:** Classification cache is per `ProcessKey`, but allowlist entries can change via `AllowlistMatcher::update_entries`: `dlp-agent/src/allowlist.rs:260`. Cached `InjectImmediately` or `SkipAllowlisted` decisions can become stale unless tied to `allowlist_version`.
- **MEDIUM:** Non-Windows stubs must not reference `AllowlistMatcher`, `ProcessKey`, or `detect_ppl` unless those modules are also exported on non-Windows. Current exports are Windows-only: `dlp-agent/src/lib.rs:157-181`.

**Suggestions**
- Include `allowlist_version` and config generation in the classifier cache key or clear cache on config reload.
- Make classifier decisions carry evidence fields: PE score, threshold, CLI status, allowlist category.

**Risk Assessment:** MEDIUM-HIGH. Good design, but stale decisions are a security and correctness risk.

### Plan 05 — LazyInjector And `resolve_tier`

**Summary:** Necessary backstop, but it does not meet the strongest coverage wording as written because the trigger event is already missed.

**Strengths**
- The existing `ClassificationCache` already has the data structures needed for lookup: `CacheHeader`, `HashEntry`, and `PrefixEntry` in `dlp-common/src/classification_cache.rs:30`.
- Current cache rebuild stores hash entries and prefix entries in predictable tables: `dlp-agent/src/classification_cache.rs:449` and `dlp-agent/src/classification_cache.rs:506`.

**Concerns**
- **HIGH:** Lazy injection after observing a T3/T4 ETW event cannot cover that same first event. It should increment missed, but this conflicts with the phase success criterion requiring `>=99% coverage of actual file-operation events`.
- **HIGH:** Plan 08 says to use a stub classification cache, but Plan 05 types the field as `Option<Arc<ClassificationCache>>`. The current cache is a concrete Windows shared-memory owner: `dlp-agent/src/classification_cache.rs:124`, so test substitution needs a trait.
- **MEDIUM:** `ClassificationCache` is only exported on Windows: `dlp-agent/src/lib.rs:151`. Non-Windows lazy-injector stubs must avoid that concrete type or add a cfg-safe abstraction.
- **MEDIUM:** Plan says use `etw_kernel_file::CHANNEL_CAPACITY`, but that constant is private: `dlp-agent/src/etw_kernel_file.rs:111`.

**Suggestions**
- Add `TierResolver` and `ProcessCreationTimeSource` traits for testability.
- Define coverage as "covered after first trigger" or add a pre-injection quarantine/hold mechanism if first-event coverage is required.
- Make `CHANNEL_CAPACITY` public or use a new public accessor/constant.

**Risk Assessment:** HIGH. This plan is central to the phase goal and currently under-proves coverage.

### Plan 06 — Service Integration

**Summary:** This is the highest blast-radius plan and it correctly targets real bugs, especially retry behavior, but the current startup wiring contradicts one of the plan's stated truths.

**Strengths**
- The retry bug is real: first retryable failure records `Skipped(Failed)` before queueing retry at `dlp-agent/src/universal_injector.rs:245-251`; `handle_retry` then re-enters `handle_event` and hits `try_claim` at `dlp-agent/src/universal_injector.rs:264-272`.
- Startup/backstop sweeps currently duplicate allowlist/PPL/inject logic: `dlp-agent/src/service.rs:3303` and `dlp-agent/src/service.rs:3404`, so centralizing is justified.
- Current ETW receiver cloning is real: `dlp-agent/src/service.rs:2177`; crossbeam receiver clones work-share, so fanout is the right fix.

**Concerns**
- **HIGH:** "Targeted/Monitor modes enable the injection subsystem even when legacy universal flag is false" is incomplete. `HookInjector` is only constructed when `cloud_hook_enabled` is true: `dlp-agent/src/service.rs:1851-1872`, and `init_universal_injection` returns disabled if `hook_injector_opt.is_none()`: `dlp-agent/src/service.rs:3030`.
- **HIGH:** The fanout plan references private `CHANNEL_CAPACITY`: `dlp-agent/src/etw_kernel_file.rs:111`.
- **MEDIUM:** `init_universal_injection` currently accepts `hook_injector_opt` but constructs a new `HookInjector` anyway: `dlp-agent/src/service.rs:3016` and `dlp-agent/src/service.rs:3085-3089`. The plan should explicitly remove that confusing parameter or reuse the supplied injector.
- **MEDIUM:** `audit_ctx` is built after `init_universal_injection`: `dlp-agent/src/service.rs:1892-1901`, but Plan 07 wants to pass it into the injector during construction.

**Suggestions**
- Move `audit_ctx` creation before `init_universal_injection`.
- Decouple hook injector construction from `cloud_hook_enabled`; targeted injection should have its own enablement path.
- Make fanout backpressure behavior explicit: drop both, block both, or preserve correlator over lazy injector.

**Risk Assessment:** HIGH. Correct target, but service startup ordering and enablement need redesign before implementation.

### Plan 07 — Telemetry And Audit

**Summary:** Good observability plan, but path privacy and audit schema side effects need tightening.

**Strengths**
- `AuditEvent::new` centralizes defaults, so adding optional `details` is manageable: `dlp-common/src/audit.rs:503`.
- Existing SIEM routing/alert hooks are simple to extend: `dlp-common/src/audit.rs:248` and `dlp-common/src/audit.rs:290`.
- Test capture exists for audit assertions: `dlp-agent/src/audit_emitter.rs:217` and `dlp-agent/src/audit_emitter.rs:263`.

**Concerns**
- **MEDIUM:** Adding `details` after `chain_hash` affects canonical hash content because `canonical_json_for_hash` only removes `prev_hash` and `chain_hash`: `dlp-common/src/audit.rs:95-103`. That is acceptable if intentional, but must be noted because telemetry details become part of the chain.
- **MEDIUM:** Plan says hash "path/image path" into `resource_path`. Hashing process image paths may reduce operator usefulness, while failing to hash raw `application_path`/details would leak anyway. Current `AuditEvent` has multiple path-like fields: `resource_path` at `dlp-common/src/audit.rs:346`, `application_path` at `dlp-common/src/audit.rs:382`.
- **LOW:** `emit_audit` is sync and drops errors by design: `dlp-agent/src/audit_emitter.rs:398`; the plan should not expect awaitable error handling.

**Suggestions**
- Use typed JSON schema for `details` values and add snapshot tests for serialized audit events.
- Explicitly state which fields are hashed, omitted, or allowed raw for each new event type.

**Risk Assessment:** MEDIUM. Mostly straightforward, but privacy mistakes are easy here.

### Plan 08 — Integration Tests And Gates

**Summary:** The right verification wave, but some proposed tests cannot work without seams added earlier.

**Strengths**
- In-crate tests are appropriate because existing modules expose many crate-private internals and Windows-only paths.
- The audit capture sink supports the planned assertions: `dlp-agent/src/audit_emitter.rs:237`.

**Concerns**
- **HIGH:** Lazy-injection tests require a fake tier resolver, but Plan 05 uses concrete `ClassificationCache`, which is Windows shared memory and not stub-friendly: `dlp-agent/src/classification_cache.rs:124`.
- **MEDIUM:** `CountingInjector` via `InjectProcess` is good, but current `UniversalInjector` is hard-wired to `Arc<HookInjector>`: `dlp-agent/src/universal_injector.rs:96-100`; Plan 06 must land first.
- **MEDIUM:** Sonar is required, but the plan assumes `SONAR_TOKEN` exists. The repo has `sonar-project.properties`, but no guarantee the env var is available locally.

**Suggestions**
- Add explicit test traits in earlier plans: `InjectProcess`, `TierResolver`, `CreationTimeSource`, and maybe `AuditSink`.
- Split verification into "required local gates" and "CI-only gates" if Sonar credentials are absent.

**Risk Assessment:** MEDIUM-HIGH. Good coverage intent, but currently blocked by missing test seams.

**Overall Risk**

**Overall risk: HIGH.** The plans are well-structured and mostly target real code seams, but the phase goal is stronger than the proposed mechanism. Lazy injection is a detection-after-first-event backstop, not full first-event prevention. The service integration also has concrete blockers: `cloud_hook_enabled` currently gates hook injector construction, ETW channel capacity is private, `audit_ctx` is created too late for planned injector wiring, and the concrete `ClassificationCache` prevents the stated stub-based tests. Fix those before execution, and the plan set becomes much more credible.

## Consensus Summary

Only Codex was invoked for this review cycle, so the consensus summary reflects Codex's findings alone.

### Agreed Strengths

- Foundation is sound: `AgentConfig` already supports `serde_ignored`, `ProcessRegistry` already uses `(PID, creation_time)` keys, and dependencies like `dashmap`, `glob`, `sha2`, `ferrisetw`, and `crossbeam-channel` are already present.
- Threat modeling correctly identifies the need for allowlist/PPL precedence, rate limiting, PID-reuse safety, and PEB-read failure handling.
- The eight-plan wave structure logically decomposes the targeted-injection feature from config to integration tests.
- The reviewer traced real bugs: retry-after-failure marks PID as processed, ETW receiver cloning is work-sharing not broadcast, and startup/backstop sweeps duplicate allowlist/PPL/inject logic.

### Agreed Concerns

- **Coverage guarantee is not proven by the mechanism.** Lazy injection responds to a T3/T4 ETW file event, so the first event from a process is missed by definition. This contradicts the stated `>=99% coverage of actual file-operation events` success criterion.
- **Testability is under-specified.** Concrete `HookInjector`, `PeImportScanner`, `CommandLineReader`, and `ClassificationCache` structs need traits or test-only seams for deterministic unit and integration tests.
- **Service enablement is incomplete.** Targeted/Monitor modes cannot run unless the legacy `cloud_hook_enabled` path constructs a `HookInjector`, and `init_universal_injection` currently ignores the passed-in injector option.
- **Existing retry logic is ineffective** because failed PIDs are recorded as `Skipped(Failed)` before the retry is queued, so the retry reclaim path cannot win the claim.
- **Private module boundaries block implementation.** `etw_kernel_file::CHANNEL_CAPACITY` is private, and several Windows-only types are not available to non-Windows stubs.
- **Audit wiring order is wrong.** `audit_ctx` is created after `init_universal_injection`, but Plan 07 wants to pass the audit context into the injector at construction time.

### Divergent Views

N/A — only one reviewer was invoked.
