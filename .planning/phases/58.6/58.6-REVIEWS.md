# Cross-AI Plan Review — Phase 58.6

## Notes

- `--codex` was requested. The default Codex model (`gpt-5.3-codex`) is not supported on this ChatGPT-linked account, so the review was run with `--model gpt-5.5`.
- GitNexus MCP resources were not available in this session; validation was performed by direct source inspection.

---

## Codex Review

**Summary**

The plans are generally well decomposed and address real integration problems in the current codebase, especially retry reclaim, ETW receiver fanout, and separating immediate vs lazy injection. However, several plans still have security and integration gaps that would prevent Phase 58.6 from safely meeting its goals. The biggest risks are lazy injection bypassing allowlist/PPL decisions for untracked PIDs, ETW lazy mode still being gated by the bypass-correlator flag, audit telemetry details not being persisted by the server, and shutdown/fanout lifecycle gaps.

I could not use GitNexus MCP because no resources/tools were exposed in this session, so this review is based on direct source inspection.

---

### Plan 58.6-01

**Strengths**
- Correctly targets foundational schema and state changes. Current `ProcessState::Injected` has no injection path and `SkipReason` lacks low-confidence/monitoring states at `dlp-agent/src/process_registry.rs:31` and `dlp-agent/src/process_registry.rs:65`.
- Correctly identifies the retry bug. Current `try_claim` returns `AlreadyClaimed` for every occupied entry, including failed entries, at `dlp-agent/src/process_registry.rs:225`.

**Concerns**
- **MEDIUM:** `InjectProcess` is planned as unconditional, but most agent injection/process modules are Windows-gated in `dlp-agent/src/lib.rs:151`, `dlp-agent/src/lib.rs:157`, `dlp-agent/src/lib.rs:180`. The plan should explicitly state which new modules are cross-platform stubs and which remain Windows-only.
- **LOW:** Adding `TargetedInjectionConfig` requires updating more manual `AgentConfig` literals than the two named tests may imply. Existing full literals are visible at `dlp-agent/src/config.rs:710` and `dlp-agent/src/config.rs:760`, with more roundtrip/default tests later.

**Suggestions**
- Add a compile check for both `cargo check -p dlp-agent` and `cargo check -p dlp-agent --tests`.
- Make the new registry state transitions explicit in tests: `Discovered -> PendingRetry -> Discovered -> Injected`.

**Risk Assessment:** **MEDIUM**. Good foundation, but cross-platform/module gating needs tighter wording.

---

### Plan 58.6-02

**Strengths**
- Adds a bounded parser for untrusted PE files, which is the right safety posture for malformed binaries.
- Correctly uses existing dependency area: Phase 49 deps are grouped at `dlp-agent/Cargo.toml:140`.

**Concerns**
- **MEDIUM:** The plan says resolver/cache key hashing uses `dlp_common::path_hash::path_hash`, but current classification-cache writer hashes raw `path.as_bytes()` at `dlp-agent/src/classification_cache.rs:509`, not `path_hash()`. If PE/classification cache normalization must match, the writer path also needs normalization or the claim is false.
- **LOW:** `path_hash()` can return `None` for malformed/device/ADS paths at `dlp-common/src/path_hash.rs:58`; the plan does not define cache behavior for unnormalizable image paths.

**Suggestions**
- Normalize cache inputs at write time or document that callers must pass normalized paths, then test both writer and reader.
- Add a test for `path_hash(None)` paths, not only case/`\\?\` equivalence.

**Risk Assessment:** **MEDIUM**. The scanner is scoped well, but cache normalization claims are not yet aligned with current writer behavior.

---

### Plan 58.6-03

**Strengths**
- Good separation of basename and command-line signals. Basename-only injection would be spoofable.
- Correctly avoids treating PEB read failures as hard injection triggers.

**Concerns**
- **HIGH:** The proposed `PROCESS_BASIC_INFORMATION` layout appears wrong for reading `PebBaseAddress`; current code has no existing PEB reader, only safe process creation-time querying in `dlp-agent/src/process_utils.rs:15`. An unsafe PEB reader must use a verified ABI layout or a Windows binding. A shifted `PebBaseAddress` would misread remote memory.
- **MEDIUM:** `detect_ppl` and process querying are direct Win32 calls today (`dlp-agent/src/universal_injector.rs:289`), so tests simulating protected/WoW64 behavior need explicit seams, not just helper injection inside tests.

**Suggestions**
- Prefer `windows` bindings for `PROCESS_BASIC_INFORMATION` where available, or add static size/offset assertions for every struct used in `ReadProcessMemory`.
- Add a trait seam for process architecture/PEB status rather than test-only conditional helpers.

**Risk Assessment:** **HIGH** due to unsafe remote-memory parsing.

---

### Plan 58.6-04

**Strengths**
- Correctly centralizes allowlist/PPL before classification. Current allowlist and PPL checks are duplicated in event and sweep paths at `dlp-agent/src/universal_injector.rs:171` and `dlp-agent/src/service.rs:3342`.
- Cache key including `allowlist_version` matches the existing config field at `dlp-agent/src/config.rs:300`.

**Concerns**
- **MEDIUM:** PPL behavior is hard to unit test without a seam because `detect_ppl` directly calls Win32 APIs at `dlp-agent/src/universal_injector.rs:289`. Plan 04 claims PPL tests but does not introduce `ProcessProtectionSource`.
- **MEDIUM:** Cache eviction over `DashMap` as "oldest inserted best effort" is acceptable, but tests must not assume deterministic iteration order.

**Suggestions**
- Add `ProcessProtectionSource` in this plan, not deferred to Plan 08.
- Make classifier tests assert precedence through injected mocks for allowlist, PPL, PE, and CLI.

**Risk Assessment:** **MEDIUM**. Architecture is sound, but testability of PPL precedence is under-specified.

---

### Plan 58.6-05

**Strengths**
- The `TierResolver` seam is a good design. Current `ClassificationCache` is raw shared memory (`dlp-agent/src/classification_cache.rs:124`), so abstracting it makes lazy injection testable.
- Correctly identifies that cloned crossbeam receivers would work-share, not broadcast, which matters because the ETW receiver is currently cloned at `dlp-agent/src/service.rs:2177`.

**Concerns**
- **HIGH:** Untracked T3/T4 events are allowed to trigger lazy injection, but `LazyInjector` has no allowlist matcher/classifier field. Current allowlist/PPL protection lives in `UniversalInjector::handle_event` at `dlp-agent/src/universal_injector.rs:171` and `dlp-agent/src/universal_injector.rs:183`. An untracked allowlisted non-PPL process could be injected.
- **HIGH:** Lazy ETW depends on `EtwKernelFileConsumer::start`, but that start is gated by `config.bypass_correlator_enabled()` at `dlp-agent/src/etw_kernel_file.rs:142`. Targeted lazy injection will not run if bypass correlation is disabled.
- **MEDIUM:** Resolver normalization may not match writer data. Prepopulation writes raw `monitored_paths` at `dlp-agent/src/service.rs:1672` and `ClassificationCache` writes raw prefix bytes at `dlp-agent/src/classification_cache.rs:491`.

**Suggestions**
- Route lazy-triggered untracked PIDs through `UniversalInjector::classify_and_inject` or inject an allowlist/PPL/classifier dependency into `LazyInjector`.
- Change ETW enablement to `bypass_correlator_enabled || targeted_lazy_enabled`.
- Normalize paths before `ClassificationCache::rebuild`, not only during lookup.

**Risk Assessment:** **HIGH**. This plan can violate the allowlist invariant and may not start when needed.

### Plan 58.6-06

**Strengths**
- Correctly fixes concrete current retry failure: first failure records `Skipped(Failed)` at `dlp-agent/src/universal_injector.rs:246`, then retry calls `handle_event` at `dlp-agent/src/universal_injector.rs:272`, which `try_claim` rejects at `dlp-agent/src/process_registry.rs:236`.
- Correctly targets duplicate `HookInjector` construction. Current `init_universal_injection` ignores the supplied injector and constructs a new one at `dlp-agent/src/service.rs:3085`.

**Concerns**
- **HIGH:** `classify_and_inject` does not explicitly include the atomic `try_claim` step. Current duplicate prevention is in `handle_event` at `dlp-agent/src/universal_injector.rs:159`; Plan 06 makes startup/backstop sweeps call `classify_and_inject` directly, so the claim must move into the helper or remain mandatory at every caller.
- **HIGH:** Shutdown plan says abort/await a `spawn_blocking` lazy injector. A blocking `Receiver::recv()` loop is not cancellable by abort once started. Current ETW shutdown happens by stopping the consumer at `dlp-agent/src/service.rs:4212`; the plan also needs to close fanout senders and join the fanout thread.
- **MEDIUM:** Plan adds a fanout OS thread but does not add a `RunLoopContext` field for its join handle. Current context tracks ETW and correlator handles at `dlp-agent/src/service.rs:1217`.

**Suggestions**
- Make `classify_and_inject` own claim/reclaim semantics, including `PendingRetry`.
- Add a shutdown channel for lazy/fanout, stop ETW before awaiting blocking lazy work, and store/join the fanout thread.
- Decouple ETW start from bypass-correlator enablement in this plan.

**Risk Assessment:** **HIGH**. The integration direction is right, but concurrency/shutdown and claim semantics need tightening.

### Plan 58.6-07

**Strengths**
- Adding optional `AuditEvent.details` with `serde(default)` is backward-compatible with old JSON. `canonical_json_for_hash` only strips `prev_hash` and `chain_hash` at `dlp-common/src/audit.rs:95`, so details would be included in the chain hash as desired.
- New event-type routing fits the existing `routed_to_siem` and `triggers_alert` pattern at `dlp-common/src/audit.rs:248`.

**Concerns**
- **HIGH:** Server persistence has no `details` field. `AuditEventRow` ends at `chain_hash` in `dlp-server/src/db/repositories/audit_events.rs:31`, inserts fixed columns at `dlp-server/src/db/repositories/audit_events.rs:103`, and `store_events_sync` drops unmapped fields at `dlp-server/src/audit_store.rs:156`. SIEM/audit telemetry details will be lost unless server DB/repository/API are updated.
- **MEDIUM:** `emit_audit` returns `()` and already logs errors at `dlp-agent/src/audit_emitter.rs:398`; the plan text saying `let _ = emit_audit(...)` with error logging is inaccurate.
- **MEDIUM:** Exhaustive `AuditEvent` literals exist outside `dlp-common`, for example `dlp-server/src/alert_router.rs:338`; Plan 07's `files_modified` omits server files.

**Suggestions**
- Add `details` to `AuditEventRow`, SQLite schema/migration, query responses, and SIEM serialization.
- Adjust plan wording to use `emit_audit(ctx, &mut event)` as best-effort `()`.
- Include dlp-server files in the plan scope.

**Risk Assessment:** **HIGH**. Telemetry may be emitted locally but not retained or routed with its payload.

### Plan 58.6-08

**Strengths**
- Good behavior matrix: targeted, universal, monitor, lazy, allowlist, PID reuse, counters.
- Uses existing audit capture helpers, which are available in `dlp-agent/src/audit_emitter.rs:217` and `dlp-agent/src/audit_emitter.rs:263`.

**Concerns**
- **MEDIUM:** PPL integration cannot be honestly claimed unless a protection seam is added earlier. Current PPL detection is direct Win32 code at `dlp-agent/src/universal_injector.rs:289`.
- **MEDIUM:** The integration module is declared as `#[cfg(test)]`, but many referenced modules are `#[cfg(windows)]` in `dlp-agent/src/lib.rs:151` through `dlp-agent/src/lib.rs:181`. If workspace tests run on non-Windows CI, this needs `#[cfg(all(test, windows))]` or stubs.
- **LOW:** Sonar is listed as a local gate, but the plan correctly allows documenting missing `SONAR_TOKEN`.

**Suggestions**
- Add or require `ProcessProtectionSource` before PPL integration tests.
- Gate the integration module by platform or ensure every dependency has non-Windows stubs.
- Include a test that verifies server-side telemetry details survive ingestion once Plan 07 is fixed.

**Risk Assessment:** **MEDIUM**. Verification is strong if prior gaps are fixed; otherwise it may overclaim coverage.

---

### Overall Risk Assessment

**HIGH.** The plan set is comprehensive, but three issues block safe completion of the phase goal: lazy injection can bypass allowlist/PPL for untracked PIDs, ETW lazy injection can be disabled by the existing bypass-correlator gate, and targeted telemetry details are not persisted by the server. Fix those before execution, then the remaining risks are mostly testability and lifecycle polish.

## Consensus Summary

Only Codex was invoked for this review cycle. The findings below reflect Codex's assessment.

### Agreed Strengths

- The plans decompose targeted injection into sensible seams (`InjectProcess`, `TierResolver`, `PeScoreSource`, `CliSignalSource`) that make the classifier and lazy injector testable without real Windows internals.
- Universal mode remains the default, preserving backward compatibility with Phase 49.
- Plan 06 correctly targets known live bugs: retry-before-claim, ETW receiver splitting, duplicate `HookInjector` construction, and `audit_ctx` ordering.
- Plan 07 addresses observability gaps with hashed paths and SIEM-routed events.
- Plan 08's integration matrix covers Targeted, Universal, Monitor, lazy injection, allowlist safety, PID reuse, and counters.

### Agreed Concerns

- **HIGH:** Plan 05 can violate the allowlist/PPL invariant for untracked PIDs because `LazyInjector` does not run allowlist/PPL/classification checks before injecting.
- **HIGH:** Plan 05's lazy ETW path is gated by `bypass_correlator_enabled()` at `dlp-agent/src/etw_kernel_file.rs:142`; targeted lazy injection will not start when bypass correlation is disabled.
- **HIGH:** Plan 07's `AuditEvent.details` payload will be dropped by server persistence (`AuditEventRow`, `store_events_sync`) unless dlp-server schema/repository/API are updated.
- **HIGH:** Plan 06 has high blast radius (service startup, retry semantics, ETW fanout, sweeps, injector ownership) and does not fully specify `try_claim`/shutdown lifecycle.
- **HIGH:** Plan 03's hand-rolled PEB struct layout risks misreading remote process memory.
- **MEDIUM:** Plan 02's cache normalization claims are not aligned with current `ClassificationCache` writer behavior.
- **MEDIUM:** Plan 04's PPL precedence is hard to test without a `ProcessProtectionSource` seam.
- **MEDIUM:** Plan 08's integration module may fail on non-Windows CI because dependencies are Windows-only.

### Divergent Views

None.
