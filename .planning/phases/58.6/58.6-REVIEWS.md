## Codex Review

## Review Summary

The plan set is directionally strong: it decomposes the feature into sensible layers, preserves the existing allowlist/PPL safety model, adds retry repair, and explicitly addresses telemetry. However, several plans assume APIs or module visibility that do not match the current source, and Plan 05 has a serious shared-cache version-word issue that could deadlock `resolve_tier` after buffer flips. Overall risk: **HIGH** until the blocking integration and cache issues are corrected.

Note: GitNexus MCP tools/resources were not available in this session, so I could not run the requested GitNexus impact/query tools. I validated by direct source inspection instead.

## 58.6-01 - Config And Registry Foundation

**Summary:** Good foundational slice, but it underestimates the blast radius of changing `ProcessState::Injected` and adding retry states.

**Strengths**
- Correctly targets existing manual `AgentConfig` literals; both tests construct exhaustive structs at `dlp-agent/src/config.rs:710` and `dlp-agent/src/config.rs:760`, so adding `targeted_injection` will require updates.
- `PendingRetry` is needed: current retry records `Skipped(Failed(_))` before enqueueing at `dlp-agent/src/universal_injector.rs:245`, and `try_claim` rejects all occupied entries at `dlp-agent/src/process_registry.rs:225`.

**Concerns**
- **MEDIUM:** `ProcessState::Injected` is matched in many places. Current shape is at `dlp-agent/src/process_registry.rs:71`; existing matches use both explicit fields and `..`, so this must be a workspace-wide update, not just `process_registry`.
- **MEDIUM:** `ProcessRegistry` cap is 1,000 entries (`dlp-agent/src/process_registry.rs:19`). New long-lived low-confidence and pending states could churn quickly on enterprise endpoints.

**Suggestions**
- Add `InjectionPath` with `#[derive(Copy)]` and make `record_injected` delegate to `record_injected_with_path(..., Immediate)`.
- Raise or make configurable `MAX_REGISTRY_SIZE` before targeted mode, because low-confidence skips become meaningful state, not just historical telemetry.

**Risk Assessment:** **MEDIUM**. Mostly straightforward, but it changes a core enum and registry accounting.

## 58.6-02 - PE Import Scanner

**Summary:** The scanner is a useful primary signal, but the module-gating plan conflicts with the current crate layout.

**Strengths**
- `dashmap` and `glob` are already dependencies (`dlp-agent/Cargo.toml:128`, `dlp-agent/Cargo.toml:143`), so the cache/classifier support libraries fit the existing stack.
- Adding `goblin` near Phase 49 dependencies is sensible; current universal injection deps are grouped at `dlp-agent/Cargo.toml:140`.

**Concerns**
- **HIGH:** The plan says add both Windows and non-Windows module declarations, but adjacent dependencies are Windows-only. `classification_cache`, `process_registry`, `allowlist`, `etw_kernel_file`, and `universal_injector` are only exported under `#[cfg(windows)]` at `dlp-agent/src/lib.rs:151`, `dlp-agent/src/lib.rs:157`, `dlp-agent/src/lib.rs:160`, `dlp-agent/src/lib.rs:171`, and `dlp-agent/src/lib.rs:180`. Non-Windows stubs that import those modules will not compile.
- **MEDIUM:** Reading only the first `pe_max_scan_bytes` may parse many large PEs poorly if import structures fall outside the truncated slice. The plan treats “scan up to cap” as sufficient, but false negatives directly hurt the phase goal.

**Suggestions**
- Keep new modules `#[cfg(windows)]` unless their stubs are completely self-contained and do not reference Windows-only crate modules.
- Add explicit tests for “truncated PE returns 0 with warning” rather than implying truncated scans remain reliable.

**Risk Assessment:** **MEDIUM-HIGH**. The concept is good, but cfg/layout and false-negative handling need tightening.

## 58.6-03 - Command Line Reader

**Summary:** Useful secondary signal, with a good safety rule that basename alone cannot trigger injection. Implementation complexity is high because remote PEB reads are fragile.

**Strengths**
- The least-privilege intent matches existing process utilities, which use `PROCESS_QUERY_LIMITED_INFORMATION` for creation time (`dlp-agent/src/process_utils.rs:17`).
- Splitting basename from command-line match reduces spoofing risk.

**Concerns**
- **MEDIUM:** The plan asks for non-Windows stubs, but the surrounding classifier dependencies are Windows-only as noted above (`dlp-agent/src/lib.rs:157` to `dlp-agent/src/lib.rs:181`).
- **MEDIUM:** The tokenizer is specified as “simple double-quoted tokens.” Windows command-line parsing has backslash/quote edge cases; a naive tokenizer may miss file arguments and create false negatives.

**Suggestions**
- Use or mirror Windows `CommandLineToArgvW` semantics for tests, even if remote read returns a raw string.
- Include tests for escaped quotes, spaces in paths, and mixed-case extensions.

**Risk Assessment:** **MEDIUM**. Valuable signal, but PEB reading and token matching are easy to get subtly wrong.

## 58.6-04 - Hybrid ProcessClassifier

**Summary:** Good centralization design. It correctly recognizes that allowlist/PPL must precede all targeting signals.

**Strengths**
- Existing UniversalInjector currently performs allowlist and PPL inline at `dlp-agent/src/universal_injector.rs:171` and `dlp-agent/src/universal_injector.rs:182`; moving that into a classifier can remove duplicated logic.
- `detect_ppl` is already public (`dlp-agent/src/universal_injector.rs:289`), so reusing it is feasible.

**Concerns**
- **HIGH:** The non-Windows stub is not viable if it references `ProcessKey` or `AllowlistMatcher`, because those modules are Windows-only exports (`dlp-agent/src/lib.rs:157`, `dlp-agent/src/lib.rs:160`).
- **MEDIUM:** A 10,000-entry classifier cache is larger than the process registry’s 1,000-entry cap (`dlp-agent/src/process_registry.rs:19`), so classifier decisions can outlive lifecycle state. The `ProcessKey` protects PID reuse, but memory and stale telemetry behavior should be explicit.
- **LOW:** “Remove oldest inserted entry” is not directly supported by `DashMap`; the plan should specify how insertion time is tracked.

**Suggestions**
- Make classifier cache size configurable and align its default with registry capacity unless profiling justifies 10,000.
- Keep the classifier Windows-only initially; add portable stubs only after moving shared types outside `#[cfg(windows)]`.

**Risk Assessment:** **MEDIUM**. Architecturally solid, with cfg and cache-bound details to fix.

## 58.6-05 - LazyInjector And ClassificationCache Lookup

**Summary:** This is the riskiest plan. Lazy injection is necessary for coverage, but the proposed `resolve_tier` algorithm conflicts with the current shared-memory version encoding.

**Strengths**
- The plan correctly identifies that cloned `crossbeam` receivers would work-share events; current service clones the ETW receiver at `dlp-agent/src/service.rs:2177`, so explicit fanout is needed.
- Existing `EtwFileEvent` is cloneable (`dlp-agent/src/etw_kernel_file.rs:63`), so fanout is mechanically possible.

**Concerns**
- **HIGH:** `resolve_tier` says “retry while `version_word` is odd,” but the current ABI uses the low bit both as active buffer and odd/write marker. The shared ABI says low bit is active buffer (`dlp-common/src/classification_cache.rs:26`), and the agent publishes `even_version_word = (new_version << 1) | inactive_buffer` (`dlp-agent/src/classification_cache.rs:399`). If `inactive_buffer == 1`, the stable word is odd, so `resolve_tier` can spin forever.
- **HIGH:** `CHANNEL_CAPACITY` is private (`dlp-agent/src/etw_kernel_file.rs:111`), but Plan 06/05 references `etw_kernel_file::CHANNEL_CAPACITY` from `service.rs`.
- **MEDIUM:** The plan’s LazyInjector depends on concrete `Arc<ClassificationCache>`, whose constructor is Windows shared-memory only (`dlp-agent/src/classification_cache.rs:124`, `dlp-agent/src/classification_cache.rs:154`). The test plan’s “stub classification cache” will not work without a trait seam.

**Suggestions**
- First fix the cache version encoding: use separate bits for writer-in-progress and active buffer, or define helper functions for `is_stable()` and `active_buffer()`.
- Make `CHANNEL_CAPACITY` public or expose `pub fn channel_capacity()`.
- Introduce a `TierResolver` trait so LazyInjector tests can use a deterministic stub.

**Risk Assessment:** **HIGH**. The version-word issue can cause a live deadlock in the lazy path.

## 58.6-06 - Service Integration

**Summary:** This is the main integration plan and it addresses real existing problems, especially duplicated sweep logic and broken retry reclaim.

**Strengths**
- Existing retry path really is broken for reclaim: first failure records `Skipped(Failed)` at `dlp-agent/src/universal_injector.rs:246`, then retry calls `handle_event` again at `dlp-agent/src/universal_injector.rs:272`, but `try_claim` rejects occupied entries at `dlp-agent/src/process_registry.rs:236`.
- Startup and backstop sweeps duplicate allowlist/PPL/inject logic at `dlp-agent/src/service.rs:3303` and `dlp-agent/src/service.rs:3404`; routing them through `classify_and_inject` is the right cleanup.

**Concerns**
- **HIGH:** The enablement formula `legacy_enabled || mode != Universal` means default `Universal` mode remains disabled when `universal_injection_enabled` is absent/false. Current call passes `agent_config.universal_injection_enabled.unwrap_or(false)` at `dlp-agent/src/service.rs:1894`, and disabled mode returns early at `dlp-agent/src/service.rs:3030`. This weakens the “default Universal fallback” story.
- **MEDIUM:** The plan says use `Arc<dyn InjectProcess>` in sweeps, but current sweep signatures take `Arc<HookInjector>` (`dlp-agent/src/service.rs:3306`, `dlp-agent/src/service.rs:3407`). All call sites at `dlp-agent/src/service.rs:3180`, `dlp-agent/src/service.rs:3203`, and `dlp-agent/src/service.rs:3254` must change together.
- **MEDIUM:** Lazy shutdown needs a receiver-close path. Current shutdown stops correlator then ETW (`dlp-agent/src/service.rs:4200`, `dlp-agent/src/service.rs:4212`); a blocking lazy loop must not be left waiting on an owned receiver.

**Suggestions**
- Decide explicitly whether Phase 58.6 default config should enable universal injection or preserve the legacy flag. The plan currently implies both.
- Add a `LazyInjector` shutdown channel or ensure dropping fanout senders closes `lazy_rx` before awaiting the blocking task.

**Risk Assessment:** **HIGH**. Correct goal, significant service wiring blast radius.

## 58.6-07 - Telemetry And Audit

**Summary:** The audit schema extension is feasible and needed, but coverage counter semantics need correction.

**Strengths**
- Existing `AuditEvent::new` centralizes construction (`dlp-common/src/audit.rs:503`), so adding optional `details` with default is manageable.
- New event routing belongs in `EventType::routed_to_siem`, currently a central match at `dlp-common/src/audit.rs:248`; alert routing is similarly centralized at `dlp-common/src/audit.rs:290`.
- Test capture already exists (`dlp-agent/src/audit_emitter.rs:217`, `dlp-agent/src/audit_emitter.rs:263`), so audit assertions are practical.

**Concerns**
- **HIGH:** Plan 05 increments `t3t4_event_missed` before attempting lazy injection, but Plan 07 uses covered/(covered+missed) as the coverage metric. A successful lazy injection would still count as missed, which can make telemetry fail the >=99% success criterion.
- **MEDIUM:** Adding `details` affects the canonical hash payload because `canonical_json_for_hash` removes only `prev_hash` and `chain_hash` (`dlp-common/src/audit.rs:95`). That is probably acceptable, but the plan should explicitly update legacy hash-chain tests.
- **LOW:** `emit_audit` logs `resource_path` on failure (`dlp-agent/src/audit_emitter.rs:413`), so the “no raw paths” rule depends on every new call hashing before emission.

**Suggestions**
- Split counters into `observed_before_injection`, `lazy_injection_succeeded`, and `uncovered_after_attempt`, or count the triggering lazy event as covered on success if that is the intended metric.
- Add a regression test that `TargetedInjectionTelemetry.details` participates in chain hashing deterministically.

**Risk Assessment:** **MEDIUM-HIGH**. Schema work is straightforward; metric semantics can invalidate the phase goal.

## 58.6-08 - Integration Tests And Gates

**Summary:** The desired behavior matrix is good, but some test mechanics do not match the planned production types.

**Strengths**
- In-crate test module is appropriate because many service helpers and registry internals are crate-private; existing test-only exports already exist in `dlp-agent/src/lib.rs:183`.
- Audit capture helpers are available and already used in service tests (`dlp-agent/src/service.rs:5716`, `dlp-agent/src/service.rs:5723`).

**Concerns**
- **HIGH:** The lazy-injection test proposes a stub classification cache, but Plan 05 uses `Option<Arc<ClassificationCache>>`, not a trait. Current `ClassificationCache` is a concrete shared-memory owner (`dlp-agent/src/classification_cache.rs:124`), so this test will either need Windows shared memory or a trait seam.
- **MEDIUM:** `LazyInjector::run` is specified as a blocking receive loop. The test plan says “call run ... or use a short receive timeout wrapper,” but without an explicit shutdown/closed-channel pattern, tests can hang.
- **MEDIUM:** Requiring `sonar-scanner` as an autonomous gate is fragile in local agent runs; it depends on external tool availability and `SONAR_TOKEN`, while network/CI context may not exist.

**Suggestions**
- Add `TierResolver` and `InjectProcess` test seams before writing integration tests.
- Make `LazyInjector::run_until_closed(rx)` semantics explicit and close senders in tests.
- Treat Sonar as a recorded best-effort gate unless the environment guarantees the scanner and token.

**Risk Assessment:** **MEDIUM-HIGH**. Coverage goals are good, but testability needs one more seam.

## Overall Risk Assessment

**Overall risk: HIGH.** The design is broadly sound, but Plan 05’s version-word interpretation is a blocker, and Plans 02-04 over-promise non-Windows stubs despite the current Windows-only module graph. The most important fixes are: correct the classification-cache seqlock encoding/reader algorithm, add trait seams for tier resolution and injection, expose or avoid private ETW constants, and settle the default enablement semantics for Universal versus Targeted mode.

# Cross-AI Plan Review: Phase 58.6 (Targeted Hook Injection)

## Overall Assessment

The eight plans form a coherent, well-structured implementation of targeted hook injection. The wave ordering is correct, the threat models are thorough, and the design decisions (weighted PE scoring, separated basename/CLI signals, ETW lazy backstop) show sound engineering judgment. However, **four HIGH-severity concerns** and several structural ambiguities must be resolved before execution.

## Plan 01 — Config, Mode Enum, ProcessRegistry Extensions

### Strengths
- `ClassificationMode::Universal` as `#[default]` is the correct fail-safe posture (backward-compatible, no silent disable)
- `serde_ignored` integration is already present at `config.rs:374` — reusing it is right
- `goblin = "0.10"` resolves correctly (confirmed: `0.10.7` on crates.io)

### Concerns

**HIGH: Blast radius of `ProcessState::Injected` payload change.** `ProcessState::Injected { arch, injected_at, hello_received_at }` at `process_registry.rs:71-75` is destructured across multiple files. The plan says "use `..` where not relevant", but the existing `counts()` at line 381-388 uses full pattern matching. Every match site in `universal_injector.rs`, `service.rs`, `process_registry.rs` tests, and potentially others needs updating. `cargo check` will catch these, but the volume could be 20-30 sites.

**MEDIUM: Test struct literals are fragile.** The two `AgentConfig` test literals (`config.rs:708-742` and `760-791`) have 20+ fields each. The plan notes they must get `targeted_injection: TargetedInjectionConfig::default()`. This is correct but easy to miss during a rebase or merge — suggest adding a `#[serde(default)]` on the field instead of relying on test maintenance.

## Plan 02 — PE Import Scanner

### Strengths
- Weighted scoring (3x for specific APIs, 2x for ntdll syscalls, 1x for DLL presence) is well-motivated
- `max_scan_bytes` capping rather than rejecting large files is the right approach
- DashMap cache with TTL avoids re-parsing

### Concerns

**MEDIUM: Trait ownership ambiguity.** Plan 02 says to define `PeScoreSource` trait (or note it is "defined in Plan 04"). Plan 04 says the same. If both plans define it, there's a duplicate definition error. **This must be resolved — define it in Plan 04 (the classifier plan) and import in Plan 02.** The plan should explicitly state "adapt the `PeScoreSource` trait defined in Plan 04" rather than `"or define it here and re-export"`.

**MEDIUM: Parsing truncated PEs.** `goblin::pe::PE::parse(image_bytes)` on a file truncated to `max_scan_bytes` (16MB) will work for most files, but if imports or sections span beyond the truncation point, the parse will fail. The fallback to score 0 is safe (conservative), but operators may wonder why large executables get score 0. Consider a `tracing::debug!` log when parse fails on a truncated file.

## Plan 03 — Remote PEB Command-Line Reader

### Strengths
- Splitting `basename_match` from `command_line_match` is correct — basename alone never triggers injection
- 32 KiB cap on command-line read prevents DoS
- PPL `AccessDenied` handled gracefully (debug log, not warn)

### Concerns

**MEDIUM: Same trait ambiguity as Plan 02.** `CliSignalSource` is claimed by both Plan 03 and Plan 04. Resolve by defining in Plan 04.

**MEDIUM: PEB reading is fragile on Windows.** Reading `RTL_USER_PROCESS_PARAMETERS` from a remote process via `ReadProcessMemory` works for normal processes but can return stale/inconsistent data if the PEB is being modified concurrently by the target process (e.g., during startup when command-line is still being parsed). Consider a retry-with-backoff for transient read failures.

## Plan 04 — Hybrid ProcessClassifier

### Strengths
- Clear precedence: allowlist > PPL > mode gate > PE score > CLI signal
- Basename alone never triggers injection (documented design constraint)
- Cache with 10,000-entry bound prevents memory exhaustion

### Concerns

**LOW: DashMap LRU eviction is approximate.** DashMap shards entries across multiple internal maps. The "oldest inserted entry" eviction strategy described is not trivially implementable across shards without an external ordering structure. The existing `process_registry.rs` uses a sequence-number-based approach (`process_registry.rs:150`) — consider reusing that pattern instead of true LRU.

---

## Plan 05 — LazyInjector

### Strengths
- T3/T4 gating prevents wasteful injection on low-sensitivity paths
- Creation-time re-verification before injection is critical PID-reuse safety
- Rate limiting per ProcessKey

### Concerns

**HIGH: `ClassificationCache::resolve_tier` is net-new and complex.** The existing `classification_cache.rs` is a **write-only** cache (agent populates, hook DLLs read). The `resolve_tier` method described (seqlock protocol, FNV hash lookup over active buffer, prefix-table longest-prefix scan) is a non-trivial reader-side implementation that introduces a new code path into a lock-free shared-memory subsystem. The prefix scan in particular has no existing test coverage. This should be its own plan with dedicated tests, not a sub-task of the lazy injector.

**MEDIUM: Blocking thread shutdown.** `tokio::task::spawn_blocking` + crossbeam `recv()` is correct, but there's no abort mechanism described. The blocking thread will hang on `recv()` unless the channel is closed. Plan 06 mentions shutdown but the mechanism is unspecified — ensure `event_rx` is dropped during shutdown to unblock the thread.

## Plan 06 — Integration into Service (HIGHEST RISK)

### Strengths
- `InjectProcess` trait seam is long overdue and enables proper unit testing
- ETW fanout closes the work-sharing receiver-clone bug
- `PendingRetry` claim semantics fix the broken retry path

### Concerns

**CRITICAL: Blast radius in 6383-line file.** `service.rs` is the largest file in the workspace. This plan simultaneously:
1. Changes `init_universal_injection` signature (return type expands from 8 to 9+ fields)
2. Replaces `startup_sweep`/`backstop_sweep` bodies entirely
3. Adds a dedicated OS thread for ETW fanout
4. Wires `LazyInjector` via `spawn_blocking`
5. Changes sweep callers to pass `Arc<UniversalInjector>` instead of separate registry/matcher/injector
6. Modifies `RunLoopContext` struct and `run_loop_shutdown`

Each of these individually is high-risk in a 6383-line file. **Recommend either splitting this plan into two waves (6a: trait seam + retry fix, 6b: fanout + lazy wiring) or accepting that a rollback here is effectively a full-service rollback.**

**HIGH: Fanout thread is a new blocking point.** The `etw-kernel-file-fanout` thread reads from `etw_consumer.receiver()` and clones to both `correlator_tx` and `lazy_tx`. If either channel is full (CHANNEL_CAPACITY = 1024), `send()` blocks, which stalls the ETW consumer and causes event loss. Consider using `try_send()` with a counter of dropped events, or a bounded non-blocking fanout.

**MEDIUM: Mode activation logic.** The plan says `let enabled = agent_config.universal_injection_enabled.unwrap_or(false) || targeted_config.mode != ClassificationMode::Universal;`. This means setting `mode = "Monitor"` enables the injection subsystem without injecting — just classifying. This is correct but might surprise operators who see "injection enabled: true" in logs when no injection occurs.

## Consensus Summary

Both reviewers agree the plan set is directionally sound and well-layered, but identify several HIGH-severity blockers that must be resolved before execution, primarily around Plan 05 (`resolve_tier` / shared-memory cache semantics) and Plan 06 (`service.rs` integration blast radius).

### Agreed Strengths

- Wave ordering is logical; the foundation/config plan (01) correctly precedes scanner/classifier/lazy-injector/integration plans.
- Allowlist/PPL precedence is preserved in the classifier design.
- Separating basename from command-line signals reduces spoofing risk.
- SHA-256 path hashing prevents sensitive path leakage to SIEM.
- ETW fanout is the correct fix for the existing work-sharing receiver-clone bug.
- `PendingRetry` claim semantics correctly repair the broken retry reclaim path.

### Agreed Concerns

- **HIGH — Plan 05 `resolve_tier` version-word semantics.** Codex notes the current ABI uses the low bit as the active buffer, so an odd stable word can cause `resolve_tier` to spin forever. OpenCode flags the complexity of adding a reader-side API to the existing write-only shared-memory cache.
- **HIGH — Plan 06 `service.rs` blast radius.** Multiple simultaneous signature, threading, and shutdown changes in a 6,000+ line file create rollback risk. Both reviewers recommend splitting or sequencing the changes.
- **HIGH — Plan 06 ETW fanout blocking.** A bounded-channel fanout can stall the ETW consumer when downstream channels are full. OpenCode recommends `try_send` with drop telemetry.
- **HIGH — Plan 07 coverage metric semantics.** Counting `t3t4_event_missed` before a lazy injection attempt means a successful lazy injection still appears as a miss, undermining the >=99% coverage success criterion.
- **HIGH — Plan 02/04 non-Windows stub viability.** Current `dlp-agent/src/lib.rs` exports adjacent dependencies only under `#[cfg(windows)]`; non-Windows stubs that reference those modules will not compile.

### Divergent Views

- **Plan 01 blast radius:** OpenCode rates the `ProcessState::Injected` payload change as HIGH due to the number of match sites; Codex treats it as MEDIUM.
- **Plan 05 scope:** OpenCode argues `resolve_tier` deserves its own plan with dedicated tests; Codex treats it as a blocking implementation issue within Plan 05.
- **Sonar gate:** Codex flags `sonar-scanner` as a fragile autonomous gate in Plan 08; OpenCode does not mention it.
