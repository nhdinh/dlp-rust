## Codex Review

**Summary**

The plans are directionally strong and mostly sequenced well, but several assumptions do not match the current code. The biggest risks are integration semantics: `crossbeam_channel::Receiver::clone()` is work-sharing, not broadcast; `ClassificationCache` has no path-tier lookup API; `AuditEvent` has no `details` payload field; and the existing retry path appears ineffective because failed PIDs are marked processed before retry. These need plan changes before execution.

### Plan 01 — Config / Registry

**Strengths**
- Good foundation: current `AgentConfig` already uses `serde_ignored` for unknown TOML keys at `dlp-agent/src/config.rs:370`, so the config extension fits existing behavior.
- `ProcessRegistry` already uses PID plus creation time at `dlp-agent/src/process_registry.rs:21`, which supports the lazy-injection safety model.

**Concerns**
- **MEDIUM:** Plan wording conflicts: it says `ProcessRegistry` recognizes `LazyInjected` lifecycle states, but the task actually models lazy injection as `Injected { injection_path: Lazy }`. Clarify this before implementation.
- **LOW:** `AgentConfig` has manual struct literals in tests at `dlp-agent/src/config.rs:710` and `dlp-agent/src/config.rs:760`; adding a required field will break these unless the plan explicitly updates them.
- **LOW:** `ClassificationMode` cannot just "derive Default" without marking a default enum variant.

**Suggestions**
- Add `#[default] Universal` to `ClassificationMode`.
- Name the model consistently: either add `ProcessState::LazyInjected` or use `InjectionPath::Lazy` everywhere.

**Risk Assessment:** **LOW-MEDIUM**. Mostly mechanical, with some compile-break risk.

### Plan 02 — PE Import Scanner

**Strengths**
- Uses existing `dashmap` and `glob` dependency patterns; `dashmap` is already present at `dlp-agent/Cargo.toml:128`.
- Adding `goblin` near Phase 49 dependencies is consistent with the dependency grouping at `dlp-agent/Cargo.toml:140`.

**Concerns**
- **MEDIUM:** The plan's scoring may over-classify because imported symbols from broad DLLs like `kernel32.dll` can easily exceed threshold even when not file-specific.
- **MEDIUM:** The 16 MiB cap may classify large Electron/browser/Office binaries as score `0`, undercutting the stated basename list.
- **LOW:** Current `lib.rs` gates Windows modules directly at `dlp-agent/src/lib.rs:151`; non-Windows stubs need careful module layout or they will import Windows-only types accidentally.

**Suggestions**
- Score specific file APIs higher than generic DLL presence.
- Make max scan size configurable or use bounded PE header/import parsing instead of rejecting large executables outright.

**Risk Assessment:** **MEDIUM**. Useful component, but false positives/false negatives need tuning.

### Plan 03 — Command-Line Reader

**Strengths**
- PEB read failures are correctly treated as unknown, matching PPL realities.
- Uses existing `glob` dependency at `dlp-agent/Cargo.toml:143`.

**Concerns**
- **HIGH:** Plan contradicts itself: the threat model says basename alone never triggers injection, but `CommandLineReader::classify` returns `FileHandler` immediately on basename and Plan 04 injects on that signal.
- **MEDIUM:** `glob::Pattern` over a whole command line may not match indicators like `C:\Data\*` when the executable path precedes the file path.

**Suggestions**
- Split results into `BasenameFileHandler` and `CommandLineIndicator` so Plan 04 can require stronger evidence if desired.
- Match indicators against tokenized command-line arguments, not the full raw string.

**Risk Assessment:** **MEDIUM-HIGH** due to spoofable basename behavior.

### Plan 04 — ProcessClassifier

**Strengths**
- Correctly prioritizes existing allowlist and PPL checks; current universal path does this at `dlp-agent/src/universal_injector.rs:171` and `dlp-agent/src/universal_injector.rs:183`.
- Caching by `ProcessKey` aligns with registry PID-reuse handling.

**Concerns**
- **MEDIUM:** Duplicating allowlist/PPL checks in both `UniversalInjector` and `ProcessClassifier` adds extra per-process work and repeated `OpenProcess` calls.
- **HIGH:** Testability is under-specified. The plan says "prefer concrete structs," but deterministic PE/PEB tests need traits or explicit test doubles.
- **MEDIUM:** The cache bound is mentioned in the threat model but not concretely implemented in tasks.

**Suggestions**
- Extract a shared exclusion decision helper instead of re-running checks.
- Define small traits for PE score and CLI classification so unit tests do not need real PEs/PEBs.

**Risk Assessment:** **MEDIUM**. Good design center, but needs test seams and clearer signal precedence.

### Plan 05 — LazyInjector

**Strengths**
- Correctly limits lazy injection to low-confidence or discovered processes.
- Rate limiting by `ProcessKey` is the right shape.

**Concerns**
- **HIGH:** `Receiver::clone()` is not broadcast. `EtwKernelFileConsumer::receiver()` returns a crossbeam receiver at `dlp-agent/src/etw_kernel_file.rs:181`, and service already clones it for the bypass correlator at `dlp-agent/src/service.rs:2177`. A lazy clone would split events between consumers, not deliver all events to both.
- **HIGH:** `ClassificationCache` has no `resolve_tier` API. It can prepopulate roots at `dlp-agent/src/classification_cache.rs:548`, but no lookup method is exposed.
- **HIGH:** `crossbeam_channel::Receiver::recv()` blocks; running it directly in an async task can block a Tokio worker.
- **HIGH:** Final injection still calls `HookInjector::inject(pid)` by PID only at `dlp-agent/src/hook_injector.rs:141`; the plan should re-check creation time immediately before injection.

**Suggestions**
- Add a fanout task for ETW file events, or integrate lazy injection into the existing correlator path.
- Add a real tier lookup API or pass protected-path config directly.
- Use `spawn_blocking` or bridge crossbeam into `tokio::mpsc`.

**Risk Assessment:** **HIGH**. This plan needs redesign before implementation.

### Plan 06 — Service Integration

**Strengths**
- Identifies the right integration points: `UniversalInjector::handle_event`, startup sweep, backstop sweep, and `service.rs`.
- Preserving no-classifier universal behavior is important.

**Concerns**
- **HIGH:** Current `init_universal_injection` takes only `hook_injector_opt`, `enabled`, and `lifecycle_tx` at `dlp-agent/src/service.rs:3016`; wiring classifier/lazy injection requires a larger signature and return tuple change.
- **HIGH:** Targeted mode is still gated by `universal_injection_enabled.unwrap_or(false)` at `dlp-agent/src/service.rs:1894` and the early return at `dlp-agent/src/service.rs:3030`. The plan must define how targeted mode enables the process watcher.
- **HIGH:** Existing retry logic appears broken: failures record `Skipped(Failed)` at `dlp-agent/src/universal_injector.rs:246`, then queue retry at `:250`, but retry calls `handle_event` at `:272`, where `try_claim` returns already processed at `:160`.
- **HIGH:** Startup/backstop sweeps currently inject all non-skipped processes at `dlp-agent/src/service.rs:3366` and `dlp-agent/src/service.rs:3473`; classifier integration there is required, not optional.

**Suggestions**
- First fix retry semantics or explicitly preserve the existing limitation.
- Replace `enabled: bool` with a resolved injection mode config.
- Centralize "classify then maybe inject" for event, startup, and backstop paths.

**Risk Assessment:** **HIGH**. This is the main blast-radius plan.

### Plan 07 — Telemetry / SIEM

**Strengths**
- Extending `EventType` is straightforward; routing is centralized at `dlp-common/src/audit.rs:248`, alerting at `:290`.
- Existing telemetry loop gives a clear insertion point at `dlp-agent/src/service.rs:3230`.

**Concerns**
- **HIGH:** `AuditEvent` has no `details` field; fields end at `chain_hash` in `dlp-common/src/audit.rs:486`. The plan's JSON payload cannot be represented without schema changes.
- **HIGH:** The proposed coverage metric is process-state coverage, not T3/T4 file-event coverage. Current telemetry already computes process coverage at `dlp-agent/src/process_registry.rs:397`; TGT-05 needs event-level covered/missed counts.
- **MEDIUM:** Lazy-injection events include full sensitive paths; the threat model notes this but does not minimize or hash the path.

**Suggestions**
- Add a typed optional telemetry payload field or dedicated audit fields, not an undefined `details`.
- Count T3/T4 ETW events where PID was already hooked or lazy-injected within SLA.
- Consider hashing `resource_path` for telemetry events unless full path is operationally required.

**Risk Assessment:** **MEDIUM-HIGH**.

### Plan 08 — Integration Tests / Gates

**Strengths**
- Covers the right behavioral matrix: Targeted, Universal, Monitor, lazy injection, allowlist/PPL, PID reuse.
- Uses existing audit capture sink; capture exists in `dlp-agent/src/audit_emitter.rs:375`.

**Concerns**
- **HIGH:** Spy `HookInjector` is not possible with the current concrete type unless earlier plans add traits or test-only seams; `HookInjector` is a concrete struct at `dlp-agent/src/hook_injector.rs:64`.
- **MEDIUM:** The immediate-injection test description manually calls classifier then injector, which does not prove `UniversalInjector::handle_event` integrates the classifier.
- **MEDIUM:** Verification path is inconsistent: plans live in both `.planning/phases/58.6` and the long slug directory, so output locations should be normalized.

**Suggestions**
- Add tests that drive `UniversalInjector::handle_event` and sweeps, not only component calls.
- Introduce an `InjectProcess` trait or test constructor before writing integration tests.
- Keep all 58.6 verification artifacts in one phase directory.

**Risk Assessment:** **MEDIUM-HIGH**.

**Overall Risk**

**HIGH until Plans 05 and 06 are revised.** The architecture is sound, but current plan text assumes broadcast ETW receivers, a cache lookup API, flexible audit details, and working retry behavior that the source does not support today. Fix those assumptions first; the rest becomes a manageable staged implementation.

## Consensus Summary

Only Codex was invoked for this review cycle, so the consensus summary reflects Codex's findings alone.

### Agreed Strengths

- Foundation is sound: `AgentConfig` already supports `serde_ignored`, `ProcessRegistry` already uses `(PID, creation_time)` keys, and dependencies like `dashmap` and `glob` are already present.
- Threat modeling correctly identifies the need for allowlist/PPL precedence, rate limiting, PID-reuse safety, and PEB-read failure handling.
- The eight-plan wave structure logically decomposes the targeted-injection feature from config to integration tests.

### Agreed Concerns

- **Integration mismatches with existing code** are the dominant risk: ETW receiver cloning is work-sharing not broadcast, `ClassificationCache` lacks a tier lookup API, and `AuditEvent` lacks a `details` field.
- **Testability is under-specified**: concrete `HookInjector`, `PeImportScanner`, and `CommandLineReader` structs need traits or test-only seams for deterministic unit/integration tests.
- **Security signal precedence** is ambiguous: basename match alone can trigger immediate injection despite the threat model claiming otherwise.
- **Existing retry logic** appears ineffective because failed PIDs are marked processed before retry.
- **Coverage metric** does not match TGT-05's event-level >= 99% requirement; it currently measures process states rather than T3/T4 file events.

### Divergent Views

N/A — only one reviewer was invoked.
