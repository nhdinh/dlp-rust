# Phase 38.2: USB Enforcement Fix - PnP Disable Actually Works - Research

**Researched:** 2026-05-06
**Domain:** Windows Configuration Manager (CM) APIs, SetupDi APIs, USB PnP device enumeration
**Confidence:** HIGH

## Summary

The root cause is confirmed: `DeviceController::disable_usb_device` constructs a CM instance ID as `USB\VID_XXXX&PID_YYYY\{serial}`, but Windows' actual CM instance IDs for USB devices are either:

1. **Serial-based**: `USB\VID_0951&PID_1666\1234567890ABCDEF` (when device has unique serial)
2. **Location-based**: `USB\VID_0951&PID_1666\5&12345678&0&0` (when device has no serial; Windows synthesizes from USB topology)

The current code always constructs `USB\VID_XXXX&PID_YYYY\{serial}` and passes it to `CM_Locate_DevNodeW`. When the serial is `(none)` (synthesized for devices without a unique serial number), the constructed ID becomes `USB\VID_XXXX&PID_YYYY\(none)` which never matches any real device node. `CM_Locate_DevNodeW` returns `CR_NO_SUCH_DEVNODE` (0x0D), and the code silently returns `Ok(())` — so USB devices are NEVER actually disabled.

**Primary recommendation:** Replace the VID/PID/serial-based instance ID construction with direct resolution of the actual CM instance ID from the `dbcc_name` device interface path using `CM_Get_Device_Interface_PropertyW` with `DEVPKEY_Device_InstanceId`. This is the canonical Windows API for this exact purpose (Vista+). The resolved instance ID string is then passed to `CM_Locate_DevNodeW` → `CM_Disable_DevNode` as before.

## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01:** `DeviceController::disable_usb_device` MUST NOT construct the CM instance ID from VID/PID/serial. Instead, it MUST resolve the actual CM instance ID via SetupDi by matching the arriving device's interface path (`dbcc_name`) against the live device tree.
- **D-02:** Use `SetupDiGetClassDevsW(GUID_DEVINTERFACE_USB_DEVICE)` + `SetupDiEnumDeviceInfo` to enumerate present USB devices, then match by VID/PID/serial. The matched `SP_DEVINFO_DATA.DevInst` yields the correct device instance handle — OR use `CM_Get_Device_IDW` on the matched devinst to get the real instance ID string for `CM_Locate_DevNodeW`.
- **D-03:** If SetupDi enumeration fails or no matching device is found, log at `ERROR` level and return `Err` — do NOT silently return `Ok(())`.
- **D-04:** Devices with synthesized serials (`(none)`) MUST fall back to location-based matching. When serial is `(none)`, match only by VID + PID, then use the first matching device node's `DevInst` directly. Log a `warn` that enforcement is proceeding with a potentially ambiguous match.
- **D-05:** If multiple devices share the same VID+PID and both have `(none)` serial, log `ERROR` and return `Err` — do not disable an arbitrary device.
- **D-06:** If PnP disable (`CM_Disable_DevNode`) fails, the DACL defense-in-depth layer (`set_volume_deny_all`) MUST still attempt. But if BOTH layers fail, the overall operation MUST return `Err`.
- **D-07:** All enforcement outcomes MUST emit structured `tracing::info!` or `tracing::error!` span with fields: `vid`, `pid`, `serial`, `drive_letter`, `tier`, `pnp_result`, `dacl_result`.
- **D-08:** This phase fixes ONLY the PnP disable path. The DACL layer is touched only for error integration.
- **D-09:** The fix applies to both hot-plug arrivals and startup scan (`scan_existing_usb_identities`).

### Pattern 1: Instance ID Resolution via CM_Get_Device_Interface_PropertyW

**What:** Directly resolve the CM instance ID from a device interface path (`dbcc_name`) using the Configuration Manager property API.

**When to use:** This is the PRIMARY and RECOMMENDED approach. It is the canonical Windows API designed for exactly this purpose. Works on Windows Vista and later.

**Example:**
```rust
// Source: https://learn.microsoft.com/en-us/windows/win32/api/cfgmgr32/nf-cfgmgr32-cm_get_device_interface_propertyw
// Source: https://microsoft.github.io/windows-docs-rs/doc/windows/Win32/Devices/DeviceAndDriverInstallation/fn.CM_Get_Device_Interface_PropertyW.html

use windows::Win32::Devices::DeviceAndDriverInstallation::{
    CM_Get_Device_Interface_PropertyW, CR_BUFFER_SMALL, CR_SUCCESS,
};
use windows::Win32::Devices::Properties::{DEVPKEY_Device_InstanceId, DEVPROP_TYPE_STRING};

/// Resolves the CM device instance ID from a device interface path (dbcc_name).
///
/// The dbcc_name format is: `\\?\USB#VID_XXXX&PID_YYYY#SERIAL#{GUID}`
/// The returned instance ID format is: `USB\VID_XXXX&PID_YYYY\SERIAL` (or location-based)
pub fn resolve_instance_id_from_dbcc_name(dbcc_name: &str) -> Result<String, DeviceControllerError> {
    let wide: Vec<u16> = dbcc_name.encode_utf16().chain(std::iter::once(0)).collect();
    let mut property_type = 0u32;
    let mut required_size: u32 = 0;

    // Step 1: Get required buffer size.
    // SAFETY: wide is a valid null-terminated UTF-16 string.
    let cr = unsafe {
        CM_Get_Device_Interface_PropertyW(
            windows::core::PCWSTR(wide.as_ptr()),
            &DEVPKEY_Device_InstanceId,
            &mut property_type,
            None,
            &mut required_size,
            0,
        )
    };

    if cr != CR_BUFFER_SMALL && cr != CR_SUCCESS {
        return Err(DeviceControllerError::ConfigManager(cr.0));
    }

    // Step 2: Allocate buffer and retrieve the instance ID.
    let mut buffer: Vec<u16> = vec![0; (required_size as usize / 2) + 1];
    let mut property_size = required_size;

    let cr = unsafe {
        CM_Get_Device_Interface_PropertyW(
            windows::core::PCWSTR(wide.as_ptr()),
            &DEVPKEY_Device_InstanceId,
            &mut property_type,
            Some(buffer.as_mut_ptr() as *mut u8),
            &mut property_size,
            0,
        )
    };

    if cr != CR_SUCCESS {
        return Err(DeviceControllerError::ConfigManager(cr.0));
    }

    // Verify the property type is a string.
    if property_type != DEVPROP_TYPE_STRING.0 {
        return Err(DeviceControllerError::ConfigManager(
            0x00000013, // CR_WRONG_TYPE - not a standard CONFIGRET but conveys the issue
        ));
    }

    let len = buffer.iter().position(|&c| c == 0).unwrap_or(buffer.len());
    Ok(String::from_utf16_lossy(&buffer[..len]))
}
```

### Pattern 2: Fallback Instance ID Resolution via SetupDi Enumeration

**What:** Enumerate all present USB devices via `SetupDiGetClassDevsW` + `SetupDiEnumDeviceInfo`, match by VID/PID/serial, and read the instance ID via `SetupDiGetDeviceInstanceIdW` or `CM_Get_Device_IDW`.

**When to use:** Fallback if `CM_Get_Device_Interface_PropertyW` fails unexpectedly. Also needed for the startup scan path (`scan_existing_usb_identities`) where we don't have a `dbcc_name` — we only have `DeviceIdentity` from `enumerate_connected_usb_devices`.

**Example:**
```rust
// Source: existing codebase pattern in dlp-common/src/usb.rs::setupdi_description_for_device
// Source: existing codebase pattern in dlp-common/src/usb.rs::enumerate_connected_usb_devices_windows

use windows::Win32::Devices::DeviceAndDriverInstallation::{
    SetupDiGetClassDevsW, SetupDiEnumDeviceInfo, SetupDiGetDeviceInstanceIdW,
    SetupDiDestroyDeviceInfoList, DIGCF_PRESENT, DIGCF_DEVICEINTERFACE,
    SP_DEVINFO_DATA,
};

const GUID_DEVINTERFACE_USB_DEVICE: windows::core::GUID = windows::core::GUID::from_values(
    0xA5DCBF10, 0x6530, 0x11D2,
    [0x90, 0x1F, 0x00, 0xC0, 0x4F, 0xB9, 0x51, 0xED],
);

/// Finds the CM instance ID for a USB device matching the given VID/PID/serial.
///
/// When serial is "(none)", matches by VID+PID only (first match).
/// Returns Err if no match or if multiple ambiguous (none) matches exist.
pub fn find_instance_id_by_vid_pid_serial(
    vid: &str,
    pid: &str,
    serial: &str,
) -> Result<String, DeviceControllerError> {
    let hdev = unsafe {
        SetupDiGetClassDevsW(
            Some(&GUID_DEVINTERFACE_USB_DEVICE),
            windows::core::PCWSTR::null(),
            None,
            DIGCF_PRESENT | DIGCF_DEVICEINTERFACE,
        )
    }.map_err(|e| DeviceControllerError::Win32(e))?;

    let mut matches: Vec<String> = Vec::new();
    let mut index: u32 = 0;

    loop {
        let mut devinfo = SP_DEVINFO_DATA {
            cbSize: std::mem::size_of::<SP_DEVINFO_DATA>() as u32,
            ..Default::default()
        };
        if unsafe { SetupDiEnumDeviceInfo(hdev, index, &mut devinfo) }.is_err() {
            break;
        }

        let mut id_buf = [0u16; 256];
        let mut required: u32 = 0;
        if unsafe {
            SetupDiGetDeviceInstanceIdW(hdev, &devinfo, Some(&mut id_buf), Some(&mut required))
        }.is_ok() {
            let instance_id = String::from_utf16_lossy(
                &id_buf.iter().copied().take_while(|&w| w != 0).collect::<Vec<u16>>()
            );

            // Parse the instance ID to extract VID/PID/serial.
            // Instance ID format: USB\VID_XXXX&PID_YYYY\SERIAL
            let reshaped = format!("\\\\?\\{}", instance_id.replace('\\', "#"));
            let candidate = parse_usb_device_path(&reshaped);

            if candidate.vid == vid && candidate.pid == pid {
                if serial == "(none)" || candidate.serial == serial || candidate.serial == "(none)" {
                    matches.push(instance_id);
                }
            }
        }

        index += 1;
        if index > 1024 { break; }
    }

    unsafe { SetupDiDestroyDeviceInfoList(hdev); }

    match matches.len() {
        0 => Err(DeviceControllerError::ConfigManager(0x0000000D)), // CR_NO_SUCH_DEVNODE
        1 => Ok(matches.into_iter().next().unwrap()),
        _ if serial == "(none)" => {
            // Ambiguous match for (none) serial — per D-05, return Err.
            Err(DeviceControllerError::ConfigManager(0x0000000D))
        }
        _ => {
            // Multiple matches but serial was specific — this shouldn't happen.
            // Return the first match with a warning (or Err per strictness).
            Ok(matches.into_iter().next().unwrap())
        }
    }
}
```

### Anti-Patterns to Avoid

- **DO NOT** construct instance IDs as `format!(r"USB\VID_{vid}&PID_{pid}\{serial}")`. This is the exact bug being fixed.
- **DO NOT** silently return `Ok(())` on `CR_NO_SUCH_DEVNODE` unless the device was genuinely removed after a successful initial locate (D-03).
- **DO NOT** use `size_of::<SP_DEVICE_INTERFACE_DETAIL_DATA_W>()` for `cbSize` when calling `SetupDiGetDeviceInterfaceDetailW`. The Rust struct has `[u16; 1]` for `DevicePath`, but the C struct uses a flexible array member. Use `6` (x86) or `8` (x64) for the cbSize field, or use the raw buffer approach shown in `dlp-common/src/disk.rs`.
- **DO NOT** parse `dbcc_name` manually to derive the instance ID. The relationship between `dbcc_name` and CM instance ID is not a simple string transformation — use the official APIs.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Instance ID from dbcc_name | String manipulation on `dbcc_name` | `CM_Get_Device_Interface_PropertyW` with `DEVPKEY_Device_InstanceId` | The mapping is kernel-managed and not a simple text transform |
| Device enumeration | Raw registry parsing | `SetupDiGetClassDevsW` + `SetupDiEnumDeviceInfo` | Registry layout changes between Windows versions |
| Device path extraction from SetupDi | Direct struct field access | Two-step call with `Vec<u8>` buffer | `SP_DEVICE_INTERFACE_DETAIL_DATA_W` has variable-length `DevicePath` |

**Key insight:** Windows provides purpose-built APIs for every step of this pipeline. The original bug was caused by hand-rolling the instance ID construction instead of using the CM property API.

## Common Pitfalls

### Pitfall 1: Missing `Win32_Devices_Properties` Feature
**What goes wrong:** `CM_Get_Device_Interface_PropertyW` compiles (it's in `DeviceAndDriverInstallation`), but `DEVPKEY_Device_InstanceId` and `DEVPROPTYPE` are in `Win32::Devices::Properties` which requires the `Win32_Devices_Properties` feature. Without it, compilation fails with "unresolved import".
**Why it happens:** The windows crate is heavily feature-gated. Each sub-module requires its own feature flag.
**How to avoid:** Add `"Win32_Devices_Properties"` to both `dlp-agent/Cargo.toml` and `dlp-common/Cargo.toml` windows dependency feature lists.
**Warning signs:** Compilation error: `error[E0433]: failed to resolve: could not find 'Properties' in 'Devices'`.

### Pitfall 2: `CR_BUFFER_SMALL` vs `CR_SUCCESS` on First Call
**What goes wrong:** The first call to `CM_Get_Device_Interface_PropertyW` with a null buffer is expected to return `CR_BUFFER_SMALL` (0x1A = 26), not `CR_SUCCESS`. If the code checks only for `CR_SUCCESS`, it treats the size-query call as a failure.
**Why it happens:** This is the standard two-step Windows API pattern, but `CR_BUFFER_SMALL` is a "success-like" error code indicating "I need a bigger buffer."
**How to avoid:** Accept both `CR_BUFFER_SMALL` and `CR_SUCCESS` as valid returns from the first (size-query) call.
**Warning signs:** `required_size` remains 0 after the first call; second call uses empty buffer.

### Pitfall 3: Buffer Size in Bytes vs Characters
**What goes wrong:** `CM_Get_Device_Interface_PropertyW` returns `required_size` in **bytes**, but `Vec<u16>` is sized in **characters**. If you allocate `vec![0u16; required_size as usize]`, you get 2x the needed buffer (wastes memory but works). If you allocate `vec![0u16; required_size as usize / 2]` and the division truncates, you may get a buffer-too-small on the second call.
**Why it happens:** The API is C-based and returns sizes in bytes for byte-oriented buffers.
**How to avoid:** Use `(required_size as usize / 2) + 1` for the `Vec<u16>` capacity, or use a `Vec<u8>` and cast.

### Pitfall 4: `(none)` Serial Ambiguity
**What goes wrong:** When a device has no unique serial, Windows synthesizes a location-based instance ID. Two identical USB sticks (same VID/PID, both no serial) plugged into different ports will have different instance IDs. If the code matches only by VID+PID, it may disable the wrong device.
**Why it happens:** The USB spec does not require unique serial numbers. Many cheap USB drives omit them.
**How to avoid:** Per D-05, if serial is `(none)` and multiple devices match VID+PID, return `Err` rather than disabling an arbitrary device. For the hot-plug path, the `dbcc_name` from `WM_DEVICECHANGE` is specific to the arriving device, so `CM_Get_Device_Interface_PropertyW` resolves the correct instance ID without ambiguity.

### Pitfall 5: `SP_DEVICE_INTERFACE_DETAIL_DATA_W` cbSize on 64-bit
**What goes wrong:** Setting `cbSize` to `size_of::<SP_DEVICE_INTERFACE_DETAIL_DATA_W>()` gives the wrong value because the Rust struct has `[u16; 1]` for `DevicePath`, but the C struct's flexible array member has size 0 in the struct definition. On x64, `size_of::<SP_DEVICE_INTERFACE_DETAIL_DATA_W>()` returns 8 (4 for cbSize + 2 for one WCHAR + 2 padding), but Windows expects 6 (4 + 2) or 8 depending on architecture.
**Why it happens:** The Rust binding approximates the C flexible array member with a fixed-size array.
**How to avoid:** The existing code in `dlp-common/src/disk.rs` already handles this correctly by using a raw `Vec<u8>` buffer and casting. Follow that pattern, or use `std::mem::size_of::<u32>() + std::mem::size_of::<u16>()` (6 on x86, also 6 on x64 since the struct is packed).

## Code Examples

### Verified Pattern: Two-Step CM_Get_Device_Interface_PropertyW

```rust
// Source: Microsoft Learn documentation + windows-rs 0.62.2 source verification
// https://learn.microsoft.com/en-us/windows/win32/api/cfgmgr32/nf-cfgmgr32-cm_get_device_interface_propertyw

use windows::Win32::Devices::DeviceAndDriverInstallation::{
    CM_Get_Device_Interface_PropertyW, CR_BUFFER_SMALL, CR_SUCCESS,
};
use windows::Win32::Devices::Properties::{DEVPKEY_Device_InstanceId, DEVPROP_TYPE_STRING};

fn get_instance_id(dbcc_name: &str) -> Result<String, Box<dyn std::error::Error>> {
    let wide: Vec<u16> = dbcc_name.encode_utf16().chain(std::iter::once(0)).collect();
    let mut prop_type = 0u32;
    let mut size: u32 = 0;

    // Step 1: Query required buffer size.
    let cr = unsafe {
        CM_Get_Device_Interface_PropertyW(
            windows::core::PCWSTR(wide.as_ptr()),
            &DEVPKEY_Device_InstanceId,
            &mut prop_type,
            None,
            &mut size,
            0,
        )
    };
    if cr != CR_BUFFER_SMALL && cr != CR_SUCCESS {
        return Err(format!("CM_Get_Device_Interface_PropertyW failed: {:#010x}", cr.0).into());
    }

    // Step 2: Allocate buffer and retrieve property.
    let mut buf: Vec<u16> = vec![0; (size as usize / 2) + 1];
    let mut size = size;
    let cr = unsafe {
        CM_Get_Device_Interface_PropertyW(
            windows::core::PCWSTR(wide.as_ptr()),
            &DEVPKEY_Device_InstanceId,
            &mut prop_type,
            Some(buf.as_mut_ptr() as *mut u8),
            &mut size,
            0,
        )
    };
    if cr != CR_SUCCESS {
        return Err(format!("CM_Get_Device_Interface_PropertyW failed: {:#010x}", cr.0).into());
    }

    // Verify type.
    assert_eq!(prop_type, DEVPROP_TYPE_STRING.0, "unexpected property type");

    let len = buf.iter().position(|&c| c == 0).unwrap_or(buf.len());
    Ok(String::from_utf16_lossy(&buf[..len]))
}
```

## Open Questions

1. **Does `CM_Get_Device_Interface_PropertyW` require admin privileges?**
   - What we know: `CM_Disable_DevNode` already requires admin (the agent runs as a service with SYSTEM privileges).
   - What's unclear: Whether `CM_Get_Device_Interface_PropertyW` has additional privilege requirements beyond what the service already has.
   - Recommendation: The service already has SYSTEM privileges; this should be sufficient. No additional research needed.

2. **What happens if a device is removed between `CM_Get_Device_Interface_PropertyW` and `CM_Locate_DevNodeW`?**
   - What we know: The window is narrow (microseconds). The existing code already handles `CR_NO_SUCH_DEVNODE` by returning `Ok(())`.
   - What's unclear: Whether the new code should preserve this behavior.
   - Recommendation: Yes — per D-03, `CR_NO_SUCH_DEVNODE` after a successful initial locate should return `Ok(())` with a warning log.

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| USB device spoofing (same VID/PID, forged serial) | Spoofing | Location-based matching for `(none)` serials; registry cache verification |
| Race condition: device removed between locate and disable | Denial of Service | `CR_NO_SUCH_DEVNODE` handling; DACL fallback always runs |
| Privilege escalation via CM API misuse | Elevation of Privilege | Agent runs as SYSTEM (required for CM_Disable_DevNode); no additional privilege grant |
