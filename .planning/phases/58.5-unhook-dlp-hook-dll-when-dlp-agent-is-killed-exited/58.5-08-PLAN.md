<objective>
Close the remaining UAT Test 7 blocker diagnosed in `.planning/debug/dll-remains-after-agent-kill.md`: even after the 58.5-07 shutdown-ordering fix, injected processes can still have `dlp_hook_dll.dll` loaded because (1) control-thread start was best-effort, (2) idle injected processes never lazily start a control thread, (3) startup/backstop sweeps may double-load the DLL, and (4) a single `FreeLibraryAndExitThread` cannot unload a module whose reference count is greater than one.

Purpose: Guarantee that every process recorded as `Injected` has a live control-poll thread before the agent requests unhook, prevent reference-count inflation from repeated injections, and make the hook DLL self-unload path degrade gracefully when the reference count is elevated.
Output: Updated `HookInjector` with hard-success control-thread start and `ensure_control_thread`; updated sweeps with `is_module_loaded` guard; updated `request_unhook_from_injected` with a reconciliation pass; updated `self_unload` with a bounded reference-count loop; and passing unit/integration tests plus live UAT re-run.
</objective>

  <name>Task 1: Make control-thread start a hard success criterion and prevent double-load</name>
  <files>dlp-agent/src/hook_injector.rs, dlp-agent/src/service.rs</files>
  <read_first>
    dlp-agent/src/hook_injector.rs (inject, inject_into_process, start_remote_control_thread, is_module_loaded, HookError)
    dlp-agent/src/service.rs (startup_sweep, backstop_sweep, sync-client watcher is_module_loaded block)
  </read_first>
  <action>
    Change `start_remote_control_thread` in `dlp-agent/src/hook_injector.rs` from `fn ... -> ()` to `fn ... -> Result<(), HookError>`, returning a concrete `HookError::RemoteThreadFailed` when `CreateRemoteThread`, `WaitForSingleObject`, `GetExitCodeThread`, or a non-zero remote exit code indicates the control thread could not be started.

    In `inject_into_process`, treat control-thread start as part of injection success:
    - If `remote_module_base` cannot be resolved after `LoadLibraryW` succeeds, return `Err(HookError::InjectionFailed { pid, exit_code })` instead of returning `Ok(())`.
    - If `control_thread_rva` is `None`, return `Err(HookError::RemoteThreadFailed { pid, detail: "StartDlpControlThread RVA not available" })` instead of falling back to lazy start.
    - If `start_remote_control_thread` returns `Err`, propagate that error as the injection result (do not return `Ok`).

    Add a new public method `HookInjector::ensure_control_thread(&self, pid: u32) -> Result<(), HookError>` that performs an idempotent "start or confirm control thread" operation without calling `LoadLibraryW`:
    - Open the target process with the access rights needed for remote thread creation.
    - Resolve the remote module base of `dlp_hook_dll.dll` using the existing `remote_module_base` helper.
    - Compute the remote entry point from the cached `StartDlpControlThread` RVA and the module base.
    - Create a remote thread at that address, wait up to 10 seconds, and verify the exit code is `0`.
    - Return `Ok(())` only when the remote export succeeds; return `Err(HookError::RemoteThreadFailed { ... })` otherwise.

    Make `inject` guard against double-loading:
    - At the start of `inject(pid)`, before allocating remote memory or calling `LoadLibraryW`, call `HookInjector::is_module_loaded(pid, "dlp_hook_dll.dll")`.
    - If it returns `Ok(true)`, skip `LoadLibraryW` and call `self.ensure_control_thread(pid)`. Return the result of `ensure_control_thread`.
    - If it returns `Err(e)`, propagate the error and do not attempt injection.
    - If it returns `Ok(false)`, proceed with the existing `LoadLibraryW` + control-thread-start path.

    Update `startup_sweep` and `backstop_sweep` in `dlp-agent/src/service.rs` to mirror the sync-client watcher pattern:
    - After `try_claim` and allowlist/PPL checks but before calling `injector.inject(pid)`, call `HookInjector::is_module_loaded(pid, "dlp_hook_dll.dll")`.
    - If `Ok(true)`, record the process as already injected (`registry.record_injected(key, "x64".into())`) and skip the `inject` call.
    - If `Ok(false)`, proceed with `injector.inject(pid)` as today.
    - If `Err(e)`, log a warning with the PID and error, record a `SkipReason::Failed` categorization, and do not call `inject` (avoid risking a double-load when the module state is unknown).

    Add or extend unit tests in `dlp-agent/src/hook_injector.rs`:
    - A test that verifies `start_remote_control_thread` returns `Err` when the computed remote address is null.
    - A test that verifies `inject` returns an error when the control-thread export RVA is missing.
    - A test that verifies `ensure_control_thread` returns `Err` for PID 0 / access denied.
  </action>
  <acceptance_criteria>
    `start_remote_control_thread` has return type `Result<(), HookError>` and returns `Err` on any failure path.
    `inject_into_process` returns `Err` when remote module base resolution fails, control-thread RVA is missing, or `start_remote_control_thread` fails.
    `ensure_control_thread` exists, is public, performs no `LoadLibraryW`, and returns `Ok` only when the remote `StartDlpControlThread` thread exits with code `0`.
    `inject` skips `LoadLibraryW` and calls `ensure_control_thread` when the module is already loaded.
    `startup_sweep` and `backstop_sweep` skip already-loaded processes and record them as injected instead of re-injecting.
  </acceptance_criteria>

  <files>dlp-hook-dll/src/lib.rs</files>

  <action>
    Refactor `self_unload` in `dlp-hook-dll/src/lib.rs` to reduce the chance that an elevated module reference count leaves the DLL loaded after a successful unhook:
    - Define a small constant `MAX_SELF_UNLOAD_DECREMENTS` (for example, `8`) with a doc comment explaining it is a safety cap, not a guaranteed reference count.
    - After the active-call drain and before the final unload, acquire the DLL instance from `DLL_INSTANCE`.
    - Loop up to `MAX_SELF_UNLOAD_DECREMENTS` times:
      - Call `FreeLibrary` on the instance handle.
      - Query `GetModuleHandleW("dlp_hook_dll.dll")`. If it returns `Ok(None)`, the module has been unmapped; call `ExitThread(0)` immediately so the calling thread terminates cleanly instead of returning into unmapped code.
      - If `GetModuleHandleW` still returns a handle, continue to the next iteration.
    - After the bounded loop, perform the final atomic unload with `FreeLibraryAndExitThread(instance, 0)`.

    Add clear comments explaining that this loop is a best-effort defense; the primary protection against reference-count inflation is the agent-side `is_module_loaded` guard added in Task 1. Because Windows does not expose a safe way to self-unload a DLL whose reference count is greater than one from inside that DLL, the loop caps the number of decrements to avoid over-freeing.

    Add unit tests in `dlp-hook-dll/src/lib.rs`:
    - A test that verifies `self_unload_check()` returns the instance captured in `DllMain` (or `None` in the test binary).
    - A test that verifies `self_unload` aborts and returns `false` when active hook calls remain.
    - If feasible, add an integration-style test that loads the built `dlp_hook_dll.dll` into a child process twice, triggers `UnhookAll`, and asserts that the module is no longer loaded after a bounded wait. Mark the test `#[ignore]` with a note that it requires elevation and the built DLL.

    Ensure the existing `handle_unhook_command` and watchdog self-unload paths continue to call `self_unload` after `stop_and_unhook` succeeds.
  </action>

    The loop calls `ExitThread(0)` if `GetModuleHandleW` reports the module is gone.
    Unit tests verify the active-call-drain guard and the captured instance accessor.
    Existing `handle_unhook_command` and watchdog paths still invoke `self_unload` after successful unhook.

| T-58.5-08-01 | Denial of Service | `inject` hard-failing when control thread cannot start | mitigate | Failures are logged as warnings and the registry records `SkipReason::Failed`; the process remains unhooked but operational, and the agent can retry on restart. |

| T-58.5-08-05 | Denial of Service | `self_unload` loop over-decrements and crashes the host | mitigate | The loop is bounded to `MAX_SELF_UNLOAD_DECREMENTS` and checks `GetModuleHandleW`; the final decrement uses `FreeLibraryAndExitThread` so the thread exits atomically with the last safe decrement. |
