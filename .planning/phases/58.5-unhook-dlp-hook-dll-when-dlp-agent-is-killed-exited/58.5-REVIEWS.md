## Codex Review (gpt-5.5)

### Summary

Overall risk: **HIGH**. Plan 01 is a reasonable shared-type foundation, but Plans 02 and 03 assume an IPC direction that the current code does not support. The hook DLL is currently a named-pipe client, and the agent owns the named-pipe server; an agent "send unhook command" helper that connects to `\\.\pipe\DlpHookPipe` will connect back to the agent's own server, not to the injected DLL. Several cleanup and safety claims also conflict with current `OnceLock`-based shared-memory lifetimes and trampoline behavior.

### Strengths

- Plan 01 fits the current common crate shape. `IpcPayloadV1` is already the shared IPC discriminant in `dlp-common/src/hook_ipc.rs:75`, with existing fire-and-response payloads through `HashEvidence` at `dlp-common/src/hook_ipc.rs:131`. Adding variants at the end should preserve existing bincode enum indexes.
- The audit extension point is straightforward. `EventType` is centralized at `dlp-common/src/audit.rs:162`, with explicit `routed_to_siem()` and `triggers_alert()` match lists at `dlp-common/src/audit.rs:242` and `dlp-common/src/audit.rs:281`.
- The core unhook primitive exists for IAT hooks. `UnhookAll()` already iterates the 12-entry `HOOKS` table and restores saved IAT pointers in `dlp-hook-dll/src/lib.rs:695`.
- The ntdll restoration primitive exists and is public. `NtdllPatcher::unpatch_all_stubs()` is already `pub` in `dlp-hook-dll/src/ntdll_patcher.rs:341`, so adding it to `UnhookAll()` is mechanically plausible.

### Concerns

- **HIGH: Agent-to-DLL unhook IPC is not actually routed.**  
  The agent creates the named-pipe server at `dlp-agent/src/hook_ipc.rs:268` and accepts clients in `dlp-agent/src/hook_ipc.rs:294`. The hook DLL only has client helpers that connect to that pipe and send requests, e.g. `send_request()` in `dlp-hook-dll/src/pipe_client.rs:60` and `send_raw_oneway()` in `dlp-hook-dll/src/pipe_client.rs:230`. Plan 03's `send_unhook_command()` would connect to the agent's own server. The current server treats unknown agent-to-DLL payloads as unexpected at `dlp-agent/src/hook_ipc.rs:507`, warns, and continues without a response. This means the core success criterion, "agent shutdown -> UnhookCommand -> hook DLL," will not happen.

- **HIGH: Plan 02 and Plan 03 disagree on where the ack is returned.**  
  Plan 02's `send_unhook_ack()` uses hook DLL `send_raw_oneway`, which opens a new client connection to the agent pipe. Plan 03's `send_unhook_command()` waits for an `UnhookAck` on the same connection it opened. The existing framing is request/response per connection, with reads immediately after writes in both DLL and agent helpers (`dlp-hook-dll/src/pipe_client.rs:83`, `dlp-hook-dll/src/pipe_client.rs:89`; `dlp-agent/src/hook_ipc.rs:744`, `dlp-agent/src/hook_ipc.rs:746`). The proposed protocol will deadlock or time out even if the command somehow reaches a handler.

- **HIGH: Shared-memory cleanup plan conflicts with current `OnceLock` lifetimes.**  
  `HookJournal` is stored in `static JOURNAL: OnceLock<Option<HookJournal>>` at `dlp-hook-dll/src/hook_journal.rs:113`, but `HookJournal` does not store the mapping handle, and the code explicitly leaves the handle open for process lifetime at `dlp-hook-dll/src/hook_journal.rs:193`. `CacheLookup` is also stored in `OnceLock<Option<CacheLookup>>` at `dlp-hook-dll/src/classification_cache.rs:95`; it stores a header pointer and mapping handle at `dlp-hook-dll/src/classification_cache.rs:77`, but `OnceLock` cannot be cleared. Unmapping while `CacheLookup::get()` still returns `Some(&'static CacheLookup)` risks dangling pointers.

- **HIGH: The proposed shutdown flag does not protect trampolines yet.**  
  Plan 02 says `SHUTTING_DOWN` plus 50 ms grace period prevents in-flight crash risk, but current trampolines do not check such a flag before classification. `HookCreateFileW` enters `classify_and_log_path()` directly at `dlp-hook-dll/src/trampolines.rs:681` and `dlp-hook-dll/src/trampolines.rs:687`; ntdll trampolines do the same at `dlp-hook-dll/src/trampolines.rs:1847` and `dlp-hook-dll/src/trampolines.rs:1853`. Without adding checks to every trampoline or shared classification helper, restoring/freeing code can still race active hook paths.

- **HIGH: The threat model overstates pipe security.**  
  The plan claims pipe security restricts access to SYSTEM/service SID, but the current descriptor grants Authenticated Users read/write: `PIPE_SDDL = "D:(A;;GRGW;;;AU)(A;;GA;;;SY)(A;;GA;;;BA)"` in `dlp-agent/src/ipc/pipe_security.rs:23`. If an `UnhookCommand` handler is added on a pipe reachable by ordinary authenticated users, fake unhook requests become a real DLP bypass risk.

- **MEDIUM: Shutdown timing is not compatible with "every injected process."**  
  The service wraps all shutdown work in a 10 second timeout at `dlp-agent/src/service.rs:84` and `dlp-agent/src/service.rs:1162`. Plan 03 proposes sequential 3 second unhook waits per injected PID. More than a few injected processes can consume the entire shutdown budget before existing cleanup completes.

- **MEDIUM: Plan 03 directly uses private registry internals.**  
  `ProcessRegistry.states` is private at `dlp-agent/src/process_registry.rs:114`. The proposed `service.rs` loop over `registry.states.iter()` will not compile from another module. The plan needs a public `injected_processes()` snapshot method rather than direct field access.

- **MEDIUM: PID-only `UnhookAck` weakens the registry's PID-reuse invariant.**  
  The registry key intentionally uses PID plus creation time at `dlp-agent/src/process_registry.rs:20`. Plan 03 adds `record_unhooked_by_pid()` because `UnhookAck` lacks `creation_time`, which partially defeats that design. The plan notes PID reuse "should not happen," but the current code exists specifically because it can.

### Suggestions

- Redesign the control channel before implementation. Either create a per-process pipe hosted by the hook DLL, or use the existing agent-hosted pipe as a polling protocol where the DLL periodically sends `PollControl`/heartbeat and the agent replies with `UnhookCommand`.
- Add `creation_time` or a stable injection/session ID to `UnhookCommand` and `UnhookAck`, and expose `ProcessRegistry::injected_entries()` plus exact-key state transitions.
- Rework shared-memory ownership before adding `unmap_*()`: store mapping handles/views explicitly, put them behind a resettable `Mutex<Option<...>>`, and make `get()` return `None` after unhook instead of a dangling `OnceLock` value.
- Thread `is_shutting_down()` into the shared trampoline paths, preferably in `classify_and_log_path()` / `classify_and_log_handle()` and ntdll trampoline entrypoints, so all hooks pass through before patch restoration.
- Harden the hook IPC DACL or add authenticated command authorization. The current Authenticated Users pipe policy is not sufficient for an unhook command.
- Make shutdown dispatch parallel with an overall bounded deadline, and reserve time inside the existing 10 second `SHUTDOWN_TIMEOUT` or explicitly adjust that timeout with tests.

### Risk Assessment

**HIGH**. The phase goal is valid and the existing code has useful primitives, but the current plan will not deliver agent-driven unhook because the IPC topology is wrong. The memory cleanup and race-safety pieces also need design changes before implementation, not just tests. Plan 01 can proceed mostly as-is; Plans 02 and 03 should be revised before coding.

## Claude Review

### Summary

The four implementation plans (58.5-01 through 58.5-04) describe a coherent cooperative unhook protocol and correctly identify the missing pieces in the live source tree. However, several proposed mechanisms are **underspecified relative to the actual code structure** and will not compile as written. The review found no fundamental design flaws, but the hook-DLL shared-memory teardown, agent-side registry access, and IPC-server plumbing need refinement before execution.

### Verified Strengths

1. **Foundation types are cleanly extensible.**  
   `dlp-common/src/hook_ipc.rs:75-132` shows `IpcPayloadV1` is a derived `Serialize/Deserialize` enum with no `UnhookCommand`/`UnhookAck` variants — confirming Plan 01's missing-types claim.
   `dlp-common/src/audit.rs:162-237` shows `EventType` lacks `AgentShutdownUnhook`, `WatchdogSelfUnload`, and `UnhookFailure`; `routed_to_siem()` and `triggers_alert()` at `audit.rs:242-293` follow the exact match-arm pattern Plan 01 proposes extending.
   No new crate dependencies are required; the plans correctly reuse `bincode`, `serde`, and existing Windows crates.

2. **Hook-DLL primitives already exist.**  
   `dlp-hook-dll/src/lib.rs:695-706` confirms `UnhookAll()` currently restores only IAT entries — it does **not** disable ntdll detours or unmap shared memory, exactly as Plan 02 states.
   `dlp-hook-dll/src/ntdll_patcher.rs:341-357` shows `NtdllPatcher::unpatch_all_stubs()` is already public and transitions `Patched → Unpatched`, so Plan 02 can call it without signature changes.
   `dlp-hook-dll/src/pipe_client.rs:230-255` shows `send_raw_oneway()` exists and can carry the new `UnhookAck` envelope with a thin wrapper.

3. **Agent-side context is available.**  
   `dlp-agent/src/service.rs:954-1103` shows `RunLoopContext` already owns `process_registry: Arc<ProcessRegistry>` (`service.rs:1031`) and `hook_ipc_handle: Option<JoinHandle<()>>` (`service.rs:1087`), so Plan 03's shutdown dispatch has the data it needs.
   `dlp-agent/src/service.rs:3758-3795` confirms the hook IPC server stop block is the right insertion point for unhook dispatch.
   `dlp-agent/src/audit_emitter.rs:194-218` shows the test-capture sink pattern Plan 03 wants to reuse for `emit_unhook_audit`.

4. **Test strategy is sound.**  
   Plan 04 correctly scopes unit tests per crate and an end-to-end integration test, and its quality-gate list (`cargo test --all`, `clippy --all-targets`, `fmt --check`) matches project standards.

### Verified Concerns

#### C1. Plan 02's shared-memory unmap helpers cannot compile against current globals
- `dlp-hook-dll/src/hook_journal.rs:113` stores the journal as `static JOURNAL: OnceLock<Option<HookJournal>>`; the mapping handle lives **inside** the `HookJournal` struct (`hook_journal.rs:94-103`), not in standalone globals.
- `dlp-hook-dll/src/classification_cache.rs:95` stores the cache as `static CACHE_LOOKUP: OnceLock<Option<CacheLookup>>`; the handle is likewise inside `CacheLookup` (`classification_cache.rs:77-85`).
- Plan 02's proposed `unmap_journal()`/`unmap_cache()` snippets assume raw global handles and will not compile. The implementation must either:
  - Add `impl HookJournal { fn unmap(&mut self) }` and `impl CacheLookup { fn unmap(&mut self) }`, or
  - Restructure the globals to hold `(HANDLE, *mut u8)` pairs that can be cleared independently.
- **Downgrade to open question if not resolved:** yes — the exact unmap API must be designed before coding.

#### C2. Plan 03's registry iteration uses a private field
- `dlp-agent/src/process_registry.rs:115` declares `states: Arc<DashMap<ProcessKey, ProcessEntry>>` as **private**.
- Plan 03's `unhook_all_injected_processes` directly iterates `registry.states.iter()` (`58.5-03-PLAN.md:226`) — this will not compile.
- Required fix: add a public accessor such as `ProcessRegistry::iter_injected() -> impl Iterator<Item = (ProcessKey, &ProcessState)>` or make the proposed helper operate internally.

#### C3. Plan 03's IPC-server plumbing is underspecified
- `dlp-agent/src/hook_ipc.rs:93-103` shows `HookIpcServer` has no `process_registry` field.
- Plan 03 wants `handle_connection` to route `UnhookAck` and call `record_unhooked_by_pid()`, but `handle_connection` (`hook_ipc.rs:351-547`) currently receives no registry parameter, and neither does `accept_loop` (`hook_ipc.rs:294-348`) nor any `HookIpcServer::new*` constructor.
- This is a multi-file signature change affecting `HookIpcServer`, `accept_loop`, `handle_connection`, and `spawn_hook_ipc_server` in `service.rs`. The plan mentions it but does not show the full call-site migration.

#### C4. Plan 03's `send_unhook_command` assumes a blocking read with no timeout
- `dlp-agent/src/hook_ipc.rs:734-748` shows `send_request`/`send_raw` use `read_frame(pipe)` with no timeout argument.
- Plan 03's snippet calls `read_frame(handle)` synchronously and relies on `tokio::time::timeout` + `spawn_blocking` at the caller. This is acceptable, but the plan should explicitly note that `read_frame` itself is unbounded and that the timeout is enforced only at the async boundary.

#### C5. `catch_unwind` around `UnhookAll()` is unsafe in practice
- Plan 02 proposes wrapping `UnhookAll()` in `std::panic::catch_unwind` (`58.5-02-PLAN.md:177-179`).
- `UnhookAll()` mutates `static mut` globals (`lib.rs:306-317`), calls `restore_iat` (raw pointer writes), and may call `NtdllPatcher::unpatch_all_stubs` which uses `retour::RawDetour::disable`. These operations are not guaranteed to be `UnwindSafe`, and a panic mid-unpatch could leave the target process with torn hooks.
- The plan acknowledges this but does not provide a mitigation. A better approach is to make `UnhookAll()` infallible-by-design (log and continue per stub) rather than catching panics.

#### C6. Watchdog self-unload testability is hand-waved
- Plan 02 proposes `FreeLibraryAndExitThread` for self-unload and a test that checks `GetModuleHandleW` for `dlp_hook_dll.dll`.
- In unit tests the module name is the **test binary**, not `dlp_hook_dll.dll`, so `GetModuleHandleW(w!("dlp_hook_dll.dll"))` will fail. The plan admits this but does not show a concrete test design (e.g., a test-only `self_unload_check()` that returns the resolved handle without exiting).

#### C7. Shutdown ordering could race with pipe disconnect
- `dlp-agent/src/service.rs:3758-3795` stops the hook IPC server by forcing a client connect/close to unblock `ConnectNamedPipe`.
- Plan 03 inserts unhook dispatch **before** this block, which is correct. However, if `unhook_all_injected_processes` times out for one PID and the server is then force-closed, any in-flight `UnhookAck` from another PID may be lost. The plan's per-PID 3-second timeout bounds this, but the aggregate timeout (`injected_count * 3s`) may exceed existing shutdown deadlines. The plan notes this in T-58.5-08 but does not quantify the current `SHUTDOWN_TIMEOUT`.

### Suggestions

1. **Restructure shared-memory globals for unmap.**  
   In `hook_journal.rs` and `classification_cache.rs`, expose the mapping handle and view pointer through a small `struct Mapping { handle: HANDLE, view: *mut c_void }` stored in the `OnceLock`, so `unmap_journal()`/`unmap_cache()` can call `UnmapViewOfFile` + `CloseHandle` and then reset the `OnceLock`.

2. **Add a public registry accessor for injected PIDs.**  
   In `process_registry.rs`, add:
   ```rust
   pub fn iter_injected(&self) -> impl Iterator<Item = (ProcessKey, &ProcessState)> + '_ { ... }
   pub fn record_unhooked_by_pid(&self, pid: u32) -> bool { ... }
   ```
   Keep `record_unhooked` for full `ProcessKey` transitions.

3. **Thread the registry through HookIpcServer explicitly.**  
   Add `registry: Option<Arc<ProcessRegistry>>` to `HookIpcServer` and a `with_registry()` builder. Update `accept_loop` and `handle_connection` signatures. Update the production constructor call in `service.rs` around `service.rs:1710`.

4. **Make `UnhookAll()` infallible per stub instead of catch_unwind.**  
   Wrap each IAT restore and each `unpatch_all_stubs` call in individual `if let Some(...)` blocks that log and continue on error. Return `bool` or a per-stub result vector so `handle_unhook_command` can set `success` without relying on `catch_unwind`.

5. **Bound total unhook dispatch time.**  
   Add a `UNHOOK_TOTAL_BUDGET` (e.g., 10s) and skip remaining PIDs once exhausted, emitting `UnhookFailure` for skipped PIDs. Verify against the existing service-control shutdown deadline.

6. **Clarify 32/64-bit semantics in Plan 02/03.**  
   Document that `UnhookCommand`/`UnhookAck` bincode payloads are architecture-agnostic and that the agent may send to both 32-bit and 64-bit injected processes over the same pipe.

### Risk Assessment

| Risk | Severity | Likelihood | Mitigation |
|---|---|---|---|
| Shared-memory unmap helpers fail to compile | Medium | High | Redesign globals before coding (C1). |
| Registry private field blocks agent dispatch | Low | High | Add public accessor (C2). |
| IPC-server signature refactor is incomplete | Medium | Medium | Update all constructors and call sites (C3). |
| `catch_unwind` leaves target process unstable | High | Medium | Make `UnhookAll()` infallible per stub (C5). |
| Aggregate unhook timeout exceeds shutdown deadline | Medium | Medium | Add total budget and skip logic (suggestion 5). |
| Test-only mock code leaks into release | Low | Low | Gate all mocks with `#[cfg(test)]` per Plan 04 threat model. |

**Overall verdict:** The plans are architecturally sound and correctly traceable to the live code, but Plans 02 and 03 require structural adjustments before they can compile. I recommend approving Plans 01 and 04 as-is, and approving Plans 02/03 only after the global-handle accessor and IPC-server plumbing details are resolved.

## Codex Review 2 (gpt-5.4)

### Summary

The phase design is directionally right, but the plan set is not aligned with the repo's current state: large parts of Plans 01, 02, and 03 are already implemented in some form, while the real gaps are architectural. The biggest issue is that the current agent "unhook command" path loops back into the agent's own pipe server instead of reaching injected DLL instances, so the phase goal is not met even though many symbols already exist (`dlp-agent/src/hook_ipc.rs:525`, `dlp-agent/src/hook_ipc.rs:792`, `dlp-agent/src/service.rs:3758`, `dlp-hook-dll/src/lib.rs:764`). I would treat this as a redesign/repair phase, not a net-new implementation phase.

### Strengths

- Plan 01 is grounded in real shared types that already exist. `IpcPayloadV1::UnhookCommand` and `IpcPayloadV1::UnhookAck` are already present in `dlp-common/src/hook_ipc.rs:131-144`, with protocol structs in `dlp-common/src/hook_ipc.rs:508-552` and round-trip tests in `dlp-common/src/hook_ipc.rs:1287-1368`.
- The unhook audit event taxonomy also already exists and is correctly wired for SIEM/alert semantics: `AgentShutdownUnhook`, `WatchdogSelfUnload`, and `UnhookFailure` are in `dlp-common/src/audit.rs:237-245`, routed in `dlp-common/src/audit.rs:251-288`, and tested in `dlp-common/src/audit.rs:1930-2014`.
- Shutdown ordering in the agent is sensible. The current service runs its unhook pass before stopping the hook IPC server, which matches the dependency intent of Plan 03 (`dlp-agent/src/service.rs:3758-3763`).
- The hook DLL already centralizes restoration in one place. `UnhookAll()` restores IAT hooks, calls `unpatch_all_stubs()`, and invokes journal/cache cleanup hooks, which is the right structural seam for this phase (`dlp-hook-dll/src/lib.rs:721-752`).

### Concerns

- **HIGH**: The current protocol does not actually send an unhook command to injected DLLs. The DLL only has outbound client helpers in `dlp-hook-dll/src/pipe_client.rs:55-116` and `dlp-hook-dll/src/pipe_client.rs:231-255`; there is no DLL-side pipe server or receive loop. Meanwhile the agent explicitly handles `UnhookCommand` as a loopback on its own server and immediately returns `UnhookAck` itself (`dlp-agent/src/hook_ipc.rs:525-539`, `dlp-agent/src/hook_ipc.rs:792-795`). So Plan 03, as written, does not achieve success criteria 1 or 3.

- **HIGH**: Plan 02 says to spawn the watchdog from `init()`, but `init()` is called from `DllMain` (`dlp-hook-dll/src/lib.rs:542-548`, `dlp-hook-dll/src/lib.rs:583-633`). Creating threads or doing complex work from that path is loader-lock-sensitive, and the codebase already documents avoiding this pattern for other background work (`dlp-hook-dll/src/background_thread.rs:13-17`, `dlp-hook-dll/src/background_thread.rs:107-123`).

- **HIGH**: The shared-memory cleanup work is materially underestimated. `unmap_journal()` and `unmap_cache()` currently just `take()` the `OnceLock` and log (`dlp-hook-dll/src/hook_journal.rs:331-339`, `dlp-hook-dll/src/classification_cache.rs:598-605`). They do not call `UnmapViewOfFile`, and `HookJournal` does not even retain the mapping handle after init (`dlp-hook-dll/src/hook_journal.rs:193-201`). That means success criterion 4 is not met by the current mechanism.

- **HIGH**: The watchdog audit path is not credible if it depends on the same agent pipe whose absence triggers self-unload. The watchdog decides the agent is gone when `is_pipe_reachable()` fails repeatedly (`dlp-hook-dll/src/lib.rs:808-825`, `dlp-hook-dll/src/pipe_client.rs:377-379`), so emitting `watchdog_self_unload` over that pipe cannot be relied on. The plan needs an alternate durable path or next-start reconciliation.

- **MEDIUM**: Plan 03's proposed `record_rehooked_by_pid` conflicts with the registry's PID-reuse-safe design. The registry key is intentionally `(pid, creation_time)` (`dlp-agent/src/process_registry.rs:1-5`, `dlp-agent/src/process_registry.rs:20-25`). Falling back to PID-only matching during ack handling risks marking the wrong process instance as exited.

- **MEDIUM**: The no-crash safety story is incomplete. The plan talks about a shutdown flag and grace period, but the modified file list omits `trampolines.rs`, and current trampolines do not consult any shutdown flag before classifying (`dlp-hook-dll/src/trampolines.rs:681-699`). Without a real pass-through mode, the race described in the research is still open.

- **MEDIUM**: Agent-side telemetry is too coarse today, and the plans do not clearly close that gap. Current shutdown emits one aggregate `AgentShutdownUnhook` with `pid=0` and empty context (`dlp-agent/src/service.rs:3880-3894`), while `UnhookAck` reception does not update registry state or emit audit (`dlp-agent/src/hook_ipc.rs:507-523`). That is weaker than the stated success criteria.

- **LOW**: Plan 01 is stale against current code. It proposes different wire shapes (`timestamp_secs`, `Option<String>`, different enum names) than the existing protocol in `dlp-common/src/hook_ipc.rs:513-545`. Executing it literally would create churn rather than progress.

### Suggestions

- Reframe Plans 02 and 03 around a single explicit IPC architecture decision first: either add a DLL-side command listener/poller, or formalize watchdog-only unhook and remove the fiction that agent-issued `UnhookCommand` reaches the DLL.
- Do not start the watchdog from `DllMain`/`init()`. Reuse the existing lazy background-thread pattern and start it from a safe post-loader-lock path.
- Change the protocol identity to preserve `ProcessKey`, not just PID. Either include `creation_time` in `UnhookCommand`/`UnhookAck` or maintain an agent-side correlation token.
- Make shared-memory cleanup real: store the journal mapping handle and mapped view explicitly, implement `Drop` or explicit `UnmapViewOfFile`/`CloseHandle`, and test those resources directly.
- Add `trampolines.rs` to the scope and define a concrete pass-through behavior during unhook, otherwise "50ms grace period" is not enough to justify success criterion 3.
- Redefine audit expectations for crash-time watchdog unload. If the agent is dead, use local persistence in the DLL/host process or record reconciliation on next agent start; do not rely on best-effort pipe emission.

### Risk Assessment

**HIGH**

The plans contain good intent, but there are multiple design-level mismatches with the current code: the current command path is loopback-only, the watchdog startup location is unsafe, shared-memory cleanup is not actually implemented, and the crash-path audit story is not viable over the dead pipe. Without resolving those first, the phase can produce code that compiles and tests superficially while still failing the core goal: reliably unhooking live injected processes when the agent exits.

### Summary

The current tree already contains most of the unhook surface, so the plans are partly stale rather than greenfield. `IpcPayloadV1::UnhookCommand/UnhookAck`, the unhook audit event types, `UnhookAll`, watchdog/self-unload, and agent-side unhook IPC handlers already exist in the source. ### Plan 58.5-01

**Summary:** The direction is right, but the plan is out of sync with the codebase. Shared IPC and audit types are already present, so this should be a verification/update pass, not a fresh design.

**Strengths:**
- It correctly centers the shared protocol contract and audit semantics, which is the right place to anchor the phase.
- Serialization and SIEM-routing coverage are the right regressions to lock down.

**Concerns:**
- **HIGH:** The proposed shapes do not match the current ABI. The source already defines `UnhookCommand { reason, pid }`, `UnhookReason::{AgentShutdown, WatchdogTimeout}`, and `UnhookAck { pid, success, error: String }`, not `timestamp_secs`, `GracefulShutdown`, `AgentCrashDetected`, or `Option<String>`. **Suggestions:**

**Risk Assessment:** MEDIUM

### Plan 58.5-02

**Summary:** The unhook order is sensible, but the plan underestimates how much of the safety/cleanup work is already implemented and how much is still structurally missing.

**Strengths:**
- The order is correct: restore IAT first, then disable ntdll detours, then release shared-memory state.
- It recognizes the watchdog/self-unload path, which is the right fail-safe for agent death.

**Concerns:**
- **HIGH:** The current `UnhookAll` already uses `UNHOOK_IN_PROGRESS`; there is no `SHUTTING_DOWN` flag or explicit grace sleep in the implementation, so the plan's race-mitigation story is incomplete. See `dlp-hook-dll/src/lib.rs:133` and `dlp-hook-dll/src/lib.rs:721`.
- **HIGH:** The plan assumes `unmap_journal()`/`unmap_cache()` can close real OS resources, but the current code only `take()`s `OnceLock`s. `HookJournal` stores raw pointers and intentionally does not keep a handle, and `CacheLookup` stores a raw `HANDLE` with no `Drop` cleanup. See `dlp-hook-dll/src/hook_journal.rs:94`, `dlp-hook-dll/src/hook_journal.rs:193`, `dlp-hook-dll/src/hook_journal.rs:331`, `dlp-hook-dll/src/classification_cache.rs:77`, and `dlp-hook-dll/src/classification_cache.rs:598`.

## Claude Review 2

### Summary

The four implementation plans (58.5-01 through 58.5-04) describe a coherent cooperative unhook protocol and correctly identify the missing pieces in the live source tree. However, several proposed mechanisms are **underspecified relative to the actual code structure** and will not compile as written. The review found no fundamental design flaws, but the hook-DLL shared-memory teardown, agent-side registry access, and IPC-server plumbing need refinement before execution.

### Verified Strengths

1. **Foundation types are cleanly extensible.**  
   `dlp-common/src/hook_ipc.rs:75-132` shows `IpcPayloadV1` is a derived `Serialize/Deserialize` enum with no `UnhookCommand`/`UnhookAck` variants — confirming Plan 01's missing-types claim.

   No new crate dependencies are required; the plans correctly reuse `bincode`, `serde`, and existing Windows crates.

2. **Hook-DLL primitives already exist.**

   `dlp-hook-dll/src/ntdll_patcher.rs:341-357` shows `NtdllPatcher::unpatch_all_stubs()` is already public and transitions `Patched → Unpatched`, so Plan 02 can call it without signature changes.
   `dlp-hook-dll/src/pipe_client.rs:230-255` shows `send_raw_oneway()` exists and can carry the new `UnhookAck` envelope with a thin wrapper.

3. **Agent-side context is available.**  
   `dlp-agent/src/service.rs:954-1103` shows `RunLoopContext` already owns `process_registry: Arc<ProcessRegistry>` (`service.rs:1031`) and `hook_ipc_handle: Option<JoinHandle<()>>` (`service.rs:1087`), so Plan 03's shutdown dispatch has the data it needs.
   `dlp-agent/src/service.rs:3758-3795` confirms the hook IPC server stop block is the right insertion point for unhook dispatch.
   `dlp-agent/src/audit_emitter.rs:194-218` shows the test-capture sink pattern Plan 03 wants to reuse for `emit_unhook_audit`.

4. **Test strategy is sound.**  
   Plan 04 correctly scopes unit tests per crate and an end-to-end integration test, and its quality-gate list (`cargo test --all`, `clippy --all-targets`, `fmt --check`) matches project standards.

### Verified Concerns

#### C1. Plan 02's shared-memory unmap helpers cannot compile against current globals
- `dlp-hook-dll/src/hook_journal.rs:113` stores the journal as `static JOURNAL: OnceLock<Option<HookJournal>>`; the mapping handle lives **inside** the `HookJournal` struct (`hook_journal.rs:94-103`), not in standalone globals.
- `dlp-hook-dll/src/classification_cache.rs:95` stores the cache as `static CACHE_LOOKUP: OnceLock<Option<CacheLookup>>`; the handle is likewise inside `CacheLookup` (`classification_cache.rs:77-85`).
- Plan 02's proposed `unmap_journal()`/`unmap_cache()` snippets assume raw global handles and will not compile. The implementation must either:
  - Add `impl HookJournal { fn unmap(&mut self) }` and `impl CacheLookup { fn unmap(&mut self) }`, or
  - Restructure the globals to hold `(HANDLE, *mut u8)` pairs that can be cleared independently.
- **Downgrade to open question if not resolved:** yes — the exact unmap API must be designed before coding.

#### C2. Plan 03's registry iteration uses a private field
- `dlp-agent/src/process_registry.rs:115` declares `states: Arc<DashMap<ProcessKey, ProcessEntry>>` as **private**.
- Plan 03's `unhook_all_injected_processes` directly iterates `registry.states.iter()` (`58.5-03-PLAN.md:226`) — this will not compile.
- Required fix: add a public accessor such as `ProcessRegistry::iter_injected() -> impl Iterator<Item = (ProcessKey, &ProcessState)>` or make the proposed helper operate internally.

#### C3. Plan 03's IPC-server plumbing is underspecified
- `dlp-agent/src/hook_ipc.rs:93-103` shows `HookIpcServer` has no `process_registry` field.
- Plan 03 wants `handle_connection` to route `UnhookAck` and call `record_unhooked_by_pid()`, but `handle_connection` (`hook_ipc.rs:351-547`) currently receives no registry parameter, and neither does `accept_loop` (`hook_ipc.rs:294-348`) nor any `HookIpcServer::new*` constructor.
- This is a multi-file signature change affecting `HookIpcServer`, `accept_loop`, `handle_connection`, and `spawn_hook_ipc_server` in `service.rs`. The plan mentions it but does not show the full call-site migration.

#### C4. Plan 03's `send_unhook_command` assumes a blocking read with no timeout
- `dlp-agent/src/hook_ipc.rs:734-748` shows `send_request`/`send_raw` use `read_frame(pipe)` with no timeout argument.
- Plan 03's snippet calls `read_frame(handle)` synchronously and relies on `tokio::time::timeout` + `spawn_blocking` at the caller. This is acceptable, but the plan should explicitly note that `read_frame` itself is unbounded and that the timeout is enforced only at the async boundary.

#### C5. `catch_unwind` around `UnhookAll()` is unsafe in practice
- Plan 02 proposes wrapping `UnhookAll()` in `std::panic::catch_unwind` (`58.5-02-PLAN.md:177-179`).
- `UnhookAll()` mutates `static mut` globals (`lib.rs:306-317`), calls `restore_iat` (raw pointer writes), and may call `NtdllPatcher::unpatch_all_stubs` which uses `retour::RawDetour::disable`. These operations are not guaranteed to be `UnwindSafe`, and a panic mid-unpatch could leave the target process with torn hooks.
- The plan acknowledges this but does not provide a mitigation. A better approach is to make `UnhookAll()` infallible-by-design (log and continue per stub) rather than catching panics.

#### C6. Watchdog self-unload testability is hand-waved
- Plan 02 proposes `FreeLibraryAndExitThread` for self-unload and a test that checks `GetModuleHandleW` for `dlp_hook_dll.dll`.
- In unit tests the module name is the **test binary**, not `dlp_hook_dll.dll`, so `GetModuleHandleW(w!("dlp_hook_dll.dll"))` will fail. The plan admits this but does not show a concrete test design (e.g., a test-only `self_unload_check()` that returns the resolved handle without exiting).

#### C7. Shutdown ordering could race with pipe disconnect
- `dlp-agent/src/service.rs:3758-3795` stops the hook IPC server by forcing a client connect/close to unblock `ConnectNamedPipe`.
- Plan 03 inserts unhook dispatch **before** this block, which is correct. However, if `unhook_all_injected_processes` times out for one PID and the server is then force-closed, any in-flight `UnhookAck` from another PID may be lost. The plan's per-PID 3-second timeout bounds this, but the aggregate timeout (`injected_count * 3s`) may exceed existing shutdown deadlines. The plan notes this in T-58.5-08 but does not quantify the current `SHUTDOWN_TIMEOUT`.

### Suggestions

1. **Restructure shared-memory globals for unmap.**  
   In `hook_journal.rs` and `classification_cache.rs`, expose the mapping handle and view pointer through a small `struct Mapping { handle: HANDLE, view: *mut c_void }` stored in the `OnceLock`, so `unmap_journal()`/`unmap_cache()` can call `UnmapViewOfFile` + `CloseHandle` and then reset the `OnceLock`.

2. **Add a public registry accessor for injected PIDs.**  
   In `process_registry.rs`, add:
   ```rust
   pub fn iter_injected(&self) -> impl Iterator<Item = (ProcessKey, &ProcessState)> + '_ { ... }
   pub fn record_unhooked_by_pid(&self, pid: u32) -> bool { ... }
   ```
   Keep `record_unhooked` for full `ProcessKey` transitions.

3. **Thread the registry through HookIpcServer explicitly.**  
   Add `registry: Option<Arc<ProcessRegistry>>` to `HookIpcServer` and a `with_registry()` builder. Update `accept_loop` and `handle_connection` signatures. Update the production constructor call in `service.rs` around `service.rs:1710`.

4. **Make `UnhookAll()` infallible per stub instead of catch_unwind.**  
   Wrap each IAT restore and each `unpatch_all_stubs` call in individual `if let Some(...)` blocks that log and continue on error. Return `bool` or a per-stub result vector so `handle_unhook_command` can set `success` without relying on `catch_unwind`.

5. **Bound total unhook dispatch time.**  
   Add a `UNHOOK_TOTAL_BUDGET` (e.g., 10s) and skip remaining PIDs once exhausted, emitting `UnhookFailure` for skipped PIDs. Verify against the existing service-control shutdown deadline.

6. **Clarify 32/64-bit semantics in Plan 02/03.**  
   Document that `UnhookCommand`/`UnhookAck` bincode payloads are architecture-agnostic and that the agent may send to both 32-bit and 64-bit injected processes over the same pipe.

## Consensus Summary

### Reviewer Agreement

All structured reviewers (Codex gpt-5.5, Claude, Codex gpt-5.4, Codex gpt-5.4-mini, Claude-2, Claude-3) independently reached the same conclusion: **Phase 58.5 is high-risk as planned because the agent-to-hook-DLL control channel is not architecturally sound**, and several proposed mechanisms will not compile or will not achieve the stated success criteria.

### Agreed Strengths

- The cooperative unhook concept is the right approach (safer than `CreateRemoteThread` + `FreeLibrary`).
- The existing codebase already contains useful primitives: `UnhookAll()`, `NtdllPatcher::unpatch_all_stubs()`, `send_raw_oneway()`, `ProcessRegistry`, and the service shutdown seam.
- Plan 01's intent (shared types + audit events) is well-placed, though reviewers disagree on whether those types already exist in the tree.
- Plan 04's quality-gate list is directionally correct but incomplete (missing SonarQube).

### Agreed Concerns (highest priority)

1. **Agent-to-DLL command path is loopback-only / does not reach injected processes.**  
   The agent's `send_unhook_command()` connects to the agent's own pipe server; the hook DLL has no inbound listener. This is the single largest blocker for success criteria 1 and 3.

2. **Shared-memory cleanup does not actually release OS resources.**  
   Current `unmap_journal()`/`unmap_cache()` only `take()` `OnceLock`s and do not call `UnmapViewOfFile`/`CloseHandle`. Success criterion 4 is not met.

3. **Plan field signatures mismatch the existing implementation.**  
   Multiple reviewers note the plans describe `timestamp_secs`, `GracefulShutdown`/`AgentCrashDetected`, and `Option<String>` error, while the source (per reviewers) uses `pid`, `AgentShutdown`/`WatchdogTimeout`, and `String` error.

4. **Registry access patterns violate invariants or won't compile.**  
   `registry.states` is private; `record_unhooked_by_pid()` defeats the `(pid, creation_time)` PID-reuse-safe key.

5. **Watchdog wiring and self-unload correctness are unresolved.**  
   The watchdog is not started from a safe path, and `self_unload()` may resolve the host module handle instead of the DLL handle.

6. **Agent-side audit integration is missing.**  
   `unhook_all_injected_processes()` does not emit `AgentShutdownUnhook` or `UnhookFailure` events.

7. **Race safety during unhook is incomplete.**  
   Trampolines do not honor a shutdown/pass-through flag, and `catch_unwind` around `UnhookAll()` is unsafe.

### Divergent Views

- **How much is already implemented?**  
  Claude-3 and Codex gpt-5.4-mini report that Plans 01 and 02 are largely already implemented and tested in the tree. Codex gpt-5.5, Claude, and Codex gpt-5.4 treat the same code as missing or incomplete. This divergence suggests the working tree may be in an intermediate state and the plans are stale relative to the code. The planner should reconcile the plan text with `git status` and the actual source before execution.

- **Watchdog-only vs. wire protocol.**  
  Codex gpt-5.4 argues the wire protocol is a fiction and the design should be watchdog-only. Claude and Codex gpt-5.5 believe a real control channel is required and should be redesigned (per-process pipe or polling protocol).

### Recommended Next Steps

1. **Reconcile plans with the live source tree.**  
   Determine which types/functions already exist and update the plans to describe only the remaining work.

2. **Resolve the IPC architecture before coding.**  
   Choose one model:
   - Per-process pipe hosted by the hook DLL, or
   - Agent-hosted polling protocol (DLL heartbeat → agent replies with `UnhookCommand`), or
   - Watchdog-only with documented acceptance criteria.

3. **Fix shared-memory ownership.**  
   Store mapping handles/views in explicitly owned, resettable structures and call `UnmapViewOfFile` + `CloseHandle`.

4. **Add registry accessors and preserve `ProcessKey`.**  
   Expose `iter_injected()`; include `creation_time` or a session token in `UnhookCommand`/`UnhookAck`.

5. **Wire audit emission and timeouts.**  
   Thread `EmitContext` through `RunLoopContext`; emit `AgentShutdownUnhook`/`UnhookFailure`; enforce `UNHOOK_ACK_TIMEOUT_MS` per PID and a total shutdown budget.

6. **Update Plan 04.**  
   Add SonarQube verification, concrete assertions, and tests for the actual (reconciled) architecture.

### Overall Consensus Risk

**HIGH**. The phase goal is correct and the existing primitives are valuable, but the current plans will not deliver reliable agent-driven unhook. The IPC topology, shared-memory cleanup, watchdog wiring, and audit integration must be redesigned before execution.

## Current HIGH Concerns
- Plan 02 still starts the DLL control-poll/watchdog thread lazily from the first hook call. Injected-but-idle processes may never poll, so graceful shutdown cannot guarantee every injected process receives `UnhookCommand`. PLAN.md should start the control thread from a safe post-attach/init path for every successful injection, not only from classification/hook execution.
- Plan 02’s unload safety is still under-specified. `SHUTTING_DOWN` plus a fixed 50 ms sleep does not prove no thread is currently inside a trampoline, journal/cache access, or DLL code when IAT/ntdll stubs are restored, views are unmapped, and `FreeLibraryAndExitThread` unloads the DLL. PLAN.md should require active-call guards/refcounts, reentry blocking, drain-with-timeout semantics, and a defined fallback if active calls do not quiesce.
- Plan 02 proposes resetting `OnceLock` mappings through pointer-cast mutable access based on a documented invariant. The invariant is not mechanically enforced, so concurrent readers can make this undefined behavior and crash-prone. PLAN.md should replace this with a lock-protected `Option<Mapping>`, `Mutex/RwLock`, or another sound ownership mechanism.
- Plan 03 routes every `UnhookAck` to `record_unhooked` without checking `ack.success`. A failed unhook ack would incorrectly transition the process to `Exited`, suppressing `UnhookFailure` while hooks/shared mappings may remain active. PLAN.md should only mark `Exited` on `success=true`; `success=false` must preserve failure state and emit/report `UnhookFailure`.

## Current Actionable Non-HIGH Concerns
- Watchdog evidence is written under `%LOCALAPPDATA%`, but the injected process user/session may differ from the SYSTEM agent’s environment, so startup reconciliation may scan the wrong directory. PLAN.md should use a service-visible global path such as `C:\ProgramData\DLP\WatchdogSelfUnload` with explicit ACLs, or specify per-user scanning.
- `PollControl` returns `UnhookCommand` based only on the global `UNHOOK_ALL_REQUESTED` flag. It does not validate that `pid + creation_time` belongs to a currently injected registry entry. PLAN.md should require registry validation before returning a command, with no-op for unknown/stale callers.
- `WatchdogSelfUnload` audit is only emitted when an evidence file matches an existing registry entry. If the registry was lost, stale, or not yet populated after agent crash, the event disappears. PLAN.md should require emitting an audit event for unmatched evidence as untracked/unknown, or define why unmatched evidence is safely retained and retried.
- The watchdog timeout is defined as three consecutive pipe failures at one-second intervals, but the plan does not distinguish transient pipe/server restart errors from true agent death. PLAN.md should add a bounded grace/backoff or agent-liveness signal so short service restarts do not unnecessarily self-unload healthy hooks.
