# Phase 58.5: Code Review Report

**Reviewed:** 2026-06-30T16:01:41Z
**Depth:** deep
**Files Reviewed:** 21
**Status:** issues_found

## Summary

Phase 58.5 implements cooperative self-unhook for the hook DLL and agent-side orchestration, plus comprehensive tests and quality-gate fixes. The code generally follows the intended protocol and the new tests cover the key paths. However, several correctness and security-relevant defects remain. The most severe is a duplicated initialization of the universal injection subsystem in `dlp-agent/src/service.rs`, which causes the hook IPC server and the service shutdown/reconciliation paths to operate on two different process registries, breaking unhook coordination. Other blockers include a double-close of the control-thread event handle and a pipe read that ignores its timeout, which can prevent the watchdog from firing.

## Critical Issues

### CR-01: Universal injection subsystem is initialized twice with different registries

**File:** `dlp-agent/src/service.rs:1828-1842` and `dlp-agent/src/service.rs:2082-2096`
**Issue:** `run_loop_init` calls `init_universal_injection` in two different places. The first call produces the `process_registry` used to build `HookIpcServerConfig` and spawn the hook IPC server. The second call shadows all returned variables and the `RunLoopContext` is populated from the second set. This means:

- The hook IPC server routes `PollControl` and `UnhookAck` updates to one registry.
- `request_unhook_from_injected`, `reconcile_watchdog_evidence`, and graceful shutdown use a second, unrelated registry.
- Duplicate ETW process watchers, backstop sweeps, and retry queue consumers are spawned; the first set is leaked.

As a result, the agent may report zero injected processes during shutdown, skip the cooperative unhook wait, and fail to reconcile watchdog evidence.
**Fix:** Initialize the subsystem once, before the hook IPC server is configured, and reuse the returned handles and registry everywhere.

```rust
// In run_loop_init, perform a single Phase 49 initialization.
let (
    process_watcher_opt,
    universal_injector_opt,
    process_registry,
    allowlist_matcher,
    backstop_shutdown_tx,
    backstop_handle,
    retry_shutdown_tx,
    retry_handle,
) = init_universal_injection(
    hook_injector_opt.as_ref(),
    agent_config.universal_injection_enabled.unwrap_or(false),
)
.await;

// Use the SAME process_registry for the IPC server...
let hook_ipc_config = HookIpcServerConfig {
    // ...
    process_registry: Arc::clone(&process_registry),
};
let hook_ipc_handle = spawn_hook_ipc_server(hook_ipc_config);

// ...and store the SAME handles/registry in RunLoopContext.
RunLoopContext {
    // ...
    process_registry,
    backstop_shutdown: Some(backstop_shutdown_tx),
    backstop_handle,
    retry_shutdown: Some(retry_shutdown_tx),
    retry_handle,
    // ...
}
```

### CR-02: Control-thread shutdown event handle is closed twice

**File:** `dlp-agent/src/service.rs` is not the affected file; the defect is in `dlp-hook-dll/src/control_thread.rs:220-221` and `dlp-hook-dll/src/control_thread.rs:121-127`
**Issue:** `shutdown_control_thread` takes the shutdown event out of the running `ControlThread`, calls `SetEvent`, joins the thread, and then explicitly calls `CloseHandle(event)`. The `ControlThread` `Drop` implementation also calls `CloseHandle(self.shutdown_event)` for the same handle value. Closing a Windows handle twice is undefined behavior: the second close may close an unrelated handle that the OS has reused, leading to crashes or resource corruption.
**Fix:** Remove the explicit `CloseHandle` in `shutdown_control_thread`; let `Drop` own the handle lifecycle. Alternatively, invalidate the handle after closing it and guard `Drop`.

```rust
// In shutdown_control_thread, remove:
unsafe {
    let _ = CloseHandle(event);   // DELETE THIS BLOCK
}
```

### CR-03: `read_frame` ignores its timeout, blocking the watchdog path

**File:** `dlp-hook-dll/src/pipe_client.rs:413-426` and `dlp-hook-dll/src/pipe_client.rs:450-473`
**Issue:** `read_frame` accepts a `_timeout_ms` parameter but delegates to `read_exact`, which calls `ReadFile` in blocking mode with no timeout. In `control_thread_loop`, `poll_control` is invoked with a 1,000 ms timeout, but the read will block indefinitely if the agent pipe is connected but not responding. This prevents the control/watchdog loop from detecting agent unresponsiveness and initiating self-unhook.
**Fix:** Honor the timeout. Use overlapped I/O or set a pipe read timeout so `read_frame` returns `PipeError::Timeout` when no data arrives within `timeout_ms`.

```rust
fn read_frame(pipe: HANDLE, timeout_ms: u32) -> Result<Vec<u8>, PipeError> {
    let mut len_buf = [0u8; 4];
    read_exact_with_timeout(pipe, &mut len_buf, timeout_ms)?;
    let len = u32::from_le_bytes(len_buf) as usize;
    const MAX_PAYLOAD: usize = 67_108_864;
    if len > MAX_PAYLOAD {
        return Err(PipeError::Malformed);
    }
    let mut payload = vec![0u8; len];
    read_exact_with_timeout(pipe, &mut payload, timeout_ms)?;
    Ok(payload)
}
```

Implement `read_exact_with_timeout` using overlapped `ReadFile` + `WaitForSingleObject` or `CancelSynchronousIo`.

## Warnings

### WR-01: `UnhookAck` failure audit uses a hard-coded `EmitContext`

**File:** `dlp-agent/src/hook_ipc.rs:564-601`
**Issue:** When an `UnhookAck` arrives with `success: false`, the handler emits a `UnhookFailure` audit event using a hard-coded context (`agent_id: "AGENT-01"`, `session_id: 0`, `user_sid: "S-1-5-18"`, `machine_name: None`). This violates the project's "Explicit Auditability" principle and makes SIEM correlation unreliable if the real agent ID, machine name, or session differ.
**Fix:** Pass the service's `EmitContext` into `HookIpcServerConfig`, store it in `HookIpcServer`, and use it when emitting failure audits.

```rust
// In HookIpcServerConfig:
pub audit_ctx: crate::audit_emitter::EmitContext,

// In HookIpcServer:
audit_ctx: Option<crate::audit_emitter::EmitContext>,

// In the UnhookAck failure branch:
if let Some(ctx) = &self.audit_ctx {
    crate::audit_emitter::emit_unhook_audit(
        ctx,
        dlp_common::EventType::UnhookFailure,
        ack.pid,
        false,
        ack.error.clone(),
    );
}
```

### WR-02: Journal sequence counter is incremented on a local copy only

**File:** `dlp-hook-dll/src/hook_journal.rs:390-410` and `dlp-hook-dll/src/hook_journal.rs:154-180`
**Issue:** `journal_write` obtains a `JournalView` (a `Copy` struct) from `HookJournal::get`, writes the entry using `self.next_seq`, and then increments `next_seq` through a raw pointer to the local `JournalView` on the stack. Because `JournalView` is copied by value, the global `HookJournal.next_seq` is never advanced. Every call writes `seq = 1`, breaking the monotonic sequence guarantee relied on for forensics and correlation.
**Fix:** Advance the sequence number on the authoritative `HookJournal` instance while the `JOURNAL` lock is held, or store `next_seq` in shared memory.

```rust
pub fn journal_write(...) {
    let Some(journal) = HookJournal::get() else { ... };
    journal.write(...);
    // Advance the global counter, not the stack copy.
    HookJournal::advance_seq();
}

impl HookJournal {
    pub fn advance_seq() {
        let mut guard = JOURNAL.lock().ok()?;
        if let Some(ref mut j) = *guard {
            j.next_seq += 1;
        }
    }
}
```

### WR-03: DACL staging GC and removal-application shutdown senders are dropped

**File:** `dlp-agent/src/service.rs:2235-2238` and `dlp-agent/src/service.rs:3927-3951`
**Issue:** `init_dacl_watcher` creates shutdown senders for the staging GC task (`_gc_shutdown_tx`) and the removal-application task (`_removal_shutdown_tx`) but binds them with underscore prefixes and stores `None` in `RunLoopContext`. `run_loop_shutdown` checks those context fields, finds `None`, and never signals the tasks. The tasks continue running until the process exits, and graceful shutdown is incomplete.
**Fix:** Keep the real senders in `RunLoopContext`.

```rust
RunLoopContext {
    // ...
    dacl_gc_shutdown: Some(_gc_shutdown_tx),
    dacl_gc_handle: Some(gc_handle),
    dacl_removal_shutdown: Some(_removal_shutdown_tx),
    dacl_removal_handle: Some(removal_handle),
    // ...
}
```

### WR-04: `CONTROL_THREAD_STOPPING` is never reset in production after shutdown

**File:** `dlp-hook-dll/src/control_thread.rs:106-107`, `dlp-hook-dll/src/control_thread.rs:177-178`, and `dlp-hook-dll/src/control_thread.rs:43-47`
**Issue:** `shutdown_control_thread` sets `CONTROL_THREAD_STOPPING` to `true` and joins the thread, but only the test helper `reset_watchdog_test_state` resets it. If the service ever restarts the agent in-process (or if the hook DLL is reloaded), the next `control_thread_loop` will exit immediately on its first iteration because the stale flag is still true, leaving the process without a watchdog.
**Fix:** Reset the flag inside `shutdown_control_thread` after a successful join, or at the start of `start_control_thread` before spawning the new thread.

```rust
pub fn shutdown_control_thread() {
    CONTROL_THREAD_STOPPING.store(true, Ordering::SeqCst);
    // ... join thread ...
    CONTROL_THREAD_STOPPING.store(false, Ordering::SeqCst);
}
```

### WR-05: Watchdog self-unload path has no explicit loop exit

**File:** `dlp-hook-dll/src/control_thread.rs:261-276`
**Issue:** In the watchdog timeout branch, the production build calls `crate::self_unload()`. In the test build the code `break`s, but in production there is no `break` or `return` after `self_unload`. `self_unload` is expected to terminate the thread via `FreeLibraryAndExitThread`, but if that ever changes or returns, the loop would continue executing code from a DLL that has been unloaded.
**Fix:** Add an explicit `return;` or `break;` after `self_unload()` as defensive code.

```rust
Err(_) => {
    if last_agent_response.elapsed().as_millis() as u64 >= watchdog_timeout_ms() {
        crate::debug_log("[dlp-hook] watchdog: agent unresponsive, initiating self-unhook\0");
        persist_watchdog_evidence(pid, creation_time);
        crate::UnhookAll();
        #[cfg(test)]
        {
            WATCHDOG_TRIGGERED.store(true, Ordering::SeqCst);
            break;
        }
        #[cfg(not(test))]
        unsafe {
            crate::self_unload();
            return; // defensive: never execute from unloaded memory
        }
    }
}
```

## Info

### IN-01: Default audit context uses fixed SYSTEM/session values

**File:** `dlp-agent/src/service.rs:3720-3729`
**Issue:** `build_audit_ctx` hard-codes `user_sid: "S-1-5-18"`, `user_name: "SYSTEM"`, and `session_id: 1`. This is correct for a service running as SYSTEM but is inflexible and could mis-tag audit events if the agent is ever run in a different security context or session. Consider deriving the session ID from the service session and documenting the assumption.
**Fix:** Document the assumption, or resolve the current session ID at startup instead of hard-coding `1`.
