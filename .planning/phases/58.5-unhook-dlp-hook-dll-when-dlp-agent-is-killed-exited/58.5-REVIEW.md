# Phase 58.5: Code Review Report

**Reviewed:** 2026-06-30T20:21:27Z
**Depth:** standard
**Files Reviewed:** 21
**Status:** issues_found

## Summary

Phase 58.5 adds cooperative self-unhook for the hook DLL and agent-side orchestration for graceful shutdown and watchdog evidence reconciliation. The protocol types are clear, the new registry helpers are well-tested, and the hook DLL correctly protects its shared-memory mappings behind locks. However, a standard-depth adversarial review found three correctness defects that can prevent the unhook protocol from working or corrupt process state, plus nine quality/correctness warnings that should be fixed before this phase ships.

## Blocker Issues

### BL-01: Universal injection subsystem is initialized twice with mismatched registries

**Classification:** BLOCKER
**File:** `dlp-agent/src/service.rs:1828-1842` and `dlp-agent/src/service.rs:2082-2096`
**Issue:** `run_loop_init` calls `init_universal_injection` twice. The first call produces the `process_registry` used by `spawn_hook_ipc_server` (line 1550). The second call shadows the same variable names and the resulting registry is stored in `RunLoopContext`. This means:

- The hook IPC server validates `PollControl` and routes `UnhookAck` against one registry.
- `request_unhook_from_injected`, `reconcile_watchdog_evidence`, and graceful shutdown use a second, unrelated registry.
- The second registry is created just before ETW startup, so `reconcile_watchdog_evidence` sees no injected processes and emits everything as untracked.
- Duplicate ETW process watchers, backstop sweeps, and retry queue consumers are spawned; the first set is leaked.

Because of this, the agent may report zero injected processes during shutdown and skip the cooperative unhook wait.

**Fix:** Initialize the subsystem once, before the hook IPC server is built, and reuse the returned handles and registry everywhere.

```rust
// Single call before spawn_hook_ipc_server.
let (
    process_watcher_opt,
    universal_injector_opt,
    process_registry,
    allowlist_matcher,
    backstop_shutdown_tx,
    backstop_handle,
    retry_shutdown_tx,
    retry_handle,
) = init_universal_injection(
    hook_injector_opt.as_ref(),
    agent_config.universal_injection_enabled.unwrap_or(false),
)
.await;

// Pass the SAME registry to the IPC server...
let server = crate::hook_ipc::HookIpcServer::with_cache_offline_and_bypass(...)
    ...
    .with_registry(Arc::clone(&process_registry));

// ...and store the SAME registry/handles in RunLoopContext.
RunLoopContext {
    process_registry,
    backstop_shutdown: Some(backstop_shutdown_tx),
    backstop_handle,
    retry_shutdown: Some(retry_shutdown_tx),
    retry_handle,
    ...
}
```

### BL-02: Control-thread shutdown event handle is closed twice

**Classification:** BLOCKER
**File:** `dlp-hook-dll/src/control_thread.rs:121-127`, `dlp-hook-dll/src/control_thread.rs:189-194`, and `dlp-hook-dll/src/control_thread.rs:220-221`
**Issue:** `shutdown_control_thread` copies the `shutdown_event` handle out of the running `ControlThread`, sets the global state back to `NotStarted` (which drops the `ControlThread` and invokes `Drop`), and then explicitly calls `CloseHandle(event)` on the same handle value. Closing a Windows handle twice is undefined behavior; the second close may close an unrelated handle that the OS has reused, leading to crashes or resource corruption.

**Fix:** Remove the explicit `CloseHandle` in `shutdown_control_thread` and let the `ControlThread` `Drop` own the handle lifecycle.

```rust
// In shutdown_control_thread, delete this block:
unsafe {
    let _ = CloseHandle(event);
}
```

### BL-03: `read_frame` ignores its timeout, blocking the watchdog path

**Classification:** BLOCKER
**File:** `dlp-hook-dll/src/pipe_client.rs:413-426` and `dlp-hook-dll/src/pipe_client.rs:450-473`
**Issue:** `read_frame` accepts a `_timeout_ms` parameter but delegates to `read_exact`, which calls `ReadFile` in blocking mode with no timeout. In `control_thread_loop`, `poll_control` is invoked with a 1,000 ms timeout, but the read will block indefinitely if the agent pipe is connected but not responding. This prevents the control/watchdog loop from detecting agent unresponsiveness and initiating self-unhook.

**Fix:** Honor the timeout by using overlapped I/O or another mechanism that returns `PipeError::Timeout` when no data arrives within `timeout_ms`.

```rust
fn read_frame(pipe: HANDLE, timeout_ms: u32) -> Result<Vec<u8>, PipeError> {
    let mut len_buf = [0u8; 4];
    read_exact_with_timeout(pipe, &mut len_buf, timeout_ms)?;
    let len = u32::from_le_bytes(len_buf) as usize;
    const MAX_PAYLOAD: usize = 67_108_864;
    if len > MAX_PAYLOAD {
        return Err(PipeError::Malformed);
    }
    let mut payload = vec![0u8; len];
    read_exact_with_timeout(pipe, &mut payload, timeout_ms)?;
    Ok(payload)
}
```

Implement `read_exact_with_timeout` with overlapped `ReadFile` + `WaitForSingleObject` or `CancelSynchronousIo` so the watchdog can fire even when the agent is hung.

## Warning Issues

### WR-01: `UnhookAck` failure audit uses a hard-coded `EmitContext`

**Classification:** WARNING
**File:** `dlp-agent/src/hook_ipc.rs:579-593`
**Issue:** When an `UnhookAck` arrives with `success: false`, the handler emits an `UnhookFailure` audit event using a hard-coded context (`agent_id: "AGENT-01"`, `session_id: 0`, `user_sid: "S-1-5-18"`, `machine_name: None`). This violates the project's "Explicit Auditability" principle and makes SIEM correlation unreliable if the real agent ID, machine name, or session differ.

**Fix:** Pass the service's `EmitContext` into the hook IPC server, store it, and use it when emitting failure audits.

```rust
// In HookIpcServer:
audit_ctx: Option<crate::audit_emitter::EmitContext>,

// In the UnhookAck failure branch:
if let Some(ctx) = &self.audit_ctx {
    crate::audit_emitter::emit_unhook_audit(
        ctx,
        dlp_common::EventType::UnhookFailure,
        ack.pid,
        false,
        ack.error.clone(),
    );
}
```

### WR-02: Hook journal sequence counter is advanced on a local copy only

**Classification:** WARNING
**File:** `dlp-hook-dll/src/hook_journal.rs:390-410`
**Issue:** `journal_write` obtains a `JournalView` (a `Copy` struct) from `HookJournal::get`, writes the entry using `self.next_seq`, and then increments `next_seq` through a raw pointer to the local `JournalView` on the stack. Because `JournalView` is copied by value, the global `HookJournal.next_seq` is never advanced. Every call writes `seq = 1`, breaking the monotonic sequence guarantee relied on for forensics and ETW correlation.

**Fix:** Advance the sequence number on the authoritative `HookJournal` instance while the `JOURNAL` lock is held, or store `next_seq` in shared memory.

```rust
pub fn journal_write(...) {
    let Some(journal) = HookJournal::get() else { ... };
    journal.write(...);
    HookJournal::advance_seq();
}

impl HookJournal {
    pub fn advance_seq() {
        let mut guard = JOURNAL.lock().ok()?;
        if let Some(ref mut j) = *guard {
            j.next_seq += 1;
        }
    }
}
```

### WR-03: DACL staging GC and removal-application shutdown senders are dropped

**Classification:** WARNING
**File:** `dlp-agent/src/service.rs:2706-2718`, `dlp-agent/src/service.rs:2234-2238`, and `dlp-agent/src/service.rs:3928-3951`
**Issue:** `init_dacl_watcher` creates shutdown senders for the staging GC task (`_gc_shutdown_tx`) and the removal-application task (`_removal_shutdown_tx`) but binds them with underscore prefixes and stores `None` in `RunLoopContext`. `run_loop_shutdown` checks those context fields, finds `None`, and never signals the tasks. The tasks continue running until the process exits, so graceful shutdown is incomplete and may hold files/ACLs open.

**Fix:** Keep the real senders in `RunLoopContext`.

```rust
RunLoopContext {
    // ...
    dacl_gc_shutdown: Some(_gc_shutdown_tx),
    dacl_gc_handle: Some(gc_handle),
    dacl_removal_shutdown: Some(_removal_shutdown_tx),
    dacl_removal_handle: Some(removal_handle),
    // ...
}
```

### WR-04: `CONTROL_THREAD_STOPPING` is never reset in production after shutdown

**Classification:** WARNING
**File:** `dlp-hook-dll/src/control_thread.rs:43-47`, `dlp-hook-dll/src/control_thread.rs:106-107`, and `dlp-hook-dll/src/control_thread.rs:177-213`
**Issue:** `shutdown_control_thread` sets `CONTROL_THREAD_STOPPING` to `true` and joins the thread, but only the test helper `reset_watchdog_test_state` resets it. If the service ever restarts the agent in-process (or if the hook DLL is reloaded), the next `control_thread_loop` will exit immediately on its first iteration because the stale flag is still true, leaving the process without a watchdog.

**Fix:** Reset the flag inside `shutdown_control_thread` after a successful join, or at the start of `start_control_thread` before spawning the new thread.

```rust
pub fn shutdown_control_thread() {
    CONTROL_THREAD_STOPPING.store(true, Ordering::SeqCst);
    // ... join thread ...
    CONTROL_THREAD_STOPPING.store(false, Ordering::SeqCst);
}
```

### WR-05: Watchdog self-unload path has no explicit loop exit

**Classification:** WARNING
**File:** `dlp-hook-dll/src/control_thread.rs:261-276`
**Issue:** In the watchdog timeout branch, the production build calls `crate::self_unload()`. The test build `break`s, but in production there is no `break` or `return` after `self_unload`. `self_unload` is expected to terminate the thread via `FreeLibraryAndExitThread`, but if that ever changes or returns, the loop would continue executing code from a DLL that has been unloaded.

**Fix:** Add an explicit `return;` after `self_unload()` as defensive code.

```rust
#[cfg(not(test))]
unsafe {
    crate::self_unload();
    return; // defensive: never execute from unloaded memory
}
```

### WR-06: `UNHOOK_ALL_REQUESTED` is not reset at service startup

**Classification:** WARNING
**File:** `dlp-agent/src/service.rs:138-140`, `dlp-agent/src/service.rs:357`, and `dlp-agent/src/service.rs:4036`
**Issue:** A `reset_unhook_signal` helper exists but is never called during service startup. `run_service` only calls `reset_shutdown_signal`. If the service is ever restarted in-process, `UNHOOK_ALL_REQUESTED` remains `true` from the previous shutdown, so new `PollControl` frames from freshly injected processes immediately receive `UnhookCommand { reason: AgentShutdown }`, causing premature unhook before a real shutdown is requested.

**Fix:** Call `reset_unhook_signal()` in `run_service` alongside `reset_shutdown_signal()`.

```rust
pub fn run_service() -> Result<()> {
    reset_shutdown_signal();
    reset_unhook_signal();
    // ...
}
```

### WR-07: Watchdog evidence reconciliation reads unbounded untrusted files

**Classification:** WARNING
**File:** `dlp-agent/src/service.rs:2309-2346` and `dlp-agent/src/service.rs:2423-2428`
**Issue:** `reconcile_watchdog_evidence_in_dir` reads any `.json` file in `C:\ProgramData\DLP\WatchdogSelfUnload` using `std::fs::read_to_string` without a size cap, parses it as untyped JSON, and embeds the raw file content directly into the audit event's `justification` field. If the directory is writable by a lower-privileged principal or contains a very large/crafted file, this can cause memory pressure, audit log inflation, or misleading audit records. In addition, the `pid` value is cast from `u64` to `u32` without range validation.

**Fix:**

- Enforce a maximum file size (e.g., 64 KiB) before reading.
- Validate the JSON schema (pid, creation_time, timestamp_secs, reason) and reject unexpected fields.
- Do not embed the raw content in the audit event; extract only the fields needed.
- Validate that `pid` fits in a `u32` before casting.

### WR-08: Default audit context hard-codes SYSTEM/session values

**Classification:** WARNING
**File:** `dlp-agent/src/service.rs:3721-3729`
**Issue:** `build_audit_ctx` hard-codes `user_sid: "S-1-5-18"`, `user_name: "SYSTEM"`, and `session_id: 1`. A Windows service runs in session 0, not session 1, and the agent may not always run as SYSTEM. These fixed values can mis-tag audit events and break session-based SIEM correlation.

**Fix:** Resolve the current process token's SID and session ID at startup, with a documented fallback only when resolution fails.

```rust
fn build_audit_ctx(machine_name: Option<String>) -> crate::audit_emitter::EmitContext {
    let (sid, session) = resolve_service_identity().unwrap_or_else(|| {
        ("S-1-5-18".to_string(), 0)
    });
    crate::audit_emitter::EmitContext {
        agent_id: std::env::var("DLP_AGENT_ID").unwrap_or_else(|_| "AGENT-UNKNOWN".to_string()),
        session_id: session,
        user_sid: sid,
        user_name: "SYSTEM".to_string(), // overridden per-event where available
        machine_name,
    }
}
```

### WR-09: `UnhookAck` failure audit is only emitted when `error` is `Some`

**Classification:** WARNING
**File:** `dlp-agent/src/hook_ipc.rs:579-593`
**Issue:** The handler only emits `UnhookFailure` when `ack.success == false` **and** `ack.error` is `Some`. If the hook DLL reports `success: false` with no error string, the failure is silently ignored and no alert is generated, even though `EventType::UnhookFailure` is configured to trigger a SIEM alert.

**Fix:** Emit the audit event for any `success: false` ack, using the provided error or a generic placeholder.

```rust
if !ack.success {
    crate::audit_emitter::emit_unhook_audit(
        ctx,
        dlp_common::EventType::UnhookFailure,
        ack.pid,
        false,
        ack.error.clone().or_else(|| Some("unhook failed".to_string())),
    );
}
```
