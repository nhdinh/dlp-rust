# Phase 58.5: Code Review Report

**Reviewed:** 2026-07-02T00:00:00Z
**Depth:** standard
**Files Reviewed:** 21
**Status:** issues_found

## Summary

This standard-depth adversarial re-review of the Phase 58.5 cooperative unhook implementation verifies the fixes claimed in `58.5-REVIEW-FIX.md` and hunts for new defects introduced by those fixes or still latent in the current code.

The prior critical issue (`self_unload` freeing the DLL while active calls remain) is resolved: `self_unload` now returns `bool` and aborts when the drain times out. The prior warnings are also addressed: panic-safe reentrancy guard, bypass-correlator lifecycle cleanup, PID-reuse-safe evidence filenames, stale-evidence audit events, better `AgentShutdownUnhook` resource paths, and byte-length `UnhookAck.error` truncation.

However, the review found one new blocker and nine warnings. The blocker is in the watchdog self-unload path, which ignores the result of `UnhookAll()` and may still free the DLL image after hook restoration or active-call drain has failed. The warnings cover dropped lifecycle notifications, registry-eviction leaks, an unnecessarily writable classification-cache mapping, unvalidated evidence fields, API-signature hygiene, test isolation, and missing coverage for the watchdog path.

## Critical Issues

### CR-01: Watchdog self-unload ignores `UnhookAll()` result

**File:** `dlp-hook-dll/src/control_thread.rs:326-342`
**Issue:** When the control thread's watchdog fires, it calls `crate::UnhookAll()` (the FFI export at `lib.rs:803-806`) and discards the return value before proceeding to `crate::self_unload()`. `UnhookAll()` internally calls `unhook_all_internal()` and ignores its result, so the watchdog has no way to know whether IAT entries were restored, ntdll stubs were unpatched, active calls were drained, or shared-memory mappings were released. If `unhook_all_internal()` returns `false` because active calls could not drain or an IAT restore failed, the watchdog may still call `self_unload()`, which frees the DLL image. Threads still executing trampoline code or the host process's IAT still pointing into the freed mapping can then crash or fault.

This is the same use-after-free class as the prior CR-01, but it remains reachable on the agent-death path (watchdog), which is exactly the scenario where safe self-unload matters most.

**Fix:** Call `unhook_all_internal()` directly in the watchdog path and check its result. Only proceed to `self_unload()` when unhook succeeded. If it failed, log and break out of the loop so the DLL remains loaded but unhooked.

```rust
let unhook_ok = crate::unhook_all_internal();
if !unhook_ok {
    crate::debug_log(
        "[dlp-hook] watchdog: UnhookAll failed -- remaining loaded but unhooked\0",
    );
    break;
}

#[cfg(test)]
{
    WATCHDOG_TRIGGERED.store(true, Ordering::SeqCst);
    break;
}
#[cfg(not(test))]
unsafe {
    if !crate::self_unload() {
        crate::debug_log(
            "[dlp-hook] watchdog: self_unload aborted -- remaining loaded but unhooked\0",
        );
        break;
    }
}
```

## Warnings

### WR-01: Lifecycle notifications can be silently dropped under load

**File:** `dlp-agent/src/process_registry.rs:283-285`, `dlp-agent/src/process_registry.rs:307-309`
**Issue:** `record_exited` and `record_unhooked` notify the bypass correlator using `crossbeam_channel::Sender::try_send` on a bounded channel of capacity 1024 (`service.rs:1843-1844`). If the correlator's `spawn_blocking` lifecycle handler is slow or a process spawn storm fills the channel, `try_send` returns an error that is silently discarded with `let _ =`. The correlator then never calls `remove_pid`, leaking the `JournalReader` and `pending_journals` entry for that PID.

**Fix:** Handle the send failure. The least-invasive fix is to log a warning (or increment a metric) so operators can detect dropped notifications:

```rust
if let Some(ref tx) = self.lifecycle_tx {
    if let Err(e) = tx.try_send(key) {
        tracing::warn!(error = %e, pid = key.pid, "process lifecycle notification dropped");
    }
}
```

A stronger fix is to size the channel for peak churn or use an unbounded channel with backpressure monitoring, but that requires operational data.

### WR-02: Registry eviction can leak bypass-correlator resources

**File:** `dlp-agent/src/process_registry.rs:297-310`, `dlp-agent/src/process_registry.rs:165-206`
**Issue:** `record_unhooked` only sends a lifecycle notification when it finds an existing `Injected` entry and transitions it to `Exited`. If the registry has hit `MAX_REGISTRY_SIZE` (1000) and the entry was already evicted by `enforce_cap`, no notification is sent and `BypassCorrelator::remove_pid` is never called. The `JournalReader` and `pending_journals` metadata for that PID leak until the agent restarts.

**Fix:** Eviction of an `Injected` entry should also trigger lifecycle cleanup. In `enforce_cap`, when an `Injected` entry is selected as the victim, send its key on `lifecycle_tx` before removing it:

```rust
if let Some(ref tx) = self.lifecycle_tx {
    if matches!(entry.value().state, ProcessState::Injected { .. }) {
        let _ = tx.try_send(*entry.key());
    }
}
self.states.remove(&key);
```

### WR-03: Classification cache is mapped with write access

**File:** `dlp-hook-dll/src/classification_cache.rs:24`, `dlp-hook-dll/src/classification_cache.rs:428`, `dlp-hook-dll/src/classification_cache.rs:437`, `dlp-hook-dll/src/classification_cache.rs:450`
**Issue:** The classification cache is opened with `FILE_MAP_ALL_ACCESS` even though the hook DLL is purely a consumer of agent-produced cache data. The module's own security doc comment was changed from `FILE_MAP_READ only` to `FILE_MAP_ALL_ACCESS only` and now incorrectly states that "Windows MMU enforces write protection" — the opposite of what `FILE_MAP_ALL_ACCESS` does. Mapping the cache writable unnecessarily increases attack surface: a compromised or buggy DLL can corrupt the cache shared with other injected processes.

**Fix:** Open the classification cache read-only with `FILE_MAP_READ`, and correct the doc comment:

```rust
use windows::Win32::System::Memory::{MapViewOfFile, OpenFileMappingW, FILE_MAP_READ};

let handle = OpenFileMappingW(
    FILE_MAP_READ.0,
    false,
    windows::core::PCWSTR::from_raw(name_wide.as_ptr()),
)?;
let view = MapViewOfFile(handle, FILE_MAP_READ, 0, 0, 0)?;
```

### WR-04: Watchdog evidence `reason` field is not validated

**File:** `dlp-agent/src/service.rs:2447-2449`, `dlp-agent/src/service.rs:2497-2500`
**Issue:** The `reason` field from the deserialized `WatchdogEvidence` JSON is embedded directly into the audit event justification without validation against the known `UnhookReason` enum. The file size is capped at 64 KiB, but unexpected or attacker-controlled values (if the evidence directory is writable) still reach the audit log. The prior review flagged this as IN-03; it remains unfixed and has security/reliability implications because the justification is forwarded to SIEM.

**Fix:** Deserialize `reason` into the bounded `dlp_common::hook_ipc::UnhookReason` enum, or validate the string against an allowlist and fall back to `"unknown"`:

```rust
let reason = match evidence.reason.as_str() {
    "watchdog_timeout" => "watchdog_timeout",
    _ => "unknown",
};
```

### WR-05: `emit_unhook_audit` accepts any `EventType`

**File:** `dlp-agent/src/audit_emitter.rs:556-586`
**Issue:** The helper documents that `event_type` should be one of `AgentShutdownUnhook`, `UnhookFailure`, or `WatchdogSelfUnload`, but the signature accepts any `dlp_common::EventType`. A future caller can accidentally emit an unrelated event through this helper, breaking audit semantics. The prior review flagged this as IN-02; it remains unfixed.

**Fix:** Restrict the type with a small enum:

```rust
pub enum UnhookEventType {
    AgentShutdownUnhook,
    UnhookFailure,
    WatchdogSelfUnload,
}

pub fn emit_unhook_audit(
    ctx: &EmitContext,
    event_type: UnhookEventType,
    pid: u32,
    success: bool,
    error: Option<String>,
    resource_path: Option<String>,
) { ... }
```

### WR-06: Tests write watchdog evidence to a system-wide directory

**File:** `dlp-hook-dll/src/control_thread.rs:92-96`
**Issue:** Test builds use fixed paths under `C:\ProgramData\DLP\WatchdogSelfUnload_Test`. Parallel test runs, tests executed without elevation, or leftover files from previous runs can conflict or fail. The prior review flagged this as IN-01; it remains unfixed.

**Fix:** Make the evidence directory injectable for tests, or use a per-test temporary directory:

```rust
#[cfg(test)]
fn watchdog_evidence_dir() -> std::path::PathBuf {
    std::env::temp_dir().join("dlp-watchdog-test").join(std::process::id().to_string())
}
```

### WR-07: `self_unload` fallback cannot free the correct module

**File:** `dlp-hook-dll/src/lib.rs:931-940`
**Issue:** `self_unload` obtains the DLL instance from `DLL_INSTANCE`. If the mutex is poisoned or empty, it falls back to `GetModuleHandleW(None)`, which returns the host executable's module handle, not the DLL's. `FreeLibraryAndExitThread` with the EXE handle decrements the executable's load count (which is meaningless) and does not unload the DLL. The thread exits but the DLL image remains mapped. After a successful unhook this is safe, but it wastes memory and contradicts the function's contract.

**Fix:** If the DLL instance cannot be determined, return `false` rather than freeing the wrong module:

```rust
let instance = DLL_INSTANCE
    .lock()
    .ok()
    .and_then(|g| *g)
    .map(|raw| HINSTANCE(raw as *mut std::ffi::c_void));
let Some(instance) = instance else {
    crate::debug_log("[dlp-hook] self_unload: cannot determine DLL instance -- aborting\0");
    return false;
};
FreeLibraryAndExitThread(instance.into(), 0);
```

### WR-08: `AgentShutdownUnhook` audit emitted before `UNHOOK_ALL_REQUESTED` is set

**File:** `dlp-agent/src/service.rs:221-235`
**Issue:** `request_unhook_from_injected` emits the `AgentShutdownUnhook` audit event and then sets the `UNHOOK_ALL_REQUESTED` flag. If the agent crashes or is killed between these two steps, the audit log records that an unhook was requested, but no injected process ever received an `UnhookCommand`. This makes forensic correlation harder.

**Fix:** Set the flag before emitting the audit, or emit the event only after the flag is armed:

```rust
UNHOOK_ALL_REQUESTED.store(true, Ordering::Release);
crate::audit_emitter::emit_unhook_audit(
    audit_ctx,
    dlp_common::EventType::AgentShutdownUnhook,
    std::process::id(),
    true,
    Some(format!("injected_count={}; target_pids={}; budget_ms={}", ...)),
    Some(format!("agent://{}/unhook_request", std::process::id())),
);
```

### WR-09: No tests exercise the watchdog self-unload path

**File:** `dlp-hook-dll/src/control_thread.rs:481-590`, `dlp-hook-dll/src/control_thread.rs:592-630`
**Issue:** `run_control_loop_for_test` is provided to mock poll results and drive the watchdog or unhook-command paths, but no test in the module actually calls it. The existing tests only cover idempotent start/shutdown, evidence serialization, and process creation time. The most critical behavior — firing the watchdog after `MAX_FAILURES` consecutive failures and the grace window — is unverified by automated tests.

**Fix:** Add tests that use `run_control_loop_for_test` to verify:

```rust
#[test]
fn watchdog_fires_after_max_failures_and_grace_window() {
    let _guard = crate::PHASE_58_5_TEST_LOCK.lock();
    let failures = vec![Err(crate::pipe_client::PipeError::ConnectionRefused); 3];
    let (iters, triggered) = run_control_loop_for_test(
        failures,
        100, // short watchdog timeout for test
        10,
    );
    assert!(triggered, "watchdog should have fired");
    assert!(iters > 0);
}
```
