# Phase 58.5: Code Review Report

**Depth:** standard
**Files Reviewed:** 21

## Summary

Phase 58.5 implements cooperative self-unhook for the hook DLL and agent-side orchestration for graceful shutdown and watchdog-evidence reconciliation. The prior review's blockers around double registry initialization, ignored pipe timeouts, and hard-coded audit contexts have been addressed, and the new tests cover the PollControl/UnhookAck round-trip and watchdog reconciliation paths. However, a standard-depth adversarial review still found one handle-lifecycle blocker, several correctness and maintainability warnings in the hook DLL lifecycle and UAT scripts, and two info-level items.

## Critical Issues

### CR-01: Control-thread shutdown event handle is used after close

**Classification:** BLOCKER
**File:** `dlp-hook-dll/src/control_thread.rs:193-210`
**Issue:** `shutdown_control_thread` copies the `shutdown_event` handle out of the running `ControlThread`, sets the global state back to `NotStarted` (which drops the `ControlThread` and invokes `Drop::drop`, closing the handle), and then calls `SetEvent(event)` on the copied handle value. After `Drop` closes the handle, the copied value is stale. Calling `SetEvent` on a closed handle is undefined behavior in the Windows API; in practice it fails with `ERROR_INVALID_HANDLE`, so the shutdown signal is never delivered.

The control thread still exits on its next 1-second poll because `CONTROL_THREAD_STOPPING` is set, but the handle lifecycle is incorrect and the join may be delayed or, in a reused-handle scenario, could signal an unrelated object.

**Fix:** Set the event before dropping the `ControlThread`, or keep the `ControlThread` alive until after `SetEvent`. For example, move the `SetEvent` call before the `*guard = ControlThreadState::NotStarted` assignment, then drop the guard explicitly after the thread has been joined.

```rust
let (event, handle) = {
    let mut guard = CONTROL_THREAD_STATE.lock().unwrap_or_else(|e| e.into_inner());
    match &mut *guard {
        ControlThreadState::Running(ct) => {
            let event = ct.shutdown_event;
            let handle = ct.thread_handle.take();
            // Signal the event BEFORE the ControlThread is dropped.
            let _ = unsafe { SetEvent(event) };
            *guard = ControlThreadState::NotStarted;
            (event, handle)
        }
        ControlThreadState::NotStarted | ControlThreadState::Starting => {
            *guard = ControlThreadState::NotStarted;
            CONTROL_THREAD_STOPPING.store(false, Ordering::SeqCst);
            return;
        }
    }
};

if let Some(handle) = handle {
    let _ = handle.join();
}
CONTROL_THREAD_STOPPING.store(false, Ordering::SeqCst);
```

## Warnings

### WR-01: `start_control_thread` / `shutdown_control_thread` race leaks the control thread

**Classification:** WARNING
**File:** `dlp-hook-dll/src/control_thread.rs:142-176` and `dlp-hook-dll/src/control_thread.rs:199-204`
**Issue:** `start_control_thread` sets the state to `Starting` and releases the mutex while it creates the event and spawns the thread. If `shutdown_control_thread` is called during this window, it sees `Starting`, resets the state to `NotStarted`, resets `CONTROL_THREAD_STOPPING` to `false`, and returns without signaling. The newly spawned thread then transitions to `Running` and runs indefinitely because the shutdown signal was suppressed.

**Fix:** Keep the mutex held across the entire start sequence, or make shutdown wait for the `Starting` state to resolve before acting. The simplest fix is to spawn the thread while still holding the mutex and only set `Running` before releasing it.

### WR-02: `AgentShutdownUnhook` audit event reports the agent PID, not the target processes

**Classification:** WARNING
**File:** `dlp-agent/src/service.rs:191-197`
**Issue:** `request_unhook_from_injected` emits the `AgentShutdownUnhook` event with `pid = std::process::id()`, which is the agent's own PID. `emit_unhook_audit` then builds `resource_path = format!("pid={pid}")`, so the audit log records an event that looks like the agent itself was unhooked. The `injected_count` metadata is in `justification`, but the primary resource identifier is misleading for SIEM correlation.

**Fix:** Use a sentinel resource path such as `"agent://<agent_pid>/unhook_request"` and include the target PID list (or count) in the justification, or change `emit_unhook_audit` to accept an explicit resource path for this event type.

### WR-03: Watchdog evidence reconciliation runs before the process registry is populated

**Classification:** WARNING
**File:** `dlp-agent/src/service.rs:2182-2183`
**Issue:** `reconcile_watchdog_evidence` is called once during `run_loop_init`, immediately after the enforcement subsystems start but before the ETW/process watcher has had time to populate the registry. Evidence files from processes that are still running may be emitted as untracked and retained until the 7-day retention window expires, even though the processes will be re-discovered moments later. This creates audit records showing "untracked" self-unloads for processes that are actually under management.

**Fix:** Delay reconciliation until after the process watcher has completed an initial scan, or run reconciliation periodically during steady state so that late-discovered processes can be matched against retained evidence.

### WR-04: Default audit context hard-codes SYSTEM identity without querying the token

**Classification:** WARNING
**File:** `dlp-agent/src/service.rs:3768-3783`
**Issue:** `resolve_service_identity` is a placeholder that unconditionally returns `("S-1-5-18", 0)`. While the session was corrected from the previous review's hard-coded `1` to `0`, the function still does not query the current process token's SID or session. If the agent runs as a managed service account or in a different session, audit events will be mis-tagged.

**Fix:** Implement `resolve_service_identity` by opening the current process token with `OpenProcessToken`, querying `TokenUser` and `TokenSessionId`, and only falling back to `("S-1-5-18", 0)` when those queries fail.

### WR-05: `read_exact_with_timeout` ignores `CancelIoEx` result, risking use-after-free on timeout

**Classification:** WARNING
**File:** `dlp-hook-dll/src/pipe_client.rs:506-514`
**Issue:** On timeout, the function calls `CancelIoEx` to cancel the pending overlapped read, waits up to one second for the operation to complete, closes the event handle, and returns `PipeError::Timeout`. The return value of `CancelIoEx` is discarded. If `CancelIoEx` fails with an error other than `ERROR_NOT_FOUND` and the overlapped I/O is still pending, the I/O may complete after the function returns and write into the caller's buffer. When the caller drops the buffer, a use-after-free can occur.

**Fix:** Check the result of `CancelIoEx`. If it fails unexpectedly, wait longer or leave the event handle valid until the operation is known to have completed. Alternatively, keep the event handle alive for the lifetime of the pipe connection and reuse it across reads.

### WR-06: UAT script crashes on empty `Read-Host` input

**Classification:** WARNING
**File:** `scripts/Uat-Execute-v0.10.0.ps1:284-287`
**Issue:** `Prompt-ScenarioResult` calls `$resp.Substring(0, 1).ToUpper()` before validating that `$resp` is non-empty. If the operator presses Enter without typing anything, `Substring(0, 1)` throws `System.ArgumentOutOfRangeException` and the script terminates because `$ErrorActionPreference = 'Stop'`.

**Fix:** Validate the input length before substringing, or default empty input to 'N-A'.

```powershell
do {
    $resp = Read-Host "Enter result [P]ass / [F]ail / [N]-A (or type notes after space)"
    $result = if ($resp.Length -gt 0) { $resp.Substring(0, 1).ToUpper() } else { '' }
} while ($result -notin @('P', 'F', 'N'))
```

### WR-07: CRIT-04 benchmark reports PASS when all baseline runs fail

**Classification:** WARNING
**File:** `scripts/Uat-Execute-v0.10.0.ps1:467-472` and `scripts/Uat-Execute-v0.10.0.ps1:532-537`
**Issue:** Both the cargo-build and Word-launch benchmarks compute `$overhead = 0` and `$passed = $true` when `$baselineMedian -eq 0`. A median of zero occurs when every baseline run failed (no successful times were added to `$baselineTimes`). In that case the script reports PASS even though no valid benchmark data was collected.

**Fix:** Treat `$baselineMedian -eq 0` as a failure and set `$passed = $false` when there are no successful baseline or hooked runs.

```powershell
$passed = ($baselineMedian -gt 0) -and ($hookedMedian -gt 0) -and ($overhead -le 25)
```

## Info

### IN-01: `GENESIS_HASH` constant does not match the documented SHA-256 value

**Classification:** INFO
**File:** `dlp-common/src/audit.rs:30-33`
**Issue:** The doc comment states `GENESIS_HASH = hex(sha256("DLP-AUDIT-CHAIN-v1-GENESIS"))`, but the constant value is a 64-character placeholder that does not equal the real digest produced by `genesis_hash()`. Because `GENESIS_HASH` is a public constant, any downstream code that uses it instead of the function will produce chain-verification failures. The constant is not currently referenced elsewhere in the codebase.

**Fix:** Either remove the constant and direct callers to `genesis_hash()`, or replace the constant with the actual computed digest.
