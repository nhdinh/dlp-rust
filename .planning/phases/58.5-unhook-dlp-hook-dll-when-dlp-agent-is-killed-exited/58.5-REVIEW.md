# Phase 58.5: Code Review Report

**Reviewed:** 2026-07-01T00:00:00Z
**Depth:** standard
**Files Reviewed:** 21
**Status:** issues_found

## Summary

Phase 58.5 implements cooperative self-unhook for the hook DLL and agent-side orchestration for graceful shutdown and watchdog-evidence reconciliation. The prior review's blockers around double registry initialization, ignored pipe timeouts, and hard-coded audit contexts have been addressed, and the new tests cover the `PollControl`/`UnhookAck` round-trip and watchdog reconciliation paths.

A standard-depth adversarial review still found **two critical issues** that must be fixed before shipping: a unit mismatch in the PID-reuse-safe process key that prevents correct unhook acknowledgment matching, and a permissive named-pipe DACL that allows any authenticated user to spoof unhook acknowledgments. There are also **nine warnings** covering lifecycle races, audit correctness, timeout arithmetic, and cleanup gaps, plus **four info-level items**.

## Critical Issues

### CR-01: `creation_time` unit mismatch breaks PID-reuse-safe unhook matching

**Classification:** BLOCKER
**File:** `dlp-hook-dll/src/control_thread.rs:382-401` and `dlp-agent/src/hook_ipc.rs:543-613`
**Issue:** `process_creation_time()` in the hook DLL converts the process creation `FILETIME` to **Unix seconds** before sending it in `PollControl` and `UnhookAck`. However, the agent side stores the registry `ProcessKey.creation_time` as the raw `FILETIME` value (100-ns intervals since 1601) obtained from the process watcher and uses it directly for equality comparisons when routing `UnhookAck` to the correct registry entry. The two values are in different units and will never match, so every `UnhookAck` from a real hook DLL will fail the key lookup and fall through to the untracked/failure path.

This silently defeats the cooperative unhook protocol: the agent will never observe successful unhooks from injected processes, will emit `UnhookFailure` audit events for successful operations, and the 5-second shutdown wait budget will expire with every process still listed as injected.

**Fix:** Use the same representation on both sides. The simplest fix is to make the hook DLL send the raw `FILETIME` value instead of converting to Unix seconds, and keep the existing agent-side logic unchanged. Update the misleading doc comments in `dlp-common/src/hook_ipc.rs` that describe `creation_time` as "FILETIME low + high parts" or "Unix timestamp" inconsistently.

```rust
fn process_creation_time() -> Option<u64> {
    unsafe {
        let mut creation: i64 = 0;
        // ... call GetProcessTimes as before ...
        if result.is_err() {
            return None;
        }
        // Return raw FILETIME so it matches the agent registry key.
        Some(creation as u64)
    }
}
```

### CR-02: Pipe DACL allows any authenticated user to spoof `UnhookAck`

**Classification:** BLOCKER
**File:** `dlp-agent/src/ipc/pipe_security.rs:1-25` and `dlp-agent/src/hook_ipc.rs:543-613`
**Issue:** `PIPE_SDDL = "D:(A;;GRGW;;;AU)(A;;GA;;;SY)(A;;GA;;;BA)"` grants Generic Read + Generic Write to **Authenticated Users**. `UnhookAck` messages are accepted from any client that can open the pipe, and the agent transitions the target process registry entry to `Exited` based solely on the `(pid, creation_time)` tuple in the ack. A low-privilege process running as any authenticated user can therefore craft an `UnhookAck` for a process it does not own, causing the agent to believe a high-integrity or privileged target has been unhooked and to stop enforcing policy on it.

**Fix:** Restrict pipe creation/connection to the same integrity level or service SID as the agent, or cryptographically authenticate `UnhookAck` payloads. At minimum, replace the `AU` ACE with an ACE that grants access only to the agent's own service SID or to processes running at the same integrity level, and validate the caller's token/SID on the server side before acting on an ack.

```rust
// Example: restrict to the service SID and local system/administrators only.
const PIPE_SDDL: &str = "D:(A;;GA;;;SY)(A;;GA;;;BA)";
```

## Warnings

### WR-01: Duration underflow panic in `wait_for_unhook_acks`

**Classification:** WARNING
**File:** `dlp-agent/src/service.rs:4070-4085`
**Issue:** The shutdown helper computes `budget - elapsed` without guarding against the case where `elapsed > budget`. If the loop iteration is delayed by async scheduling or a slow registry lock acquisition, `budget - elapsed` will panic in debug builds or produce a `Duration` overflow panic in release.

**Fix:** Use `saturating_sub` or explicit comparison before subtraction.

```rust
let elapsed = start.elapsed();
if elapsed >= budget {
    return registry.iter_injected().len();
}
let sleep_for = UNHOOK_POLL_INTERVAL.min(budget - elapsed);
tokio::time::sleep(sleep_for).await;
```

### WR-02: Race between watchdog timeout and `UnhookFailure` emission

**Classification:** WARNING
**File:** `dlp-agent/src/hook_ipc.rs:580-613` and `dlp-agent/src/service.rs:4070-4085`
**Issue:** When the agent shutdown budget expires, `wait_for_unhook_acks` returns the count of remaining injected processes but does not itself emit `UnhookFailure` audit events. The failures are only emitted later when `UnhookAck` messages arrive with `success: false` or when stale entries are garbage-collected. If the agent exits immediately after the budget expires, there is no persistent record of which processes failed to unhook during shutdown.

**Fix:** On budget exhaustion, iterate the remaining injected processes and emit one `UnhookFailure` event per process (or a single batched event with the PID list) before returning from the shutdown path.

### WR-03: Matched 5-second budgets cause false unhook failures

**Classification:** WARNING
**File:** `dlp-agent/src/service.rs:4065-4085`
**Issue:** Both the agent shutdown `UNHOOK_WAIT_BUDGET` (5 s) and the hook DLL watchdog `WATCHDOG_TIMEOUT_MS` (30 s) are measured from different starting points, but the shutdown helper only polls every 100 ms. If a slow process takes just over 5 s to drain active calls and acknowledge, the agent gives up and reports failure, even though the DLL is still actively unhooking. There is no reconciliation after agent restart for graceful-shutdown failures.

**Fix:** Increase the shutdown budget, make it configurable via the agent config, or persist pending unhook requests so the next agent instance can reconcile late acks against the registry.

### WR-04: Hook DLL self-unloads even when `UnhookAck` reports failure

**Classification:** WARNING
**File:** `dlp-hook-dll/src/control_thread.rs:288-320`
**Issue:** `handle_unhook_command` sends the `UnhookAck` with `success: unhook_ok` and then unconditionally calls `self_unload()` (non-test builds). If `unhook_all_internal` returned `false` because hooks could not be safely restored or active calls could not drain, the DLL still unloads, leaving the host process with partially restored or unmonitored IAT entries. The agent receives `success: false` and cannot distinguish "unloaded with broken hooks" from "still hooked and responsive".

**Fix:** Only call `self_unload()` when `unhook_ok` is true. When unhook fails, remain loaded and continue the control loop so the agent can retry or escalate.

```rust
if unhook_ok {
    #[cfg(not(test))]
    unsafe { crate::self_unload(); }
}
```

### WR-05: `FreeLibraryAndExitThread` race with active hook calls

**Classification:** WARNING
**File:** `dlp-hook-dll/src/lib.rs` (self_unload) and `dlp-hook-dll/src/trampolines.rs`
**Issue:** `self_unload` calls `FreeLibraryAndExitThread`, which frees the DLL image and terminates the calling thread. Other threads that entered hooked APIs before the shutdown flag was raised may still be executing trampoline code inside the DLL image. Removing the image while those threads are mid-call is a use-after-free risk.

**Fix:** Ensure the active-call counter reaches zero and stays zero before freeing the library. The current `unhook_all_internal` drains calls but does not guarantee no new calls enter after the drain completes. Hold the shutdown state across the final self-unload or use a two-phase teardown: drain, unhook, then wait for the active-call counter to reach zero again before calling `FreeLibraryAndExitThread`.

### WR-06: Bypass correlator is not notified when processes unhook

**Classification:** WARNING
**File:** `dlp-agent/src/bypass_correlator.rs` and `dlp-agent/src/hook_ipc.rs:580-613`
**Issue:** `bypass_correlator` maintains a `DashMap<u32, JournalReader>` keyed by PID. When a process transitions to `Exited` after unhook, no cleanup hook removes its reader. Over long agent uptime, leaked `JournalReader` entries accumulate for every unhooked or exited process, wasting memory and keeping file handles open.

**Fix:** Add a registry observer or explicit call from `record_unhooked`/`record_process_exited` to remove the corresponding `JournalReader` from the bypass correlator.

### WR-07: `UnhookAck.error` string is forwarded to audit logs without validation

**Classification:** WARNING
**File:** `dlp-agent/src/hook_ipc.rs:580-613` and `dlp-agent/src/audit_emitter.rs`
**Issue:** The `error` field of `UnhookAck` is a free-form `String` from the hook DLL. It is included in audit events without length limits, character filtering, or sanitization. A compromised or malicious hook DLL could emit a very large string or inject control characters into the audit stream.

**Fix:** Validate or truncate the `error` string before emitting. Reject non-UTF-8 or over-length values, and limit the field to a reasonable size (e.g., 256 characters) in the audit event.

### WR-08: Unhook audit events are emitted after the audit flush task has been stopped

**Classification:** WARNING
**File:** `dlp-agent/src/service.rs:4079-4090`
**Issue:** The shutdown sequence stops the audit buffer flush task before calling `request_unhook_from_injected`. Any `AgentShutdownUnhook`, `UnhookFailure`, or `WatchdogSelfUnload` events generated during the unhook handshake are queued in memory but may never be flushed if the process exits immediately after the unhook budget expires.

**Fix:** Perform the unhook handshake and emit all related audit events before stopping the flush task, or ensure a final synchronous flush runs after unhook handling completes.

### WR-09: Watchdog timer truncation on 32-bit targets

**Classification:** WARNING
**File:** `dlp-hook-dll/src/control_thread.rs:267`
**Issue:** `last_agent_response.elapsed().as_millis() as u64` truncates the elapsed duration to milliseconds and converts from `u128`. On 32-bit Windows targets, `as_millis()` returns `u128`, but the cast pipeline is unnecessarily wide and the `ControlPollIntervalMs` constant is `u32`. More importantly, `last_agent_response.elapsed().as_millis() as u64` is fine on 64-bit, but the comparison `>= watchdog_timeout_ms()` only checks at poll granularity (1 s), so the actual watchdog firing can be delayed by up to one poll interval.

**Fix:** Use a finer-grained wait that combines the shutdown event and a deadline, rather than polling once per second. If polling must remain, document and test the worst-case delay.

## Info

### IN-01: `request_unhook_from_injected` holds an unnecessary `Arc` around the registry

**Classification:** INFO
**File:** `dlp-agent/src/service.rs:191-197`
**Issue:** `request_unhook_from_injected` takes `registry: Arc<ProcessRegistry>` but only uses it through immutable borrow. Changing the signature to `&ProcessRegistry` removes an allocation/cloning requirement and makes the function easier to test.

**Fix:**

```rust
async fn request_unhook_from_injected(registry: &ProcessRegistry) { ... }
```

### IN-02: `AgentShutdownUnhook` audit event uses the agent PID as the resource identifier

**Classification:** INFO
**File:** `dlp-agent/src/service.rs:191-197`
**Issue:** `request_unhook_from_injected` emits the `AgentShutdownUnhook` event with `pid = std::process::id()`, which is the agent's own PID. The resulting `resource_path = "pid=<agent_pid>"` implies the agent itself was unhooked. Although `injected_count` appears in `justification`, the primary resource identifier is misleading.

**Fix:** Use a sentinel resource path such as `"agent://<agent_pid>/unhook_request"` and include the target PID list (or count) in the justification, or change `emit_unhook_audit` to accept an explicit resource path for this event type.

### IN-03: Watchdog evidence files are deleted silently after successful reconciliation

**Classification:** INFO
**File:** `dlp-agent/src/service.rs` (`reconcile_watchdog_evidence`)
**Issue:** Evidence files are removed after reconciliation without an explicit audit event. If the files are deleted by another process or by a bug in the reconciliation logic, there is no durable record that a self-unload occurred.

**Fix:** Emit an audit event confirming reconciliation and retention/deletion of each evidence file, even when the matching process is found.

### IN-04: Tests write watchdog evidence to `ProgramData`

**Classification:** INFO
**File:** `dlp-hook-dll/src/control_thread.rs:86-90`
**Issue:** The test build uses `C:\ProgramData\DLP\WatchdogSelfUnload_Test`, a system-wide directory. Parallel test runs or tests run without elevation may conflict or fail to create the directory.

**Fix:** Use a per-test temporary directory (e.g., `std::env::temp_dir()` plus a unique subdirectory) for test evidence, or inject the evidence path as a test-only parameter.
