<objective>
Close Gap 2 from Phase 58.5 UAT: when the agent stops, every process injected with `dlp_hook_dll.dll` receives an `UnhookCommand` and can self-unhook, including idle processes that never call a hooked API. The root causes are (a) agent sweeps register processes with `creation_time: 0` while the DLL sends the real process creation time, breaking `ProcessKey` matching, and (b) the control-poll thread is started lazily on first hook call, so idle processes never poll.
</objective>

  <files>dlp-agent/src/service.rs, dlp-agent/src/process_registry.rs</files>
  <action>
    Add a Windows helper `get_process_creation_time(pid: u32) -> Option<u64>` in `dlp-agent/src/service.rs` that opens the target process with `PROCESS_QUERY_LIMITED_INFORMATION`, calls `GetProcessTimes`, and returns the creation `FILETIME` converted to the same 100-ns epoch used by the hook DLL's `control_thread::process_creation_time()`.

    Update `startup_sweep` and `backstop_sweep` to call `get_process_creation_time(pid)` and store the returned value in the `ProcessKey { pid, creation_time }` instead of `creation_time: 0`. If creation time cannot be queried, fall back to `creation_time: 0` and log a warning so the existing PID-only behavior degrades gracefully.

    Add unit tests in `dlp-agent/src/service.rs` (or a new `service_tests.rs` if the file is too large) that:
    - Verify `get_process_creation_time` returns the same value for the current process as `std::process::id()` queried via the same API.
    - Verify `ProcessKey` recorded by `startup_sweep`/`backstop_sweep` carries a non-zero creation time for an injectable test process.

    Ensure non-Windows builds continue to compile via `#[cfg(windows)]` guards.
  </action>

  </verify>
  <done>Agent sweeps record the real process creation time in `ProcessKey`, and the helper has unit-test coverage.</done>

    Add a unit test in `dlp-hook-dll/src/lib.rs` that loads the DLL symbol locally (via `GetProcAddress` after `LoadLibraryW` in the test) and verifies it returns 0 and that the control thread state transitions to running. Use `PHASE_58_5_TEST_LOCK` and reset helpers from Plan 58.5-05.

<task type="auto">
  <name>Task 3: Call the control-thread export after remote LoadLibraryW injection</name>
  <files>dlp-agent/src/hook_injector.rs, dlp-agent/src/service.rs, dlp-agent/tests/hook_ipc_integration.rs</files>
  <action>
    Extend `HookInjector::inject_into_process` in `dlp-agent/src/hook_injector.rs` so that after the remote `LoadLibraryW` thread succeeds (exit_code != 0), it:
    1. Records the remote module base address from the `LoadLibraryW` exit code.
    2. Loads the same DLL locally via `LoadLibraryW` and resolves `StartDlpControlThread` with `GetProcAddress`.
    3. Computes the export RVA by subtracting the local module base from the local export address.
    4. Creates a second remote thread whose start address is `remote_module_base + export_rva`.
    5. Waits up to 10 seconds for the second thread and validates its exit code is 0; if it fails, log a warning but do NOT fail the overall injection (the DLL is still loaded; it will lazily start on first hook call as before).

    Add defensive checks: ensure local `LoadLibraryW` succeeds, `GetProcAddress` returns non-null, and the computed remote address is not null before creating the second thread. Add unit tests for the RVA computation logic using a mock/local DLL. Add an integration test in `dlp-agent/tests/hook_ipc_integration.rs` that injects a child process and verifies the agent receives a `PollControl` frame with the correct `creation_time` even when the child does not call any hooked API.

    Update `dlp-agent/src/service.rs` startup/backstop sweeps if any injection-result logging needs to reflect the new "thread started" status.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent -> injected process | The agent writes remote memory and creates remote threads; this is a high-privilege boundary. |
| injected process -> agent named pipe | `PollControl` frames cross from an injected user process to the agent service. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-58.5-06-01 | Elevation of Privilege | `HookInjector` remote thread creation | accept | Injection already requires `PROCESS_ALL_ACCESS`; this plan reuses the same privilege boundary. |
| T-58.5-06-02 | Tampering | Remote export address computation | mitigate | Compute RVA from local module and add to remote base; validate addresses are non-null before thread creation; log warnings on failure. |
| T-58.5-06-03 | Denial of Service | Control-thread export call failure blocking injection | mitigate | Export-start failure is logged but does not fail injection; lazy start remains as fallback. |
| T-58.5-06-04 | Information Disclosure | `PollControl` carries process creation time | accept | `creation_time` is already sent by the DLL; matching it exactly in the registry is a security improvement (PID-reuse safety). |
| T-58.5-06-SC | Tampering | cargo/pip installs | accept | No new package installs in this plan. |
</threat_model>
