# Phase 58.5: Unhook dlp_hook_dll.dll when dlp-agent is killed/exited - Research

**Researched:** 2026-06-29
**Domain:** Windows user-mode DLP hook DLL lifecycle management, DLL injection/uninjection, IAT/ntdll trampoline restoration
**Confidence:** HIGH

## Summary

This phase ensures the DLP agent cleanly unhooks `dlp_hook_dll.dll` from all injected processes when the agent service is killed, exits, or restarts. The goal is to restore original IAT/ntdll trampolines and release shared-memory resources without crashing host processes.

The codebase already contains the core primitives for this work: `UnhookAll()` in `dlp-hook-dll/src/lib.rs` restores IAT entries, and `NtdllPatcher::unpatch_all_stubs()` in `ntdll_patcher.rs` disables retour detours. However, these are currently only invoked on `DLL_PROCESS_DETACH` (which fires when a process exits naturally), not on agent-driven unhook. The agent tracks injected PIDs via `ProcessRegistry` but has no mechanism to send an unhook command or trigger self-unload in target processes.

The primary challenge is that Windows provides no clean "uninject DLL" API. The standard approaches are: (1) `CreateRemoteThread` + `FreeLibrary` (risky, may crash if hooks are active), (2) a cooperative IPC command telling the hook DLL to self-unhook and then `FreeLibraryAndExitThread`, or (3) process termination. We must use approach (2) for safety.

**Primary recommendation:** Implement a cooperative unhook protocol: agent sends `UnhookCommand` via named pipe, hook DLL calls `UnhookAll()` + `unpatch_all_stubs()`, releases shared memory, then self-unloads via `FreeLibraryAndExitThread`. For crash/unexpected termination, add a per-process watchdog thread in the hook DLL that polls pipe connectivity and self-unloads on agent absence.

### Pattern 1: Cooperative Unhook Protocol
**What:** Agent sends a command frame over the existing named pipe; hook DLL performs self-restoration and self-unload.
**When to use:** All agent-driven shutdown scenarios (graceful stop, service restart, upgrade).
**Example:**
```rust
// In dlp-common/src/hook_ipc.rs
#[derive(Serialize, Deserialize, Debug, Clone)]
pub struct UnhookCommand {
    pub reason: UnhookReason, // GracefulShutdown, AgentCrashDetected, etc.
    pub timestamp_secs: u64,
}

#[derive(Serialize, Deserialize, Debug, Clone)]
pub struct UnhookAck {
    pub pid: u32,
    pub success: bool,
    pub error: Option<String>,
}
```

### Pattern 2: Watchdog Self-Unload
**What:** A background thread in the hook DLL polls pipe connectivity every N seconds; if the pipe is unreachable for M consecutive attempts, the DLL self-unhooks.
**When to use:** Agent crash, unexpected termination, or power loss scenarios where the agent cannot send UnhookCommand.
**Example:**
```rust
// In dlp-hook-dll/src/background_thread.rs (or new watchdog.rs)
fn spawn_watchdog_thread(pipe_name: &'static str, timeout_ms: u64) {
    std::thread::spawn(move || {
        let mut failures = 0u32;
        const MAX_FAILURES: u32 = 3;
        loop {
            std::thread::sleep(Duration::from_millis(timeout_ms));
            if pipe_is_reachable(pipe_name) {
                failures = 0;
                continue;
            }
            failures += 1;
            if failures >= MAX_FAILURES {
                // Agent is gone — self-unhook
                crate::debug_log("[dlp-hook] watchdog: agent unreachable — self-unhooking\0");
                UnhookAll();
                // Unmap shared memory
                // FreeLibraryAndExitThread
                self_unload();
                return; // unreachable
            }
        }
    });
}
```

### Anti-Patterns to Avoid
- **Do NOT use `CreateRemoteThread` + `FreeLibrary` directly without cooperative unhook first.** This leaves IAT entries pointing to freed trampoline memory, causing immediate crashes on the next file I/O call.
- **Do NOT unhook from `DllMain` during `DLL_PROCESS_DETACH` if the process is terminating.** Windows calls `DllMain` with `DLL_PROCESS_DETACH` during process exit; unhooking is unnecessary but harmless. The real problem is agent-driven unhook while the process continues running.
- **Do NOT forget to disable retour detours before freeing the DLL.** The detour trampoline memory lives inside the DLL's code section; if the DLL is freed while a detour is still active, any thread entering the ntdll stub will jump to freed memory.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| IAT restoration | Custom byte-patching logic | `restore_iat()` in `pe_utils.rs` | Already implemented, tested, and handles VirtualProtect correctly |
| ntdll detour disable | Manual 5-byte JMP restoration | `retour::RawDetour::disable()` | retour handles the exact bytes saved at creation time; manual restoration risks tearing on multi-core systems |
| Shared memory unmapping | Raw `NtUnmapViewOfSection` | `UnmapViewOfFile` from `windows` crate | Standard, well-tested, handles all edge cases |
| Self-unload | `ExitThread` + hope | `FreeLibraryAndExitThread` | Official Windows API that decrements the DLL ref count and exits the calling thread atomically |

**Key insight:** The hardest part of this phase is not the unhooking itself (the primitives exist) but the *coordination* between agent and hook DLL across process boundaries. The cooperative protocol must be robust to pipe failures, partial unhooks, and concurrent file I/O during the unhook window.

## Common Pitfalls

### Pitfall 1: Unhooking While File I/O Is In Progress
**What goes wrong:** A thread in the target process enters a hooked function (e.g., `CreateFileW`) just as the hook DLL is restoring the IAT entry. The thread executes the trampoline, which may be freed before it returns.
**Why it happens:** Race between the unhook thread and application threads.
**How to avoid:** Use a reentrancy guard (already exists: `crash_guard::with_reentrancy_guard`). Before unhooking, set a global "shutting down" flag that causes all trampolines to immediately pass through to the original function without doing any work. Wait a short grace period (e.g., 50ms) for in-flight calls to complete, then restore patches.
**Warning signs:** Crash dumps in target processes with `EXCEPTION_ACCESS_VIOLATION` at addresses inside `dlp_hook_dll.dll` after agent shutdown.

### Pitfall 2: Retour Detour Not Disabled Before DLL Unload
**What goes wrong:** The ntdll stub still contains a JMP to the detour trampoline, which lives in the DLL's `.text` section. When the DLL is freed, the JMP target becomes invalid.
**Why it happens:** `NtdllPatcher::unpatch_all_stubs()` is not called from `UnhookAll()` in the current code.
**How to avoid:** Ensure `UnhookAll()` calls `NTDLL_PATCHER.get().map(|m| m.lock().unpatch_all_stubs())` before returning. Verify with a test that all 4 stubs are in `Unpatched` state after unhook.
**Warning signs:** Random crashes in `ntdll.dll` during agent shutdown, especially in processes that continue running (e.g., Explorer, sync clients).

### Pitfall 3: Watchdog False Positives
**What goes wrong:** The watchdog thread detects a temporary pipe disconnection (e.g., agent busy, pipe instance exhausted) and self-unhooks prematurely.
**Why it happens:** Aggressive timeout thresholds or single-failure-triggered unhook.
**How to avoid:** Require N consecutive failures (e.g., 3) with a backoff delay. Use a heartbeat frame (e.g., `HealthPing` / `HealthPong`) rather than just testing pipe existence, to distinguish "agent alive but busy" from "agent dead".
**Warning signs:** Hook DLLs spontaneously unload in healthy systems; audit events show `watchdog_self_unload` without corresponding agent crash.

### Pitfall 4: Shared Memory Leak After Self-Unload
**What goes wrong:** The hook DLL unmaps its journal but the `Global\DlpHookJournal_<pid>` section object persists because the agent may still hold a handle to it.
**Why it happens:** Windows keeps the section object alive as long as any handle to it is open.
**How to avoid:** The agent should close its `OpenFileMapping` handle to the journal after detecting process exit or unhook. The hook DLL only needs to unmap its view; the section object will be destroyed when the last handle closes.
**Warning signs:** `Global\DlpHookJournal_*` objects accumulate in the Global namespace (visible via WinObj or Process Explorer).

## Code Examples

### Verified Pattern: Cooperative Unhook Flow
```rust
// dlp-agent/src/service.rs — added to run_loop_shutdown
async fn unhook_all_injected_processes(registry: &ProcessRegistry) {
    for entry in registry.states.iter() {
        if let ProcessState::Injected { .. } = &entry.value().state {
            let pid = entry.key().pid;
            let pipe_name = format!(r"\\.\pipe\DlpHookPipe_{}", pid);
            // Send UnhookCommand via existing pipe_client or custom helper
            if let Err(e) = send_unhook_command(pid, &pipe_name).await {
                warn!(pid, error = %e, "unhook command failed — process may retain hooks");
            }
        }
    }
}
```

### Verified Pattern: Hook DLL Self-Unload
```rust
// dlp-hook-dll/src/lib.rs
#[unsafe(no_mangle)]
pub extern "system" fn UnhookAll() {
    debug_log("[dlp-hook] UnhookAll called — restoring IAT and ntdll stubs\0");
    unsafe {
        for hook in HOOKS.iter() {
            let iat_opt = *(hook.iat_ptr as *const Option<*mut usize>);
            let orig_opt = *(hook.original_ptr as *const Option<usize>);
            if let (Some(iat), Some(orig)) = (iat_opt, orig_opt) {
                let _ = restore_iat(iat, orig);
            }
        }
    }
    // Phase 58.5: Disable ntdll detours before potential DLL unload.
    if let Some(patcher) = NTDLL_PATCHER.get() {
        if let Ok(mut guard) = patcher.lock() {
            guard.unpatch_all_stubs();
        }
    }
    // Release shared memory mappings.
    crate::hook_journal::unmap_journal();
    crate::classification_cache::unmap_cache();
}

fn self_unload() {
    unsafe {
        let module = GetModuleHandleW(w!("dlp_hook_dll.dll")).unwrap_or_default();
        if !module.is_invalid() {
            FreeLibraryAndExitThread(module, 0);
        }
    }
}
```

## Assumptions Log

| # | Claim | Section | Risk if Wrong |
|---|-------|---------|---------------|
| A1 | `FreeLibraryAndExitThread` is safe to call from a thread created inside the hook DLL | Standard Stack | If the thread is not the one that loaded the DLL, the ref count may not drop to zero; but `FreeLibraryAndExitThread` always decrements the ref count of the specified module regardless of calling thread |
| A2 | `retour::RawDetour::disable()` is safe to call from any thread, not just the one that created it | Standard Stack | retour's documentation states detours are process-global; disable should work from any thread. If wrong, we may need to marshal the disable call to the original thread |
| A3 | The named pipe `\\.\pipe\DlpHookPipe` is accessible from the agent to each injected process for sending UnhookCommand | Architecture Patterns | If the pipe is not available (e.g., process running as different user with no cross-session pipe access), the agent must fall back to `CreateRemoteThread` + `FreeLibraryAndExitThread` directly, which is riskier |

## Open Questions

1. **Should the watchdog use a dedicated per-process pipe or the existing `DlpHookPipe`?**
   - What we know: The existing pipe is multiplexed across all hooked processes using pipe instances.
   - What's unclear: Whether per-process pipes (e.g., `DlpHookPipe_<pid>`) are needed for reliable watchdog detection.
   - Recommendation: Use the existing pipe for simplicity; if reliability issues arise, migrate to per-process pipes in a follow-up phase.

2. **What is the acceptable timeout for watchdog self-unload?**
   - What we know: Agent heartbeat is every 30s (configurable). Hook DLL pipe timeout is 50ms per operation.
   - What's unclear: Whether 3 consecutive failures at 5s intervals (15s total) is too aggressive or too lenient.
   - Recommendation: Start with 3 failures at 5s intervals = 15s total. Tune based on UAT results in Phase 58.3.

3. **Should unhook failures be retried?**
   - What we know: Some processes may be in a state where they cannot receive pipe commands (e.g., suspended, debugging).
   - What's unclear: Whether retrying unhook is worth the complexity or if we should just leave the hooks in place (which is the current behavior).
   - Recommendation: Do not retry unhook. Log a warning and emit an `unhook_failure` audit event. The hooks will be cleaned up when the process exits naturally.
