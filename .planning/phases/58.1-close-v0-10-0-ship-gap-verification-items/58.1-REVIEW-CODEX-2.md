## Live-Code Observations (Non-Blocking)

The following observations are documented for awareness during implementation. They do not block plan approval because they are pre-existing live-code conditions that the plans correctly account for.

### OBS-01: `HookIpcServer` struct lacks `bypass_tx` field; `with_bypass_channel` does not exist in production code

**File:** `dlp-agent/src/hook_ipc.rs:92-98` (struct definition), `dlp-agent/src/hook_ipc.rs:100-186` (impl block)
**Observation:** The `HookIpcServer` struct has no `bypass_tx` field:
```rust
pub struct HookIpcServer {
    pipe_name: String,
    handler: HookHandler,
    diagnostics_handler: Option<DiagnosticsHandler>,
    health_handler: Option<HealthHandler>,
    override_handler: Option<OverrideHandler>,
}
```
The impl block provides `new`, `with_cache`, `with_diagnostics_handler`, `with_health_handler`, `with_override_handler`, and `run` / `run_with_ready` — but **no `with_bypass_channel` or `with_cache_offline_and_bypass`**. The test code at lines 1310-1329 and 1355-1379 references these constructors and asserts `server.bypass_tx.is_some()`, which would be compile errors if the tests were run.

**Impact:** The plan 58.1-02 Task 1 correctly identifies that `service.rs` must use `with_bypass_channel`, but this constructor does not exist in the production code. The implementer will need to add both the `bypass_tx` field to `HookIpcServer` and the `with_bypass_channel` constructor (or update `handle_connection` to accept a bypass sender parameter). This is **expected work** for the phase, not a plan defect — the plan correctly identifies the gap.

**Why non-blocking:** The plan's acceptance criteria require `HookIpcServer` to be constructed via `with_bypass_channel`, which implicitly requires implementing it. The plan does not falsely claim the constructor already exists.

### OBS-02: `service.rs` uses `unbounded` channel but plan 58.1-02 specifies `bounded(1000)`

**File:** `dlp-agent/src/service.rs:1432`
**Observation:** Live code uses `crossbeam_channel::unbounded::<BypassAlert>()` but plan 58.1-02 Task 3 acceptance criteria specify `crossbeam_channel::bounded::<BypassAlert>(1000)`. The plan's threat model (bypass_rx flooding) explicitly calls for a bounded channel.

**Impact:** The implementer must change `unbounded` to `bounded(1000)` in `service.rs`. This is correctly identified as required work in the plan.

### OBS-03: `handle_connection` at `hook_ipc.rs:320-323` still drops `BypassAlert` with `continue`

**File:** `dlp-agent/src/hook_ipc.rs:320-323`
**Observation:** The live code has:
```rust
IpcPayloadV1::BypassAlert(ref alert) => {
    debug!(reason = ?alert.reason, stub = %alert.stub_name, "Hook IPC: bypass alert received");
    continue;
}
```
This drops the alert. Plan 58.1-02 Task 1 correctly requires replacing this with routing to `bypass_tx`. The plan is accurate about the live code state.
