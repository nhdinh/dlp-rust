## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Hook DLL writes journal entry for ALL mutating file operations: WriteFile, WriteFileEx, NtWriteFile, DeleteFileW, MoveFileExW, CopyFileExW, CopyFile2, SetFileInformationByHandle, NtSetInformationFile. Pure opens/create calls are NOT journaled.
- **D-02:** Journal entry stays minimal: `seq`, `file_object`, `op`, `path_hash`, `ts_qpc` (56-byte `JournalEntry` from Phase 53). Content hashes and approval override tokens are NOT duplicated in journal.
- **D-03:** Journal entry is written BEFORE calling the original Win32/NT API, regardless of ABAC decision (ALLOW or DENY).
- **D-04:** If journal mapping is lost or ring buffer full, hook preserves ABAC decision and emits `HookJournalLost`/`JournalDegraded` alert via named pipe. Does NOT fail-closed on journal-only fault.
- **D-05:** `BypassCorrelator::run()` spawns a dedicated tokio task to drain `bypass_rx` (crossbeam `Receiver<BypassAlert>`). Existing single-threaded `run()` loop continues ETW-to-journal correlation.
- **D-06:** Agent/hook-submitted bypass alerts go DIRECTLY to `BypassAlertRepository::insert` / `insert_batch` and skip ETW correlation. They carry their own `correlation_reason` set by hook DLL.
- **D-07:** ETW-derived and agent-submitted alerts share the same `bypass_alerts` table and same SIEM/alert-router routing. No separate storage schema.
- **D-08:** Agent-submitted alerts use same `batch_id` + composite-unique dedup semantics as ETW-derived alerts (WR-08 from Phase 53). Failed retries generate new `batch_id` per attempt.
- **D-09:** Create `VERIFICATION.md` for EVERY v0.10.0 phase 48-58.1 that does not already have one.
- **D-10:** Each `VERIFICATION.md` follows strict template: phase goal, requirement traceability table, PASS/FAIL verdict per success criterion, evidence (test names, log excerpts, commit SHAs), caveats/notes.
- **D-11:** Lightweight checklists are NOT acceptable for this ship gate. Milestone audit requires auditable evidence of each success criterion.
- **D-12:** Phase 58.1 plan must include discovery step listing which phases already have `VERIFICATION.md` and which need one created.
- **D-13:** Phase 58.1 produces a manual execution script/checklist for OPS-04 UAT on physical Windows 11 hardware, derived from `.planning/milestones/v0.10.0-UAT.md`.
- **D-14:** Actual execution on physical hardware is DEFERRED to a separate manual task outside Phase 58.1. Claude cannot operate physical devices; fabricated evidence is unacceptable.
- **D-15:** The handoff artifact must be self-contained: exact PowerShell snippets, expected outputs, pass/fail criteria, and CRIT-04 benchmark protocol.
- **D-16:** Phase 58.1 may generate simulated/automated evidence only for portions that do not require physical hardware (e.g., unit-test coverage reports, clippy/fmt reports, build artifact hashes). Physical-device scenarios remain unexecuted and explicitly marked PENDING.

### Pattern 1: Journal Write Before Original API

**What:** In each mutating trampoline, write a `JournalEntry` to the per-process ring buffer BEFORE calling the original Win32/NT API.

**When to use:** All mutating operations per D-01.

**Example:**
```rust
// Source: CONTEXT.md D-01/D-03 + existing hook_journal.rs patterns
pub unsafe extern "system" fn HookWriteFile(
    hfile: HANDLE,
    lpbuffer: *const u8,
    nnumberofbyteswrite: u32,
    lpnumberofbyteswritten: *mut u32,
    lpoverlapped: *mut OVERLAPPED,
) -> BOOL {
    guard_trampoline("WriteFile", || {
        with_reentrancy_guard(|| {
            // 1. Compute path hash from handle context (or cache)
            let path_hash = compute_path_hash_from_handle(hfile);
            let file_object = hfile.0 as u64;
            let op = JournalOp::Write;
            let ts_qpc = query_performance_counter();
            
            // 2. Write journal entry BEFORE any API call
            // D-03: Write before original API, regardless of ABAC decision
            if let Err(e) = JOURNAL.with(|j| {
                j.borrow_mut().write_entry(JournalEntry {
                    seq: next_seq(),
                    file_object,
                    op,
                    path_hash,
                    ts_qpc,
                })
            }) {
                // D-04: Emit alert but preserve ABAC decision
                emit_journal_degraded_alert(file_object, op, e);
            }
            
            // 3. ABAC decision (classification, policy evaluation)
            let decision = classify_handle(hfile, Action::Write);
            
            // 4. Apply decision
            match decision {
                Decision::Allow => {
                    let original = ORIGINAL_WRITEFILE.load(Ordering::SeqCst);
                    let fn_ptr: unsafe extern "system" fn(...) = std::mem::transmute(original);
                    fn_ptr(hfile, lpbuffer, nnumberofbyteswrite, lpnumberofbyteswritten, lpoverlapped)
                }
                Decision::Deny => fail_closed!(DenyReturn::Bool(FALSE)),
            }
        })
    })
}
```

### Pattern 2: Dedicated bypass_rx Consumer Task

**What:** Spawn a tokio task that drains `bypass_rx` and routes alerts directly to `BypassAlertRepository::insert_batch`.

**When to use:** D-05 requires dedicated task for hook-submitted bypass alerts.

**Example:**
```rust
// Source: CONTEXT.md D-05/D-06 + existing crossbeam patterns in agent
impl BypassCorrelator {
    pub async fn run(mut self, mut shutdown: ShutdownSignal) -> Result<(), CorrelatorError> {
        // Spawn dedicated task for bypass_rx (D-05)
        let bypass_handle = tokio::spawn(async move {
            loop {
                match self.bypass_rx.try_recv() {
                    Ok(alert) => {
                        tracing::info!(metric = "bypass_rx_processed", alert_id = ?alert.id);
                        if let Err(e) = self.repository.insert_batch(&[alert]).await {
                            tracing::warn!(metric = "bypass_rx_insert_failed", error = ?e);
                        }
                    }
                    Err(TryRecvError::Empty) => {
                        tokio::time::sleep(Duration::from_millis(10)).await;
                    }
                    Err(TryRecvError::Disconnected) => {
                        tracing::warn!(metric = "bypass_rx_dropped", reason = "channel_closed");
                        break;
                    }
                }
            }
        });
        
        // Existing single-threaded ETW-to-journal correlation loop
        let etw_handle = tokio::spawn(async move {
            self.run_etw_correlation_loop().await
        });
        
        tokio::select! {
            _ = shutdown.recv() => {
                bypass_handle.abort();
                etw_handle.abort();
                Ok(())
            }
            r = bypass_handle => r.map_err(|e| CorrelatorError::Join(e)),
            r = etw_handle => r,
        }
    }
}
```

### Anti-Patterns to Avoid

- **Writing journal AFTER original API call:** Violates D-03 invariant. ETW could observe the operation before the hook records it, causing false-positive bypass alerts.
- **Failing closed on journal write failure:** Violates D-04. A journal-only fault should not block user operations; emit alert and continue.
- **Blocking the ETW correlation loop with bypass_rx:** Violates D-05. The two streams must be processed independently to prevent one from starving the other.
- **Creating separate bypass alert storage schema:** Violates D-07. Both alert sources must share the same table and routing logic.

## Common Pitfalls

### Pitfall 1: Journal Write Ordering
**What goes wrong:** Writing the journal entry AFTER the original API call means ETW can observe the operation before the hook records it, producing false-positive `NoHookJournal` bypass alerts.
**Why it happens:** Developer places journal write after the ABAC decision, conflating "journal for correlation" with "journal for audit evidence."
**How to avoid:** Per D-03, journal write MUST be the first operation in the trampoline, before any classification or API call. The journal records the intent to operate, not the outcome.
**Warning signs:** Unit tests showing `BypassAlert` with `correlation_reason=NoHookJournal` for operations that clearly passed through a hooked API.

### Pitfall 2: bypass_rx Blocking ETW Loop
**What goes wrong:** Adding `bypass_rx` consumption to the existing `run()` loop serializes ETW correlation and bypass alert processing. Under high bypass alert load, ETW events queue up and correlation latency exceeds the 5-second target.
**Why it happens:** Single-threaded loop processes one stream at a time; bypass alerts are bursty (e.g., during EDR re-patch events).
**How to avoid:** Per D-05, spawn a DEDICATED tokio task for `bypass_rx`. The existing `run()` loop continues ETW-to-journal correlation uninterrupted.
**Warning signs:** Integration tests showing ETW correlation latency > 5s under bypass alert load; `bypass_rx` channel full warnings.

### Pitfall 3: Journal Entry Format Bloat
**What goes wrong:** Temptation to add content hash, approval token, or other fields to the 56-byte `JournalEntry` to "make correlation easier."
**Why it happens:** Developer sees that the named pipe carries richer evidence and wants to duplicate it in the journal.
**How to avoid:** Per D-02, the journal is intentionally minimal. Content hashes and approval tokens travel via the named-pipe audit path (`IpcPayloadV1::BypassAlert`). The journal's sole purpose is ETW correlation (seq/file_object/op/path_hash/ts_qpc).
**Warning signs:** `JournalEntry` size growing; ring buffer capacity decreasing; cache line alignment breaking.

### Pitfall 4: VERIFICATION.md as Lightweight Checklist
**What goes wrong:** Generated VERIFICATION.md files contain only a checklist of items without evidence, test names, or commit SHAs.
**Why it happens:** Rushing documentation generation; treating verification as a checkbox exercise rather than an audit artifact.
**How to avoid:** Per D-10/D-11, each success criterion must have: PASS/FAIL verdict, evidence (test names, log excerpts, commit SHAs), and a caveats/notes section. Use `57-VERIFICATION.md` as the template.
**Warning signs:** VERIFICATION.md files with only bullet lists and no evidence tables; missing requirement traceability.

### bypass_rx Consumer Task Spawn

```rust
// Source: CONTEXT.md D-05 + existing agent service.rs patterns
// In service.rs where BypassCorrelator is constructed:

let (bypass_tx, bypass_rx) = crossbeam::channel::bounded(1000);
let correlator = BypassCorrelator::new(
    etw_consumer,
    journal_discovery,
    bypass_rx,  // D-05: dedicated task will drain this
    repository,
    siem_connector,
    alert_router,
);

// Wire bypass_tx into hook_ipc server
let hook_ipc_server = HookIpcServer::new(bypass_tx.clone(), ...);

// In BypassCorrelator::run():
let mut bypass_task = tokio::spawn(async move {
    let mut batch = Vec::with_capacity(100);
    let mut batch_timer = tokio::time::interval(Duration::from_secs(1));
    
    loop {
        tokio::select! {
            _ = batch_timer.tick() => {
                if !batch.is_empty() {
                    if let Err(e) = repository.insert_batch(&batch).await {
                        tracing::warn!(metric = "bypass_rx_batch_failed", count = batch.len(), error = ?e);
                    }
                    batch.clear();
                }
            }
            msg = bypass_rx.recv_async() => {
                match msg {
                    Ok(alert) => {
                        tracing::info!(metric = "bypass_rx_processed", alert_id = ?alert.id);
                        batch.push(alert);
                        if batch.len() >= 100 {
                            if let Err(e) = repository.insert_batch(&batch).await {
                                tracing::warn!(metric = "bypass_rx_batch_failed", count = batch.len(), error = ?e);
                            }
                            batch.clear();
                        }
                    }
                    Err(_) => {
                        tracing::warn!(metric = "bypass_rx_dropped", reason = "channel_closed");
                        break;
                    }
                }
            }
        }
    }
});
```

## Open Questions

1. **Hook DLL journal write performance impact**
   - What we know: Journal write is a shared-memory ring buffer operation (sub-microsecond).
   - What's unclear: Whether adding journal writes to ALL 9 mutating trampolines measurably impacts the CRIT-04 <=25% overhead gate.
   - Recommendation: Include a benchmark task in the plan that runs `cargo build --workspace --release` with journal writes enabled vs. disabled. If overhead exceeds 2% from journal alone, profile before shipping.

2. **BypassCorrelator bypass_rx backpressure strategy**
   - What we know: D-05 specifies a dedicated tokio task; D-08 specifies batch insert with max 100 alerts.
   - What's unclear: Whether the task should use `try_recv` (non-blocking) or `recv_async` (blocking) and what the batch timeout should be.
   - Recommendation: Use `recv_async` with a 1-second batch timer (as shown in Code Examples). This balances latency (alerts visible in DB within 1s) with throughput (batch insert amortizes SQLite overhead).

3. **VERIFICATION.md evidence sourcing for phases without automated verification**
   - What we know: Some phases (e.g., 50, 52, 53, 55, 56) were completed before the verification template was standardized. Their evidence may be scattered across plan summaries, STATE.md entries, and commit messages.
   - What's unclear: Whether sufficient evidence exists to populate the strict template for all 8 missing phases.
   - Recommendation: Plan a discovery task that audits each missing phase's plans, commit history, and test results. If evidence is insufficient, mark the criterion as "VERIFIED BY INSPECTION" with explicit rationale rather than fabricating evidence.

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
