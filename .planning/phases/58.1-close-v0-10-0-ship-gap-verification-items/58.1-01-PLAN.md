# Plan 58.1-01: Hook DLL Journal Writes in Mutating Trampolines

**Goal:** Ensure every mutating file operation in the hook DLL writes a journal entry to the per-process ring buffer BEFORE calling the original Win32/NT API, so the Phase 53 bypass correlator does not produce false-positive `NoHookJournal` bypass alerts.

**Requirement:** SC-58.1-01 (derived from ROADMAP success criterion 1: hook DLL writes ring journal entry for every ETW-correlated trampoline operation)

**Depends on:** Phase 53 (hook journal ring buffer exists), Phase 48 (trampolines exist)

---

## Threat Model

| Threat | STRIDE | Mitigation |
|--------|--------|------------|
| Journal overflow causes hook to fail-closed, blocking legitimate operations | Denial of Service | D-04: fail-open on journal fault — emit alert but allow operation to proceed |
| Journal write after original API call causes ETW to observe unjournaled operation | Tampering (detection) | D-03: journal write is placed before the original Win32/NT API call, after classification, consistent with existing trampolines |
| Journal entry bloat increases ring buffer pressure | Denial of Service | D-02: 56-byte fixed entry size, no content hashes or approval tokens in journal |
| False-positive bypass alerts from missing journal entries | Information Disclosure | D-01: all 9 mutating trampolines journaled; pure opens are not (correctly) |

**ASVS Level:** 1 (operational hardening, no new crypto or auth surface)
**Blocking threshold:** High severity threats only — none identified; this plan is defense-in-depth.

---

## must_haves

### truths

- D-02: The journal entry stays minimal: seq, file_object, op, path_hash, ts_qpc (56-byte JournalEntry from Phase 53). Content hashes and approval override tokens are not duplicated in the journal; the named-pipe audit path already carries that evidence.
- D-03: The journal entry is written before calling the original Win32/NT API, regardless of whether the ABAC decision is ALLOW or DENY. This guarantees ETW cannot observe an operation the hook has not yet recorded. The existing placement in `classify_and_log_path` and `classify_and_log_handle` (after classification, before returning the decision) satisfies this invariant.
- D-04: If the journal mapping is lost or the ring buffer cannot accept an entry, the hook preserves the ABAC decision and emits a `JournalDegraded` alert through the named pipe. It does not fail the operation closed, to avoid productivity loss from a journal-only fault.

### Task 3: Add JournalDegraded alert emission on journal fault

<read_first>
- dlp-hook-dll/src/hook_journal.rs (write_entry error handling, HookJournal::get pattern)
- dlp-hook-dll/src/pipe_client.rs (send_raw_oneway signature)
- dlp-common/src/hook_ipc.rs (IpcPayloadV1 enum, existing BypassAlert variant)
- .planning/phases/58.1-close-v0-10-0-ship-gap-verification-items/58.1-PATTERNS.md (JournalDegraded alert emission pattern)
</read_first>

<action>
1. In `dlp-common/src/hook_ipc.rs`, add a new `JournalDegraded(JournalDegradedAlert)` variant to the `IpcPayloadV1` enum. Define a new `JournalDegradedAlert` struct with fields: `file_object: u64`, `op: u8`, `error: String`. Derive `Debug, Clone, PartialEq, Serialize, Deserialize` on both.

2. In `dlp-hook-dll/src/hook_journal.rs`, if `journal_write_from_trampoline` returns an error (journal mapping lost, ring buffer full), the hook must NOT fail the operation closed. Instead, construct a `JournalDegradedAlert`, serialize it with `bincode::serialize`, and emit it via `pipe_client::send_raw_oneway` to the agent named pipe. The alert payload must contain: `file_object: u64`, `op: u8`, `error: String`. This alert is best-effort (fire-and-send); if the pipe is unreachable, the error is silently dropped. The ABAC decision (ALLOW or DENY) proceeds unchanged.

3. The agent's `handle_connection` in `dlp-agent/src/hook_ipc.rs` must not treat `IpcPayloadV1::JournalDegraded` as a fatal error. At minimum, it should log receipt and continue (or route it to an appropriate handler if one exists). The plan should note this as a cross-plan dependency with 58.1-02.
</action>

<acceptance_criteria>
- `IpcPayloadV1::JournalDegraded(JournalDegradedAlert { file_object: u64, op: u8, error: String })` variant exists in dlp-common
- Both the variant and `JournalDegradedAlert` derive `Debug, Clone, PartialEq, serde::Serialize, serde::Deserialize`
- On journal write failure, the trampoline constructs a `JournalDegradedAlert`, serializes it with `bincode::serialize`, and calls `pipe_client::send_raw_oneway` before returning the ABAC decision
- The ABAC decision is preserved regardless of journal write success or failure
- The agent's `handle_connection` does not panic or error on `IpcPayloadV1::JournalDegraded` (logs and continues)
- Code compiles with `cargo build -p dlp-hook-dll` with zero warnings
</acceptance_criteria>

## Revision Notes

This plan was revised to address the following Codex review findings:

- **HIGH-001:** Replaced all references to `HookMessage::JournalDegraded` with `IpcPayloadV1::JournalDegraded(JournalDegradedAlert)`. The `HookMessage` enum does not exist in the codebase; the wire protocol uses `IpcEnvelope::V1(IpcMessageV1 { payload: ... })`. Added `JournalDegradedAlert` struct definition and updated Task 3 action to use `bincode::serialize` before `send_raw_oneway`. Added a note that the agent's `handle_connection` must not error on the new variant.
- **MEDIUM-001:** Changed Task 2 journal write placement wording from "FIRST operation inside the closure, BEFORE any ABAC classification" to "before the original Win32/NT API call and after classification, consistent with D-03." The live code already places the journal write after classification (lines 397, 534 in trampolines.rs), which satisfies D-03. The task now verifies this placement rather than requiring a move.
- **LOW-002:** Added explicit `bincode::serialize` step to Task 3 action before calling `send_raw_oneway`, matching the actual function signature (`&[u8]`).
