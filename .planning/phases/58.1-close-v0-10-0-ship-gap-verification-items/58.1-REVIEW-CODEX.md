## Findings

### HIGH-001: HookMessage::JournalDegraded variant does not exist in dlp-common
**Plan:** 58.1-01 (Task 3)
**Severity:** HIGH
**Category:** correctness
**Description:** Plan 58.1-01 Task 3 requires adding a `HookMessage::JournalDegraded` variant to `dlp-common/src/hook_ipc.rs` and using it for alert emission from `hook_journal.rs`. However, there is no `HookMessage` enum anywhere in the codebase — the only reference is a design comment at line 485 of `hook_ipc.rs` saying "There is no HookMessage::CacheDelta variant." The plan assumes `HookMessage` exists as a distinct type from `IpcEnvelope`, but the actual code uses `IpcEnvelope::V1(IpcMessageV1 { payload: ... })` as the wire format. The `JournalDegraded` alert cannot be emitted as specified because the type it targets does not exist.
**Evidence:** `dlp-common/src/hook_ipc.rs` — no `HookMessage` enum defined; grep across `dlp-common/src` finds only the comment at line 485. The plan's Task 3 action says "Add the `JournalDegraded` variant to the `HookMessage` enum in `dlp-common/src/hook_ipc.rs` if it does not already exist."
**Recommendation:** Either (a) add `JournalDegraded` as a new `IpcPayloadV1` variant instead of `HookMessage`, or (b) define a separate `HookMessage` enum and update `pipe_client.rs` to serialize it. The plan must be revised to match the actual wire protocol. If using `IpcPayloadV1`, the agent's `handle_connection` must also be updated to route the new variant (not just `continue`).

### HIGH-002: bypass_rx task already exists in BypassCorrelator::run() — plan describes adding it as new
**Plan:** 58.1-02 (Task 2)
**Severity:** HIGH
**Category:** correctness
**Description:** Plan 58.1-02 Task 2 instructs adding a "dedicated tokio task" to drain `bypass_rx` as a 4th task alongside proc, etw, and flush. However, the live code in `dlp-agent/src/bypass_correlator.rs` lines 1016-1029 already show a `bypass_handle` task using `tokio::task::spawn_blocking` that drains `bypass_rx` and calls `submit_bypass_alert`. The plan treats this as missing work, but it is already implemented. Executing the plan as written would duplicate the task (two bypass_rx consumers) or cause a merge conflict. The plan's acceptance criteria ("4th tokio task") are already satisfied by the existing code.
**Evidence:** `dlp-agent/src/bypass_correlator.rs:1016-1029` — existing `bypass_handle` task. Also `58.1-PATTERNS.md` lines 991-1049 reproduce this exact code as the "pattern" to follow, confirming it already exists.
**Recommendation:** Revise 58.1-02 Task 2 to "verify existing bypass_rx task behavior matches specification" rather than "add a new task." The task should verify: (1) batching with 100-alert cap and 1s timer, (2) `recv_async` vs `recv` usage, (3) metric logging. The existing code uses `recv()` (blocking sync) inside `spawn_blocking`, not `recv_async` with `tokio::select!` — if the plan's `recv_async` + timer design is the desired end state, the plan must explicitly call for refactoring the existing task, not adding a new one.

### MEDIUM-001: Plan 58.1-01 Task 2 journal write placement contradicts D-03 invariant
**Plan:** 58.1-01 (Task 2)
**Severity:** MEDIUM
**Category:** correctness
**Description:** The plan's Task 2 action says to insert `journal_write_from_trampoline` "as the FIRST operation inside the `with_reentrancy_guard` closure, BEFORE any ABAC classification or original API call." However, the live code in `trampolines.rs` already places the journal write at the END of `classify_and_log_path` / `classify_and_log_handle` (lines 397-398 and 534), AFTER classification and BEFORE returning the decision. The PATTERNS.md file (lines 395-399) documents this as the existing pattern. D-03 says "before calling the original Win32/NT API" — the current placement is AFTER classification but BEFORE the original API call, which satisfies D-03. The plan's "FIRST operation" wording is stricter than D-03 and would require moving the journal write before the allowlist check, cache lookup, and fail-mode state machine — a significant refactor with no stated benefit. The plan should align with D-03, not invent a stricter invariant.
**Evidence:** `dlp-hook-dll/src/trampolines.rs:395-399` — journal write is last operation before returning decision. `58.1-CONTEXT.md` D-03: "before calling the original Win32/NT API, regardless of whether the ABAC decision is ALLOW or DENY." The current code satisfies this.
**Recommendation:** Change Task 2's placement instruction from "FIRST operation" to "before the original API call and after classification," matching the existing pattern and D-03. Verify the existing placement is correct rather than requiring a move.

### MEDIUM-002: Plan 58.1-02 Task 1 hook_ipc.rs BypassAlert arm already routes to bypass_tx
**Plan:** 58.1-02 (Task 1)
**Severity:** MEDIUM
**Category:** completeness
**Description:** Plan 58.1-02 Task 1 says to verify the `IpcPayloadV1::BypassAlert` arm in `hook_ipc.rs` and replace `continue` with routing to `bypass_tx`. However, the live code at `hook_ipc.rs:320-323` shows `continue` (which drops the alert), but the test `test_bypass_alert_routes_through_server_to_receiver` at lines 1383-1435 already exists and passes — it uses `HookIpcServer::with_bypass_channel` which wires `bypass_tx`. The discrepancy is that the `handle_connection` function (the server-side dispatcher) has `continue`, but the `HookIpcServer` struct has a `bypass_tx` field and a constructor `with_bypass_channel` that sets it. The test proves the bypass channel works end-to-end. The plan's Task 1 is partially correct (the `handle_connection` arm does need updating) but the framing "If the arm contains `continue;` (logs and drops the alert), replace it with routing to `bypass_tx`" is accurate. However, the plan does not mention that `HookIpcServer` must be constructed with `with_bypass_channel` (not `new`) for `bypass_tx` to exist. The acceptance criteria should include this constructor requirement.
**Evidence:** `dlp-agent/src/hook_ipc.rs:320-323` — `continue` in handle_connection. Lines 1383-1435 — `test_bypass_alert_routes_through_server_to_receiver` passes. `service.rs:1437` — uses `spawn_hook_ipc_server` which may or may not use `with_bypass_channel`.
**Recommendation:** Clarify Task 1 to state: the `handle_connection` function must be updated to send to `self.bypass_tx`, AND the server must be constructed via `with_bypass_channel` (or `with_cache_offline_and_bypass`). Verify `service.rs` uses the correct constructor.

### LOW-002: Plan 58.1-01 Task 3 uses `pipe_client::send_raw_oneway` but the function signature may not match
**Plan:** 58.1-01 (Task 3)
**Severity:** LOW
**Category:** correctness
**Description:** The plan's Task 3 action says to emit `HookMessage::JournalDegraded` via `pipe_client::send_raw_oneway`. The `send_raw_oneway` function takes `&[u8]` (raw bytes), not a structured enum. The implementer would need to `bincode::serialize` the message first. The plan does not mention serialization, which could lead to a type mismatch at compile time. This is a minor omission since the test in Task 5 does mention `bincode::serialize`, but the action in Task 3 should be explicit.
**Evidence:** `58.1-PATTERNS.md` lines 154-179 show `send_raw_oneway(pipe_name: &str, payload: &[u8])` signature. Plan 58.1-01 Task 3 says "emit a `HookMessage::JournalDegraded` alert via `pipe_client::send_raw_oneway`" without mentioning serialization.
**Recommendation:** Add "serialize the alert with `bincode::serialize` before passing to `send_raw_oneway`" to the Task 3 action.

## Cross-plan consistency check

### Consistency between 58.1-01 and 58.1-02
- **Consistent:** Both plans correctly reference D-01 through D-08 from CONTEXT.md. The threat models are aligned (DoS via channel flooding, false-positive bypass alerts).
- **Inconsistent:** 58.1-01 Task 3 and 58.1-02 Task 1 both touch the IPC wire format. 58.1-01 assumes `HookMessage` exists; 58.1-02 assumes `IpcPayloadV1::BypassAlert` exists. The wire format is actually `IpcEnvelope::V1(IpcMessageV1 { payload: IpcPayloadV1::BypassAlert(...) })` — there is no `HookMessage`. The two plans are inconsistent in their assumptions about the IPC type hierarchy. This must be resolved before execution.

### Consistency between 58.1-02 and live code
- **Inconsistent:** 58.1-02 treats `bypass_rx` consumption as missing work, but it is already implemented in `bypass_correlator.rs`. The plan's acceptance criteria ("4th tokio task") are already met. The plan should be reframed as "verify and refine" rather than "add."

### Consistency between 58.1-01 and live code
- **Partially consistent:** The live `trampolines.rs` already has `journal_write_from_trampoline` calls in `classify_and_log_path` and `classify_and_log_handle` (lines 397, 534). The plan's Task 1 says to audit which trampolines call it — the answer is "all mutating trampolines already call it indirectly via the classify functions." The plan should verify this rather than assume gaps exist.

### Consistency between 58.1-03 and D-09
- **Inconsistent:** D-09 requires VERIFICATION.md for phases 48-58.1. The plan only covers 8 phases. The plan must explicitly address the remaining phases.

## Verdict Rationale

**Verdict: NEEDS_REVISION**

Two HIGH findings block execution:
1. **HIGH-001:** The `HookMessage` enum does not exist. The plan's JournalDegraded alert emission cannot be implemented as specified. The wire protocol must be reconciled (likely using `IpcPayloadV1` instead).
2. **HIGH-002:** The bypass_rx task already exists in `BypassCorrelator::run()`. Executing the plan as written risks duplicating the task or creating merge conflicts. The plan must be reframed as verification/refinement.

Both HIGH findings require plan revision before any code changes should be attempted. The MEDIUM and LOW items are actionable but do not block execution if the HIGH items are resolved.
