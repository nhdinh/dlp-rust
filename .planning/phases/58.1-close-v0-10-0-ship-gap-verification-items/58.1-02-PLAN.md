# Plan 58.1-02: BypassCorrelator bypass_rx Routing

**Goal:** Wire `BypassCorrelator::run()` to consume `bypass_rx` events submitted by the hook DLL over the named pipe via `IpcPayloadV1::BypassAlert`, routing them to `BypassAlertRepository::insert_batch` without dropping agent-submitted bypass alerts.

**Requirement:** SC-58.1-02 (derived from ROADMAP success criterion 2: `BypassCorrelator::run()` consumes `bypass_rx` events and routes them to alert storage)

**Depends on:** Phase 53.1 (IpcPayloadV1::BypassAlert variant exists), Phase 53 (BypassAlertRepository::insert_batch exists)

---

## Threat Model

| Threat | STRIDE | Mitigation |
|--------|--------|------------|
| bypass_rx flooding exhausts agent memory | Denial of Service | Bounded crossbeam channel (1000 entries); batch insert with 1s timeout; backpressure via channel fullness |
| bypass_rx processing blocks ETW correlation loop | Denial of Service | D-05: dedicated tokio task for bypass_rx; ETW loop runs independently |
| bypass_tx.send() failure silently drops alerts | Information Disclosure | `tracing::warn!` with `metric = "bypass_tx_dropped"` on every drop; channel bounded to surface backpressure |
| Audit-mode bypass alerts trigger false-positive alerts | Tampering (detection) | Three-layer guard: `handle_etw_event` entry, `submit_bypass_alert` boundary, `emit_alert` emission boundary (pattern from Phase 55.1) |

**ASVS Level:** 1 (operational hardening)
**Blocking threshold:** High severity — memory exhaustion from unbounded channel is mitigated by bounded crossbeam channel.

### Task 2: Add bypass_rx consumer task to BypassCorrelator::run()

<read_first>
- dlp-agent/src/bypass_correlator.rs (run() method, submit_bypass_alert method)
- dlp-agent/src/service.rs (BypassCorrelator construction and run() call)

- .planning/phases/58.1-close-v0-10-0-ship-gap-verification-items/58.1-CONTEXT.md (decisions D-05, D-06, D-07, D-08)
</read_first>

<action>
In `BypassCorrelator::run()`, add a dedicated tokio task that drains `bypass_rx` (crossbeam `Receiver<BypassAlert>`). The task must:
1. Use `recv_async` (blocking await) with a 1-second `tokio::time::interval` batch timer via `tokio::select!`.
2. On receiving an alert, push it to an in-memory `Vec<BypassAlert>` batch buffer.
3. When batch reaches 100 alerts OR the 1-second timer fires, call `self.submit_bypass_alert(alert)` for each alert in the batch (or call a new `submit_bypass_alert_batch` if more efficient). The existing `submit_bypass_alert` method already handles audit-mode suppression, severity assignment, and `PendingAlert` creation.
4. Log `info!(metric = "bypass_rx_processed", alert_id = ?alert.id)` per alert received.
5. Log `warn!(metric = "bypass_rx_dropped", reason = "channel_closed")` when `recv_async` returns `Err(Disconnected)`.
6. The task runs alongside the existing ETW correlation loop and process event loop; all three are joined via `tokio::select!` in `run()`.
7. The `submit_bypass_alert` method already routes to SIEM and alert_router; no new routing logic needed.
</action>

<acceptance_criteria>
- `BypassCorrelator::run()` spawns a 4th tokio task (bypass_rx consumer) alongside proc_handle, etw_handle, and flush_handle
- The bypass_rx task uses `tokio::select!` with `recv_async` and a 1-second interval timer
- Batch size is capped at 100 alerts per insert operation
- Each received alert logs `metric = "bypass_rx_processed"`
- Channel disconnection logs `metric = "bypass_rx_dropped"` with `reason = "channel_closed"`
- The task calls `submit_bypass_alert` for each alert (reusing existing severity, audit-mode, and routing logic)
- Code compiles with `cargo build -p dlp-agent` with zero warnings
</acceptance_criteria>
