## Critical Issues

### CR-01: JournalDegraded handler sends no response, causing client-side hang

**File:** `dlp-agent/src/hook_ipc.rs:386-389`
**Issue:** In `handle_connection`, the `IpcPayloadV1::JournalDegraded` branch uses `continue` (line 388) instead of sending a response envelope back to the client. The hook DLL's `emit_journal_degraded_alert` sends the payload via `pipe_client::send_raw_oneway` (fire-and-forget), but if the client ever switches to a request/response pattern or if a future code change reuses the same connection frame for bidirectional traffic, the server will drop the frame without acknowledgment. More importantly, the `continue` skips the response serialization and `write_frame` at lines 397-405, leaving the client waiting for a response that never arrives. This is a protocol-level hang risk.

**Fix:**
```rust
IpcPayloadV1::JournalDegraded(ref alert) => {
    debug!(...);
    // Send an empty ACK so the client doesn't block on a missing response.
    IpcPayloadV1::Response(HookResponse {
        decision: dlp_common::Decision::ALLOW,
        reason: "journal degraded alert received".to_string(),
        cache_hint: None,
        cache_version: 0,
        approval_override: None,
    })
}
```

### CR-02: resolve_proc uses dangling pointer from dropped Vec

**File:** `dlp-hook-dll/src/lib.rs:630-642`
**Issue:** `resolve_proc` creates a `Vec<u16>` (`dll_wide`) on line 631, then calls `.as_ptr()` on it and passes that pointer to `GetModuleHandleW` via `PCWSTR::from_raw` on line 632. The `Vec` is dropped at the end of the statement (or at the end of the block), but the pointer is used inside `GetModuleHandleW`. In practice, the `Vec` is likely still alive because the expression `GetModuleHandleW(PCWSTR::from_raw(dll_wide.as_ptr()))` is evaluated as a single call, but this is a fragile pattern. If future refactoring splits this into multiple statements, the `Vec` could be freed before the Windows API reads it, leading to a use-after-free or incorrect module resolution.

**Fix:**
```rust
unsafe fn resolve_proc(dll_name: &str, fn_name: &str) -> *const std::ffi::c_void {
    let dll_wide: Vec<u16> = dll_name.encode_utf16().chain(std::iter::once(0)).collect();
    let dll = GetModuleHandleW(windows::core::PCWSTR::from_raw(dll_wide.as_ptr()));
    // dll_wide must remain alive until after GetModuleHandleW returns.
    let dll = match dll {
        Ok(h) => h,
        Err(_) => return std::ptr::null(),
    };
    let name = windows::core::PCSTR::from_raw(fn_name.as_ptr());
    match GetProcAddress(dll, name) {
        Some(p) => p as *const std::ffi::c_void,
        None => std::ptr::null(),
    }
}
```

### CR-03: Watchdog force-exits service process on slow shutdown

**File:** `dlp-agent/src/service.rs:214-225`
**Issue:** `shutdown_and_join` spawns a watchdog thread that calls `std::process::exit(1)` after `SHUTDOWN_TIMEOUT * 4 + 5s` (45 seconds). This is a nuclear option: if any blocking thread is stuck in a Win32 call (e.g., `ConnectNamedPipeW` with no client), the entire service process is terminated uncleanly. This bypasses the SCM `StopPending` -> `Stopped` state machine, prevents the Windows Service Control Manager from knowing the service stopped abnormally, and skips any cleanup that would happen after `shutdown_and_join` returns (e.g., reporting `Stopped` to the SCM at line 422). A service that exits via `std::process::exit(1)` while the SCM thinks it is in `StopPending` will be marked as "did not stop correctly" and may trigger recovery actions.

**Fix:** Replace the watchdog with a more surgical approach:
1. Use `CancelSynchronousIo` or `CancelIoEx` on the stuck thread's handle to unblock `ConnectNamedPipeW`.
2. If cancellation fails after the timeout, log the error and report `ServiceExitCode::Win32(ERROR_SERVICE_SPECIFIC_ERROR)` to the SCM instead of force-exiting.
3. Only force-exit as an absolute last resort, and only after reporting `StopPending` with a wait hint that the SCM can extend.

### CR-04: Stub get_image_path_for_pid and get_creation_time_for_pid silently drop security metadata

**File:** `dlp-agent/src/bypass_correlator.rs:994-1006`
**Issue:** Both `get_creation_time_for_pid` and `get_image_path_for_pid` are stub implementations that unconditionally return `None` and `String::new()` respectively. These values are used for:
- PID reuse detection (creation_time mismatch triggers journal re-open)
- Alert enrichment (image_path is sent to the SIEM for attribution)
- SHA-256 computation (image_path empty -> no hash -> no integrity verification)

With the stubs in place, every bypass alert will have empty `image_path` and `image_sha256`, and PID reuse detection is non-functional. This is a security monitoring gap: the SIEM cannot attribute alerts to specific executables, and a malicious process that reuses a PID will inherit the old journal mapping, potentially evading detection.

**Fix:** Implement these using `NtQuerySystemInformation(SystemProcessInformation)` or `OpenProcess(PROCESS_QUERY_INFORMATION) + GetProcessImageFileNameW` on Windows. On non-Windows, return `None`/`String::new()` with a clear warning log. The stubs should not be shipped in production.

## Warnings

### WR-01: is_write_action case sensitivity may miss mixed-case actions

**File:** `dlp-hook-dll/src/trampolines.rs:466-488`
**Issue:** `is_write_action` matches action strings using byte literals (`b"CREATE"`, `b"write"`, etc.). The match covers both uppercase and lowercase variants, but not mixed case (e.g., `"Create"`, `"Write"`). If the caller passes a mixed-case action string (which is common in Windows APIs or user code), the function returns `false`, classifying a write as a read. This causes the cache fast-path to incorrectly allow a T3/T4 write operation that should have been denied.

**Fix:**
```rust
fn is_write_action(action: &str) -> bool {
    let upper = action.to_ascii_uppercase();
    matches!(
        upper.as_bytes(),
        b"CREATE" | b"WRITE" | b"MOVE" | b"COPY" | b"DELETE" | b"REPLACE" | b"SET_INFO" | b"NT_WRITE" | b"NT_SET_INFO"
    )
}
```

### WR-02: Empty catch-equivalent in spawn_blocking bridge

**File:** `dlp-agent/src/bypass_correlator.rs:1044-1059`
**Issue:** In the `bypass_rx` task, `rt.block_on(bypass_corr.submit_bypass_alert(alert))` is called inside `spawn_blocking`. If `submit_bypass_alert` panics or the runtime is unavailable, the error is silently swallowed because there is no `.await` on the outer `spawn_blocking` handle (the handle is dropped immediately). The `tokio::select!` at line 1073 awaits the handle, but if the task panics, `select!` will just see the handle complete without propagating the panic. This is the async equivalent of an empty catch block.

**Fix:**
```rust
let bypass_handle = tokio::task::spawn_blocking(move || {
    while let Ok(alert) = bypass_rx.recv() {
        let bypass_corr = Arc::clone(&bypass_corr);
        if let Ok(rt) = tokio::runtime::Handle::try_current() {
            if let Err(e) = std::panic::catch_unwind(|| {
                rt.block_on(bypass_corr.submit_bypass_alert(alert))
            }) {
                error!(error = ?e, "bypass alert handler panicked");
            }
        }
    }
});
// Then await the handle and log if it panics.
```

### WR-03: Unbounded loop in accept_loop with no backoff on pipe creation failure

**File:** `dlp-agent/src/hook_ipc.rs:264-314`
**Issue:** If `create_pipe` fails repeatedly (e.g., the pipe name is already in use by another process, or the system is out of handles), `accept_loop` will spin in a tight loop: it calls `create_pipe`, fails, logs a warning, and immediately calls `create_pipe` again. There is no sleep or backoff. This consumes 100% CPU and floods the logs.

**Fix:** Add a small sleep (e.g., 100ms) after pipe creation failure, with exponential backoff up to a maximum (e.g., 5s):
```rust
let mut backoff = Duration::from_millis(100);
loop {
    if crate::service::shutdown_requested() { ... }
    let pipe = match create_pipe(&pipe_name) {
        Ok(p) => { backoff = Duration::from_millis(100); p }
        Err(e) => {
            warn!(error = %e, "pipe creation failed, retrying in {:?}", backoff);
            std::thread::sleep(backoff);
            backoff = (backoff * 2).min(Duration::from_secs(5));
            continue;
        }
    };
    // ... rest of loop
}
```

### WR-04: close_pipe leaks handle in test helper

**File:** `dlp-hook-dll/tests/journal_degraded_test.rs:56-58`
**Issue:** `close_pipe` calls `pipe.into_raw_handle()` which consumes the `std::fs::File` and returns the raw handle, but never calls `CloseHandle` on it. The handle is leaked. In tests this is mostly harmless, but it is a pattern that could be copied into production code, and it causes handle exhaustion if the test is run many times.

**Fix:**
```rust
fn close_pipe(pipe: std::fs::File) {
    use std::os::windows::io::AsRawHandle;
    unsafe {
        let _ = windows::Win32::Foundation::CloseHandle(windows::Win32::Foundation::HANDLE(pipe.as_raw_handle() as _));
    }
    drop(pipe);
}
```

### WR-05: flush_batch builds batch_id from first alert but retries use per-alert IDs

**File:** `dlp-agent/src/bypass_correlator.rs:937-971`
**Issue:** `flush_batch` extracts `batch_id` from the first alert (line 954) and uses it for the server POST. If the POST fails, `requeue_with_retry` generates a NEW `batch_id` per alert (line 988). This means the server sees a different `batch_id` on retry, which breaks idempotency checks that key off the batch ID. The intent of WR-10 (new batch_id per retry) is to avoid server dedup blocking, but the server-side contract is ambiguous: does the server dedup by batch_id or by alert content? If by batch_id, retries will create duplicates. If by content, the batch_id change is unnecessary.

**Fix:** Document the server-side dedup contract explicitly. If the server dedups by `(batch_id, alert content)`, then `requeue_with_retry` should keep the same `batch_id` for the same alert content and only change it if the alert content changes (which it doesn't on retry). If the server dedups by `batch_id` alone, then the current behavior is correct but will create duplicate alerts in the SIEM. Either way, the contract needs to be clarified and the code made consistent.

### IN-02: test_pure_open_no_journal documents known behavior drift

**File:** `dlp-hook-dll/tests/journal_integration.rs:115-143`
**Issue:** The test comment (lines 127-136) acknowledges that pure opens (CreateFileW, NtCreateFile, NtOpenFile) are journaled even though D-01 says they should NOT be. The justification is that "extra entries don't harm correlation." However, this increases journal pressure, consumes ring buffer slots, and could cause mutating operations to be overwritten earlier than expected on high-frequency processes. It is a minor inefficiency, not a bug, but should be tracked.

**Fix:** File a low-priority issue to skip journal writes for op=1 (Create) in the pure-open trampolines, or update D-01 to reflect the actual behavior.
