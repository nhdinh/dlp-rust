# Phase 58.1: Code Review Report

**Reviewed:** 2026-06-23
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

This review covers the 12 source files modified during Phase 58.1 ("close-v0-10-0-ship-gap-verification-items"). The phase focused on closing gaps for the v0.10.0 ship milestone, including: JournalDegraded ACK responses, bypass correlator batch semantics, retry with new batch_id, UAT execution scripts, and hook DLL journal integration tests.

The review identified **5 Critical**, **5 Warning**, and **3 Info** findings. The most severe issues are: a hardcoded SYSTEM SID fallback in the real hook IPC server that bypasses ABAC identity checks; a shutdown watchdog that calls `std::process::exit(1)` which kills the entire agent process without graceful cleanup; and JWT signature validation being disabled in the approval poll loop. Several stub functions (`get_creation_time_for_pid`, `get_image_path_for_pid`) return hardcoded None/empty values, meaning PID reuse detection and image enrichment are non-functional. The hook DLL's `resolve_proc` passes a non-null-terminated Rust string to `GetProcAddress` via `PCSTR::from_raw`, which is undefined behavior.

## Critical Issues

### CR-01: Hardcoded SYSTEM SID Fallback Bypasses ABAC Identity Checks

**File:** `dlp-agent/src/service.rs:1877`
**Issue:** The real hook IPC server (spawned in `run_loop_init`) uses `get_process_user_sid(req.pid).unwrap_or_else(|| "S-1-5-18".to_string())` as the `user_sid` in the `EvaluateRequest`. When `get_process_user_sid` fails (e.g., process exited, access denied, or non-elevated caller), the fallback SID is `S-1-5-18` (NT AUTHORITY\SYSTEM). This means:
1. Any failed SID lookup is treated as SYSTEM, which typically has the highest privileges in ABAC policies.
2. A non-elevated or terminated process could be evaluated with SYSTEM privileges, potentially bypassing deny rules intended for normal users.
3. The fallback is silent — no warning is logged when the fallback is used.

This is a security vulnerability because it undermines the "Least Privilege" and "Explicit Auditability" principles from the project CLAUDE.md.

**Fix:**
```rust
let user_sid = match get_process_user_sid(req.pid) {
    Some(sid) => sid,
    None => {
        warn!(pid = req.pid, "failed to resolve process SID — denying request");
        return dlp_common::HookResponse {
            decision: dlp_common::Decision::DENY,
            reason: "identity resolution failed".to_string(),
            cache_hint: None,
            cache_version: 0,
            approval_override: None,
        };
    }
};
```

### CR-02: Shutdown Watchdog Calls `std::process::exit(1)` — Kills Agent Without Cleanup

**File:** `dlp-agent/src/service.rs:218-224`
**Issue:** `BlockingThreads::shutdown_and_join` spawns a watchdog thread that sleeps for `watchdog_timeout` then calls `std::process::exit(1)`. This is a Critical issue because:
1. It bypasses all Rust destructors, `Drop` implementations, and cleanup code (including flushing the SQLite offline audit queue, closing named pipes, and releasing the single-instance mutex).
2. If the SQLite connection is in the middle of a transaction, the database file may be left in a corrupted or WAL-locked state.
3. The service control manager (SCM) is not notified of the abnormal termination, potentially leaving the service in "StopPending" indefinitely from Windows' perspective.
4. The watchdog timeout is computed as `SHUTDOWN_TIMEOUT.saturating_mul(4).saturating_add(Duration::from_secs(5))`, but if `SHUTDOWN_TIMEOUT` is large, the watchdog may never fire, and if it's small, it may fire during normal shutdown.

**Fix:** Replace `std::process::exit(1)` with a structured escalation:
```rust
// Instead of std::process::exit(1):
error!(?watchdog_timeout, "shutdown watchdog: threads failed to join — forcing abort");
// 1. Log the stuck thread names.
// 2. Force-close named pipe handles to unblock ConnectNamedPipeW.
// 3. Use std::process::abort() only as absolute last resort, or better:
//    signal the SCM that shutdown failed, then return from service_main.
```
A better approach is to cancel pending I/O on the named pipes (using `CancelSynchronousIo` or closing the pipe handles) to unblock the threads, then join normally.

### CR-03: JWT Signature Validation Disabled in Approval Poll Loop

**File:** `dlp-agent/src/service.rs:3236`
**Issue:** The `approval_poll_loop` function decodes JWT tokens with `insecure_disable_signature_validation()`. The code comment justifies this by stating "the token was just fetched from the trusted server over HTTPS." However:
1. The token is being parsed from a server response, but the decoding key is `DecodingKey::from_secret(&[])` (empty secret), and signature validation is explicitly disabled.
2. If the server response is tampered with in transit (e.g., via a compromised proxy, DNS hijacking, or a man-in-the-middle attack on the local network), malicious approval tokens could be injected into the cache.
3. The comment says "The signature is re-verified on every cache read via ApprovalCache::check() using the cached public key" — but if the initial parse is unverified, a malformed token could exploit parser vulnerabilities or cause a denial of service by crashing the JWT decoder before the re-verification step.

**Fix:** Use the server's public key (already cached in `ApprovalCache`) to verify the signature during the initial parse:
```rust
let token_data = match jsonwebtoken::decode::<ApprovalClaims>(
    &entry.token,
    &approval_cache.get_decoding_key(), // or fetch from cached public key
    &{
        let mut v = jsonwebtoken::Validation::new(jsonwebtoken::Algorithm::EdDSA);
        v.set_issuer(&["dlp-server"]);
        v
    },
) {
    Ok(data) => data.claims,
    Err(e) => {
        warn!(approval_id = %entry.id, error = %e, "approval token signature verification failed");
        continue;
    }
};
```

### CR-04: `resolve_proc` Passes Non-Null-Terminated Rust String to `GetProcAddress`

**File:** `dlp-hook-dll/src/lib.rs:637`
**Issue:** `resolve_proc` constructs a `PCSTR` from a raw pointer to a Rust `&str`:
```rust
let name = windows::core::PCSTR::from_raw(fn_name.as_ptr());
match GetProcAddress(dll, name) {
```
Rust `&str` values are NOT null-terminated. `GetProcAddress` expects a null-terminated C string (or an ordinal). Passing a non-null-terminated pointer is undefined behavior — `GetProcAddress` will read past the end of the string until it finds a null byte, potentially causing:
1. Reading into adjacent memory, causing an access violation.
2. Resolving the wrong function (if a null byte happens to appear later in memory).
3. Information disclosure if the read crosses a page boundary into sensitive memory.

**Fix:** Explicitly null-terminate the string:
```rust
let name_c = std::ffi::CString::new(fn_name).ok()?;
let name = windows::core::PCSTR::from_raw(name_c.as_ptr() as *const u8);
match GetProcAddress(dll, name) {
    Some(p) => p as *const std::ffi::c_void,
    None => std::ptr::null(),
}
```

### CR-05: Stub Functions `get_creation_time_for_pid` and `get_image_path_for_pid` Return Hardcoded None/Empty

**File:** `dlp-agent/src/bypass_correlator.rs:994-1006`
**Issue:** Both `get_creation_time_for_pid` and `get_image_path_for_pid` are documented as "Will be integrated with process_registry" but are currently stubs that always return `None` and `String::new()` respectively. This has serious consequences:
1. **PID reuse detection is completely disabled**: `handle_etw_event` (line 690-708) checks `expected_creation != 0 && journal.creation_time() != expected_creation`, but `expected_creation` is always 0, so the condition is never true. A reused PID will use the old journal, causing false negatives or false positives in correlation.
2. **Image path enrichment is broken**: `emit_alert` (line 820) and `submit_bypass_alert` (line 798) both call `get_image_path_for_pid`, which always returns an empty string. This means `image_sha256` is never computed (line 821-825), and the `image_path` field in every bypass alert is empty. Forensic analysis of alerts is severely degraded.
3. **Journal discovery fails on first attempt**: `handle_etw_event` (line 660) returns early if `creation_time == 0`, storing the PID as pending. Every ETW event for a new PID goes through this slow path until the process registry (unimplemented) provides the creation time.

**Fix:** Integrate with the process registry immediately, or at minimum, use `OpenProcess` + `GetProcessTimes` to get the creation time and `QueryFullProcessImageNameW` to get the image path:
```rust
async fn get_creation_time_for_pid(&self, pid: u32) -> Option<u64> {
    use windows::Win32::System::Threading::{OpenProcess, GetProcessTimes, PROCESS_QUERY_LIMITED_INFORMATION};
    use windows::Win32::Foundation::FILETIME;
    unsafe {
        let handle = OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, false, pid).ok()?;
        let mut creation = FILETIME::default();
        let mut exit = FILETIME::default();
        let mut kernel = FILETIME::default();
        let mut user = FILETIME::default();
        if GetProcessTimes(handle, &mut creation, &mut exit, &mut kernel, &mut user).is_ok() {
            let _ = CloseHandle(handle);
            Some(((creation.dwHighDateTime as u64) << 32) | (creation.dwLowDateTime as u64))
        } else {
            let _ = CloseHandle(handle);
            None
        }
    }
}
```

## Warnings

### WR-01: `JournalDegraded` Alerts Are ACKed But Never Forwarded to Bypass Correlator

**File:** `dlp-agent/src/hook_ipc.rs:386-396`
**Issue:** When a `JournalDegraded` alert arrives from the hook DLL, the handler responds with an ACK (so the DLL doesn't block) but does NOT forward the alert to the `bypass_tx` channel. This means:
1. The `BypassCorrelator` never sees `JournalDegraded` alerts.
2. There is no server-side tracking of journal degradation events, which are important diagnostic signals for hook health.
3. The comment at line 387 says "journal degraded alert received" but the alert data is discarded.

**Fix:** Forward the alert to the bypass correlator (or a dedicated diagnostics channel) so it can be batched and sent to the server:
```rust
IpcPayloadV1::JournalDegraded(ref alert) => {
    debug!(file_object = alert.file_object, op = alert.op, error = %alert.error, "Hook IPC: journal degraded alert received");
    if let Some(tx) = bypass_tx {
        let bypass_alert = dlp_common::hook_ipc::BypassAlert {
            reason: dlp_common::hook_ipc::BypassReason::EdrDetected, // or a new Degraded variant
            stub_name: "journal_degraded".to_string(),
            pid: 0, // could be extracted from pipe client info
            timestamp_secs: std::time::SystemTime::now().duration_since(std::time::UNIX_EPOCH).unwrap_or_default().as_secs(),
            version: 2,
            agent_id: String::new(),
            image_path: String::new(),
            image_sha256: None,
            file_path: String::new(),
            operation: format!("op={}", alert.op),
            file_object: alert.file_object,
            qpc_timestamp: 0,
            severity: "warn".to_string(),
            correlation_reason: format!("Journal degraded: {}", alert.error),
        };
        let _ = tx.send(bypass_alert);
    }
    IpcPayloadV1::Response(HookResponse {
        decision: dlp_common::Decision::ALLOW,
        reason: "journal degraded alert received".to_string(),
        cache_hint: None,
        cache_version: 0,
        approval_override: None,
    })
}
```

### WR-02: Hook DLL Closes `CreateFileMapping` Handle After `MapViewOfFile`, Leaking View Lifetime Management

**File:** `dlp-hook-dll/src/hook_journal.rs:195`
**Issue:** After successfully calling `MapViewOfFile`, the code calls `CloseHandle(handle)` (line 195), where `handle` is the `CreateFileMappingW` / `OpenFileMappingW` handle. The comment says "Keep the mapping handle alive by leaking it." However, `CloseHandle` does NOT leak the handle — it decrements the handle reference count. If this is the only handle to the mapping, the mapping object itself may be destroyed by the kernel, even though the view is still mapped. While the view remains valid in the process's address space until `UnmapViewOfFile` is called, the underlying section object could be reused or its name freed, causing issues if the agent tries to open the same mapping name later.

**Fix:** Either:
1. Actually leak the handle by removing the `CloseHandle` call (and document that the handle is intentionally leaked for the process lifetime), OR
2. Store the handle in the `HookJournal` struct and close it in a proper cleanup path (e.g., `DllMain` `DLL_PROCESS_DETACH`).

Option 1 (leak) is acceptable for a hook DLL that lives for the process lifetime:
```rust
// Intentionally leak the mapping handle so the mapping object stays alive
// for the lifetime of the process. The view is unmapped automatically on exit.
std::mem::forget(handle); // or store it in HookJournal
```

### WR-03: `spawn_blocking` Bypass Handler Uses `block_on` Inside Loop — Risk of Thread Pool Exhaustion

**File:** `dlp-agent/src/bypass_correlator.rs:1044-1059`
**Issue:** The bypass alert handler is wrapped in `tokio::task::spawn_blocking`, but inside the loop it calls `rt.block_on(bypass_corr.submit_bypass_alert(alert))`. This means:
1. Every bypass alert blocks a `spawn_blocking` thread for the duration of `submit_bypass_alert` (which acquires an async mutex).
2. If the bypass channel receives alerts faster than they can be processed, the `spawn_blocking` thread pool (default size = number of CPU cores) can be exhausted.
3. The `block_on` call is nested inside a `spawn_blocking` context, which is an anti-pattern. Tokio's `block_on` should not be called from within a Tokio runtime context.

**Fix:** Convert the bypass channel to an async channel (e.g., `tokio::sync::mpsc`) and process alerts in a normal `tokio::spawn` task:
```rust
// Task 3: Bypass alert handler (async channel).
let bypass_handle = tokio::spawn(async move {
    while let Some(alert) = bypass_rx.recv().await {
        let bypass_corr = Arc::clone(&bypass_corr);
        tracing::info!(...);
        bypass_corr.submit_bypass_alert(alert).await;
    }
});
```
If `crossbeam_channel` must be used for the sync/async boundary, use a dedicated bridge task instead of `block_on` inside `spawn_blocking`.

### WR-04: `flush_batch` Uses `alerts.first().map(...).unwrap_or_default()` for batch_id — Empty Batch Panic Risk

**File:** `dlp-agent/src/bypass_correlator.rs:954-957`
**Issue:** After extracting alerts from the batch mutex, `flush_batch` computes the `batch_id` as:
```rust
let batch_id = alerts.first().map(|a| a.batch_id.clone()).unwrap_or_default();
```
While the early return at line 943-944 prevents this when the batch is empty at lock acquisition, the `unwrap_or_default()` means that if `alerts` somehow becomes empty between the lock release and this line (e.g., due to a logic error in future refactoring), the `batch_id` becomes an empty string. The server may reject empty batch IDs, causing all alerts in the batch to be dropped silently.

**Fix:** Add an explicit assertion or use `expect` with a clear message:
```rust
let batch_id = alerts.first()
    .map(|a| a.batch_id.clone())
    .expect("flush_batch: alerts non-empty after early return check");
```

### WR-05: `test_batch_insert_max_100` Test Name Is Misleading — Batch Size Is a Flush Boundary, Not Submission Boundary

**File:** `dlp-agent/tests/bypass_rx_batch_test.rs:40-75`
**Issue:** The test is named `test_batch_insert_max_100` and sends 150 alerts, asserting that "all 150 alerts should be in the pending batch." However, the comment correctly states that "batch size is a flush boundary, not a submission boundary." The test name and assertion are misleading — they suggest the batch is capped at 100, but `submit_bypass_alert` pushes to an unbounded `Vec` (the `alert_batch` is a `Mutex<Vec<PendingAlert>>`). The actual 100-alert boundary is in `flush_batch` (which is not tested here). This test does not verify the flush boundary behavior, only that the Vec grows without limit.

**Fix:** Rename the test to `test_batch_insert_unbounded` and add a separate test that verifies `flush_batch` actually splits at 100:
```rust
#[tokio::test(flavor = "multi_thread")]
async fn test_flush_batch_splits_at_100() {
    // Send 150 alerts, then trigger flush_batch manually.
    // Assert that the first flush contains 100 alerts and the second contains 50.
}
```

## Info

### IN-01: `BypassAlert` Struct Has `file_object: u64` but No Validation That It Is Non-Zero

**File:** `dlp-common/src/hook_ipc.rs:280-281`
**Issue:** The `file_object` field is documented as "Kernel FILE_OBJECT pointer (forensics correlation only)" and is "EXPLICITLY set from ETW event.file_object per CR-08." However, there is no validation that `file_object` is non-zero before sending. A zero value (which is the default for `u64`) is a valid kernel pointer value for NULL, and sending it could confuse downstream forensics tools.

**Fix:** Add a validation check in `emit_alert` before creating the `BypassAlert`:
```rust
if event.file_object == 0 {
    warn!(pid = event.pid, "ETW event has zero file_object — forensics correlation may be impaired");
}
```

### IN-02: `test_bypass_rx_batch_of_100` Uses `tokio::time::sleep` Then Drops `bypass_tx` — Race Condition in Test

**File:** `dlp-agent/tests/bypass_correlator_rx_test.rs:122-162`
**Issue:** The test sleeps for 100ms, then drops `bypass_tx` to signal the channel to close. However, the `spawn_blocking` task is reading from `bypass_rx` and calling `block_on(submit_bypass_alert)`. If the task is still processing alerts when `bypass_tx` is dropped, some alerts may not be processed before the channel closes. The 100ms sleep is arbitrary and may fail on slow CI runners.

**Fix:** Use a synchronization primitive (e.g., `tokio::sync::Notify` or a counter) to wait until all alerts are processed before dropping the sender:
```rust
let (done_tx, done_rx) = tokio::sync::oneshot::channel();
let bypass_rx_handle = tokio::task::spawn_blocking(move || {
    let mut count = 0;
    while let Ok(alert) = bypass_rx.recv() {
        // ... process alert ...
        count += 1;
        if count == 100 {
            let _ = done_tx.send(());
        }
    }
});
done_rx.await.expect("all 100 alerts processed");
drop(bypass_tx);
```

### IN-03: `Uat-Execute-v0.10.0.ps1` Uses `Start-Process` for Word Without Capturing Exit Code or Verifying Document Open

**File:** `scripts/Uat-Execute-v0.10.0.ps1` (scenarios involving Word launch)
**Issue:** The UAT script launches Microsoft Word to test file-open interception, but it does not:
1. Capture the Word process exit code to verify it launched successfully.
2. Verify that the document actually opened (e.g., by checking for a window title or process main window handle).
3. Handle the case where Word is already running (which may cause `Start-Process` to return immediately without creating a new process).

This makes the UAT test flaky and unable to distinguish between "Word failed to launch" and "Word launched but the hook did not intercept."

**Fix:** After `Start-Process`, add a wait loop that checks for the process to have a main window, and verify the window title contains the expected document name:
```powershell
$proc = Start-Process -FilePath "winword.exe" -ArgumentList "`"$testDoc`"" -PassThru
$timeout = 30
$elapsed = 0
while ($proc.MainWindowHandle -eq 0 -and $elapsed -lt $timeout) {
    Start-Sleep -Seconds 1
    $elapsed++
    $proc.Refresh()
}
if ($proc.MainWindowHandle -eq 0) {
    throw "Word did not open a window within $timeout seconds"
}
# Verify window title
$title = $proc.MainWindowTitle
if ($title -notlike "*$docName*") {
    throw "Word window title '$title' does not contain expected document name '$docName'"
}
```
