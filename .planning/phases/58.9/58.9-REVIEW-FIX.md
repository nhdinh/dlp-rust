## Fixed Issues

### WR-01: Drained diagnostic batch is permanently lost on any transient upload failure

**Files modified:** `dlp-agent/src/service.rs`
**Commit:** `65698863`
**Applied fix:** On a failed `submit_diagnostic_snapshot` the drained batch is now re-ingested into the aggregator under the aggregate `(pid 0, agent_id)` key, so the documented "retried next interval" contract actually holds. A module-level `DIAGNOSTIC_PUSH_DROPPED_TOTAL: AtomicU64` running counter is incremented and read back into a `dropped_total` field on the warning log, giving operators an observable signal for silent compliance-feed gaps. Re-buffer growth is bounded by the aggregator's existing per-DLL cap (`max_entries_per_dll` truncates the oldest entries), so a permanently-down server cannot regrow the aggregator without bound. The function doc comment was corrected to describe re-buffering and the cap.

### WR-02: Agent writes an ACK for one-way `DiagnosticsResponse` frames the DLL never reads

**Files modified:** `dlp-agent/src/hook_ipc.rs`
**Commit:** `98e448e7`
**Applied fix:** The `DiagnosticsResponse`, `HealthResponse`, `HashEvidence`, `BypassAlert`, and `JournalDegraded` receive arms in `handle_connection` now `continue` instead of building an ALLOW ACK that fell through to the unconditional `write_frame`. Verified on the DLL side that every one of those clients uses `send_raw_oneway` (write + `FlushFileBuffers` + `CloseHandle`, no read), so the ACK was a wasted `WriteFile` that raced the client's `CloseHandle` and produced spurious `ERROR_BROKEN_PIPE` warnings. This mirrors the pre-existing `RequestOverride` arm. The `PullDiagnostics`/`PullHealth` *reply* arms are unaffected (they still produce `DiagnosticsResponse`/`HealthResponse` as their response). Stale "respond with empty ACK" comments were updated.

### WR-03: Full-ring drain is emitted as one unchunked frame

**Files modified:** `dlp-hook-dll/src/trampolines.rs`
**Commit:** `b215cf83`
**Applied fix:** The cadence drain (`drain_snapshots(1000)`) is now emitted in bounded chunks of `DIAG_FRAME_SNAPSHOT_CAP = 250` via `snapshots.chunks(...)` + per-chunk `send_diagnostics`. At ~32 k-char worst-case NTFS paths a 250-snapshot chunk is ~8 MiB, comfortably under the agent's 64 MiB `read_frame` cap, so a single oversized path can at most drop its own small chunk rather than the whole destructively-drained ring. On the first chunk failure the loop `break`s (best-effort) so the hooked file operation is never blocked on repeated pipe I/O; unsent chunks are dropped rather than re-queued (diagnostics are best-effort). The reviewer's optional `abac_resource` truncation was intentionally *not* applied — chunking alone bounds the frame size, and truncation would discard troubleshooting data; recorded as a discretionary follow-up.

### WR-04: Shutdown final-flush is not time-bounded and can exceed the 5 s join budget

**Files modified:** `dlp-agent/src/service.rs`
**Commit:** `b486e321`
**Applied fix:** Both the periodic tick submit and the shutdown final-flush in `diagnostic_push_loop` are now wrapped in a per-call `DIAGNOSTIC_SUBMIT_TIMEOUT = 2 s`. Worst case (mid-flight tick submit + shutdown flush) is ~4 s, under the 5 s `run_loop_shutdown` join budget, so the task can no longer be abandoned. On timeout the tick arm re-buffers the batch (preserving the WR-01 retry contract); the shutdown arm counts and drops the batch (no next interval to retry on during shutdown) and logs `dropped_total`. The function doc comment was updated to describe the bounded submit.

## Skipped Issues

### WR-05: Any authenticated user can forge/pollute diagnostics (and health/bypass) telemetry — PID-only attribution

**File:** `dlp-agent/src/hook_ipc.rs:730-753`, `dlp-agent/src/hook_ipc.rs:382-405`, `dlp-agent/src/ipc/pipe_security.rs`, `dlp-hook-dll/src/pipe_client.rs`
**Reason:** Deferred — no safe inline fix exists; every real mitigation is a discrete cross-cutting feature, and the one "cheap" option (tightening the DACL) would break the product.

The hook pipe DACL is `D:(A;;GRGW;;;AU)(A;;GA;;;SY)(A;;GA;;;BA)` — it *must* grant Authenticated Users read/write because the legitimate injected DLLs run as the interactive user (confirmed in `pipe_security.rs` and the `named_pipe_client_pid` doc comment: "the injected DLLs run as the interactive user"). Restricting the DACL to `LocalSystem` + Administrators would deny every real hook DLL and silently disable DLP enforcement, so it is not a fix.

The two mitigations that would actually bind one-way frames to a verified injected-process identity are both large:
- (a) Server-side image allowlist: resolve the client PID to its image path + SHA-256 (`OpenProcess` + `QueryFullProcessImageNameW` + hash), maintain an injected-process allowlist, plumb a fail-mode decision into `handle_connection`, and handle access-denied / protected-process / cross-session cases without failing open.
- (b) Per-injection nonce challenge over the existing `PollControl` channel, required on `DiagnosticsResponse`/`HealthResponse`/`BypassAlert` — a protocol change touching both DLL and agent plus key/nonce lifecycle.

A half-fix (e.g., an image check that fails open on any error, or gating on a DLL-supplied field) would create a false sense of security and could drop legitimate telemetry under access-denied. Per the phase guidance, the existing `GetNamedPipeClientProcessId` anti-spoof was left intact and not weakened. PID-keying still bounds blast radius to the attacker's own PID bucket (no cross-PID eviction). Recommend filing a dedicated phase for (a) or (b) with an explicit threat-model decision on fail-open vs fail-closed.

**Original issue:** Open pipe DACL + PID-only attribution lets a malicious/compromised process running as the user push fabricated `DiagnosticsResponse` (and `HealthResponse`/`BypassAlert`/`JournalDegraded`) frames keyed under its own honest PID; these are uploaded and surfaced in `/admin/diagnostics` as if genuine. Bounded to the attacker's own PID bucket but not eliminated.

## Deferred (out of scope this pass)

The four Info findings were not in `critical_warning` scope and were left unchanged. Recorded here so they are not lost:

- **IN-01** — `named_pipe_client_pid(...).unwrap_or(0)` silently collapses attribution under key `0_{agent_id}` when the OS PID query fails. Suggest a rate-limited `warn!` + counter on PID-resolution failure.
- **IN-02** — `interval: Duration` is shadowed by `let mut interval = tokio::time::interval(interval);`. Rename the binding to `ticker` and make `MissedTickBehavior` explicit.
- **IN-03** — bare `server_url` normalizes to `http://`; diagnostics carry `abac_resource`/`user_sid`. Deployment-hardening note: require `https://` (or loopback) in production. No code change required in 58.9.
- **IN-04** — `HEALTH_EMIT_COUNTER` and `DIAGNOSTIC_EMIT_COUNTER` are phase-locked (both start at 0, interval 100), so each 100th round-trip opens the pipe twice back-to-back. Document the lockstep or stagger one counter by `INTERVAL/2`.
