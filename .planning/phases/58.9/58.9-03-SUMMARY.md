# Phase 58.9 Plan 03: agent diagnostics producer (consumer + orchestration) Summary

**The agent now ingests one-way `IpcPayloadV1::DiagnosticsResponse` frames from the hook DLL into `DiagnosticAggregator` under a PID-keyed, anti-spoof `{pid}_{agent_id}` key, and a periodic `diagnostic_push_loop` drains that aggregator every 60 s via `drain_all` and POSTs the batch to `POST /agents/{id}/diagnostics` via `submit_diagnostic_snapshot` — wired into the service lifecycle by POPULATING the two `RunLoopContext` fields 58.8 reserved (`diagnostic_push_shutdown`/`diagnostic_push_handle`), with flush-and-stop on shutdown. This closes the consumer/orchestration half of DIFF-04 (criterion 2 + the consumer half of criterion 3); the producer half shipped in Plan 02.**

## Decisions Made

- **Single builder threads identity + aggregator together:** `with_diagnostic_aggregator(agent_id, aggregator)` (authoritative PLAN signature). Threading both makes the A3 invariant (ingest `agent_id` == server-push `agent_id`) visible at one call site and prevents constructing a server that ingests under a different identity than it pushes. The PATTERNS excerpt showed the fields separately; the PLAN governs.
- **Trust the pipe, never the payload (anti-spoof):** the ingest key uses `named_pipe_client_pid(pipe).unwrap_or(0)` (the REAL connecting PID from `GetNamedPipeClientProcessId`), NOT any field inside `DiagnosticsResponse` (which carries no pid). A malicious/buggy DLL cannot attribute snapshots to another PID (T-58.9-11). `pid == 0` (lookup failed) collapses to a benign shared bucket, never a spoofed identity.
- **Reuse, don't extend, `IpcPayloadV1`:** the inbound arm matches the existing `DiagnosticsResponse` variant (dual-use: reply to `PullDiagnostics` AND one-way inbound). No new variant -> no bincode discriminant shift -> `dlp-common/src/hook_ipc.rs` byte-for-byte unchanged (DIFF-04 A2; mirrors Plan 02's producer decision and the 58.8-03 `HealthResponse` precedent).
- **Drain before await (no guard across `.await`):** `drain_all(&self)` returns an OWNED `Vec<(String, Vec<DiagnosticSnapshot>)>`; the `submit_diagnostic_snapshot(...).await` happens after the call returns, so no non-`Send` `DashMap` guard is ever held across the await point (T-58.9-14 / RESEARCH Pitfall 4). `&self` (Plan 01 decision) lets the loop call through `Arc<DiagnosticAggregator>` without an exclusive borrow.
- **429/non-2xx non-fatal, single-shot POST:** `submit_diagnostic_snapshot` maps every non-2xx (incl. 429) to `ServerClientError::ServerError`; the loop logs `warn!` and continues — the per-agent rate limit is honored by the 60 s cadence + the non-fatal mapping, with no retry storm (T-58.9-12 / RESEARCH A4).
- **Populate existing fields, add none:** the two `RunLoopContext` fields reserved by 58.8 (`diagnostic_push_shutdown`/`diagnostic_push_handle`) are filled in; NO new fields were added to `RunLoopContext`, `HookIpcServerConfig` gained only the one `agent_id` field the PLAN requires, and `cargo test --tests --no-run` confirms zero struct-literal drift across all 12 test binaries (T-58.9-15).
- **Lifecycle mirrors health:** start on run (only when `server_client` is present — agent-only mode never pushes, so no loop, no inconsistency), flush-and-stop on shutdown (final `drain_all` + best-effort push inside the shutdown arm; 5 s join budget consistent with the health stop). Verified by `diagnostic_push_loop_drains_pushes_and_shuts_down` (flush exactly once, aggregator left empty).
- **`spawn_diagnostic_push_loop` extracted for testability:** a pure helper lets `diagnostic_push_spawn_populates_handles_when_server_present` assert the `(None,None)`/`(Some,Some)` contract without booting the service. DRY + testability; behavior at the spawn site is identical to inlining.
- **DIFF-04 not marked complete:** consistent with STATE decisions #339/#342 — DIFF-04 spans Plans 01-04 and criterion 3 (end-to-end `GET /admin/diagnostics`) is only proven by Plan 04. There is no main-repo `REQUIREMENTS.md` to update. Marking complete now would overstate coverage.
