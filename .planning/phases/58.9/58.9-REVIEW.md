# Phase 58.9: Code Review Report

**Reviewed:** 2026-07-11
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

Reviewed the DIFF-04 agent-side diagnostics producer pipeline: the DLL cadence drain (`trampolines.rs` + `perf_telemetry.rs` + `diagnostic_ring.rs`), the named-pipe client/server framing (`pipe_client.rs` + `hook_ipc.rs` + `ipc/frame.rs`), the in-memory aggregator (`diagnostic_aggregator.rs`), the server upload (`server_client.rs::submit_diagnostic_snapshot`), and the push-loop lifecycle in `service.rs`. The two large files (`service.rs`, `trampolines.rs`) were reviewed via the phase diff against `97ef75d8` plus targeted full-context reads; supporting modules (`diagnostic_ring.rs`, `ipc/frame.rs`, `dlp-common/src/hook_ipc.rs`) were read to verify cross-module contracts.

No memory-safety or authentication-bypass defects were found — the new code adds no `unsafe` blocks and reuses the existing `DLP-AGENT` agent auth and `GetNamedPipeClientProcessId` anti-spoofing correctly. The bincode discriminant reuse (DIFF-04 A2) is sound. PII (paths/SIDs) is correctly kept out of logs.

The findings cluster around **data-loss semantics and IPC robustness**: silent batch loss on transient upload failure (with a doc comment that falsely promises retry), an ACK the agent writes for one-way frames that the documented fire-and-send DLL client never reads (wasted syscall + spurious broken-pipe warnings), an unchunked full-ring drain that can exceed the 64 MiB frame cap and drop an entire batch, an unbounded final-flush that can outlive the 5 s shutdown join budget, and telemetry forgery/pollution by any authenticated user (bounded but not eliminated by PID attribution).

## Critical Issues

None.

## Warnings

### WR-01: Drained diagnostic batch is permanently lost on any transient upload failure

**File:** `dlp-agent/src/service.rs:1786-1796` (tick arm), `dlp-agent/src/service.rs:1798-1808` (shutdown arm), `dlp-agent/src/server_client.rs:539-547`

**Issue:** `diagnostic_push_loop` calls `diagnostic_aggregator.drain_all()` (destructive — snapshots leave the `DashMap`) and then `await`s `submit_diagnostic_snapshot`. On any non-2xx (429 rate-limit, 5xx) or network error, `submit_diagnostic_snapshot` returns `Err`, the loop logs `warn!(error = %e, count = snapshots.len(), "failed to submit diagnostics")`, and the drained snapshots are gone — they are never re-buffered. The function's own doc comment states failures are "logged and retried on the next interval (RESEARCH A4)", but there is nothing buffered to retry: the next interval only forwards *newly* arrived snapshots. This contradicts the `drain_all` contract ("each snapshot is forwarded exactly once") — under failure the batch is forwarded *zero* times. It is also inconsistent with the audit path in the same file, which re-buffers failed events to the offline queue (`server_client.rs:1238-1268`). There is no dropped-batch counter/metric, so operators cannot detect silent gaps in the compliance/troubleshooting feed.

Diagnostics are documented as best-effort, so this is not a crash or a breach, but silent, unobservable loss with a misleading retry promise is a correctness defect for a DLP product.

**Fix:** On `Err`, re-ingest the drained snapshots (or a capped remainder) so they are retried on the next tick, and emit a dropped-batches metric. At minimum, correct the doc and add a counter:

```rust
let snapshots = diagnostic_aggregator.drain_all();
if snapshots.is_empty() {
    debug!("no diagnostic snapshots to push");
    continue;
}
if let Err(e) = server_client
    .submit_diagnostic_snapshot(&agent_id, 0, &snapshots)
    .await
{
    let dropped = snapshots.len();
    warn!(error = %e, count = dropped, "failed to submit diagnostics — re-buffering");
    // Re-buffer so the "retried next interval" contract actually holds.
    // Re-attribute under agent key; per-pid fidelity is already inside each snapshot.
    diagnostic_aggregator.ingest(&agent_id, 0, snapshots);
    DIAGNOSTIC_PUSH_DROPPED_TOTAL.fetch_add(dropped as u64, Ordering::Relaxed);
}
```
Cap the re-buffer (e.g. keep newest N) so a permanently-down server cannot regrow the aggregator without bound. Wrap the shutdown-arm final submit the same way, or accept-and-log loss explicitly there.

### WR-02: Agent writes an ACK for one-way `DiagnosticsResponse` frames the DLL never reads

**File:** `dlp-agent/src/hook_ipc.rs:730-753` (receive arm), `dlp-agent/src/hook_ipc.rs:855-864` (unconditional response write), `dlp-hook-dll/src/pipe_client.rs:411-436` (`send_raw_oneway` — no read)

**Issue:** The DLL emits `DiagnosticsResponse` via `send_diagnostics` → `send_raw_oneway`, which writes the frame, `FlushFileBuffers`, and `CloseHandle` — it performs **no read**. But `handle_connection`'s `DiagnosticsResponse(ref resp)` arm builds a `HookResponse` ALLOW and falls through to the unconditional `write_frame(pipe, &payload)` at 855-864, so the agent writes an ACK into a pipe whose client is not reading and is likely already closed. `FlushFileBuffers` synchronizes the *read* side; the client's `CloseHandle` then races the agent's `WriteFile`, so under load the agent frequently hits `ERROR_BROKEN_PIPE` and emits `warn!(error = %e, "Hook IPC: write response failed — disconnecting")`. The `RequestOverride` arm (612) already does this correctly via `continue` (skip the write); the new `DiagnosticsResponse` arm (and the pre-existing `HealthResponse`/`HashEvidence`/`BypassAlert`/`JournalDegraded` arms) repeat the anti-pattern. Consequences: (1) a wasted `WriteFile` syscall on every diagnostics frame in the hot path, and (2) spurious broken-pipe warnings from a security component that mask genuine pipe failures.

**Fix:** Treat the genuinely one-way payloads like `RequestOverride` — `continue` instead of falling through to the response write. This does not affect the *reply* use of `IpcPayloadV1::DiagnosticsResponse`/`HealthResponse` (those are values the agent sends in the `PullDiagnostics`/`PullHealth` arms):

```rust
IpcPayloadV1::DiagnosticsResponse(ref resp) => {
    let pid = named_pipe_client_pid(pipe).unwrap_or(0);
    debug!(pid, count = resp.snapshots.len(), "Hook IPC: diagnostics received from DLL");
    if let (Some(aggregator), Some(aid)) = (diagnostic_aggregator, agent_id) {
        aggregator.ingest(aid.as_ref(), pid, resp.snapshots.clone());
    } else {
        warn!("Hook IPC: diagnostics received but no aggregator configured");
    }
    // One-way fire-and-send: the DLL used send_raw_oneway and does not read.
    continue;
}
```
Apply the same `continue` to the `HealthResponse(ref)`, `HashEvidence(ref)`, `BypassAlert(ref)`, and `JournalDegraded(ref)` receive arms for consistency (those DLL clients are also fire-and-send).

### WR-03: Full-ring drain is emitted as one unchunked frame — long paths can exceed the 64 MiB cap and drop the entire batch

**File:** `dlp-hook-dll/src/trampolines.rs:358-366` (`drain_snapshots(1000)` + single `send_diagnostics`), `dlp-hook-dll/src/pipe_client.rs:373-392` (`send_diagnostics`), `dlp-agent/src/ipc/frame.rs:27-33` (`MAX_PAYLOAD = 64 MiB`)

**Issue:** On cadence, the DLL drains up to 1000 snapshots (the whole ring) and serializes them into a single `IpcEnvelope` / single length-prefixed frame. Each `DiagnosticSnapshot` carries several `String`s, including `abac_resource` (an arbitrary file path — up to ~32 k chars on NTFS long paths) and `user_sid`. The agent's `read_frame` rejects any payload `> 64 MiB` with a malformed-frame error and drops the connection. A burst of denies on long paths can therefore push a single frame past 64 MiB, at which point the agent discards the *entire* 1000-snapshot batch with no partial recovery, and the DLL has already destructively drained the ring. There is no chunking, no per-field length bound, and no fallback. Typical short paths keep this well under 64 MiB, but the unbounded single-frame design is a latent data-loss edge for a DLP that must tolerate adversarial/deeply-nested paths.

**Fix:** Chunk the drained snapshots so each frame stays comfortably under the cap, and/or bound serialized path length at enqueue time:

```rust
// trampolines.rs cadence arm
const DIAG_FRAME_SNAPSHOT_CAP: usize = 250; // ~250 x worst-case path << 64 MiB
let mut snapshots = crate::diagnostic_ring::drain_snapshots(1000);
while !snapshots.is_empty() {
    let tail = snapshots.split_off(snapshots.len().min(DIAG_FRAME_SNAPSHOT_CAP));
    let chunk = std::mem::take(&mut snapshots);
    snapshots = tail;
    if let Err(e) = crate::pipe_client::send_diagnostics(crate::current_pipe_name(), &chunk) {
        crate::debug_log(&format!("[dlp-hook] diagnostics chunk send failed: {}\0", e));
        break; // best-effort; remaining chunks dropped rather than blocking
    }
}
```
Also consider truncating `abac_resource` to a sane maximum (e.g. 1024 chars) in `push_snapshot`, since the full path is rarely needed for troubleshooting.

### WR-04: Shutdown final-flush is not time-bounded and can exceed the 5 s join budget

**File:** `dlp-agent/src/service.rs:1798-1808` (shutdown arm), `dlp-agent/src/service.rs:3010-3022` (`run_loop_shutdown` stop), `dlp-agent/src/server_client.rs:43` (`REQUEST_TIMEOUT = 5 s`)

**Issue:** `tokio::select!` picks one ready branch and runs its body to completion. If the tick branch is selected and `submit_diagnostic_snapshot(...).await` runs the full `REQUEST_TIMEOUT` (5 s, slow server), the shutdown signal is not observed until that await returns and the loop re-polls — at which point the shutdown arm performs its *own* unbounded `submit_diagnostic_snapshot(...).await` (another up-to-5 s). Meanwhile `run_loop_shutdown` joins the handle with `tokio::time::timeout(Duration::from_secs(5), handle)`. Worst case (~10 s) the task outlives the join budget, logs `warn!("diagnostic push task did not shut down within 5s")`, and the `JoinHandle` is dropped while the underlying tokio task keeps running until runtime teardown — a shutdown-ordering/task-leak smell and a delayed service stop.

**Fix:** Bound the final flush and make the in-flight submit cancellable on shutdown. Simplest robust version: wrap both submits in a short per-call timeout and select the final flush against a deadline:

```rust
const FLUSH_TIMEOUT: Duration = Duration::from_secs(2);
// shutdown arm:
let snapshots = diagnostic_aggregator.drain_all();
if !snapshots.is_empty() {
    let _ = tokio::time::timeout(
        FLUSH_TIMEOUT,
        server_client.submit_diagnostic_snapshot(&agent_id, 0, &snapshots),
    )
    .await;
}
return;
```
and reduce `REQUEST_TIMEOUT` for the diagnostic client (or use a dedicated client with a 2 s timeout) so a mid-flight tick submit cannot consume the entire join budget. Alternatively, make the periodic submit itself `select!`-aware so shutdown cancels it.

### WR-05: Any authenticated user can forge/pollute diagnostics (and health/bypass) telemetry — PID-only attribution

**File:** `dlp-agent/src/hook_ipc.rs:730-753` (one-way ingest), `dlp-agent/src/hook_ipc.rs:382-405` (`create_pipe` / `PipeSecurity` DACL), `dlp-hook-dll/src/pipe_client.rs:373-392`

**Issue:** The pipe DACL must allow any authenticated user (injected DLLs run as the interactive user), and the agent's anti-spoof control is `named_pipe_client_pid` (T-58.9-11). That prevents impersonating *another* PID, but a malicious/compromised process running as the user can still connect and push fabricated `DiagnosticsResponse` frames with attacker-controlled `abac_resource` and `user_sid`, keyed under its own (honest) PID, and these are uploaded to the server and surfaced in `/admin/diagnostics` as if genuine. The same applies to `HealthResponse`, `BypassAlert` (whose `image_sha256` is DLL-supplied and therefore untrusted), and `JournalDegraded`. PID-keying bounds blast radius to the attacker's own PID bucket (it cannot evict another PID's entries — good), but it does not prevent telemetry forgery/pollution that an admin may act on. This is a known architectural trade-off of an open DACL; flagging because 58.9 adds a new high-volume forgery surface (`DiagnosticsResponse`) carrying sensitive-looking path/SID fields.

**Fix:** Bind one-way frames to a verified injected-process identity, not just a PID. Options, in increasing strength: (1) resolve the client PID to its image path + SHA-256 server-side (`GetProcessImageFileName` + hash) and require the image to be on the agent's injected-process allowlist before accepting one-way telemetry; (2) challenge the DLL with a per-injection nonce over the existing `PollControl` channel and require it on `DiagnosticsResponse`/`HealthResponse`/`BypassAlert`; (3) at minimum, record the OS-resolved image path/hash alongside each ingested snapshot so forged entries are attributable and filterable in the admin view. Document the residual risk explicitly if (1)/(2) are deferred.

## Info

### IN-01: `pid = 0` fallback silently collapses attribution when `GetNamedPipeClientProcessId` fails

**File:** `dlp-agent/src/hook_ipc.rs:734`

**Issue:** `let pid = named_pipe_client_pid(pipe).unwrap_or(0);` keys snapshots under `0_{agent_id}` whenever the OS PID query fails (e.g. client disconnected between connect and query). This does not allow spoofing a chosen PID, but it silently merges such frames into one bucket and degrades the anti-spoof evidence without any log/metric. Emit a `warn!` (rate-limited) and/or a counter when PID resolution fails so operators can see attribution is degraded rather than silently keying under 0.

### IN-02: `interval` parameter shadowed by the `tokio::time::Interval` binding

**File:** `dlp-agent/src/service.rs:1784`

**Issue:** `async fn diagnostic_push_loop(..., interval: Duration, ...)` then does `let mut interval = tokio::time::interval(interval);`, shadowing the `Duration` with an `Interval` of the same name. Legal but confusing, and `tokio::time::interval` fires its first tick immediately (so the loop drains an empty aggregator at startup and logs debug). Rename the binding (e.g. `let mut ticker = tokio::time::interval(interval);`) and call `ticker.reset()` / `MissedTickBehavior` explicitly so the cadence intent is clear.

### IN-03: Diagnostics now place file paths and SIDs onto the (possibly plaintext) server channel

**File:** `dlp-agent/src/server_client.rs:347-353` (`normalize_url` defaults bare host to `http://`), `dlp-agent/src/server_client.rs:513-556` (`submit_diagnostic_snapshot`)

**Issue:** Pre-existing transport behavior: a bare `server_url` is normalized to `http://`. The new diagnostics payload carries `abac_resource` (sensitive path) and `user_sid`. Logging correctly omits them, but if a deployment uses `http://` (the compiled default is loopback, so safe there; remote is the concern) these fields traverse the network in cleartext protected only by the shared `DLP-AGENT` hash. Worth a deployment-hardening note: require `https://` (or localhost) for `DLP_SERVER_URL`/`server_url` in production and document that diagnostics carry path/SID telemetry. No code change strictly required in 58.9; recorded for the threat model.

### IN-04: Health and diagnostics cadences are phase-locked (identical effective interval)

**File:** `dlp-hook-dll/src/trampolines.rs:339-368`, `dlp-hook-dll/src/perf_telemetry.rs:59,87`

**Issue:** `HEALTH_EMIT_COUNTER` and `DIAGNOSTIC_EMIT_COUNTER` are both incremented in the same function, both start at 0, and both have interval `100`, so the health emit and the diagnostic drain always fire on the exact same round-trips — each 100th call opens the pipe twice back-to-back (`send_health_snapshot` then `send_diagnostics`, each a fresh `send_raw_oneway` connection). The doc says diagnostics fire "on its own cadence"; technically separate counters, but effectively identical and synchronized forever. Not a correctness bug, but worth either documenting the lockstep or staggering (e.g. seed one counter at `INTERVAL/2`) to smooth pipe load.
