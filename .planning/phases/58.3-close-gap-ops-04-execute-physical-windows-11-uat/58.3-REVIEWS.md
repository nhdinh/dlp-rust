# Cross-AI Plan Review: Phase 58.3 — Close gap: OPS-04 (execute physical Windows 11 UAT)

**Scope:** Plans 58.3-01, 58.3-02, 58.3-03
**Reviewed against:** live repository files, execution harness, and agent source code

---

## Summary

Phase 58.3 is a pure execution/documentation phase: run 36 manual UAT scenarios on physical Windows 11 hardware and transcribe the results into `.planning/milestones/v0.10.0-UAT.md`. The underlying product features the scenarios exercise are largely implemented in the agent (hook injection, DACL tripwire, ETW bypass correlation, cloud/print enforcement, volume classification, AppInit/Secure Boot detection, Authenticode allowlisting). The plans are well-structured and correctly identify the script-level Word benchmark gap. However, the phase has several **operational readiness gaps** that could invalidate evidence or block ship verification: unfilled `RELEASE_NOTES.md` placeholders directly required by J01/J05, a print-enforcement feature gate that defaults off, and heavy reliance on manual human steps without sufficient automated pre-checks. The risk is therefore not that the code is missing, but that the UAT environment and release artifacts are not fully prepared before execution begins.

## Strengths

1. **Scenario count is consistent across script, plan, and milestone-fix instruction.**
   - `scripts/Uat-Execute-v0.10.0.ps1:51` sets `$SCRIPT:ScenarioCount = 36`.
   - Plan 03 explicitly instructs changing the milestone sign-off table from 30 to 36, matching the script.

2. **Plan 02 correctly detects and compensates for the script's Word benchmark deficiency.**
   - `scripts/Uat-Execute-v0.10.0.ps1:491-557` only starts `WINWORD.EXE`, sleeps 3 seconds, and kills the process — it does not open or save a document.
   - Plan 02 Task 2 adds a manual Word COM automation fallback (`Open` + `Save` + `Close`) and makes it the canonical I02 evidence if it differs from the script result. This closes a real evidence gap.

3. **Cloud sync blocking is implemented, supporting C01-C04.**
   - `dlp-agent/src/cloud_enforcer.rs` defines `CloudProvider` covering OneDrive, GoogleDrive, Dropbox, and Box, and `CloudEnforcer::check` blocks T3/T4 write-like actions inside detected sync folders.

4. **Volume classification supports peripheral scenarios E01-E05 / D01.**
   - `dlp-agent/src/detection/usb.rs` classifies drives into `VolumeClass` variants (`LocalNTFS`, `USBRemovable`, `SDCard`, `Optical`, `Virtual`, `NetworkShare`).
   - `dlp-agent/src/detection/disk.rs` provides mount-time blocking and grace-period logic.

5. **Allowlist + PPL detection supports J01-J03.**
   - `dlp-agent/src/allowlist.rs:101-161` checks self-process, system-critical basenames in trusted Windows dirs, path rules, and certificate subject/thumbprint.
   - `dlp-agent/src/universal_injector.rs:289-327` detects PPL via `GetProcessMitigationPolicy(ProcessSignaturePolicy)`.

6. **DACL tripwire + repair watcher supports B01-B06 and H02.**
   - `dlp-agent/src/dacl_tripwire.rs:236-439` builds a canonical security descriptor with SYSTEM/DLP-Admin allow and DLP deny for Authenticated Users.
   - `dlp-agent/src/dacl_tripwire.rs:83-85` disables the deny ACE only in Audit global mode.
   - `dlp-agent/src/dacl_repair_watcher.rs:199-289` watches for ACL tampering via `ReadDirectoryChangesW`, and `:598-688` adds a 60-second polling backstop.

7. **ETW bypass correlator supports G01.**
   - `dlp-agent/src/bypass_correlator.rs:616-755` correlates ETW Kernel-File events against hook DLL journals with QPC tolerance and short-circuits in Audit mode.
   - `dlp-agent/src/etw_kernel_file.rs:47-55` maps event IDs 12/16/18/30 to Create/Write/Delete/SetInfo.

8. **AppInit/Secure Boot detection supports J04.**
   - `dlp-agent/src/appinit.rs:33-60` reads `AppInit_DLLs`, `LoadAppInit_DLLs`, `RequireSignedAppInit_DLLs`.
   - `dlp-agent/src/appinit.rs:138-161` detects Secure Boot via `GetFirmwareEnvironmentVariableW`.

9. **Authenticode verification path supports J01.**
   - `dlp-agent/src/allowlist.rs` performs certificate subject/thumbprint matching.
   - `RELEASE_NOTES.md` contains hash and Authenticode verification scripts, though the actual v0.10.0 values are still placeholders.

10. **Policy mapper provides path-prefix classification for A/B scenarios.**
    - `dlp-agent/src/interception/policy_mapper.rs:21-26` maps `C:\Restricted\`, `C:\Confidential\`, `C:\Data\`, `C:\Public\` to T4/T3/T2/T1.
    - `:69-78` performs an 8 KB content scan fallback.

## Concerns

### HIGH

1. **`RELEASE_NOTES.md` placeholders will block J01/J05 evidence.**
   - `RELEASE_NOTES.md:20-96` and `:131-166` contain hash-generation and Authenticode-verification scripts, but the v0.10.0 sections still show `[TO BE FILLED AT RELEASE]` for SHA-256/SHA-512 hashes, build provenance, and certificate thumbprint.
   - J01 (verify signed binaries) and J05 (hash verification) require real values. None of the three plans includes a task to populate these placeholders before UAT execution. If they remain empty, the operational verification scenarios cannot produce meaningful PASS/FAIL evidence.

2. **Print enforcement is gated and defaults off, threatening E01-E05.**
   - `dlp-agent/src/config.rs:267` defines `print_enabled`, and `dlp-agent/src/print_enforcer.rs` gates `PrintWatcher` behind `print_enabled.unwrap_or(false)`.
   - If the UAT agent config does not explicitly set `print_enabled = true`, print interception is a no-op. The plans do not include a pre-check to confirm this flag is enabled, so E01-E05 could spuriously fail or need to be marked N/A.

3. **Canonical I02 evidence depends entirely on a manual fallback step.**
   - Although Plan 02 Task 2 provides the COM automation fallback, it is not integrated into `scripts/Uat-Execute-v0.10.0.ps1`. If the tester forgets to run it, the CRIT-04 evidence will reflect only process-launch time, not the file-I/O overhead the UAT plan actually requires. The script's own `word_launch` result could then be misused as canonical.

### MEDIUM

4. **The `>=80%` pass threshold in the formal decision matrix is unjustified.**
   - Plan 03 states: *"PASS if 0 blocking failures AND >=80% of non-N/A scenarios pass"*. The rationale for 80% is not explained in any plan or context document. With only 36 scenarios, a single non-blocking failure could flip the verdict depending on N/A count; the threshold should be documented or tied to a known risk acceptance criteria.

5. **Cloud client sign-in verification relies on tester attestation.**
   - Plan 02 says to mark C01-C04 N/A if a cloud client is not signed in, but there is no automated pre-check to confirm sign-in state. This is error-prone and could lead to false passes if a client silently signed out or is in a throttled/disconnected state.

6. **Minor contradiction in service-restart guidance.**
   - Plan 02 Task 1 step 4 says: *"Restart the dlp-agent service between scenarios within the same category"*.
   - `58.3-CONTEXT.md` D-11 says: *"Use relaxed isolation: restart the dlp-agent service between scenarios within a category"*.
   - While aligned, the step-level instruction does not make clear whether this is mandatory for every scenario or only when contamination is suspected, which could slow execution unnecessarily.

7. **The 30-to-36 scenario-count fix is manual and easy to miss.**
   - `.planning/milestones/v0.10.0-UAT.md:609` still reads `Total Scenarios | 30`. Plan 03 instructs changing it to 36, but there is no automated verification (e.g., `sed`/`Select-String` assertion) in the plan steps. A missed edit would create an inconsistent ship record.

### LOW

8. **Screenshot naming convention uses Phase 57 prefix.**
   - Plan 02 Task 1 step 3 requires `UAT-57-{ScenarioID}_screenshot_...`. This is Phase 58.3; the prefix is a leftover from earlier UAT work and could confuse artifact tracking.

9. **`>50% N/A` escalation rule is vague for small categories.**
   - D-10 says escalate if a category has `>50% N/A`. For categories with only 1-2 scenarios (e.g., H has 3, I has 2, J has 5), a single N/A triggers escalation. This is correct but should be explicitly noted so the tester does not treat it as unexpected.

10. **No cleanup task for `C:\UAT\v0.10.0\TestData\`.**
    - `58.3-CONTEXT.md` D-07 says to prepare test data under `C:\UAT\v0.10.0\TestData\` and clean up after UAT. None of the three plans includes an explicit cleanup task or verification step.

## Suggestions

1. **Add a Plan 01 task to populate `RELEASE_NOTES.md` v0.10.0 placeholders.**
   - Required for J01 and J05. Include hashes, build provenance, and Authenticode certificate thumbprint before UAT execution begins.

2. **Add an automated pre-check for `print_enabled = true`.**
   - Read the active agent config and fail/flag UAT prep if print interception is disabled before E01-E05 run.

3. **Add automated cloud-client sign-in checks.**
   - For each provider in C01-C04, verify the sync folder exists and the client reports a signed-in state before marking scenarios ready.

4. **Integrate the COM automation benchmark into the script for I02.**
   - Replace or augment `scripts/Uat-Execute-v0.10.0.ps1:491-557` with the open/save benchmark so the canonical evidence is generated automatically and cannot be forgotten.

5. **Document the rationale for the 80% pass threshold.**
   - If it is a project standard, reference the standard; if it is a one-off risk acceptance, record the approver and date in the milestone.

6. **Add a verification assertion for the scenario-count fix.**
   - In Plan 03 Task 1, include a `Select-String` check that `Total Scenarios | 36` appears in the sign-off table before committing.

7. **Update screenshot prefix to `UAT-58.3-...`.**
   - Keeps artifact naming consistent with the phase number.

8. **Add an explicit TestData cleanup task to Plan 03.**
   - Include deletion of `C:\UAT\v0.10.0\TestData\` after evidence is archived.

## Risk Assessment

**Overall Risk: MEDIUM-HIGH**

The core implementation risk is low: the code paths required by the 36 scenarios exist and are wired into the agent. The dominant risks are **operational and human**:

- **Evidence validity risk (HIGH):** If `RELEASE_NOTES.md` placeholders are not filled and `print_enabled` is not verified, J01/J05 and E01-E05 cannot produce trustworthy PASS/FAIL evidence. The Word benchmark fallback is similarly human-dependent.
- **Transcription/consistency risk (MEDIUM):** Moving 36 scenario results from `results.json` into `.planning/milestones/v0.10.0-UAT.md` manually, plus the 30→36 count correction, creates a non-trivial chance of copy errors or omissions.
- **Environment drift risk (MEDIUM):** Cloud client sign-in state, EDR allowlist status, peripheral availability, and agent config flags are all dynamic and depend on pre-UAT setup that is not fully automated in the plans.
- **Scope/schedule risk (LOW):** The plans stay within the declared boundary (no new product code, no CI automation, no robotic peripherals). No scope creep was identified.

**Recommendation:** Phase 58.3 can proceed, but only after adding explicit pre-UAT checks for `RELEASE_NOTES.md` completeness, `print_enabled`, and cloud-client sign-in, and after integrating or hardening the I02 COM automation benchmark step. Without these, the ship record may contain placeholder evidence or spurious failures.
