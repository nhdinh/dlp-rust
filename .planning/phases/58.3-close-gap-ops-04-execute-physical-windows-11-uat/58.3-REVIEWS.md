# Cross-AI Review: Phase 58.3 UAT Execution Plans

## Summary

The three plans (01–03) form a coherent manual-UAT workflow for closing the OPS-04 gap on physical Windows 11 hardware. They correctly anchor to the canonical UAT scenario matrix (`.planning/milestones/v0.10.0-UAT.md`), the committed PowerShell harness (`scripts/Uat-Execute-v0.10.0.ps1`), and the deployment-guide allowlist procedures. However, the plans contain two **blocking-level discrepancies** against the actual script and template: (1) Plan 02 demands that blocking scenarios run first, but the committed script runs categories A→J sequentially; (2) the UAT sign-off template lists **30** total scenarios while the script and plan both count **36**. Several MEDIUM concerns also exist around the Word benchmark fidelity, test-data/policy setup omissions, and cross-platform verification commands.

---

## Strengths

- **Strong prerequisite gate.** Plan 01 mirrors D-17 strictly and requires admin rights, Windows 11 build check, dlp-agent service, signtool, EDR allowlist, and a WhatIf script dry-run before any scenario executes (`58.3-01-PLAN.md:76-100`).
- **Correct artifact model.** All three plans treat `C:\UAT\v0.10.0\results.json` and `crit04_results.json` as the canonical machine-readable artifacts and `.planning/milestones/v0.10.0-UAT.md` as the human-auditable ship record, matching D-14/D-15 (`58.3-02-PLAN.md:25-34`, `58.3-03-PLAN.md:21-30`).
- **CRIT-04 protocol alignment.** Plan 02 and the script both use warm-up + 3 baseline + 3 hooked runs with median overhead, consistent with the UAT plan and `v0.10.0-UAT-EXECUTION.md` (`scripts/Uat-Execute-v0.10.0.ps1:378-489`, `v0.10.0-UAT.md:501-518`).
- **Failure handling is tiered correctly.** Blocking failures pause execution per D-13, non-blocking failures are logged and triaged later, and N/A escalation follows the >50% rule from D-10 (`58.3-02-PLAN.md:83-87`, `v0.10.0-UAT.md:62-70`).
- **Threat model is proportionate.** The STRIDE registers cover tampering of the script, repudiation of tester input, EDR quarantine DoS, and incorrect transcription into the milestone doc (`58.3-01-PLAN.md:159-176`, `58.3-03-PLAN.md:160-177`).

---

## Concerns

### HIGH

- **Plan 02’s “blocking scenarios first” ordering is incompatible with the committed script.**
  - Plan 02 Task 1 instructs the tester to execute B, G, H, I, J blocking scenarios first (`58.3-02-PLAN.md:68-71`).
  - However, `scripts/Uat-Execute-v0.10.0.ps1:740-761` executes categories in fixed order A→B→C→D→E→F→G→H→I→J with no priority reordering.
  - D-01 says use the script “exactly as-is,” so the tester cannot rely on the script to enforce the priority order without either manual out-of-script execution or violating D-01. This will delay critical blocking evidence until late in the session.

- **UAT sign-off template says 30 scenarios, but the plan/script define 36.**
  - `.planning/milestones/v0.10.0-UAT.md:609` lists `Total Scenarios | 30`.
  - The script and plan both count 36 (`scripts/Uat-Execute-v0.10.0.ps1:51`, `58.3-02-PLAN.md:19`).
  - If Plan 03 transcribes counts as-is, the milestone document will contain an obvious inconsistency that undermines the ship record.

### MEDIUM

- **Word launch benchmark in the script does not match the UAT plan’s “launch/save” workload.**
  - The UAT plan I02 specifies Word COM automation: open a T4 document and save it (`v0.10.0-UAT.md:512-513`, `v0.10.0-UAT-EXECUTION.md:416-458`).
  - The script only starts `WINWORD.EXE`, sleeps 3 seconds, and kills the process (`scripts/Uat-Execute-v0.10.0.ps1:491-557`). It never opens or saves a document, so I02 will not exercise the Office file-I/O path the CRIT-04 success criteria intends.

- **Plan 01 omits protected-path registration and classification setup.**
  - Scenarios B01–B06, F01–F03, and H01–H03 require `C:\Protected\Test\` to be registered as a protected path with T4 classification via the admin TUI/API.
  - Plan 01 only copies `t4_test.txt` into `C:\Protected\Test\` (`58.3-01-PLAN.md:109-114`) and does not mention policy registration or classification. Without this, file-blocking and DACL-tripwire scenarios will fail for setup reasons rather than product reasons.

- **EDR hash-exclusion scope in Plan 01 is broader than the deployment guide documents.**
  - Plan 01 says apply “hash exclusions for all 6 DLP binaries” (`58.3-01-PLAN.md:86`).
  - `docs/operations/deployment-guide.md:100-102` specifies hash exclusions only for `dlp-agent.exe`, `dlp_hook_dll.dll`, and `dlp-user-ui.exe` (path exclusion covers the install folder). The other three binaries are not listed for hash exclusion.
  - This mismatch could cause the tester to spend time hunting for hashes that the guide never intended to be allowlisted individually.

- **Verification command in Plan 03 is not Windows-native.**
  - Plan 03 uses `grep -c "TO BE FILLED..."` (`58.3-03-PLAN.md:84`) and `git diff --stat` in the same automated block (`58.3-03-PLAN.md:125`). `grep` is unavailable in stock PowerShell; `Select-String` should be used on the test host.

- **Script’s ship-recommendation logic does not match the documented decision matrix.**
  - `scripts/Uat-Execute-v0.10.0.ps1:587-589` recommends `SHIP` if `failed -eq 0 -and na -lt 10`, `NO-SHIP` only if `$blocking.Count -gt 0`, otherwise “Engineering Discretion Required.”
  - The UAT execution guide (`v0.10.0-UAT-EXECUTION.md:555-560`) and Plan 03 (`58.3-03-PLAN.md:112`) say `PASS` requires 0 blocking failures + sign-off, `FAIL` for 1+ blocking, and `CONDITIONAL` for 0 blocking with major issues. The script conflates N/A count with the blocking/major/minor distinction and could auto-recommend `SHIP` even when major failures exist.

### LOW

- **Agent log capture happens after the result prompt.**
  - `scripts/Uat-Execute-v0.10.0.ps1:291` calls `Capture-AgentLogSnippet` only after the tester enters Pass/Fail. The last 100 lines may not include the actual denial event if the tester waited before responding, especially for cloud-sync scenarios where sync is delayed.

- **Cloud-client version detection is fragile.**
  - `scripts/Uat-Execute-v0.10.0.ps1:188-196` captures `$p.Path` (not version) and assumes process names `OneDrive`, `GoogleDriveFS`, `Dropbox`, `BoxDrive`. Box Drive’s process name may differ; the field name “version” in `environment.json` will actually contain a path.

- **No reboot step in Plan 01 despite deployment guide requiring it for hook activation.**
  - `docs/operations/deployment-guide.md:14` and `v0.10.0-UAT-EXECUTION.md:163-170` list reboot as a pre-flight step. Plan 01 never includes it; this risks scenarios A01/A04 failing because existing processes were started before AppInit_DLLs/ETW registration.

- **Service-name inconsistency in privilege check.**
  - Plan 01 uses `sc qprivs dlp-agent` (`58.3-01-PLAN.md:89`), which matches the installed service name in the script and deployment guide (`docs/operations/deployment-guide.md:839`). However, the deployment guide also refers to `NT SERVICE\DlpAgent` in Section 4.6 (`docs/operations/deployment-guide.md:610`). On Windows these are usually equivalent, but the tester should confirm the exact service name installed by the MSI.

## Suggestions

1. **Reconcile scenario ordering before execution.** Either (a) add an explicit manual step to Plan 02 that runs blocking scenarios out of script order while still using the script for per-scenario prompts, or (b) update `scripts/Uat-Execute-v0.10.0.ps1` to support a `-BlockingFirst` switch. Given D-01, option (a) is safer for this phase; option (b) should be logged as a follow-up.

2. **Fix the UAT template’s scenario count.** Update `.planning/milestones/v0.10.0-UAT.md:609` from 30 to 36 before Plan 03 begins, or Plan 03 will produce a contradictory ship record.

3. **Align the Word benchmark with the UAT plan.** Update `scripts/Uat-Execute-v0.10.0.ps1:491-557` to use the COM automation open/save loop from `v0.10.0-UAT-EXECUTION.md:416-458`. If D-01 truly forbids script changes, add a manual fallback step in Plan 02 to run the COM benchmark and overwrite the script-generated `crit04_results.json` Word section.

4. **Add protected-path registration to Plan 01.** Include a step to open `dlp-admin-cli.exe`, register `C:\Protected\Test\` with T4 classification, and wait for policy sync before any B/F/H scenarios.

5. **Correct EDR hash-exclusion wording.** Change Plan 01 from “all 6 DLP binaries” to “path exclusion for `C:\Program Files\DLP\` plus hash exclusions for the three injection-related binaries per deployment-guide.md Section 3,” to match `docs/operations/deployment-guide.md:97-102`.

6. **Use PowerShell-native verification in Plan 03.** Replace `grep -c` with `(Select-String -Path ... -Pattern ...).Count` and run `git` commands from a shell that has Git available.

7. **Add a reboot checkpoint to Plan 01.** Insert a reboot-and-recheck step before the human-verify checkpoint, consistent with `v0.10.0-UAT-EXECUTION.md:163-170`.

8. **Clarify service account / service name in Plan 01.** Have the tester run `Get-CimInstance Win32_Service -Filter "Name='dlp-agent'"` and record both `Name` and `StartName` before checking privileges.

## Risk Assessment

**Overall risk: HIGH**

Justification: The phase is operationally straightforward (run a script, record results), but two HIGH-severity issues directly threaten the validity of the ship record: the script does not execute blocking scenarios first as the plan requires, and the milestone template’s scenario count is wrong. Either could force a re-run or produce a document that cannot be signed. MEDIUM issues around Word benchmark fidelity and protected-path setup further increase the chance that the CRIT-04 evidence and core blocking scenarios will not actually test the intended product behavior. The plans are structurally sound, but they need to be reconciled with the actual script and template before execution begins.
