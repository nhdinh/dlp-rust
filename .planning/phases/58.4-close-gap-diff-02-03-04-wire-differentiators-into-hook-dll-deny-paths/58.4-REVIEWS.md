## Primary Reviewer (Claude Code) — Source-Grounded Findings

### Summary

Phase 58.4 is a gap-closure phase that wires three differentiator capabilities (DIFF-02 diagnostic snapshots, DIFF-03 content SHA-256 hashing, DIFF-04 self-health monitoring) into the hook DLL deny paths. The four plans are well-scoped and follow established patterns from Phases 48-58.2. However, **three HIGH-severity concerns** were identified through source verification: (1) `HookResponse` lacks the hash fields the plans claim already exist, (2) the hash evidence architecture proposed in Plan 02 adds significant complexity without a clear need, and (3) the health snapshot emission cadence in Plan 03 contradicts the existing `EMIT_INTERVAL = 1000` constant in `perf_telemetry.rs`. These must be resolved before execution.

### Strengths

- **Clear scope boundary.** Plans explicitly state what Phase 58.4 does NOT build (no new TUI screens, no new schema, no new modules), which prevents scope creep. This is a mature planning practice.
- **Fire-and-forget invariant.** Every plan correctly emphasizes that snapshot push, hash computation, and health emission must never block, panic, or alter the deny decision. This preserves the hot-path latency guarantee from Phase 50.
- **Good dependency ordering.** Plans 01-03 are wave 1 (independent), Plan 04 is wave 2 (depends on 01-03). This is correct for a gap-closure phase.
- **Threat model coverage.** Each plan includes a STRIDE threat register with concrete threat IDs, categories, and mitigation plans. This is enterprise-grade security practice.
- **Source-grounded verification instructions.** The review prompt explicitly asks reviewers to verify claims against `path/to/file:line` evidence, which the plans themselves reference accurately.

### Concerns

#### HIGH: HookResponse lacks `content_sha256`, `hash_truncated`, `hash_skipped` fields

**Plan 02 (58.4-02-PLAN.md, line 151)** asserts: "Extend HookResponse to include hash fields (already exists in dlp-common)." **This is false.**

Source verification at `dlp-common/src/hook_ipc.rs:176-200` shows `HookResponse` has only these fields:
- `decision: Decision`
- `reason: String`
- `cache_hint: Option<CacheHint>`
- `cache_version: u64`
- `approval_override: Option<bool>`

There are **no** `content_sha256`, `hash_truncated`, or `hash_skipped` fields on `HookResponse`. The `with_content_hash` builder method exists on `AuditEvent` (`dlp-common/src/audit.rs:758`), not on `HookResponse`.

**Impact:** Plan 02's entire hash evidence architecture assumes the hook can return hash data in `HookResponse`. Since the hash is computed AFTER the agent has already sent `HookResponse` (the hook receives `HookResponse` from the agent, then computes the hash on DENY), the hook cannot retroactively attach the hash to the already-sent response. This invalidates the "Option A" approach in Plan 02 Task 2 and forces the use of the more complex "HashEvidence" one-way IPC frame (Option B), which Plan 02 Task 3 then proposes.

**Mitigation:** Add the three hash fields to `HookResponse` in `dlp-common/src/hook_ipc.rs` with `#[serde(default)]` for backward compatibility. This is a schema change but is safe because bincode ignores unknown fields when `#[serde(default)]` is present on the reader side. However, even with this change, the timing problem remains: the hash is computed after the `HookResponse` is received. The hook would need to send a follow-up `HashEvidence` frame or the agent would need to correlate by (pid, handle_value, timestamp). Plan 02 should be rewritten to acknowledge this timing constraint explicitly.

#### HIGH: HashEvidence IPC frame does not exist; agent-side HashCache not implemented

**Plan 02 (58.4-02-PLAN.md, Task 3)** proposes adding a new `IpcPayloadV1::HashEvidence` variant and a `HashCache` in the agent. **Neither exists today.**

Source verification at `dlp-common/src/hook_ipc.rs:75-126` shows `IpcPayloadV1` has these variants:
- `Request`, `Response`, `VolumeClassQuery`, `VolumeClassResponse`, `RequestOverride`, `PullDiagnostics`, `DiagnosticsResponse`, `PullHealth`, `HealthResponse`, `BypassAlert`, `JournalDegraded`

There is no `HashEvidence` variant. Adding one requires:
1. New struct `HashEvidenceFrame` in `dlp-common`
2. New `IpcPayloadV1::HashEvidence` variant
3. Agent-side routing in `dlp-agent/src/hook_ipc.rs:handle_connection` (~line 375)
4. New `HashCache` type (DashMap-based) in `dlp-agent`
5. Periodic cleanup task for the HashCache
6. Audit event enrichment logic in the agent's request handler

This is significantly more work than the plan acknowledges. The plan labels this as "Task 3" under Plan 02 but does not account for the cross-crate schema change and new agent-side module.

**Impact:** Underestimation of implementation complexity. The plan's "must_haves" claim "The computed hash (or skipped flag) is returned in HookResponse" which is unachievable without the schema change. The fallback "HashEvidence" approach is untested and adds a new IPC frame to a protocol that has been stable since Phase 53.

**Mitigation:** Either (a) add hash fields to `HookResponse` and accept that the agent must send them back in the same response (impossible for timing reasons), or (b) implement the `HashEvidence` frame properly with full cross-crate schema updates, agent routing, and a TTL-governed HashCache. Option (b) is the only viable path. The plan should be expanded to include the schema change as a prerequisite task.

#### HIGH: Plan 03 emission cadence (100) contradicts existing `EMIT_INTERVAL = 1000`

**Plan 03 (58.4-03-PLAN.md, Task 2)** states: "In perf_telemetry.rs, modify `record_latency` to emit a health snapshot every 100 pipe round-trips." It also adds a separate `HEALTH_EMIT_INTERVAL: u64 = 100` constant.

Source verification at `dlp-hook-dll/src/perf_telemetry.rs:52` shows:
```rust
const EMIT_INTERVAL: u64 = 1000;
```

The existing telemetry emission is every 1000 calls, not 100. Plan 03's claim of "every 100 pipe round-trips" is a 10x increase in emission frequency. While this may be intentional for fresher dashboard data, the plan does not justify why 100 is the right number or discuss the IPC overhead impact.

**Impact:** If implemented as written, the hook DLL would emit health snapshots 10x more frequently than existing telemetry, potentially increasing named-pipe contention. The plan also proposes adding `HEALTH_EMIT_COUNTER` inside `record_latency`, which means health snapshots are emitted on the latency measurement path — but `record_latency` is called on every classification (including ALLOW paths), not just pipe round-trips. This would mean health snapshots are emitted based on total classification calls, not pipe round-trips as D-09 requires.

**Mitigation:** Clarify the emission cadence in the plan. If 100 is intentional, document the rationale and verify pipe overhead. If the intent is "every 100 pipe round-trips," the counter should be incremented only in `classify_path` / `classify_handle` on cache miss (where a pipe call is made), not in `record_latency` which is called on every classification. Alternatively, keep the existing 1000-call cadence and add a separate health-specific counter that triggers on pipe calls only.

#### MEDIUM: `send_health_snapshot` does not exist in `pipe_client.rs`

**Plan 03 (58.4-03-PLAN.md, Task 2)** proposes adding `send_health_snapshot` to `pipe_client.rs`. Source verification confirms this function does not exist. The plan correctly identifies this as new work, but the "must_haves" section claims the artifact "provides: send_health_snapshot one-way IPC helper" without acknowledging it is a new function. This is a minor documentation gap, not a structural issue, but it should be flagged as a new artifact rather than a modified one.

#### MEDIUM: `get_current_user_sid()` helper not implemented

**Plan 01 (58.4-01-PLAN.md, Task 1)** requires resolving the user SID from the process token via `OpenProcessToken -> GetTokenInformation(TokenUser) -> ConvertSidToStringSidA`. No such helper exists in the current codebase. The plan provides a fallback to "S-1-5-18" (SYSTEM) but does not include the implementation as a task. This is a new Windows API integration that requires careful error handling and testing.

**Impact:** The `user_sid` field in `DiagnosticSnapshot` will be empty or hardcoded to SYSTEM for all snapshots until this helper is implemented. This reduces the forensic value of diagnostic snapshots.

**Mitigation:** Add a dedicated task in Plan 01 to implement `get_current_user_sid()` with unit tests. The helper should be placed in a new file (e.g., `dlp-hook-dll/src/sid.rs`) or in `lib.rs` if small enough.

#### MEDIUM: Plan 04 integration test for blocked write audit contains hash is too heavy

**Plan 04 (58.4-04-PLAN.md, Task 4)** proposes testing `test_blocked_write_audit_contains_hash` at the `handle_hook_request` level with a pre-populated `HashCache`. However, as noted in the HIGH concern above, `HashCache` does not exist and `HookResponse` lacks hash fields. The test cannot be written as described until the schema changes from Plan 02 are complete. The plan acknowledges this may be "too heavy for a pure IPC integration test" but does not provide a concrete fallback test design.

**Mitigation:** Split Plan 04 into two waves: wave 1 tests the hook DLL unit tests (snapshot push, hash computation, health emission), wave 2 tests the integration paths after the schema changes from Plan 02 are landed. The integration test for hash attachment should mock the `HashEvidence` frame ingestion and verify the audit event builder path.

#### LOW: `classification_age_ms` is hardcoded to 0 in Plan 01

**Plan 01 (58.4-01-PLAN.md, Task 1)** sets `classification_age_ms: 0` with a note that "cache age not tracked in this closure; acceptable per D-02 discretion." While this is acceptable per the locked decision, it means diagnostic snapshots will not include the cache staleness information that operators need to triage false positives caused by stale cache data. This is a known limitation, not a bug, but it should be documented in the plan's "Deferred Ideas" section.

#### LOW: `matched_policy_id` and `enforcement_mode` are `None` in diagnostic snapshots

**Plan 01 (58.4-01-PLAN.md, Task 1)** acknowledges that `matched_policy_id` and `enforcement_mode` are not available in the hook DLL without parsing the `HookResponse`. This is correct — the hook DLL only receives the `Decision` enum, not the full ABAC evaluation metadata. However, this significantly reduces the diagnostic value of snapshots. The plan notes this is "acceptable per D-02" but does not propose a future improvement path.

**Mitigation:** Consider extending `HookResponse` to optionally include `matched_policy_id` and `enforcement_mode` in a future phase. This would require a protocol version bump but would greatly improve false-positive triage.

### Suggestions

1. **Rewrite Plan 02 Task 2 to acknowledge the `HookResponse` hash field gap.** The plan should explicitly state that `HookResponse` does not currently have hash fields and that adding them is a prerequisite. The timing constraint (hash computed after response received) should be documented, and the `HashEvidence` frame approach should be promoted from "option B" to the primary architecture.

2. **Add a prerequisite task to Plan 02 for `HookResponse` schema extension.** Before any hash wiring can occur, `dlp-common/src/hook_ipc.rs` must be updated to add `content_sha256: Option<String>`, `hash_truncated: bool`, `hash_skipped: bool` to `HookResponse` with `#[serde(default)]`. This is a cross-crate change that affects all IPC peers.

3. **Clarify health emission cadence in Plan 03.** Either align with the existing `EMIT_INTERVAL = 1000` or provide a documented rationale for 100. If 100 is chosen, ensure the counter is incremented only on actual pipe round-trips (cache misses), not on all `record_latency` calls.

4. **Add `get_current_user_sid()` implementation task to Plan 01.** This is new Windows API work that should not be implicit.

5. **Split Plan 04 into pre-schema and post-schema test waves.** Unit tests in `dlp-hook-dll` can be written immediately. Integration tests requiring `HashEvidence` or `HookResponse` hash fields must wait for the schema changes from Plan 02.

6. **Consider a simpler hash evidence approach.** Instead of a new `HashEvidence` IPC frame and `HashCache`, consider extending `HookRequest` to include the hash fields. The hook computes the hash BEFORE sending the `HookRequest` in `classify_handle`. Wait — the hash should only be computed on DENY, and the hook doesn't know the decision until after the `HookResponse` is received. So this approach doesn't work. The `HashEvidence` frame is indeed the correct architecture, but the plan should be honest about the complexity.

### Risk Assessment

**Overall Risk: HIGH**

Justification: Three HIGH-severity concerns were identified, all of which could block execution or produce incorrect results:
1. The `HookResponse` hash field gap invalidates Plan 02's core architecture assumption.
2. The `HashEvidence` frame approach requires significant cross-crate work that the plan underestimates.
3. The health emission cadence discrepancy could cause unexpected IPC overhead or incorrect counter behavior.

The plans are well-structured and follow established patterns, but they contain false assumptions about the current state of the codebase. These must be corrected before `/gsd-execute-phase` is run. The risk is mitigated by the fact that all issues are detectable at compile time (schema mismatches) or test time (counter behavior), but undetected they would produce a broken differentiator pipeline.
