# Phase 58.4: Code Review Report

**Reviewed:** 2026-07-06T07:22:31Z
**Depth:** standard
**Files Reviewed:** 35

## Summary

This review re-examines the Phase 58.4 implementation that wires diagnostic snapshots (DIFF-02), content hashing (DIFF-03), and self-health telemetry (DIFF-04) into the hook DLL deny paths. Several findings from the prior review artifact are now invalid because the source has been corrected (TLS parsing, handle-request envelope framing, hash-cache TTL, `bypass_alerts` CHECK constraint, blocked-write audit handle correlation, native-write hash coverage, and health-snapshot error handling). This report removes those and records the verified BLOCKER and WARNING issues that remain.

Two blockers remain: the hook DLL still performs IAT patching directly inside `DllMain` under the Windows loader lock, and handle-based hooks bypass the shared-memory cache and fail-mode state machine entirely. Five warnings cover empty-list TUI navigation, a no-op diagnostic `since` filter, disabled diagnostic-ring expiry on QPC failure, silent SID fallback to SYSTEM, and empty `abac_resource` fields in handle-based diagnostic snapshots.

## Blockers

### BL-01: IAT Patching Runs Inside `DllMain` Under the Loader Lock

**File:** `dlp-hook-dll/src/lib.rs:666-678`, `dlp-hook-dll/src/lib.rs:720-755`
**Issue:** `DllMain` calls `init()` directly from `DLL_PROCESS_ATTACH`. `init()` walks the host module's import table and patches entries (via `patch_iat`, which calls `VirtualProtect`/`WriteProcessMemory`-style writes) while the Windows loader lock is held. Patching imports under the loader lock is a well-known source of deadlocks and crashes: resolving or writing an IAT entry can trigger load-order dependencies that try to acquire the same loader lock.

**Fix:** Defer all IAT patching out of `DllMain`. Set a lazy-initialisation flag in `DllMain` and perform the actual patching on the first trampoline invocation, or spawn a one-shot worker thread to do the patching before any hooked API is called. The ntdll patcher already uses this lazy pattern; the IAT patcher should do the same.

```rust
// In DllMain(DLL_PROCESS_ATTACH):
LAZY_INIT_REQUIRED.store(true, Ordering::Relaxed);

// In each trampoline entry, or a shared pre-classify helper:
if LAZY_INIT_REQUIRED.swap(false, Ordering::SeqCst) {
    init();
}
```

### BL-02: Handle-Based Classification Bypasses Cache and Fail-Mode Logic

**File:** `dlp-hook-dll/src/trampolines.rs:605-697`, `dlp-hook-dll/src/lib.rs:1154-1186`
**Issue:** `classify_and_log_handle` always performs a synchronous named-pipe round-trip through `classify_handle`. Unlike `classify_and_log_path`, it never consults the shared-memory classification cache, never evaluates `FailState::Degraded`/`Isolated`/`Resync`, and never applies tier-gated fail-mode decisions. When the agent pipe is down, handle-based writes (WriteFile, WriteFileEx, NtWriteFile, NtSetInformationFile) fail-closed even for T1/T2 data that the documented fail-open semantics should allow. This breaks the fail-mode ABAC invariant and can cause unnecessary application failures.

**Fix:** Refactor `classify_and_log_handle` to share the same decision pipeline as `classify_and_log_path`: check the allowlist, check the shared-memory cache and thread-local LRU, evaluate the current `FailState`, and only round-trip when Healthy (or during a Degraded retry). Keep the handle-to-path resolution inside the agent by continuing to send the `handle://<value>` envelope.

```rust
// Pseudocode for the shared pipeline:
let op = if is_write_action(action) { HookOp::Write } else { HookOp::Read };
let cache_lookup = crate::classification_cache::CacheLookup::get();
let cache_classification = cache_lookup.and_then(|c| c.lookup_by_handle(handle_value, op, now_secs));
match get_fail_state().current_state() {
    FailState::Healthy => { /* pipe on cache miss */ }
    FailState::Degraded => { /* cache or retry */ }
    FailState::Isolated => crate::fail_mode::decide_isolated(cache_classification, op),
    FailState::Resync => { /* flush LRU, then healthy path */ }
}
```

## Warnings

### WR-01: Menu Navigation Can Panic on Empty Lists

**File:** `dlp-admin-cli/src/screens/dispatch.rs:99-109`
**Issue:** `nav(selected, count, key)` does not guard against `count == 0`. The Up branch computes `selected.checked_sub(1).unwrap_or(count - 1)`, which underflows when `count` is 0. The Down branch computes `(*selected + 1) % count`, which divides by zero when `count` is 0. Current dynamic callers (policy/agent/device lists) guard against empty lists, but the helper is also used for fixed-size menus and could be called from a future screen with zero items, crashing the admin CLI.

**Fix:** Return early when the menu is empty:

```rust
fn nav(selected: &mut usize, count: usize, key: KeyCode) {
    if count == 0 {
        return;
    }
    match key {
        KeyCode::Up => *selected = selected.checked_sub(1).unwrap_or(count - 1),
        KeyCode::Down => *selected = (*selected + 1) % count,
        _ => {}
    }
}
```

### WR-02: Diagnostic `since` Filter Is a No-Op

**File:** `dlp-agent/src/diagnostic_aggregator.rs:158-169`
**Issue:** `matches_filter` accepts a `since: Option<DateTime<Utc>>` but only binds it to `_` and returns `true`. Admin API callers requesting only snapshots after a given time therefore receive the full, unfiltered set. This silently breaks the documented time-window filtering and makes audit triage unreliable.

**Fix:** Add a wall-clock capture timestamp to `DiagnosticSnapshot` (or maintain an agent boot-time QPC baseline) and implement the comparison. Until that is available, reject or clearly document that the `since` parameter is unsupported, rather than silently ignoring it.

```rust
if let Some(ref since) = filter.since {
    if let Some(captured_at) = snap.wall_clock_utc {
        if captured_at < *since {
            return false;
        }
    }
}
```

### WR-03: Diagnostic-Ring Expiry Disabled When QPC Frequency Fails

**File:** `dlp-hook-dll/src/diagnostic_ring.rs:81-99`, `dlp-hook-dll/src/diagnostic_ring.rs:137-155`
**Issue:** `drain_snapshots` computes `qpc_ok = now_qpc > 0 && freq > 0`. If `QueryPerformanceFrequency` fails and returns 0, the expiry check is skipped entirely. Old snapshots are then retained until the 1000-entry ring wraps, so operators may receive stale diagnostic context. While the cap prevents unbounded growth, stale data can still mislead incident response.

**Fix:** Fall back to wall-clock expiry when QPC frequency is unavailable:

```rust
let (now_qpc, freq) = (unsafe { query_performance_counter() }, unsafe { query_performance_frequency() });
let one_hour_ticks = freq.saturating_mul(ENTRY_EXPIRY_SECONDS);
let qpc_ok = now_qpc > 0 && freq > 0;
let now_wall = std::time::SystemTime::now().duration_since(std::time::UNIX_EPOCH).ok();
// ...
let expired = if qpc_ok {
    snapshot.timestamp_qpc > 0 && now_qpc.wrapping_sub(snapshot.timestamp_qpc) > one_hour_ticks
} else if let (Some(now), Some(ts)) = (now_wall, snapshot.timestamp_secs) {
    now.as_secs().saturating_sub(ts) > ENTRY_EXPIRY_SECONDS
} else {
    false
};
if expired { continue; }
```

### WR-04: SID Resolution Silently Falls Back to SYSTEM

**File:** `dlp-hook-dll/src/sid.rs:19-87`
**Issue:** `get_current_user_sid` returns `"S-1-5-18"` (SYSTEM) on any failure path: token open failure, buffer allocation failure, SID conversion failure, or a null SID pointer. No log or debug message is emitted. When the fallback is hit, every diagnostic snapshot and audit event attributes the operation to SYSTEM, degrading forensic attribution and making it impossible to distinguish a real SYSTEM process from a user process whose SID could not be resolved.

**Fix:** Log each fallback path with the specific failure reason (without exposing sensitive data), and consider returning a sentinel such as `"S-1-0-0"` (NULL SID) so consumers can detect the failure instead of misattributing to SYSTEM.

```rust
if result.is_err() {
    crate::debug_log("[dlp-hook] get_current_user_sid: OpenProcessToken failed, falling back to SYSTEM\0");
    return "S-1-5-18".to_string();
}
```

### WR-05: Handle-Based Deny Snapshots Record Empty `abac_resource`

**File:** `dlp-hook-dll/src/trampolines.rs:675-691`, `dlp-hook-dll/src/lib.rs:1154-1186`
**Issue:** `classify_and_log_handle` constructs the `DiagnosticSnapshot` with `abac_resource: path.to_string()`. However, handle-based trampolines such as `HookWriteFile` and `HookNtWriteFile` pass `""` as the `path` argument, so the resulting snapshots have an empty resource field. The DIFF-02 contract explicitly calls for falling back to `format!("handle:{}", handle_value)` when no path is available, so the current snapshots omit the only correlation key available for handle-based denies.

**Fix:** Use the handle fallback as documented:

```rust
abac_resource: if path.is_empty() {
    format!("handle:{}", handle_value)
} else {
    path.to_string()
},
```
