# Phase 58.4: Code Review Report

**Reviewed:** 2026-07-04T12:00:00Z
**Depth:** standard
**Files Reviewed:** 35
**Status:** issues_found

## Summary

This review covers the Phase 58.4 implementation that wires three differentiator capabilities into the hook DLL deny paths: DIFF-02 (diagnostic snapshots), DIFF-03 (content SHA-256 hashing), and DIFF-04 (self-health monitoring). The review examined 35 source files across the dlp-admin-cli, dlp-agent, dlp-common, dlp-hook-dll, and dlp-server crates.

The implementation follows established patterns and the DIFF features are structurally in place, but **three critical correctness/security issues** were identified that must be fixed before this code ships. These include an inverted TLS-verification environment variable in the admin CLI, a protocol routing mismatch that prevents handle-based classification requests from reaching the agent's evaluator, and a fail-mode state-machine bug that fail-closes writes during RESYNC contrary to the documented behavior. Twelve warnings cover TTL/expire logic, database CHECK constraints, timeout accounting, fail-mode bypasses, and hash-coverage gaps. Four info-level items note dead code and cleanup/signal hygiene.

## Critical Issues

### CR-01: Inverted TLS Verification Environment Variable

**File:** `dlp-admin-cli/src/client.rs:69-84`
**Issue:** The logic that parses `DLP_ENGINE_TLS_VERIFY` is inverted. Setting the variable to `"false"` sets `tls_verify = true`, which causes the HTTP client builder to call `danger_accept_invalid_certs(true)`. An operator attempting to disable TLS verification for a self-signed dev cert will succeed, but the same code path is also reachable in production if the variable is ever set to `"false"`. This silently disables certificate validation for an admin tool that authenticates to the DLP server with JWT/bcrypt credentials, enabling trivial man-in-the-middle attacks.

**Fix:**
```rust
let tls_verify = std::env::var("DLP_ENGINE_TLS_VERIFY")
    .map(|v| v.to_ascii_lowercase() != "false")
    .unwrap_or(true);

if !tls_verify {
    tracing::warn!("TLS verification disabled (DLP_ENGINE_TLS_VERIFY=false)");
    builder = builder.danger_accept_invalid_certs(true);
}
```

### CR-02: Handle-Based Classification Requests Are Not Routable by the Agent

**File:** `dlp-hook-dll/src/lib.rs:1018-1027`
**Issue:** `classify_handle` serializes a raw `HandleHookRequest` and sends it via `pipe_client::send_raw_request`. `HandleHookRequest` is a standalone struct; it is **not** a variant of `IpcPayloadV1`. The agent's `HookIpcServer::handle_connection` (`dlp-agent/src/hook_ipc.rs:509-775`) first tries to deserialize the frame as `IpcEnvelope`, then falls back to legacy raw `HookRequest`. It has no branch for raw `HandleHookRequest`, so the frame is logged as malformed and no response is sent. The client times out, `classify_handle` returns `Err`, and `classify_and_log_handle` fail-closes the operation. Consequently, every handle-based write (`WriteFile`, `WriteFileEx`, `SetFileInformationByHandle`, `NtWriteFile`, `NtSetInformationFile`) is denied when the agent pipe is reachable, making normal application I/O impossible.

**Fix:** Wrap handle classification in `IpcEnvelope::V1(IpcPayloadV1::Request(...))` and extend `HookRequest` (or add a new `IpcPayloadV1` variant) to carry `handle_value`. The agent must route that payload to the ABAC evaluator and resolve the handle to a path server-side. At minimum, send an `IpcEnvelope` the server understands:
```rust
let envelope = dlp_common::hook_ipc::IpcEnvelope::V1(dlp_common::hook_ipc::IpcMessageV1 {
    payload: dlp_common::hook_ipc::IpcPayloadV1::Request(HookRequest {
        path: format!("handle://{handle_value}"),
        action: action.to_string(),
        pid: std::process::id(),
        ..Default::default()
    }),
});
let payload = bincode::serialize(&envelope)?;
let response_bytes = pipe_client::send_raw_request(pipe_name, &payload, 50)?;
```
Then add agent-side handle-to-path resolution before ABAC evaluation.

### CR-03: RESYNC Fail-State Fail-Closes Unknown Writes Instead of Using Cache/Pipe

**File:** `dlp-hook-dll/src/fail_mode.rs:467-471`
**Issue:** The doc comment on `decide_resync` states "Same logic as Healthy: use cache if available, otherwise pipe." The implementation, however, calls `decide_isolated(classification, op)`. `decide_isolated` denies any write operation when no cache classification is present. During RESYNC the hook DLL is expected to flush the LRU and re-evaluate with fresh cache data; hard-denying writes that are not yet cached breaks the contract and can cause data loss or application failures after a cache version bump. The unit test at line 852-858 even encodes the wrong behavior, asserting that `decide_resync(Some(T4), Write)` denies.

**Fix:**
```rust
pub fn decide_resync(classification: Option<Classification>, op: HookOp) -> Option<DenyReturn> {
    // Same logic as Healthy: authoritative decision from cache when available;
    // when unknown, defer to the pipe (caller will attempt pipe round-trip).
    match classification {
        Some(cls) => decide_cached(cls, op),
        None => None, // caller proceeds to pipe
    }
}
```
Update the unit test to match the documented contract.

## Warnings

### WR-01: HashCache Lookup Returns Expired Entries

**File:** `dlp-agent/src/hash_cache.rs:57-61`
**Issue:** `lookup_hash` returns the cached frame unconditionally. The doc comment claims it returns `Some(frame)` only when "found and not expired," but the TTL is never checked at lookup time. Stale hash evidence can therefore be attached to audit events long after the 60-second TTL has elapsed, especially if the cleanup thread is delayed.

**Fix:**
```rust
pub fn lookup_hash(cache: &HashCache, pid: u32, handle_value: u64) -> Option<HashEvidenceFrame> {
    cache.get(&(pid, handle_value)).and_then(|entry| {
        let (frame, inserted) = entry.value();
        if Instant::now().duration_since(*inserted) < Duration::from_secs(60) {
            Some(frame.clone())
        } else {
            None
        }
    })
}
```

### WR-02: bypass_alerts CHECK Constraint Excludes Valid BypassReason Variants

**File:** `dlp-server/src/db/mod.rs:532`
**Issue:** The `correlation_reason` column is constrained to `('no_hook_journal', 'op_mismatch', 'hook_overwritten')`. The `BypassReason` enum also defines `PatchRaced` and `EdrDetected`. `dlp-agent/src/hook_ipc.rs:570` converts `JournalDegraded` alerts into `BypassAlert { reason: BypassReason::EdrDetected, ... }`. Inserting that alert into the SQLite repository will violate the CHECK constraint and fail, dropping bypass evidence on the floor.

**Fix:** Extend the CHECK constraint (and any corresponding repository enums) to include all `BypassReason` variants:
```sql
correlation_reason TEXT NOT NULL CHECK(correlation_reason IN (
    'no_hook_journal', 'op_mismatch', 'hook_overwritten', 'PatchRaced', 'EdrDetected'
))
```

### WR-03: Pipe Read Timeout Is Per 64 KiB Slice, Not Per Frame

**File:** `dlp-hook-dll/src/pipe_client.rs:470-481`, `dlp-hook-dll/src/pipe_client.rs:428-440`
**Issue:** `read_exact_with_timeout` applies `timeout_ms` to each 64 KiB slice. A large frame (e.g., a 64 MiB diagnostic pull response) can therefore take up to 1,000 times the intended timeout before `PipeError::Timeout` is returned. This undermines the watchdog's bounded-latency guarantees.

**Fix:** Track an overall deadline and pass the remaining time to each `WaitForSingleObject` call:
```rust
let deadline = Instant::now() + Duration::from_millis(timeout_ms as u64);
while remaining > 0 {
    let slice_timeout = deadline.saturating_duration_since(Instant::now()).as_millis() as u32;
    if slice_timeout == 0 { return Err(PipeError::Timeout); }
    // ... use slice_timeout instead of timeout_ms ...
}
```

### WR-04: Diagnostic Snapshot Expiry Is Disabled When QPC Fails

**File:** `dlp-hook-dll/src/diagnostic_ring.rs:81-96`, `dlp-hook-dll/src/diagnostic_ring.rs:133-151`
**Issue:** `drain_snapshots` computes `one_hour_ticks = query_performance_frequency().saturating_mul(ENTRY_EXPIRY_SECONDS)`. If `QueryPerformanceFrequency` fails, the function returns 0, making `one_hour_ticks == 0`. The expiry check `age > one_hour_ticks` is then never true, so old snapshots are never evicted and can accumulate until the 1000-entry ring wraps. A failing QPC is rare but possible on exotic hardware or under memory pressure; the function also returns 0 on non-Windows builds.

**Fix:** Treat QPC failure as a signal to fall back to wall-clock expiry, or explicitly skip returning expired snapshots by checking `freq == 0`:
```rust
let (now_qpc, freq) = (unsafe { query_performance_counter() }, unsafe { query_performance_frequency() });
let one_hour_ticks = freq.saturating_mul(ENTRY_EXPIRY_SECONDS);
let qpc_ok = now_qpc > 0 && freq > 0;
// ...
if qpc_ok && snapshot.timestamp_qpc > 0 && now_qpc.wrapping_sub(snapshot.timestamp_qpc) > one_hour_ticks {
    continue;
}
```

### WR-05: USB Serial Matching Accepts Any Candidate When Target Has No Serial

**File:** `dlp-common/src/usb.rs:301-306`, `dlp-common/src/usb.rs:770-775`
**Issue:** When the target serial is `"(none)"`, the match arms `("(none)", "(none)") => true` and `("(none)", _) => true` accept the first candidate with matching VID/PID regardless of the candidate's real serial. If multiple devices share a VID/PID but have different real serials, the function can return the description or instance ID of the wrong device. This weakens device-identity resolution for USB enforcement.

**Fix:** When the target has no serial, only match candidates that also have no serial:
```rust
let serial_match = match (parsed.serial.as_str(), candidate.serial.as_str()) {
    ("(none)", "(none)") => true,
    ("(none)", _) => false, // do not accept a real serial as a match for a no-serial target
    (_, "(none)") => false,
    (t, c) => t == c,
};
```

### WR-06: HookRequest Operation Field Defaults to Read for All Actions

**File:** `dlp-hook-dll/src/lib.rs:991-998`
**Issue:** `classify_path` constructs a `HookRequest` with `..Default::default()`, which sets `op: HookOp::Read` regardless of the actual action. The local cache lookup in `classify_and_log_path` (`trampolines.rs:169-173`) computes the correct `op` from `action`, so the cache decision itself is correct. However, the `op` value transmitted to the agent is misleading for logging, telemetry, and any future agent-side fast-path logic. It also means the agent cannot perform operation-specific decisions based on the request payload.

**Fix:** Compute and set `op` explicitly in `classify_path`:
```rust
let op = if action.eq_ignore_ascii_case("WRITE")
    || action.eq_ignore_ascii_case("CREATE")
    || action.eq_ignore_ascii_case("NT_WRITE")
{
    dlp_common::hook_ipc::HookOp::Write
} else {
    dlp_common::hook_ipc::HookOp::Read
};
let req = HookRequest {
    path: path.to_string(),
    action: action.to_string(),
    source_volume_class,
    destination_volume_class,
    pid: std::process::id(),
    op,
    ..Default::default()
};
```

### WR-07: Handle-Based Classification Bypasses Fail-Mode State Machine

**File:** `dlp-hook-dll/src/trampolines.rs:584-676`
**Issue:** `classify_and_log_handle` always performs a synchronous pipe round-trip and fail-closes on any error. Unlike `classify_and_log_path`, it never checks the shared-memory cache, never evaluates `FailState::Degraded`/`Isolated`/`Resync`, and never applies tier-gated fast-path decisions. In Degraded or Isolated states, handle-based operations therefore continue to depend on a pipe that may be down, and they deny operations that should be allowed based on cached classifications.

**Fix:** Refactor `classify_and_log_handle` to share the same decision pipeline as `classify_and_log_path`: check cache, evaluate fail-mode state, and only round-trip when Healthy (or Degraded with retry). If handle-to-path resolution is required, do it before the shared pipeline.

### WR-08: NtWriteFile Paths Do Not Compute Content Hash on Deny

**File:** `dlp-hook-dll/src/trampolines.rs:1677`, `dlp-hook-dll/src/trampolines.rs:2145`
**Issue:** DIFF-03 content hashing is only implemented in the Win32 `HookWriteFile` and `HookWriteFileEx` trampolines. The native `HookNtWriteFile` and `NtdllTrampolineNtWriteFile` trampolines call `classify_and_log_handle` and return `STATUS_ACCESS_DENIED` without hashing. Applications that write via `NtWriteFile` (common for bypass-aware code and some runtimes) will produce `Block` audit events without hash evidence, weakening forensic value.

**Fix:** Add the same hash-evidence block used in `HookWriteFile` to `HookNtWriteFile` and `NtdllTrampolineNtWriteFile` before returning the deny value.

### WR-09: IAT Patching Is Performed Inside DllMain Under Loader Lock

**File:** `dlp-hook-dll/src/lib.rs:578-588`
**Issue:** `DllMain` calls `init()` directly from `DLL_PROCESS_ATTACH`. `init()` walks the IAT and calls `VirtualProtect`/`WriteProcessMemory`-style writes to patch import entries while the Windows loader lock is held. Although the code correctly avoids creating the ntdll patcher from `DllMain`, the IAT patching itself is still loader-lock work and can deadlock if any patched import triggers load-order dependencies. This is a long-standing anti-pattern for API-hook DLLs.

**Fix:** Defer all patching to a worker thread created from `DllMain` (or to the first trampoline invocation), as is already done for the ntdll patcher. Set a flag in `DllMain` and let `get_fail_state` or the first hooked API call perform the actual patching.

### WR-10: Blocked-Write Audit Uses Handle Value 0 for Hash Correlation

**File:** `dlp-agent/src/service.rs:1653-1660`
**Issue:** When emitting a `Block` audit event for a denied write, the code looks up the hash cache with `handle_value: 0` because `HookRequest` does not carry the real handle value. The hook DLL sends `HashEvidenceFrame` keyed by the actual handle value, so the cache lookup will usually miss. The inline comment acknowledges this as a "known limitation," but it means the hash-evidence feature is effectively non-functional for its primary use case.

**Fix:** Add `handle_value` to `HookRequest`, populate it in the handle-based trampolines, and use it in the cache lookup:
```rust
let hash = crate::hash_cache::lookup_hash(&hash_cache_for_closure, req.pid, req.handle_value);
```

### WR-11: Health Snapshot Send Result Is Silently Dropped

**File:** `dlp-hook-dll/src/trampolines.rs:112`
**Issue:** `record_pipe_round_trip_and_maybe_emit` calls `pipe_client::send_health_snapshot(...)` and discards the result with `let _ = ...`. If the pipe is disconnected or the send fails, the failure is invisible to telemetry and operators, making the DIFF-04 health-monitoring system unreliable.

**Fix:**
```rust
if let Err(e) = crate::pipe_client::send_health_snapshot(crate::DEFAULT_PIPE_NAME, &snapshot) {
    crate::debug_log(&format!("[dlp-hook] health snapshot send failed: {}\0", e));
}
```

### WR-12: EngineClient::new Ignores Its TLS Verification Parameter

**File:** `dlp-agent/src/engine_client.rs:66`, `dlp-agent/src/service.rs:1793`
**Issue:** `EngineClient::new` takes a `_tls_verify: bool` parameter that is deliberately unused (prefixed with underscore). The fallback in `service.rs` passes `false` with a comment suggesting it will "skip TLS verification if env is misconfigured," but the parameter has no effect; TLS verification is always enabled. This is misleading and creates a future hazard if the parameter is ever wired up inconsistently.

**Fix:** Either honor the parameter:
```rust
pub fn new(base_url: impl Into<String>, tls_verify: bool) -> Result<Self> {
    let client = Client::builder()
        .timeout(Duration::from_secs(10))
        .danger_accept_invalid_certs(!tls_verify)
        .build()
        .context("failed to build reqwest HTTPS client")?;
    Ok(Self { client, base_url: base_url.into() })
}
```
or remove it and update the call sites and comments.

### IN-02: Hash Cache Cleanup Thread Has No Shutdown Signal

**File:** `dlp-agent/src/hash_cache.rs:43-50`
**Issue:** `spawn_hash_cache_cleanup_task` spawns a thread that sleeps for the TTL and then evicts stale entries. If the `HashCache` is dropped (e.g., during agent restart or test teardown), the thread continues running until the process exits. This is not a leak in the strict sense, but it is unclean and can interfere with deterministic shutdown.

**Fix:** Accept an `Arc<AtomicBool>` shutdown flag and poll it with a short sleep interval:
```rust
pub fn spawn_hash_cache_cleanup_task(
    cache: HashCache,
    ttl: Option<Duration>,
    shutdown: Arc<std::sync::atomic::AtomicBool>,
) {
    let cutoff = ttl.unwrap_or(Duration::from_secs(60));
    std::thread::spawn(move || {
        while !shutdown.load(std::sync::atomic::Ordering::Relaxed) {
            std::thread::sleep(cutoff);
            let now = Instant::now();
            cache.retain(|_key, (_frame, inserted)| now.duration_since(*inserted) < cutoff);
        }
    });
}
```

### IN-03: SID Fallback to SYSTEM Is Silent

**File:** `dlp-hook-dll/src/sid.rs:19-87`
**Issue:** `get_current_user_sid` returns the SYSTEM SID `"S-1-5-18"` on any failure (token open failure, buffer allocation failure, SID conversion failure, etc.) without logging. When the fallback is hit, all diagnostic snapshots and audit events will attribute the operation to SYSTEM, reducing forensic value.

**Fix:** Add a `tracing::warn!` call before each fallback return, including the specific failure reason (without exposing sensitive data).

### IN-04: Unnecessary `.unwrap_or_default()` for UNIX Epoch in Telemetry

**File:** `dlp-hook-dll/src/trampolines.rs:209-212`, `dlp-hook-dll/src/trampolines.rs:918-921`
**Issue:** Several trampolines compute the current wall-clock timestamp using `SystemTime::now().duration_since(UNIX_EPOCH).unwrap_or_default()`. This is only ever expected to fail if the system clock is before 1970, in which case silently returning `Duration::ZERO` masks a serious clock problem.

**Fix:** Use `expect("system clock before 1970")` or propagate the error to the caller so a misconfigured clock is surfaced:
```rust
let now_secs = std::time::SystemTime::now()
    .duration_since(std::time::UNIX_EPOCH)
    .expect("system clock must be after 1970-01-01")
    .as_secs();
```
