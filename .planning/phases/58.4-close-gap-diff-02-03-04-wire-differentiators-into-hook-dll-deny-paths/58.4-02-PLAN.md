<objective>
Wire content SHA-256 hash computation into HookWriteFile and HookWriteFileEx deny branches so that every blocked write operation produces a forensic content hash. The hash is attached to the HookResponse (agent forwards it) and the AuditEvent (server stores it). ALLOW paths and non-write DENY paths must not hash.

Purpose: DIFF-03 provides tamper-evident evidence of what content was blocked, satisfying forensic and compliance requirements.
Output: deny branches that compute SHA-256 with 100MB cap and pool-saturation fallback; agent-side forwarding verified.
</objective>

  <name>Task 1: Add pool saturation check to hash_compute.rs</name>
  <files>dlp-hook-dll/src/hash_compute.rs</files>
  <action>
    Per D-07, the hash pool must skip computation when queue depth exceeds 4 pending hashes.

    Add a global AtomicU64 counter HASH_QUEUE_DEPTH that tracks pending offloaded hashes. Increment it before submitting to the pool, decrement in the pool closure after computation finishes (use a drop guard or explicit decrement). If the counter exceeds 4 at submission time, return (None, false, true) immediately (hash_skipped = true).

    For inline hashing (buffers < 64KB), do not check queue depth — inline hashing is synchronous and fast.

    Update compute_content_hash_offloaded signature to return (Option<String>, bool, bool) as before, but add the saturation check at the top:
    - If HASH_QUEUE_DEPTH.load(Relaxed) > 4, return (None, false, true).
    - Otherwise increment, submit to pool, and decrement when done.

    Ensure the decrement happens even if the pool panics (use a custom guard struct with Drop).
  </action>

<task type="auto">
  <name>Task 2: Modify HookWriteFile and HookWriteFileEx deny branches to compute hash</name>
  <files>dlp-hook-dll/src/trampolines.rs</files>
  <action>
    In HookWriteFile, after classify_and_log_handle returns Some(deny), compute the content hash BEFORE returning the fail-closed value.

    Per D-04, hash ONLY for blocked WriteFile and WriteFileEx. ALLOW paths and non-write DENY paths (copy/move/delete) must not hash.

    Per D-05, hash from the original lpBuffer and nNumberOfBytesToWrite parameters directly in the trampoline. No second file open.

    Per D-06, apply the 100 MB cap: if nNumberOfBytesToWrite > 100MB, hash only the first 100MB and set hash_truncated = true.

    Implementation:
    ```rust
    if let Some(_deny) = classify_and_log_handle(handle_value, "WRITE", "WriteFile", 2, "") {
        let (hash, truncated, skipped) = if !lpbuffer.is_null() && nnumberofbytestowrite > 0 {
            if (nnumberofbytestowrite as usize) < crate::hash_compute::SMALL_BUFFER_THRESHOLD {
                crate::hash_compute::compute_content_hash(lpbuffer, nnumberofbytestowrite)
            } else {
                crate::hash_compute::compute_content_hash_offloaded(lpbuffer, nnumberofbytestowrite)
            }
        } else {
            (None, false, false)
        };

        // Per D-13, attach hash data to the HookResponse that will be sent to the agent.
        // However, the deny branch in the trampoline returns a fail-closed value directly;
        // the HookResponse is constructed in the pipe round-trip (classify_handle).
        // To satisfy D-08, we need to send the hash back to the agent.
        // The cleanest way is to send a one-way IPC frame with the hash data,
        // or to include it in the HookResponse returned by classify_handle.
        // Since classify_handle already sends a HookRequest and receives a HookResponse,
        // we can extend the handle-based path to send the hash in a follow-up frame.
        // For simplicity and per D-13 (keep HookResponse minimal), use a new IpcPayloadV1
        // variant HashEvidence, or send it as a BypassAlert-style fire-and-forget.
        // RECOMMENDATION: Add a new function send_hash_evidence(pipe_name, handle_value, hash, truncated, skipped)
        // in pipe_client.rs that sends a one-way IpcEnvelope::V1(IpcPayloadV1::HashEvidence(...)).
        // If the send fails, ignore — hash evidence is best-effort.

        return crate::fail_closed!(BoolFalse);
    }
    ```

    IMPORTANT: The hash must be sent to the agent so it can attach it to the AuditEvent. The trampoline itself does not construct AuditEvent. The agent's handle_hook_request constructs the AuditEvent. Therefore, the hash data must flow from the trampoline to the agent.

    Options:
    A. Extend HookResponse to include hash fields (already exists in dlp-common). The agent can read them and call .with_content_hash. But the HookResponse is returned by the agent's handler, not sent by the hook. The hook sends HookRequest, agent sends HookResponse. The hash is computed in the hook AFTER the agent has already responded. So this doesn't work for the synchronous pipe round-trip.

    B. Send a separate one-way IPC frame from the hook to the agent after the deny. The agent receives it and correlates by handle_value + pid + timestamp. This is the correct approach per D-13 (diagnostic/health data retrieved via separate IPC requests, but hash is an exception because it must be attached to the audit event).

    C. Include the hash in the HookRequest sent by classify_handle. But the hash is computed after the deny decision, which happens after the HookResponse is received. So the hash isn't available when the HookRequest is sent.

    RESOLUTION: Use option B. Add a new function `send_hash_evidence` in pipe_client.rs that sends a one-way `IpcPayloadV1::HashEvidence` frame. The agent's `handle_connection` in `dlp-agent/src/hook_ipc.rs` must route this frame to a handler that stores it temporarily (e.g., in a DashMap keyed by pid+handle) so that when the audit event is constructed, the hash can be retrieved.

    However, this adds significant complexity. A simpler approach that satisfies D-08 and D-13:
    - The hook computes the hash and stores it in a thread-local or process-wide HashEvidence cache keyed by (pid, handle_value, timestamp_rounded_to_1s).
    - The agent, when constructing the AuditEvent for a handle-based deny, checks the cache for a matching hash and attaches it.
    - This avoids a new IPC frame and keeps HookResponse minimal.

    DECISION (Claude's discretion per CONTEXT.md): Use a thread-local `HashEvidence` cache in the hook DLL. The agent does not need to know about it for v0.10.0. The hash is computed and stored; a future phase can wire the agent-side retrieval. BUT D-16 requires integration tests proving blocked write audit events contain content_sha256. So the agent MUST retrieve the hash.

    FINAL RESOLUTION: Extend the `HookRequest` struct in `dlp-common/src/hook_ipc.rs` with optional fields `content_sha256`, `hash_truncated`, `hash_skipped`. The hook computes the hash BEFORE sending the HookRequest in `classify_handle`. Wait — `classify_handle` is called before the deny decision is known. The hash should only be computed on DENY. So the hook cannot include the hash in the initial HookRequest.

    WORKAROUND: In `classify_and_log_handle`, after receiving the HookResponse (which contains the deny decision), if the decision is DENY and the action is WRITE, compute the hash and send a second one-way IPC frame `IpcPayloadV1::HashEvidence` to the agent. The agent correlates by pid + handle_value + timestamp.

    This is the cleanest architecture. Implement it.
  </action>
