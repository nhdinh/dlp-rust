# Phase 58.4: Close gap DIFF-02/03/04 — wire differentiators into hook DLL deny paths - Research

**Researched:** 2026-06-26
**Domain:** Rust / Windows Hook DLL / Diagnostic Ring Buffer / SHA-256 Content Hashing / Self-Health Monitoring / Named Pipe IPC
**Confidence:** HIGH

## Summary

Phase 58.4 is a **gap-closure phase** that makes the differentiator infrastructure built in Phase 58 actually produce real data by invoking it from the hook DLL deny paths and the consolidated hook IPC handler built in Phase 58.2. No new modules, no new TUI screens, no new SQLite schema — only wiring existing code into the right call sites.

The three requirements are:
- **DIFF-02 (Diagnostic snapshots)** — Push `DiagnosticSnapshot` on every DENY decision in `classify_and_log_path` and `classify_and_log_handle`; `PullDiagnostics` returns non-empty snapshots.
- **DIFF-03 (Content SHA-256 hash evidence)** — `HookWriteFile` / `HookWriteFileEx` deny branches compute `compute_content_hash` from `lpBuffer` and attach the hash to `HookResponse` / `AuditEvent`.
- **DIFF-04 (Hook DLL self-health)** — Emit `HookHealthSnapshot` every 100 pipe round-trips and on every `FailState` transition; agent-side `PullHealth` returns the current snapshot.

All infrastructure already exists from Phase 58: `diagnostic_ring.rs`, `hash_compute.rs`, `perf_telemetry.rs`, `HookIpcServer` builder methods, `IpcPayloadV1` variants, and `HookHealthSnapshot` / `DiagnosticSnapshot` types. This phase is purely integration work.

**Primary recommendation:** Implement in the order DIFF-02 -> DIFF-03 -> DIFF-04. DIFF-02 is the simplest (add a function call to the deny branch). DIFF-03 requires trampoline modification to pass `lpBuffer`/`nNumberOfBytesToWrite` into the hash path. DIFF-04 requires extending `perf_telemetry.rs` with health counter emission and a new cadence.

### Locked Decisions
- **D-01:** Push a `DiagnosticSnapshot` on **every DENY decision** returned by `classify_and_log_path` and `classify_and_log_handle`, regardless of the intercepted operation (`WriteFile`, `CopyFileExW`, `MoveFileExW`, `DeleteFileW`, etc.). This maximizes false-positive triage value without adding ALLOW-path overhead.
- **D-02:** The snapshot must include: `hook_function`, `classification_source` (`CacheHit` / `CacheMiss` / `Pipe`), `classification_age_ms`, `abac_subject` (resolved SID), `abac_resource` (path), `abac_action`, `abac_environment` (volume class, device health), `matched_policy_id`, `enforcement_mode`, `decision_latency_us`, `timestamp_qpc`, and `user_sid`.
- **D-03:** Reuse the existing in-memory `DiagnosticRing` (1000-entry lock-free buffer). If the ring is full, silently drop the oldest entry via `ArrayQueue::push` semantics.
- **D-04:** Compute SHA-256 **only for blocked `WriteFile` and `WriteFileEx`** operations. ALLOW paths and non-write DENY paths (copy/move/delete) do not hash content.
- **D-05:** Hash from the original `lpBuffer` / `nNumberOfBytesToWrite` parameters directly in the trampoline. No second file open.
- **D-06:** Apply the existing 100 MB cap: if `nNumberOfBytesToWrite > 100 MB`, hash only the first 100 MB and set `hash_truncated = true`.
- **D-07:** Use the existing 2-thread rayon hash pool. If the pool is saturated (queue depth > 4 pending hashes), skip hashing and set `hash_skipped = true`; the DENY still occurs.
- **D-08:** Attach the computed hash to the `AuditEvent` via `content_sha256`, `hash_truncated`, and `hash_skipped` fields. Also return it in `HookResponse` so the agent can forward it without a second lookup.
- **D-09:** Emit a `HookHealthSnapshot` every **100 pipe round-trips** by reusing the existing `PerfTelemetry` emission cadence, plus on every `FailState` transition (`Healthy → Degraded → Isolated → Resync`).
- **D-10:** The snapshot includes: `injected_pids`, `patched_modules`, `pipe_round_trips_60s`, `cache_hit_rate_60s`, `current_fail_state`, and `timestamp_secs`.
- **D-11:** `PullHealth` returns **only the current snapshot**. The agent maintains the 12-snapshot / 12-minute rolling history in its `HealthAggregator`.
- **D-12:** Health counters are updated lock-free with `AtomicU64` / `AtomicU8`; snapshot emission resets the 60-second counters atomically.
- **D-13:** Keep `HookResponse` minimal. Do not bloat it with diagnostic or health data. Hash data is the only enrichment allowed in `HookResponse` (via existing optional fields). Diagnostic and health data are retrieved via the existing `PullDiagnostics` / `PullHealth` IPC requests.
- **D-14:** Verify that the consolidated `HookIpcServer` routes `PullDiagnostics`, `PullHealth`, and `RequestOverride` to the correct Phase 58 handlers without re-introducing duplicate initialization.
- **D-15:** Unit tests in `dlp-hook-dll` prove: snapshot is pushed on DENY, hash matches known value for a test buffer, 100 MB truncation works, health counters increment and emit correctly.
- **D-16:** Integration tests in `dlp-agent` prove: `PullDiagnostics` returns non-empty snapshots after a DENY; `PullHealth` returns a valid snapshot; blocked write audit events contain `content_sha256`.

**What:** On every DENY decision in `classify_and_log_path` and `classify_and_log_handle`, capture a `DiagnosticSnapshot` with full decision context and push to the lock-free ring buffer.
**When to use:** DIFF-02 implementation in both path-based and handle-based trampolines.
**Example:**

### Pattern 2: SHA-256 Computation in WriteFile Deny Branch
**What:** Compute SHA-256 from `lpBuffer` on blocked `WriteFile`/`WriteFileEx`, offloaded to the dedicated rayon thread pool for buffers > 64KB.
**When to use:** DIFF-03 in `HookWriteFile` and `HookWriteFileEx` trampolines only.
**Example:**

        if nnumberofbytestowrite < 64 * 1024 {
            crate::hash_compute::compute_content_hash(lpbuffer, nnumberofbytestowrite)
        } else {
            crate::hash_compute::compute_content_hash_offloaded(lpbuffer, nnumberofbytestowrite)
        }
    } else {
        (None, false, false)
    };

    // DIFF-02: Emit diagnostic snapshot
    // (see Pattern 1)

    // Return deny with hash data attached to HookResponse
    // Note: HookResponse is returned via pipe, but the deny path here returns
    // a fail-closed value directly. The hash must be attached to the
    // HookResponse that the agent receives, or sent separately.
    // Per D-13, HookResponse should carry hash data via existing optional fields.
    return crate::fail_closed!(BoolFalse);

### Pattern 3: Health Counter Emission
**What:** Extend `PerfTelemetry` to emit `HookHealthSnapshot` every 100 pipe round-trips and on every `FailState` transition.
**When to use:** DIFF-04, integrated into existing `perf_telemetry.rs`.
**Example:**
```rust
// In perf_telemetry.rs, add to record_latency or a new function:
pub fn emit_health_snapshot() -> dlp_common::hook_ipc::HookHealthSnapshot {
    let pipe_round_trips = PIPE_ROUND_TRIPS_60S.swap(0, Ordering::Relaxed);
    let cache_hits = CACHE_HITS_60S.swap(0, Ordering::Relaxed);
    let cache_misses = CACHE_MISSES_60S.swap(0, Ordering::Relaxed);
    let total = cache_hits + cache_misses;
    let hit_rate = if total > 0 { (cache_hits as f64) / (total as f64) } else { 0.0 };

    dlp_common::hook_ipc::HookHealthSnapshot {
        injected_pids: INJECTED_PIDS.load(Ordering::Relaxed),
        patched_modules: PATCHED_MODULES.load(Ordering::Relaxed),
        pipe_round_trips_60s: pipe_round_trips,
        cache_hit_rate_60s: hit_rate,
        current_fail_state: CURRENT_FAIL_STATE.load(Ordering::Relaxed),
        timestamp_secs: std::time::SystemTime::now()
            .duration_since(std::time::UNIX_EPOCH)
            .unwrap_or_default()
            .as_secs(),
    }
}
```

### Anti-Patterns to Avoid
- **Computing SHA-256 on ALLOW decisions:** D-04 explicitly limits hashing to blocked writes only. Computing on ALLOW would add unnecessary hot-path overhead.
- **Persisting diagnostic snapshots to disk:** D-03 mandates in-memory only. Writing to disk from the hook DLL would introduce I/O blocking and potential security issues.
- **Using a mutex for the diagnostic ring buffer:** The hook DLL hot path is multi-threaded (one trampoline per thread). A mutex would serialize all DENY decisions, creating a bottleneck.
- **Computing hash synchronously on the hooked thread for large buffers:** SHA-256 of 100MB can take milliseconds. The hooked thread must not block; use the rayon thread pool for buffers > 64KB.
- **Creating a new thread per hash computation:** Thread creation is expensive. Use the pre-sized rayon ThreadPool initialized lazily via OnceLock.
- **Emitting health snapshots from DllMain:** Windows holds the loader lock during DllMain. Any operation that might trigger initialization can deadlock. Use trampoline-first invocation.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Lock-free ring buffer | Hand-rolled CAS loop | `crossbeam-queue::ArrayQueue` | Battle-tested, correct memory ordering, handles ABA, MPMC-safe |
| SHA-256 implementation | Custom hash or `openssl` C bindings | `sha2` crate (pure Rust) | NIST FIPS 180-4 compliant, streaming API, already in workspace |
| Thread pool for CPU work | `std::thread::spawn` per task | `rayon::ThreadPool` (2 threads) | Work-stealing, already in workspace, bounded parallelism |
| Health counter atomic ops | `Mutex<u64>` | `AtomicU64` | Lock-free, no contention in hot path |
| Diagnostic snapshot JSON | Manual string concatenation | `serde_json` | Already in workspace, correct escaping, structured |
| Health snapshot emission | Custom timer thread | Reuse `PerfTelemetry` emission cadence | Less code, consistent timing, already tested |

**Key insight:** The hook DLL hot path is extremely sensitive to latency (target: < 25% overhead per CRIT-04). Every millisecond matters. Using optimized, battle-tested crates for concurrency primitives and cryptography is non-negotiable.

## Common Pitfalls

### Pitfall 1: Hook DLL Deadlock from DllMain
**What goes wrong:** Initializing the diagnostic ring, hash pool, or health counters from `DllMain` causes loader-lock deadlock.
**Why it happens:** Windows holds the loader lock during `DllMain`. Any operation that might acquire another lock (including `OnceLock::get_or_init` with blocking initialization) can deadlock.
**How to avoid:** Initialize all `OnceLock` values from the first trampoline invocation, NOT from `DllMain`. This pattern is already established in `perf_telemetry.rs`, `hook_journal.rs`, and `fail_mode.rs`.
**Warning signs:** Process hangs immediately after DLL injection; no log output; debugger shows all threads blocked in `ntdll!LdrLockLoaderLock`.

### Pitfall 2: Cross-Architecture IPC Breakage
**What goes wrong:** Adding new fields to `HookMessage` or `AuditEvent` without `#[serde(default)]` breaks bincode deserialization when an old agent talks to a new hook DLL (or vice versa).
**Why it happens:** Bincode requires exact layout match. JSON supports missing fields via `serde(default)`, but bincode does not.
**How to avoid:** Phase 58.4 does NOT add new fields to existing IPC structs. It only wires existing fields (`content_sha256`, `hash_truncated`, `hash_skipped` in `HookResponse` and `AuditEvent`) that already have `#[serde(default)]`. If new fields are needed, use a versioned envelope pattern (like `IpcEnvelope::V1`).
**Warning signs:** `bincode::ErrorKind::InvalidEncoding` or `UnexpectedEof` in pipe communication tests.

### Pitfall 3: SHA-256 Buffer Overread
**What goes wrong:** Computing hash from `lpBuffer` with `nNumberOfBytesToWrite` that exceeds the actual buffer size causes a segfault.
**Why it happens:** The application (not the hook DLL) owns the buffer. If the application has a bug or the parameters are manipulated, the buffer may be smaller than claimed.
**How to avoid:** The 100MB cap (D-06) is also a safety boundary. Use `std::slice::from_raw_parts` only after the cap is applied. Consider adding a second safety cap at 1GB as an absolute maximum.
**Warning signs:** Access violation in `HookWriteFile`; crash dumps pointing to `hash_compute.rs`.

### Pitfall 4: Health Counter Overflow
**What goes wrong:** `AtomicU64` counters for pipe_round_trips and cache_hits overflow after ~584 years of continuous operation at 1M ops/sec.
**Why it happens:** U64 overflow is theoretically possible in extreme scenarios, but practically impossible. More realistically, the 60-second window calculation can drift if the polling thread stalls.
**How to avoid:** Use saturating arithmetic for ratio computation. Reset counters atomically when emitting the snapshot. Use `fetch_add` with `Ordering::Relaxed` (correct for independent counters).
**Warning signs:** Negative or >100% cache hit rates in health dashboard.

### Pitfall 5: Diagnostic Ring Buffer Memory Leak
**What goes wrong:** `DiagnosticSnapshot` contains `String` fields (hook_function, abac_resource, etc.). If the ring buffer is not drained, these strings accumulate and the process memory grows.
**Why it happens:** `ArrayQueue` stores owned values. If the agent stops polling, the queue fills and old entries are dropped, but the `String` heap allocations are freed on drop.
**How to avoid:** The 1000-entry cap (D-03) bounds memory to ~1MB (each snapshot ~1KB with strings). The 1-hour lazy eviction is implemented by skipping expired entries during drain, not by removing from the queue.
**Warning signs:** Process memory growth in hook-injected processes; diagnostic snapshots with very old timestamps.

### Pitfall 6: HookResponse Bloat
**What goes wrong:** Adding diagnostic or health data to `HookResponse` increases IPC payload size and deserialization cost on every classification request.
**Why it happens:** `HookResponse` is sent on every pipe round-trip, not just on DENY. Bloat affects the common path (ALLOW decisions).
**How to avoid:** Per D-13, keep `HookResponse` minimal. Hash data is the only enrichment allowed. Diagnostic and health data are retrieved via separate `PullDiagnostics` / `PullHealth` IPC requests.
**Warning signs:** Increased p99 latency in hook IPC round-trip tests; larger bincode payloads.

### Pitfall 7: Missing Hash Data in Audit Event
**What goes wrong:** The hook DLL computes the hash and returns it in `HookResponse`, but the agent does not forward it to the `AuditEvent` before sending to the server.
**Why it happens:** The agent's audit event builder may not be updated to read the new `HookResponse` fields.
**How to avoid:** Verify the agent's audit event creation path reads `content_sha256`, `hash_truncated`, and `hash_skipped` from `HookResponse` and attaches them via `with_content_hash(...)`.
**Warning signs:** Audit events in SQLite have NULL `content_sha256` despite blocked writes.

        if nnumberofbytestowrite < 64 * 1024 {
            crate::hash_compute::compute_content_hash(lpbuffer, nnumberofbytestowrite)
        } else {
            crate::hash_compute::compute_content_hash_offloaded(lpbuffer, nnumberofbytestowrite)
        }
    } else {
        (None, false, false)
    };

    // DIFF-02: Emit diagnostic snapshot (see Pattern 1)
    // ...

    // Return deny. The hash data must be sent to the agent somehow.
    // Option A: Attach to HookResponse (requires pipe round-trip to return hash).
    // Option B: Send a separate fire-and-forget frame (adds complexity).
    // Per D-13, use Option A: the agent's handler reads HookResponse.hash fields.
    return crate::fail_closed!(BoolFalse);
}

## Open Questions

1. **How should the hash data be returned from the hook DLL to the agent?**
   - What we know: D-13 says keep `HookResponse` minimal, but D-08 says attach hash to `HookResponse`. These are compatible if hash fields are optional and only populated on DENY.
   - What's unclear: Whether the agent's audit event builder is already wired to read these fields.
   - Recommendation: Verify `dlp-agent/src/audit.rs` or equivalent reads `HookResponse.content_sha256` and calls `AuditEvent::with_content_hash(...)`. If not, add that wiring as part of this phase.

2. **Should diagnostic snapshots include the resolved volume class from the ABAC environment?**
   - What we know: D-02 lists `abac_environment` as a field.
   - What's unclear: Whether the hook DLL has access to the resolved volume class at the point of DENY.
   - Recommendation: Yes — `source_volume_class` is already resolved in `classify_and_log_path` before the pipe call. Include it in `abac_environment` as a JSON string.

3. **How should the health snapshot be sent from the hook DLL to the agent?**
   - What we know: D-09 says emit every 100 pipe round-trips and on state transitions.
   - What's unclear: Whether `pipe_client.rs` has a `send_health_snapshot` function.
   - Recommendation: Add a fire-and-forget `send_health_snapshot` function to `pipe_client.rs` that sends an `IpcEnvelope::V1(IpcPayloadV1::HealthResponse(...))` frame. The agent's `BypassAlert` routing can be reused as a pattern.
