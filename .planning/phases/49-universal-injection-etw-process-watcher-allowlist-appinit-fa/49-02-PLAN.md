<objective>
Create the server-side database schema, repository layer, and admin REST API for managing process allowlist entries. Operators can add, edit, delete, and view allowlist entries through the admin API, which feeds into the agent config TOML response.

Purpose: The agent's allowlist matcher (Plan 01) needs a data source. This plan creates the persistence and API layer so operators can manage allowlist entries without editing raw config files.
Output: `allowlist_entries` SQLite table, `AllowlistRepository`, `/admin/allowlist` CRUD endpoints.
</objective>

| Agent config poll -> allowlist_entries | Server reads DB and includes in agent config TOML response |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-49-06 | Tampering | Allowlist entry creation | mitigate | JWT authentication required on all /admin/allowlist endpoints via existing `admin_auth::require_auth` middleware |
| T-49-07 | Elevation of Privilege | Invalid category injection | mitigate | Category CHECK constraint in SQLite + handler validation rejects invalid categories with Validation error |
| T-49-08 | Information Disclosure | Allowlist entry listing | mitigate | All endpoints behind JWT auth; no sensitive data in allowlist entries (paths and cert subjects are operational config, not secrets) |
| T-49-09 | Denial of Service | Mass allowlist entry creation | accept | Rate limiting already applied via `default_config()` middleware on protected routes |
</threat_model>
