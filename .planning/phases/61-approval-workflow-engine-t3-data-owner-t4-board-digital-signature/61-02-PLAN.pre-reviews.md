   - If `q.status` is Some, call `ApprovalRepository::list_by_status(pool, &status)`
   - Otherwise call `ApprovalRepository::list(pool)`
   - Map `ApprovalRow` to `Approval` struct and return as JSON array
   - Use `tokio::task::spawn_blocking` for DB calls

2. `get_approval`:
   - Call `ApprovalRepository::get_by_id(pool, &id)`
   - Map to `Approval` and return JSON

3. `grant_approval`:
   - Fetch the approval row by id; return 404 if not found
   - Verify status is `pending`; return 409 Conflict if not
   - Resolve the approver SID from the JWT auth claims (use `admin_auth::Claims` extractor pattern)
   - Look up the data object via `LabelRepository::get_by_id(pool, &row.data_object_id)` to determine tier
   - If tier is T4:
     - Verify `body.signature` is Some; return 400 if missing with message "T4 approval requires valid Board signature"
     - Retrieve board public key from `system_kv` via `ApprovalTokenService::get_board_public_key`
     - Verify the signature using `ApprovalTokenService::verify_board_signature` against the JWT payload bytes (construct a canonical message from the approval fields)
     - Return 400 if verification fails
   - Generate `ApprovalClaims`:
     ```rust
     let now = chrono::Utc::now();
     let claims = ApprovalClaims {
         sub: row.requester_sid.clone(),
         obj: row.data_object_id.clone(),
         act: row.allowed_action.clone(),
         dst: row.destination_scope.clone(),
         dev: None, // resolved from approval request if stored
         iat: now.timestamp(),
         exp: chrono::DateTime::parse_from_rfc3339(&body.valid_until)?.timestamp(),
         jti: id.clone(),
     };
     ```
   - Sign token: `state.approval_token_service.sign_token(&claims)?`
   - Update approval state:
     ```rust
     ApprovalRepository::update_state(&uow, &id, "approved", Some(&approver_sid), Some(&now.to_rfc3339()), Some(&body.valid_until), body.signature.as_deref(), &now.to_rfc3339())?;
     ```
   - Commit transaction
   - Emit audit event via `audit_store::store_events_sync` (or spawn_blocking with AuditEvent)
   - Emit alert via `state.alert.send_alert(&audit_event).await` (best-effort, fire-and-forget)
   - Return `GrantResponse { approval, token }`

4. `reject_approval`:
   - Verify status is `pending`; return 409 if not
   - Update state to `rejected` with approver_sid
   - Emit audit event
   - Return `ApprovalResponse`

5. `revoke_approval`:
   - Verify status is `approved`; return 409 if not
   - Update state to `revoked`
   - Emit audit event
   - Invalidate the approval in the policy_store cache (call `policy_store.invalidate_approval(...)` — this method will be added in Plan 03; for now add a TODO comment)
   - Return `ApprovalResponse`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Admin TUI -> API | JWT-authenticated; only dlp-admin can grant/reject/revoke |
| API -> DB | SQL parameterized; no string interpolation |
| Board signature -> T4 grant | Cryptographic verification against stored pubkey |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-61-06 | Spoofing | `grant_approval` approver_sid | mitigate | Extracted from validated JWT claims; cannot be forged by client |
| T-61-07 | Tampering | T4 signature bypass | mitigate | Server verifies Ed25519 signature against stored board pubkey; missing/invalid = 400 |
| T-61-08 | Elevation of Privilege | Non-admin grants approval | mitigate | Route is under JWT auth layer; only dlp-admin token valid |
| T-61-09 | Repudiation | Missing audit on grant | mitigate | Every state change emits AuditEvent to siem_connector; append-only audit_events table |
| T-61-10 | Information Disclosure | Token in audit event | accept | Token is a signed JWT; no private key material exposed |
</threat_model>
