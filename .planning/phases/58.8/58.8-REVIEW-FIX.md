### CR-01: Pipe 1 dispatcher double-removes the pending override (race with submitter)

**Files modified:** `dlp-agent/src/ipc/pipe1.rs`
**Commit:** `ddfe830f`
**Status:** fixed — requires human verification (ownership / state-handling)
**Applied fix:** The `UserConfirmed` arm now does
`store.lock().get(…).cloned()` (look up, do **not** remove) and only enqueues
a `ConfirmedOverride`. The async `confirmed_override_loop` is the single owner
that removes the entry and submits it to the server, so the dispatcher can no
longer drop the approval request by racing the submitter. Added regression
test `dispatch_user_confirmed_does_not_remove_pending_entry`.

### CR-02: Override prompt routed to the wrong session (hardcoded session 0)

**Files modified:** `dlp-common/src/hook_ipc.rs`, `dlp-hook-dll/src/trampolines.rs`, `dlp-agent/src/service.rs`, `dlp-agent/src/ipc/pipe1.rs`, `dlp-agent/tests/hook_ipc_integration.rs`
**Commit:** `f30f9aec`
**Status:** fixed — requires human verification (routing logic / fail-closed path)
**Applied fix:** Plumb the requesting PID through `OverrideRequest`
(`GetCurrentProcessId` at DLL emit time; `#[serde(default)]` for legacy). The
agent resolves the owning interactive session via `pid_to_session_id`
(`ProcessIdToSessionId`), stores `session_id` on `PendingOverride`, and routes
`send_to_ui(session_id, …)`. If the session cannot be resolved, or no UI is
registered for it, the agent **fails closed**: it keeps the operation denied
and removes the freshly-inserted pending entry so state cannot leak.
`send_to_ui` now returns `Err` for an unregistered session (was a silent
`Ok(())`), and a 120s TTL reaper (`override_pending_reaper`) discards
never-confirmed overrides. Added regression test
`send_to_ui_returns_err_for_unknown_session`. All other `send_to_ui` callers
already use `if let Err`, so the new error only adds logging (no control-flow
change).
**Residual / follow-up:** PID-derived session is trustworthy for the local
case but is supplied by the (unprivileged) hook process; a future hardening
pass should read the peer PID via `GetNamedPipeClientProcessId` on the agent
side instead of trusting the field. Tracked as a follow-up.

### WR-06: UI Pipe 1 read loop can hang on a live-but-silent agent

**Files modified:** `dlp-user-ui/src/ipc/pipe1.rs`
**Commit:** `8ed1ea4e`
**Status:** fixed — requires human verification (threading / timeout semantics)
**Applied fix:** `client_loop` now runs the blocking `read_frame` on a
dedicated reader thread that forwards frames over an `mpsc` channel; the main
loop waits with `recv_timeout(PIPE_POLL_INTERVAL = 100ms)` so the heartbeat
clock is evaluated even when no frame arrives. The clock starts at connect
time (an agent that never writes a single frame is still detected within
`HEARTBEAT_TIMEOUT = 15s`). On exit the pipe handle is closed from the main
thread to unblock the reader's pending read so it terminates cleanly, then the
reader is joined. The previous implementation only checked the clock **after**
a frame arrived, so a silent agent could park the read thread forever.
