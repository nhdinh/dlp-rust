### WR-01: Override `classification` is derived from the deny-return enum, not the data tier

**Files modified:** `dlp-hook-dll/src/trampolines.rs`, `dlp-hook-dll/tests/override_request_test.rs`
**Commit:** `63e470f0`
**Applied fix:**
- Path site (`classify_and_log_path`): hoisted a new `let mut override_tier: Option<Classification>` out of the `measure` closure (the reviewer's `cache_classification` is declared *inside* the closure and is not in scope at the deny site), mirror it from `cache_classification` right after the cache lookup, and format the override classification from the resolved tier via `format!("{c:?}")` (Debug yields the tier code `"T3"` that `audit_classification_for_override` recognises), falling back to an honest `"Unknown"` on a cache-miss pipe deny (no local tier). The string stays non-empty so the prompt is still offered and the audit default of `T3` applies.
- Handle site (`classify_and_log_handle`): no data tier is resolved locally there (the agent classifies by handle from its own tracker), so the override reports an honest `"Unknown"` instead of the deny-return enum's `Debug`.
- Added `assert_eq!(req.classification, "Unknown")` to `request_override_is_emitted_on_deny` (the field IN-01 noted was unasserted). That test is a cache-miss pipe deny, so `"Unknown"` is the correct post-fix value and pins the regression guard without expanding scope.
**Verification:** `cargo check -p dlp-hook-dll --tests` clean; the targeted test passes (`test request_override_is_emitted_on_deny ... ok`).

### WR-02: Modal dialogs run on the Pipe-1 read thread and starve the heartbeat

**Files modified:** `dlp-user-ui/src/ipc/pipe1.rs`
**Commit:** `042601b3`
**Applied fix:** Moved the blocking Win32 modals off the read loop using the same non-modal rationale the file already documents for approval outcomes (`:350-354`). Added a `std::sync::mpsc::channel::<Vec<u8>>` (`dialog_tx`/`dialog_rx`); `handle_block_notify` and `handle_override_request` now spawn a dedicated thread that runs the modal and pushes the serialised `UserConfirmed`/`UserCancelled` bytes onto the channel, returning `None` immediately. The read loop drains completed responses each poll via a new `drain_dialog_responses` helper (non-blocking `try_recv`) and writes them, so the loop keeps servicing `Ping`/`Pong` and advancing the 15s heartbeat clock while a dialog is open. `handle_agent_msg` gained a `dialog_tx` parameter; only the two cited modal paths were changed.
**Verification:** `cargo check -p dlp-user-ui` clean; `ipc::pipe1::tests::block_request_ids_are_unique_per_event` passes.
**Note (not in cited scope):** `handle_password_dialog` (`show_password_dialog`) is still modal-inline; it shares the same pattern but is the security-sensitive stop flow and was not part of this finding, so it was left unchanged for a targeted follow-up.

### WR-03: An approved override is silently lost when the confirm channel is saturated

**Files modified:** `dlp-agent/src/ipc/pipe1.rs`
**Commit:** `ba1d578f`
**Applied fix:** Replaced the non-blocking `try_send` (which dropped a `ConfirmedOverride` on bounded-channel saturation) with guaranteed-delivery backpressure in `dispatch`. Because `dispatch` runs inside the synchronous blocking pipe server, the send is awaited via the current Tokio runtime handle (`Handle::try_current().block_on(sender.send(...))`) in production, and via `Sender::blocking_send(...)` when no runtime handle is present (synchronous unit tests). Both forms block until capacity is available and only error on a closed channel, so a confirmed override can no longer be stranded until the 120s reaper after the UI already reported "Approved". `dispatch`'s signature and all call sites are unchanged.
**Verification:** `cargo check -p dlp-agent` clean; both `ipc::pipe1` unit tests pass, including `dispatch_user_confirmed_does_not_remove_pending_entry` (exercises the synchronous `blocking_send` fallback).

### WR-04: Granted-override audit records `user_name` as the raw SID

**Files modified:** `dlp-agent/src/service.rs`
**Commit:** `cf963d3d`
**Applied fix:** In `emit_override_granted_audit`, `EmitContext.user_name` is now populated by resolving the requester SID to an account name through the existing cached `crate::identity::IdentityResolver::lookup_account_name`, falling back to `"UNKNOWN"` only when the SID genuinely cannot be resolved — never duplicating the raw SID (which remains in `user_sid`). Implemented as a localized cold-path lookup at emit time rather than threading a new field through `PendingOverride` and its five construction sites, keeping the blast radius minimal and avoiding any struct/test changes.
**Verification:** `cargo check -p dlp-agent` clean; the `confirmed_override_loop` tests pass, including `test_confirmed_override_loop_removes_pending_on_submit_success`, which now drives the new SID-lookup path against the test fixture's unresolvable SID (`"S-1-5-21-1"` -> `"UNKNOWN"`) without panicking.
