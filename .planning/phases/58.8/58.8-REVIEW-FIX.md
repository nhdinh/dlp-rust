## Fixed Issues

### CR-01: Syslog drain backoff adds nanoseconds as seconds — one transient failure disables forwarding for years

**Files modified:** `dlp-server/src/main.rs`
**Commit:** 8cab0015
**Applied fix:** Extracted a bounded `syslog_backoff(consecutive_failures)` helper
that computes jitter with `subsec_nanos()` (0..1e9) modulo 500_000_000 (0..0.5 s)
and returns `Duration::from_secs(delay) + jitter`, with `delay` capped at 60 via
`exp = min(failures, 6)`. Both the drain-loop sleep and `compute_next_attempt`
now use it, so retries stay within `[delay, delay + 0.5 s]` (<= 60.5 s) instead
of sleeping up to ~951 years or overflowing `chrono::Duration::from_std` to zero.
Added three unit tests: per-failure backoff bounded within `[delay, delay+0.5)`,
never exceeds 60.5 s, and `compute_next_attempt` lands within ~60.6 s of now.
All three tests pass; `cargo check -p dlp-server` clean.

**Applied fix:** `AgentIdOrIpKeyExtractor::extract` no longer keys on the `:id`

## Skipped Issues

The five skipped Warnings are all deep IPC / security-infrastructure changes.
Each was evaluated against the actual source and judged unsafe to blind-apply in
an automated fixer pass: verification here is syntax-level only and cannot
exercise multi-client concurrency or real named-pipe connect/close timing, and a
subtle mistake in any of these would silently break a production DLP workflow
(override prompts, UI registration, dashboard/SIEM ingest). Each entry states

### WR-02: Single shared `DLP-AGENT` hash authenticates every agent → cross-agent impersonation

**File:** `dlp-server/src/admin_api.rs:129-182`; client `dlp-agent/src/server_client.rs:462-464`
**Reason:** Architectural, not a localized fix. The reviewer's own fix is to
"store/verify a per-agent credential keyed by `agent_id` (`agent_auth_hashes`
map) and reject when the presented `agent_id` has no enrolled secret." That
requires a new per-agent credentials table and migration, an enrollment API
(admin-provisioned per-agent secret), constant-time lookup keyed by the claimed
`agent_id`, agent-side provisioning so `ServerClient` holds its own secret
(currently production never calls `fetch_auth_hash` — see CR-02 note),
rotation/revocation, and audit. Touching the auth middleware's contract without
the enrollment path would lock every agent out (fail-closed on "no enrolled
secret" for all agents), so this cannot be staged safely as one commit.
**Original issue:** One global `DLPAuthHash` authenticates every agent;
`agent_id` is only inserted into extensions, never bound to a per-agent secret,
so one leaked hash forges health/diagnostics for every agent and defeats
per-tenant isolation.

### WR-04: Concurrent, unsynchronized `WriteFile`s to the same Pipe-1 handle; `SendableHandle` safety comment is false

**File:** `dlp-agent/src/ipc/pipe1.rs:56-69, 252, 389-403, 413-471`
**Reason:** The genuine fix requires every writer to a handle to share one
mutex — including the per-client `client_loop`, which currently writes responses
on its bare `pipe` (line 252) bypassing the `CLIENTS` map entirely. Wrapping only
the map value in `Arc<Mutex<SendableHandle>>` leaves `client_loop` unsynchronized
and gives a false sense of safety; the correct change threads an
`Arc<Mutex<SendableHandle>>` into `client_loop` and rewrites `send_to_ui`,
`send_password_dialog`, and `send_ping_to_all` to clone the `Arc` out of the read
lock, release the map lock, then lock the per-handle mutex across the full
`write_frame`. That is a concurrency refactor in the agent's core UI command
pipe with no multi-client concurrency test to validate it; a deadlock or a
write-under-`CloseHandle` race (cf. IN-03) here silently kills override/block
prompts in production. Land only with an integration test that hammers one
session from concurrent heartbeat + password-stop + override tasks.
**Original issue:** `send_to_ui`/`send_password_dialog`/`send_ping_to_all` are
called from other tokio tasks while `client_loop` writes on the same handle;
`CLIENTS.read()` only serializes the map lookup, so two length-prefixed frames
can interleave and corrupt UI framing, invalidating the `unsafe impl Send/Sync`
invariant.

### WR-07: Override session routing still trusts the hook-supplied `pid` (incomplete CR-02 hardening)

**File:** `dlp-agent/src/service.rs:2309` (uses `req.pid`); emit `dlp-hook-dll/src/trampolines.rs:291`; helper `dlp-agent/src/hook_ipc.rs:370`
**Reason:** The naive overwrite (set `req.pid = named_pipe_client_pid(pipe)` in
the `RequestOverride` arm and fail-closed on `None`) is **unsafe**: `RequestOverride`
is fire-and-forget — the DLL closes the pipe immediately after
`send_raw_oneway` (hook_ipc.rs:558-560). If `GetNamedPipeClientProcessId` returns
`None` because the peer already disconnected, a fail-closed-on-`None` would drop
EVERY legitimate override and silently disable the entire unblock workflow.
`named_pipe_client_pid` is reliable for `UnhookAck` only because that path is
request/response (the peer is still connected when the server checks). The
correct fix captures the peer PID at accept time (the guaranteed-connected
moment right after `ConnectNamedPipe` succeeds) and threads it through
`handle_connection` and the `OverrideHandler` type (hook_ipc.rs:74) into the
service, which needs a signature change at service.rs:1968 plus an integration
test over a real pipe that asserts routing by the authoritative peer. That is a
broader, API-visible refactor than is safe to blind-apply and syntax-check only.
**Original issue:** `pid_to_session_id(req.pid)` trusts the DLL-supplied `pid`
over a pipe writable by any authenticated user, so a local user can steer the
override prompt (and any auto-confirm) to a chosen session, or to a session with
no UI to force fail-closed denial.

### WR-08: Pipe 1 `RegisterSession` trusts the client-supplied `session_id` → any local user can hijack a session's UI slot

**File:** `dlp-agent/src/ipc/pipe1.rs:204-212`; DACL `dlp-agent/src/ipc/pipe_security.rs:23`
**Reason:** Two coupled changes, both risky without integration coverage: (1)
bind registration to the authoritative peer via `GetNamedPipeClientProcessId` +
`ProcessIdToSessionId` and reject a claimed `session_id` that does not match the
peer's real session; (2) refuse to overwrite an existing live registration for
the same session. The overwrite-on-reconnect behavior at pipe1.rs:210-212 may be
required by the UI respawn flow (`Pipe2AgentMsg::UiRespawn`), so adding
no-overwrite blind risks stranding a legitimately respawned UI with no slot.
Likewise a wrong peer-session mapping (service UI, RDP, fast user switching)
would fail-closed and reject legitimate UIs. There is no integration test that
exercises peer-session resolution across the respawn path, so this needs a
human-led change with that harness.
**Original issue:** The Pipe-1 DACL grants `GRGW` to Authenticated Users and
`handle_client` keys `CLIENTS` by the client-chosen `session_id` with no peer
check and unconditional overwrite, so any local user can steal a victim UI's
slot, receive its `BlockNotify`/`OverrideRequest`/`PasswordDialog`, and
auto-confirm or suppress its dialogs.

### WR-09: Hook pipe ingests dashboard/SIEM telemetry from any authenticated user with no sender authentication

**File:** `dlp-agent/src/hook_ipc.rs:578-672` (`BypassAlert`, `JournalDegraded`, `HashEvidence`, `HealthResponse`); DACL `dlp-agent/src/ipc/pipe_security.rs:23`
**Reason:** Not a uniform "claimed pid == peer pid" check. `HashEvidence` (639)
and `HealthResponse` (649) are fire-and-forget, so the same peer-pid-at-handle
reliability concern as WR-07 applies; worse, `HealthResponse` carries no sender
pid (its `HookHealthSnapshot` has none) and `JournalDegraded` synthesizes a
`BypassAlert` with `pid: 0` (600), so there is no claimed pid to compare for two
of the four payloads. The robust control is to validate the peer against the
process registry (the injected set) or split the pipe into a SYSTEM/BA-only
telemetry channel and a least-privilege classification channel — both
architectural. Doing only the easy half (`BypassAlert`/`HashEvidence` pid
checks) would leave the dashboard/SIEM forgery vector open while appearing to
close it. Land with a registry-based binding and integration tests that forge
each payload from an un-injected peer.
**Original issue:** `\\.\pipe\DlpHookPipe` is `GRGW` to Authenticated Users and
the SYSTEM agent acts on `HealthResponse`/`BypassAlert`/`JournalDegraded`/
`HashEvidence` with no sender verification, allowing forged critical health,
forged hook-overwrite/EDR alerts to the SIEM, and hash-cache poisoning.
