# Cross-AI Plan Review — Phase 58.8

## Codex Review

### Overall Summary

The plans target the right two blockers, and most referenced code paths exist. The main risks are not in the high-level intent but in cross-crate wiring details: diagnostics still lack a server ingestion path, the proposed health ingest endpoint weakens the stated agent-auth requirement, and the deferred override flow in Plan 58.8-03 is under-specified for the current synchronous Pipe 1 architecture.

### Plan 58.8-01: Hook DLL Override Trigger

#### Summary

Good target and mostly good scope. `classify_and_log_path` and `classify_and_log_handle` are the right hook-DLL choke points, and existing `approval_override` handling proves future approved overrides can allow later operations. The plan needs sharper test design because the existing hook DLL mock server only handles `HookRequest`.

#### Strengths

- Correct hook locations: `classify_and_log_path` is the path-based gate at `dlp-hook-dll/src/trampolines.rs:163`, and `classify_and_log_handle` is the handle-based gate at `dlp-hook-dll/src/trampolines.rs:614`.
- Existing protocol support is present: `IpcPayloadV1::RequestOverride` exists at `dlp-common/src/hook_ipc.rs:96`, with `OverrideRequest` fields at `dlp-common/src/hook_ipc.rs:383`.
- Approved override fast path already exists: denied responses with `approval_override == Some(true)` allow the operation at `dlp-hook-dll/src/trampolines.rs:311` and `dlp-hook-dll/src/trampolines.rs:691`.

#### Concerns

- **MEDIUM:** The plan says "user-initiated," but the proposed wiring emits on every DENY. Cooldown reduces flooding, but this is still "prompt user for override" rather than "user clicked request override."
- **LOW:** The current `MockAgentServer` only accepts a `HookRequest -> HookResponse` handler (`dlp-hook-dll/src/test_utils.rs:81`), so the integration test cannot capture `RequestOverride` unless the test builds a custom `HookIpcServer` with an override handler.
- **LOW:** `send_raw_oneway` is consistent with existing one-way frames, but `HookIpcServer` still writes a response for `RequestOverride` at `dlp-agent/src/hook_ipc.rs:552`. This should be verified to avoid noisy broken-pipe behavior.

#### Suggestions

- Make the test use `HookIpcServer::with_override_handler`, not the existing `MockAgentServer`.
- Clarify UX language: "emit an override prompt request on deny" unless a real prior user action exists.
- Include a test for approved override not emitting a new override prompt.

#### Risk Assessment

**MEDIUM.** The code target is right, but test infrastructure and exact semantics need tightening.

### Plan 58.8-02: Server-Side Health Infrastructure

#### Summary

The server health-store plan is directionally sound, especially mirroring `DiagnosticSnapshotStore`, but it does not fully close DIFF-04 because it initializes `diagnostic_store` without adding any production path that ingests diagnostics into it. The agent health endpoint also conflicts with the project's "agent-authenticated" requirement.

#### Strengths

- Existing production gap is real: `AppState` only has `diagnostic_store` today at `dlp-server/src/lib.rs:80`, and production initializes it as `None` at `dlp-server/src/main.rs:297`.
- The diagnostics route is already JWT-protected through the protected router at `dlp-server/src/admin_api.rs:1280` and auth middleware at `dlp-server/src/admin_api.rs:1291`, so `/admin/health` can follow the same pattern.
- `DiagnosticSnapshotStore` provides a good bounded in-memory model with `DashMap`, per-key caps, and global key eviction at `dlp-server/src/diagnostic_store.rs:40`.

#### Concerns

- **HIGH:** Success criterion 3 says `GET /admin/diagnostics` returns real snapshots when diagnostics have been ingested, but this plan adds no server-side diagnostics ingest route. Current diagnostics handler only reads `state.diagnostic_store` at `dlp-server/src/admin_api.rs:5429`.
- **HIGH:** The plan calls `POST /agents/{id}/health` "public" and accepts spoofing, but the phase research explicitly says agent ingestion should reuse agent auth. Existing public routes include unauthenticated `/audit/events` and `/audit/bypass` at `dlp-server/src/admin_api.rs:1083`, so copying that pattern perpetuates a known weak boundary.
- **MEDIUM:** `per_agent_config()` keys only by URL path segment (`dlp-server/src/rate_limiter.rs:55`), so unauthenticated callers can choose arbitrary agent IDs to spread load across rate-limit buckets.

#### Suggestions

- Add `POST /agents/{id}/diagnostics` or equivalent agent push plumbing, otherwise do not claim DIFF-04 diagnostics is fixed.
- Add an explicit agent authentication story for health telemetry, even if lightweight.
- Validate that path `{id}` matches payload `agent_id` if the payload includes one.

#### Risk Assessment

**HIGH.** `/admin/health` can be delivered, but diagnostics and authentication gaps leave DIFF-04 only partially closed.

### Plan 58.8-03: Agent Health Push + Deferred Override Submission

#### Summary

This plan correctly identifies the semantic bug: the agent currently submits approval immediately with the hook DLL's justification before the UI response. However, the proposed deferred submission does not fit the current Pipe 1 implementation unless the plan adds an explicit async boundary and stores the full override request context.

#### Strengths

- The immediate-submit bug is real: the service task forwards to UI at `dlp-agent/src/service.rs:1956`, then immediately calls `submit_approval_request` at `dlp-agent/src/service.rs:1977`.
- The UI currently captures justification but discards it when constructing `UserConfirmed` at `dlp-user-ui/src/ipc/pipe1.rs:209`.
- `HealthAggregator::get_current_status()` already exposes the latest snapshot for a health push loop at `dlp-agent/src/health_aggregator.rs:225`.

#### Concerns

- **HIGH:** `OVERRIDE_PENDING` stores only `session_id` and `created_at` (`dlp-agent/src/ipc/pipe1.rs:47`), not `requester_sid`, `data_object_id`, `action`, `destination_scope`, or `resource_path`. That is insufficient to build the later server approval request.
- **HIGH:** `dispatch` is synchronous (`dlp-agent/src/ipc/pipe1.rs:275`) and has no `ServerClient`. Calling an async `submit_approval_request_with_justification` from `UserConfirmed` needs a channel/callback/runtime handoff that the plan does not specify.
- **HIGH:** The duplicated UI message enum must be updated in both crates. The plan lists `dlp-agent/src/ipc/messages.rs`, but `dlp-user-ui/src/ipc/messages.rs:43` also defines `Pipe1UiMsg::UserConfirmed`.
- **MEDIUM:** The health round-trip test proves the server API, but not the actual periodic agent task or shutdown behavior.

#### Suggestions

- Store a full `PendingOverride { request, session_id, created_at }`.
- Add a `tokio::mpsc::Sender<ConfirmedOverride>` registered with Pipe 1 dispatch, so synchronous dispatch can enqueue confirmation and an async service task can submit it.
- Update and test both duplicated `Pipe1UiMsg` enums.
- Add a focused unit test for the confirmation channel path, not only server API round-trip.

#### Risk Assessment

**HIGH.** The intent is right, but current architecture needs more explicit wiring than the plan states.

### Plan 58.8-04: Test Propagation + Admin CLI Test

#### Summary

This is a useful compile-hardening and client-verification plan, but it overlaps with Plan 58.8-02 and should be treated as a cleanup/verification pass after the server shape stabilizes.

#### Strengths

- AppState blast radius is real: many literals exist in `dlp-server/src/admin_api.rs`, `dlp-server/src/lib.rs`, and integration tests.
- Admin client auth behavior is testable: `set_token` sets the bearer token at `dlp-admin-cli/src/client.rs:164`, and all `get()` calls apply it at `dlp-admin-cli/src/client.rs:233`.
- `/admin/health` 401 testing matches the protected-router pattern already used for `/admin/diagnostics`.

#### Concerns

- **MEDIUM:** Plan 58.8-02 already says it updates all `AppState` literals, while Plan 58.8-04 repeats that work. This is harmless if sequenced, but it is a conflict risk if work is split across agents.
- **LOW:** The admin CLI test only validates generic JSON success. It should also assert the fields consumed by the TUI: `snapshot.overall_status`, `history`, and the operational counters.
- **LOW:** The mock response should match the dashboard response shape, not just any non-empty object.

#### Suggestions

- Move "update every AppState literal" entirely to either Plan 02 or Plan 04, not both.
- Add client assertions for the exact `/admin/health` contract.
- Keep the 401 server test in Plan 04; it is a good regression guard.

#### Risk Assessment

**MEDIUM.** Mostly compile/test coverage work, but duplication with Plan 02 can cause avoidable churn.

### Final Risk Assessment

**Overall risk: HIGH** until the diagnostics ingest gap and deferred override async boundary are resolved. The phase goals are achievable, but the current plans do not yet fully prove `GET /admin/diagnostics` receives production data, and Plan 58.8-03 needs a concrete channel-based design to submit approvals after UI confirmation.

## Consensus Summary

Only Codex was invoked for this review cycle (Claude was skipped as the executing runtime, and no other external AI CLIs were requested or available). The consensus below is therefore derived entirely from Codex's source-grounded findings.

### Agreed Strengths

- The phase targets the correct blockers: `IpcPayloadV1::RequestOverride` emission from the hook DLL deny paths and the missing `GET /admin/health` route / uninitialized `diagnostic_store`.
- Existing protocol and store primitives (`IpcPayloadV1::RequestOverride`, `DiagnosticSnapshotStore`, `HealthAggregator::get_current_status`, admin-router JWT protection) make the goals feasible.
- Source-grounded evidence confirms the cited file locations and current behavior.

### Agreed Concerns

- **HIGH:** Plan 58.8-02 does not add a server-side diagnostics ingest route, so success criterion 3 (`GET /admin/diagnostics` returns real snapshots after ingestion) is not yet supported by the plan.
- **HIGH:** Plan 58.8-03's deferred override submission is under-specified: `OVERRIDE_PENDING` currently stores only `session_id`/`created_at`, the synchronous Pipe 1 dispatch lacks an async handoff, and both duplicated `Pipe1UiMsg::UserConfirmed` definitions must be updated.
- **HIGH:** `POST /agents/{id}/health` is designated public/unauthenticated, which conflicts with the research requirement to reuse agent auth and perpetuates a known weak boundary.
- **MEDIUM:** Plans 58.8-02 and 58.8-04 both claim responsibility for updating every `AppState` literal, creating duplication/conflict risk.
- **MEDIUM:** `per_agent_config()` rate-limit keying by URL path segment allows arbitrary `agent_id` selection, weakening per-agent throttling.
- **MEDIUM/LOW:** Integration tests for Plans 01, 03, and 04 need stronger assertions (custom `HookIpcServer` override handler, channel-based confirmation path, exact dashboard response shape).

### Divergent Views

None — only one reviewer was invoked. The findings above should be treated as a single source of adversarial input and validated by the planner during `--reviews` incorporation.
