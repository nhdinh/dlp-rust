# Cross-AI Plan Review — Phase 58.8

## Codex Review

**Summary**

The four plans target the right blockers, but the phase is higher-risk than the wave layout suggests. DIFF-04 is well localized: `AppState` has only `diagnostic_store` today, production initializes it to `None`, and `/admin/health` is absent. DIFF-01 is trickier: the hook DLL deny branches are the missing trigger, but the existing agent path currently submits server approval immediately before UI confirmation, and the UI captures a justification then drops it. Plan 58.8-03 is therefore essential, not just follow-up wiring.

Note: GitNexus MCP resources were not available in this session, so Codex verified by source inspection.

### Plan 58.8-01

#### Strengths

- Correctly targets the hook DLL decision helpers. `classify_and_log_path` returns deny from pipe, cache, degraded, isolated, and resync branches, then already has a single post-decision diagnostic block at `dlp-hook-dll/src/trampolines.rs:411` and `dlp-hook-dll/src/trampolines.rs:815`, making it a good place to add one override emission path.
- Preserves existing approved-override behavior: denied responses with `approval_override == Some(true)` already allow the operation in path and handle flows at `dlp-hook-dll/src/trampolines.rs:310` and `dlp-hook-dll/src/trampolines.rs:691`.
- The bounded cooldown requirement is appropriate because a single blocked application can repeatedly hit the same deny branch.

#### Concerns

- **MEDIUM:** "Submitted asynchronously" is overstated if implemented with existing `send_raw_oneway`. That helper still connects, writes, flushes, and closes on the hooked thread with a 50ms connect budget at `dlp-hook-dll/src/pipe_client.rs:360` and `dlp-hook-dll/src/pipe_client.rs:381`. It is fire-and-forget from a response perspective, but not fully async.
- **MEDIUM:** Plan should explicitly require emission after the final `decision/result` variable, not inside individual deny arms. There are many return paths in `classify_and_log_path`, including cache deny at `dlp-hook-dll/src/trampolines.rs:353` and isolated deny at `dlp-hook-dll/src/trampolines.rs:407`; placing the hook too early could miss non-pipe deny paths.
- **LOW:** Tests need a way to observe one-way frames. `pipe_client::send_health_snapshot` already uses `send_raw_oneway` for one-way IPC at `dlp-hook-dll/src/pipe_client.rs:322`, but the test plan does not mention adding a test seam for override frames.

#### Suggestions

- Rename the plan language from "asynchronously" to "one-way, bounded blocking budget," unless a background queue is actually introduced.
- Add an explicit assertion that `approval_override == Some(true)` does not emit `RequestOverride`, because those branches allow the operation.
- Include a test for handle-based deny with an empty path, since `classify_and_log_handle` may only have `handle:<value>` resource context at `dlp-hook-dll/src/trampolines.rs:821`.

#### Risk Assessment

**MEDIUM.** The change is localized, but it runs in hot file-operation paths and can add latency if pipe connection attempts stack up.

### Plan 58.8-02

#### Strengths

- Correctly identifies the production initialization gap: `AppState` currently has `diagnostic_store` only at `dlp-server/src/lib.rs:78`, and production sets it to `None` at `dlp-server/src/main.rs:297`.
- Correctly places `/admin/health` in the protected router model. Existing protected routes are built separately at `dlp-server/src/admin_api.rs:1112`, and `/admin/diagnostics` is already JWT-protected there at `dlp-server/src/admin_api.rs:1279`.
- The proposed store mirrors a real existing pattern: `DiagnosticSnapshotStore` uses `DashMap`, per-key retention, and global key eviction at `dlp-server/src/diagnostic_store.rs:40` and `dlp-server/src/diagnostic_store.rs:124`.

#### Concerns

- **HIGH:** The plan calls `POST /agents/{id}/health` "public" and accepts spoofing. Current public agent routes are genuinely unauthenticated, including `/agents/{id}/heartbeat` and `/audit/events` at `dlp-server/src/admin_api.rs:1078` and `dlp-server/src/admin_api.rs:1083`. For a dashboard that operators may trust, accepting forged health snapshots can create false healthy/critical states.
- **MEDIUM:** `GET /admin/health` response mapping needs to preserve the TUI contract, not just raw `HookHealthSnapshot`. Raw snapshots have `current_fail_state`, not `overall_status`, at `dlp-common/src/hook_ipc.rs:475`.
- **LOW:** The route docs use both `/agents/{id}/health` and `/agents/:id` language. The codebase uses axum's `{id}` syntax in routes, e.g. `dlp-server/src/admin_api.rs:1080`; keep the implementation consistent.

#### Suggestions

- Add at least weak authenticity: validate that the path `agent_id` exists in the agents table, and prefer reusing the configured agent secret if available.
- Make `HealthSnapshotStore::get_dashboard_snapshot` deterministic for empty state and multi-agent aggregation; tests should cover no snapshots, mixed healthy/degraded/critical, and stale timestamps.
- Update `AppState::Debug` to include the new health store, mirroring existing diagnostic-store debug output at `dlp-server/src/lib.rs:123`.

#### Risk Assessment

**MEDIUM-HIGH.** The server wiring is straightforward, but unauthenticated health ingestion can undermine operator trust unless explicitly treated as untrusted telemetry.

### Plan 58.8-03

#### Strengths

- Correctly fixes a real semantic bug: the agent currently submits approval immediately after receiving a hook DLL override request at `dlp-agent/src/service.rs:1967`, using `req.justification` at `dlp-agent/src/service.rs:1974`.
- Correctly identifies that UI justification is currently captured and then dropped. The UI receives `OverrideDialogResult::Approved { justification }` at `dlp-user-ui/src/ipc/pipe1.rs:209`, logs it, then sends `Pipe1UiMsg::UserConfirmed { request_id }` without the justification at `dlp-user-ui/src/ipc/pipe1.rs:216`.
- The health push loop builds on existing aggregation: `HealthAggregator::get_current_status()` already returns status plus latest snapshot at `dlp-agent/src/health_aggregator.rs:223`.

#### Concerns

- **HIGH:** The files list omits `dlp-user-ui/src/ipc/messages.rs`. The UI has duplicated IPC enums, and `Pipe1UiMsg::UserConfirmed` is defined there without justification at `dlp-user-ui/src/ipc/messages.rs:47`. Updating only `dlp-agent/src/ipc/messages.rs` will break or silently mismatch JSON shape.
- **HIGH:** Current pending override storage is not usable for server submission. `OVERRIDE_PENDING` stores only `session_id` and `created_at` at `dlp-agent/src/ipc/pipe1.rs:49`, and current `UserConfirmed` handling only emits an audit event at `dlp-agent/src/ipc/pipe1.rs:290`; it has no `OverrideRequest` fields needed to build `ApprovalRequest`.
- **MEDIUM:** The agent service already has reserved health push fields set to `None` at `dlp-agent/src/service.rs:2473`, so shutdown wiring must update construction and shutdown paths, not just add the loop.

#### Suggestions

- Add `dlp-user-ui/src/ipc/messages.rs` to the plan artifacts.
- Replace `OverrideContext` with a struct containing requester SID, object ID, action, destination scope, resource path, and generated request ID, or add a separate pending approval map owned by `service.rs`.
- Add tests for: cancel does not submit, confirm submits exactly once with UI justification, unknown confirmation is ignored, and pending context is removed after submit.

#### Risk Assessment

**HIGH.** This is the core DIFF-01 semantic fix and crosses hook IPC, agent service state, pipe1 IPC, duplicated UI message types, and server approval submission.

### Plan 58.8-04

#### Strengths

- Correctly recognizes broad compile impact from adding `AppState.health_snapshot_store`: there are 38 `AppState { ... }` literals across server source/tests today.
- The admin CLI auth test is well targeted. `get_self_health()` delegates to `self.get("admin/health")` at `dlp-admin-cli/src/client.rs:597`, and `get()` applies bearer auth through `apply_auth` at `dlp-admin-cli/src/client.rs:233`.
- The 401 test is necessary because `/admin/diagnostics` already has an unauthenticated 401 test at `dlp-server/src/admin_api.rs:12451`, and `/admin/health` should match that boundary.

#### Concerns

- **MEDIUM:** This plan overlaps with Plan 58.8-02, which already says to "update all `AppState` struct literals." If run by separate agents, both may touch the same 38 literals and conflict.
- **MEDIUM:** The CLI mock response must match the dashboard shape the TUI expects, not just any non-empty JSON. The renderer expects fields like `overall_status`, `injected_pids`, and `cache_hit_rate_60s`.
- **LOW:** The plan only mentions `dlp-admin-cli/src/client.rs`; if typed health response structs are introduced in Plan 02, client tests should validate those fields rather than raw `serde_json::Value`.

#### Suggestions

- Move all `AppState` literal updates into Plan 58.8-02 or Plan 58.8-04, not both. Keep them in 58.8-02 because it owns the field addition.
- Add a test that `GET /admin/health` with a valid token returns `snapshot` and `history`, not only the unauthenticated 401 path.
- Make the CLI test assert the exact Authorization header and at least one expected snapshot field.

#### Risk Assessment

**MEDIUM.** Mostly compile/test cleanup, but overlap with Plan 02 creates coordination risk and can waste time resolving conflicts.

### Overall Risk

**HIGH until Plan 58.8-03 is tightened.** The plans can achieve the phase goal, but only if DIFF-01 is treated as an end-to-end semantic change: hook emits request, agent stores full pending context, UI returns justification, and server submission happens only after confirmation. DIFF-04 is lower-risk mechanically, but public health ingestion should be called out as untrusted or authenticated before operators rely on it.

## Consensus Summary

Only Codex was invoked for this review cycle (Claude was skipped as the executing runtime, and no other external AI CLIs were requested or available). The consensus below is therefore derived entirely from Codex's source-grounded findings.

### Agreed Strengths

- The phase targets the correct blockers: `IpcPayloadV1::RequestOverride` emission from hook DLL deny paths and the missing `GET /admin/health` route / uninitialized `diagnostic_store`.
- Existing protocol and store primitives (`IpcPayloadV1::RequestOverride`, `DiagnosticSnapshotStore`, `HealthAggregator::get_current_status`, admin-router JWT protection) make the goals feasible.
- Source-grounded evidence confirms the cited file locations and current behavior.

### Agreed Concerns

- **HIGH:** Plan 58.8-02 designates `POST /agents/{id}/health` as public/unauthenticated, which conflicts with the research requirement to reuse agent auth and lets forged health snapshots distort the operator dashboard.
- **HIGH:** Plan 58.8-03's deferred override submission is under-specified: `OVERRIDE_PENDING` stores only `session_id`/`created_at`, the synchronous Pipe 1 dispatch lacks an async handoff, and both duplicated `Pipe1UiMsg::UserConfirmed` definitions must be updated.
- **HIGH:** Plan 58.8-03's file list omits `dlp-user-ui/src/ipc/messages.rs`, so updating only `dlp-agent/src/ipc/messages.rs` would break or silently mismatch the UI-to-agent JSON shape.
- **MEDIUM:** Plans 58.8-02 and 58.8-04 both claim responsibility for updating every `AppState` literal, creating duplication/conflict risk.
- **MEDIUM:** Plan 58.8-01's "submitted asynchronously" language overstates `send_raw_oneway` behavior; it is fire-and-forget but still blocks the hooked thread for connect/write/flush with a 50ms budget.
- **MEDIUM:** Plan 58.8-01 should require override emission after the final `decision/result` variable to avoid missing cache/isolated/resync deny paths.
- **MEDIUM:** Plan 58.8-02's `GET /admin/health` response mapping must preserve the TUI contract (`overall_status`, etc.) rather than expose raw `HookHealthSnapshot` fields such as `current_fail_state`.
- **MEDIUM:** Plan 58.8-03 must update agent service construction and shutdown paths because reserved health-push fields are currently set to `None`.
- **MEDIUM:** Plan 58.8-04's CLI mock response must match the exact dashboard shape consumed by the TUI.
- **LOW:** Test coverage gaps: one-way override frame observation in Plan 01, route-doc `{id}` vs `:id` consistency in Plan 02, typed response validation in Plan 04.

### Divergent Views

None — only one reviewer was invoked. The findings above should be treated as a single source of adversarial input and validated by the planner during `--reviews` incorporation.
