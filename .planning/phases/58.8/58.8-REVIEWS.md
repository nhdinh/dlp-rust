# Cross-AI Plan Review — Phase 58.8

## Codex Review

### Summary

The phase is directionally correct: it targets the real missing hook-DLL trigger and the absent `/admin/health` server route. The highest-risk gaps are DIFF-01 semantics and `/agent/health` security. The plans assume the existing override workflow already provides a user-confirmed, justified server approval request, but the source shows the agent submits to the server immediately with an empty DLL-provided justification, while the UI confirmation path drops the user's justification. On DIFF-04, the health store and admin route design are reasonable, but the planned "agent-authenticated" ingest endpoint is actually unauthenticated and not even per-agent keyed for `/agent/health`.

### Plan 58.8-01: Hook DLL Override Trigger

**Strengths**

- Correctly targets the two central hook decision helpers: `classify_and_log_path` and `classify_and_log_handle` exist at `dlp-hook-dll/src/trampolines.rs:163` and `dlp-hook-dll/src/trampolines.rs:614`.
- The requested IPC payload exists: `IpcPayloadV1::RequestOverride` is defined at `dlp-common/src/hook_ipc.rs:92`, and `OverrideRequest` has the planned fields at `dlp-common/src/hook_ipc.rs:383`.
- Fire-and-forget transport is consistent with existing one-way pipe helpers; `send_raw_oneway` uses a 50ms connect timeout and performs no read at `dlp-hook-dll/src/pipe_client.rs:360`.

**Concerns**

- **HIGH:** This plan does not actually prove DIFF-01 round-trip behavior. The existing agent submits an approval request to the server immediately when it receives a DLL request at `dlp-agent/src/service.rs:1947` and `dlp-agent/src/service.rs:1967`, before the UI confirms. The UI captures justification at `dlp-user-ui/src/ipc/pipe1.rs:209`, but then sends only `Pipe1UiMsg::UserConfirmed { request_id }` at `dlp-user-ui/src/ipc/pipe1.rs:216`; the message type has no justification field at `dlp-agent/src/ipc/messages.rs:61`.
- **MEDIUM:** The proposed integration test re-export may not compile as written. `classify_and_log_path` is `pub(crate)` at `dlp-hook-dll/src/trampolines.rs:163`, so `pub use trampolines::classify_and_log_path` from `lib.rs` cannot expose it to an integration test unless the function visibility is changed under `cfg`.
- **MEDIUM:** A global per-path `HashMap<String, Instant>` cooldown can grow without bound if many unique paths are denied. The plan limits repeated spam but not memory growth.
- **LOW:** The plan says "Every DENY decision emits" but inserts only after helper-level `result.is_some()`. That is probably correct for these helpers, but tests should include cache/fail-mode denies, not only pipe-returned denies.

**Suggestions**

- Add DIFF-01 acceptance for "server approval is submitted only after user confirmation, with the entered justification," or explicitly declare that as a separate blocker.
- Use a bounded cooldown structure or periodic eviction, e.g. cap entries and remove expired keys during insert.
- Gate `classify_and_log_path` visibility with `#[cfg(any(test, feature = "test-helpers"))] pub fn ...` or add a dedicated public test helper wrapper.

**Risk Assessment:** **HIGH** because the DLL trigger is useful, but the current plan can still leave "user-initiated override" semantically broken.

### Plan 58.8-02: Server-Side Health Infrastructure

**Strengths**

- Correctly identifies the production bug: `diagnostic_store` is `None` in production `AppState` construction at `dlp-server/src/main.rs:297`, while `/admin/diagnostics` returns empty data when the store is absent at `dlp-server/src/admin_api.rs:5429`.
- The admin route placement is sound: protected routes are wrapped with `admin_auth::require_auth` at `dlp-server/src/admin_api.rs:1291`, and `/admin/diagnostics` is already in that protected section at `dlp-server/src/admin_api.rs:1279`.
- The dashboard field mapping is necessary because raw `HookHealthSnapshot` has `current_fail_state`, not `overall_status` or `fail_state`, at `dlp-common/src/hook_ipc.rs:475`.

**Concerns**

- **HIGH:** The plan calls `POST /agent/health` "agent-authenticated," but placing it in `public_routes` makes it unauthenticated (`dlp-server/src/admin_api.rs:1066`). `per_agent_config()` is only rate limiting, not auth, and its extractor only recognizes `/agents/{id}` paths at `dlp-server/src/rate_limiter.rs:55`, so `/agent/health` falls back to IP at `dlp-server/src/rate_limiter.rs:40`.
- **MEDIUM:** Returning `AppError::BadRequest("health snapshot store not configured")` for missing server wiring is misleading; that is server configuration, not a client request problem.
- **LOW:** Adding `AppState.health_snapshot_store` will also require the lib test helper at `dlp-server/src/lib.rs:267`, not just `admin_api.rs` and integration tests.

**Suggestions**

- Either add real agent authentication for `/agent/health`, or downgrade the plan language to "unauthenticated telemetry endpoint" and document why that is acceptable.
- Change the route to `/agents/{id}/health` if you want the existing rate-limit extractor to key per agent.
- Return `500`/internal error for missing store in production, or make the field non-optional if production must always initialize it.

**Risk Assessment:** **MEDIUM-HIGH** due to the auth/rate-limit mismatch on an ingest endpoint.

### Plan 58.8-03: Agent Health Push + Round-Trip Test

**Strengths**

- Correctly targets the existing agent health aggregator; `get_current_status()` returns the latest snapshot at `dlp-agent/src/health_aggregator.rs:225`.
- The agent service already has reserved `health_push_shutdown` and `health_push_handle` fields at `dlp-agent/src/service.rs:1396`, and currently initializes them to `None` at `dlp-agent/src/service.rs:2473`, so the lifecycle insertion point is real.
- The round-trip server test is the right kind of integration test for DIFF-04.

**Concerns**

- **MEDIUM:** The proposed `ServerClient::submit_health_snapshot` error style does not match the file. Existing methods return `Result<_, ServerClientError>` and manually convert non-2xx responses at `dlp-agent/src/server_client.rs:913`; the plan's `.context("failed to submit health snapshot")` would not fit without changing the error model.
- **MEDIUM:** `HealthAggregator::get_current_status()` returns `Option<(HealthStatus, HookHealthSnapshot)>`, not just a snapshot, at `dlp-agent/src/health_aggregator.rs:225`; the loop plan needs explicit destructuring.
- **MEDIUM:** The shutdown path currently has no health-push stop section; `run_loop_shutdown` stops many tasks explicitly, e.g. config at `dlp-agent/src/service.rs:4566` and audit at `dlp-agent/src/service.rs:4686`. Plan 03 says to await shutdown, but should specify exactly where.

**Suggestions**

- Mirror `post_bypass`'s status handling style for `submit_health_snapshot`.
- Add focused tests for non-2xx server responses, not only unreachable server.
- Specify shutdown insertion near the diagnostic/health task fields and add a unit test or compile assertion covering `RunLoopContext` construction.

**Risk Assessment:** **MEDIUM**. The feature is straightforward, but lifecycle and error-type mismatches need correction.

### Plan 58.8-04: Test Propagation + Admin CLI Test

**Strengths**

- The admin CLI client method exists and calls `GET admin/health` through the generic authenticated `get()` path at `dlp-admin-cli/src/client.rs:597`; auth is applied by `apply_auth` at `dlp-admin-cli/src/client.rs:221`.
- The WireMock testing pattern already exists in the same file at `dlp-admin-cli/src/client.rs:765`.
- The plan correctly anticipates broad `AppState` literal fallout; integration tests construct many literals under `dlp-server/tests`, e.g. `diagnostics_api_integration.rs:76`.

**Concerns**

- **MEDIUM:** The listed integration-test files are not enough as a verification strategy unless the executor also searches all literals. `AppState` literals also exist in `dlp-server/src/admin_api.rs:5774` and `dlp-server/src/lib.rs:267`.
- **LOW:** Several listed files do not currently construct `AppState` according to `rg`, so the plan may waste effort while still missing source test literals if followed mechanically.
- **LOW:** The admin CLI test only validates JSON parsing and path success. It does not assert that the Authorization header was sent, even though `/admin/health` is intended to be JWT-protected.

**Suggestions**

- Replace the fixed file list with `rg -n "AppState \{" dlp-server/src dlp-server/tests` as an explicit task.
- In the WireMock test, assert `Authorization: Bearer test-token`.
- Add one server route test proving unauthenticated `GET /admin/health` returns `401`, mirroring diagnostics auth tests at `dlp-server/src/admin_api.rs:12451`.

**Risk Assessment:** **LOW-MEDIUM**. Mostly mechanical, but incomplete literal discovery could cause avoidable compile failures.

### Overall Risk

**HIGH** until DIFF-01 semantics and `/agent/health` authentication language are corrected. The implementation work is feasible, but the current plans can pass their proposed tests while still failing the phase's real intent: a user-confirmed override request with justification, and a properly protected or honestly documented health ingest path.

## Consensus Summary

Only one external reviewer (Codex) produced output. The current Claude Code instance was skipped for independence. The consensus below reflects Codex's findings.

### Agreed Strengths

- Accurate root-cause diagnosis with source-verified evidence for both DIFF-01 and DIFF-04.
- Plans build on existing, correctly-shaped infrastructure (`IpcPayloadV1::RequestOverride`, `HookHealthSnapshot`, protected admin router, WireMock client tests).
- The four plans are correctly wave-ordered: hook-DLL trigger and server-side store in Wave 1, agent push and test propagation in Wave 2.

### Agreed Concerns

- **DIFF-01 semantics (HIGH):** The plan can emit override requests and still not achieve a user-confirmed, justified approval because the agent submits immediately and the UI drops the justification.
- **`/agent/health` auth language (HIGH):** The plan calls the endpoint "agent-authenticated" but places it in the unauthenticated public route set; the per-agent rate limiter does not key on `/agent/health`.
- Plan 03 has lifecycle and error-model mismatches that need correction before implementation (MEDIUM).
- Plan 04's fixed file list may miss `AppState` literals in `admin_api.rs` and `lib.rs` test helpers (MEDIUM).

### Divergent Views

None — only one external reviewer participated.
