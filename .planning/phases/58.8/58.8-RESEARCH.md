# Phase 58.8: Fix DIFF-01 and DIFF-04 - Research

**Researched:** 2026-07-09
**Domain:** Rust / Windows DLP hook DLL, agent-server IPC, admin API
**Confidence:** HIGH for root-cause and code locations; HIGH for the server-side health store shape because it mirrors the existing `DiagnosticSnapshotStore`; MEDIUM for the exact TUI health response fields because the admin TUI expects a dashboard-specific snapshot shape that differs from the raw `HookHealthSnapshot`.

## Summary

The v0.10.0 milestone integration audit found two remaining DIFF wiring gaps:

1. **DIFF-01** — The hook DLL deny path never emits `IpcPayloadV1::RequestOverride`, so users cannot initiate an override from a blocked file operation. The agent-side `OverrideRequest` handler, the user UI dialog, and the server approval submission are already wired in `dlp-agent/src/service.rs:1940-2000` [VERIFIED: codebase]. The missing trigger is entirely in `dlp-hook-dll/src/trampolines.rs`.

2. **DIFF-04** — `dlp-admin-cli/src/client.rs::get_self_health()` calls `GET /admin/health`, but no matching route exists in `dlp-server/src/admin_api.rs`. In addition, `diagnostic_store` is initialized to `None` in production `AppState` construction (`dlp-server/src/main.rs:297`), so `GET /admin/diagnostics` returns empty snapshots even though the `DiagnosticSnapshotStore` implementation is complete [VERIFIED: codebase, CITED: .planning/milestones/v0.10.0-MILESTONE-AUDIT-2026-07-09.md].

**Primary recommendation for DIFF-01:** Add a small helper in `dlp-hook-dll/src/trampolines.rs` that, on a DENY decision from `classify_and_log_path` / `classify_and_log_handle`, emits a fire-and-forget `IpcPayloadV1::RequestOverride` frame over the existing named pipe. The original operation must still be denied while the override request is submitted asynchronously; an approved override can only affect future operations via the existing `HookResponse.approval_override` path.

**Primary recommendation for DIFF-04:**
- Add a server-side in-memory `HealthSnapshotStore` in `dlp-server/src/health_snapshot_store.rs`, modeled on `dlp-server/src/diagnostic_store.rs`, to retain the latest hook health snapshot and rolling history per agent.
- Add `POST /agent/health` (agent-authenticated, rate limited) so the agent can push `HookHealthSnapshot` data to the server.
- Add `GET /admin/health` (admin JWT) returning `{ "snapshot": <dashboard snapshot>, "history": [...] }`.
- Initialize `diagnostic_store` in `dlp-server/src/main.rs` with a real `DiagnosticSnapshotStore` instance.
- Wire a small agent-side periodic push task that POSTs the latest aggregated health snapshot to the server.

### Pattern 1: Fire-and-forget override request from hook DLL

**What:** After `classify_and_log_path`/`classify_and_log_handle` returns `Some(deny)`, serialize `IpcPayloadV1::RequestOverride(OverrideRequest { ... })` and send it via `pipe_client::send_raw_request` with a short timeout.

**When to use:** On every DENY where the user might want to request an override.

**Example:**

```rust
// Source: dlp-hook-dll/src/trampolines.rs (proposed)
fn emit_override_request(path: &str, action: &str) {
    let req = dlp_common::hook_ipc::OverrideRequest {
        requester_sid: crate::get_current_user_sid(),
        data_object_id: path.to_string(),
        action: action.to_string(),
        destination_scope: None,
        justification: String::new(), // user fills this in UI
        resource_path: path.to_string(),
    };
    let envelope = dlp_common::hook_ipc::IpcEnvelope::V1(dlp_common::hook_ipc::IpcMessageV1 {
        payload: dlp_common::hook_ipc::IpcPayloadV1::RequestOverride(req),
    });
    if let Ok(bytes) = bincode::serialize(&envelope) {
        let _ = crate::pipe_client::send_raw_request(crate::current_pipe_name(), &bytes, 50);
    }
}
```

### Pattern 2: Server-side in-memory store with bounded retention

**What:** Use `DashMap<String, VecDeque<HookHealthSnapshot>>` keyed by `agent_id`, with a per-agent cap and LRU eviction for the number of agents.

**When to use:** For both `DiagnosticSnapshotStore` and the new `HealthSnapshotStore`.

**Example:**

### Pattern 3: Agent health push on a bounded interval

**What:** A tokio task in `dlp-agent/src/service.rs` reads `health_aggregator.get_current_status()` every 60 seconds and POSTs the snapshot to `POST /agent/health` when a server client is available.

**When to use:** Whenever the agent needs to mirror local health state to the server.

### Pattern 4: Admin TUI health response shape

**What:** `GET /admin/health` returns a JSON object with `snapshot` and `history`. The `snapshot` must expose fields the TUI reads: `overall_status`, `injected_pids`, `patched_modules`, `pipe_round_trips_60s`, `cache_hit_rate_60s`, `fail_state` [VERIFIED: dlp-admin-cli/src/screens/render.rs:4763-4780]. The raw `HookHealthSnapshot` uses `current_fail_state: u8` and lacks `overall_status`, so the server must map to a dashboard-specific type.

**When to use:** Only in the `GET /admin/health` response construction.

## Anti-Patterns to Avoid

- **Do not block the deny path waiting for override approval.** The override request is fire-and-forget; the original operation is denied immediately. Approval only helps future operations via `HookResponse.approval_override`.
- **Do not persist health or diagnostic snapshots to disk.** Both stores must remain in-memory only per CLAUDE.md / DIFF-02 security constraints.
- **Do not expose `GET /admin/health` without JWT protection.** It must be mounted inside the protected admin router.
- **Do not accept `POST /agent/health` without agent authentication.** Reuse the existing agent auth middleware/rate limiter used for `/audit/events` and `/audit/bypass`.
- **Do not initialize `diagnostic_store` to `None` in production.** `dlp-server/src/main.rs` must construct a real `DiagnosticSnapshotStore`.

## Open Questions / Risks

| Risk | Mitigation |
|------|------------|
| The agent's `HealthAggregator` status computation (`Healthy`/`Degraded`/`Critical`) may differ from the TUI's `overall_status` string expectations. | Map `HealthStatus` to the TUI's expected strings (`healthy`, `degraded`, `critical`) in the server response builder. |
| Agent push of health snapshots could flood the server if the interval is too short or the payload is too large. | Cap history at 12 entries per agent, use a 60-second push interval, and apply per-agent rate limiting on `POST /agent/health`. |
| `RequestOverride` emission from every DENY could generate many override requests for repeated operations. | Consider a short per-path cooldown or only emit on the first DENY in a window; document this in the plan if implemented. |
