## Critical Issues

### CR-01: Syslog drain backoff adds nanoseconds as seconds — one transient failure disables forwarding for years

**File:** `dlp-server/src/main.rs:556-561` and `dlp-server/src/main.rs:604-609` (`compute_next_attempt`)
**Issue:** Still present and unguarded (no unit test bounds the computed
backoff; the only syslog tests cover the config handlers and DB tables).
```rust
let jitter = (std::time::SystemTime::now()
    .duration_since(std::time::UNIX_EPOCH)
    .unwrap_or_default()
    .as_nanos()                                  // ~1.7e18 (ns since epoch)
    % (delay as u128 * 500_000_000 + 1)) as u64; // jitter ∈ [0, delay·5e8) NANOSECONDS
let backoff = std::time::Duration::from_secs(delay + jitter); // read back as SECONDS
```
`jitter` is a nanosecond-magnitude value (modulus `500_000_000` = 0.5 s in ns)
but is added to `delay` (whole seconds) and passed to `Duration::from_secs`,
i.e. interpreted as seconds. With `delay` capped at 60 the backoff reaches up
to `60·5e8 = 3e10` s (~951 years); even on the first failure (`delay == 1`) it
can be ~`5e8` s (~15.8 years). The same value is written into the retry
timestamp via `compute_next_attempt` (`Utc::now() + from_std(backoff)`), so a
single transient syslog/TLS error schedules retries in the far future and the
drain thread sleeps an effectively-infinite duration. For the largest values
`chrono::Duration::from_std(backoff)` silently overflows to `zero()` via
`.unwrap_or_default()` (main.rs:610), so the bug manifests as either "never
retry" or "retry immediately" depending on magnitude — masking itself.
**Fix:**
```rust
let nanos = std::time::SystemTime::now()
    .duration_since(std::time::UNIX_EPOCH)
    .unwrap_or_default()
    .subsec_nanos() as u64;                       // 0..1e9, bounded
let jitter = std::time::Duration::from_nanos(nanos % 500_000_000); // 0..0.5s
let backoff = std::time::Duration::from_secs(delay) + jitter;
```
Apply the identical change in `compute_next_attempt` and add a unit test
asserting the computed `backoff` is within `[delay, delay + 0.5s]` for
`delay ∈ {1,2,4,8,16,32,60}`.

### CR-02: Agent-facing approval endpoints are fully unauthenticated — signed-token exfiltration and forged requests

**File:** `dlp-server/src/admin_api.rs:1185-1197` (route wiring) + `dlp-server/src/approval_api.rs:786-858` (`submit_approval_request`), `861-926` (`list_active_approvals`); consumer `dlp-agent/src/server_client.rs:888-942`
**Issue:** The comment at `admin_api.rs:1185` claims these are
"agent-authenticated", but unlike `/agents/{id}/health` (`:1164-1172`) none of
the three routes carries the `agent_auth_middleware` layer, and the handlers
take no `Authorization`/`Extension<String>`:
- `POST /agent/approval-request` (`approval_api.rs:786`) inserts a pending
  approval using `requester_sid`, `data_object_id`, `allowed_action`,
  `destination_scope`, `justification` taken **entirely from the request body**,
  then emits an `ApprovalRequest` audit event attributed to the literal string
  `"agent"` (`:842`). Any network client can forge requests for any SID/object
  and spam the admin workflow + audit log.
- `GET /agent/approvals/active` (`approval_api.rs:861`) returns every
  approved+unexpired approval **and freshly signs an Ed25519 JWT for each**
  (`:921`, `state.approval_token_service.sign_token(&claims)`), handing the
  signed `token` + `claims` to any caller. The agent consumes exactly these
  tokens into its local approval cache
  (`server_client.rs:888-910`, `sync_active_approvals`). An unauthenticated
  caller on the network therefore obtains the same server-signed approvals the
  agent trusts to authorize access — approval-token theft / DLP bypass.

There is no integration test asserting auth on either endpoint (grep for
`approvals/active` / `approval-request` / `active_approvals` under
`dlp-server/tests` returns nothing), so the gap is unguarded. This is strictly
worse than the previous review's "information disclosure" framing (old WR-06):
it is credential issuance to anonymous callers.
**Fix:** Apply the agent middleware and bind identity to the path/body:
```rust
.route(
    "/agent/approval-request",
    post(approval_api::submit_approval_request)
        .route_layer(rate_limiter::per_agent_config())
        .layer(middleware::from_fn_with_state(Arc::clone(&state), agent_auth_middleware)),
)
.route(
    "/agent/approvals/active",
    get(approval_api::list_active_approvals)
        .route_layer(rate_limiter::per_agent_config())
        .layer(middleware::from_fn_with_state(Arc::clone(&state), agent_auth_middleware)),
)
```
`GET /agent/approvals/public-key` may stay public (it is a verifying key). Move
the two endpoints out of the "Unauthenticated" doc block and add a 401 test
mirroring `get_agent_auth_hash_requires_admin_auth`. Inside
`submit_approval_request`, prefer the authenticated `agent_id`/`Extension` over
body-supplied identity fields.

## Warnings

### WR-01: UI `Pipe1AgentMsg` enum omits `ApprovalGranted`/`ApprovalRejected` — approvals are silently dropped

**File:** `dlp-user-ui/src/ipc/messages.rs:17-45` vs `dlp-agent/src/ipc/messages.rs:52-67`; drop site `dlp-user-ui/src/ipc/pipe1.rs:135-141, 305-326`
**Issue:** The agent-side `Pipe1AgentMsg` defines `ApprovalGranted` /
`ApprovalRejected` (round-trip tested at `messages.rs:463-504`), but the UI
"mirror" enum omits them and `handle_agent_msg` matches only
`BlockNotify/OverrideRequest/ClipboardRead/PasswordDialog/Ping` with no
catch-all. Because the enum is internally tagged with no `#[serde(other)]`, an
approval frame fails `serde_json::from_slice` (`pipe1.rs:135`), hits the `Err`
arm, logs at error level, and `continue`s — the approval notification is lost.
The UI header (`messages.rs:1`) claims it "mirrors dlp-agent/src/ipc/messages.rs";
it does not.
**Fix:** Add the two variants to the UI enum with identical field shapes and
handle them in `handle_agent_msg`, or add `#[serde(other)]` + an explicit
`Unknown` variant so unknown messages are counted rather than lost. Keep the two
enums in sync via a shared crate or a compile-time assertion.

### WR-02: Single shared `DLP-AGENT` hash authenticates every agent → cross-agent impersonation

**File:** `dlp-server/src/admin_api.rs:129-182` (compare at `:159-178`); client `dlp-agent/src/server_client.rs:462-464`
**Issue:** `agent_auth_middleware` parses `Authorization: DLP-AGENT <agent_id>:<hash>`
but compares `<hash>` (now constant-time — good) against one global
`DLPAuthHash` (`:159`). `agent_id` is only inserted into extensions (`:180`);
it is never bound to a per-agent secret. Any party holding the single hash can
present any `agent_id` and pass. `post_agent_health_handler` (`:5608`) then only
checks `Extension(agent_id) == Path(id)` — both attacker-controlled — so one
leaked hash forges health/diagnostics for every agent and defeats the
per-tenant isolation the dashboard relies on.
**Fix:** Store/verify a per-agent credential keyed by `agent_id`
(`agent_auth_hashes` map) and reject when the presented `agent_id` has no
enrolled secret; at minimum bind the hash lookup to the claimed `agent_id`.

### WR-03: Missing/unprovisioned auth hash returns 500 and echoes the DB error to an unauthenticated caller

**File:** `dlp-server/src/admin_api.rs:158-163`; error mapping `dlp-server/src/lib.rs:221-247`
**Issue:** `CredentialsRepository::get(...).map_err(AppError::Database)?`
converts every failure — including "no hash enrolled yet" — into
`AppError::Database`, which `IntoResponse` maps to **500** and whose body is the
raw `rusqlite` string (`"database error: Query returned no rows"`). Because this
route is public, an anonymous caller learns the credential store is empty, and a
genuine DB outage is indistinguishable from a missing credential in
logs/metrics. The same echo affects the (now protected) `get_agent_auth_hash`
(`:1937`), whose doc promises 404 but actually returns 500.
**Fix:** Distinguish not-found from a real storage failure and return
`AppError::Unauthorized` (401) for no/wrong credential; reserve 500 for real DB
errors. Stop echoing internal error text to clients for `Database`/`Internal`
(emit a generic body; log the detail server-side).

### WR-04: Concurrent, unsynchronized `WriteFile`s to the same Pipe-1 handle; `SendableHandle` safety comment is false

**File:** `dlp-agent/src/ipc/pipe1.rs:56-69, 252, 389-403, 413-471`
**Issue:** The `SendableHandle` comment (`:55-56`) claims the handle is
"confined to the single-threaded pipe server," but `send_to_ui` (`:389`),
`send_password_dialog` (`:413`) and `send_ping_to_all` (`:455`) are `pub` and are
called from other tokio tasks (heartbeat, password-stop, override service) while
the per-client `client_loop` task also writes responses (e.g. `Pong` at `:252`)
on the same handle. `CLIENTS.read()` only serializes the map lookup — the
subsequent `write_frame` calls from different tasks are not mutually excluded,
so two length-prefixed frames can interleave on the wire and corrupt the UI's
framing. The `unsafe impl Send/Sync` (`:68-69`) therefore rests on an invariant
the code does not uphold.
**Fix:** Serialize writes per handle — wrap each entry in a
`tokio::sync::Mutex<HANDLE>` (or a per-client write channel with a single writer
task) and hold it across the full `write_frame`. Correct the safety comment to
describe the actual synchronization.

### WR-05: User-confirmed override is lost if the server submit fails (remove-before-submit)

**File:** `dlp-agent/src/service.rs:1629-1663` (pending map `:79`; reaper `:1594`; `OVERRIDE_PENDING_TTL:1587`)
**Issue:** `confirmed_override_loop` removes the `PendingOverride` from
`OVERRIDE_PENDING` (`:1631`) and then performs the HTTP submit. On `Err(e)`
(`:1656-1662`) it only logs — there is no requeue/retry, the context is gone,
and the reaper can no longer help because the entry was already removed. This is
amplified in agent-only mode: `submit_approval_request_with_justification`
(`:1490-1506`) returns `Err` whenever `server_client` is `None`, so every
confirmed override is silently dropped after removal when no server is
configured. The fail-closed removal in the request path (`:2362`) is correct for
the request side; the confirmation side has no retry.
**Fix:** Remove the pending entry only after a confirmed-successful submit; on
failure requeue onto the channel (bounded) or leave it for the reaper and emit
an error/audit event so the approval is not silently dropped.

### WR-06: Rate limiter keys health/diagnostics on the attacker-controlled path, not the authenticated agent

**File:** `dlp-server/src/rate_limiter.rs:33-52`; wiring `dlp-server/src/admin_api.rs:1164-1181`
**Issue:** `AgentIdOrIpKeyExtractor::extract` prefers
`req.extensions().get::<String>()` (the `agent_id` set by
`agent_auth_middleware`). But the route is built as
`post(handler).route_layer(rate_limiter::per_agent_config()).layer(agent_auth_middleware)`:
`route_layer` is outer, `layer` is inner, so the rate limiter runs **before**
the auth middleware has populated the extension. At extract time no `String`
extension exists, so the extractor falls through to
`extract_agent_id_from_path` (`:40-42`) and keys on the `:id` path segment —
which is fully attacker-controlled. Combined with the single shared hash
(WR-02), one credential-holder can rotate `:id` per request to obtain a fresh
200/60s bucket each time, defeating the stated per-agent isolation
(`rate_limiter.rs:19-26`). (Unauthenticated `/audit/events` has no `:id` and
correctly falls back to peer IP; the bug is specific to the `/{id}` routes.)
**Fix:** Run the agent-auth layer outermost (e.g. apply `agent_auth_middleware`
via `.layer` on a sub-router that is then wrapped by the rate limiter), or key
the limiter on a value available pre-auth (peer IP) and enforce per-agent
fairness inside the authenticated handler. Add a test that two distinct `:id`
values with the same bearer share one bucket.

### WR-07: Override session routing still trusts the hook-supplied `pid` (incomplete CR-02 hardening)

**File:** `dlp-agent/src/service.rs:2309` (uses `req.pid`); contrast `dlp-agent/src/hook_ipc.rs:713-732` (UnhookAck uses authoritative peer PID); emit `dlp-hook-dll/src/trampolines.rs:291`
**Issue:** For `UnhookAck` the agent correctly ignores the payload `pid` and
verifies the sender with `GetNamedPipeClientProcessId` (`hook_ipc.rs:718-719`).
For `RequestOverride` it does the opposite: it routes the dialog with
`pid_to_session_id(req.pid)` (`service.rs:2309`), trusting the `pid` field the
(unprivileged, authenticated-users-writable — see WR-08/WR-09) hook pipe
carried. Any local user can connect to `\\.\pipe\DlpHookPipe` and send a
`RequestOverride` with a chosen `pid`, steering the override prompt (and its
auto-confirm under WR-08) to a session of their choice, or to a session with no
UI to force fail-closed denial. The authoritative API is already used a few
hundred lines away.
**Fix:** Resolve the session from the pipe peer, not the payload:
```rust
let peer_pid = named_pipe_client_pid(pipe); // already implemented in hook_ipc.rs
// pass peer_pid (not req.pid) into the override handler / pid_to_session_id
```
Keep `req.pid` only as a consistency hint / telemetry. Track removal of the
CR-02 follow-up.

### WR-08: Pipe 1 `RegisterSession` trusts the client-supplied `session_id` → any local user can hijack a session's UI slot

**File:** `dlp-agent/src/ipc/pipe1.rs:204-212`; DACL `dlp-agent/src/ipc/pipe_security.rs:23`
**Issue:** The Pipe-1 DACL grants `GRGW` to `AU` (Authenticated Users,
`pipe_security.rs:23`), and `handle_client` keys `CLIENTS` by the
**client-chosen** `session_id` from `RegisterSession` with no peer check
(`:204-212`): `CLIENTS.write().insert(session_id, …)` overwrites any existing
registration for that session. Any authenticated local user can therefore
connect to `\\.\pipe\DLPCommand`, send `RegisterSession { session_id: <victim> }`,
and steal the victim UI's slot — thereafter receiving the victim's
`BlockNotify`/`OverrideRequest`/`PasswordDialog` and being able to auto-confirm
overrides (compounded by WR-01/WR-07) or suppress the victim's dialogs (DoS of
the override workflow). The agent already proves the peer PID/session for
`UnhookAck` (WR-07) but not for Pipe-1 registration.
**Fix:** Bind registration to the authoritative peer: call
`GetNamedPipeClientProcessId` + `ProcessIdToSessionId` on the accepted handle
and reject `RegisterSession` whose claimed `session_id` does not match the
peer's real session; refuse to overwrite an existing live registration for the
same session.

### WR-09: Hook pipe ingests dashboard/SIEM telemetry from any authenticated user with no sender authentication

**File:** `dlp-agent/src/hook_ipc.rs:578-672` (`BypassAlert`, `JournalDegraded`, `HashEvidence`, `HealthResponse`); DACL `dlp-agent/src/ipc/pipe_security.rs:23`
**Issue:** `\\.\pipe\DlpHookPipe` is `GRGW` to Authenticated Users
(`pipe_security.rs:23`), and the agent (SYSTEM) acts on several payloads with no
sender verification:
- `HealthResponse` (`:650-672`) is fed straight into `health_aggregator`
  (`:660`) and then pushed to the server dashboard — any local user can forge
  `current_fail_state = 2` to page operators as critical, or forge healthy to
  mask a real fault.
- `BypassAlert`/`JournalDegraded` (`:578-626`) are forwarded to the SIEM via
  `bypass_tx` — forged hook-overwrite / EDR alerts.
- `HashEvidence` (`:627-647`) is inserted into `hash_cache` keyed by
  attacker-chosen `(pid, handle)` — cache poisoning.
Only `UnhookAck` (`:713`) checks the peer PID. There is no per-message
authentication, signature, or peer-PID binding on the telemetry path.
**Fix:** Bind every trusted payload to `GetNamedPipeClientProcessId(pipe)` (and
validate against the process registry where applicable), or split the pipe into
a privileged control channel (SYSTEM/BA-only DACL) for telemetry and a
least-privilege channel for classification requests. At minimum, reject
`HealthResponse`/`BypassAlert`/`HashEvidence` whose claimed `pid` does not match
the peer PID.

### WR-10: `BlockNotify` request id is not unique — responses collide under concurrent blocks

**File:** `dlp-user-ui/src/ipc/pipe1.rs:222`
**Issue:** `handle_block_notify` builds `let request_id = format!("block-{}", session_id);`.
Every block event for a session shares one id, so the agent cannot correlate
`UserConfirmed`/`UserCancelled` to a specific `BlockNotify`; two near-simultaneous
blocks (common when the hook DLL bursts) produce indistinguishable responses and
the wrong event can be confirmed/cancelled.
**Fix:** Use a per-event unique id (monotonic counter or UUID), ideally echoing
an id supplied by the agent in the `BlockNotify` payload, and have the agent key
pending block state on that id.

### WR-11: Router doc still advertises `GET /agent-credentials/auth-hash` as "Unauthenticated"

**File:** `dlp-server/src/admin_api.rs:1097-1106` (doc) vs route `:1244-1247` (protected) and handler doc `:1920-1927`
**Issue:** The router-level doc lists the auth-hash GET under "Unauthenticated",
but the route is mounted under `require_auth` and the handler's own doc explains
it must be authenticated specifically so an unauthenticated caller cannot read
the `DLP-AGENT` secret. A reviewer/operator trusting the doc will believe the
credential is world-readable and tune WAF/network policy accordingly.
**Fix:** Move `GET /agent-credentials/auth-hash` out of the "Unauthenticated"
doc block into the authenticated section; keep router docs mechanically in sync
with the actual layer (a compile-checked route table would prevent recurrence).

## Info

### IN-01: "LRU" eviction is actually FIFO-by-first-seen

**File:** `dlp-server/src/health_snapshot_store.rs:11, 67-68, 144-152`
**Issue:** Docs/field comments claim LRU eviction, but `key_queue` is only
pushed on `is_new_key`; re-ingesting an existing agent never refreshes its
position. A hot agent inserted early is evicted before a cold agent inserted
later. The global cap (`max_keys = 10_000`) still bounds memory, so this is a
mislabeled policy rather than a memory bug.
**Fix:** Rename "LRU" to "FIFO"/"insertion-order", or refresh the key position
on re-ingest.

### IN-02: Pipe handle leak on the `create_pipe` error path in the hook accept loop

**File:** `dlp-agent/src/hook_ipc.rs:481, 493`
**Issue:** The loop pre-creates `next_pipe = create_pipe(&pipe_name)?;` after a
client connects (`:493`). If `create_pipe` fails, the `?` returns without
closing the still-open current `pipe` HANDLE (and the `ConnectNamedPipe` error
path at `:481` recycles correctly, but the success-then-create-fail path does
not). Minor handle leak on the error path.
**Fix:** Track the outstanding handle in a scope guard/`Drop` so every early
return closes it.

### IN-03: Handle-close ABA race when unblocking the Pipe-1 reader

**File:** `dlp-user-ui/src/ipc/pipe1.rs:111-125, 170-176`
**Issue:** The main thread `CloseHandle(pipe)`s the handle the reader thread is
blocked on inside `read_frame`. Because `SendableHandle` is `Copy`, the reader
still holds the (now-closed) HANDLE value; if the OS reuses that handle value
before `ReadFile` returns, the reader could briefly operate on an unrelated
object. In practice `ReadFile` fails fast with `ERROR_INVALID_HANDLE`, but
closing only after `reader.join()` (or `CancelIoEx` on the reader thread)
removes the window entirely. Low confidence.
**Fix:** Join the reader before closing, or cancel the pending I/O explicitly.

### IN-04: UI `connected` flag is set on connect but never cleared on disconnect/heartbeat timeout

**File:** `dlp-user-ui/src/ipc/pipe1.rs:71-73` vs `:153-161`
**Issue:** `connect_and_run` sets `*connected.write() = true` after the TCP/pipe
connect (`:71-73`) but never writes `false` when `client_loop` returns — including
the heartbeat-timeout path (`:160`, `break Err(...)`). A downstream reader of the
flag keeps observing "connected" after the agent is gone.
**Fix:** Set the flag to `false` in a `Drop`/finally on every `connect_and_run`
exit (success, read error, and heartbeat timeout), or scope it to the lifetime
of `client_loop`.
