## Summary

This is a re-review of the CURRENT tree for Phase 58.8 (user-prompted override +
server-mediated approval), performed after the `fix(58.8)` commits for
WR-01 / WR-05 / WR-06 / WR-10. None of those prior fixes were assumed correct;
each was re-traced against the live code.

Depth was concentrated on the security-relevant surface — IPC parsing and
request-id correlation, agent/server authentication and peer identity, the
rate-limiter key scope, the pending-override / BlockNotify state machine, named-
pipe framing, and secret/PII handling. The broader pre-existing server
integration suite was scanned for vacuous-assertion patterns but not re-read in
full, as it is outside the 58.8 delta.

Verified-correct (no finding): WR-06 (`AgentIdOrIpKeyExtractor` never keys on
the attacker-controlled `:id`; `main.rs` wires `ConnectInfo<SocketAddr>` so the
peer-IP fallback is real; handlers additionally enforce authenticated
`agent_id == Path(id)` — secure under either layer ordering). WR-03
(`AppError::into_response` returns a generic "internal server error" body for
5xx, so the unprovisioned-hash path is 401/404, never a leaking 500). WR-01
(`ApprovalGranted`/`ApprovalRejected` present on both agent and UI enums with
identical serde shape, plus a drift-guard test). WR-05 (pending override removed
only after the server accepts the submit). WR-10 (`mint_block_request_id` via
process-wide `AtomicU64` → `block-{session}-{seq}`). The hook-DLL
`approval_override` path is intentionally fail-closed and explicitly deferred
(granted approvals do not yet unblock the endpoint on retry); this is safe but
is the known WORKFLOW-04 follow-up, not a defect.

One defect survived the fixes and three robustness issues were newly
identified; all are warnings (no auth bypass, injection, or data loss).

## Critical Issues

None. No authentication bypass, injection, secret/PII disclosure, or data-loss
path was found in the in-scope code.

## Warnings

### WR-01: Override `classification` is derived from the deny-return enum, not the data tier

**File:** `dlp-hook-dll/src/trampolines.rs:739` and `dlp-hook-dll/src/trampolines.rs:1094`
**Issue:** Both deny sites format the wrong value as the override classification:

```rust
// line 738-740 (classify_and_log_path)
if decision.is_some() {
    let classification = decision.map(|c| format!("{c:?}")).unwrap_or_default();
    emit_override_request(path, action, handle_value, &classification);
}
// line 1093-1095 (classify_and_log_handle) — same bug with `result`
if result.is_some() {
    let classification = result.map(|c| format!("{c:?}")).unwrap_or_default();
    emit_override_request(path, action, handle_value, &classification);
}
```

`decision` / `result` are `Option<DenyReturn>` (the return-value shape:
`BoolFalse`, `InvalidHandleValue`, `StatusAccessDenied` — see the call sites at
548, 558, 607, 690, 695). `format!("{c:?}")` therefore yields `"BoolFalse"` etc.,
which becomes `OverrideRequest.classification` (`emit_override_request`,
trampolines.rs:294). The actual tier (`cache_classification: Option<Classification>`,
e.g. `trampolines.rs:456`, and the `tier_str` already computed for the isolated
branch at `trampolines.rs:626`) is in scope but never used for the override.

Blast radius (traced, not assumed):
- The value flows into the UI override dialog (`service.rs` keeps the prompt
  because the string is non-empty) — the user is shown `"BoolFalse"` as the data
  classification at the exact moment they decide whether to approve a bypass.
- It flows into the granted-override audit via
  `audit_classification_for_override` (`service.rs:1531-1538`), which does not
  recognise `"BoolFalse"` and silently defaults to `T3`, so the audit record for
  the most security-sensitive event (an approved bypass) is mislabelled.

Severity rationale (why not a blocker): authorization is unaffected — the
server re-evaluates from `requester_sid` / `data_object_id` / `action`
(`build_approval_request` carries no classification), and no data is lost. The
impact is a misleading security-decision UX plus an integrity defect in the
override-grant audit trail, hence WARNING.

**Fix:** Source the classification from the resolved tier, defaulting to an
honest `"Unknown"` (kept non-empty so the prompt is still offered and the audit
default of `T3` applies) rather than the deny enum's `Debug`:

```rust
// Replace lines 738-741 (and the analogous 1093-1096 block).
if decision.is_some() {
    let classification = cache_classification
        .map(|c| format!("{c:?}"))
        .unwrap_or_else(|| "Unknown".to_string());
    emit_override_request(path, action, handle_value, &classification);
}
```

For the isolated branch, reuse the `tier_str` already built at
`trampolines.rs:626`. Then add an assertion on `req.classification` in the
override tests (see IN-01) so this cannot regress silently.

### WR-02: Modal dialogs run on the Pipe-1 read thread and starve the heartbeat

**File:** `dlp-user-ui/src/ipc/pipe1.rs:142-178` (via `pipe1.rs:245` and `pipe1.rs:276`)
**Issue:** `client_loop` handles each agent frame synchronously on the single
read thread. `BlockNotify` and `OverrideRequest` invoke blocking Win32 modal
dialogs inline:

- `pipe1.rs:157` → `handle_agent_msg` → `handle_block_notify` (`pipe1.rs:231`)
  → `show_block_dialog_with_result` (`pipe1.rs:245`).
- `pipe1.rs:157` → `handle_override_request` (`pipe1.rs:262`)
  → `show_override_dialog` (`pipe1.rs:276`).

While a modal is open, the loop cannot receive frames, so (a) `last_message` is
never reset by incoming agent frames and (b) `handle_ping` (`pipe1.rs:316-324`)
never runs, so no `Pong` is written. If the user takes longer than
`HEARTBEAT_TIMEOUT` (15s, `pipe1.rs:105`) to read and decide — realistic for an
override justification — the UI declares its own agent dead
(`pipe1.rs:168-172`) and tears down the pipe. The code already acknowledges this
exact hazard as the reason `ApprovalGranted`/`ApprovalRejected` are deliberately
non-modal (`pipe1.rs:350-354`: "popping a modal dialog inside the pipe read loop
would stall heartbeat responses and trip the agent's UI watchdog"), yet the
`BlockNotify` / `OverrideRequest` paths do precisely that.

Impact: an availability/robustness defect — a normally-paced user decision can
drop the UI↔agent pipe mid-prompt. The agent fails closed (no security bypass),
so this is WARNING rather than BLOCKER.

**Fix:** Move modal dialogs off the read thread. Spawn the blocking dialog on
`tokio::task::spawn_blocking` (or a dedicated UI thread) and have the read loop
continue to service `Ping`/`Pong` and the heartbeat clock meanwhile; deliver the
dialog result back to the loop over a channel and only then write the
`UserConfirmed`/`UserCancelled` response. Concretely, keep `handle_agent_msg`
non-blocking: clone `pipe`, `request_id`, and the dialog inputs into a
`spawn_blocking` task that returns the `Pipe1UiMsg`, and send the response from
the loop when the task completes.

### WR-03: An approved override is silently lost when the confirm channel is saturated

**File:** `dlp-agent/src/ipc/pipe1.rs:313`
**Issue:** `UserConfirmed` enqueues the deferred submission with a non-blocking
`try_send` on the bounded channel and drops it on saturation:

```rust
// pipe1.rs:309-319
let confirmed = ConfirmedOverride {
    request_id: request_id.clone(),
    justification,
};
if let Err(e) = confirmed_override_tx.try_send(confirmed) {
    warn!(
        request_id,
        error = %e,
        "Pipe 1: confirmed override channel saturated — dropping"
    );
}
```

By design (CR-01 / WR-05) the pending entry is only peeked here
(`pipe1.rs:299-301`, `.get().cloned()`) and is removed solely by
`confirmed_override_loop` after the server accepts the submit. So when
`try_send` returns `Full`: the confirm never reaches the consumer, the pending
entry is left in place, the UI has already reported "Approved" to the user, and
the entry is eventually reaped by the 120s `override_pending_reaper`. Net
effect: a user-approved override silently expires with no feedback and no audit,
whenever more confirmations arrive than the bounded channel can drain in time
(or the consumer is momentarily stalled).

**Fix:** Apply backpressure instead of dropping. The dispatcher runs in a Tokio
context, so await the send:

```rust
if let Err(e) = confirmed_override_tx.send(confirmed).await {
    warn!(request_id, error = %e, "Pipe 1: confirmed override channel closed");
}
```

If the dispatcher must stay synchronous, switch to an unbounded channel for this
control path, or surface the saturation back to the UI so the user is not told
the override succeeded. A regression test that fills the channel to capacity and
asserts the approval is still submitted (not dropped) should accompany the fix.

### WR-04: Granted-override audit records `user_name` as the raw SID

**File:** `dlp-agent/src/service.rs:1576`
**Issue:** `emit_override_granted_audit` duplicates the SID into `user_name`:

```rust
// service.rs:1573-1578
agent_id: agent_id.to_string(),
session_id: pending.session_id,
user_sid: user_sid.clone(),
user_name: user_sid,          // <- SID string, e.g. "S-1-5-21-..."
machine_name: None,
```

Every other `EmitContext` in the file uses a human identity (`"SYSTEM"` at
`service.rs:4809`, `7255`, `7730`). Duplicating the SID into `user_name` adds no
information (the SID is already in `user_sid`) and degrades the audit/compliance
record for the most sensitive event: SIEM dashboards, alerts, and forensic
queries that group or display by `user_name` will show an opaque SID for every
approved override. This reads as a copy-paste of the `user_sid` line.

**Fix:** Populate `user_name` from the resolved identity carried on the
originating `PendingOverride` (the requester name known at override-request
time), falling back to a constant such as `"UNKNOWN"` only when genuinely
unavailable — never the SID:

```rust
user_name: pending.requester_name.clone().unwrap_or_else(|| "UNKNOWN".to_string()),
```

(If a requester name is not currently stored on `PendingOverride`, thread it
through from the `OverrideRequest` handler alongside `requester_sid`.)

## Info

### IN-01: The override `classification` field is never asserted by tests

**File:** `dlp-hook-dll/tests/override_request_test.rs:141-144` and `dlp-agent/tests/hook_ipc_integration.rs:290-307`
**Issue:** Neither test checks `OverrideRequest.classification`.
`override_request_test.rs` asserts `action`, `resource_path`, `data_object_id`,
and a non-empty `requester_sid` but never `classification`; the consolidated
server test sends `classification: "T3"` and only asserts the handler ran once.
This is precisely why WR-01 shipped undetected: there is no test that would have
caught `format!("{c:?}")` on the deny enum.

**Fix:** Add `assert_eq!(req.classification, "T3")` (or the expected tier) to
`request_override_is_emitted_on_deny` and assert the classification round-trips
in `test_consolidated_server_routes_override_frame`.

### IN-02: Bare `\n` inside a Win32 STATIC prompt may render as a glyph

**File:** `dlp-user-ui/src/dialogs/override_request.rs:216-221`
**Issue:** The override prompt string is built with `"\n"` (LF) separators and
shown in a Win32 `STATIC` control. `STATIC` controls only break lines on CRLF
(`"\r\n"`); a lone LF is typically rendered as a small box/undefined glyph
rather than a newline, so the justification prompt can display an odd character
between lines. Cosmetic UX only; no functional impact.

**Fix:** Build the prompt with `"\r\n"` (and ensure the static is created with
multi-line style), e.g.:

```rust
let prompt = format!(
    "Classification: {classification}\r\nResource: {resource_path}\r\n\r\nReason:\r\n{reason}"
);
```
