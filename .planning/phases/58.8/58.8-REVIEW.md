# Phase 58.8: Code Review Report

**Reviewed:** 2026-07-10T13:30:00Z
**Depth:** standard
**Files Reviewed:** 32
**Status:** issues_found

## Summary

Reviewed the Phase 58.8 DIFF-01 (deferred override submission: hook DLL -> agent named-pipe -> server) and DIFF-04 (agent health-snapshot push -> server ingest -> admin health endpoint) change set across 32 source files. Three defects are release-blocking.

The DIFF-01 deferred-override path is non-functional end-to-end for two independent reasons: the Pipe 1 dispatcher removes the `PendingOverride` before the async submitter reads it (CR-01), and the override is routed to hardcoded Windows session 0 so the interactive UI never receives the request on a real workstation (CR-02). Either bug alone breaks the feature; together they also leak `OVERRIDE_PENDING` entries and emit a fabricated "override granted" audit event that the server never learns about.

DIFF-04's ingest authentication is fully bypassable: the very bcrypt hash used as the `DLP-AGENT` bearer credential is served, unauthenticated, by `GET /agent-credentials/auth-hash` (CR-03). Any network-reachable client can read it and forge health/diagnostics for arbitrary agent ids, defeating the stated mitigation (T-58.8-05). The admin CLI correctly uses JWT for `GET /admin/health`, so the blast radius is precisely the agent -> server ingest path that CR-03 undermines.

Secondary issues: a single global agent credential with a non-constant-time comparison and bcrypt pass-the-hash misuse (WR-01), fabricated audit identity/classification on the override-grant event (WR-02), a TOCTOU duplicate-key race in `HealthSnapshotStore::ingest` (WR-03), an idle-agent false-"critical" dashboard heuristic pinned by a tautological test (WR-04), a UI client with no read-side timeout that cannot detect a live-but-silent agent (WR-06), and test gaps that let all three blockers ship (WR-05). No `assert!(true)`, `todo!()`, `dbg!()`, or production `println!`/`eprintln!` of secrets were found (first-run `println!` in `dlp-server/src/main.rs` is the only console output and contains no secret).

## Critical Issues

### CR-01: Deferred override never reaches the server (double `remove` of `OVERRIDE_PENDING`)

**File:** `dlp-agent/src/ipc/pipe1.rs:293-313` and `dlp-agent/src/service.rs:1517-1548`
**Issue:** Two owners remove the same `OVERRIDE_PENDING` entry. The Pipe 1 dispatcher removes it on `UserConfirmed` and only then enqueues a `ConfirmedOverride`; the async submitter removes it again and therefore always observes `None`, logs "Confirmed override has no pending context — ignoring", and skips `submit_approval_request_with_justification`.

`pipe1.rs` (dispatcher):
```rust
// 293-313
let removed = OVERRIDE_PENDING
    .get()
    .and_then(|store| store.lock().remove(&request_id));   // first remove
if let Some(ctx) = removed {
    ...
    let confirmed = ConfirmedOverride { request_id: request_id.clone(), justification };
    if let Err(e) = confirmed_override_tx.try_send(confirmed) { ... }
    // 314-334: emits an "override granted" audit event here
}
```

`service.rs` (submitter):
```rust
// 1517-1548
while let Some(confirmed) = receiver.recv().await {
    let pending = OVERRIDE_PENDING
        .get()
        .and_then(|store| store.lock().remove(&confirmed.request_id));  // second remove -> None
    if let Some(pending) = pending {
        // submit_approval_request_with_justification(...)  // NEVER REACHED
    } else {
        warn!(request_id = %confirmed.request_id,
              "Confirmed override has no pending context — ignoring");
    }
}
```

Net effect: the user approves, the agent locally emits an "override granted" audit record (CR-01/WR-02), but the server is never told. The server-side approval/audit trail diverges from endpoint reality and the compliance record for the grant is lost. This is data loss of a security-relevant record and breaks the central DIFF-01 deliverable.

**Fix:** Make the Pipe 1 dispatcher enqueue only; let `confirmed_override_loop` be the single owner that removes the entry and submits to the server. Read the context for the audit event with `get` (not `remove`) so the submitter still finds it:
```rust
// pipe1.rs UserConfirmed arm
if let Some(store) = OVERRIDE_PENDING.get() {
    let ctx = store.lock().get(&request_id).cloned();   // do NOT remove
    if let Some(ctx) = ctx {
        if confirmed_override_tx.try_send(ConfirmedOverride {
            request_id: request_id.clone(),
            justification,
        }).is_ok() {
            emit_override_granted_audit(&ctx);          // real fields, see WR-02
        }
    }
}
```
Leave `service.rs:1517-1520` as the sole `remove` + server submission. Add a unit test that drives `dispatch(UserConfirmed)` and asserts the entry is still present until `confirmed_override_loop` drains it.

### CR-02: Override routed to hardcoded session 0 — UI never receives it; `OVERRIDE_PENDING` leaks

**File:** `dlp-agent/src/service.rs:2181-2212`, `dlp-agent/src/ipc/pipe1.rs:402-416`, `dlp-common/src/hook_ipc.rs:383-401`
**Issue:** `override_handle` inserts every pending override with `session_id: 0` and forwards via `send_to_ui(0, &ui_msg)`. `send_to_ui` looks up `CLIENTS` by session id and silently drops the message when no client is registered for that session. The interactive UI registers with its real session id (`dlp-user-ui/src/ipc/pipe1.rs:63-76` sends `RegisterSession { session_id }`); on Windows the logged-on user is session 1+, never session 0 (session 0 is the services session). So `CLIENTS.get(&0)` returns `None`, the `OverrideRequest` is dropped after a `debug!` log, the user never sees a dialog, and the entry inserted at `service.rs:2182-2189` is never removed (neither CR-01's confirm path nor the `UserCancelled` path at `pipe1.rs:347-349` ever runs). `OverrideRequest` carries no `pid`/`session` field (`dlp-common/src/hook_ipc.rs:383-401` has `requester_sid`, `data_object_id`, `resource_path`, etc. but no `pid`), so the agent has nothing to derive the target session from and hardcodes 0.

`service.rs`:
```rust
// 2181-2189
store.lock().insert(request_id.clone(), PendingOverride {
    request: req.clone(),
    session_id: 0,                 // hardcoded
    created_at: Instant::now(),
});
...
// 2210
if let Err(e) = crate::ipc::pipe1::send_to_ui(0, &ui_msg) { ... }   // routed to session 0
```

`pipe1.rs`:
```rust
// 402-416
pub fn send_to_ui(session_id: u32, msg: &Pipe1AgentMsg) -> Result<()> {
    let pipe = match CLIENTS.read().get(&session_id).map(|h| h.as_handle()) {
        Some(h) => h,
        None => {
            debug!(session_id, "Pipe 1: no client for session — dropping message");
            return Ok(());          // silent drop; caller's Err branch never fires
        }
    };
    ...
}
```

Net effect: on any real workstation the override feature is entirely inert (requests vanish), and `OVERRIDE_PENDING` grows by one entry per distinct `(requester_sid, resource_path, action)` that the 30s cooldown does not suppress — an unbounded leak keyed by attacker-influenceable file paths. This is both a correctness blocker and a memory-leak/data-loss risk.

**Fix:** Carry the requesting process identity so the agent can route to the owning session, and reap orphans.
1. Add `pid: u32` (and/or `session_id`) to `OverrideRequest` in `dlp-common/src/hook_ipc.rs` and populate it in the DLL (`trampolines.rs::emit_override_request` already runs in-process, so `GetCurrentProcessId()` is trivial).
2. In `override_handle`, resolve PID -> session id (`ProcessIdToSessionId`) and broadcast/route to the registered interactive session(s); store the resolved session in `PendingOverride` instead of `0`. If no UI is registered for the session, fail closed: do not insert a leak, log at `warn!`, and (per CLAUDE.md default-deny) keep the operation denied.
3. Add a TTL reaper for `OVERRIDE_PENDING` (e.g., sweep entries older than the dialog timeout, ~60s) so a confirmation that never arrives cannot accumulate.
4. Change `send_to_ui` to return `Err` when no client is registered so callers can react instead of dropping silently.

### CR-03: Public auth-hash endpoint hands out the `DLP-AGENT` bearer secret — ingest auth fully bypassable

**File:** `dlp-server/src/admin_api.rs:1176`, `dlp-server/src/admin_api.rs:1912-1930`, `dlp-server/src/admin_api.rs:129-176`, `dlp-agent/src/server_client.rs:570-571`
**Issue:** `GET /agent-credentials/auth-hash` is registered in `public_routes` with no `agent_auth_middleware` and no `require_auth`, and its handler returns the single global `DLPAuthHash` credential (the doc comment literally says "(public)"). That same value is what `agent_auth_middleware` accepts as the bearer secret for `POST /agents/{id}/health` and `POST /agents/{id}/diagnostics`, with the caller-supplied `agent_id` only required to be non-empty and to match the path.

`admin_api.rs` route wiring:
```rust
// 1157-1177 (public_routes)
.route("/agents/{id}/health",
    post(post_agent_health_handler)
        .route_layer(rate_limiter::per_agent_config())
        .layer(middleware::from_fn_with_state(Arc::clone(&state), agent_auth_middleware)))
.route("/agents/{id}/diagnostics", /* same auth */)
.route("/agent-credentials/auth-hash", get(get_agent_auth_hash))   // NO auth layer
```

`admin_api.rs` handler:
```rust
// 1912-1930
/// `GET /agent-credentials/auth-hash` — fetch the agent auth hash (public).
async fn get_agent_auth_hash(State(state): State<Arc<AppState>>) -> Result<Json<AuthHashResponse>, AppError> {
    ...
    let row = CredentialsRepository::get(&pool, "DLPAuthHash").map_err(AppError::Database)?;
    Ok((row.value, row.updated_at))   // the raw secret, no auth
}
```

`admin_api.rs` verifier:
```rust
// 158-172
let configured_hash = ... CredentialsRepository::get(&pool, "DLPAuthHash").map(|row| row.value) ...
if provided_hash != configured_hash { return Err(AppError::Unauthorized(...)); }  // 168, plain ==
```

Attack: `GET /agent-credentials/auth-hash` (no auth) -> read `hash` -> `POST /agents/<victim-or-arbitrary>/health` with `Authorization: DLP-AGENT <same-id>:<hash>`. The agent id is attacker-chosen (only `is_empty()` and path-match are enforced at `admin_api.rs:148` and the handlers), so an attacker can inject forged snapshots for any agent id, pollute `/admin/health` and `/admin/diagnostics`, and mask or fabricate agent compromise. This defeats T-58.8-05 outright. Corroborated by `dlp-server/src/main.rs` supporting `--bind 0.0.0.0:9090` with no global mTLS and the agent using a plain `reqwest` client (`server_client.rs:570-571` fetches the hash over the same unauthenticated channel). The admin CLI is unaffected (it uses JWT for `/admin/health`), so the exposure is concentrated exactly on the agent ingest path DIFF-04 added.

**Fix:** Stop serving the shared secret on an unauthenticated route.
- Remove `GET /agent-credentials/auth-hash` from `public_routes`, or gate it behind `require_auth` (admin JWT) plus a bootstrap/mTLS-bound provisioning channel for first-run agent enrollment.
- Replace the single global hash with per-agent credentials bound to `agent_id`: store `bcrypt::hash(agent_secret)` per agent, verify with `bcrypt::verify` (constant-time) in `agent_auth_middleware`, and require the verified credential's `agent_id` to equal the path `{id}`.
- Until per-agent creds land, at minimum return a one-time provisioning token from the auth-hash endpoint (not the reusable bearer secret) and require TLS + client auth on every agent route.

## Warnings

### WR-01: One global agent credential, non-constant-time compare, bcrypt pass-the-hash

**File:** `dlp-server/src/admin_api.rs:148-172`
**Issue:** All agents share one `DLPAuthHash`; compromise of any single agent (or of CR-03) authenticates every agent id. The comparison is `provided_hash != configured_hash` (plain `String` equality, line 168), which is not constant-time. The inline comment (165-167) acknowledges this and treats the bcrypt hash as a bearer token — which defeats bcrypt's purpose (bcrypt is for verifying a memorized secret, not for being transmitted as the secret). The `mismatched_agent_id` integration test (`dlp-server/tests/health_api_integration.rs:302`) actually demonstrates the weakness: one hash authenticates any id, and the only rejection is a path-vs-header id mismatch.

**Fix:** Per-agent `agent_credentials` rows keyed by `agent_id`; verify with `bcrypt::verify(provided_secret, &stored_hash)` (constant-time) and reject when the verified identity does not equal the path id. Rotate on enrollment. If a shared bootstrap secret is unavoidable, scope it to enrollment only and short TTL.

### WR-02: Override-grant audit event is fabricated

**File:** `dlp-agent/src/ipc/pipe1.rs:315-334`
**Issue:** The "override granted" audit event hardcodes `EventType::Access`, resource `"OVERRIDE"`, `Classification::T1`, `Action::READ`, `user_sid = "OVERRIDE"`, `user_name = "OVERRIDE"`, `agent_id = "AGENT"`. The real resource path, classification, action, and requester SID exist in `PendingOverride` but are discarded (also a casualty of CR-01's premature `remove`). This pollutes the compliance audit trail with fabricated identity and a fixed `T1`/`READ` classification for what is typically a high-sensitivity allow decision — undermining the explicit-auditability requirement in CLAUDE.md and misrepresenting the decision to SIEM.

**Fix:** Build the `AuditEvent` from the `PendingOverride` context (read via `get`, per CR-01 fix): real `data_object_id` as resource, the request's classification, the actual action, and `requester_sid` as `user_sid`. Emit it from `confirmed_override_loop` after a successful server submission so the audit record matches the server-side state.

### WR-03: `HealthSnapshotStore::ingest` TOCTOU race duplicates keys and corrupts global LRU eviction

**File:** `dlp-server/src/health_snapshot_store.rs:113-141`
**Issue:** `is_new_key = !self.snapshots.contains_key(&key)` (115) is checked before `self.snapshots.entry(key).or_insert_with(...)` (118-124). Two concurrent first ingests of the same agent both observe `contains_key == false`, both set `is_new_key = true`, and both push to `key_queue` (132-134). The duplicate queue entries make `queue.len()` over-count distinct agents, so the global `max_keys` eviction (135-138) pops the same key twice / evicts a still-live agent prematurely, producing wrong dashboard membership under concurrent ingest.

**Fix:** Determine newness atomically from the insert itself. With DashMap, use the entry API's returned state instead of a pre-check, e.g. hold a per-key insert gate or restructure so `key_queue` is updated only inside the `or_insert_with` closure (which runs once per key). Alternatively gate the whole `contains_key`+`entry`+`queue.push` under one short critical section.

### WR-04: Idle agents reported as "critical" (and pinned by a tautological test)

**File:** `dlp-server/src/health_snapshot_store.rs:177-183`, `dlp-server/tests/health_api_integration.rs:182-192`
**Issue:** `overall_status = "critical"` whenever `total_pipe_round_trips == 0` (177). A healthy but idle agent (injected, no blocked file ops in the last 60s — overnight, user away, allow-listed workload) reports zero round-trips and is paged as critical, causing alert fatigue and masking real `fail_state == 2` events. The integration test enshrines this: `assert!(["healthy","degraded","critical"].contains(&status))` (190) passes for any of the three values, so it cannot catch a heuristic that always returns "critical".

**Fix:** Treat zero round-trips as an idle/healthy state, not critical; reserve `critical` for `max_fail_state == 2` (and optionally a sustained low cache-hit rate with non-zero volume). Replace the permissive assertion with an exact expectation seeded from a known snapshot (e.g., assert `"healthy"` for the snapshot in `post_agent_health_surfaces_in_admin_health`, and a dedicated test that asserts `"critical"` only when `current_fail_state == 2`).

### WR-05: Test coverage does not exercise the paths that contain CR-01/CR-02/CR-03

**File:** `dlp-hook-dll/tests/override_request_test.rs`, `dlp-server/tests/health_api_integration.rs:279-322`
**Issue:** `override_request_test.rs` drives a mock `HookIpcServer` that forwards `RequestOverride` to an mpsc channel and asserts on the channel. It never instantiates `service.rs::override_handle`, never opens a real Pipe 1 client in a non-zero session, and never runs `pipe1.rs::dispatch`, so neither the session-0 drop (CR-02) nor the double-remove (CR-01) is reachable from the test suite. On the server side there is no test asserting that `GET /agent-credentials/auth-hash` requires authentication (CR-03), and the only auth test for the ingest endpoints is the mismatched-id 400 (`health_api_integration.rs:302`), which does not probe credential-per-agent binding.

**Fix:**
- Add an agent integration test that injects a `RequestOverride`, runs the real `override_handle` against an in-process Pipe 1 server registered in a non-zero session, simulates `UserConfirmed`, and asserts `submit_approval_request_with_justification` (or a recorded server call) fires exactly once with the user's justification.
- Add a server test that `GET /agent-credentials/auth-hash` without credentials returns 401/403, and that a valid `DLP-AGENT` credential cannot authorize a different agent id.

### WR-06: UI Pipe 1 client has no read-side timeout — live-but-silent agent hangs the client loop

**File:** `dlp-user-ui/src/ipc/pipe1.rs:44-57, 93-130`
**Issue:** The pipe is opened with a synchronous `CreateFileW` (no `FILE_FLAG_OVERLAPPED`, `FILE_FLAG_NO_BUFFERING`) and `client_loop` blocks in `read_frame(pipe)`. The heartbeat check (126) runs only after a successful read and is guarded by `last_message.is_some_and(...)`, and `last_message` starts as `None` (96). A fully dead agent is detected (broken pipe -> `read_frame` Err -> break), but an agent that stays connected yet stops writing (wedged emitter, deadlocked on its side) leaves `read_frame` blocked forever: the timeout never evaluates, the loop never exits, and there is no reconnect path. The agent-initiated `Ping` does not help here because detection still requires a frame to arrive.

**Fix:** Use overlapped I/O with a wait/timeout (or `WaitNamedPipe`/`PeekNamedPipe` + timed `ReadFile`), or run the blocking read on a cancellable task and arm a `tokio::time::timeout` around each `spawn_blocking` read iteration; on timeout, close the handle and trigger the reconnect logic. Initialise `last_message` to `Instant::now()` at connect so silence is measurable from t=0.

## Info

### IN-01: `OverrideCooldownMap` serialized under one global mutex on the hot deny path

**File:** `dlp-hook-dll/src/trampolines.rs:188, 243-244`
**Issue:** A single `static OVERRIDE_COOLDOWN: LazyLock<Mutex<OverrideCooldownMap>>` guards the whole map; `should_emit` does an O(n) `retain` and eviction scans under that lock on every denied operation. Every hooked process contends on one lock for a hot path. (Performance/contention is out of v1 scope, noted for completeness.)
**Fix:** Shard the map by key hash, or keep a small lock-free epoch cache; bound scans.

### IN-02: Synthetic `data_object_id` for handle operations weakens the audit trail

**File:** `dlp-hook-dll/src/trampolines.rs:277, 1063`
**Issue:** For handle-based operations the resource is set to `format!("handle:{}", handle_value)`, which is not a stable object identity and becomes the audit/override `data_object_id`. Override approvals and audit events then reference an ephemeral handle number rather than a path.
**Fix:** Resolve handle -> path (`NtQueryObject(ObjectNameInformation)`) before emitting, or omit `data_object_id` for handle ops and key cooldown/audit on a resolved identity.

### IN-03: Panic path in library client heartbeat

**File:** `dlp-agent/src/server_client.rs:542`
**Issue:** `serde_json::to_value(identity).expect("serialize endpoint identity")` can panic. Infallible in practice for a plain serializable struct, but CLAUDE.md forbids panics on library paths.
**Fix:** Propagate with `?` mapped to `ServerClientError`.

### IN-04: `println!` in the server binary first-run path

**File:** `dlp-server/src/main.rs:632, 640`
**Issue:** First-run setup prints to the console via `println!` while the rest of the service uses `tracing`. No secret is logged, but it is inconsistent with project conventions and will not appear in structured logs.
**Fix:** Emit via `tracing::info!` once the subscriber is initialised, or keep the interactive prompt but document that it is pre-tracing.

### IN-05: Rate-limit key read from a type-keyed `String` extension is fragile

**File:** `dlp-server/src/rate_limiter.rs` (`AgentIdOrIpKeyExtractor`)
**Issue:** The extractor prefers `req.extensions().get::<String>()` for the agent id. Because extensions are keyed by `TypeId`, any other middleware that inserts a bare `String` would hijack the rate-limit key (or collide), producing cross-tenant rate limiting.
**Fix:** Insert a dedicated newtype (e.g., `struct AgentId(String)`) from `agent_auth_middleware` and read that exact type in the extractor.

### IN-06: `AppState` test builder duplicated across the diagnostics integration tests

**File:** `dlp-server/tests/diagnostics_api_integration.rs` (builder repeated ~5x)
**Issue:** The same ~80-line `AppState` construction is copied in each test, so any field change (e.g., the new `health_snapshot_store`) must be edited in every copy; this is how stale test fixtures hide regressions.
**Fix:** Extract a single `build_test_app(opts)` helper shared by the diagnostics/health integration tests.
