## Critical Issues

### CR-01: Syslog drain backoff adds nanoseconds as seconds — drain effectively stalls for years after the first failure

**File:** `dlp-server/src/main.rs:556-561` (and identical logic at `dlp-server/src/main.rs:604-609` inside `compute_next_attempt`)
**Issue:**
```rust
let jitter = (std::time::SystemTime::now()
    .duration_since(std::time::UNIX_EPOCH)
    .unwrap_or_default()
    .as_nanos()                                  // ~1.7e18 (nanoseconds since epoch)
    % (delay as u128 * 500_000_000 + 1)) as u64; // jitter ∈ [0, delay·5e8) NANOSECONDS
let backoff = std::time::Duration::from_secs(delay + jitter); // treated as SECONDS
```
`jitter` is a nanosecond-scale value (modulus `500_000_000` = 0.5 s in ns), but it is added to `delay` (whole seconds) and passed to `Duration::from_secs`, i.e. interpreted as seconds. With `delay` capped at 60, `jitter` reaches up to `60·5e8 = 3e10`, so `from_secs(delay + jitter)` ≈ `from_secs(3e10)` ≈ **951 years**; even on the very first failure (`delay == 1`) the backoff can be up to ~`5e8` seconds ≈ **15.8 years**. The same value is then written into the retry timestamp via `compute_next_attempt` (`chrono::Utc::now() + from_std(backoff)`), so failed syslog events are scheduled for a far-future retry and the drain thread sleeps a duration that is effectively infinite. A single transient syslog/TLS error permanently disables syslog forwarding. `chrono::Duration::from_std(backoff)` also overflows silently to `zero()` via `unwrap_or_default()` on the largest values, masking the bug as either "never retry" or "retry now" depending on magnitude.

**Fix:** keep jitter in one unit. Compute jitter as a sub-second `Duration` and add to a `Duration`:
```rust
let nanos = std::time::SystemTime::now()
    .duration_since(std::time::UNIX_EPOCH)
    .unwrap_or_default()
    .subsec_nanos() as u64;                      // 0..1e9, no huge epoch magnitude
let jitter = std::time::Duration::from_nanos(nanos % 500_000_000); // 0..0.5s
let backoff = std::time::Duration::from_secs(delay) + jitter;
```
Apply the identical fix in `compute_next_attempt`. Add a unit test asserting the computed backoff is within `[delay, delay + 0.5s]` for `delay ∈ {1,2,4,8,16,32,60}`.

## Warnings

### WR-01: Agent↔UI `Pipe1AgentMsg` enum skew — UI silently drops `ApprovalGranted`/`ApprovalRejected`

**File:** `dlp-agent/src/ipc/messages.rs:52-67` vs `dlp-user-ui/src/ipc/messages.rs:17-45`; drop site `dlp-user-ui/src/ipc/pipe1.rs:135-140, 305-327`
**Issue:** The agent-side `Pipe1AgentMsg` defines `ApprovalGranted`/`ApprovalRejected` (with tests at messages.rs:465-502), but the UI "mirror" enum omits them and `handle_agent_msg` matches only `BlockNotify/OverrideRequest/ClipboardRead/PasswordDialog/Ping`. Because the enum is internally tagged with no `#[serde(other)]`, an approval frame fails `serde_json::from_slice`, hits the `Err` arm, logs at error level, and `continue`s — the approval is dropped with no response. The UI header comment claims it "mirrors dlp-agent/src/ipc/messages.rs"; it does not.
**Fix:** Add the two variants to the UI enum (matching field shapes exactly) and handle them in `handle_agent_msg`, or add `#[serde(other)]` + an explicit `Unknown` variant so unknown messages are counted rather than lost. Keep the two enums in sync via a shared crate or a compile-time assertion.

### WR-02: Single shared `DLP-AGENT` hash authenticates every agent → cross-agent impersonation

**File:** `dlp-server/src/admin_api.rs:129-182` (compare at `:172`); client `dlp-agent/src/server_client.rs:443-465`
**Issue:** `agent_auth_middleware` parses `Authorization: DLP-AGENT <agent_id>:<hash>` but compares `<hash>` (constant-time) against one global `DLPAuthHash`. The `agent_id` is not bound to a per-agent secret, so any party holding the single hash can present *any* `agent_id` and pass. `post_agent_health_handler` then only checks `Extension(agent_id) == Path(id)` — both attacker-controlled — so one leaked hash lets an attacker post forged health/diagnostics for every agent. This defeats the per-tenant isolation the phase-58.8 dashboard relies on.
**Fix:** Store and verify a per-agent credential keyed by `agent_id` (e.g. `agent_auth_hashes` map), and reject when the presented `agent_id` has no enrolled secret. At minimum, bind the hash lookup to the claimed `agent_id`.

### WR-03: Unprovisioned/missing auth hash returns 500 instead of 401/503, and masks real DB errors

**File:** `dlp-server/src/admin_api.rs:158-163`
**Issue:** The credential lookup is `.map_err(AppError::Database)?`, which converts every failure — including "no hash enrolled yet" — into `AppError::Database` → HTTP 500. A not-yet-provisioned agent (expected during rollout) reads as a server fault in logs/metrics, and a genuine database outage is indistinguishable from a missing credential.
**Fix:** Distinguish `NotFound`/no-row from a real DB error (e.g. match on repository error kind) and return `AppError::Unauthorized` (401) for no/wrong credential and reserve 500 for actual storage failures.

### WR-04: Concurrent, unsynchronized `WriteFile`s to the same Pipe-1 handle; `SendableHandle` safety comment is false

**File:** `dlp-agent/src/ipc/pipe1.rs:56-69, 82, 210-217, 389-412, 413-447, 455-475`
**Issue:** The `SendableHandle` comment claims the handle is "confined to the single-threaded pipe server," but `send_to_ui`, `send_password_dialog`, and `send_ping_to_all` are `pub` and are called from other tokio tasks (heartbeat, password-stop, override service) while the per-client `handle_connection` task also writes responses (e.g. `Pong`) on the *same* handle. `CLIENTS.read()` only serializes the map lookup — the subsequent `write_frame`/WriteFile calls from different tasks are not mutually excluded, so two length-prefixed frames can interleave on the wire and corrupt the UI's framing. The `unsafe impl Send/Sync` therefore rests on an invariant the code does not uphold.
**Fix:** Serialize writes per handle: wrap each entry in a `tokio::sync::Mutex<HANDLE>` (or a per-client write channel with one writer task) and hold it across the full `write_frame`. Correct the safety comment to describe the actual synchronization.

### WR-05: User-confirmed override is lost if the server submit fails (remove-before-submit)

**File:** `dlp-agent/src/service.rs:1624-1672` (pending map at `:79`, TTL reaper `:1594`/`OVERRIDE_PENDING_TTL:1587`)
**Issue:** `confirmed_override_loop` removes the `PendingOverride` from `OVERRIDE_PENDING` and *then* performs the HTTP submit (corroborated by `test_confirmed_override_loop_removes_pending_context`). If the submit fails transiently (network blip, 5xx), the context is gone: there is no requeue, the user's approval is silently lost, and the reaper (120 s TTL) can no longer help because the entry was already removed. The fail-closed removal in the request path (`service.rs:2362`) is correct for the *request* side, but the *confirmation* side has no retry.
**Fix:** Remove the pending entry only after a confirmed-successful submit; on failure, requeue onto the channel (bounded) or leave it for the reaper and surface an error/audit event so the approval is not silently dropped.

### WR-06: `/agent/approvals/active` is registered on the unauthenticated route group

**File:** `dlp-server/src/admin_api.rs:1190-1193` (under the "Unauthenticated (additional):" group at `:1135`)
**Issue:** The active-approvals endpoint is mounted with the public/unauthenticated routes, so any network client can enumerate pending approval workflow state (request ids, classifications, paths) — information disclosure that also aids phishing/social-engineering of approvals.
**Fix:** Move the route into the `require_auth` (JWT) `protected_routes` group, alongside the auth-hash route at `:1245`, and add a 401 test mirroring the existing unauthenticated-route tests.

### WR-07: Router doc still advertises `GET /agent-credentials/auth-hash` as "Unauthenticated"

**File:** `dlp-server/src/admin_api.rs:1097-1106` (doc) vs route at `:1245-1246` (protected) and handler doc at `:1883, 1920-1923`
**Issue:** The router-level doc lists the auth-hash GET under "Unauthenticated," but the route is mounted under `require_auth` and the handler's own doc explains it must be authenticated specifically so an unauthenticated caller cannot read the `DLP-AGENT` secret. Stale security docs are dangerous: a reviewer/operator trusting the doc will believe the credential is world-readable and tune WAF/network policy accordingly.
**Fix:** Move `GET /agent-credentials/auth-hash` out of the "Unauthenticated" doc block into the authenticated section; keep router docs mechanically in sync with the actual layer (a doctest/compile-checked route table would prevent recurrence).

### WR-08: `BlockNotify` request id is not unique — responses collide under concurrent blocks

**File:** `dlp-user-ui/src/ipc/pipe1.rs:222`
**Issue:** `handle_block_notify` builds `let request_id = format!("block-{}", session_id);`. Every block event for a session shares one id, so the agent cannot correlate `UserConfirmed`/`UserCancelled` to a specific `BlockNotify`; two near-simultaneous blocks (common when the hook DLL bursts) produce indistinguishable responses and the wrong event can be confirmed/cancelled.
**Fix:** Use a per-event unique id (monotonic counter or UUID), ideally echoing an id supplied by the agent in the `BlockNotify` payload, and have the agent key pending block state on that id.

## Info

### IN-01: "LRU" eviction is actually FIFO-by-first-seen

**File:** `dlp-server/src/health_snapshot_store.rs:10, 67, 144-152`
**Issue:** Docs/field comments claim LRU eviction, but `key_queue` is only pushed on `is_new_key`; re-ingesting an existing agent never refreshes its position. A hot agent inserted early is evicted before a cold agent inserted later. The global cap (`max_keys = 10_000`) still bounds memory, so this is mislabeled policy rather than a memory bug — rename "LRU" to "FIFO"/"insertion-order" or refresh the key on re-ingest.

### IN-02: Handle-close ABA race when unblocking the Pipe-1 reader

**File:** `dlp-user-ui/src/ipc/pipe1.rs:111-125, 172-176`
**Issue:** The main thread `CloseHandle(pipe)`s the handle the reader thread is blocked on inside `read_frame`. Because `SendableHandle` is `Copy`, the reader still holds the (now-closed) HANDLE value; if the OS reuses that handle value before `ReadFile` returns, the reader could briefly operate on an unrelated object. In practice `ReadFile` fails fast with `ERROR_INVALID_HANDLE`, but capturing the handle in an `Arc`/closing only after `reader.join()` (or using `CancelIoEx` on the reader thread) removes the window entirely. Low confidence; included for completeness.

### IN-03: Pre-created `next_pipe` leaks if `handle_connection` returns and `create_pipe` then fails

**File:** `dlp-agent/src/hook_ipc.rs` (accept loop)
**Issue:** The loop pre-creates `next_pipe` before `handle_connection`; on a `create_pipe` error the loop returns without closing the still-open current `pipe` HANDLE (minor leak on the error path). Track the outstanding handle in a scope guard/`Drop` so every early-return closes it.
