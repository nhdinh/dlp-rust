# Phase 68.1: Close gap: DEVICE-05/TAMPER-03/04 — wire tamper detection to SIEM and health - Context

**Gathered:** 2026-06-13
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 68.1 closes the integration gaps identified in the v0.11.0 milestone audit for DEVICE-05, TAMPER-03, and TAMPER-04. The phase wires tamper-evident hash-chain break detection into device health transitions, SIEM/syslog forwarding, and the admin TUI. It does **not** add new tamper-detection algorithms, new health states, or new audit-event schema — it only connects the existing Phase 63 and Phase 64 machinery so the end-to-end flow works.

**Requirements:** DEVICE-05, TAMPER-03, TAMPER-04

**Success Criteria (what must be TRUE):**
1. When the server detects a hash-chain break for an agent, that agent transitions its local `DeviceHealthStatus` to `Tampered` and emits a `DeviceHealthChange` audit event (DEVICE-05).
2. Synthetic `ChainBreakDetected` events reach both the SIEM relay (`SiemConnector::relay_events`) and the encrypted syslog queue (`SyslogQueueRepository`) — not only `alert_router` (TAMPER-03).
3. ABAC `EvaluateRequest` carries the endpoint's live `current_health()` instead of the hardcoded `Healthy` default (DEVICE-05 / TAMPER-04 cross-cutting).
4. The admin TUI provides an Audit Integrity screen that consumes `GET /admin/audit/integrity` and displays per-agent chain status and break count (TAMPER-04).
5. All changes pass workspace tests, clippy (`-D warnings`), `cargo fmt --check`, and `sonar-scanner` quality gate.

**Out of scope:**
- New hash-chain algorithms or Merkle/signature verification (deferred from Phase 63).
- Agent-side chain verification (the server remains the authoritative verifier; this phase only surfaces the result to the agent).
- Health recovery logic beyond what Phase 64 already implements (recovery via successful heartbeat).

</domain>

<decisions>
## Implementation Decisions

### D-01: Server reports chain breaks back to the agent in the ingest response
- **D-01.1:** Extend the `POST /audit/events` response from `StatusCode::CREATED` to a JSON body containing `{ "tamper_detected_for_agent": Option<String>, "chain_breaks": Vec<ChainBreakSummary> }`.
- **D-01.2:** The server populates `tamper_detected_for_agent` with the agent's own ID when at least one chain break in the batch belongs to that agent. This avoids server-to-agent push complexity and reuses the existing synchronous ingest round-trip.
- **D-01.3:** The response body is additive; older agents ignore unknown fields via `#[serde(default)]`.

### D-02: Agent calls `report_tamper_detected()` when its own chain break is confirmed
- **D-02.1:** In the agent's audit batch upload path (where it processes the `POST /audit/events` response), check `tamper_detected_for_agent == Some(self.agent_id)`. If true, call `crate::device_identity::report_tamper_detected()`.
- **D-02.2:** The call is fire-and-forget from the upload task; health transition and registry persistence are already synchronous inside `report_tamper_detected()`.
- **D-02.3:** The agent does **not** call `report_tamper_detected()` for chain breaks belonging to other agents; health is local to the endpoint.

### D-03: Synthetic `ChainBreakDetected` events route through SIEM and syslog
- **D-03.1:** After chain-break synthetic events are persisted in `audit_store.rs::ingest_events`, append them to the event collections used for syslog queuing and SIEM relay **before** those background tasks are spawned.
- **D-03.2:** Because `syslog_events` and `relay_events` currently operate on the original `events` batch, the synthetic events are added to a clone that is passed to both paths.
- **D-03.3:** `EventType::ChainBreakDetected` already returns `true` for both `routed_to_siem()` and `triggers_alert()`, so no routing logic changes are required in `siem_connector.rs` or `alert_router.rs`.
- **D-03.4:** Deduplication performed for persistence (per `agent_id` + reason) is preserved; the same deduplicated synthetic events are relayed.

### D-04: ABAC `EvaluateRequest` uses live device health
- **D-04.1:** Replace the hardcoded `device_health: DeviceHealthStatus::default()` in `dlp-agent/src/identity.rs` `to_subject()` and `to_subject_with_ad()` with `crate::device_identity::current_health()`.
- **D-04.2:** Replace the hardcoded `device_health: DeviceHealthStatus::default()` in `dlp-agent/src/interception/mod.rs` `build_evaluate_request` (or equivalent request construction site) with `crate::device_identity::current_health()`.
- **D-04.3:** `current_health()` is a non-blocking read of the static `AtomicU8`; it is safe to call from both async and hook-IPC contexts.
- **D-04.4:** The deprecated `to_subject()` is still updated because it remains compiled and is used in some test/code paths.

### D-05: Admin TUI Audit Integrity screen
- **D-05.1:** Add a new screen `dlp-admin-cli/src/screens/audit_integrity.rs` following the `screens/bypass_alerts.rs` and `screens/protected_paths.rs` pattern (mod/dispatch/render/client/app.rs extensions).
- **D-05.2:** The screen consumes `GET /admin/audit/integrity` with optional `agent_id` filter and displays:
  - Overall `integrity_ok` boolean as a status banner.
  - Per-agent rows: agent ID, total events, verified events, break count, last chain hash.
  - A detail popup for the chain breaks list (agent ID, event ID, expected vs actual prev hash).
- **D-05.3:** Navigation uses the same key bindings as other list screens: arrow keys/PgUp/PgDn, `Enter` for detail, `Esc` to go back, filter cycling with `f`.
- **D-05.4:** A new client method `list_audit_integrity(agent_id: Option<&str>)` is added in `dlp-admin-cli/src/client.rs` and unit-tested.

### D-06: Audit event emission for tamper-driven health transition
- **D-06.1:** `report_tamper_detected()` already calls `transition_health(DeviceHealthStatus::Tampered)`, which emits `EventType::DeviceHealthChange` when the state changes. No new event type is needed.
- **D-06.2:** The `DeviceHealthChange` event routes through SIEM and syslog automatically because `EventType::DeviceHealthChange::routed_to_siem()` is `true`.

### Claude's Discretion
- **Tamper notification channel:** Using the synchronous ingest response keeps the architecture pull-based and avoids adding a new server-to-agent push mechanism. If later phases need real-time tamper notification, a dedicated push channel can be added; for this gap-close, the response-body approach is sufficient.
- **Synthetic event relay order:** Synthetic events are appended to the relay/syslog list after persistence so that any relay failure does not roll back the audit log record of the break.
- **Health read consistency:** `current_health()` is the same source used by heartbeats and `build_endpoint_identity()`, so ABAC, heartbeat, and audit contexts remain consistent.
- **TUI detail scope:** The integrity screen shows break metadata only (no full event payload) to stay within the phase boundary; deep event inspection remains available through the existing audit query screen.

</decisions>

## Existing Code Insights

### Reusable Assets
- `report_tamper_detected()` (`dlp-agent/src/device_identity.rs:252`) — already implements one-way transition to `Tampered` and registry persistence; only missing a caller.
- `current_health()` (`dlp-agent/src/device_identity.rs`) — returns the live `AtomicU8` health state; same source used by heartbeats.
- `DeviceHealthStatus` (`dlp-common/src/endpoint.rs`) — four-variant enum with `Ord` ordering; `Healthy < Degraded < Offline < Tampered`.
- `EventType::ChainBreakDetected` (`dlp-common/src/audit.rs`) — already routed to SIEM and triggers alert.
- `EventType::DeviceHealthChange` — already routed to SIEM and triggers alert.
- `get_audit_integrity()` (`dlp-server/src/audit_store.rs:594`) — existing paginated integrity endpoint returning `AuditIntegrityResponse`.
- `AuditIntegrityResponse`, `AgentChainStatus`, `ChainBreak` — already defined in `dlp-server/src/audit_store.rs`.
- Admin TUI `BypassAlertsList` screen (`dlp-admin-cli/src/screens/bypass_alerts.rs`) — ready template for list + detail popup + filter.

### Established Patterns
- **Three-stage pipeline** (Phase 61/66.1): NTFS check → ABAC policy check → approval cache override. Health status is part of the ABAC subject/environment, so D-04 feeds into the second stage.
- **Fire-and-forget SIEM/syslog relay** (`audit_store.rs:465-519`): events are cloned into separate background tasks for syslog queue and SIEM relay; synthetic events must be added before those clones are taken.
- **Synchronous response extension for agent signaling** (Phase 50 cache hints): `EvaluateResponse` was extended with additive fields and `#[serde(default)]`; the same pattern applies to the ingest response.
- **Admin TUI screen lifecycle** (Phase 54 bypass alerts): mod/dispatch/render/client/app.rs extensions with stable ID handling and optimistic ack.

### Integration Points
- `dlp-server/src/audit_store.rs:418-453` — synthetic `ChainBreakDetected` events are constructed here but only passed to `alert_router.send_alert()`.
- `dlp-server/src/audit_store.rs:465-510` — `syslog_events` is built from the original `events` batch; synthetic events are not included.
- `dlp-server/src/audit_store.rs:512-519` — `relay_events` is passed to `SiemConnector::relay_events()`; synthetic events are not included.
- `dlp-agent/src/identity.rs:46` and `:95` — `device_health: DeviceHealthStatus::default()` (Healthy) hardcoded.
- `dlp-agent/src/interception/mod.rs` — `EvaluateRequest` construction with hardcoded `device_health` (exact line to be confirmed during planning).
- `dlp-admin-cli/src/app.rs` — system menu and screen routing; add "Audit Integrity" entry next to "Bypass Alerts".

### Code Gaps
- `report_tamper_detected()` has zero production callers.
- `ChainBreakDetected` synthetic events bypass `syslog_events` and `relay_events`.
- `EvaluateRequest` is constructed with `DeviceHealthStatus::default()` instead of `current_health()`.
- No admin TUI screen calls `GET /admin/audit/integrity`.

</code_context>

<specifics>
## Specific Ideas

- Ingest response body should be small and stable:
  ```rust
  #[derive(Serialize)]
  struct IngestEventsResponse {
      tamper_detected_for_agent: Option<String>,
      chain_break_count: usize,
  }
  ```
- The agent's batch upload task should log at `tracing::error!` level when a local tamper is detected, then call `report_tamper_detected()`.
- Synthetic event relay: collect the same `Vec<AuditEvent>` used for `alert_router` (already deduplicated and persisted) and extend both `syslog_events` and `relay_events` with it before spawning the background tasks.
- Admin TUI integrity screen columns: Agent ID | Events | Verified | Breaks | Last Hash (truncated).
- Filter cycling on the integrity screen: `None` (all agents), then per-agent IDs discovered from the response (or a text-input filter deferred to a follow-up if complex).

</specifics>

<deferred>
## Deferred Ideas

- Real-time server-to-agent tamper push channel (WebSocket or long-polling) — out of scope; synchronous response is sufficient for this gap.
- Merkle-tree or signature-based integrity verification — deferred from Phase 63.
- Agent-side chain verification independent of server — not required; server remains authoritative.
- Bulk integrity export or scheduled integrity report jobs — new capability, future phase.
- TUI integrity screen deep-linking to full audit event detail — future UX enhancement.

</deferred>
