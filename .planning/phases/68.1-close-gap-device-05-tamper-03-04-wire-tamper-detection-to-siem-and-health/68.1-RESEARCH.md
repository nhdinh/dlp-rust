# Phase 68.1: Close gap: DEVICE-05/TAMPER-03/04 — wire tamper detection to SIEM and health - Research

**Researched:** 2026-06-13
**Domain:** Rust / Enterprise DLP / Audit Integrity / Device Health / SIEM Integration
**Confidence:** HIGH

## Summary

Phase 68.1 closes four integration gaps identified in the v0.11.0 milestone audit: (1) `report_tamper_detected()` has zero callers, so hash-chain breaks never transition device health to `Tampered`; (2) synthetic `ChainBreakDetected` events are persisted and sent to `alert_router` only, bypassing both `syslog_events` and `relay_events`; (3) ABAC `EvaluateRequest` hardcodes `device_health` to `DeviceHealthStatus::default()` (Healthy) instead of `current_health()`; (4) no admin TUI screen consumes `GET /admin/audit/integrity`. The phase is purely wiring — no new algorithms, no new event types, no new health states. The hardest part is ensuring the server-side ingest response extension is backward-compatible with older agents and that the TUI screen follows the established `BypassAlertList` pattern correctly.

**Primary recommendation:** Extend the `POST /audit/events` response body, add synthetic events to the relay/syslog clones before spawning, replace hardcoded health with `current_health()`, and add an `AuditIntegrityList` TUI screen mirroring `BypassAlertList`.

```
    -> ServerClient::send_audit_events()  [POST /audit/events]

Agent interception/mod.rs run_event_loop
  -> build_evaluate_request()
     -> subject.device_health = current_health()  [was: DeviceHealthStatus::default()]
```


### Pattern 1: Synchronous Response Extension for Agent Signaling
**What:** Add additive fields to an HTTP response body with `#[serde(default)]` so older agents ignore them.
**When to use:** When the server needs to communicate a result back to the agent without adding a push channel.
**Example:**
```rust
// dlp-server/src/audit_store.rs
#[derive(Serialize)]
struct IngestEventsResponse {
    tamper_detected_for_agent: Option<String>,
    chain_break_count: usize,
}
// Response changed from StatusCode::CREATED to Json<IngestEventsResponse>
```

### Pattern 2: Fire-and-Forget SIEM/Syslog Relay
**What:** Clone events into separate background tasks for syslog queue and SIEM relay so the HTTP response is not delayed.
**When to use:** Any audit ingestion path that must also route to external SIEM/syslog.
**Example:**
```rust
// dlp-server/src/audit_store.rs:465-519
let syslog_events = Arc::new(events);
// ... spawn_blocking for syslog queue ...
// ... tokio::spawn for SIEM relay ...
```

### Pattern 3: Admin TUI Screen Lifecycle
**What:** mod/dispatch/render/client/app.rs extensions with stable ID handling and optimistic ack.
**When to use:** Any new admin TUI screen that lists server data with detail popup.
**Example:** `BypassAlertList` in `dlp-admin-cli/src/screens/bypass_alerts.rs` (lines 1-40) and `dispatch.rs` (lines 7745-7865).

### Anti-Patterns to Avoid
- **Do NOT add a WebSocket or push channel** for tamper notification. The synchronous response extension is sufficient per CONTEXT.md D-01.
- **Do NOT change the `ChainBreakDetected` event type routing.** It already returns `true` for both `routed_to_siem()` and `triggers_alert()` (verified in `dlp-common/src/audit.rs:274,290`).
- **Do NOT modify `report_tamper_detected()` or `transition_health()` internals.** They are already correct; only a caller is missing.

## Common Pitfalls

### Pitfall 1: Backward-Incompatible Ingest Response
**What goes wrong:** Changing `POST /audit/events` from `StatusCode::CREATED` to a JSON body breaks older agents that expect an empty 201 response.
**Why it happens:** `reqwest::Response::json()` on an empty body returns a deserialization error.
**How to avoid:** Return a JSON body on ALL success paths. Older agents that ignore the body are unaffected. The new agents deserialize the body. No agent-side change needed for backward compat.
**Warning signs:** Integration tests with pre-Phase 68.1 agent mock clients fail with parse errors.

### Pitfall 2: Synthetic Events Added After Clone
**What goes wrong:** Synthetic `ChainBreakDetected` events are persisted but not relayed because they are added to `events` AFTER `relay_events = events.clone()` (line 301).
**Why it happens:** The clone happens before synthetic events are constructed (lines 353-409 inside `spawn_blocking`).
**How to avoid:** Collect synthetic events into a `Vec<AuditEvent>` inside the `spawn_blocking` closure, return them from the closure, then append them to both `syslog_events` and `relay_events` before spawning the background tasks. Alternatively, construct synthetic events BEFORE the clone (but they need DB persistence for `id`). The CONTEXT.md D-03.2 approach is: append synthetic events to a clone that is passed to both paths.
**Warning signs:** SIEM/syslog integration tests show zero `ChainBreakDetected` events.

### Pitfall 3: Hardcoded Health in Multiple Places
**What goes wrong:** Only one of `identity.rs` or `interception/mod.rs` is updated, leaving another path with `Healthy`.
**Why it happens:** `to_subject()` is deprecated but still compiled; `to_subject_with_ad()` is the production path; `interception/mod.rs` has a fallback `Subject` construction for no-AD mode.
**How to avoid:** Update ALL three sites: `identity.rs:46`, `identity.rs:95`, and `interception/mod.rs:385`. Use `crate::device_identity::current_health()` in all.
**Warning signs:** ABAC tests with `DeviceHealth` policy conditions pass when `current_health()` is mocked but fail in integration because the real value is still `Healthy`.

### Pitfall 4: TUI Screen Not Registered in System Menu
**What goes wrong:** The new `AuditIntegrityList` screen is implemented but unreachable because `SystemMenu` does not have an entry for it.
**Why it happens:** `SystemMenu` has 14 items (indices 0-13). Adding a 15th requires updating `nav(selected, 14, key.code)` to `nav(selected, 15, key.code)` and adding the entry at index 14.
**How to avoid:** Follow the Phase 54 pattern: add the screen variant, add the dispatch handler, add the render function, add the client method, add the system menu entry, and add a test for `system_menu_item_count_and_order` (see `dispatch.rs` tests around line 8236).
**Warning signs:** Manual TUI test shows 14 items but "Audit Integrity" is missing.

## Open Questions (RESOLVED)

1. **How to pass synthetic events out of `spawn_blocking`?**
   - What we know: Synthetic events are constructed inside `spawn_blocking` (lines 353-409) after DB persistence.
   - What's unclear: The current `spawn_blocking` returns `Result<(), AppError>`. To relay synthetic events, we need to return them from the closure.
   - Recommendation: Change the closure return type to `Result<Vec<AuditEvent>, AppError>` and return the deduplicated synthetic events. Then append them to `relay_events` and `syslog_events` before spawning the background tasks.

2. **Where is the agent's `agent_id` available during `send_audit_events`?**
   - What we know: `ServerClient` has `base_url` but no `agent_id` field.
   - What's unclear: The `AuditBuffer` or `ServerClient` may need to carry the agent ID to compare against `tamper_detected_for_agent`.
   - Recommendation: Add `agent_id: String` to `ServerClient` or `AuditBuffer`, populated from `service.rs` startup. Alternatively, the caller of `send_audit_events` (the `AuditBuffer::flush` task) can do the comparison if it has the agent ID.

3. **Should `send_audit_events_json` (offline queue drain) also process the response?**
   - What we know: `send_audit_events_json` is used for offline queue drain and sends pre-serialized JSON.
   - What's unclear: If the response contains a tamper flag, should the offline drain path also call `report_tamper_detected()`?
   - Recommendation: Yes — any successful ingestion response that indicates tamper for this agent should trigger `report_tamper_detected()`, regardless of whether the events came from the live buffer or the offline queue. Update both `send_audit_events` and `send_audit_events_json` to return `IngestResponse`.
