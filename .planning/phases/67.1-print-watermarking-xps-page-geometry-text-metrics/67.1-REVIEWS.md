# Cross-AI Plan Review -- Phase 67.1

## Claude Review

### 1. Summary

Both plans are well-structured and correctly separate concerns: Plan 01 establishes pure, testable geometry/text-metric primitives, while Plan 02 layers on streaming XPS ZIP mutation. The trait-based `FontMetrics` abstraction and use of streaming XML/ZIP processing are sound choices that align with the existing tech stack. However, a **critical gap exists in Plan 02**: the proposed `Glyphs` element does not include a `FontUri` attribute, and there is no provision for embedding or referencing the Arial/Segoe UI font resource inside the XPS package. Without this, the watermark may fail to render or survive rasterization, violating the phase's core success criterion #3. Several smaller issues around unit conversion documentation, truncation efficiency, and XPS relationship handling also need tightening before execution.

---

### 2. Strengths

- **Clean separation of waves.** Plan 01 builds pure geometry/metrics; Plan 02 consumes them for XPS mutation. This makes testing and rollback straightforward.
- **Testable design.** The `FontMetrics` trait with `TestFontMetrics` stub allows CI on non-Windows runners while keeping a Windows-specific DirectWrite implementation.
- **Streaming processing.** Using `quick_xml::Reader` + `Writer` and the `zip` crate avoids loading entire XPS packages into memory, supporting large spool files.
- **Consistent error handling.** Plans use `Result`, `?`, `anyhow::Context`, and avoid `.unwrap()`, matching project standards.
- **Appropriate fallback.** DirectWrite falls back from Arial to Segoe UI, reducing failure surface.
- **Threat model included.** Risks are identified and mostly mitigated, with clear acceptance of intentional PII in watermark text.

---

### 3. Concerns

#### Plan 01

- **HIGH -- Missing DirectWrite-to-XPS unit conversion detail.** DirectWrite `GetMetrics` returns values in design units/em size that must be converted to XPS units (1/96 inch). The plan mentions XPS native units for padding/font size but does not explicitly define the conversion path from `DWRITE_TEXT_METRICS` to the `OriginX/Y` and `FontRenderingEmSize` attributes. This is easy to get wrong and hard to debug visually.
- **MEDIUM -- `FontMetrics` trait is under-parameterized.** `measure(&self, text, family, em_size)` omits weight, style, and locale. While the watermark spec fixes these, the trait should probably accept a `FontStyle` or `TextFormatDesc` struct to avoid future breaking changes if requirements evolve.
- **MEDIUM -- `truncate_with_ellipsis` is O(n^2).** Iteratively removing one character and re-measuring is fine for short watermark strings, but a pathological case could be expensive. Since watermark strings are bounded this is acceptable, but worth a comment or binary-search alternative.
- **LOW -- Test stub uses `chars().count()`.** The plan notes this is an approximation, which is acceptable for tests but should be clearly documented as a deliberate simplification.

#### Plan 02

- **HIGH -- Injected `Glyphs` lacks `FontUri` and no font resource is added to the XPS package.** Per the XPS specification, a `Glyphs` element **must** have a `FontUri` attribute referencing an OpenType font part in the package. The plan lists attributes for the injected `Glyphs` but omits `FontUri`. Without an embedded Arial/Segoe UI font part and a valid relationship, printer drivers may either ignore the watermark glyphs or substitute a different font, breaking success criterion #3 ("survives rasterization").
- **HIGH -- No handling of XPS relationships/OPC structure.** Rewriting a ZIP is not enough; the XPS/Open Packaging Convention requires `[Content_Types].xml` entries and `.rels` relationship files for any new font part or modified page. The plan tests preservation of `[Content_Types].xml` but does not address updating it.
- **MEDIUM -- No validation of rewritten XPS structural integrity.** Tests verify byte preservation of ancillary files and presence of injected elements, but there is no test that the output is a valid XPS package (e.g., OPC relationships still resolve, required parts present).
- **MEDIUM -- Missing malformed ZIP/XPS tests.** Threat T-67.1-01 mentions malformed ZIP, but the test list does not include tests for corrupt ZIP headers, missing `[Content_Types].xml`, or truncated `.fpage` files.
- **MEDIUM -- Compression metadata may be lost.** The plan says "copy non-`.fpage` verbatim," which is correct for bytes, but `zip` crate defaults may re-compress `.fpage` differently. This is usually harmless but could matter for spool file hashes or downstream tooling.
- **LOW -- Empty text watermark test is unrealistic.** The requirements always supply populated fields; this test is fine but does not add operational confidence.

---

### 4. Suggestions

- **Add `FontUri` support to `Glyphs` injection.** Either reference an existing font part if the XPS already embeds Arial/Segoe UI, or embed a fallback font part and register it in `[Content_Types].xml` and the relevant `.rels` file.
- **Introduce explicit unit conversion constants/functions.** Define a `pt_to_xps_units(pt: f64) -> f64` helper and document the 96 DPI basis so `8 pt = 10.6667` and `15 pt = 20` are derived from a single source of truth.
- **Make `FontMetrics::measure` accept a descriptor struct.** Replace `(text, family, em_size)` with a `TextFormatRequest { text, family, em_size, weight: ..., style: ... }` to keep the API stable.
- **Add malformed-input tests for Plan 02.** Include corrupt ZIP, missing `[Content_Types].xml`, truncated `.fpage`, and XML missing `FixedPage`.
- **Validate output as an XPS package.** After injection, re-parse the output ZIP to ensure OPC relationships resolve and required parts are present.
- **Optimize truncation.** Consider binary search or a max-iterations guard with a clear comment; ensure the loop terminates if even the ellipsis does not fit.
- **Preserve ZIP compression method.** When rewriting `.fpage`, mirror the original compression method and options from the source entry.
- **Add a Unicode/wide-character geometry test.** Watermark text may contain non-ASCII usernames or device fingerprints; ensure width measurement and truncation handle multi-byte characters correctly.
- **Document COM apartment assumptions.** Since DirectWrite requires COM, add a note that callers must have initialized COM on the thread (e.g., `CoInitializeEx` with `COINIT_APARTMENTTHREADED` or `COINIT_MULTITHREADED`).

---

### 5. Risk Assessment

**Overall Risk: HIGH**

The plans are technically sound in isolation, but Plan 02 has a **blocking gap** in XPS font resource handling. Without embedding or correctly referencing a font part, the watermark may silently fail to render during printer-driver rasterization, violating the phase's most important success criterion. The other issues (unit conversion documentation, OPC relationship updates, malformed-input testing) are manageable but compound the risk. I recommend **approving Plan 01 for execution** after minor API tightening, and **revising Plan 02** to address font embedding/referencing and OPC structural integrity before implementation begins.

## OpenCode Review

### Plan 01: Foundational XPS Page Geometry + Text Metrics

#### Summary
Solid foundational module with good trait abstraction for testability. Correctly separates DirectWrite COM code from pure geometry logic. Scope matches the phase goal -- neither over- nor under-engineered.

#### Strengths
- `FontMetrics` trait design enables both real (DirectWrite) and stub (test) implementations -- good testability strategy
- `compute_watermark_geometry` as a pure function is clean and unit-testable
- `truncate_with_ellipsis` handles the important edge case of overflow text
- No `.unwrap()` policy and streaming XML parse for geometry extraction are appropriate
- DEFAULT page size fallback with warning is the right call
- Watermark string format matches D-05 precisely

#### Concerns

1. **HIGH: CoInitializeEx not addressed.** The plan mentions COM safety comments but doesn't specify where/when `CoInitializeEx(COINIT_MULTITHREADED)` is called. DirectWrite requires COM initialized on the calling thread. This will crash at runtime on any thread that hasn't initialized COM. Needs a `CoInitializeEx` guard or explicit requirement that caller initializes COM.

2. **MEDIUM: Font fallback chain is incomplete.** Plan specifies Arial -> Segoe UI fallback with `tracing::warn!`. But if *both* fail (e.g., WinPE, WinRE, or minimal WinSxS), `CreateTextFormat` returns an error and `measure()` returns `Err`. This is correct but the plan doesn't specify what *em_size* to use in `compute_watermark_geometry` when measurement fails. The caller (Plan 02) would need to handle this -- but the spec says font failure is an error returned to Phase 67. Clarify whether `compute_watermark_geometry` can still produce geometry without font metrics (e.g., fallback to a default char width).

3. **LOW: quick-xml for simple attribute extraction is heavyweight.** `extract_page_geometry` uses a `Reader` when the XML is small and well-structured. Could use a simpler parser or even string search for `Width`/`Height` attributes. Not a blocker but adds code surface.

4. **LOW: truncation loop performance bounds.** Iterative remove-and-re-measure could be O(n^2) for very long text. The empty-text guard prevents infinite loops, but a binary-search approach or pre-computed average char width could improve performance. Realistically, watermark text is ~80-120 chars so negligible.

#### Suggestions
- Add a `CoGuard` struct (or document the contract) that ensures `CoInitializeEx` is called before any DirectWrite call
- Consider making `compute_watermark_geometry` accept `Option<FontMetrics>` or a fallback char width for the error case
- The `FontMetrics` trait should use `thiserror::Error` or `anyhow::Error` as its error type -- currently unspecified

#### Risk Assessment: **LOW**
Well-scoped, good abstractions, good test coverage. The sole HIGH concern (COM init) is easily fixable and the plan already references COM safety. No architectural risk.

### Plan 02: XPS ZIP Watermark Injection

#### Summary
Correct streaming approach using `quick_xml::Reader` + `Writer` for XML injection, with verbatim byte copy for non-page files. The per-page geometry closure is a good design choice. Main risk is around XML namespace handling and edge cases in the XPS format.

#### Strengths
- Streaming XML injection preserves existing markup (attributes, namespaces, etc.)
- Non-`.fpage` files copied verbatim -- eliminates risk of corrupting unrelated XPS parts
- Per-page geometry closure correctly supports multi-page documents with varying dimensions
- `rewrite_xps_with_watermark` returning `Result<Vec<u8>>` and using `?` propagation throughout is clean
- Convenience wrapper `inject_watermark` ties the two plans together cleanly

#### Concerns

1. **HIGH: Namespaced FixedPage tags.** `Event::End(FixedPage)` will not match `{http://schemas.microsoft.com/xps/2005/06}FixedPage`. XPS files use qualified names by default. The match must handle `Event::End(BytesEnd::end("FixedPage"))` or check the local-name after stripping the namespace URI. quick-xml's `Reader` returns events with namespace prefixes resolved -- need `BytesEnd` local name matching.

2. **MEDIUM: Multiple document structures.** XPS packages can have nested `FixedDocument` -> `FixedPage` relationships, and some have `DocumentReference` chains. The plan assumes all `.fpage` files should receive the same watermark treatment, which is correct, but doesn't mention handling `FixedDocument` without any `FixedPage` children (should pass through silently).

3. **MEDIUM: Canvas element namespace.** The injected `Canvas` element may need an explicit `xmlns=""` or appropriate namespace to be valid XPS. The plan doesn't specify whether the Canvas inherits the namespace from the FixedPage (which would be correct for XPS). If the FixedPage uses a namespace, the `Glyphs` and `Canvas` tags might produce unqualified elements that the XPS renderer rejects.

4. **LOW: Full-file memory load.** `rewrite_xps_with_watermark` takes and returns `Vec<u8>`. For a typical XPS spool file (50-500 KB), this is fine. For multi-hundred-page documents (could reach 5-10 MB with images), memory doubles. Not a practical concern for current scope but worth a comment.

5. **LOW: Empty Canvas injection for empty text.** D-04 says empty string should still produce a watermark element. An empty `Glyphs` element with `UnicodeString=""` should render nothing but injects an extra element into every page. This is intentional per the plan but worth verifying the XPS renderer doesn't choke on an empty glyph run.

6. **LOW: ZIP writer atomicity.** The plan reads the entire XPS into memory, decompresses, then re-compresses. The `zip` crate's `ZipWriter` may produce a different binary than the original for non-page files. Tests must verify round-trip integrity (not just structure).

#### Suggestions
- Add namespace handling: detect FixedPage's namespace from `BytesStart` and propagate to injected elements, or use `BytesEnd::end("FixedPage")` with local-name matching
- Add a test case for namespaced XPS input (the common case, not the raw/unqualified case)
- Clarify that the per-page closure receives the file path (for logging/error context) not just dimensions
- Consider adding `tracing::info!` at injection noting page count and watermark text (observability for debugging failed prints)

#### Risk Assessment: **LOW**
Conceptually sound. The namespace concern is the only genuine risk -- if untested, watermark injection silently fails on real XPS files. Easily fixable with a local-name-aware match. Everything else is straightforward Rust with well-understood libraries.

## Codex Review (gpt-5.5)

### Summary

The two-plan split is mostly coherent: Plan 01 builds the geometry and metrics foundation, and Plan 02 layers XPS ZIP/XML rewriting on top. The plans are strong on test coverage and explicit unit conversion, but Plan 02 has several correctness risks around XML namespace handling and "verbatim" preservation. Plan 01 also needs tighter Windows gating and a real COM initialization strategy for DirectWrite.

### Strengths

- Clear dependency ordering: metrics and geometry before ZIP/XML injection.
- Good separation between production `DirectWriteFontMetrics` and deterministic `TestFontMetrics`.
- Explicit XPS unit conversion and DirectWrite DIP equivalence are well called out.
- Truncation behavior is deterministic and testable.
- The threat model correctly treats XPS/XML/ZIP bytes as untrusted input.
- Plan 02 includes useful malformed input tests: bad ZIP, missing `[Content_Types].xml`, truncated `.fpage`, missing `FixedPage`.
- Preserving non-page ZIP entries and avoiding in-place mutation are good design choices.

### Concerns

- **HIGH: Plan 02 namespace handling is under-specified and likely incorrect.**
  `quick_xml` does not automatically resolve namespace URIs from prefixes just by calling `e.name().namespace()` or `prefix()` in the way the plan assumes. For prefixed XPS, the implementation likely needs to inspect `xmlns` / `xmlns:xps` attributes on `FixedPage`, track the prefix, and emit matching qualified names or a default namespace deliberately.

- **HIGH: `trim_text(true)` conflicts with preserving XML events.**
  Plan 02 says the streaming reader-writer preserves markup verbatim, but `trim_text(true)` can drop or alter whitespace text nodes. Also, `quick_xml::Writer` generally preserves semantic XML, not byte-for-byte original markup. The plan should weaken "verbatim" claims or avoid trimming in rewrite paths.

- **HIGH: `inject_watermark_into_fpage` must error if no `FixedPage` end tag is seen.**
  The tests require this, but the action steps only say inject on `Event::End(FixedPage)` and return the writer output on EOF. Without an explicit `injected` flag, XML without `FixedPage` may silently return unchanged output.

- **HIGH: DirectWrite module needs explicit platform gating.**
  If `print_watermark_directwrite.rs` imports `windows::Win32::Graphics::DirectWrite`, the module should be behind `#[cfg(windows)]`, or the file must provide a non-Windows stub. Otherwise non-Windows CI may fail even if tests are gated.

- **HIGH: COM initialization contract is too weak if tests call DirectWrite directly.**
  The plan documents a caller prerequisite but Windows unit tests like `test_directwrite_measure_hello` must initialize COM themselves. Also, `FindFirstPrinterChangeNotification` is not COM initialization, so the plan should not rely on that as evidence that COM is initialized.

- **MEDIUM: Plan 02 may be scope creep for "foundational portions only."**
  The initial phase description includes rewriting a `.fpage` XML buffer, but Plan 02 adds full XPS ZIP rewrite, font URI scanning, OPC validation, compression preservation, and structural validation. Useful, but it is significantly broader than page geometry and text metrics.

- **MEDIUM: Compression preservation requirement is internally inconsistent.**
  Plan 02 says non-`.fpage` entries preserve original compression, but `.fpage` entries are always written as `Stored`. If the input `.fpage` was deflated, this changes package characteristics. That may be acceptable, but the plan should say so explicitly.

- **MEDIUM: Font fallback behavior may not work as stated.**
  DirectWrite font fallback usually happens during layout/rendering, while `CreateTextFormat` with a nonexistent family may still succeed depending on system font fallback behavior. A test that "verifies fallback path is exercised" likely needs an injectable helper or should be removed as a unit test expectation.

- **MEDIUM: XML injection attributes need escaping guarantees.**
  `UnicodeString` contains user-derived text. Using `BytesStart::push_attribute` should escape correctly if used with string values, but the plan should explicitly require structured attribute writing and test special characters like `&`, `<`, `"`, and apostrophes.

- **LOW: Truncation complexity is acceptable, but the max-iteration guard should be based on `chars().count()`, not `text.len()`.**
  `text.len()` is byte length and can greatly exceed character count for Unicode. It is safe as an upper bound, but the doc/test intent says character removal.

- **LOW: Plan references `watermark::inject` test filters that may not match module paths.**
  The module is `print_watermark`, so `cargo test -p dlp-agent watermark::inject` may run fewer tests than intended. Prefer `cargo test -p dlp-agent print_watermark`.

### Suggestions

- Add explicit `#[cfg(windows)] pub mod print_watermark_directwrite;` and a non-Windows compile path if needed.
- In DirectWrite tests, initialize COM with a small test guard before calling `measure`.
- Replace namespace assumptions with a concrete algorithm:
  - detect whether `FixedPage` is unqualified, default-namespaced, or prefixed;
  - parse the relevant `xmlns` attribute;
  - emit either `Canvas` with default namespace or `xps:Canvas` with the same prefix.
- Do not use `trim_text(true)` in XML rewrite functions that claim preservation.
- Track `saw_fixed_page` and `injected_watermark`; return `Err` if injection never happened.
- Add tests for XML escaping in `UnicodeString`.
- Clarify whether `.fpage` compression is intentionally normalized to `Stored` or should preserve the original method.
- Consider splitting Plan 02 into a smaller XML-buffer injection plan and a later full ZIP-rewrite plan if Phase 67.1 must stay narrow.

### Risk Assessment

**Overall risk: MEDIUM-HIGH.**

Plan 01 is medium risk, mostly because of Windows/COM integration details. Plan 02 is higher risk because namespace handling and XML preservation are easy to get subtly wrong, and XPS packages are strict enough that malformed injected markup could break printing. The plans are test-heavy and directionally sound, but they need tighter implementation constraints before execution.

4. **DirectWrite-to-XPS unit conversion** -- Explicitly document the conversion from `DWRITE_TEXT_METRICS` (DIPs, 1/96 inch) to XPS units.

**Additional Codex-specific concerns to address:**
7. **trim_text(true) conflict** -- Do not use `trim_text(true)` in XML rewrite functions that claim preservation.
8. **XML attribute escaping** -- Add tests for special characters (`&`, `<`, `"`) in `UnicodeString`.
9. **Compression method explicitness** -- Clarify whether `.fpage` compression is intentionally normalized to `Stored`.
10. **Test filter paths** -- Use `cargo test -p dlp-agent print_watermark` not `watermark::inject`.

**Recommendation**: Proceed with implementation after adding the namespace fix, COM contract, platform gating, and missing-FixedPage detection to the plans. The `FontUri` question should be resolved with a decision record in CONTEXT.md (reference existing font part vs. embed fallback vs. accept substitution) before Plan 02 execution begins. Address trim_text, XML escaping, and compression explicitness as implementation details.
