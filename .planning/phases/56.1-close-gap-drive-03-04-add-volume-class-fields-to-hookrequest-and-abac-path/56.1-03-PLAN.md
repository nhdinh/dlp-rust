## Objective

Wire the agent's hook IPC handler to perform volume-class-aware ABAC evaluation using the volume class data from the hook DLL's `HookRequest`. Replace the placeholder `build_cache_hint` heuristic with a proper `HookRequest` → `EvaluateRequest` conversion that forwards `source_volume_class` and `destination_volume_class`, then calls `OfflineManager::offline_decision` (synchronous, no async bridging) for authoritative policy decisions. The user identity remains synthetic (placeholder SID) — this is a known limitation deferred to a follow-up phase.

Purpose: After Plans 01 and 02, the `HookRequest` IPC payload carries volume class fields and the hook DLL populates them. This plan closes the final gap: the agent must convert the `HookRequest` into an `EvaluateRequest` (with volume class forwarded), evaluate it through the real ABAC pipeline via the synchronous `offline_decision` method, and return the authoritative decision to the hook DLL. Without this, volume-class policies still won't fire for hook-intercepted operations.

Output: Agent hook IPC path with real ABAC evaluation and volume-class-aware integration tests.

### build_cache_hint Disposition

The existing `build_cache_hint` function (lines 482-503) is a placeholder heuristic that classifies paths by text matching ("SECRET", "CONFIDENTIAL", etc.). After real ABAC evaluation is wired:

1. `build_cache_hint` is RETAINED but updated to use the classification from `EvaluateResponse` instead of path text matching.
2. The cache hint is built AFTER the ABAC evaluation returns, using the `EvaluateResponse.matched_label_id` or `resource.classification` from the response.
3. If the response has no classification (e.g., unclassified path), `build_cache_hint` returns `None`.
4. The cache hint remains non-authoritative — it only warms the DLL's LRU cache.
