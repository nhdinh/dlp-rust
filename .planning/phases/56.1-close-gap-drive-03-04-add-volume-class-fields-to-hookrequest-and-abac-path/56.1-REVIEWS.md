# Cross-AI Plan Review — Phase 56.1

## Claude Review

### Summary

The three plans provide a coherent, sequential path to close the DRIVE-03/04 gap: first extend the wire formats, then populate them in the hook DLL, and finally consume them in real ABAC evaluation. The scope is well-contained and the serde backward-compatibility strategy is sound. However, Plan 03 introduces a significant architectural tension by attempting "real ABAC evaluation" while still using a placeholder user SID, and its chosen `block_on` pattern inside the agent's hook handler risks runtime panics and reactor blocking. The plans also understate cross-plan dependencies and do not address cache invalidation, test data construction, or whether volume class failures should be fail-open or fail-closed consistently.

### Strengths

- **Clean separation of concerns** across the three plans: wire format → producer population → consumer evaluation.
- **Backward compatibility is explicitly designed in** via `#[serde(default, skip_serializing_if = "Option::is_none")]` and tested, protecting against old peer deserialization failures.
- **Fail-closed default** for missing volume class (`None` evaluates to `false` in `volume_class_matches`) aligns with the project's "ABAC tightens NTFS" invariant.
- **Threat model is present** for each plan and covers tampering, DoS, elevation, and information disclosure.
- **Success criteria are concrete and testable**, making verification straightforward.

### Concerns

- **HIGH — Placeholder user_sid undermines "real" ABAC evaluation in Plan 03.** Using `S-1-5-21-hook` means identity-based conditions will not fire correctly, so the end-to-end data flow is proven for volume class but not for a realistic policy. This should be called a partial integration, not real evaluation, unless the test harness explicitly uses only resource/action/environment conditions.
- **HIGH — `tokio::runtime::Handle::current().block_on()` is unsafe inside an async runtime.** Plan 03's mitigation mentions `block_in_place`/`spawn_blocking` only as a possibility; the chosen approach can panic or deadlock if the hook handler already runs on a Tokio worker thread. This needs to be resolved before execution.
- **MEDIUM — Cross-plan dependencies are not explicit.** Plan 01 must merge before Plan 02 can compile, and Plan 02 must merge before Plan 03's integration tests can pass end-to-end. The plans should state ordering and branch/merge strategy.
- **MEDIUM — Removal of `build_cache_hint` without replacement caching.** Plan 03 replaces a heuristic cache hint with full evaluation; if this code path is hot, latency may regress. The plan should mention whether caching is intentionally deferred or whether an `OfflineManager` result cache covers it.
- **MEDIUM — "Accept" stance on hook-DLL tampering is inconsistent with fail-closed design.** While the hook DLL is in-process, accepting forged volume classes without validation means a compromised user process can downgrade a `Removable` destination to `LocalDisk`. The threat model should at least require audit logging of mismatches or future server-side reconciliation.
- **LOW — Plan 03 success criterion #4 ("Integration tests prove end-to-end data flow") is vague.** It does not specify how the test will inject `HookRequest`, mock `OfflineManager`, or assert on policy decisions.

### Suggestions

- **Replace `block_on` with `tokio::task::block_in_place` or an explicit thread-pool bridge** in Plan 03, and document why the hook handler thread model permits it.
- **Rename Plan 03's objective** to clarify that user identity is still synthetic, e.g., "Wire volume-class-aware ABAC evaluation with deferred PID-to-SID resolution."
- **Add a dependency diagram or ordered task list** stating that Plan 01 blocks Plan 02, and Plan 02 blocks Plan 03.
- **Define the failure mode when volume class cannot be resolved** consistently across all three plans (currently implied as `None`/`false`, but not explicitly documented).
- **Add an audit event requirement** when volume class from the hook DLL is used in an ABAC decision, so forgery attempts leave a forensic trail.
- **Expand Plan 03 tests** to explicitly assert: (a) `LocalDisk`→`Removable` triggers a deny rule, (b) `LocalDisk`→`LocalDisk` does not, and (c) missing volume class defaults to deny when a rule requires it.
- **Consider a lightweight validation step** comparing the hook DLL's reported volume class against a server-side or agent-side re-classification for `Removable`/`Network` destinations to mitigate T-56.1-01/T-56.1-02.

### Risk Assessment

**Overall: MEDIUM-HIGH**

Justification: Plan 01 and Plan 02 are low-risk, mechanical changes with good test coverage and backward compatibility. Plan 03 is where the risk concentrates: it mixes synchronous hook-IPC handling with async ABAC evaluation using a placeholder identity, which can produce runtime panics, misleading policy results, and a false sense of completeness. If the `block_on` issue is resolved and the placeholder SID is clearly documented as a known limitation rather than "real" evaluation, the risk drops to **MEDIUM**. Without those changes, the phase could ship technically passing tests but operationally incorrect enforcement.

## OpenCode Review

### Plan 01: Add volume class fields to HookRequest and EvaluateRequest

**Summary:** A clean, well-scoped data-model change. Adds two optional fields to two structs with serde backward-compatibility attributes, updates one `From` impl, adds tests. Minimal blast radius.

**Strengths:**
- `#[serde(default)]` on new fields correctly handles old-peer deserialization — no wire-format breakage
- `skip_serializing_if = "Option::is_none"` keeps payload size unchanged for the common case
- T-56.1-03 mitigation (None → fail-closed via `volume_class_matches`) is the correct default
- Test plan covers backward-compat explicitly

**Concerns:**
- **LOW:** The `From<EvaluateRequest> for AbacContext` conversion is mentioned as a single change but may span multiple match arms or helper functions. Worth verifying there aren't other code paths that also hardcode `None` for volume class in `AbacContext` construction (grep for `volume_class: None`).
- **LOW:** No mention of updating `Display`/`Debug` impls for `HookRequest` or `EvaluateRequest` if they exist. New fields would cause compile warnings or missing output.

**Suggestions:**
- Add a grep step to find all places that construct `AbacContext` with `volume_class: None` to ensure none are missed
- Search for `Debug`/`Display` impls on both structs and add the new fields if applicable

**Risk: LOW** — Self-contained schema change with backward-compat, clearly scoped.

### Plan 02: Hook DLL volume class field population

**Summary:** Straightforward wiring — remove `#[allow(unused_variables)]`, stop prefixing params with `_`, set the struct fields, propagate through call chain. Correctly scoped to the DLL side only.

**Strengths:**
- Correctly identifies the `_` prefix + `#[allow(unused_variables)]` as the symptom of discarding
- Keeping changes in the DLL only — clean separation from Plan 03
- Narrow, well-bounded scope

**Concerns:**
- **MEDIUM:** "Update all trampoline call sites to pass resolved volume classes" is underspecified. How many trampolines? What are their signatures? If there are many call sites, this could cascade. The plan should estimate the count or list them.
- **MEDIUM:** No description of what "resolved volume classes" means at each trampoline. Does each trampoline need to call `get_volume_class` again, or is it already available? If re-resolution is needed, there's a performance cost (a `GetDriveTypeW` call per I/O).
- **LOW:** The "hook DLL volume class population test" in task 4 is vague — is this a unit test, an integration test, or both?

**Suggestions:**
- Audit and enumerate all trampoline call sites before implementation to scope the work accurately
- If volume class is already resolved at the trampoline level, pass it through rather than re-resolving; if not, evaluate whether caching is worthwhile
- Specify what the test in task 4 exercises (e.g., "verify that `classify_path_with_volume_class` returns a `HookRequest` with matching volume class fields")

**Risk: LOW** — Wiring-only changes, but risk of scope surprise if there are many undocumented trampoline call sites.

### Plan 03: Agent hook IPC real ABAC evaluation

**Summary:** The most significant plan — replaces a heuristic placeholder with real ABAC evaluation. Correctly identifies the threading concern with `block_on` and proposes mitigations.

**Strengths:**
- Replacing `build_cache_hint` with `OfflineManager::evaluate` is the right architectural direction
- Threat model correctly identifies `block_on` from within a Tokio runtime as a risk (T-56.1-06)
- Acknowledges the known limitation of placeholder user_sid (T-56.1-07) rather than pretending to solve it

**Concerns:**
- **HIGH:** `block_on` inside a Tokio runtime context is **not safe** — it will panic with "Cannot start a runtime from within a runtime" if the current thread is a Tokio worker. The mitigation mentions `block_in_place` or `spawn_blocking`, but this needs to be decided, not deferred. If the hook IPC handler is on a Tokio task, `block_in_place` requires the `rt-multi-thread` flavor and will still deadlock if the runtime has no spare threads. This is a genuine design risk.
- **MEDIUM:** `hook_request_to_evaluate_request` is described but not specified. Key mapping logic is unclear: How does `FileOperation` (copy/move/rename) map to ABAC `Action`? How is the subject (user identity) resolved? The `EvaluateRequest` requires subject, resource, action, and environment attributes — the plan only mentions `source_volume_class`/`destination_volume_class` forwarding but doesn't specify how the other fields are populated from `HookRequest`.
- **MEDIUM:** Existing `build_cache_hint` code path — should it be removed entirely, or kept as a fallback? The plan says "instead of the placeholder" but doesn't specify whether the old code is deleted or gated behind a feature flag.
- **LOW:** Integration tests (task 3) — "3 tests" without scenarios. Should specify: (a) volume class matches policy → allow, (b) volume class mismatches policy → deny, (c) None/unknown volume class → fail-closed.

**Suggestions:**
- **Critical:** Resolve the `block_on` design before implementing. Document the exact threading model: is the hook IPC handler on a Tokio task or a dedicated thread? If Tokio task, use `tokio::task::spawn_blocking` wrapping a synchronous `block_on` on a new runtime, or restructure the handler to be async and use `OfflineManager::evaluate` directly (either make it async or use `tokio::task::spawn_blocking` for the sync call).
- Specify the `HookRequest` → `EvaluateRequest` mapping explicitly in a table or pseudocode, especially the `FileOperation` → `Action` mapping and subject resolution
- Decide whether `build_cache_hint` is deleted, kept as fallback, or gated
- Name the three integration test scenarios concretely

**Risk: MEDIUM** — The `block_on`/threading issue is a real design problem that could cause runtime panics. The unspecified mapping logic is a gap that needs filling before implementation.

---

### Overall Phase Risk: MEDIUM

**Justification:**

Plans 01 and 02 are low-risk, well-scoped, and ready for implementation. Plan 03 has a concrete threading concern (HIGH severity if not resolved) and unspecified mapping logic that could lead to an incomplete or incorrect implementation. The phase goal — "volume class from hook DLL reaches ABAC evaluation and affects policy decisions" — is achievable, but Plan 03 needs the `block_on` design resolved and the `EvaluateRequest` mapping specified before coding begins.

**Reordering recommendation:** Implement Plans 01 → 02 → 03 in order (they're already correctly sequenced). Do not start Plan 03 until the `block_on` threading model is decided and documented. Consider adding a thread-model decision record as a Plan 03 prerequisite task.

## Consensus Summary

### Agreed Strengths

- **Clean three-plan separation** (wire format → DLL population → agent evaluation) praised by both reviewers
- **Backward compatibility via `#[serde(default)]`** correctly identified as a strength by both reviewers
- **Fail-closed default (`None` → false)** aligns with project security invariant; both reviewers confirm this is correct
- **Threat model coverage** is present and adequate for Plans 01 and 02

### Agreed Concerns

- **HIGH: `block_on` in Plan 03 is unsafe** — both Claude and OpenCode independently flag this as a critical design issue. The consensus is that the threading model must be resolved before Plan 03 implementation begins.
- **HIGH: Placeholder user_sid undermines "real" ABAC** — Claude flags this as HIGH; OpenCode notes the mapping logic is underspecified. Both agree the placeholder identity should be clearly documented as a known limitation.
- **MEDIUM: Cross-plan dependencies are implicit** — both reviewers note that Plans 01→02→03 ordering is correct but not explicitly stated in the plans.
- **MEDIUM: Plan 03 mapping logic is underspecified** — both reviewers note that `hook_request_to_evaluate_request` lacks detail on subject resolution, action mapping, and `build_cache_hint` disposition.

### Divergent Views

- **Claude raises MEDIUM concern about cache hint removal** (latency regression risk) that OpenCode does not mention. OpenCode focuses more on whether `build_cache_hint` should be deleted vs. kept as fallback.
- **Claude raises MEDIUM concern about hook-DLL tampering** (accept stance on forged volume classes) and suggests audit logging + server-side reconciliation. OpenCode does not raise this concern.
- **OpenCode raises LOW concern about `Display`/`Debug` impls** for `HookRequest`/`EvaluateRequest` that Claude does not mention.
- **OpenCode raises MEDIUM concern about trampoline call site enumeration** (scope surprise risk) that Claude does not mention.

### Actionable Recommendations (for PLAN.md incorporation)

1. **Plan 03 — Resolve `block_on` threading model before coding.** Add a prerequisite task to document the hook IPC handler thread model and select `spawn_blocking` or `block_in_place` with justification. Both reviewers agree this is the highest-priority fix.
2. **Plan 03 — Clarify "real ABAC evaluation" wording.** Rename objective to "Wire volume-class-aware ABAC evaluation with deferred PID-to-SID resolution" and document the placeholder SID as a known limitation.
3. **All Plans — Add explicit dependency ordering.** Add a "Prerequisites" section to each plan stating which prior plan(s) must be merged first.
4. **Plan 03 — Specify `HookRequest` → `EvaluateRequest` mapping in detail.** Add a mapping table (action strings → ABAC Action, subject resolution strategy, `build_cache_hint` disposition).
5. **Plan 03 — Define concrete integration test scenarios.** Name the three tests: (a) volume class matches policy → allow, (b) volume class mismatches policy → deny, (c) missing volume class → fail-closed.
6. **Plan 02 — Enumerate trampoline call sites before implementation.** Add a pre-implementation audit task to count and list all trampoline call sites that need updating.
7. **Plan 01 — Add grep step for `volume_class: None` in `AbacContext` construction.** Ensure no other code paths hardcode `None` after the `From` impl is updated.
8. **Plan 03 — Add audit event requirement for volume-class ABAC decisions.** Per Claude's suggestion, log when volume class from hook DLL is used in a decision to leave a forensic trail.
