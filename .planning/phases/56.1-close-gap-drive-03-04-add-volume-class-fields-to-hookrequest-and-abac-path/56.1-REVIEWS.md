### Plan 03: Agent hook IPC real ABAC evaluation

**Status: NOT YET implemented.** The current `inner_handler` in `handle_hook_request` (`hook_ipc.rs:442`) is a stub that delegates to the `HookHandler` closure, and `build_cache_hint` (`hook_ipc.rs:482`) uses a heuristic path-pattern check rather than real ABAC evaluation. This is the critical remaining gap.

| Dimension | Assessment |
|-----------|-----------|
| **Strengths** | The `HookIpcServer` architecture cleanly separates pipe transport from evaluation logic. The existing `HookHandler` type makes it injectable. The `OfflineManager` with its `async fn evaluate(&self, request: &EvaluateRequest) -> EvaluateResponse` is the right evaluation target. The codebase already has patterns for bridging sync/async boundaries (e.g., `bypass_correlator.rs:964` uses `rt.block_on`). |
| **Concerns** | **HIGH — Async/sync boundary.** `HookHandler` is a synchronous closure (`Fn(HookRequest) -> HookResponse`), but `OfflineManager::evaluate` is `async`. The plan's mitigation of `block_in_place` or `spawn_blocking` is misapplied: those are for running blocking code from async context, not the reverse. The correct approaches are: (a) use `tokio::runtime::Handle::current().block_on(...)` which requires a runtime handle to be set on the pipe server thread, or (b) create a dedicated `tokio::runtime::Runtime` in the pipe handler and call `rt.block_on(...)`. Approach (b) is safer since the pipe server runs on a bare `std::thread` and `Handle::current()` would panic without an `Entered` guard. |
|| **HIGH — Performance.** Real ABAC evaluation involves policy loading, attribute resolution, and rule evaluation. If it's done synchronously in the hook callback, it blocks the pipe thread and every outstanding hook call. The plan must specify: (a) whether `OfflineManager::evaluate` can be called concurrently (does the `EngineClient` HTTP client handle concurrent requests?), (b) what timeout is enforced (the hook DLL has a `timeout_ms` in `send_request`), (c) whether classification/tier-based fast-path should bypass ABAC entirely (e.g., T1 reads -> immediate ALLOW). |
|| **MEDIUM — Response conversion.** The plan only mentions converting `HookRequest -> EvaluateRequest`. It does not mention converting the `EvaluateResponse` back to `HookResponse`, which requires mapping `decision`, `reason`, and potentially `matched_policy_id`. |
|| **MEDIUM — Error handling.** If `block_on` panics (e.g., no runtime, evaluate panics), the hook handler must not crash. The `handle_hook_request` function must either catch panics and return a safe fail-closed DENY, or use `std::panic::catch_unwind`. |
|| **MEDIUM — Where does the real handler get wired?** The plan does not specify where in `service.rs` (or `main.rs`) the real evaluation `HookHandler` is constructed and injected into `HookIpcServer`. This is a non-trivial assembly point that needs the `OfflineManager` reference, `CacheAccessor`, and potentially `ApprovalCache` to be available at server startup. |
|| **LOW — Placeholder SID (T-56.1-07).** The plan correctly accepts this as a known limitation. Worth documenting: without real SID resolution, volume-based policies that vary by user group will not fire correctly through the hook path. |
| **Risk** | **HIGH** — The async/sync boundary and lack of timeout/error guarantees in the hook callback path could cause hard crashes or service hangs if not handled correctly. |

**Suggestions:**
1. Replace `block_in_place`/`spawn_blocking` mitigation with concrete code: create a `lazy_static` or `once_cell::sync::OnceCell` tokio `Runtime` scoped to the hook IPC thread, and use `runtime.block_on(...)`. Alternatively, set a `tokio::runtime::Handle` on the pipe server thread using `handle.enter()`.
2. Add a `timeout` wrapper around `block_on` to prevent a stuck engine call from blocking the pipe thread indefinitely:
   ```rust
   tokio::time::timeout(Duration::from_secs(5), fut)
   ```
3. Specify the response conversion: `EvaluateResponse.decision -> HookResponse.decision`, `EvaluateResponse.reason -> HookResponse.reason`.
4. Use `std::panic::catch_unwind` around the evaluate call to ensure the hook handler never panics — return `HookResponse { decision: DENY, reason: "internal error" }` on panic.
5. Add an integration test that: (a) starts a mock engine + `HookIpcServer` with real `OfflineManager`, (b) sends a `HookRequest` with volume classes set, (c) verifies `HookResponse.decision` reflects volume-class ABAC policy.

## Claude Review

### Plan 01: Add volume class fields to HookRequest and EvaluateRequest

### Summary
Plan 01 is a clean, minimal schema change that enables the rest of the phase. Adding `source_volume_class` and `destination_volume_class` as `Option<T>` fields with `serde(default, skip_serializing_if = "Option::is_none")` correctly preserves backward compatibility with old peers while keeping the wire format compact. The decision to forward these fields into `AbacContext` instead of hardcoding `None` is the exact pivot point that makes DRIVE-03/04 enforceable.

### Strengths
- `serde(default)` mitigates T-56.1-02 (old peers) without requiring protocol versioning.
- Fail-closed semantics (None evaluates false) align with the project's Default Deny principle.
- Round-trip and backward-compatibility tests are the right verification focus for a schema change.

### Concerns
- **MEDIUM**: The review does not state how `AbacContext` represents volume class or what happens when the field is `None`. If the ABAC engine implicitly treats `None` as a wildcard match rather than a false condition, the fail-closed claim is violated.
- **MEDIUM**: Five tests should explicitly cover: missing field, explicit `null`, valid source only, valid destination only, and both set. The plan should list these cases to avoid a false sense of coverage.
- **LOW**: `skip_serializing_if = "Option::is_none"` is correct for new->old peers, but old->new peers will still omit the field; this is already handled by `serde(default)`.

### Suggestions
1. Add a requirement to audit the ABAC `Attribute`/`Condition` evaluation path to confirm `None` never matches a positive rule.
2. Enumerate the exact five test matrix cases in the plan.
3. Consider adding a unit test that asserts `AbacContext` built from an `EvaluateRequest` with `None` volume classes evaluates to `false` for a volume-class-specific policy.

### Risk Assessment: LOW
The change is localized, well-scoped, and uses standard serde patterns. The only real risk is an incorrect assumption about ABAC default semantics, which is fixable with one focused test.

## Plan 02: Hook DLL volume class field population

### Summary
Plan 02 correctly targets the data origin: the hook DLL already classifies paths by volume and now needs to carry that classification through `HookRequest`. Refactoring `classify_path_with_volume_class` and `classify_and_log_path` to accept and forward volume-class parameters is the right structural change. Updating trampoline call sites is necessary but is the highest-touch, most error-prone part of the phase.

### Strengths
- Populates volume class at the source rather than re-deriving it later, which is more efficient and less racy.
- Keeps the existing classification machinery intact.
- Includes a hook DLL test, which is important because hook code is harder to exercise in integration.

### Concerns
- **HIGH**: Volume class resolution in the hook DLL runs inside the target process on every intercepted I/O operation. If classification involves synchronous system calls (WMI, registry, DeviceIoControl), it can introduce latency, jitter, or deadlocks inside hooked applications. The plan does not mention caching.
- **MEDIUM**: Trampoline call sites may include operations without a clear source/destination pair (e.g., delete, create). The plan must specify the convention for which parameter is `None` and ensure every site is updated consistently.
- **MEDIUM**: Hook DLL test coverage is described as a single test. Given the number of trampolines, one test is likely insufficient unless it exercises the classification plumbing end-to-end for multiple operation types.

### Suggestions
1. Document the volume-class cache strategy (e.g., cached per volume path with TTL) and add a performance requirement.
2. Explicitly list each trampoline operation affected and whether it supplies source, destination, or both.
3. Add at least one test per operation class (read, write/copy, move/rename) rather than a single generic test.

### Risk Assessment: MEDIUM
The schema and logic changes are sound, but performance and correctness risks in hook code are real. Missing a single trampoline call site would leave a volume-class policy bypass.

## Plan 03: Agent hook IPC real ABAC evaluation

### Summary
Plan 03 is the integration point: it converts `HookRequest` into `EvaluateRequest` and replaces placeholder behavior with real ABAC evaluation through `OfflineManager`. The goal is correct, but the proposed execution mechanism—`tokio::runtime::Handle::current().block_on()`—is dangerous inside an async handler and the plan's own threat model flags it without choosing a definitive mitigation.

### Strengths
- Centralizing the conversion in `hook_request_to_evaluate_request` is a good abstraction.
- Using `OfflineManager::evaluate` finally closes the loop so hook-intercepted operations are subject to the same ABAC policies as other paths.
- Integration tests are the right tool for verifying end-to-end policy firing.

### Concerns
- **HIGH**: `Handle::current().block_on()` from within an async runtime context can panic or deadlock in tokio. The plan mentions `block_in_place` or `spawn_blocking` as mitigations but does not commit to one. This is a blocking architectural decision that must be resolved before implementation starts.
- **MEDIUM**: Placeholder SID (T-56.1-07) means volume-class policies that depend on user identity may evaluate incorrectly. The plan accepts this as a known limitation, but the phase goal should explicitly state whether identity-aware ABAC is in or out of scope.
- **MEDIUM**: Three integration tests may not cover the matrix of: (source volume class match, destination volume class match, both match, neither match, missing field, offline manager unavailable).
- **LOW**: The plan does not clarify whether `HookHandler` already holds an `OfflineManager` reference or whether it needs to be injected, which affects how many call sites change.

### Suggestions
1. Mandate `tokio::task::spawn_blocking` (or `block_in_place` with a clear justification) in the plan, not as an afterthought.
2. Explicitly scope identity-aware evaluation: if SID is still a placeholder, document that volume-class-only policies are the target of this phase.
3. Expand the integration test matrix to at least six cases covering all match/no-match combinations and the missing-field path.
4. Verify that `HookHandler` has access to `OfflineManager` and, if not, add a dependency injection task.

### Risk Assessment: HIGH
The execution-model risk is genuine and could cause runtime instability. Resolving it is straightforward, but leaving it ambiguous during implementation would be dangerous.

## Overall Phase Assessment

### Dependency Ordering
The plans are correctly ordered: **Plan 01 must land first** because Plans 02 and 03 depend on the `HookRequest` schema. After Plan 01, Plan 02 and Plan 03 can proceed in parallel, but Plan 03's integration tests cannot meaningfully assert volume-class forwarding until Plan 02 populates the fields. Therefore:
1. Plan 01 (schema)
2. Plan 02 (hook DLL population) and Plan 03 (agent evaluation) in parallel
3. Joint integration validation after both land

### Cross-Cutting Concerns
- **Security**: The fail-closed default is appropriate, but it must be verified in the ABAC engine, not only in serde defaults.
- **Performance**: Volume class lookup in the hook DLL is the main hot-path concern; require caching.
- **Scope creep**: The three plans stay within the DRIVE-03/04 gap and do not introduce unnecessary features. The placeholder SID should be explicitly out of scope.
- **Test coverage**: Each plan's test count is a lower bound; specify the exact scenarios to prevent under-coverage.

### Overall Risk Level: MEDIUM
Plan 01 is low risk. Plan 02 introduces correctness and performance risks in hook code but is manageable with explicit trampoline enumeration and caching. Plan 03 is the highest risk due to the unresolved async execution strategy. If the `block_on` issue is firmly resolved before coding begins, the overall phase risk drops to **LOW-MEDIUM**.
