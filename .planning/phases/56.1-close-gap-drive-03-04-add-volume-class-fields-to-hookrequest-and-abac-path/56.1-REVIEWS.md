**Assessment: Substantially complete, plan overstates remaining work**

**Strengths:**
- Correct `#[serde(default)]` and `#[serde(default, skip_serializing_if = "Option::is_none")]` annotations already in place

**Concerns:**
- **MEDIUM**: Plan asserts 5 new tests are needed; 5+ tests already exist. If these were written as Nyquist anchors before implementation, the review should note they must be verified to pass — otherwise the plan is describing already-complete work under the guise of new work.
- **LOW**: The threat model correctly identifies T-56.1-02 (DoS via bincode deserialization failure) — `#[serde(default)]` is sufficient for JSON but **bincode will still fail** on missing fields since bincode doesn't support default. If they do cross version boundaries, JSON serde is fine (HTTP paths); bincode (pipe) will break.

**Suggestions:**

- Add a test verifying `skip_serializing_if = "Option::is_none"` actually omits `source_volume_class`/`destination_volume_class` from JSON when `None` (matching the pattern used for `source_application` at test_evaluate_request_omits_none_app_identity_fields:823).

### Plan 03: Agent hook IPC real ABAC evaluation

**Assessment: Correct design, some gaps in detail**

**Strengths:**
- Correctly avoids `block_on`/`spawn_blocking`/`block_in_place` — `offline_decision` is synchronous by definition (offline.rs:144)
- `HookHandler` type (`Arc<dyn Fn(HookRequest) -> HookResponse + Send + Sync + 'static>`) at hook_ipc.rs:54 is sync-only, so the constraint is structurally enforced
- `build_cache_hint` retained with response-based classification is pragmatic for cache warming
- Placeholder SID "S-1-5-21-hook" correctly documented as deferred — this is acceptable since the hook path is advisory/audit, and ABAC authority lives on the server via `OfflineManager::evaluate` (which goes to the Policy Engine server when online)
- Four integration tests covering all combinations is thorough

**Concerns:**
- **HIGH**: The **interception event loop** (`interception/mod.rs:389-406`) is a separate production path that builds `EvaluateRequest` with `..Default::default()` — it does **NOT** set `source_volume_class` or `destination_volume_class`. If volume class ABAC policies are expected to apply through this path, there is a gap. If Phase 56.1 scope is strictly the hook DLL → agent pipe path, this is out of scope — but the plans should explicitly state this boundary.
- **MEDIUM**: **`offline_decision` does not consider volume class** (offline.rs:144-159). It returns `fail_closed_response(request.resource.classification)` which is pure tier-based. An offline cache miss will bypass all volume-class conditions. This is consistent with fail-closed semantics (volume class None → condition doesn't match → policy doesn't match → default-allow/deny based on tier), but the plan should acknowledge this implicit behavior.
- **MEDIUM**: The end-to-end test with **real NamedPipe + PolicyStore** is fragile. NamedPipe tests require Windows and fail on CI runners without the `\\.\pipe\` namespace. Consider either: (a) marking it `#[cfg(windows)]` with `#[ignore]` for non-Windows CI, or (b) using an in-memory `HookHandler` with a real `PolicyStore` in a sub-test, and a separate pipe test with mock handler.
- **MEDIUM**: The plan says `build_cache_hint` should use `EvaluateResponse` classification, but `build_cache_hint` currently takes a `&str` path. If the response from ABAC evaluation contains the classification, the function signature needs to change to `fn build_cache_hint(path: &str, classification: Option<Classification>) -> Option<CacheHint>`. The plan should specify this signature change and the fallback when classification is `None`.
- **LOW**: `hook_request_to_evaluate_request` needs to populate `user_sid` with the placeholder "S-1-5-21-hook" as documented. The plan should specify where this happens and add a `reason` field explanation in the `EvaluateResponse.reason` so audit logs are clear it came from the hook path with a placeholder.
- **LOW**: `map_hook_action_to_abac` — the mapping from `HookRequest.action` (string: "CREATE", "WRITE", "READ", etc.) to `Action` enum. This can fail (unknown action string). Should it return `Result<Action>` or default to a safe value (e.g., `Action::WRITE`)? The plan should specify: fail-closed (default WRITE = conservative) vs. fail-open (return error -> ALLOW?).

**Suggestions:**
- Add an explicit scope note: "Phase 56.1 covers only the hook DLL → agent named-pipe path. The interception event loop path (`interception/mod.rs`) is out of scope and will be addressed separately."
- Change `build_cache_hint` signature to accept `Option<Classification>` from the ABAC response, falling back to the path heuristic when `None`.
- For `map_hook_action_to_abac`, use a match with explicit mapping and default to `Action::WRITE` (conservative) for unknown strings.
- Make the end-to-end NamedPipe test `#[cfg(windows)]` and have a separate pure-logic integration test (no pipe) that tests the full `HookRequest → EvaluateRequest → OfflineManager::offline_decision` path.

## Claude Review (Cycle 2)

### Plan 01: Add volume class fields to HookRequest and EvaluateRequest

### Summary
This is a clean, well-scoped foundation plan. It correctly identifies backward compatibility as the primary constraint and uses `#[serde(default)]` plus `skip_serializing_if` to safely evolve the IPC contract without breaking old peers. The test count and success criteria are concrete.

### Strengths
- `#[serde(default)]` on new fields is the correct mitigation for T-56.1-02 (DoS via deserialization failure).
- Distinguishing `HookRequest` (bincode IPC) from `EvaluateRequest` (ABAC input) avoids leaking wire-format concerns into policy evaluation.
- Fail-closed default (`None` evaluates to false) is the right security posture for T-56.1-03.
- Explicit success criterion "No other code paths hardcode volume_class: None" prevents regression.

### Concerns
- **MEDIUM**: The plan doesn't specify the concrete type of `source_volume_class`/`destination_volume_class`. If it's an enum, there needs to be a backward-compatible variant ordering; if it's `Option<String>`, ABAC will need normalization/validation to avoid policy bypass via casing or unexpected values.
- **MEDIUM**: `skip_serializing_if = "Option::is_none"` on `EvaluateRequest` is fine for JSON, but if `EvaluateRequest` is ever serialized with bincode, the size/offset semantics change — the plan should confirm `EvaluateRequest` is JSON-only.
- **LOW**: "5 new tests total" is reasonable but should explicitly include at least one round-trip for `HookRequest` (bincode) and one for `EvaluateRequest` (JSON), not just backward compatibility.

### Suggestions
- Add a success criterion defining the volume class type (enum vs string) and its `Default` behavior.
- Include a test that serializes `HookRequest` with the *old* struct layout and deserializes with the *new* struct layout using bincode, since bincode is not as forgiving as serde_json.
- Document whether `EvaluateRequest` is intended to cross any IPC boundary or stay in-process.

## Plan 02: Hook DLL volume class field population

### Summary
This plan correctly focuses on forwarding already-resolved volume class information through the hook DLL's internal pipeline and into the `HookRequest`. Its scope is narrow and builds directly on Plan 01.

### Strengths
- Trampoline audit is the right first task; volume class propagation is easy to miss at a single call site.
- Reusing `classify_path_with_volume_class` keeps the change localized.
- The plan acknowledges that volume class in the pipe payload is acceptable operational metadata.

### Concerns
- **HIGH**: The test coverage is very thin. "Verify hook DLL volume class population test exists" implies one test, but there are likely multiple trampolines (CreateFile, WriteFile, CopyFile, MoveFile, etc.) and multiple code paths (network drive, removable media, local NTFS). One test will not cover all call sites.
- **MEDIUM**: The plan doesn't address how volume class is *resolved*. If `classify_path_with_volume_class` already exists, is its logic trustworthy? Edge cases like UNC paths, mounted VHDs, or reparse points could misclassify and silently populate wrong fields.
- **MEDIUM**: No mention of error handling when volume classification itself fails. If the helper returns an error, does the hook request fail-closed or default to `None`?

### Suggestions
- Add a test matrix covering each trampoline/action that constructs a `HookRequest`.
- Add unit tests for `classify_path_with_volume_class` edge cases: UNC paths, removable drives, unknown/missing paths, and paths the hook cannot resolve.
- Define the failure mode: if classification fails, populate `None` (fail-closed) and log at `tracing::warn!`.

## Plan 03: Agent hook IPC real ABAC evaluation

### Summary
This is the riskiest and most consequential plan. It correctly avoids async runtime abuse by calling `offline_decision` synchronously, but it introduces a known-weak identity signal (placeholder SID) and a complex end-to-end test. The design decisions are clearly documented, which helps, but the placeholder SID needs scrutiny.

### Strengths
- Explicitly forbidding `block_on`, `spawn_blocking`, `block_in_place`, and new Tokio runtimes in the hook handler prevents deadlocks and reactor starvation (T-56.1-06).
- Retaining `build_cache_hint` and updating it to use the response classification preserves performance without reintroducing the placeholder heuristic.
- Four integration tests cover the core decision matrix: match→deny, mismatch→allow, missing→fail-closed, plus end-to-end.
- Converting `HookRequest` → `EvaluateRequest` in a dedicated function isolates mapping logic for testing.

### Concerns
- **HIGH**: The placeholder `user_sid: "S-1-5-21-hook"` is a significant authorization weakness. ABAC policies keyed to user attributes will evaluate against a fake SID, which means real per-user policies cannot be enforced on the hook path. This is acceptable only if documented as a hard limitation, but the phase goal says "wire agent ABAC evaluation" — a placeholder SID means the ABAC evaluation is not fully operational for identity-dependent rules.
- **HIGH**: The end-to-end test ("real NamedPipe+PolicyStore") is valuable but likely flaky and slow. If it requires Windows-specific handles or real NTFS paths, it may not run in CI. The plan should state whether this test is gated behind `#[cfg(windows)]` or a feature flag.
- **MEDIUM**: `map_hook_action_to_abac` must handle unknown action strings. If the hook DLL adds a new action and the agent is older, the mapping should fail closed (deny) rather than default to an allow action.
- **MEDIUM**: The threat model repeatedly marks tampering as "accept (advisory; audit trail)." The plan needs to confirm that volume class values are written to the audit log so the advisory nature is actually observable.
- **MEDIUM**: No mention of what happens if `offline_decision` returns an error. The hook handler must return a deny decision to the DLL, not crash or allow by default.
- **LOW**: Three mock-server tests plus one end-to-end test may not cover action mapping exhaustively. Add a test for each mapped action.

### Suggestions
- Add a success criterion that unknown/unmapped hook actions result in `Deny` (fail-closed).
- Make the end-to-end test conditional (`#[cfg(windows)]` or integration-test feature) and document its runtime requirements.
- Add an audit-log assertion in the mock-server tests verifying that `source_volume_class` and `destination_volume_class` appear in the decision record.
- Consider splitting Plan 03 into two phases: (1) synchronous ABAC wiring with placeholder SID, and (2) real PID-to-SID resolution, since the latter is a non-trivial Windows security exercise.
- Add a test for `offline_decision` returning an error and the handler returning `Deny`.

## Overall Risk Assessment: MEDIUM-HIGH

**Justification:**

The phase goals are technically achievable, and Plans 01 and 02 are low-risk foundation work. The overall risk is elevated primarily by Plan 03:

1. **Placeholder SID** undermines the ABAC value proposition. If policies rely on user identity, the hook path will silently make incorrect decisions. This is acceptable as a documented limitation, but it means the phase does not fully close the DRIVE-03/DRIVE-04 gap for identity-aware rules.
2. **End-to-end test complexity** may lead to either a flaky test or a test that is skipped in practice, reducing confidence in the closure claim.
3. **Thin test coverage in Plan 02** for multiple trampolines and volume-class edge cases creates a regression risk.

If the placeholder SID is explicitly scoped as a follow-up item (e.g., "PID-to-SID resolution tracked in phase X.Y") and the end-to-end test is made CI-stable, the risk drops to **MEDIUM**. Without those mitigations, the phase ships with a known authorization gap.
