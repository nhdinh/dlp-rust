# DLP-RUST — Enterprise Data Loss Prevention System

## Core Value

Prevent enterprise data exfiltration across all major Windows endpoint channels — file copy, USB, clipboard, drag-and-drop, cloud sync, print — through ABAC-based policy enforcement, without requiring kernel drivers or EV code signing.

## Mission

Deliver production-grade DLP for Windows enterprises that combines NTFS access control, Active Directory identity, and a fine-grained ABAC policy engine into a four-layer defense stack with centralized administration, real-time enforcement, and full audit/SIEM integration.

## What This Is

A five-crate Rust workspace deployed as Windows services and operator tooling:

| Crate | Role |
|-------|------|
| `dlp-common` | Shared types — ABAC engine, audit events, classification, AD client, disk/USB models |
| `dlp-server` | Central HTTP server — admin API, policy store, audit store, SIEM relay, alert router |
| `dlp-agent` | Windows Service — file/clipboard/USB/disk/cloud/print interception, policy enforcement, IPC |
| `dlp-user-ui` | User-session GUI — notifications, dialogs, clipboard monitor, system tray |
| `dlp-admin-cli` | Interactive TUI — password management, policy CRUD, system config screens |

### Architecture Layers

1. **Identity** — Active Directory via `ldap3`; AD is the source of identity truth.
2. **Access** — NTFS ACLs provide coarse-grained baseline enforcement.
3. **Policy** — ABAC engine evaluates user/resource/action/environment attributes against operator-authored rules (boolean ALL/ANY/NONE composition).
4. **Enforcement** — `dlp-agent` (SYSTEM session) intercepts I/O through OS-level hooks; `dlp-user-ui` (user session) handles clipboard and notifications.

### Critical Invariant

If NTFS ALLOW and ABAC DENY → FINAL RESULT = DENY. ABAC always tightens, never loosens, the underlying NTFS gate.

### Tech Stack

- **Async runtime:** Tokio (multi-threaded)
- **Platform:** Windows 10/11 only (Win32 API dependencies via `windows` 0.62)

## Phase 56.1: Close gap DRIVE-03/04 — add volume class fields to HookRequest and ABAC path

**Status:** Ready for planning
**Source:** Beads issue dlp-rust-5ih

This gap-closure phase carries the volume-class classification that the hook DLL already determines locally across the IPC boundary into the agent's ABAC evaluation.

The hook DLL currently determines source/destination volume class locally but discards those parameters before constructing `HookRequest`. `HookRequest` has no volume-class fields, so the agent's ABAC evaluation cannot evaluate actual volume class.

**Downstream effect:** Policies that should distinguish `LocalDisk`, `Removable`, `Optical`, `Network`, `Virtual` (e.g., SD/optical/virtual drive exfiltration rules) cannot fire correctly.

**Scope:**
- Add source/destination volume class fields to the IPC `HookRequest` payload
- Populate those fields in the hook DLL instead of discarding them
- Update agent ABAC evaluation to pass volume class into policy conditions
- Add tests covering SD/optical/virtual drive policy decisions
- Run Nyquist tasks and mark complete

## Requirements Addressed

- DRIVE-03: HookRequest carries source_volume_class
- DRIVE-04: HookRequest carries destination_volume_class
- DRIVE-03: Hook DLL populates source_volume_class
- DRIVE-04: Agent ABAC evaluates volume class from HookRequest
- DRIVE-03/04: SD/Optical/Virtual drive policy decisions

## Plans to Review

### Plan 01: Add volume class fields to HookRequest and EvaluateRequest

**Objective:** Add `source_volume_class` and `destination_volume_class` fields to the IPC `HookRequest` payload and the ABAC `EvaluateRequest` wire format, then update the `From<EvaluateRequest> for AbacContext` conversion to forward these fields instead of hardcoding `None`.

**Tasks:**
1. Add volume class fields to `HookRequest` (dlp-common/src/hook_ipc.rs) and `EvaluateRequest` (dlp-common/src/abac.rs) with `#[serde(default, skip_serializing_if = "Option::is_none")]`
2. Update `From<EvaluateRequest> for AbacContext` to forward `req.source_volume_class` and `req.destination_volume_class` instead of hardcoding `None`
3. Add backward-compatibility and round-trip tests (5 new tests total)

**Threat Model:**
- T-56.1-01: Tampering — Hook DLL sends fake volume class → accept (Hook DLL is in-process protected by injection; volume class is advisory, ABAC authority is on agent/server)
- T-56.1-02: Denial of Service — Bincode deserialization failure from old peers → mitigate (`#[serde(default)]` on new fields ensures old peers don't cause Malformed errors)
- T-56.1-03: Elevation of Privilege — Volume class defaulting to LocalNTFS → mitigate (`None` evaluates to `false` in `volume_class_matches`, fail-closed)
- T-56.1-04: Information Disclosure — Volume class in audit logs → accept (operational metadata, not PII)

**Success Criteria:**
1. `HookRequest` has `source_volume_class` and `destination_volume_class` fields with `#[serde(default, skip_serializing_if = "Option::is_none")]`.
2. `EvaluateRequest` has the same two fields with the same serde attributes.
3. `From<EvaluateRequest> for AbacContext` forwards `req.source_volume_class` and `req.destination_volume_class` instead of hardcoding `None`.
4. All new fields have backward-compatibility tests (JSON deserialization without fields → None).
5. All existing dlp-common tests continue to pass.

### Plan 03: Agent hook IPC real ABAC evaluation

**Objective:** Wire the agent's hook IPC handler to perform real ABAC evaluation using the volume class data from the hook DLL's `HookRequest`. Replace the placeholder `build_cache_hint` heuristic with a proper `HookRequest` → `EvaluateRequest` conversion that forwards `source_volume_class` and `destination_volume_class`, then calls `OfflineManager::evaluate` for authoritative policy decisions.

**Tasks:**
1. Create `hook_request_to_evaluate_request` function that converts `HookRequest` to `EvaluateRequest` with volume class fields forwarded, subject/resource/environment construction, action mapping
2. Update `HookHandler` to use `OfflineManager::evaluate` via `tokio::runtime::Handle::current().block_on()`
3. Add hook IPC volume class integration tests (3 tests)

**Threat Model:**
- T-56.1-06: Denial of Service — `block_on` panics if called from within Tokio runtime → mitigate (use `tokio::task::block_in_place` or `spawn_blocking` if problematic; document threading model)
- T-56.1-07: Elevation of Privilege — Placeholder user_sid "S-1-5-21-hook" could be exploited → accept (known limitation; real PID-to-SID resolution is deferred per RESEARCH.md Open Question #1)
- T-56.1-08: Information Disclosure — EvaluateRequest with volume class in audit logs → accept (operational metadata)

**Success Criteria:**
1. `hook_request_to_evaluate_request` converts `HookRequest` to `EvaluateRequest` with `source_volume_class` and `destination_volume_class` forwarded.
2. The agent's hook IPC handler performs real ABAC evaluation via `OfflineManager::evaluate` instead of the placeholder `build_cache_hint` heuristic.
3. Volume class from the hook DLL reaches `PolicyStore::evaluate` and affects policy decisions.
4. Integration tests prove the end-to-end data flow works correctly.
5. All existing dlp-agent tests continue to pass.
