# Phase 56.1: Code Review Report

**Reviewed:** 2026-06-18
**Depth:** standard
**Files Reviewed:** 11
**Status:** issues_found

## Summary

This review covers the Phase 56.1 changes adding `source_volume_class` and `destination_volume_class` fields to `HookRequest` and `EvaluateRequest`/`AbacContext`, along with the corresponding ABAC `PolicyCondition` variants and hook DLL trampoline integration. The changes span `dlp-common`, `dlp-hook-dll`, and `dlp-agent` crates.

Four critical issues were found, including a security gap in the Chrome handler (fail-open instead of fail-closed), a placeholder SID that will break identity-based policies, and two bincode backward-compatibility breakages. Six warnings cover missing volume class propagation in handle-based trampolines, missing validation, and test quality issues. Three info items note documentation/comment issues.

---

## Critical Issues

### CR-01: Chrome handler falls OPEN when no evaluator is set (security gap)

**File:** `dlp-agent/src/chrome/handler.rs:328`
**Issue:** The `dispatch_request` function uses `unwrap_or(Decision::ALLOW)` when the policy evaluator is not set. This is a fail-open behavior for a security-critical path. If the evaluator is not initialized (startup race, bug, or crash), all clipboard paste operations from Chrome are allowed, bypassing DLP policy entirely.

**Fix:** Change to fail-closed. For clipboard paste (which carries data exfiltration risk), the default should be `Decision::DENY` with an appropriate reason when no evaluator is available:

```rust
let decision = evaluator_opt
    .map(|evaluator| evaluator(&evaluate_request).decision)
    .unwrap_or(dlp_common::abac::Decision::DENY); // Fail-closed
```

Additionally, log a warning at `error!` level when this fallback is triggered so operators are alerted to the misconfiguration.

### CR-02: Placeholder SID in `hook_request_to_evaluate_request` breaks identity-based policies

**File:** `dlp-agent/src/hook_ipc.rs:121`
**Issue:** The `hook_request_to_evaluate_request` function hardcodes a synthetic SID `"S-1-5-21-hook"` and user name `"hook_user"` for all hook-derived requests. This means any ABAC policy that uses `MemberOf` conditions, user-specific rules, or identity-based access controls will evaluate incorrectly. The comment acknowledges this is a "known limitation" but the code is in production paths (`with_cache_and_offline` constructor).

**Fix:** At minimum, add a prominent warning log every time this synthetic identity is used. Better: fail-closed by returning `Decision::DENY` when the real SID cannot be resolved, or add a `subject.is_synthetic` flag that policies can check. The TODO on line 117 has been there for multiple phases without resolution.

```rust
// Add to the Subject construction:
tracing::warn!(
    path = %req.path,
    "hook_request_to_evaluate_request: using synthetic SID — identity-based policies will not match"
);
```

### CR-03: Bincode backward compatibility broken for `HookRequest` (old peers cannot deserialize)

**File:** `dlp-common/src/hook_ipc.rs:102-136`
**Issue:** The `HookRequest` struct uses `#[serde(default)]` on the new `source_volume_class` and `destination_volume_class` fields. This works for JSON deserialization (serde handles missing fields), but **bincode does not support `serde(default)`**. Bincode requires exact field layout match. When an old hook DLL (without the new fields) sends a raw `HookRequest` frame to a new agent, or vice versa, bincode deserialization will fail.

The `handle_connection` function in `dlp-agent/src/hook_ipc.rs` has a fallback path (lines 537-558) that attempts legacy `HookRequest` deserialization, but this only helps in one direction (new agent receiving old-format requests). An old agent receiving a new-format request will fail.

**Fix:** The protocol already has `IpcEnvelope` versioning. The correct approach is to bump the protocol version and only include volume class fields in `IpcEnvelope::V2` (or later), never in raw `HookRequest` bincode. Alternatively, if raw `HookRequest` bincode must be used, the fields must be appended at the end with a custom bincode config that ignores trailing bytes, or the protocol must mandate envelope wrapping for all new fields.

### CR-04: `VolumeClassQuery` handler in agent returns `None` unconditionally (unimplemented)

**File:** `dlp-agent/src/hook_ipc.rs:510-524`
**Issue:** The `VolumeClassQuery` payload handler always returns `VolumeClassResponse { class: None }`, regardless of the drive letter. This means the hook DLL's `classify_path_with_volume_class` function (which sends volume class queries when the cache misses) will always receive `None`, causing volume-class ABAC conditions to fail-closed (evaluate to false). While fail-closed is correct from a security standpoint, this means the entire volume-class feature is non-functional in production — all volume-class policies will silently fail to match.

**Fix:** Wire the `VolumeClassQuery` handler to the actual `VolumeDetector` or `volume_class_map` from the agent's state. The handler should look up the drive letter in the agent's volume class cache and return the actual classification. Until this is implemented, add an `error!` log so operators know the feature is not working:

```rust
IpcPayloadV1::VolumeClassQuery(query) => {
    error!(drive_letter = query.drive_letter, "VolumeClassQuery not implemented — returning None (fail-closed)");
    // ... existing response code ...
}
```

## Warnings

### WR-01: Handle-based trampolines do not resolve or forward volume class

**File:** `dlp-hook-dll/src/trampolines.rs:402-451` (classify_and_log_handle)
**Issue:** The `classify_and_log_handle` function (used by `HookWriteFile`, `HookWriteFileEx`, `HookSetFileInformationByHandle`, `HookNtWriteFile`, `HookNtSetInformationFile`) calls `crate::classify_handle` which does NOT include volume class in the request. The `classify_path_with_volume_class` function is only used by path-based trampolines. Handle-based operations on USB/optical drives will not have volume class context for ABAC evaluation.

**Fix:** Either extend `classify_handle` to resolve the path from the handle and then look up the volume class, or document this as a known limitation with a TODO. The handle-to-path resolution is non-trivial (requires `NtQueryObject` or `GetFinalPathNameByHandleW`) but should be tracked.

---

### WR-02: `is_write_action` uses `to_ascii_uppercase().as_str()` which allocates unnecessarily

**File:** `dlp-hook-dll/src/trampolines.rs:377-390`
**Issue:** `is_write_action` allocates a new `String` via `to_ascii_uppercase()` on every call, then matches against string literals. This is a hot-path function called for every file operation. The allocation is unnecessary — `eq_ignore_ascii_case` or a custom match on bytes would avoid the heap allocation.

**Fix:**

```rust
fn is_write_action(action: &str) -> bool {
    matches!(
        action.as_bytes(),
        b"CREATE" | b"WRITE" | b"MOVE" | b"COPY" | b"DELETE" | b"REPLACE" | b"SET_INFO" | b"NT_WRITE" | b"NT_SET_INFO"
        | b"create" | b"write" | b"move" | b"copy" | b"delete" | b"replace" | b"set_info" | b"nt_write" | b"nt_set_info"
    )
}
```

Or use `eq_ignore_ascii_case` from `std::ascii::AsciiExt` (unstable) or implement manually.

### WR-03: `map_hook_action_to_abac` also allocates with `to_ascii_uppercase()`

**File:** `dlp-agent/src/hook_ipc.rs:80-88`
**Issue:** Same pattern as WR-02 — `to_ascii_uppercase()` allocates a `String` on every call. This is in the agent's IPC handler, called for every hook request.

**Fix:** Use a case-insensitive match without allocation, or match on the original string with `eq_ignore_ascii_case`:

```rust
pub fn map_hook_action_to_abac(action: &str) -> Action {
    if action.eq_ignore_ascii_case("CREATE") || action.eq_ignore_ascii_case("WRITE") || action.eq_ignore_ascii_case("NT_WRITE") {
        Action::WRITE
    } else if action.eq_ignore_ascii_case("READ") || action.eq_ignore_ascii_case("NT_READ") {
        Action::READ
    } else if action.eq_ignore_ascii_case("COPY") {
        Action::COPY
    } else if action.eq_ignore_ascii_case("MOVE") || action.eq_ignore_ascii_case("DELETE") || action.eq_ignore_ascii_case("REPLACE") || action.eq_ignore_ascii_case("SET_INFO") || action.eq_ignore_ascii_case("NT_SET_INFO") {
        Action::DELETE
    } else {
        Action::READ
    }
}
```

### WR-04: `resolve_volume_class_from_path` does not validate drive letter lookup result

**File:** `dlp-common/src/abac.rs:77-97`
**Issue:** The `resolve_volume_class_from_path` function returns `None` when the `lookup` closure returns `None` for a drive letter path. This is correct fail-closed behavior. However, there is no validation that the `lookup` closure itself is well-behaved (e.g., returns `Some(LocalNTFS)` for all drive letters). The doc comment warns against using `VolumeClass::default()` as a fallback, but there is no runtime enforcement.

**Fix:** This is primarily a documentation/design concern. Consider adding a `debug_assert!` in the lookup path to catch tests that accidentally use `default()` as a fallback. Not a runtime blocker.

---

### WR-05: `VolumeClass::default()` is `LocalNTFS` which contradicts fail-closed invariant

**File:** `dlp-common/src/abac.rs:25-41`
**Issue:** The `VolumeClass` enum derives `Default` with `LocalNTFS` as the default variant. The doc comment explicitly says "NEVER use `VolumeClass::default()` as a fallback for unclassifiable paths" and "`Default` exists only for serde backward compatibility." However, `Default` is a public trait and any code can call `VolumeClass::default()` accidentally. If serde deserializes an unknown/invalid variant, it may use `Default` (depending on serde configuration), which would incorrectly classify unknown drives as `LocalNTFS`.

**Fix:** Remove the `Default` derive from `VolumeClass` and handle serde backward compatibility explicitly. If `Default` must remain for serde, implement it manually and add a `#[deprecated]` attribute to discourage direct use. Alternatively, use a custom serde visitor that returns `None` for unknown variants instead of defaulting.

### WR-06: Integration test `test_hook_ipc_volume_class_mismatch_allow` uses wrong path for T1 classification

**File:** `dlp-agent/tests/volume_class_integration.rs:558-602`
**Issue:** The test uses `r"C:\public\readme.txt"` expecting T1 classification from `PolicyMapper::provisional_classification`. However, `PolicyMapper` uses path prefix matching, and `"C:\public\"` is not in the default sensitive prefixes. The test asserts `!resp.decision.is_denied()` which relies on the mock engine's behavior (not the actual PolicyStore). The test is actually testing the mock handler, not the real policy evaluation pipeline.

**Fix:** The test should either use a real `PolicyStore` with explicit policies (like the other tests in the file), or document that it is testing the mock handler's fallback behavior. The current test name (`test_hook_ipc_volume_class_mismatch_allow`) implies it tests volume-class mismatch allowing the operation, but the allow is actually from the default-allow for T1, not from the policy mismatch.

## Info

### IN-01: `#[allow(dead_code)]` on `build_cache_hint_from_response` suggests incomplete wiring

**File:** `dlp-agent/src/hook_ipc.rs:654-661`
**Issue:** The `build_cache_hint_from_response` function is marked `#[allow(dead_code)]` and its body is a placeholder returning `None`. The comment says "This function is a placeholder for future response-aware cache hint logic." This indicates the cache hint system is not fully wired to use ABAC evaluation responses.

**Fix:** Track this as a follow-up item. The function should be wired into `handle_hook_request` so that cache hints use the actual classification from the ABAC response rather than the legacy path heuristic.

---

### IN-02: `classify_and_log_path` has 300+ lines of cyclomatic complexity

**File:** `dlp-hook-dll/src/trampolines.rs:88-348`
**Issue:** The `classify_and_log_path` function is 260 lines long and contains nested match expressions for `FailState` variants, each with their own cache hit/miss logic. This is a code smell that increases the risk of bugs when modifying the fail-mode logic. The function handles Healthy, Degraded, Isolated, and Resync states with subtly different paths.

**Fix:** Extract state-specific handlers into separate functions (e.g., `handle_healthy`, `handle_degraded`, `handle_isolated`, `handle_resync`). This would improve testability and reduce the risk of introducing bugs in one state when modifying another.

---

### IN-03: `test_volume_class_response_none_fail_closed_semantic` is tautological

**File:** `dlp-common/src/hook_ipc.rs:772-781`
**Issue:** The test `test_volume_class_response_none_fail_closed_semantic` asserts that `resp.class.is_none()` is true when `resp.class` is `None`. This test has no behavioral value — it only verifies that `None` is `None`. The fail-closed semantic is documented in comments but not tested by actual ABAC evaluation.

**Fix:** Replace with a test that actually exercises the fail-closed path: construct an `AbacContext` with `source_volume_class: None`, evaluate against a policy with a `SourceVolumeClass` condition, and assert the condition does not match (policy does not trigger).
