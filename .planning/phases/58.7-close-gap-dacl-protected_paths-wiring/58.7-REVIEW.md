# Phase 58.7: Code Review Report

**Reviewed:** 2026-07-09T02:33:28Z
**Depth:** standard
**Files Reviewed:** 4
**Status:** issues_found

## Summary

Phase 58.7 wires `AgentConfig.protected_paths` through the DACL watcher lifecycle, introduces runtime reinit via `DaclWatcherManager`, and adds agent-side DLP Deny ACE removal under the per-path lock. The implementation is well-structured, but the review found three critical defects: watcher OS threads are leaked on every `Reinit`/shutdown, staged removal rows are not cleared when a path is re-added (which can silently unprotect a path), and `global_enforcement_mode` changes do not trigger reinit so mode transitions do not apply/remove tripwires. Several warnings around path normalization, error handling, and command-channel reliability were also identified.

## Critical Issues

### CR-01: `DaclWatcherBundle::shutdown` never stops watcher OS threads

**File:** `dlp-agent/src/service.rs:2838-2866`
**Issue:** `DaclWatcherBundle::shutdown()` signals and awaits the repair task, poll backstop, GC task, and removal task, but it never calls `watcher.unregister_all()`. The `ReadDirectoryChangesW` OS threads created by `DaclWatcher::register` are therefore detached and continue holding directory handles. On every runtime `Reinit` this leaks threads and handles, and the new bundle registers additional watchers on the same directories, causing duplicate monitoring and resource exhaustion over time.
**Fix:** After awaiting the repair and poll task handles, call `watcher.unregister_all()` to set each watcher thread's shutdown flag and close its directory handle:
```rust
async fn shutdown(mut self) {
    if let Some(tx) = self.removal_shutdown.take() { let _ = tx.send(true); }
    if let Some(tx) = self.gc_shutdown.take() { let _ = tx.send(true); }
    if let Some(tx) = self.watcher_shutdown.take() { let _ = tx.send(true); }
    if let Some(tx) = self.poll_shutdown.take() { let _ = tx.send(true); }

    if let Some(h) = self.removal_handle.take() { let _ = h.await; }
    if let Some(h) = self.gc_handle.take() { let _ = h.await; }
    if let Some(h) = self.watcher_handle.take() { let _ = h.await; }
    if let Some(h) = self.poll_handle.take() { let _ = h.await; }

    if let Some(w) = self.watcher.take() {
        w.unregister_all();
    }
}
```

### CR-02: Staged removal rows are not cleared when a path is re-added

**File:** `dlp-agent/src/service.rs:932-989`, `3319-3400`, `3053-3215`
**Issue:** `apply_payload_to_config` stages removals in SQLite for paths that leave `protected_paths`, but it does not delete those staging rows when a path is later added back. After a `Reinit`, `init_dacl_watcher` re-applies the tripwire to the re-added path and creates a new removal task. The new task reads the old `operation='remove'` row and calls `remove_tripwire_from_path`, unregistering the watcher and leaving the path unprotected even though it is in the current `protected_paths` list.
**Fix:** Either (a) in `apply_payload_to_config`, delete any staging rows whose path is in the computed `additions` set, or (b) in `spawn_removal_application_task`, before applying a removal, check whether the normalized path is still present in `AgentConfig.protected_paths` and, if so, clear the stale staging row instead of removing the tripwire. Option (a) is preferable because it keeps the staging table consistent with config intent:
```rust
// In apply_payload_to_config, after computing additions:
if !additions.is_empty() {
    if let Some(db) = agent_db() {
        if let Err(e) = crate::dacl_staging::clear_staged_removals(db, &additions) {
            tracing::warn!(error = %e, "failed to clear stale staged removals for re-added paths");
        }
    }
}
```

### CR-03: `global_enforcement_mode` changes do not trigger DACL reinit

**File:** `dlp-agent/src/service.rs:1084-1095`, `991-1015`
**Issue:** `signal_dacl_reinit_if_needed` only signals `DaclManagerCommand::Reinit` when `changed_fields` contains `"protected_paths"`. `apply_payload_to_config` detects `global_enforcement_mode` changes and adds `"global_enforcement_mode"` to `changed_fields`, but no reinit is triggered. As a result, switching from `Audit` to `Block` does not apply the DLP Deny ACE tripwires, and switching from `Block` to `Audit` does not remove them, until the next `protected_paths` change or service restart.
**Fix:** Extend `signal_dacl_reinit_if_needed` to also signal reinit on `global_enforcement_mode` changes, because `reinit_dacl_bundle` already reads `global_mode` fresh from config:
```rust
fn signal_dacl_reinit_if_needed(
    changed_fields: &[&str],
    dacl_manager_tx: &Option<tokio::sync::mpsc::Sender<DaclManagerCommand>>,
) {
    if changed_fields.contains(&"protected_paths") || changed_fields.contains(&"global_enforcement_mode") {
        if let Some(ref tx) = dacl_manager_tx {
            if let Err(e) = tx.try_send(DaclManagerCommand::Reinit) {
                warn!(error = %e, "failed to signal DACL watcher reinit from config poll");
            } else {
                info!("signalled DACL watcher reinit from config poll");
            }
        }
    }
}
```

## Warnings

### WR-01: `normalize_protected_path` rejects UNC paths with forward slashes

**File:** `dlp-agent/src/dacl_staging.rs:167-194`
**Issue:** The UNC check `path.starts_with(r"\\")` runs before forward slashes are converted to backslashes. A server-pushed path such as `//server/share/data` is rejected as `NotAbsolute`, even though it is a valid UNC path after normalization.
**Fix:** Perform the slash replacement before the absolute-path check, or add a forward-slash UNC check:
```rust
let normalized = path.replace('/', r"\");
let is_unc = normalized.starts_with(r"\\");
```

### WR-02: `BypassCorrelator::set_protected_paths` does not normalize inputs

**File:** `dlp-agent/src/bypass_correlator.rs:401-416`, `572-579`
**Issue:** `set_protected_paths` stores the provided strings verbatim and relies on callers to normalize them. If a future caller passes unnormalized paths, `is_protected_path` will do string-prefix matching against inconsistent formats, causing false positives or negatives in severity mapping. The method is public, so the contract is not enforced by the type system.
**Fix:** Normalize inside `set_protected_paths` (or document that inputs must already be normalized) and store canonical forms:
```rust
pub fn set_protected_paths(&self, paths: Vec<String>) {
    let normalized: Vec<String> = paths
        .into_iter()
        .filter_map(|p| crate::dacl_staging::normalize_protected_path(&p).ok())
        .collect();
    *self.protected_paths.write() = normalized;
}
```

### WR-03: Failed tripwire removal still marks the staging row applied

**File:** `dlp-agent/src/service.rs:3357-3380`
**Issue:** In `spawn_removal_application_task`, if `remove_tripwire_from_path` fails, the error is logged but the row is still marked applied and the watcher is unregistered. The Deny ACE therefore remains on the path even though config considers it unprotected, and the repair watcher no longer monitors it, so the inconsistency will not self-heal.
**Fix:** Only mark applied and unregister when `remove_tripwire_from_path` succeeds. On failure, leave the row unapplied so the next interval retries, and consider adding a retry/backoff limit rather than a single unconditional attempt:
```rust
match watcher_clone.get_snapshot(&path_clone) {
    Some(snapshot) => {
        match crate::dacl_tripwire::remove_tripwire_from_path(&path_clone, &snapshot) {
            Ok(()) => {
                tracing::info!(path = %row_path, "DLP tripwire removed from path");
                if let Err(e) = staging_clone.mark_applied_locked(&normalized_clone) {
                    tracing::warn!(path = %row_path, error = %e, "failed to mark removal as applied");
                }
                if let Err(e) = watcher_clone.unregister(&path_clone) {
                    tracing::warn!(path = %row_path, error = %e, "failed to unregister watcher");
                }
            }
            Err(e) => {
                tracing::warn!(path = %row_path, error = %e, "failed to remove DLP tripwire; will retry");
            }
        }
    }
    None => {
        tracing::warn!(path = %row_path, "no canonical snapshot found for removed path");
    }
}
```

### WR-04: `try_send` for `Reinit` can silently drop commands

**File:** `dlp-agent/src/service.rs:1086`, `2079`
**Issue:** The DACL manager channel has capacity 4, and `signal_dacl_reinit_if_needed` uses `try_send`. If the manager is slow (e.g., a long `bundle.shutdown().await` during reinit) and multiple config changes occur, the latest `Reinit` can be dropped. Because the config poll loop will see no further diff on the next tick (config already matches the server), the dropped reinit is never retried, leaving the watcher out of sync with the current `protected_paths`.
**Fix:** Use a reliable signalling mechanism for the latest state, such as a `tokio::sync::watch::Sender<Option<ReinitRequest>>` that overwrites the pending command, or retry the last queued command on each poll when `protected_paths` has changed. Alternatively, check in `config_poll_loop` whether the watcher has actually processed the latest config version and re-signal if needed.

## Info

### IN-01: Raw `protected_paths` comparison can cause spurious reinit/staging

**File:** `dlp-agent/src/service.rs:932`, `939-960`
**Issue:** `apply_payload_to_config` uses `cfg.protected_paths != payload.protected_paths` to detect changes. Because the comparison is on raw `ProtectedPathConfig` objects, differences in case or trailing slash that normalize to the same canonical path still trigger `Reinit` and staging activity.
**Fix:** Compare normalized sets instead of raw vectors:
```rust
let old_set: HashSet<String> = cfg.protected_paths.iter().filter_map(|p| normalize_protected_path(&p.path).ok()).collect();
let new_set: HashSet<String> = payload.protected_paths.iter().filter_map(|p| normalize_protected_path(&p.path).ok()).collect();
if old_set != new_set {
    changed_fields.push("protected_paths");
    // ...
}
```

### IN-02: Removal task tests rely on wall-clock sleeps

**File:** `dlp-agent/src/service.rs:6328`, `6388-6390`, `6402`, `6412`
**Issue:** `test_removal_task_removes_tripwire` and `test_removal_task_lock_scope` use `tokio::time::sleep` and `std::thread::sleep` to wait for the removal task to tick. These tests are timing-sensitive and can flake on slow or heavily loaded runners.
**Fix:** Replace sleeps with explicit synchronization, such as a `tokio::sync::watch` channel that the task signals after each poll cycle, or inject a fake clock/ticker into the task for tests.
