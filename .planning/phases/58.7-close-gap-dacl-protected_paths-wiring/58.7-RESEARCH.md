# Phase 58.7: Close gap: DACL protected_paths wiring - Research

**Researched:** 2026-07-08
**Domain:** Rust / Windows NTFS DACL tripwire, agent policy sync, bypass correlation
**Confidence:** HIGH for root-cause and code locations; MEDIUM for the dynamic reinit approach because the agent currently has no runtime re-plumbing for the DACL watcher.

## Summary

The v0.10.0 milestone integration audit found that `dlp-agent` stores server-pushed protected paths in `AgentConfig.protected_paths` but the three enforcement consumers still read from `AgentConfig.monitored_paths` [VERIFIED: codebase, CITED: .planning/milestones/v0.10.0-MILESTONE-AUDIT.md]. The affected consumers are:

1. `init_dacl_watcher` / `init_dacl_watcher_without_staging` (`dlp-agent/src/service.rs:2777, 2927`) — iterates `agent_config.monitored_paths` to apply or remove the Deny ACE tripwire.
2. `BypassCorrelator` construction (`dlp-agent/src/service.rs:2270`) — seeds severity mapping from `agent_config.monitored_paths.clone()`.
3. Classification cache prepopulation (`dlp-agent/src/service.rs:1775`) — feeds T3/T4 roots from `agent_config.monitored_paths`.

`apply_payload_to_config` already diffs `cfg.protected_paths` against `payload.protected_paths`, stages removals in `protected_paths_staging`, and writes the new list to `cfg.protected_paths` [VERIFIED: codebase]. The server-side admin API and repository also already populate `AgentConfigPayload.protected_paths` from `ProtectedPathsRepository::list_all()` [VERIFIED: codebase]. Therefore the gap is purely agent-side wiring: the consumers must switch to `agent_config.protected_paths` (using the `.path` field) and the config-poll loop must reinitialize the watcher/cache when the list changes.

**Primary recommendation:** Change the three consumers to read `agent_config.protected_paths`, add a helper that extracts `Vec<String>` from `Vec<ProtectedPathConfig>`, and extend the config-poll loop so that a `protected_paths` change triggers a controlled restart of the DACL watcher and a cache rebuild. If runtime reinit is out of scope for the urgent fix, document that an agent restart is required after protected-path changes.

### Pattern 1: Extract protected path strings from config

**What:** Convert `Vec<ProtectedPathConfig>` to `Vec<String>` once and pass it to every consumer.

**When to use:** Whenever a subsystem needs the path list (tripwire, watcher, correlator, cache).

**Example:**

```rust
// Source: dlp-agent/src/service.rs (proposed)
let protected_paths: Vec<String> = agent_config
    .protected_paths
    .iter()
    .map(|p| p.path.clone())
    .collect();
```

### Pattern 2: Two-phase staged removal

**What:** On policy sync, removals are staged in SQLite so the repair watcher suppresses tamper alerts while the ACL is legitimately removed.

**When to use:** For every server-driven protected path removal.

**Example:**

```rust
// Source: dlp-agent/src/service.rs:932-970 (already implemented)
if cfg.protected_paths != payload.protected_paths {
    changed_fields.push("protected_paths");
    let old_paths: HashSet<String> = cfg.protected_paths.iter().map(|p| p.path.clone()).collect();
    let new_paths: HashSet<String> = payload.protected_paths.iter().map(|p| p.path.clone()).collect();
    let removals: Vec<String> = old_paths.difference(&new_paths).cloned().collect();
    if !removals.is_empty() {
        if let Some(db) = agent_db() {
            crate::dacl_staging::stage_removals(db, &removals)?;
        }
    }
    cfg.protected_paths = payload.protected_paths.clone();
}
```

### Pattern 3: Global-mode gating

**What:** `should_apply_tripwire_for_global_mode` returns `false` in `Audit` mode and `true` for `Block`, `PerPolicy`, and `AuditAndBlock`.

**When to use:** Before applying or removing Deny ACEs in `init_dacl_watcher`.

**Example:**

```rust
// Source: dlp-agent/src/dacl_tripwire.rs:83-85
pub fn should_apply_tripwire_for_global_mode(global_mode: EnforcementMode) -> bool {
    global_mode != EnforcementMode::Audit
}
```

### Anti-Patterns to Avoid

- **Do not read `monitored_paths` for DACL or bypass decisions.** `monitored_paths` controls the file monitor scope; `protected_paths` controls the tripwire/backstop scope.
- **Do not ignore config-poll `protected_paths` changes.** The current `config_poll_loop` only logs field names; it never reinitializes the watcher or cache.
- **Do not append Deny ACEs incrementally.** Always rebuild the canonical ACL via `apply_tripwire_to_path` / `remove_tripwire_by_rebuilding_without_deny`.
- **Do not log full path values.** The existing code logs field names only (`T-06-09`); keep that behavior.

## Common Pitfalls

### Pitfall 1: Consuming `monitored_paths` instead of `protected_paths`
**What goes wrong:** Admin-created protected paths are ignored by the tripwire, repair watcher, and bypass severity. The milestone audit marks DACL-01..DACL-05 unsatisfied.
**Why it happens:** `AgentConfig` grew a dedicated `protected_paths` field, but the consumer code was left reading `monitored_paths` during earlier incremental phases.
**How to avoid:** Replace every `agent_config.monitored_paths` reference in the DACL/bypass/cache path with `agent_config.protected_paths` mapped to `.path`.
**Warning signs:** UAT F01 fails when a path registered in the admin TUI does not get a Deny ACE; UAT G01 fails when bypass severity on a protected path is `warn` instead of `crit`.

### Pitfall 2: No runtime reinitialization after policy sync
**What goes wrong:** A new protected path pushed by the server does not receive a Deny ACE until the agent restarts.
**Why it happens:** `init_dacl_watcher` is called only once in `run_loop_init`; `config_poll_loop` updates the in-memory config but never restarts the watcher or cache.
**How to avoid:** When `changed_fields` contains `"protected_paths"`, signal shutdown of the existing watcher tasks, call `init_dacl_watcher` with the new config, and call `classification_cache.prepopulate_t3_t4_roots` with the new roots. Store the watcher handles in `RunLoopContext` so they can be replaced.
**Warning signs:** UAT F01 says "wait for policy sync" but the ACE only appears after service restart.

### Pitfall 3: Path case and trailing-slash mismatch
**What goes wrong:** A staged removal row is keyed as `C:\Protected\Test` but the watcher checks against `C:\Protected\Test\`; the tamper alert fires during a legitimate removal.
**Why it happens:** `ProtectedPathConfig.path` may not include a trailing separator, while `monitored_paths` entries often do.
**How to avoid:** Normalize to uppercase with a trailing backslash before staging and before `is_staged` checks, or normalize at the point of diffing.
**Warning signs:** UAT F03 produces a spurious `DaclTamperDetected` after TUI removal.

### Pitfall 4: Applying tripwire in Audit mode
**What goes wrong:** Deny ACEs are written even when the global mode is `Audit`, blocking legitimate access in monitor-only mode.
**Why it happens:** `init_dacl_watcher` already gates on `should_apply_tripwire_for_global_mode`, but any new reinit path must preserve that gate.
**How to avoid:** Always call `should_apply_tripwire_for_global_mode` before applying or removing Deny ACEs.
**Warning signs:** Category H monitor-mode tests fail because writes are blocked.

### Pitfall 5: Removal task does not actually remove the Deny ACE
**What goes wrong:** The path is removed from the config and the watcher is unregistered, but the Deny ACE remains on disk.
**Why it happens:** `spawn_removal_application_task` only calls `staging.mark_applied` and `watcher.unregister`; it assumes the admin API already modified the ACL [VERIFIED: codebase].
**How to avoid:** Verify the server/TUI flow actually removes the ACE. If not, add a call to `remove_tripwire_from_path` before marking applied.
**Warning signs:** UAT F03 passes the "no tamper alert" check but `icacls` still shows the Deny ACE.

## Open Questions

1. **Should policy-sync changes to `protected_paths` trigger immediate DACL watcher/cache reinitialization, or is agent restart acceptable for v0.10.0?**
   - What we know: The UAT scenario F01 says "Wait for policy sync (or restart agent to force sync)", so restart is currently acceptable.
   - What's unclear: Whether the milestone audit expects runtime reinit as part of "wire from policy sync".
   - Recommendation: Implement startup wiring first (smallest change), then add a `protected_paths` change handler in `config_poll_loop` that restarts the watcher and rebuilds the cache if time permits.

2. **Who is responsible for removing the Deny ACE when a protected path is deleted?**
   - What we know: `spawn_removal_application_task` only marks the staging row applied and unregisters the watcher; it does not call `remove_tripwire_from_path` [VERIFIED: codebase].
   - What's unclear: Whether the server-side admin delete handler or the TUI already strips the ACE.
   - Recommendation: Verify the server/TUI delete flow. If it does not remove the ACE, add an agent-side removal step before `mark_applied`.

3. **What path normalization should be authoritative for staging keys and watcher registration?**
   - What we know: `ProtectedPathConfig.path` is a plain string; `monitored_paths` historically used trailing backslashes.
   - What's unclear: Whether the server normalizes paths before storage.
   - Recommendation: Normalize to uppercase with trailing backslash in the agent before diffing, staging, and watcher registration.
