# Cross-AI Plan Review — Phase 58.7

## Claude Code (Self) Review

### Summary

The three plans form a coherent, correctly sequenced fix for the milestone-audit finding that `AgentConfig.protected_paths` exists but the DACL watcher, bypass correlator, and classification cache still consume `AgentConfig.monitored_paths`. Source verification confirms the bug (six references to `monitored_paths` in `dlp-agent/src/service.rs` at lines 1776, 2270, 2777, 2812, 2854, 2927, 2942, 2957) and confirms the target symbols exist with the shapes the plans assume. The wave ordering is sound: Plan 58.7-01 switches the source field and introduces path normalization, Plan 58.7-02 adds runtime reinit, and Plan 58.7-03 closes the removal gap by restoring the original ACL from the stored snapshot. The main risks are (1) a one-time staging-key mismatch for existing rows when normalization is introduced, (2) the size of the Plan 58.7-02 manager refactor touching `RunLoopContext`/`run_loop_shutdown`, and (3) a subtle ordering question in the removal task where `remove_tripwire_from_path` should be attempted before `mark_applied` but after the per-path lock is acquired.

### Strengths

- Root-cause diagnosis is precise and source-verified. `AgentConfig.protected_paths` exists at `dlp-agent/src/config.rs:318` as `Vec<crate::server_client::ProtectedPathConfig>` (`path` field at `dlp-agent/src/server_client.rs:169`), while every DACL/bypass/cache consumer in `service.rs` still reads `monitored_paths`.
- `apply_payload_to_config` already diffs `protected_paths` and stages removals (`dlp-agent/src/service.rs:932-970`), so Plans 01/03 build on an existing correct data path rather than reimplementing it.
- The three plans are correctly wave-ordered: Plan 01 changes return types and adds normalization; Plan 02 depends on the `DaclWatcherBundle` return type; Plan 03 depends on `normalize_protected_path` from Plan 01.
- The threat model is thorough, especially T-58.7-11/T-58.7-14 covering snapshot absence and staging-table spoofing.
- Tests are concrete and tied to specific functions (`test_dacl_watcher_uses_protected_paths`, `test_config_poll_reinit_signal`, `test_removal_task_removes_tripwire`), matching the project's TDD requirement.

### Concerns

- **HIGH — Plan 58.7-01 staging-key migration not addressed.** The plan introduces `normalize_protected_path` and applies it to all staging keys. Existing `protected_paths_staging` rows on deployed agents are keyed by the raw `ProtectedPathConfig.path` string (e.g., `C:\Data`). After the change, `is_staged`/`mark_applied` will look for `C:\DATA\`. Old rows will become unreachable, so staged removals in flight during an upgrade could re-emit `DaclTamperDetected` or leave rows un-GC'd.
  - Evidence: `DaclStaging::stage_removal` currently inserts `path` verbatim (`dlp-agent/src/dacl_staging.rs:244-253`); no normalization happens today.
  - Suggested fix: add a one-shot migration in `DaclStaging::new`/`init_staging_table` that re-keys existing rows with `normalize_protected_path`, or document that agents must be restarted with an empty staging table.

- **MEDIUM — Plan 58.7-02 manager refactor blast radius.** Replacing nine individual `RunLoopContext` DACL fields with `dacl_manager_tx` + `dacl_manager_handle` and rewiring `run_loop_shutdown` is correct but large. Any test or helper that pattern-matches on the old fields will break.
  - Evidence: `run_loop_shutdown` individually stops removal, GC, watcher, and poll handles at `dlp-agent/src/service.rs:4246-4295`; `RunLoopContext` is constructed at `dlp-agent/src/service.rs:2328-2403` with all nine fields.
  - Suggested fix: explicitly list affected test helpers in the plan and add a compile-check task before the functional tests.

- **MEDIUM — Plan 58.7-03 per-path lock ordering.** The plan says the removal task should call `watcher.get_snapshot(&path)`, then `remove_tripwire_from_path`, then `staging.mark_applied`, then `watcher.unregister`. `mark_applied` acquires the per-path lock internally, but `get_snapshot`/`remove_tripwire_from_path` do not. If the repair task concurrently reads the same path's snapshot, the snapshot could be removed by `unregister` before the repair task finishes.
  - Evidence: `DaclStaging::with_path_lock` serializes per-path mutations (`dlp-agent/src/dacl_staging.rs:216-227`), but `DaclWatcher::snapshots` is a separate `Mutex<HashMap>` (`dlp-agent/src/dacl_repair_watcher.rs:123`).
  - Suggested fix: acquire the per-path lock around the entire `get_snapshot` → `remove_tripwire_from_path` → `mark_applied` → `unregister` sequence, or document why `mark_applied` alone is sufficient.

- **MEDIUM — Plan 58.7-02 `BypassCorrelator` RwLock hot-path latency.** `is_protected_path` is called for every ETW file event. Wrapping `protected_paths` in `RwLock<Vec<String>>` is safe but adds a contended read lock on a hot path. With high-volume ETW traffic this could add latency.
  - Evidence: `BypassCorrelator::is_protected_path` is in the correlation hot path (`dlp-agent/src/bypass_correlator.rs`); the plan changes the field to `RwLock<Vec<String>>` and adds `set_protected_paths`.
  - Suggested fix: consider an `ArcSwap<Vec<String>>` or `arc-swap` crate (already common in the codebase?) so readers are wait-free. If `RwLock` is chosen, add a micro-benchmark or latency test.

- **LOW — Plan 58.7-01 `normalize_protected_path` Windows path edge cases.** The plan normalizes to uppercase with a trailing backslash. It does not explicitly reject relative paths, `..`, or forward slashes in the middle of a path. A server-pushed `..\Secret` could escape the intended root.
  - Evidence: The research notes path-traversal as a known threat pattern but the plan's normalization helper is purely string-based.
  - Suggested fix: add a validation step in `normalize_protected_path` or in `apply_payload_to_config` that rejects non-absolute paths and `..` segments before staging/applying.

- **LOW — Plan 58.7-02 runtime reinit does not re-apply tripwire to added paths immediately.** The manager calls `init_dacl_watcher`, which applies tripwires during reinit. However, `apply_payload_to_config` logs "will apply on next watcher init" for additions. If the manager reinit races with the initial startup reinit, additions are handled, but the plan should state that the manager is the *only* path for runtime application.
  - Evidence: `apply_payload_to_config` at `dlp-agent/src/service.rs:962-968` logs additions as deferred; Plan 02 is the mechanism that makes that deferral immediate.
  - Suggested fix: clarify in Plan 02 that the `Reinit` command is the runtime application path for additions, not just removals/cache rebuilds.

### Suggestions

1. Add a migration/cleanup task for existing staging rows when `normalize_protected_path` is introduced (HIGH concern above).
2. Add a compile-only check task to Plan 58.7-02 before functional tests, because the `RunLoopContext` field change is structural.
3. In Plan 58.7-03, explicitly state the lock scope for the entire removal sequence or add a test that exercises concurrent repair/removal on the same path.
4. Document whether `BypassCorrelator` dynamic updates are expected to be rare (policy sync) or frequent; if frequent, evaluate `ArcSwap`.
5. Add a negative test to Plan 58.7-01 that verifies a server-pushed relative/traversal path is rejected before reaching `SetFileSecurityW`.
6. Consider collapsing `init_dacl_watcher` and `init_dacl_watcher_without_staging` return types to `Option<DaclWatcherBundle>` so the `empty()` bundle pattern is consistent.

### Risk Assessment

**MEDIUM-HIGH.** The plans correctly identify and sequence the fix, and the target symbols exist as assumed. The HIGH concern around staging-key migration is fixable with a small added task. The MEDIUM concerns (manager refactor blast radius, removal-task lock ordering, correlator hot-path lock) are manageable but need explicit attention during execution. If these are addressed, the phase should close the milestone audit finding cleanly.
