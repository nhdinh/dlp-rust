# Phase 58.2: Fix double HookIpcServer and wire volume classes - Context

**Gathered:** 2026-06-24
**Status:** Ready for planning

## Phase Boundary

Eliminate the duplicate `HookIpcServer` initialization in `dlp-agent` and complete the wiring of `source_volume_class` / `destination_volume_class` from the hook DLL through the agent's ABAC evaluation path so volume-class policies enforce correctly for hook-intercepted file operations.

## Implementation Decisions

### Server consolidation

- **D-01:** There must be exactly one `HookIpcServer` per agent lifecycle. Replace the two independent initializations (`spawn_hook_ipc_server` and the inline block in `run_loop_init`) with a single builder path.
- **D-02:** Introduce a `HookIpcServerConfig` struct that carries all dependencies needed to build the server: classification cache, `OfflineManager`, `bypass_tx`, diagnostic aggregator, health aggregator, override sender, and approval cache. `run_loop_init` assembles the config; the builder function constructs the server.
- **D-03:** The consolidated server uses `HookIpcServer::with_cache_offline_and_bypass` for the real ABAC handler and chains `.with_diagnostics_handler`, `.with_health_handler`, and `.with_override_handler` so the DIFF-01/02/04 handlers are not lost.
- **D-04:** Preserve the existing DIFF-01 approval-cache override behavior on the hook path: resolve the caller SID, build an `ApprovalCacheKey`, and return the cached decision if present; otherwise run full offline ABAC evaluation.
- **D-05:** Track the consolidated server thread handle only in `RunLoopContext::hook_ipc_handle`. Remove the duplicate `BlockingThreads::hook_ipc` field and its join path; the existing `run_loop_shutdown` pipe-close + join logic remains the single shutdown mechanism.

### Volume class wiring

- **D-06:** Forward both `source_volume_class` and `destination_volume_class` from `HookRequest` into `EvaluateRequest` unchanged.
- **D-07:** Add a private `hook_request_to_evaluate_request` helper in `dlp-agent/src/service.rs` that converts the hook action string to an ABAC `Action`, builds the `Subject` from the resolved caller SID, and copies the volume class fields.
- **D-08:** Leave `agent`, `source_application`, `destination_application`, `source_origin`, and `destination_origin` as `None`; `HookRequest` does not carry them and populating them is out of scope for Phase 58.2.
- **D-09:** Rely on the existing fail-closed `PolicyStore` behavior where `None` volume class values never match a volume-class condition. Log a `warn!` when a `COPY`/`MOVE` request has a `None` source or destination volume class to surface potential hook DLL classification gaps.

### Identity resolution

- **D-10:** Resolve the subject SID from `req.pid` using the existing `get_process_user_sid` helper (or a thin `get_caller_sid` wrapper).
- **D-11:** If PID → SID resolution fails (process exited, access denied, `pid = 0`), return `DENY` with reason `"identity resolution failed"`.
- **D-12:** Add a `#[cfg(not(windows))]` stub for the PID → SID helper so the agent module compiles and tests run on non-Windows targets.

### Test and verification strategy

- **D-13:** Unit test `hook_request_to_evaluate_request` with injected SIDs and volume classes to verify action mapping and field forwarding.
- **D-14:** Make `hook_request_to_evaluate_request` take a resolved `caller_sid: String` so identity resolution can be tested separately from conversion.
- **D-15:** Add an integration test that constructs the consolidated server on a unique pipe name and verifies that `Request`, `PullDiagnostics`, `PullHealth`, and `RequestOverride` frames route to the correct handlers. Assert that only one server thread is created.
- **D-16:** Extend `dlp-agent/tests/volume_class_integration.rs` to exercise the consolidated server end-to-end and assert `ALLOW`/`DENY` decisions based on `source_volume_class` / `destination_volume_class`. Keep the existing `PolicyStore` unit tests as regression guards.

### Claude's Discretion

- The exact name and field layout of `HookIpcServerConfig` are left to the implementer; the key requirement is that `run_loop_init` stays slim and all hook-IPC construction is grouped.
- The `warn!` for missing volume classes on `COPY`/`MOVE` may be elevated to an audit event in a future phase if operational experience shows it is useful.

## Existing Code Insights

### Reusable Assets
- `HookIpcServer::with_cache_offline_and_bypass` — production constructor that combines cache-aware wrapper, offline handler, and bypass channel. This is the natural base for the consolidated server.
- `HookIpcServer::with_diagnostics_handler`, `with_health_handler`, `with_override_handler` — builder methods that attach the DIFF-02/04 handlers without changing the core accept loop.
- `OfflineManager::offline_decision` — synchronous ABAC evaluator used by the production hook handler.
- `get_process_user_sid` in `service.rs` — existing Windows-only PID → SID helper used by the duplicate inline server.
- `ApprovalCache` and `ApprovalCacheKey` — already available in `run_loop_init` and can be passed through `HookIpcServerConfig`.

### Established Patterns
- `RunLoopContext` owns long-lived subsystem handles and `run_loop_shutdown` closes the named pipe from a client handle to unblock `ConnectNamedPipeW`.
- `BlockingThreads` owns pre-tokio blocking threads joined by `run_service` after `run_loop` returns; the hook-IPC thread currently exists in both `BlockingThreads` and `RunLoopContext`, which is the duplication to remove.
- The cache-aware handler in `handle_hook_request` never uses the cache to bypass ABAC authority; it only detects stale DLLs and returns cache-version metadata.
- `PolicyStore` treats `None` volume class as a non-match (fail-closed), so forwarding `None` is safe.

### Integration Points
- The hook DLL sends `HookRequest` frames over the named pipe; these already contain `source_volume_class` and `destination_volume_class`.
- The agent's handler must convert `HookRequest` → `EvaluateRequest` → `OfflineManager::offline_decision`.
- Diagnostics/health/override handlers route into the same `DiagnosticAggregator`, `HealthAggregator`, and `override_tx` infrastructure built in Phase 58.
- `run_loop_shutdown` will close the single consolidated pipe and join the single thread handle stored in `RunLoopContext`.

## Specific Ideas

- Name the new builder `spawn_hook_ipc_server(config: HookIpcServerConfig) -> Option<std::thread::JoinHandle<()>>` to keep the existing call site stable while expanding its inputs.
- Use a unique pipe name in integration tests (not `DEFAULT_PIPE_NAME`) so tests can run without interfering with a live service or each other.
- The consolidated handler closure should read: resolve caller SID → check approval cache → build `EvaluateRequest` via `hook_request_to_evaluate_request` → call `offline.offline_decision` → return `HookResponse`.
