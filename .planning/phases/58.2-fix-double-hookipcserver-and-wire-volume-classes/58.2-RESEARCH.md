# Phase 58.2: Fix double HookIpcServer and wire volume classes - Research

**Researched:** 2026-06-24
**Domain:** Rust / Windows named-pipe IPC / ABAC policy enforcement / DLP agent service lifecycle
**Confidence:** HIGH

## Summary

Phase 58.2 eliminates two independent `HookIpcServer` initializations in `dlp-agent/src/service.rs` and completes the volume-class attribute wiring from the hook DLL through the agent's ABAC evaluation path. The duplication is a clear bug: one server is spawned in `spawn_hook_ipc_server` (lines 1208-1290) with real offline ABAC evaluation but no diagnostics/health/override handlers; a second is constructed inline inside `run_loop_init` (lines 1837-1929) with DIFF-01/02/04 handlers but a stub ALLOW handler that skips real ABAC. Both listen on the same `DEFAULT_PIPE_NAME`, creating a race for the named pipe and leaving enforcement partially broken.

The fix introduces a `HookIpcServerConfig` struct that carries all dependencies (classification cache, `OfflineManager`, `bypass_tx`, diagnostic aggregator, health aggregator, override sender, approval cache) so `run_loop_init` assembles the config and a single builder function constructs the consolidated server. The consolidated server uses `HookIpcServer::with_cache_offline_and_bypass` as its base and chains `.with_diagnostics_handler`, `.with_health_handler`, and `.with_override_handler` so no DIFF handlers are lost.

Volume-class wiring is straightforward: `HookRequest` already carries `source_volume_class` and `destination_volume_class` (added in Phase 56.1). The new `hook_request_to_evaluate_request` helper maps the hook action string to an ABAC `Action`, builds the `Subject` from the resolved caller SID, and copies both volume class fields into `EvaluateRequest`. The existing `From<EvaluateRequest> for AbacContext` conversion (dlp-common/src/abac.rs lines 536-571) already forwards these fields, and `PolicyStore::evaluate` already implements `SourceVolumeClass`/`DestinationVolumeClass` conditions with fail-closed semantics (`None` never matches). No changes are needed in dlp-server or dlp-common.

**Primary recommendation:** Replace both `spawn_hook_ipc_server` and the inline `run_loop_init` block with a single `HookIpcServerConfig`-based builder, remove `BlockingThreads::hook_ipc`, and add `hook_request_to_evaluate_request` with unit and integration tests.

### Pattern 1: HookIpcServerConfig Builder

**What:** A struct that carries all dependencies needed to build a fully configured `HookIpcServer`. `run_loop_init` fills it; `spawn_hook_ipc_server` consumes it.

**When to use:** Any subsystem that needs multiple dependencies wired into a builder chain.

**Example:**
```rust
// Source: CONTEXT.md D-02 / D-03
pub struct HookIpcServerConfig {
    pub pipe_name: String,
    pub cache: Arc<dyn crate::hook_ipc::CacheAccessor>,
    pub offline: Arc<crate::offline::OfflineManager>,
    pub bypass_tx: crossbeam_channel::Sender<dlp_common::hook_ipc::BypassAlert>,
    pub diagnostic_aggregator: Arc<crate::diagnostic_aggregator::DiagnosticAggregator>,
    pub health_aggregator: Arc<crate::health_aggregator::HealthAggregator>,
    pub override_tx: tokio::sync::mpsc::Sender<dlp_common::hook_ipc::OverrideRequest>,
    pub approval_cache: Arc<crate::approval_cache::ApprovalCache>,
}

fn spawn_hook_ipc_server(config: HookIpcServerConfig) -> Option<std::thread::JoinHandle<()>> {
    let diag = Arc::clone(&config.diagnostic_aggregator);
    let health = Arc::clone(&config.health_aggregator);
    let override_tx = config.override_tx.clone();
    let approval = Arc::clone(&config.approval_cache);
    let offline = Arc::clone(&config.offline);
    let cache = Arc::clone(&config.cache);

    let server = crate::hook_ipc::HookIpcServer::with_cache_offline_and_bypass(
        config.pipe_name,
        cache,
        Arc::new(move |req: dlp_common::HookRequest| {
            // ... handler body using offline, approval, etc.
        }),
        config.bypass_tx,
    )
    .with_diagnostics_handler(Arc::new(move |req| { /* ... */ }))
    .with_health_handler(Arc::new(move |_req| { /* ... */ }))
    .with_override_handler(Arc::new(move |req| { /* ... */ }));

    std::thread::Builder::new()
        .name("hook-ipc".into())
        .spawn(move || {
            if let Err(e) = server.run() {
                tracing::error!(error = %e, "Hook IPC server exited with error");
            }
        })
        .ok()
}
```

### Pattern 2: hook_request_to_evaluate_request

**What:** Pure conversion function from `HookRequest` to `EvaluateRequest`. Takes a resolved `caller_sid: String` so identity resolution is testable separately.

**When to use:** Any time an IPC wire type needs to be converted into an ABAC evaluation type.

**Example:**
```rust
// Source: CONTEXT.md D-07 / D-14
fn hook_request_to_evaluate_request(req: &dlp_common::HookRequest, caller_sid: String) -> dlp_common::EvaluateRequest {
    let action = map_hook_action_to_abac(&req.action);
    dlp_common::EvaluateRequest {
        subject: dlp_common::Subject {
            user_sid: caller_sid,
            ..Default::default()
        },
        resource: dlp_common::Resource {
            path: req.path.clone(),
            ..Default::default()
        },
        environment: dlp_common::Environment::default(),
        action,
        agent: None,
        source_application: None,
        destination_application: None,
        source_origin: None,
        destination_origin: None,
        source_volume_class: req.source_volume_class,
        destination_volume_class: req.destination_volume_class,
    }
}

fn map_hook_action_to_abac(action: &str) -> dlp_common::Action {
    match action.to_ascii_uppercase().as_str() {
        "READ" | "NT_READ" => dlp_common::Action::READ,
        "WRITE" | "CREATE" | "NT_WRITE" => dlp_common::Action::WRITE,
        "COPY" => dlp_common::Action::COPY,
        "DELETE" | "MOVE" | "RENAME" | "REPLACE" | "SET_INFO" | "NT_SET_INFO" => dlp_common::Action::DELETE,
        _ => dlp_common::Action::READ,
    }
}
```

### Anti-Patterns to Avoid

- **Do NOT keep two `HookIpcServer` instances.** Both `spawn_hook_ipc_server` and the inline `run_loop_init` block create a listener on `DEFAULT_PIPE_NAME`. The second `CreateNamedPipeW` will fail with `ERROR_PIPE_BUSY` (231) or silently shadow the first, leaving the real ABAC handler unreachable.
- **Do NOT default `None` volume class to `LocalNTFS`.** The fail-closed invariant (Phase 56) requires `None` to remain `None` so `SourceVolumeClass`/`DestinationVolumeClass` conditions evaluate to `false`. Defaulting to `LocalNTFS` would incorrectly allow operations that should be blocked.
- **Do NOT call `get_process_user_sid` inside `hook_request_to_evaluate_request`.** The helper must remain pure and testable; identity resolution belongs in the handler closure so the helper can be unit-tested with injected SIDs.
- **Do NOT forget to remove `BlockingThreads::hook_ipc`.** The duplicate field and its join path in `shutdown_and_join` must be deleted to prevent a double-join attempt on shutdown.

| Problem | Don't Build | Use Instead | Why |

## Common Pitfalls

### Pitfall 1: Duplicate named-pipe listener causes `ERROR_PIPE_BUSY`
**What goes wrong:** Two `HookIpcServer` instances call `CreateNamedPipeW` on the same name. The second fails or shadows the first, causing hook DLL connections to route to the wrong handler (stub ALLOW instead of real ABAC).
**Why it happens:** `spawn_hook_ipc_server` was added in Phase 53/56.1 for real ABAC evaluation, but the inline block in `run_loop_init` (Phase 58) was never removed.
**How to avoid:** Delete the inline block entirely; route all construction through the single `spawn_hook_ipc_server` builder.
**Warning signs:** Hook DLL logs show `ALLOW` for operations that should be `DENY`; `run_loop_init` logs "Hook IPC server started" twice.

### Pitfall 2: Forgetting to chain `.with_diagnostics_handler` / `.with_health_handler` / `.with_override_handler`
**What goes wrong:** The consolidated server uses `with_cache_offline_and_bypass` but never attaches the DIFF-02/04 handlers. Diagnostics/health/override requests from the hook DLL are silently dropped or return empty defaults.
**Why it happens:** The inline block currently chains these builders; the `spawn_hook_ipc_server` function does not.
**How to avoid:** Ensure the builder chain in `spawn_hook_ipc_server` includes all three `.with_*` calls.
**Warning signs:** Admin TUI Diagnostic List and Self-Health Dashboard show no data; override requests from hook DLL are not forwarded to the UI.

### Pitfall 3: `BlockingThreads::hook_ipc` double-join on shutdown
**What goes wrong:** If both `BlockingThreads` and `RunLoopContext` hold the same `JoinHandle`, `shutdown_and_join` may attempt to join it, then `run_loop_shutdown` joins it again, causing a panic or hang.
**Why it happens:** The handle is currently stored in both places.
**How to avoid:** Remove the `hook_ipc` field from `BlockingThreads` and its join path. Rely solely on `RunLoopContext::hook_ipc_handle` and the existing `run_loop_shutdown` pipe-close + join logic.
**Warning signs:** Service shutdown hangs at "joining hook-ipc thread" for >10s.

### Pitfall 4: `get_process_user_sid` fails for `pid = 0` or exited processes
**What goes wrong:** `OpenProcess` returns `ERROR_INVALID_PARAMETER` for `pid = 0`, or `ERROR_ACCESS_DENIED` for elevated processes. The handler must not panic or return `ALLOW`.
**Why it happens:** `HookRequest::pid` defaults to `0` for old hook DLLs or when the PID could not be captured.
**How to avoid:** Return `None` from `get_process_user_sid` when any step fails; the handler closure returns `DENY` with reason `"identity resolution failed"`.
**Warning signs:** `warn!(pid = 0, "failed to resolve process SID")` appears in logs; hook DLL receives `ALLOW` for blocked operations.

### Pitfall 5: Non-Windows compilation fails because `get_process_user_sid` is Windows-only
**What goes wrong:** `dlp-agent` unit tests and CI runners may run on Linux/macOS. The `#[cfg(windows)]` gate on `get_process_user_sid` causes compilation errors in the handler closure.
**Why it happens:** The handler closure calls `get_process_user_sid` unconditionally.
**How to avoid:** Add a `#[cfg(not(windows))]` stub that returns `Some("S-1-5-18-test".to_string())` or similar placeholder so the module compiles and tests run.
**Warning signs:** `cargo test --workspace` fails on non-Windows targets with "unresolved import" or "function not found".

## Open Questions

1. **Should `hook_request_to_evaluate_request` also populate `agent` (machine_name / current_user)?**
   - What we know: `EvaluateRequest::agent` is `AgentInfo` used for request tracing, not ABAC attributes. The existing `spawn_hook_ipc_server` sets it to `None`.
   - What's unclear: Whether the offline manager or audit emitter needs `agent` populated for SIEM routing.
   - Recommendation: Leave `agent` as `None` per CONTEXT.md D-08; populate it in a future phase if needed.

2. **What is the correct `Action` mapping for `NT_SET_INFO` and `REPLACE`?**
   - What we know: The existing `spawn_hook_ipc_server` maps `MOVE | RENAME` to `Action::MOVE`, but the integration test `test_map_hook_action_to_abac_all_variants` expects `MOVE` to map to `Action::DELETE`.
   - What's unclear: Whether the existing mapping or the test expectation is correct.
   - Recommendation: Align with the integration test (which is the newer, more comprehensive test) and map `MOVE`/`RENAME` to `Action::DELETE` if that is the established convention; otherwise fix the test. This must be resolved during implementation.

3. **Does `HookIpcServer::with_approval_cache` need to be added to `hook_ipc.rs` lib code?**
   - What we know: The constructor exists only in `hook_ipc.rs` unit tests (line 1438) but is not part of the public `HookIpcServer` API.
   - What's unclear: Whether the consolidated server should use `with_approval_cache` or pass the approval cache through the handler closure.
   - Recommendation: Pass `Arc<ApprovalCache>` through `HookIpcServerConfig` and use it inside the handler closure; no need to add `with_approval_cache` to the public API unless the cache-aware wrapper in `handle_hook_request` needs it.
